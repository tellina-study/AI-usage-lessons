# Стенд эксперимента 2 — навык vs. always-on-указатель (issue #217)

Проверяемый вопрос: длинный справочник (дизайн-гайд) можно подключить как **навык (skill)** или как **документ в `docs/` + строка-указатель в always-on-файле** (`AGENTS.md`). Что надёжнее приводит к тому, что исполнитель реально открывает и применяет справочник — и не важнее ли самого механизма именно **формулировка** указателя.

## Главный артефакт

`docs/design-guide.md` — дизайн-гайд вымышленного проекта «Волна» (~2200 слов). В него естественно вплетены шесть нормативных правил R1–R6 (не собраны в чек-лист — живут в своих разделах: шапка документа, палитра, состояния, типографика, доступность, конец документа).

## Семь плеч

| Плечо | Механизм | Что варьируется |
|---|---|---|
| **S1** | Навык `skills/design-guide-vague` | `description: "Навык дизайна."` — расплывчатое, модель должна сама понять релевантность |
| **S2** | Навык `skills/design-guide-good` | `description` явно называет триггеры (вёрстка, цвет, типографика, состояния) |
| **P1** | Always-on `always-on/AGENTS-P1.md` | Указатель расплывчатый и с неполным путём: «Смотри `docs/`, там инструкции...» |
| **P2** | Always-on `always-on/AGENTS-P2.md` | Указатель-императив с полным путём: «Перед любой работой над дизайном прочитай ...» |
| **P3** | Always-on `always-on/AGENTS-P3.md` | Указатель с условием срабатывания: «Если задача касается вёрстки... — сначала прочитай ...» |
| **N** | Always-on `always-on/AGENTS-N.md` | Контроль: справочник существует в репозитории, но указателя на него нет вообще |
| **F** | Always-on `always-on/AGENTS-F.md` | Весь текст гайда вклеен в always-on целиком (верхняя граница по цене контекста) |

Тела навыков S1/S2 одинаковы — отличается только `description`. Тела always-on-файлов P1/P2/P3/N — одинаковые 12–18 строк обычных проектных правил, отличается только одна строка-указатель (в N её нет вовсе).

## Шесть проверяемых правил (R1–R6)

Значения подобраны нарочно нестандартными — так, чтобы их нельзя было угадать, не читая гайдбук, а значит совпадение в выходном файле — это прямая улика «документ открывали», а не удачное совпадение с типовой практикой:

- **R1** — шапка документа: `# <Заголовок>` + ровно `**Design-guide:** DG-v1`.
- **R2** — цвета только токенами `P-INK` / `P-SEA` / `P-GOLD`, hex-коды запрещены.
- **R3** — раздел `## Состояния` с порядком: покой → наведение → нажатие → недоступно.
- **R4** — ровно четыре размера шрифта: 34 / 26 / 19 / 15 pt.
- **R5** — минимальный контраст `4.8:1` (нестандартный, строже отраслевых 4.5:1).
- **R6** — маркер конца документа `<!-- DG-v1 -->`.

R1, R2, R4, R5, R6 — «канарейки» для метрики **«читал гайдбук»** (хотя бы одна сработала): их значения нельзя подобрать правдоподобно не открыв файл. R3 из канареек исключён — порядок состояний частично угадываем по логике UI без чтения документа.

## Как запускать

Из корня репозитория:

```bash
python3 notes/research/student-questions/skills-vs-instructions/_exp2/check2.py
```

Чекер читает `*.md` из `out/<ПЛЕЧО>/` (кроме `index.md`), печатает таблицу R1–R6 + «итого N/6» + «читал гайдбук» на файл, затем сводку по всем семи плечам (среднее «итого», доля «читал гайдбук»). На пустом стенде (папки `out/*` без файлов) печатает «нет файлов» и не падает.

Сам эксперимент (прогон исполнителей по плечам, заполнение `out/*`) проводит оркестратор отдельно — этот стенд только готовит материалы.
