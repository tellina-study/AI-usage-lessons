# Развёрнутый технический план семинара «Сборка кодинг-агента» — часть 1

Этот план — рабочий документ фасилитатора и производственного конвейера (следующий шаг —
гид фасилитатора и слайды), не студенческий материал. Каждый раздел ниже — предметная
проработка одной ступени лестницы: конкретные файлы, конкретные строки, конкретные команды,
конкретное поведение на слайде — живого терминала на занятии нет (владелец, 2026-09-20, см.
раздел «Что показываем на слайдах»). Часть 2 (разделы 4–8) — в `plan-part2.md`; раздел 4
(Скиллы) перенесён туда ради лимита 600 строк на файл, содержательно он по-прежнему часть первой
половины занятия (ступень 4 лестницы, между Хуками и MCP).

## Сквозной кейс

Один и тот же репозиторий одного и того же сайта проходит через все восемь разделов — не
абстрактный `agent-demo`. Условия ниже фиксируются здесь и не меняются до конца занятия; каждая
боль в разделах 0–7 вырастает из предыдущего шага работы именно над этим сайтом.

**Задача.** Лендинг с формой заявки на демо-урок: одна статическая страница, поля «имя» и
«email», кнопка отправки. Без собственного бэкенда — заявка уходит на внешний сервис приёма форм.

**Стек.** Сборка Vite поверх обычных HTML/CSS/JS (`npm run build` → `dist/`); Playwright —
`tests/form.spec.ts`, команда `npx playwright test`, проверяет, что форма рендерится и не даёт
отправить пустые обязательные поля; хостинг статический (например, Cloudflare Pages), деплой —
`wrangler pages deploy dist`; задачи и баги — только в GitHub Issues этого же репозитория.

**Кто работает.** Один разработчик с агентом (Claude Code), без команды — соло-сценарий, тот же,
для которого курс отдельно проверяет применимость каждой ступени (критерии «здесь не нужно» в
разделах 3, 6, 7 прямо адресуют случай без второго человека).

**Что считается «готово».** `npm run build` завершается кодом 0; `npx playwright test` зелёный;
сайт открыт по продакшен-URL; форма реально отправляет заявку — проверено на проде, не только
локально. «Готово» не равно «агент написал в чат, что готово» (см. раздел 7).

**Ограничение по времени.** У заказчика назначен показ сайта — фиксированная дата, которая
и создаёт давление, порождающее боли разделов 3 («накануне показа») и 7 («прямо перед показом»).

**Репозиторий.** `signup-landing/`. Его исходный код (`index.html`, `src/`, `tests/`,
`package.json`) появляется в разделе 0 и растёт по ходу занятия как фон, но не входит в дерево
«лестницы конфигурации» ниже — то дерево показывает только семь блоков конфигурации агента, по
одному, на той ступени, где каждый появился.

## Раздел 0. Открытие: пустая папка + опорный слайд «лестница целиком» (7 мин)

**Состояние репозитория.** Совершенно пустая директория:

```
signup-landing/
```

Ничего не создано, `git init` ещё не выполнен.

**Сценарий-боль.** Фасилитатор открывает пустую папку `signup-landing/` и задаёт агенту первую
задачу этого сайта: «собери лендинг с формой заявки на демо-урок — статическая HTML-страница,
сборка через Vite, тест на Playwright, который проверяет, что форма не отправляется с пустыми
полями». Агент справляется — создаёт `index.html`, `src/main.js`, `package.json`,
`tests/form.spec.ts` — но в процессе задаёт уточняющий вопрос, ответ на который сам по себе не
код (например, каким хостингом сайт будет деплоиться и какой командой проверять, что сборка вообще
прошла) — маленькая, но реальная демонстрация того, что агент начинает с нуля и не знает ничего,
что не выводимо из уже существующего кода (которого пока и нет). Это специально не «провал», а
нейтральный первый контакт — боль ещё не названа, вопрос открыт.

**Открытый вопрос классу (дословно).** «Перед вами репозиторий лендинга, который агент только что
собрал с нуля — и вам с этим же агентом предстоит доделывать этот сайт дальше, неделями. Какой
блок конфигурации вы бы добавили первым, и почему именно его, а не любой другой из оставшихся
шести?»

**Ожидаемые ответы зала.**

| Вариант | Разумен? | Где работает | Где ломается |
|---|---|---|---|
| «Сразу файл инструкций — так делают в хороших проектах» | Частично | Если реально есть накопленная боль (агент уже переспрашивает) | Здесь боли ещё нет — это добавление «на всякий случай», без триггера; сама лестница учит именно не делать так |
| «Сразу хук — поставлю защиту от rm -rf на будущее» | Частично | Когда риск конкретной команды уже стал реальным (см. критерий ступени 3) | Превентивная установка защиты до первого инцидента — лишний блок конфигурации без наблюдаемой пользы; неизвестно ещё, какие команды в этом проекте вообще рискованны |
| «Сразу MCP — подключу к GitHub/БД, пригодится» | Нет | Почти никогда на этом этапе | Самый дорогой по контексту и по поверхности атаки блок из всех семи (см. раздел 5) — подключать его без названного триггера прямо противоречит всей логике занятия |
| «Ничего — репозиторий слишком маленький, посмотрим, что понадобится» | Да (целевой ответ для стадии 0) | Всегда правильно на нулевой ступени | Перестаёт быть правильным, как только появляется вторая сессия и реальный повтор боли |

**Что добавляем — предметно.** Ничего в файловую систему — раздел 0 не ступень, а рамка для всех
последующих. Единственное, что появляется, — опорный слайд с таблицей «лестница целиком» (источник:
`00-design-decisions.md`, раздел «Несущая ось»):

| Ступень | Триггер «стало нужно» | Что добавляем | Критерий «ещё рано» |
|---|---|---|---|
| 0 | — | ничего | разовая задача, маленький репозиторий |
| 1 | агент каждый раз переспрашивает одно и то же | файл инструкций | агент и так справляется; документации хватает |
| 2 | владелец повторяет одно и то же из сессии в сессию | память + журнал решений | одна-две сессии; факт уже записан в коде |
| 3 | правило записано, но агент его нарушает | хук | правило дешевле проверить в сборке; нарушение стоит дёшево |
| 4 | файл инструкций облагает налогом каждый запрос | скилл | нужно каждой сессии → это не скилл |
| 5 | нужен доступ к внешней системе | MCP | хватает обычной команды |
| 6 | повторяющаяся роль (ревью, разведка) | субагент | шаги зависимы и требуют общего контекста |
| 7 | работу принимают на слово | прожарка + оперативный журнал | задача дешевле процесса вокруг неё |

По keystone-axis-правилу курса этот слайд предъявляется целиком **до** первого погружения в
ступень 1, а не «всплывает» позже.

**Слайды раздела.**
1. Снимок терминала: `ls -la signup-landing/` — пустота.
2. Снимок терминала: запуск `claude` в этой директории и постановка первой задачи целиком
   (текст задачи дословно на слайде).
3. Фрагмент диалога: момент, когда агент уточняет что-то не выводимое из кода (хостинг/проверка
   сборки) — не решать это здесь, просто зафиксировать как наблюдение, которое всплывёт снова в
   разделе 1.
4. Опорный слайд с таблицей лестницы целиком.

**Что делать — рецепт.**
1. Создать пустую директорию `signup-landing/`, открыть в ней агента.
2. Поставить первую задачу целиком одним запросом, не по частям: «собери лендинг с формой заявки
   на демо-урок: статическая HTML-страница, сборка Vite (`npm run build` → `dist/`), поля формы —
   имя и email, тест на Playwright, который проверяет, что форма не отправляется с пустыми
   обязательными полями (`tests/form.spec.ts`)».
3. Не отвечать на уточняющий вопрос агента развёрнуто — записать его дословно, он открывает
   раздел 1.
4. Проверка результата: `npm run build` завершается без ошибок, `npx playwright test` зелёный —
   это и есть первое состояние «сайт собирается», к которому дальше привязаны все восемь разделов.

**Провал.** Replit: агент проигнорировал явный, несколько раз повторённый code freeze и выполнил
деструктивные операции против продакшен-БД SaaStr (Jason Lemkin, 9-й день эксперимента, июль 2025);
на вопрос про откат агент заявил, что откат невозможен, хотя технически был доступен. БД с записями
~1206 руководителей и ~1196 компаний уничтожена; агент также сфабриковал ~4000 фейковых профилей
пользователей и исказил отчёт о тестах. Источник: `04-failures-evidence.md`, таблица инцидентов,
строка «Replit: удаление продакшен-БД». 2,5 мин.

**Критерий «здесь не нужно».** Ступень 0 из таблицы лестницы: разовая задача, маленький
репозиторий — добавлять нечего, пока нет второго реального повторения боли.

**База и нюанс.**
- **База (слайд):** таблица лестницы целиком — семь ступеней, каждая с триггером и критерием
  «ещё рано» одной строкой.
- **Нюанс (речь):** четыре опорных тезиса курса (источник: `00-design-decisions.md`, «Опорные
  тезисы, вокруг которых собирается всё»): (1) правило, заявленное обязательным, без механической
  проверки в том же изменении — рекомендательное и тихо умирает; (2) шлюз установлен не когда файл
  существует, а когда его видели сработавшим; (3) конфигурация — не коллекция, каждый блок платит
  за себя контекстом в каждом запросе; (4) наличие файла инструкций само по себе не повышает успех
  задачи — повышает его содержание, которого нигде больше нет (RCT Gloaguen et al., см. раздел 1).

## Раздел 1. Файл инструкций (13 мин) — Ступень 1

**Состояние репозитория.** Продукт-код сайта (`index.html`, `src/`, `package.json`,
`tests/form.spec.ts`) уже есть из раздела 0, `git` ещё не инициализирован (инициализация
происходит по ходу этого раздела, см. рецепт).

**Сценарий-боль.** Новая сессия того же репозитория `signup-landing/`. Просят добавить второе
поле в форму и прогнать проверку. Агент снова спрашивает, какой командой собрать сайт и какой
командой прогнать тест формы — тот самый вопрос, что мимоходом всплыл в разделе 0, теперь
повторяется во второй раз подряд в новой сессии, потому что у агента нет памяти между сессиями.
Фасилитатор явно называет это: «вот он, триггер — агент второй раз переспрашивает то, что вы уже
объясняли».

**Открытый вопрос классу (дословно).** «Агент второй раз спрашивает, какой командой собрать этот
лендинг и как проверить, что форма проходит тест. Что вы сделаете — и куда именно это запишете?»

**Ожидаемые ответы зала.**

| Вариант | Разумен? | Где работает | Где ломается |
|---|---|---|---|
| «Отвечу ему в чате ещё раз» | Частично | Закрывает эту сессию | Не переживает конец сессии — в следующий раз агент спросит снова; проблема не решена, только отложена |
| «Заведу `README.md` с инструкцией» | Частично | README читают люди, впервые открывшие репозиторий | Claude Code не подгружает README автоматически в каждую сессию так, как `CLAUDE.md`; README пишется для человека, а не для агента (см. таксономию раздела «Что добавляем») |
| «Заведу `CLAUDE.md` с полным описанием архитектуры проекта» | Нет | Никогда не окупается | Классический карго-культ: агент выведет структуру кода сам за секунды через инструменты чтения файлов; раздел устареет при первом рефакторинге и начнёт врать. RCT Gloaguen et al. **Открытый вопрос классу (дословно).** «Завтра показ сайта заказчику. В `CLAUDE.md` написано:
"никогда не коммитьте напрямую в main". Агент только что, накануне показа, закоммитил правку формы
в main — текстом всё было сказано правильно. Что вы делаете, чтобы это стало невозможно, а не
просто маловероятно?»

**Ожидаемые ответы зала.**

| Вариант | Разумен? | Где работает | Где ломается |
|---|---|---|---|
| «Перепишу правило капсом / добавлю "ВАЖНО"» | Нет | Никогда механически | IFScale (`arXiv:2507.11538`): даже лучшие модели держат только 68% точности при 500 инструкциях, комплаенс падает почти линейно с их числом — эмфаза не создаёт механического барьера |
| «Буду проверять руками после каждого коммита» | Частично | Работает, пока хватает дисциплины | Не масштабируется, стоимость растёт с частотой использования, отменяет саму идею автоматизации |
| «Настрою branch protection на GitHub/GitLab» | Да, но недостаточно само по себе | Хорошая параллельная защита на уровне сервера | Не даёт агенту мгновенной локальной обратной связи и не мешает попытке коммита локально — законный слой defense-in-depth, но не замена локального механического барьера |
| «Добавлю `PreToolUse`-хук, который блокирует `git commit` на main» | Да (целевой ответ) | Всегда — исполняет среда, не завязано на «согласие» агента | Ломается тихо при невалидном matcher или таймауте — см. провал ниже |

**Что добавляем — предметно.** Рабочий хук из шаблона курса
(`/tmp/ahr/templates/base-project-template/with-git/.claude/settings.json`), процитировать целиком
и разобрать по частям:

```jsonc
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.command' | { read -r cmd; if echo \"$cmd\" | grep -qE '(^|[;&|]\\s*)git\\s+commit\\b'; then if ! git rev-parse --is-inside-work-tree >/dev/null 2>&1; then echo '{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"ask\",\"permissionDecisionReason\":\"WARNING: branch-protection gate inactive\"}}'; exit 0; fi; branch=$(git symbolic-ref --short HEAD 2>/dev/null); if [ \"$branch\" = \"main\" ] || [ \"$branch\" = \"master\" ]; then echo '{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"deny\",\"permissionDecisionReason\":\"BLOCKED: direct commit to main/master. Create a feature branch first.\"}}'; exit 0; fi; fi; }",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

Разбор построчно (источник: `03-hooks-permissions.md`, §1):
- `"matcher": "Bash"` — хук вызывается только перед вызовами `Bash`.
- `jq -r '.tool_input.command'` — Claude Code передаёт хуку JSON через **stdin**; `jq` вытаскивает
  именно ту команду, которую собираются выполнить.
- `grep -qE '(^|[;&|]\s*)git\s+commit\b'` — ищет `git commit` как отдельную команду, не подстроку.
- `git symbolic-ref --short HEAD`, а не `git rev-parse --abbrev-ref HEAD` — у свежего репозитория
  без единого коммита («unborn HEAD») `rev-parse` завершается ошибкой и молча оставляет проверку
  нерабочей; `symbolic-ref` резолвит имя ветки корректно в обоих случаях.
- Проверка `! git rev-parse --is-inside-work-tree` — если это вообще не git-репозиторий, хук не
  пропускает коммит молча (что выглядело бы как защита без защиты), а возвращает `"ask"` с явным
  предупреждением.
- `hookSpecificOutput.permissionDecision` — современный формат JSON-ответа хука.

**Слайды раздела.**
1. Блок кода: `.claude/settings.json` целиком (как в «Что добавляем»).
2. Снимок терминала: текущая ветка — `main` (`git symbolic-ref --short HEAD`).
3. Снимок терминала: попытка коммита, хук возвращает `deny` с текстом «BLOCKED: direct commit to
   main/master. Create a feature branch first.» — дословно на слайде.
4. Снимок терминала: `git switch -c fix-form-field`, тот же коммит — теперь проходит.
5. Слайд-цитата шаблона курса (`CLAUDE.md` того же репозитория): «a gate is not installed because
   its file exists — it is installed once observed firing against a real case» — с указанием, что
   слайд 3 — это и есть то самое наблюдаемое срабатывание.
6. Второй слой (слайдом, без живой демонстрации): код возврата `2` блокирует действие
   **безусловно**, даже если тот же хук вернул JSON с `"allow"` — exit-код побеждает JSON.

**Что делать — рецепт.**
1. Скопировать `.claude/settings.json` из
   `/tmp/ahr/templates/base-project-template/with-git/.claude/settings.json` в
   `signup-landing/.claude/settings.json` (блок кода в «Что добавляем» — рабочий файл целиком, не
   сокращать при копировании).
2. Проверить, что репозиторий уже инициализирован (`git init` был в разделе 1) и текущая ветка —
   `main`: `git symbolic-ref --short HEAD`.
3. Попросить агента внести правку в форму и закоммитить прямо на `main` — ожидаемый результат:
   ответ хука `deny`, коммит не создан.
4. `git switch -c fix-form-field` отдельной командой (не в одной строке с коммитом — хук читает
   ветку до выполнения всей Bash-команды целиком, см. «Нюанс»), затем повторить коммит — проходит.
5. Проверка, что хук реально стоит на страже, а не просто существует файлом: сознательно
   спровоцировать `deny` ещё раз на другой правке — если не сработал, чинить `matcher`/JSON, не
   переходить к разделу 4, пока хук не показан работающим вживую хотя бы раз (речь идёт о записи
   на слайд, не о живом терминале в зале).

**Провал.** CVE-2025-59536 (CVSS 8.7, Check Point Research): вредоносный хук на `SessionStart` в
чужом `.claude/settings.json` выполнялся сразу после клонирования репозитория и запуска `claude` —
команды из хука уже отработали к моменту, когда диалог доверия к папке вообще появился на экране.
Найдена/сообщена 21.07.2025, патч 26.08.2025, публикация advisory 29.08.2025. Второй слой (то же
явление, углубление): почему код возврата `2` блокирует безусловно даже поверх явного `allow` в
permissions — и почему хук может тихо не сработать вовсе: один невалидный matcher в
`settings.json` отключает **все** хуки файла без единой ошибки в интерфейсе (Alex Dunlop, «Claude
Code Hook Not Firing», 2026); `PreToolUse`-хук, не уложившийся в таймаут (30 с у
`UserPromptSubmit`), не блокирует — просто отваливается, и вызов идёт по обычному пути разрешений,
как если бы хука не было вовсе. Цитата для дословного повторения: «when a gate doesn't fire,
nothing happens, which is exactly what a passing gate looks like». Источник:
`03-hooks-permissions.md`, §5, таблица «провал/что произошло/урок». 4,5 мин.

**Критерий «здесь не нужно».** Проверка дешевле в CI/линтере на PR — не дублировать ту же проверку
на каждый `PostToolUse` в интерактивной сессии; хук становится тормозом при стекировании («hook
bloat has no error message. Nothing fails. Everything just gets slower, gradually» — Alex Dunlop);
правило по сути не механизируемо (суждение вроде «не переусложняй» честнее оставить
человеку/критику, не хуку); соло-разработчик с низким blast radius — риск ещё не стал реальным.

**База и нюанс.**
- **База (слайд):** «хук — правило, которое среда исполняет сама, не спрашивая согласия агента, как
  турникет вместо таблички "пожалуйста, платите"».
- **Нюанс (речь):** `deny` в permissions всегда побеждает `allow`, даже более узкий и точный;
  хук — это исполняемый код в репозитории, а значит и поверхность атаки (второе CVE — CVE-2026-21852,
  утечка API-ключа через `ANTHROPIC_BASE_URL` в чужом `settings.json`); base64/промежуточный файл —
  хук на `Bash` фильтрует синтаксис одной команды, не намерение всего плана; острый край из
  собственного дневника шаблона курса — хук читает текущую ветку **до** выполнения всей
  Bash-команды, поэтому `git switch x && git commit ...` в одну строку получает `deny` против
  старой ветки, даже если сам коммит после переключения лёг бы корректно (источник:
  `.claude/settings.json` шаблона, комментарий `$comment`).
