# Когда нужна иерархическая резка

## Assertion

Второй индекс не бесплатен — его выгода измеряется на своих данных, не берётся по умолчанию.

## Visual

> **Нужна.** Длинные структурированные документы с осмысленной иерархией разделов — регламенты, контракты, нормативные акты, — где цена отдать модели лишний контекст оправдана ценой ошибки, если этого не сделать.

> **Не нужна.** Маленькая база, плоские FAQ-документы без вложенной структуры — выгоду иерархии нужно измерить, её нельзя просто принять по умолчанию, и на маленькой базе рост цены вызова (почти вдвое на этом корпусе) может не окупиться вовсе.

## Speaker notes

Иерархическую резку не стоит ставить везде по умолчанию только потому, что она один раз выиграла на этом замере. У приёма есть чёткая граница, и формулируется она прямо: когда нужен, когда не нужен.

Нужен этот приём там, где документы длинные и структурированные, с осмысленной иерархией разделов: регламенты, контракты, нормативные акты — ровно та картина, которая стоит за реальным случаем, перенёсшим этот кейс на сюжет курса. На таких документах цена отдать модели лишний контекст — больше токенов, больше денег за вызов — явно оправдана ценой ошибки, если этого не сделать: неполный или неверный ответ по регламенту безопасности стоит дороже, чем несколько лишних центов на вызов модели.

Не нужен этот приём там, где база маленькая, а документы плоские — набор вопросов и ответов без вложенной структуры, без разделов, на которые можно было бы сослаться. На такой базе, как показывал замер версии 1 на самом первом занятии этой темы, даже не идеальный кусок почти наверняка оказывается единственным похожим на вопрос — разводить единицу поиска и единицу ответа здесь попросту нечего защищать. Рост цены вызова, который этот замер честно показал почти вдвое, на маленькой базе может не окупиться вовсе: выгоду иерархии нужно измерить на своих данных, её нельзя просто принять по умолчанию только потому, что приём когда-то выиграл замер на другом корпусе.

Эта граница — зеркало того же принципа, который закрывал прошлый кейс и прошлое занятие: любое усложнение рецепта имеет цену, и брать его стоит только там, где эта цена действительно оправдана дефектом, который оно чинит. Что с той же оси верно для семантической резки — следующим тактом.
