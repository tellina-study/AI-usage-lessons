# Что сделать с резкой документа

## Assertion

Пять способов распорядиться резкой документа, когда база выросла до тысяч документов.

## Visual

> **Что сделать с резкой документа?**

`резать по границам предложений, как в прошлый раз` · `резать мельче — и отдавать модели родительский документ целиком` · `резать там, где разрыв смысла между соседними предложениями больше порога` · `резать рекурсивным каскадом разделителей (абзац → строка → предложение → слово)` · `отдавать модели найденный кусочек вместе с соседними кусочками той же нарезки`

## Speaker notes

Пять действий, и все — реальный инженерный выбор на этом шаге. Первое — ничего не менять: резать документ по границам предложений, тем же рецептом, который прошлое занятие уже проверило и одобрило. Второе — резать мельче, чем раньше, а при ответе отправлять модели сам документ целиком — тот, из которого найден кусочек. Третье — отказаться от заранее заданного размера куска вовсе и резать там, где смысл текста между соседними предложениями расходится сильнее порога. Четвёртое — резать каскадом разделителей по убыванию размера: сначала пробовать разрез по абзацам, потом по строкам, потом по предложениям, и только если кусок всё равно больше цели — по словам. Пятое — саму резку и сам поиск не менять вовсе, а при ответе отдавать модели не только найденный кусочек, но и соседний слева, и соседний справа той же нарезки.

Прикиньте: документ по технике безопасности нашёлся верно — поиск указал ровно на тот регламент, где лежит ответ. Какова вероятность, что кусочек, который поиск вернул из этого регламента, на самом деле содержит нужный абзац, а не какой-то другой, формально похожий по теме?

Пятнадцать секунд на выбор. Голосование теперь идёт по пяти карточкам, не по четырём, как раньше. Все пять опираются на один и тот же замер — тот же корпус, те же семьдесят два вопроса, тот же способ проверки ответа, которым прошлое занятие уже пользовалось. Разбор того, как устроено каждое действие, — следующим экраном; структура самого замера и результат — дальше.

Ни одно из пяти действий не является очевидно правильным заранее. Первое — самое дешёвое: оно вообще ничего не меняет в уже работающем рецепте. Второе требует второго хранилища — и документа целиком, и его маленьких кусочков. Третье требует отдельного прохода эмбеддинга по каждому предложению документа, которого первые два не требуют вовсе. Четвёртое не требует эмбеддинга текста для самой резки, но дробит длинные предложения, которые первое действие оставляло целым куском, — что это значит для ответа, станет ясно после разбора. Пятое не требует ни нового хранилища, ни нового эмбеддинга — но модель на каждый вопрос читает больше текста, чем в первом действии, и у кусочка на самом краю документа соседа с одной из сторон может не быть вовсе. Выбор без замера здесь — выбор вслепую: все пять кусочков выглядят нормально, если просто открыть и прочитать их глазами, а проблема обнаруживается только тогда, когда конкретный вопрос пользователя попадает ровно в точку, где рецепт либо держит контекст документа, либо его теряет.
