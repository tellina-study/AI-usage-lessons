# Собственный мини-эксперимент: Skill vs always-on vs ссылочный файл vs раздутый файл — соблюдение процедуры

**Date:** 2026-10-02 · **Access date:** 2026-10-02 · **Issue:** #217

> Отчёт о мини-эксперименте, проведённом оркестратором на этом репозитории 2026-10-02. Все числа
> ниже пересчитаны лично из `_exp/RAW-*` — ничего не взято из брифа задачи как готовое число.
> Сырые материалы: `_exp/PROCEDURE.txt`, `_exp/process.md`, `_exp/skills/note-format/SKILL.md`,

> `_exp/RAW-condition1-compliance.txt`, `_exp/RAW-condition2-compliance.txt`,

## 1. Что тестировалось

Один и тот же исполнитель — субагент на модели Haiku (младшая, дешёвая модель; выбор сделан, чтобы
не маскировать эффект способа подачи сильной моделью, которая может домыслить конвенцию и без
явного текста) — получал одну и ту же пятишаговую проверяемую процедуру **P-NOTE v2** и задачу
«напиши заметку 150–250 слов на тему X». Процедура (идентичный текст во всех плечах, см.
`_exp/PROCEDURE.txt`):

1. Файл начинается строкой `# <Заголовок>`, следующая непустая строка — ровно
   `**Date:** 2026-10-02 · **Issue:** #217-EXP`.
2. В файле есть таблица с шапкой ровно `| утверждение | источник | тип |` (≥2 строки данных).
3. В файле есть раздел `## Что НЕ доказано`.
4. Последняя непустая строка — ровно `<!-- checked: P-NOTE v2 -->`.
5. После записи заметки — одна строка в `index.md` той же папки (создать, если нет).

**Четыре плеча подачи того же текста:**

| Плечо | Как подан текст | Файл-источник | Размер |
|---|---|---|---|
| **A** | Текст процедуры прямо в контексте задачи (аналог короткого always-on-файла, всегда активного инструктивного файла, загружаемого целиком) | — (инлайн) | идентичен `PROCEDURE.txt` |
| **B** | Только указатель в контексте: «конвенции описаны в `_exp/process.md`» | `_exp/process.md` | 1092 байта |
| **C** | Только одна строка `description` навыка `note-format` + путь к `SKILL.md`; тело подгружается по решению модели (аналог progressive disclosure — поэтапной подгрузки навыка: сначала метаданные, тело — по требованию) | `_exp/skills/note-format/SKILL.md` | 1553 байта (с YAML-фронтматтером) |
| **D** | Процедура спрятана внутри раздутого файла инструкций — реальный `CLAUDE.md` этого курса (702 строки) с вставленной процедурой на строке 347 из 702 (≈49% глубины файла), под заголовком `## Процедура оформления заметок P-NOTE (ENFORCED)`; исполнителю велено прочитать файл целиком | `_exp/instructions-bloated.md` | 62 152 байта (62 КБ) |

Текст самой процедуры в A/B/D идентичен байт-в-байт (`PROCEDURE.txt` и тело `process.md` —
1092 байта, одинаковы); в C тот же текст составляет тело `SKILL.md` плюс YAML-фронтматтер
(`name: note-format`, `description: ...`), отсюда разница в 461 байт.

**Два условия:**
- **Условие 1** («велено соблюдать») — в задаче прямо сказано: «оформление должно соответствовать
  конвенции курса». Прогнано на двух темах, T1 и T2 (T1 — «slash-команда vs хук», T2 — «почему
  инструменты требуют описания / 50 инструментов ≈ 15k токенов overhead»).
- **Условие 2** («без напоминания») — задача говорит только «напиши заметку», без упоминания
  процедуры. Прогнано на двух темах, E2 («зачем субагенту отдельное контекстное окно») и E3
  («почему проверка кодом надёжнее просьбы к модели») — по одной теме на плечо, n=2 на плечо
  (каждое плечо прогнано на обеих темах отдельно).

**Измерения:** (1) соблюдение каждого из 5 шагов — механически, скриптом `check.py` (и его копиями
`check2.py`/`check3.py` для второй/третьей партии выходов — файлы идентичны, различается только
переменная `OUT`, указывающая на `out`/`out2`/`out3`); (2) расход токенов субагента и число вызовов
инструментов, как их сообщает харнесс при делегировании (`_exp/RAW-tokens.csv`).

## 2. Как измеряли — не на глаз

`check.py` читает файл заметки построчно и проверяет 5 условий программно (не LLM-оценкой):
первая непустая строка начинается с `# `, вторая непустая строка совпадает **ровно** с заданной
шапкой; наличие точной строки-шапки таблицы и ≥2 строк данных после неё; наличие строки
`## Что НЕ доказано`; последняя непустая строка — ровно маркер; существование `index.md` в той же
папке со строкой, содержащей имя файла заметки. Результат — булева таблица 5 колонок на файл, без
интерпретации смысла содержимого. Это то, что отличает это измерение от «похоже на выполненное» —
соблюдение формы проверено детерминированным кодом, а не оценкой модели или человека.

## 4. Результаты — Условие 2 («без напоминания»)

Из `_exp/RAW-condition2-compliance.txt` (тема E2) и `_exp/RAW-condition2b-compliance.txt`
(тема E3):

| Плечо | E2 | E3 |
|---|---|---|
| A | 5/5 | 5/5 |
| B | **0/5** | **0/5** |
| C | 5/5 | 5/5 |
| D | 5/5 | 5/5 |

**B — 0/5 на обеих независимых темах.** Открыв `_exp/out2/B/B-E2.md` и `_exp/out3/B/B-E3.md`
напрямую: оба файла — связные, качественные по содержанию заметки (с заголовком `#`, с
подзаголовками), но **ни один из пяти формальных признаков процедуры не присутствует** — нет
строки `**Date:** ... · **Issue:** #217-EXP` на нужной позиции, нет таблицы с заданной шапкой, нет
раздела `## Что НЕ доказано`, нет финального маркера, не создан `index.md` в папке B. Исполнитель
написал заметку по смыслу задачи, не открыв `process.md` вовсе.

Это видно и по числу вызовов инструментов харнесса (та же `RAW-tokens.csv`): на E2 — A=6, B=**3**,
C=5, D=4; на E3 — A=4, B=**2**, C=4, D=4. У B систематически на 1–3 вызова меньше, чем у остальных
плеч на тех же темах — прямое количественное подтверждение «не открыл файл», не только вывод по
отсутствию формы в тексте.

**В условии 1 ровно то же плечо B дало 5/5 на обеих темах** (T1, T2) — то есть B не «ненадёжен
всегда», у него специфический, бинарный режим отказа: срабатывает полностью при прямом упоминании
процедуры в задаче и полностью не срабатывает без него. Корректная формулировка — не «ссылочный
файл не работает», а «у ссылочного файла нет структурной точки, которая бы инициировала его чтение
без явного триггера в тексте задачи» (механика — см. `01-mechanics.md` §3).

## 5. Стоимость в токенах — пересчёт по `RAW-tokens.csv`

| Условие/тема | A | B | C | D |
|---|---|---|---|---|
| Условие 1, T1 | 61 032 | 58 940 | 59 057 | 77 665 |
| Условие 1, T2 | 59 971 | 59 010 | 60 142 | 78 162 |
| Условие 2, E2 | 60 055 | 57 588 | 59 246 | 77 115 |
| Условие 2, E3 | 58 294 | 57 213 | 58 833 | 77 508 |

Беря плечо **B** как базу (минимальный текст в контексте в покое — только одна строка-указатель):

| Сравнение | T1 | T2 | E2 | E3 |
|---|---|---|---|---|
| **D vs B** (раздутый файл) | +31,8% | +32,5% | +33,9% | +35,5% |
| **A vs B** (инлайн-текст) | +3,5% | +1,6% | +4,3% | +1,9% |
| **C vs B** (skill-проба) | +0,2% | +1,9% | +2,9% | +2,8% |

**D дороже B на +31,8…+35,5% токенов при идентичном результате по форме** (в условии 1 — 5/5 у
обоих; в условии 2 — 5/5 у D против 0/5 у B, то есть здесь D не просто дороже, а единственный из
двух сработавший). **A и C — в пределах +0,2…+4,3% от B**, то есть почти не отличимы по цене от
минимального указателя, несмотря на то что везут процедуру целиком (A) или метаданные + тело по
требованию (C).

**Важная оговорка по атрибуции цены D:** рост стоимости у D — это стоимость **прочитать файл на
62 КБ целиком** (явно данная инструкция «прочитай файл целиком»), а не стоимость самой процедуры
P-NOTE — процедура внутри D занимает те же ~1 КБ, что и в A/B. Эксперимент показывает цену
конкретной реализации «раздутый файл, который инструктируют прочитать полностью», а не абстрактного
«always-on-слоя» как такового (см. ограничение №3 ниже).

## 6. Дефект пилотного прогона — найден и устранён, не скрыт

Первый (пилотный) прогон (`_exp/pilot/`) использовал **общий `index.md` на все три плеча** (A, B,
C — плечо D появилось позже, пилот его не включает) вместо отдельного `index.md` на плечо, как в
основном дизайне (`_exp/out/*/index.md`). Результат виден в `_exp/pilot/index.md`:

```
- A-T1.md — Slash-команда это явный синхронный вызов, хук это асинхронный автоматический триггер...
- C-T1.md — Slash-команды — явные синхронные интерактивные вызовы; хуки — асинхронные...
```

Строка для **B-T1.md отсутствует**, хотя сам файл `_exp/pilot/B-T1.md` существует и по тексту
полностью соответствует процедуре (шапка, таблица, раздел «Что НЕ доказано», маркер
`<!-- checked: P-NOTE v1 -->` — все на месте). Три независимых исполнителя писали в один файл
`index.md` параллельно/последовательно без координации — классическая **гонка одновременной
записи** (race condition): позднейшая перезапись затёрла строку, добавленную раньше. Шаг 5 для
плеча B в пилоте — **недостоверен**: по факту заметка была оформлена правильно, но измерение шага 5
дало бы ложный «нет», если бы пилот использовался как результат.

**Устранение:** в основном дизайне (условия 1 и 2) каждое плечо получило отдельную папку со своим
собственным `index.md` (`_exp/out/A/index.md`, `_exp/out/B/index.md` и т.д.) — гонка исключена
структурно, не повторной попыткой. Пилотные данные **не использованы** в результатах §3–§5;
приведены здесь только как пример найденного и исправленного дефекта дизайна измерения. Отдельно
заметен побочный эффект: в пилоте процедура была версии **P-NOTE v1** (маркер `<!-- checked:
P-NOTE v1 -->`), в основном прогоне — **v2** (другая версия самой процедуры, не только дизайна
измерения) — то есть пилот и основной эксперимент не строго идентичны по тексту задачи, ещё одна
причина не смешивать пилотные числа с основными.

## 7. Наблюдение на самом репозитории курса (это тоже измерение, не рассуждение)

Проверено командой по всем 13 файлам `.claude/skills/*/SKILL.md` этого репозитория:

```bash
for f in .claude/skills/*/SKILL.md; do echo "=== $f ==="; head -8 "$f"; done
```

Результат: **13 skills в `.claude/skills/`, YAML-фронтматтер с полем `description` есть только у
одного — `pre-user-gate`.**

```yaml
---
name: pre-user-gate
description: Pre-USER-GATE walkthrough — orchestrator self-review before presenting GATE to user.
  Reduces user feedback rounds.
---
```

У `compile-wiki` фронтматтера (блока `---...---`) **нет вообще** — первая строка файла `#
compile-wiki`, но непосредственно под заголовком есть прозаическая строка-резюме («Compile and
maintain the wiki knowledge base: index all sources, populate ontology, ingest into RAG, generate
wiki pages.»), которая *по содержанию* играет роль описания, но *не оформлена* как YAML-поле
`description` — отсюда «частично» в формулировке задачи: смысловой эквивалент описания
присутствует, структурного поля для парсинга метаданных — нет. Это не то же самое, что у 11
остальных (`build-deck`, `catalog-docs`, `diagram-refresh`, `extract-links`, `impact-check`,
`issue-from-change`, `publish-article`, `query-kb`, `reflect`, `sync-library`, `update-lecture`) —
там первая строка файла сразу `# <имя>`, фронтматтера нет совсем, и даже прозаического
резюме-кандидата в соответствующем месте не всегда структурно отделено от роли/тела.

**Следствие по механике (из `01-mechanics.md` §1.3, §1.5):** активация skill — это сопоставление
моделью текста `description` из YAML-фронтматтера с запросом **на этапе, когда тело файла ещё не
загружено**. Skill без `description` в метаданных не даёт модели материала, по которому принять
решение о релевантности *до* открытия файла — то есть 12 из 13 skills этого репозитория физически
не могут авто-триггернуться по смыслу запроса (в терминах §1.3 — они всегда в режиме
«недо-триггер», потому что для auto-invocation просто нет входных данных). На практике такой skill
вырождается в аналог slash-команды: сработает, только когда оркестратор явно напечатает/укажет имя
навыка (`/catalog-docs` или прямую ссылку на файл) — ровно то, что фактически и происходит в этом
проекте (skills вызываются по имени из `tools/*/README.md` и `CLAUDE.md`, а не автоматически).

**Выученный урок:** это не обвинение — 12 из 13 skills были написаны до того, как в проекте
появилась практика YAML-фронтматтера (видна только в самом новом, `pre-user-gate`). Но если цель —
переход на авто-триггер по смыслу задачи (а не только по явному вызову оркестратора), всем
12 файлам необходим `description` в фронтматтере; без него текущее поведение этого репозитория —
не «skills, которые модель выбирает», а «процедуры, которые оркестратор вызывает по имени» — то
есть архитектурно это уже ближе к плечу A/D (явно подсунутая инструкция), а не к плечу C
(progressive disclosure по смысловому триггеру) данного эксперимента.

## 8. Ограничения эксперимента (жёстко — главная защита от переобобщения)

1. **Плечо C — не настоящая вендорская фича Agent Skills, а её проба (proxy).** Описание навыка
   было вручную положено в контекст, тело — в отдельный файл; тело подгружалось оркестратором по
   решению модели в рамках этого эксперимента, а не через нативный механизм Claude Skills
   платформы (который имеет собственный контракт `name`/`description`, лимиты символов, кэш после
   компакции — см. `01-mechanics.md` §1). Эксперимент проверяет **механизм активации**
   (в контексте по умолчанию — только описание; тело — по требованию), а не конкретную реализацию
   Anthropic. **Нельзя говорить «Agent Skills работают лучше»** на основании этого результата —
   можно говорить только «механизм разделения метаданных и тела при этой реализации сработал так
   же надёжно, как инлайн-текст, и дешевле раздутого файла».
2. **n=2 на плечо, одна модель (Haiku), одна процедура, короткие однозадачные сессии.** Это
   показывает **направление** эффекта, не размер. Статистический тест (доверительный интервал,
   p-значение) не проводился и при n=2 на условие **невозможен** — любое «средне плечо X на Y%
   лучше» было бы псевдоточностью. Другая модель, более длинная многошаговая сессия или другая по
   природе процедура (не формат документа, а, например, код-конвенция) может дать другую картину —
   особенно учитывая, что внешние измерения (`02-empirics-instruction-following.md`, SEQUOR/Laban,
   McMillan) показывают сильную зависимость соблюдения от числа шагов сессии, а здесь сессии
   были короткими (1 заметка, не многошаговый агентный прогон).
3. **Плечо D — это «большой файл инструкций, прочитанный целиком по явному велению», а не
   буквальная always-on-инъекция.** В реальном always-on-механизме Claude Code файл грузится в
   контекст автоматически при старте сессии харнессом (§2.2 `01-mechanics.md`), а не читается по
   отдельной инструкции «прочитай файл X целиком» внутри промпта делегирования. Здесь D ближе к
   «субагенту велели прочитать длинный референс», чем к «субагент стартовал с этим файлом в
   системном промпте». Вывод про раздувание always-on-слоя **переносится с этой оговоркой**: цена
   чтения большого файла подтверждена, но не доказано, что ИМЕННО механизм автозагрузки при старте
   сессии (а не сам факт «прочитать 62 КБ текста») даёт тот же ценовой эффект.
4. **Потолок 5/5 во всех плечах условия 1 означает: эксперимент ничего не говорит о различиях
   КАЧЕСТВА, когда задача сама называет процедуру.** Единственное различие, которое условие 1
   показало — цена (§5). О надёжности форматирования в этом сценарии вывод один: «одинаково
   надёжно у всех четырёх при явном упоминании», не более и не менее.
5. **Нельзя говорить «ссылочный файл не работает».** В условии 1 он сработал 2/2 (T1, T2) —
   идентично остальным плечам. Корректное утверждение — у него специфический, воспроизведённый
   дважды на независимых темах режим отказа: **молчаливое несрабатывание без прямого упоминания
   процедуры в задаче**, то есть бинарный переключатель «есть триггер в тексте задачи → работает;
   нет триггера → полностью не работает», а не частичная деградация. Именно эта бинарность — причина,
   почему ссылочный файл не годится для правила, которое обязано действовать всегда независимо от
   формулировки конкретной задачи.
6. **Проверялось соблюдение ФОРМЫ** (5 машинно-проверяемых структурных признаков), а не качество
   содержания заметки. И B-E2.md, и B-E3.md (0/5 по форме) — связные, содержательные по смыслу
   заметки с собственным заголовком и структурой; просто не той структуры, которую требовала
   процедура. Эксперимент не измеряет, стала бы заметка B хуже или лучше как учебный материал —
   только то, что заданный формальный контракт не был выполнен.

## 9. Как воспроизвести

Все команды — из корня репозитория (`notes/research/student-questions/skills-vs-instructions/`
относительно корня — рабочая директория для путей внутри `check.py`).

```bash
# 1. Механическая проверка соблюдения — три партии результатов (out / out2 / out3)
python3 notes/research/student-questions/skills-vs-instructions/_exp/check.py   # -> out  (условие 1)
python3 notes/research/student-questions/skills-vs-instructions/_exp/check2.py  # -> out2 (условие 2, тема E2)
python3 notes/research/student-questions/skills-vs-instructions/_exp/check3.py  # -> out3 (условие 2, тема E3)

# 2. Сверка сырых чисел соблюдения (как в §3-§4 выше)
cat notes/research/student-questions/skills-vs-instructions/_exp/RAW-condition1-compliance.txt
cat notes/research/student-questions/skills-vs-instructions/_exp/RAW-condition2-compliance.txt
cat notes/research/student-questions/skills-vs-instructions/_exp/RAW-condition2b-compliance.txt

# 3. Пересчёт стоимости токенов (как в §5)
column -s, -t notes/research/student-questions/skills-vs-instructions/_exp/RAW-tokens.csv

# 4. Наблюдение на репозитории курса (как в §7)
for f in .claude/skills/*/SKILL.md; do echo "=== $f ==="; head -8 "$f"; done

# 5. Прямой осмотр провалившихся файлов плеча B (условие 2)
cat notes/research/student-questions/skills-vs-instructions/_exp/out2/B/B-E2.md
cat notes/research/student-questions/skills-vs-instructions/_exp/out3/B/B-E3.md
ls notes/research/student-questions/skills-vs-instructions/_exp/out2/B/   # index.md отсутствует
```

Три копии скрипта проверки (`check.py`/`check2.py`/`check3.py`) идентичны логикой и отличаются
только переменной `OUT` (путь к папке с результатами) — это артефакт итеративного прогона
(сначала условие 1, затем условие 2 на двух темах отдельными партиями), не три разных метода
проверки.

**Чего в `_exp/` нет и что не стоит пытаться восстановить:** точный текст промпта делегирования
субагенту для каждого прогона (сама формулировка задачи «напиши заметку 150–250 слов на тему X» +
способ подачи процедуры) не сохранён отдельным логом — воспроизведены только артефакты-входы
(`PROCEDURE.txt`, `process.md`, `SKILL.md`, `instructions-bloated.md`) и артефакты-выходы (заметки,
`RAW-*`). Повторный прогон этого эксперимента потребует восстановить формулировку делегирования по
структуре этих файлов, а не копированием несуществующего лога.
