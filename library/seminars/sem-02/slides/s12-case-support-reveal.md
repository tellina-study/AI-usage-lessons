# Закрытый вендор

## Assertion

«У вендора вашей helpdesk-системы нет открытого API и нет возможности кастомизации».

## Visual

Вверху дополнительная вводная в кавычках: «У вендора вашей helpdesk-системы нет открытого API и нет возможности кастомизации интерфейса — это закрытая коробочная система». Ниже — 3 карточки вариантов в ряд, у каждой название и цена: 1) «Решение сбоку» — расширение браузера или вторая панель; цена: «два места одновременно, риск низкого adoption». 2) «Смена вендора» — helpdesk-система с открытым API; цена: «миграция данных, переобучение команды, риск простоя». 3) «Пересмотр scope» — асинхронный помощник, готовит черновики заранее; цена: «оператор открывает готовое там, где удобно, но нужен отдельный процесс чтения данных». Внизу строка: «Единственно верного ответа нет».

## Speaker notes

Дополнительная вводная: у вендора вашей helpdesk-системы нет открытого API и нет возможности кастомизации интерфейса — это закрытая коробочная система.

Кто передумал? Почему? Это специально неоднозначный кейс без единственно верного ответа — дождитесь минимум трёх разных направлений мнений, не форсируйте один вывод.

Три реальных варианта, которые стоит вытащить в разговор, если аудитория сама их не назовёт. Решение «сбоку» — расширение браузера или вторая панель рядом с helpdesk-интерфейсом; цена — пользователю нужно физически смотреть в два места, риск низкого adoption: оператор просто не будет туда заглядывать под нагрузкой. Смена вендора helpdesk-системы на систему с открытым API; цена — миграция исторических данных, переобучение всей команды, риски простоя, крупное решение ради одной фичи. Пересмотр scope задачи: помощник работает асинхронно, готовит черновики по тикету заранее через отдельный фоновый процесс, а оператор открывает готовое там, где ему удобно.

У этого кейса нет единственно верного ответа — на реальной работе вы будете принимать похожее решение исходя из бюджета, срочности и того, готова ли компания на организационные издержки ради качества интеграции. Задача была не найти «правильный» ответ, а увидеть, что организационное ограничение — закрытый вендор — может определить архитектуру не хуже, чем технические требования.

### Self-check
1. Какой из трёх вариантов вы бы выбрали для команды с ограниченным бюджетом и высокой срочностью — и почему именно он?
2. Почему «пересмотр scope» иногда оказывается дешевле по деньгам, но дороже по инженерному изяществу решения — согласны ли вы с этим trade-off'ом?
