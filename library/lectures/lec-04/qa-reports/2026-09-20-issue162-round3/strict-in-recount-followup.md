# Strict-in % Follow-up Recount — Часть 3, после точечной правки §3.2 (issue #162, round 3)

VERDICT: REVISE (проходит порог формально, но с хрупким запасом — см. «Чувствительность»)

Узкая проверка по запросу — НЕ полное ревью. Метод и денаминатор/числитель-логика идентичны `strict-in-recount.md` (тот же построчный проход, Решение #78, partial→out консервативно). Существующая база (3303 in / 11556 total, до правки) взята из этого отчёта без пересчёта — проверено, что она осталась валидной (см. ниже).

## Что проверено

1. **Валидность базы 3303.** Правка локализована в §3.2: секция выросла с 985 до 1391 слов (+406), остальной файл — 11556−985=10571 слов «прочего контента» до правки vs 11949−1391=10558 после (−13 слов, из-за переименования заголовков/TOC при реордеринге §3.3d↔§3.3e, не влияет на in/out-классификацию содержания). Значит база **3303** (сумма in-абзацев вне двух новых фрагментов) переносится без изменений — новая правка не затронула никакой другой ранее классифицированный контент.

2. **Идентификация двух новых абзацев.** `git diff` подтверждает: оба абзаца — чистые добавления (не правки существующего текста):
   - Строка 59: **«Честное фундаментальное ограничение: context rot (in-bucket: ограничение → урок → критерий)»** — **212 слов** (`wc -w` на строке).
   - Строка 68: **«Честное ограничение: несвежий AGENTS.md вреднее отсутствующего (in-bucket: провал → урок; ...)»** — **232 слова**.
   - Итого новых in-слов: **444**. (Файл вырос на 393 слова нетто — разница объясняется тем, что старые ~30+~20-словные упоминания context rot / несвежего AGENTS.md внутри прежнего сводного абзаца L62 были вычищены/перестроены при выделении новых абзацев; в старом подсчёте эти ~50 слов уже были классифицированы out, так что на числитель это не влияет.)

3. **Содержательная проверка (не просто тег).**
   - **Абзац 1 (context rot).** Организован строго вокруг: ограничение (нелинейная деградация retrieval, системное свойство на 18 моделях, начинается до заполнения окна — не баг одной модели) → урок (курирование — не экономия токенов, а условие корректности; «дамп всего репозитория» **активно ухудшает** качество) → явный критерий («больше контекста — безопасный default» — ложная эвристика; безопасный default — курировать). Механики (JIT/компакция/заметки) в этом абзаце нет вообще — она вынесена в соседние абзацы, которые остаются out. **Подтверждено: полностью in-bucket, тег соответствует содержанию.**
   - **Абзац 2 (несвежий AGENTS.md).** Организован строго вокруг: провал (устаревший AGENTS.md хуже отсутствующего, т.к. отсутствие компенсируется разведкой, а устаревший файл — доверяют буквально; два конкретных режима отказа — устаревшая команда сборки, снятое архитектурное ограничение) → урок (AGENTS.md — живой артефакт, ревьюится вместе с проектом, Böckeler-цитата инкрементального строительства; «несвежий контекст гниёт»). Никакой сторонней механики в абзаце нет. **Подтверждено: полностью in-bucket, тег соответствует содержанию.**

   Оба абзаца — не просто маркированы `(in-bucket: ...)`, а содержательно организованы именно как заявлено в теге. Ни один не является «оговоркой в один-два предложения поверх механики» (тот паттерн, из-за которого исходный отчёт классифицировал их как partial→out).

## Итоговый расчёт

```
numerator = 3303 (база) + 212 (context rot) + 232 (AGENTS.md) = 3747
denominator = 11949 (реальный wc -w файла после правки)
3747 / 11949 = 31.36%
```

**Итог: 3747 / 11949 = 31.36% strict-in.**

**Порог 30% ENFORCED — формально пройден, запас +1.36 п.п.**

## Чувствительность (обязательна для честности — исходный отчёт указывал диапазон 27.0–30.1% ДО правки)

Применяя ту же консервативную поправку, что исходный отчёт применял к базе (исключение 3 Q&A-абзацев В3/В4/В5, 184 слова, как «в основном recap, не новое развитие» — это и была нижняя граница диапазона 27.0%):

```
low-bound: (3303 − 184) + 444 = 3563 → 3563 / 11949 = 29.82%
```

**Это НИЖЕ порога 30%.** При том же консервативном классификационном допущении, которое исходный отчёт уже применял к базе, результат опускается под порог.

Верхняя граница (если также засчитать §3.3b anti-hype-хвост, +174 слова, как в исходном отчёте):
```
high-bound: (3303 + 174 − 184) + 444 = 3737... 
```
пересчитано аккуратно: (3477 base upper − 184) + 444 = 3737 / 11949 = 31.28% (upper остаётся выше порога независимо).

**Диапазон после правки: 29.82% – 32.81%, медиана/основной расчёт 31.36%.**

## Вердикт и запас

- **Основной (наиболее защитимый) расчёт: 31.36%, запас +1.36 п.п. — формально проходит.**
- **Но margin <1.5 п.п. и нижняя граница чувствительности (29.82%) уходит под порог** — то есть ровно то предупреждение, о котором просил запрос: **запас недостаточно надёжен**, метрика по-прежнему переворачивается от одного subjective call (та же Q&A-классификация, что качнула исходный расчёт с 28.6% до 27.0%).
- Это **лучше**, чем было (медиана до правки — 28.6%, не проходила вовсе), правка сработала в заявленном направлении и по заявленному объёму (+444 in-bucket слов из +393 нетто прироста файла — почти весь прирост файла содержательно попал в bucket, что подтверждает точность правки). Но формальный проход на +1.36 п.п. при диапазоне чувствительности, ныряющем под порог, — это **не тот комфортный запас**, который можно закрыть без дальнейшего действия.

## Следующий шаг (если нужен комфortный запас, а не «еле-еле»)

Закрыть оставшиеся ~1.5–2 п.п. до **уверенного** прохождения (запас ≥3 п.п., т.е. numerator ≥ ~3660 при консервативной базе или ~13% буфера на денаминаторе) одним из:
1. Небольшое доп. расширение (+100–150 слов) любого из двух новых абзацев или третьего честного ограничения в §3.2/§3.3 (тот же паттерн ограничение→урок→критерий) — самый прямой путь.
2. Trim ~200–300 слов чисто механического out-контента в §3.3b/§3.3d (описание вендор-ландшафта/паттернов) — поднимает % через знаменатель без риска раздувания объёма (эта рекомендация уже была в исходном отчёте, п.2, не выполнена в этом раунде правки).
3. Комбинация 1+2 — самый безопасный путь к запасу, который не рушится от одного пограничного классификационного решения.

Без одного из этих шагов Часть 3 формально «проходит», но GATE будет одобрять метрику, которая статистически неотличима от непройденной.
