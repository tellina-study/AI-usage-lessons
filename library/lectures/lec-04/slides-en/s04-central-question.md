The lecture's question is about discipline, not about the tool

## Body

## Speaker notes

Let's formulate the central question the lecture will return to in every phase. AI writes code better and better — but what makes AI development reliable? Not the tool, but engineering discipline across the lifecycle phases: which human-owned artifact and which check are needed at each phase, where the methods of different players converge, and what is not delegated to the tool in any phase. The bottleneck of AI development is not typing code but the intent itself: precisely expressing what to build is still hard [1].

Notice the wording: this is not "what AI tools are there" and not "which tool is best." It is a question about practice. And the reason is precisely this: tools change from quarter to quarter, while the practice "between intent and code there is always a human-reviewed artifact" is stable for years. This is confirmed by the industry's systemic conclusion: AI amplifies what is already there — that is, discipline is primary and the tool secondary [2]. Moreover, the question "which tool is best" is poorly posed — best for what, in which phase, in which mode? Therefore, each time we name a tool, we will separate the durable pattern — that is, the method that will remain — from the vendor hype, the marketing exaggeration worth double-checking.

And the same applies to the goals of the lecture. None of them sounds like "be able to use tool X." The first — to recognize by phase where AI helps and where discipline is not replaced by a tool. The second — to distinguish method from vendor hype and understand why the tool is secondary [2]. The third — to apply the checklist of practices "when AI yes, when no" to your own task. The lecture's answer will be not "AI is good" and not "AI is bad", but an apparatus with which the engineer, for a specific phase, names the appropriate practice, its artifact, and the point of mandatory human control.
