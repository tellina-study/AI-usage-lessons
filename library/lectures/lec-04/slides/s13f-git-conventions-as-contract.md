# Visible content

## Title bar
Git-конвенции как контракт для агента — не свободный текст, а формат

## Body
[3 карточки в Ocean rounded box]

**Conventional Commits**
`type(scope): описание` — фиксированный набор типов (feat/fix/docs/refactor…).
→ парсится автоматически: генерирует changelog, определяет semver, фильтрует историю по типу.

**Именование веток**
`feature/`, `fix/`, префикс номера задачи (`feature/TASK-123-…`).
→ автосвязь ветки с трекером задач, без ручного указания номера в PR.

**Структурированные секции PR**
Summary / Test Plan / Breaking Changes — заполняются по шаблону, не «своими словами».
→ превращает описание PR в машинно-проверяемый чек-лист, а не в прозу, которую нужно интерпретировать.

[Teal callout]
Разница с обычной прозой не стилистическая: **формат парсится программой** (CI, генератор changelog, бот-линковщик), а не восстанавливается моделью из вольного текста заново на каждый запуск. Тот же принцип, что и у steering-файла, — конкретный, называемый формат вместо предположений.

## Speaker notes

Отдельный слой инженерной дисциплины — как агент коммитит и оформляет pull request. Здесь работает тот же принцип, что и со steering-файлом: машинно-читаемое правило вместо свободного текста.

Conventional Commits — формат `тип(область): описание`, где тип берётся из фиксированного набора значений: feat, fix, docs, refactor и так далее. Это не стилистическое пожелание — по этому формату автоматически генерируется changelog, определяется следующая версия по semver, фильтруется история коммитов по типу изменения.

Именование веток с префиксом типа и номером задачи — `feature/TASK-123-…` — даёт автоматическую связь ветки с трекером, без того чтобы кто-то вручную вписывал номер задачи в описание PR.

Структурированные секции pull request — Summary, Test Plan, Breaking Changes — заполняются по шаблону, а не пересказываются своими словами. Это превращает описание изменения в машинно-проверяемый чек-лист: можно автоматически проверить, что секция Test Plan не пустая, прежде чем разрешить merge.

Разница с обычной прозой не стилистическая, а функциональная: формат парсится программой — CI, генератором changelog, ботом, который линкует PR с задачей, — а не восстанавливается моделью заново из вольного текста на каждый запуск. Тот же принцип, что и у steering-файла в целом: конкретный, называемый формат вместо предположений о том, что имелось в виду.
