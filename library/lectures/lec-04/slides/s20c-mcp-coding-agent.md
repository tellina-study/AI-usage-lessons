# Visible content

## Title bar
MCP убирает человека-мост между агентом и системами вне репозитория — и тем же каналом открывает риск

## Body
[В центре — агент, встроенный доступ vs MCP-расширение]

Кодинг-агент по умолчанию видит только **файловую систему рабочей копии и шелл**. Этого хватает для кода, но не для issue-трекера, живого браузера, деплой-таргета — всего, что **вне репозитория**. Без MCP инженер сам копирует контекст туда-обратно.

MCP-сервер публикует список инструментов при подключении — агент видит их как обычные функции, решает, когда вызвать, **тем же циклом**, что и встроенные.

[Три примера — карточки]

**GitHub MCP server**: issues, PR, CI, алерты безопасности — по наборам (toolsets), выборочно. Явный **режим только для чтения**: инструменты на запись пропускаются, даже если запрошены.

**Playwright MCP server**: не скриншот, а **accessibility-дерево** — структурное описание элементов. Кликает, заполняет формы, генерирует тест.

**Filesystem MCP** — не один сервер, а класс: доступ к директориям **вне** рабочей копии (соседний репозиторий, общий диск).

[Мост к безопасности]
Один MCP-сервер часто закрывает **два угла** Lethal Trifecta одним подключением: доступ к данным (issues, приватные репо) **и** канал действия наружу (создать PR). Третий угол — недоверенный контент — прилетает через тот же сервер, когда агент читает чужой issue.

Задокументированный случай: GitHub MCP server — вредоносные инструкции в публичных issues эксфильтровали данные через создаваемые PR.

[Gold callout]
MCP только для чтения по умолчанию там, где запись не нужна; доступ на запись — осознанное решение о безопасности, а не настройка, которую никто не пересматривал.

## Speaker notes

MCP — открытый протокол для обнаружения и вызова внешних инструментов, мы разбирали его механику в третьей лекции. Здесь вопрос другой: что конкретно MCP даёт именно кодинг-агенту, чего у него нет без MCP. По умолчанию агент видит только файловую систему рабочей копии и shell — этого достаточно для кода, но недостаточно для всего, что вне репозитория: трекер задач, живой браузер, деплой-таргет, API непрерывной интеграции. Без MCP инженер остаётся человеком-мостом. MCP убирает мост: сервер публикует список своих инструментов при подключении, и агент видит их как обычные функции, решая, когда их вызвать, тем же циклом, что и для встроенных.

Три примера делают это конкретным. GitHub MCP server даёт доступ к issues, pull requests, CI — но по наборам инструментов, которые администратор включает выборочно; и здесь есть реальный переключатель — read-only режим, при котором write-инструменты пропускаются, даже если явно запрошены. Playwright MCP server даёт браузер для end-to-end проверки: агент получает не скриншот, а структурное accessibility-дерево — описание каждого интерактивного элемента текстом — и может сгенерировать Playwright-тест, воспроизводящий сделанное вручную. Filesystem MCP — не один сервер, а класс: доступ к файлам вне рабочей директории агента, другому репозиторию, общему диску.

Короткий мост к безопасности — подробный разбор Lethal Trifecta будет в разделе про ревью дальше по лекции, здесь его не повторяем. Специфика именно MCP в том, что один сервер часто закрывает сразу два угла трифекты одним подключением: доступ к данным и канал действия наружу — а третий угол, недоверенный контент, прилетает через тот же сервер, когда агент читает чужой issue. Задокументированный пример: GitHub MCP server позволял добираться до приватных репозиториев через issues с инструкциями prompt injection, которые эксфильтровали данные через создаваемые pull request. Отсюда инженерное следствие: read-only MCP по умолчанию там, где запись не нужна, и write-доступ — осознанное решение о риске, а не настройка, которую никто не пересматривал.
