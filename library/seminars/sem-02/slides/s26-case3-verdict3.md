# Протоколы встреч — разбор 2

## Assertion

Начинайте с простейшего варианта, усложняйте только когда требование не закрыть иначе

## Visual

Схема-расширение schema v2: прежние блоки (письмо → вызов модели → протокол
→ хранилище → индексация → поиск → фрагменты в модель) остаются на месте,
приглушены серым/бледным. Новые блоки выделены цветом и добавлены справа:
«извлечь поручение» → «вызвать API таск-трекера» → «создать задачу» →
«проверить результат». Внизу — отдельная строка-вывод: «каждое расширение
оплачено новым требованием». Никакой полосы вариантов под схемой.

## Speaker notes

Появилось действие во внешней системе: нужно вызвать API таск-трекера,
создать задачи, проверить, что они создались корректно, с правильным
исполнителем и сроком. Один вызов модели или даже поиск по базе такое не
закрывают — нужен workflow или полноценный агент, который вызывает
внешний инструмент и проверяет результат вызова. Смотрите на схему целиком:
прежний путь с хранилищем и поиском никуда не делся, он просто дополнен
справа новыми блоками — извлечь поручение, вызвать API, создать задачу,
проверить результат. Каждое расширение оплачено новым требованием: разовый
вызов был оправдан, пока входило всё в один транскрипт; RAG появился, когда
база выросла; агент появился, когда потребовалось действие во внешней
системе. Архитектурный выбор двигали конкретные новые требования, а не
мода на технологию. Начинайте с простейшего варианта, который решает
текущую задачу, и усложняйте только тогда, когда появляется требование,
которое простой вариант закрыть физически не может. Не наоборот.
