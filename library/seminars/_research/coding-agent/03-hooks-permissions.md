# Блок 3: хуки и разрешения/песочница — механические гарантии вместо честного слова

> Материал для семинара «Пошаговая сборка конфигурации кодинг-агента». Ступень: агент уже умеет писать код и коммитить; следующий вопрос — как заставить его *не мочь* нарушить правило, а не просто попросить не нарушать.

## Резюме (тезисы)

1. Правило, записанное словами в CLAUDE.md/system prompt, агент может проигнорировать (забыть, неверно интерпретировать, обойти под давлением задачи). Хук — это не просьба, а процесс, который харнесс исполняет сам, вне зависимости от того, «согласен» агент или нет.
2. Git-хук (`.git/hooks/*`) не версионируется по умолчанию и требует ручной установки в каждом новом клоне — типичный источник «мы же настраивали, почему не сработало». Хук Claude Code живёт в `.claude/settings.json`, коммитится вместе с репозиторием и автоматически активен в любом свежем клоне/воркtree — без отдельного шага установки.
3. У Claude Code на сегодня (сентябрь 2026) официально задокументировано свыше 30 событий хуков — от `SessionStart` до `WorktreeRemove`. Для старта нужны единицы: `PreToolUse` (запрет действия), `PostToolUse` (реакция после), `Stop`/`SessionStart` (проверки на входе/выходе).
4. Код возврата `2` блокирует действие безусловно — даже если тот же хук вернул JSON с `"allow"`. Формат ответа — `hookSpecificOutput.permissionDecision` (`allow`/`deny`/`retry`) внутри JSON на stdout; произвольный текст на stdout, не начинающийся с `{`, идёт в отладочный лог, а не агенту.
5. `deny`-правило в `permissions` побеждает любое более узкое `allow`-правило, и хук не может обойти явный `deny` из `settings.json` — deny всегда впереди allow, на любом уровне конфигурации.
6. Хук отказывает не громко, а тихо: удалённый/переименованный скрипт, неверный matcher, неподдерживаемое для события поле — и защита пропадает без единого сообщения об ошибке. «Не сработавший гейт выглядит точно как прошедший гейт» — это структурный риск, не гипотетический.
7. Хук — это ещё и исполняемый код в репозитории: два реальных CVE (2025–2026) показали, что вредоносный `.claude/settings.json` в чужом репозитории выполняет команды или крадёт API-ключ ещё до того, как пользователь успел прочитать диалог доверия к папке.
8. Хук работает на уровне одного вызова инструмента, а агент — на уровне многошагового плана: запрет `cat .env` не мешает агенту прочитать файл инструментом Read на предыдущем шаге и переслать его содержимое через `base64` в разрешённой команде.

## 1. Классическая база: что такое хук вообще

Хук в самом обычном, «не-ИИ» смысле — это скрипт, который система запускает сама в фиксированной точке жизненного цикла, без участия человека. Самый узнаваемый пример — git-хуки: файл `.git/hooks/pre-commit`, который git вызывает перед созданием коммита. Если скрипт завершается с ненулевым кодом — коммит не создаётся. Это ровно то же самое, что «правило» в голове разработчика («не коммить без прогона тестов»), только исполняемое механически.

У git-хуков есть два системных ограничения, которые касаются именно совместной работы:

- **они не версионируются вместе с репозиторием.** `.git/hooks/` — часть локального `.git`, git её не отслеживает; чтобы хук заработал у коллеги, кто-то должен вручную скопировать файл в каждый новый клон (или подключить отдельный инструмент вроде Husky, который сам это автоматизирует).
- **они молча отсутствуют, пока их не поставили.** Новый клон репозитория без хуков ведёт себя абсолютно нормально — никакого сообщения «у вас не настроена защита» не будет.

В этом же проекте пример другого типа git-хука лежит рядом: `.claude/hooks/pre-commit-viz.sh` в `lessons-3bb49d40` — он не блокирует коммит, а перегенерирует визуализации онтологии, если изменились файлы `ontology/`. Это иллюстрация того, что git-хуки бывают не только «стоп-краном», но и автоматизацией по триггеру («если изменилось X — пересчитай Y»). Важно не путать: несмотря на путь `.claude/hooks/`, это **git pre-commit hook**, а не хук Claude Code — он никак не встроен в жизненный цикл агента и сработает даже если коммит делает человек руками, без всякого ИИ.

**Хук Claude Code — другой механизм.** Он не про git-события, а про события в жизненном цикле самого агента: перед вызовом инструмента, после него, перед отправкой промпта, при завершении хода и т. д. Он может не просто среагировать постфактум, а **запретить действие до того, как оно произошло** — например, не дать выполниться команде `git commit`, а не откатывать её после. И главное отличие для совместной работы: хук Claude Code настраивается в `.claude/settings.json`, обычном JSON-файле проекта, который коммитится в git точно так же, как любой код. Он автоматически активен в любом свежем `git clone` или `git worktree add` — установочного шага нет вообще.

Рабочий пример из этого же репозитория (`/tmp/ahr/templates/base-project-template/with-git/.claude/settings.json`) блокирует прямой коммит в `main`/`master`:

```jsonc
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.command' | { read -r cmd; if echo \"$cmd\" | grep -qE '(^|[;&|]\\s*)git\\s+commit\\b'; then if ! git rev-parse --is-inside-work-tree >/dev/null 2>&1; then echo '{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"ask\",\"permissionDecisionReason\":\"WARNING: branch-protection gate inactive — не git-репозиторий, проверить нечего\"}}'; exit 0; fi; branch=$(git symbolic-ref --short HEAD 2>/dev/null); if [ \"$branch\" = \"main\" ] || [ \"$branch\" = \"master\" ]; then echo '{\"hookSpecificOutput\":{\"hookEventName\":\"PreToolUse\",\"permissionDecision\":\"deny\",\"permissionDecisionReason\":\"BLOCKED: direct commit to main/master. Create a feature branch first.\"}}'; exit 0; fi; fi; }",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

Разбор построчно:

- `"matcher": "Bash"` — хук вызывается только перед вызовами инструмента `Bash`, не перед `Edit`/`Read` и т.п.
- `jq -r '.tool_input.command'` — Claude Code передаёт хуку JSON с описанием предстоящего вызова через **stdin**; `jq` вытаскивает поле `tool_input.command` — именно ту команду, которую сейчас попытаются выполнить.
- `read -r cmd` — читает эту команду в переменную оболочки для дальнейших проверок.
- `grep -qE '(^|[;&|]\s*)git\s+commit\b'` — ищет `git commit` как отдельную команду (в начале строки или после `;`, `&&`, `|`), а не как подстроку внутри другого слова.
- Почему `git symbolic-ref --short HEAD`, а не более привычный `git rev-parse --abbrev-ref HEAD`: у свежесозданного репозитория без единого коммита («unborn HEAD») `rev-parse --abbrev-ref` завершается ошибкой и молча оставляет проверку ветки нерабочей. `symbolic-ref --short HEAD` корректно резолвит имя ветки и в этом крайнем случае, и в обычном.
- Проверка `! git rev-parse --is-inside-work-tree` — что если это вообще не git-репозиторий (например, шаблон скопировали в обычную папку до `git init`)? Хук **не** пропускает коммит молча (это выглядело бы как защита, хотя защиты нет), а возвращает `permissionDecision: "ask"` с явным предупреждением — принцип «гейт, который отказывает молча, не доказан, пока его не заставили отказать громко».
- Ответ в формате `hookSpecificOutput.permissionDecision` — современный формат JSON-ответа хука (устаревший `decision`/`reason` тоже поддерживается для обратной совместимости, но новый формат — стандарт).

Ключевой тезис из `CLAUDE.md` этого же шаблона (`/tmp/ahr/templates/base-project-template/with-git/CLAUDE.md`), который стоит процитировать студентам дословно:

> «Every rule in this file that's stated as binding/mandatory should have a mechanical check (a hook, a CI step, a lint rule) landing in the same change, or it should be labeled advisory... a gate is not installed because its file exists — it is installed once observed firing against a real case.»

То есть: обязательное правило без механической проверки — это не правило, а пожелание, помеченное как обязательное по ошибке. И гейт не «работает», потому что файл лежит в репозитории — он работает, когда его видели сработавшим на реальном кейсе.

## 2. Полный список событий хуков Claude Code

По официальной документации на сегодня (`code.claude.com/docs/en/hooks`, дата обращения 20.09.2026) события сгруппированы по фазам жизненного цикла сессии:

**Сессия целиком:** `SessionStart` (начало/резюме сессии), `Setup` (разовая инициализация при `--init`/`--maintenance`), `SessionEnd` (завершение).

**Каждый ход (turn):** `UserPromptSubmit` (до обработки промпта пользователя), `UserPromptExpansion` (раскрытие слэш-команды в промпт), `Stop` (агент закончил отвечать — можно не дать остановиться), `StopFailure` (ход прервался из-за ошибки API).

**Вызовы инструментов:** `PreToolUse` (до вызова — можно заблокировать), `PostToolUse` (после успешного вызова), `PostToolUseFailure` (после неуспешного), `PostToolBatch` (после пачки параллельных вызовов), `PermissionRequest` (нужно решение по разрешению), `PermissionDenied` (авто-режим отказал в вызове).

**Субагенты:** `SubagentStart`, `SubagentStop`, `TaskCreated`, `TaskCompleted`, `TeammateIdle`.

**Файлы и окружение:** `FileChanged` (отслеживаемый файл поменялся на диске), `CwdChanged`, `DirectoryAdded`, `WorktreeCreate`, `WorktreeRemove`.

**Конфигурация:** `ConfigChange`, `InstructionsLoaded` (загрузился CLAUDE.md/`.claude/rules/*.md`), `PreCompact`/`PostCompact` (сжатие контекста).

**Модель:** `PreModelSwitch` (можно заблокировать переключение модели), `PostModelSwitch`.

**MCP и интерфейс:** `Elicitation`/`ElicitationResult` (MCP-сервер запрашивает ввод пользователя), `Notification`, `MessageDisplay`.

Для семинара важно проговорить: этот список за последние два года вырос примерно втрое (в ранних версиях документировалось около 8–9 событий — `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SubagentStop`, `SessionStart`, `SessionEnd`, `PreCompact`, `Notification`). Практический вывод: **перед тем как строить хук на конкретное событие, проверяйте актуальный список командой `/hooks` в сессии или в документации**, а не по памяти — API меняется быстрее, чем конспекты.

### Коды возврата

- **`0`** — успех. Claude Code парсит JSON со stdout, если он есть (строка начинается с `{` и заканчивается `}`); иначе текст уходит в отладочный лог (или, для некоторых событий вроде `UserPromptSubmit`, становится контекстом для агента). Отсутствие JSON-решения = обычный ход событий, ничего не заблокировано.
- **`2`** — блокирующая ошибка. Блокирует действие **безусловно**, даже если JSON в том же ответе содержит `permissionDecision: "allow"` — exit-код побеждает JSON. Причина блокировки берётся из stderr или из `reason` в JSON. Работает не на всех событиях: блокируемые — `PreToolUse`, `UserPromptSubmit`, `UserPromptExpansion`, `PreModelSwitch`, `Stop` (не даёт агенту остановиться). На неблокируемых событиях (`PostToolUse`, `PermissionRequest`, `Elicitation` и др.) код `2` игнорируется — действие уже произошло или управляется другим полем.
- **Другие коды (1, 3...)** — неблокирующая ошибка: действие проходит, но в транскрипте отмечается «hook error». Если при этом хук всё же напечатал валидный JSON — он применяется, просто ход помечается как «упавший». Исключение: `WorktreeCreate`/`WorktreeRemove` падают при любом ненулевом коде, JSON не спасает.

### Формат JSON-ответа

Универсальные поля внутри `hookSpecificOutput`: `hookEventName`, `systemMessage` (текст, видимый агенту как контекст — не на всех событиях), `terminalSequence` (управление терминалом).

Решающие поля по типам событий:

| Событие | Поле | Значения | Эффект |
|---|---|---|---|
| `PreToolUse`, `PostToolUse`, `PermissionRequest`, `PermissionDenied` | `permissionDecision` | `allow` / `deny` / `retry` | разрешить/заблокировать/разрешить повтор |
| `UserPromptSubmit` | `permissionDecision` | `deny` | блокирует промпт (стирает ввод) |
| `PreModelSwitch` | `permissionDecision` | `deny` | блокирует смену модели |
| `Stop` / `SubagentStop` | `continue` + `stopReason` | `true`/строка | не дать агенту остановиться, с объяснением почему |

Поле `additionalContext` (тоже внутри `hookSpecificOutput`) — способ не просто заблокировать, а **объяснить агенту, что делать вместо этого** («Use safer alternatives like: rm -i»). Это отдельная, важная для педагогики фишка — см. раздел 7.

### Matcher (по чему фильтруется срабатывание хука)

- `"*"`, `""` или отсутствие поля — сработает всегда.
- Строка из букв/цифр/`_`/`-`/пробелов/`,`/`|` — точное совпадение или список через `|` (например, `Edit|Write`).
- Любые другие символы — трактуется как нерегулярное (unanchored) регулярное выражение (`^Bash$`, `mcp__.*`).
- MCP-инструменты называются `mcp__<сервер>__<инструмент>`; голое имя сервера без `.*` ничего не заматчит.
- У каждого события — своя семантика matcher: для `SessionStart` это тип старта (`startup`/`resume`/`clear`/`compact`/`fork`), для `SubagentStart`/`SubagentStop` — тип субагента, для `PreCompact` — триггер (`manual`/`auto`), для `Notification` — тип уведомления и т.д. Единого «имени инструмента» для всех событий нет — это частый источник ошибки, когда matcher, работающий на `PreToolUse`, молча ничего не делает на `SessionStart`.

## 3. Разрешения и песочница

### Слои `settings.json`

Порядок приоритета — от высшего к низшему (официальная документация, `code.claude.com/docs/en/settings`):

1. **Managed settings** — политика организации (`managed-settings.json`, MDM, консоль claude.ai). Перекрывает всё, кроме нескольких ключей безопасности, которые управляемая политика в принципе не может ослабить (список — «exceptions to managed settings precedence»).
2. **Командная строка** (`claude --settings`) — на одну сессию.
3. **`.claude/settings.local.json`** — лично для вас в этом проекте; по умолчанию в `.gitignore`, не уезжает в репозиторий.
4. **`.claude/settings.json`** — общий для всех, кто работает в проекте; коммитится в git.
5. **`~/.claude/settings.json`** — лично для вас, во всех проектах на этой машине.

Важная деталь для хуков конкретно: **массивы (в том числе списки хуков) не перезаписываются между уровнями, а объединяются** («Lists merge instead of overriding»). Значит, если у вас в `~/.claude/settings.json` есть свой хук на `PreToolUse`, а в проектном `.claude/settings.json` — другой хук на то же событие, сработают **оба**, а не один вместо другого. Это отличается от скалярных настроек (модель, тема), где более специфичный уровень действительно перекрывает менее специфичный.

### allow / deny / ask

Правила разрешений задаются в виде `Инструмент(спецификатор)`, например `Bash(aws s3 ls)`, `Bash(*)` (=`Bash`, весь инструмент). Приоритет между списками:

- **`deny` побеждает `allow` всегда**, даже если `allow`-правило точнее. Пример из документации: `Bash(aws *)` в `deny` блокирует **все** вызовы `aws`, включая те, что совпадают с более узким `allow`-правилом вроде `Bash(aws s3 ls)` — allow не может «прорезать дыру» в deny.
- Та же логика для `ask` над `allow`: если правило `ask` совпадает с вызовом, будет спрошено подтверждение, даже если более специфичный `allow` тоже совпадает.
- **Хук не обходит `permissions`.** Явное `deny`-правило блокирует вызов независимо от того, что вернул `PreToolUse`-хук. А блокирующий хук (exit `2`) в свою очередь побеждает `allow`-правило — то есть хук может *добавить* запрет поверх широкого allow (типичный паттерн: разрешить весь `Bash`, а конкретные опасные команды резать хуком), но не может *снять* явный deny.
- Это же правило работает и между уровнями конфигурации: `deny` в пользовательских настройках блокирует `allow` в проектных, и наоборот — deny с любого уровня проверяется раньше allow.

### Режимы разрешений

- **`default`** — спрашивает подтверждение почти на всё, кроме чтения файлов в рабочей директории и встроенного списка read-only bash-команд.
- **`acceptEdits`** — автоматически принимает правки файлов, остальное по обычным правилам.
- **`plan`** — агент только читает и планирует, не выполняет изменяющих действий.
- **`bypassPermissions`** (он же `--dangerously-skip-permissions`) — не спрашивает вообще ничего. Название режима — не случайность: это явный, «кричащий» флаг в самом ключе, чтобы его нельзя было включить случайно и не заметить.

### Песочница (sandbox)

Отдельно от логики разрешений в `settings.json`, Claude Code умеет выполнять bash-команды в **песочнице на уровне ОС**: на macOS — через встроенный фреймворк Seatbelt, на Linux/WSL2 — через два системных пакета с seccomp-фильтром. Песочница ограничивает файловую систему и сеть *на уровне ядра*, а не на уровне решения агента — то есть даже если сам агент «решит» обойти правило, операционная система физически не даст процессу выйти за объявленные границы (какие файлы/домены разрешены). При включённой песочнице и `autoAllowBashIfSandboxed: true` (по умолчанию) bash-команды внутри песочницы выполняются без запроса подтверждения — граница песочницы **замещает** запрос разрешения, а не отменяет его смысл.

### Почему «разрешить всё» — плохая идея (и когда оправданно)

Без ограничений агент, столкнувшись с вредоносным содержимым в файле, веб-странице или выводе MCP-инструмента (prompt injection), выполнит вредоносную инструкцию с теми же правами, что и легитимную — потому что для него это просто следующий шаг плана. `bypassPermissions`/широкий `allow` убирают последний барьер именно в момент, когда агент дальше всего от контроля человека. Оправданно это в одноразовом изолированном окружении без секретов и без сети наружу (контейнер CI, эфемерная VM) — то есть когда роль ограничителя уже выполняет **инфраструктурная** изоляция (песочница/контейнер), а не решение агента.

## 4. Лестница хуков: что ставить первым

| Порядок | Хук | Что запрещает/делает | Триггер «когда становится нужно» |
|---|---|---|---|
| 1 | Защита ветки | `PreToolUse` на `Bash`, блокирует `git commit`/`git push` в `main`/`master` | как только появилась общая ветка, в которую можно случайно закоммитить напрямую (даже соло-разработчик — потеряете линейную историю фиксов) |
| 2 | Запрет опасных команд | `PreToolUse` на `Bash`, deny-список (`rm -rf /`, `git push --force` в защищённые ветки, `curl \| bash`, запись в `.env`/секреты) | после первого реального близкого промаха или инцидента с разрушительной командой — не превентивно на пустом месте |
| 3 | Форматирование/линт после правки | `PostToolUse` на `Edit\|Write`, запускает `prettier`/`black`/`eslint --fix` | когда стиль кода агента начинает расходиться и линт в CI начинает падать на PR |
| 4 | Проверка перед завершением задачи | `Stop`, проверяет что тесты прогнаны / чек-лист закрыт / `continue: true` если нет | когда агент несколько раз объявлял задачу выполненной с незакрытыми пунктами |

Логика та же, что в «growth ladder» этого же шаблона (`design-and-usage.md`): не строить все четыре хука заранее «на всякий случай», а добавлять по одному, когда конкретный риск из абстрактного стал реальным — «heavy/critical code → extend the PreToolUse hook array... same git-tracked mechanism, one more entry». Хуки 3 и 4 при этом дешевле и менее рискованны, чем 1 и 2: они не блокируют, а реагируют/напоминают, поэтому с них не страшно начать, если blast radius проекта пока мал.

## 5. Провалы и ограничения

### Хук, который молча не срабатывает

Самый частый и самый опасный класс отказа — не «хук выдал неверный вердикт», а «хука как будто не было». Причины, задокументированные независимо (Alex Dunlop, «Claude Code Hook Not Firing», 2026 — decision tree на основе issues репозитория `anthropics/claude-code`):

- **Один невалидный matcher в `settings.json` отключает все хуки в файле** целиком, без единой ошибки в интерфейсе — «a single schema-invalid matcher anywhere in `settings.json` silently disables every hook in that file».
- Скрипт хука удалён, переименован или потерял право на выполнение — вызов «fail-open» (не блокирует, просто не срабатывает).
- Matcher не совпал из-за регистра (`bash` ≠ `Bash`) или неанкорованного regex (`Edit.*` матчит и `NotebookEdit`, чего не ждали).
- Вызовы Bash/Edit/Write/Read/Grep, сделанные **субагентом** через инструмент `Agent`, по сообщённому в issue #34692 поведению не триггерят `PreToolUse`/`PostToolUse` хуки родительской сессии — без какого-либо индикатора, что хуки были пропущены.
- Таймаут: у `UserPromptSubmit` таймаут по умолчанию 30 секунд против 600 у большинства других событий; хук `PreToolUse`, который не уложился в таймаут, **не блокирует** вызов — он просто отваливается, и вызов инструмента идёт по обычному пути разрешений, как если бы хука не было вовсе. То есть «медленный» защитный хук превращается не в строгий, а в тихо отключённый.

Вывод, который стоит процитировать студентам дословно: «when a gate doesn't fire, nothing happens, which is exactly what a passing gate looks like» — не сработавший гейт неотличим от сработавшего-и-пропустившего по своему внешнему поведению.

### Хук как вектор атаки (реальные CVE)

Поскольку `.claude/settings.json` — обычный файл репозитория, любой, у кого есть право на коммит (или кто прислал PR/дал ссылку на форк), может вписать туда вредоносный хук.

- **CVE-2025-59536** (CVSS 8.7, Check Point Research). Вредоносный хук на `SessionStart` в `.claude/settings.json` выполняется, как только жертва клонирует репозиторий и запускает `claude` — команды из хука уже отработали в фоне к моменту, когда диалог доверия к папке вообще появился на экране, а формулировка диалога («файлы могут быть выполнены с вашего разрешения») не предупреждала явно, что именно хук-команды запустятся автоматически. Найдена/сообщена 21.07.2025, патч 26.08.2025, публикация advisory 29.08.2025.
- **CVE-2026-21852** (CVSS 5.3). Два связанных вектора: (1) вредоносный `ANTHROPIC_BASE_URL` в `.claude/settings.json` перехватывал API-ключ пользователя в открытом виде ещё до подтверждения доверия к папке; (2) `enableAllProjectMcpServers` в настройках репозитория обходил диалог согласия на подключение MCP-серверов — «immediately upon running claude — before the user could even read the trust dialog». API-эксфильтрация сообщена 28.10.2025, патч 28.12.2025, CVE опубликован 21.01.2026.

Актуальная официальная документация (`code.claude.com/docs/en/permissions`, раздел «What runs before you trust a folder», дата обращения 20.09.2026) прямо перечисляет, что запускается ещё **до** прохождения диалога доверия, даже сегодня, уже после патчей: хуки из settings-файлов, блок `env`, помощники вроде `apiKeyHelper` — помечены «Used» (используются) и когда доверена только родительская папка, и в режиме `claude -p`/SDK, где диалог доверия вообще никогда не показывается. Это не баг, а осознанно документированный компромисс — что прямо подчёркивает: **хуки — единственный из перечисленных механизмов, который в принципе не блокируется отсутствием доверия к папке**, поэтому именно они — самая частая точка входа для атаки через репозиторий.

Для сравнения — та же категория проблем в другом популярном агентном редакторе, Cursor:

- **CVE-2025-59944** — уязвимость чувствительности к регистру, позволявшая обойти проверку auto-run команд (Lakera, 2025).
- **CurXecute, CVE-2025-54135** (CVSS 8.6) — RCE через prompt injection, патч в версии 1.3 от 29.07.2025 (Tenable).
- **MCPoison** — после того как пользователь один раз одобрил MCP-сервер, конфигурацию можно незаметно подменить и получать постоянное скрытое выполнение кода без повторного запроса согласия (Check Point Research) — урок для семинара: «одобрено один раз» не значит «безопасно навсегда», конфиг нужно перепроверять, а не доверять по инерции.
- **DuneSlide, CVE-2026-50548/50549** (CVSS 9.8) — обход песочницы IDE через zero-click prompt injection (Cato Networks, 2026).

Вывод для аудитории: это не специфика конкретного продукта, а системный риск класса «конфигурация агента = исполняемый код, который приезжает вместе с недоверенным репозиторием».

### Обход хука самим агентом

Хук уровня `PreToolUse` видит **один вызов инструмента в изоляции**; агент действует на уровне многошагового плана с целью и контекстом. Это структурное несоответствие — не баг конкретной реализации:

- **Документированный в этом же проекте («live-confirmed in dogfooding») случай**: хук проверяет ветку **до** выполнения всей bash-команды — значит `git switch feature-x && git commit ...` в одном вызове получает отказ по *старой* ветке, хотя после `switch` коммит лёг бы корректно. Обход здесь не злонамеренный, а естественный побочный эффект того, как хук видит команду — целиком, но не после промежуточных эффектов.
- **base64/промежуточный файл**: запрет команды `cat .env` не мешает агенту прочитать файл инструментом `Read` на предыдущем шаге (Read вообще может не матчиться под `Bash`-хук), закодировать содержимое в `base64` и переслать его через разрешённую команду или записать во временный файл — с точки зрения хука это просто безобидная команда, потому что хук не знает, что этот шаг — продолжение плана «достать секрет» (dev.to, «Why Claude Code PreToolUse Hooks Can Still Be Bypassed», 2026).

Практический вывод: хук на `Bash` — это фильтр на **синтаксис одной команды**, а не на **намерение**. Для действительно чувствительных данных (секреты, ключи) надёжнее файловый/сетевой барьер (deny-правило на чтение файла + песочница), а не попытка перечислить все способы, которыми можно прочитать и переслать байты.

### Таблица «провал / что произошло / урок»

| Провал | Что произошло | Урок |
|---|---|---|
| Тихий сбой matcher | Один невалидный matcher в `settings.json` отключил все хуки файла без единой ошибки | После правки `settings.json` — обязательный самотест (провоцирующий истинное срабатывание), не просто валидный JSON |
| Таймаут = не блокировка | `PreToolUse`-хук не уложился в таймаут — вызов прошёл по обычному пути разрешений, как без хука | Не делайте защитный хук медленным/сетезависимым; таймаут — это тихое «allow», а не «deny» |
| Chained-команда | `git switch x && git commit ...` денайнут по *старой* ветке — хотя коммит лёг бы верно | Хук видит команду до выполнения; не связывайте рискованное действие и его предпосылку в один вызов |
| RCE через SessionStart-хук (CVE-2025-59536) | Клонировали репозиторий → запустили `claude` → вредоносный хук выполнился до диалога доверия | Не запускайте `claude` в непроверенном клоне без `--settings '{"disableAllHooks": true}'` или `--setting-sources user` |
| Эксфильтрация API-ключа (CVE-2026-21852) | `ANTHROPIC_BASE_URL` в чужом `settings.json` перехватил ключ ещё до подтверждения доверия | Проверяйте `.claude/settings.json` из PR/форков так же, как код — это исполняемая конфигурация, не текст |
| base64-обход | Запрет `cat .env` не помешал прочитать файл через `Read` и переслать закодированным | Хук на синтаксис команды — не барьер на намерение; для секретов нужен барьер на уровне файла/сети, а не список запрещённых команд |

## 6. Когда хук здесь не нужен

- **Проверка дешевле в CI/линтере.** Если правило можно проверить один раз на PR (типы, тесты, линт), не стоит гонять ту же проверку на каждый `PostToolUse` в интерактивной сессии — это дублирование стоимости без выигрыша: CI всё равно última инстанция перед мержем.
- **Хук превращается в тормоз.** «Hook bloat has no error message. Nothing fails. Everything just gets slower, gradually» (Alex Dunlop) — если на каждый вызов `Bash`/`Edit` навешано пять последовательных хуков, сессия ощутимо тормозит, и это не диагностируется как ошибка, а просто снижает продуктивность работы с агентом.
- **Правило по сути не механизируемо.** Хук может проверить синтаксис (совпадение с regex, наличие файла, код возврата линтера), но не смысл («не переусложняй», «пиши по делу», «выбери разумную абстракцию»). Такие правила честнее оставить рекомендательными в CLAUDE.md и проверять на review/gate человеком или критик-субагентом — попытка «захукать» суждение даёт ложное чувство контроля без реальной механики (см. Roast-Before-Implement Rule этого же курса — там роль ревью намеренно остаётся за человеком/критиком, не за хуком).
- **Соло-разработчик, низкий blast radius.** Не каждое командное правило масштабируется на одного человека и один репозиторий — growth ladder шаблона прямо предлагает добавлять хук только когда риск конкретного действия (production-путь, security-чувствительный код) стал реальным, а не заранее «на всякий случай».

## 7. Фишки для продвинутых

**Самотест хука.** Гейт не «установлен», пока его не заставили сработать на реальном (или намеренно спровоцированном) кейсе — создайте одноразовый тестовый репозиторий/ветку, выполните действие, которое хук обязан заблокировать, и убедитесь, что блокировка пришла с правильным сообщением. Повторяйте периодически: обновление Claude Code, рефакторинг `settings.json` или смена matcher-синтаксиса (задокументирован случай, когда поведение matcher для дефисных имён инвертировалось между версиями) может незаметно выключить хук.

**«Unverified» честнее вычисленного «pass».** Если проверка зависит от внешнего входа, который может не сработать (сеть, API, отсутствующая зависимость) — хук должен явно вернуть «не проверено», а не по умолчанию посчитать успехом. Вычисленный «pass» неотличим от настоящего именно в тот момент, когда это важнее всего.

**Хук как обучающая обратная связь, а не просто стоп-кран.** Поле `additionalContext`/`permissionDecisionReason` — способ не молча отказать, а объяснить агенту, что делать вместо запрещённого действия («Destructive command blocked — use `rm -i` or scope the path»). Хук, который только блокирует без объяснения, заставляет агента угадывать; хук, который объясняет, экономит следующий ход.

**Matcher по инструменту — узко и предсказуемо.** `Bash` матчит все bash-вызовы; `Edit|Write` — конкретные инструменты правки; `mcp__memory__.*` — все инструменты одного MCP-сервера. Чем шире matcher, тем больше ложных срабатываний и тем выше цена ошибки в самой логике хука (каждый лишний вызов — это ещё и латентность).

**Чтение stdin через `jq`.** Claude Code передаёт хуку JSON-описание события через stdin, а не через переменные окружения или аргументы — стандартный паттерн: `jq -r '.tool_input.command'` для команды bash, `jq -r '.tool_input.file_path'` для пути редактируемого файла. Это же самое стоит показать студентам как общий приём: любой хук начинается с того, что вы «распаковываете» JSON, а не парсите произвольный текст.
