# Зачем субагенту отдельное контекстное окно

**Date:** 2026-10-02 · **Issue:** #217-EXP

| утверждение | источник | тип |
|---|---|---|
| Отдельное окно субагента изолирует контекст от родителя и других субагентов | архитектура multi-turn LLM | ежедневная практика |
| Размер окна (context window) — критический ресурс при параллельной работе нескольких агентов | CAO/harness-control слой управления сессиями | инженерный факт |
| Общее окно создаёт race conditions и информационный шум в длинных сессиях | опыт производства лекций, Лекция 4-10 | наблюдение |

## Основная идея

Субагенту нужно отдельное контекстное окно, потому что:

1. **Фокус.** Агент сосредоточен на одной задаче без шума других параллельных работ — не видит история других субагентов, не перемешивает state.

2. **Масштабируемость.** При параллельной работе (3–4 субагента одновременно) единое окно переполняется быстро. Отдельные окна позволяют балансировать tokens: big task → big window, quick check → small window.

3. **Безопасность контекста.** В единое окно легко просочится sensitive data из другого агента или предыдущей фазы. Разделение окон — естественный boundary для конфиденциальности и audit trail.

4. **Воспроизводимость.** Детерминированный результат субагента зависит от его окна, не от порядка других агентов. Проще отладить и повторить.

5. **Ресурсное управление.** Оркестратор видит usage subagent's по отдельности (не усреднённо), может лучше распределить quota и обнаружить problem early.

**Альтернатива** — один большой окно на всех — создаёт информационный хаос в production (Лекция 2–9 production: ~50+ agentурных взаимодействий, полный лог становится неуправляем).

## Что НЕ доказано

— Точные метрики overheads отдельного окна (task-dispatch latency, token амортизация на headers).
— Нижняя граница размера окна, при которой isolation становится неэффективен.
— Оптимальная частота обновления контекста между фазами.
