# Резюме (тезисы)

1. **Механика хуков не изменилась с 20.09.2026** — список событий, коды возврата, формат JSON-ответа, приоритет `deny` над `allow`, слияние списков хуков между уровнями настроек остаются такими, как описаны в базовом исследовании. Официальная документация сегодня перечисляет **33** события жизненного цикла (было «свыше 30» в базовом документе) — рост подтверждён, но некритичен для занятия.
2. **Самое ценное новое — не про механику хука вообще, а про ровно тот хук, который уже используется в материале курса.** 20.09.2026 внешняя ревью-сессия того же цикла, что проверяла Семинар 4, провела пять раундов адверсариального тестирования именно против нашего grep-хука защиты ветки и нашла четыре конкретных обхода синтаксиса одной команды: `/usr/bin/git commit`, `env git commit`, `git -C . commit`, многострочная команда.
3. **Найден шестой и седьмой задокументированные способы тихого отказа хука**, которых нет в базовом исследовании: (1) режим `bypassPermissions` в определённых сценариях подменяет инструмент чтения/записи на `Bash`-команды и тем самым тихо отключает хуки, привязанные к `Edit|Write` (issue `#92271`, 05.09.2026); (2) хуки, объявленные во frontmatter конкретного субагента, не срабатывают вовсе, тогда как идентичный хук в проектных настройках — срабатывает (issue `#95650`, 20.09.2026).
4. **Найдена новая CVE именно про обход диалога доверия для запуска хуков** — `CVE-2026-40068` (CVSS 7.7, патч в версии 2.1.84): подделанный путь `git worktree commondir` заставляет харнесс решить, что папка уже доверена, и хуки из чужого `.claude/settings.json` выполняются без единого запроса подтверждения. Это глубже базового `CVE-2025-59536` — там диалог доверия хотя бы появлялся (просто хуки успевали отработать раньше), здесь диалог не показывается вообще.
5. **Прямой численной базы для утверждения «столько-то процентов нарушений правила файла инструкций» не нашлось** — ни в контролируемом эксперименте на 1650 сессиях Claude Code (только затухание соблюдения на ~5,6% шансов за каждую следующую функцию сессии, не исходная доля), ни в смежном исследовании конфликта правил (64,6% — другая метрика, не про одно однозначное правило). Это честный пробел, а не находка.
6. **Контринтуитивный поворот про «хук не видит человека, печатающего `git commit` напрямую в терминале» — не внешняя находка, а собственное наблюдение курса**, зафиксированное в `owner-questions.md` того же ревью-цикла (пункт 5) и структурно верное: `PreToolUse` — событие жизненного цикла агента, оно не перехватывает произвольный процесс, запущенный человеком в независимой оболочке.
7. **Падение `git rev-parse --abbrev-ref HEAD` на репозитории без коммитов лично воспроизведено в этой сессии** (код возврата 128) в контрасте с корректной работой `git symbolic-ref --short HEAD` (код возврата 0) — это самый сильный уровень доказательства из возможных: не цитата, а прямое повторение эксперимента.
8. **Найдена новая архитектурная рекомендация, полезная для раздела «предотвращаем vs решаем»**: не пытаться расширять текстовый grep-паттерн до покрытия всех синтаксических форм git-команды (структурно неполная задача — POSIX раскрывает слова непосредственно перед выполнением, после того как хук уже принял решение по тексту), а строить три слоя — git-hook «пол», платформенный ruleset «потолок», и узкий `PreToolUse`-хук, ловящий только заведомые попытки отключить защиту (`--no-verify`, манипуляция `core.hooksPath`, переменные окружения менеджеров хуков).

- **`anthropics/claude-code#95650`** — баг-репорт: хук, объявленный во frontmatter конкретного субагента (не в проектном `settings.json`), не срабатывает на `PreToolUse` на версии 2.1.258, хотя идентичный хук в `settings.json` для того же субагента срабатывает и блокирует корректно. ## 1.2. Существовало раньше 20.09.2026, но не попало в базовое исследование

Формально это не «новое после 20.09», но раз обнаружено сейчас — стоит знать, и это прямо закрывает часть требуемых разрывов:

- **`CVE-2026-40068`** (CVSS 7.7; NVD-публикация 05.05.2026, обновление 07.05.2026; версии 2.1.63–2.1.83; патч в 2.1.84). Механизм: харнесс хранит список доверенных директорий и для git worktree резолвит канонический путь репозитория через файл `.git/commondir` — без проверки его содержимого. Подделанный `commondir`, указывающий на путь, уже присутствующий в списке доверенных, заставляет харнесс пропустить диалог доверия целиком и сразу выполнить хуки из `.claude/settings.json`. Это структурно отличается от `CVE-2025-59536` из базового исследования: там хуки выполнялись в узком временном окне *до того, как диалог доверия успевал прогрузиться на экран* — диалог всё же должен был появиться. Здесь диалог не появляется вообще, потому что харнесс считает папку уже доверенной.
- **`anthropics/claude-code#92271`** (05.09.2026, закрыт). В режиме `bypassPermissions` харнесс — на части моделей, за флагом `CLAUDE_CODE_THRIFTY_SONIC` — добавляет мета-инструкцию: предпочитать `Bash`-команды (`cat`, `sed`, эвристики через `grep`/`find`) выделенным инструментам `Read`/`Edit`/`Write`. Автор issue воспроизвёл ровно тот случай, который относится к теме занятия: хук, привязанный `matcher`-ом к `Edit|Write`, никогда не видит правку, сделанную через `sed -i` или heredoc в `Bash`, — потому что формально это вызов инструмента `Bash`, а не `Edit`. Разбор в §1.3 таблицы «модель × флаг» показывает, что на момент issue инструкция была активна для `fable[1m]`, но не для `claude-sonnet-5[1m]` и не для `haiku` без явного флага — то есть эффект модельно-зависимый и непостоянный, что делает его ещё труднее диагностировать вслепую. Воркэраунд: `"env": {"CLAUDE_CODE_THRIFTY_SONIC": "0"}` в `settings.json`.
- **`CVE-2026-35603`** (раскрытие Anthropic 05.01.2026, публикация 11.08.2026). Другой канал: на Windows системный каталог `C:\ProgramData\...` для `managed-settings.json` был доступен на запись любому локальному пользователю с низкими правами — то есть локальный непривилегированный процесс мог подложить вредоносный `managed-settings.json`, который применяется системно ко всем пользователям машины, включая администраторов, и содержит хук-триггеры. Важная деталь для занятия: та же категория уязвимости нашлась параллельно в трёх других агентных инструментах (Cursor `hooks.json`, Codex CLI `config.toml`, Gemini CLI `system-defaults.json`) — Claude Code единственный из четырёх на сегодня пофикшен (2.0.76), причём Anthropic перенесла настройки в защищённый от записи каталог и уведомила клиентов проактивно, до публикации; у остальных трёх — не решено. Это полезный контраст «реакция вендора бывает разной» без домысливания причин.
- **arXiv `2605.10039`**, «Instruction Adherence in Coding Agent Configuration Files: A Factorial Study of Four File-Structure Variables» — контролируемый эксперимент (Claude Code CLI, 1650 сессий, 16 050 наблюдений на уровне функций, TypeScript-кодовые базы, несколько моделей). Разобрано подробно в §3 и §8.
- Официальная документация (`code.claude.com/docs/en/hooks`, обращение 25.09.2026) сегодня перечисляет **33** события против «свыше 30» в базовом исследовании — сверено пересчётом списка лично, подтверждено независимым источником (`morphllm.com`, дата публикации статьи 06.09.2026, тот же счёт). Некритичное для занятия, но точное обновление.

# 4. Контринтуитивные повороты

## 4.1. «Хук поставлен» ≠ «хук защищает» — и это теперь подтверждено на ровно нашем коде

**Что ответит зал интуитивно.** Файл `.claude/settings.json` лежит в репозитории, в нём читаемый текст, который явно запрещает коммит в `main`. Интуиция: раз файл существует и синтаксически корректен — защита работает.

**Почему это неверно.** Базовое исследование уже перечисляло пять причин тихого отказа (невалидный matcher гасит все хуки файла, удалённый/неисполняемый скрипт, регистр/незаякоренный шаблон, хуки субагента не триггерят хуки родителя, таймаут = тихое разрешение). К этому занятию добавились ещё два подтверждённых способа и один прямой обход именно нашего кода:

- **Шестой способ.** `bypassPermissions` на части моделей подменяет `Edit`/`Write`/`Read` на `Bash`-эквиваленты — хук с `matcher: Edit|Write` физически не видит вызов (`#92271`, воспроизведено с точным repro и кодом ошибки).
- **Седьмой способ.** Хук, объявленный во frontmatter субагента, не срабатывает вовсе, хотя идентичный хук в `settings.json` для того же субагента — срабатывает (`#95650`).
- **Прямой обход нашего конкретного паттерна.** Тот самый grep на `git\s+commit\b` пропускает `/usr/bin/git commit`, `env git commit`, `git -C . commit` и любую команду, где `git commit` не в первой строке многострочного вызова (`workain/agent-harness-registry#65`).

**Чем доказывается.** Не рассуждением, а воспроизведением: adversarial-тест против того же кода дал четыре конкретных команды, которые проходят мимо хука молча — то есть внешне неотличимо от разрешённого, легитимного вызова.

## 4.2. Хук харнесса не видит человека, набравшего `git commit` в терминале напрямую

**Что ответит зал интуитивно.** «Мы поставили защиту ветки, теперь никто не закоммитит в `main` напрямую» — с неявным допущением «никто», включая самого человека за клавиатурой.

**Почему это неверно.** `PreToolUse` — событие жизненного цикла **агента**: харнесс генерирует его перед тем, как модель вызывает инструмент. Человек, открывший отдельный терминал и набравший `git commit` руками, не вызывает никакой инструмент харнесса — для харнесса этого действия попросту не существует. Формула «правила в коде — законы», которую занятие вводит как главный вывод раздела, остаётся верной строго для агента; для человека, действующего в обход агента, тот же самый хук — не закон и не просьба, он его просто не видит.

**Чем доказывается.** Это не внешняя публикация, а собственное наблюдение курса, зафиксированное после внешнего ревью Семинара 4: `owner-questions.md` того же ревью-цикла, пункт 5, прямо называет это «шестым слепым пятном» самотеста ворот и явно указывает — не `.git/hooks/`, а механизм харнесса, который реагирует на вызовы инструментов агентом. Источник первого лица, внутренний, но методически надёжный: он написан по итогам той же самой ревью-сессии, которая нашла обходы `#65`.

## 4.3. Более широкие права читаются как «то же самое, но без лишних вопросов» — а могут тихо выключить целый класс хуков

**Что ответит зал интуитивно.** `bypassPermissions` — это тот же набор действий, что и в обычном режиме, просто без диалогов подтверждения; хуки как проверяли действия — так и проверяют.

**Почему это неверно.** На части моделей режим `bypassPermissions` добавляет отдельную мета-инструкцию, побуждающую агента предпочитать `Bash`-команды выделенным инструментам `Read`/`Edit`/`Write`. Если хук матчится по имени инструмента (`Edit|Write`), а не по семантике действия, — он рассчитан на то, что агент будет вызывать именно `Edit`/`Write`. Как только агент вместо этого выполняет `sed -i`/heredoc через `Bash`, хук с матчером `Edit|Write` этот вызов просто не видит: событие `PreToolUse` для него сработало, но matcher не совпал — то есть формально всё «как задумано», просто задумано было для другого инструмента.

**Чем доказывается.** Точное воспроизведение в `#92271`: одна и та же команда через `Read`-инструмент возвращает оба ожидаемых маркера контекста (нагрузка сработала), та же команда через `Bash cat` — ни одного. Таблица «модель × флаг» в issue показывает, что эффект был активен для `fable[1m]` и не активен по умолчанию для `claude-sonnet-5[1m]`/`haiku` на момент теста — то есть нестабилен между моделями, а значит, невозможно один раз проверить и на этом успокоиться.

# 5. Предотвращаем vs решаем: куда попадает эта ступень

Ось Семинара 4 переносится сюда без изменений в логике: одни решения закладываются на день 0 как универсальная гигиена (дёшево, не требует сигнала, не зависит от конкретного инцидента), другие ждут реального сигнала (дороже поддерживать, оправданы только когда риск стал конкретным).

Хук защиты ветки внутри себя расслаивается на два разных по своей природе слоя, и это расслоение подтверждается новой архитектурной рекомендацией `dubbl-a/house-rules#58`, а не придумывается заново:

- **День 0, универсальная гигиена — то, что не зависит от конкретного сигнала.** Серверная защита ветки (GitHub ruleset или классические branch protection rules) с пустым списком исключений по умолчанию. Это «потолок» в терминологии `#58`: платформенный барьер, который срабатывает независимо от того, что происходит локально, и не деградирует со временем, потому что не завязан на текст команды. Уже базовое исследование помещало этот шаг первым в лестнице хуков («как только появилась общая ветка, в которую можно случайно закоммитить напрямую»); новый источник добавляет параллельный «пол» — git-хук, подключённый через `core.hooksPath` и версионируемый вместе с репозиторием, который работает **после** того, как git уже разрешил конфликт неоднозначности состояния (какая ветка, какой HEAD, какой алиас), а не до него.
- **По сигналу, узкая доработка — то, что растёт реактивно.** Сам `PreToolUse`-хук на `Bash`, который занятие собирает вместе с залом (пять вопросов, §A.5 в плане раздела) — вписывается сюда честнее, чем изначально казалось. Попытка довести текстовый grep-паттерн до покрытия всех синтаксических форм git-команды (`git -C`, `env git`, алиасы, многострочные команды) — структурно проигрышная гонка: POSIX раскрывает слова и алиасы непосредственно **перед** выполнением команды, то есть уже после того, как хук принял решение по тексту. Расширять паттерн «на каждый найденный обход» — это ровно паттерн «решаем по сигналу», а не гигиена, потому что список обходов растёт быстрее, чем список правок паттерна.
- **Практический вывод для занятия, дословно годный на слайд.** Правильная граница ответственности узкого `PreToolUse`-хука — не «поймать весь возможный синтаксис git commit», а «поймать заведомые попытки отключить защиту» (`--no-verify`, манипуляция `core.hooksPath`, переменные окружения хук-менеджеров) — небольшой, перечислимый список, который **можно** довести до полноты, в отличие от бесконечного пространства форм одной shell-команды. Это не отменяет ценность co-building-сессии занятия — она остаётся педагогически верной («хук нужно собрать самим, чтобы увидеть его хрупкость»), но даёт честную формулировку предела: узкий хук — сигнал-driven усиление конкретной, ограниченной угрозы, а не замена платформенного потолка.

# 6. Провалы и ограничения (3 слоя)

## Слой 1 — конфигурация агента как исполняемый код, приезжающий с чужим репозиторием

Базовое исследование уже разбирало `CVE-2025-59536` (RCE до диалога доверия) и `CVE-2026-21852` (утечка API-ключа через подменённый `ANTHROPIC_BASE_URL`). Новый материал углубляет этот слой в двух направлениях:

- **`CVE-2026-40068`** (CVSS 7.7, версии 2.1.63–2.1.83, патч в 2.1.84, NVD-публикация 05.05.2026) показывает более серьёзный вариант той же проблемы: подделка `.git/commondir` в git worktree заставляет харнесс решить, что папка уже присутствует в списке доверенных, и выполнить хуки из чужого `.claude/settings.json` **без единого показа диалога доверия вообще**. Разница с базовой `CVE-2025-59536` принципиальна для формулировки на занятии: там хуки успевали отработать *раньше*, чем диалог появлялся на экране (окно гонки); здесь диалог **не появляется вообще**, потому что состояние доверия подделано заранее.
- **`CVE-2026-35603`** (раскрытие 05.01.2026, публикация 11.08.2026) — другой канал атаки, специфичный для Windows: системный каталог для `managed-settings.json` был доступен на запись любому локальному пользователю с низкими правами, что позволяло подложить конфигурацию, применяемую системно ко всем пользователям машины. Полезная деталь для честного разговора о вендорах: та же категория проблемы нашлась параллельно в трёх других агентных инструментах (Cursor, Codex CLI, Gemini CLI), и на сегодня решена только у Claude Code — при этом реакция была проактивной (уведомление клиентов до публикации, перенос в защищённый каталог), а не реактивным патчем постфактум.

Формулировка для зала, унаследованная и подтверждённая: конфигурация агента — исполняемый код, который приезжает вместе с недоверенным репозиторием; смотреть на `.claude/settings.json` из чужого pull request нужно с той же внимательностью, что и на код.

## Слой 2 — хук отказывает тихо (расширенный список причин)

К пяти задокументированным в базовом исследовании причинам (невалидный matcher гасит все хуки файла; удалённый/неисполняемый скрипт; несовпадение регистра/незаякоренный шаблон; вызовы субагента не триггерят хуки родителя; таймаут — тихое разрешение) добавляются две новых, подтверждённых после 20.09.2026:

- **Шестая: `bypassPermissions` на части моделей молча выключает хуки, привязанные к `Edit`/`Write`**, потому что агент подталкивается использовать `Bash` вместо выделенных инструментов (`#92271`). Эффект модельно-зависимый (на момент issue активен для `fable[1m]`, неактивен по умолчанию для `claude-sonnet-5[1m]`/`haiku`) — то есть проверка на одной модели не гарантирует то же поведение на другой.
- **Седьмая: хук, объявленный во frontmatter субагента, может не сработать вовсе**, даже когда идентичный хук в проектных настройках для того же субагента срабатывает корректно (`#95650`, версия 2.1.258).

Численной базы «какая доля установленных хуков реально отказывает тихо во флоте реальных проектов» по-прежнему не найдено — только качественные утверждения («most hook problems don't throw errors — they just silently fail») и растущий список подтверждённых единичных багов. Формулировка курса остаётся точной: «когда гейт не срабатывает, не происходит ничего — а именно так выглядит и успешно пройденный гейт».

## Слой 3 — хук фильтрует синтаксис команды, а не намерение плана (усилен прямым обходом нашего кода)

Базовое исследование иллюстрировало этот слой двумя примерами — chained `git switch && git commit` и base64-обход запрета на чтение файла. Новый материал добавляет не гипотетический, а прямой, воспроизведённый обход **ровно того паттерна**, что показан на слайде занятия:

- `grep -qE '(^|[;&|]\s*)git\s+commit\b'` не совпадает, если перед `git` стоит путь (`/usr/bin/git commit`) или обёртка (`env git commit`), если добавлен флаг рабочей директории (`git -C . commit`), или если `git commit` не в первой строке команды (потому что `read -r cmd` читает только одну строку).
- Техническое объяснение, почему это в принципе не решается расширением списка паттернов: POSIX-оболочка раскрывает слова и алиасы **непосредственно перед выполнением** команды — то есть уже после того, как хук на `PreToolUse` увидел текст и принял по нему решение. Хук структурно не может увидеть финальную развёрнутую форму команды раньше, чем она будет исполнена, — а значит, полнота текстового сканирования принципиально недостижима, а не просто «пока не докрутили список случаев».

Вывод для слайда, обновлённый и усиленный: хук на `Bash` — фильтр на синтаксис одной команды в её нераскрытой текстовой форме, а не на намерение плана и не на финальную исполняемую форму этой же команды. Для действительно чувствительного действия («не дать закоммитить в `main`») недостаточно расширять регулярное выражение — нужен слой, который не зависит от текста вообще (платформенный ruleset, git-хук, работающий после раскрытия состояния).

# 7. Критерии «ещё рано» и «не нужно вообще»

**«Здесь ещё рано»** (унаследовано из базового исследования, без изменений — новый материал не опроверг ни один пункт):

- Проверку дешевле сделать один раз в сборке/линтере на pull request, чем гонять на каждом вызове интерактивной сессии.
- Хук становится тормозом раньше, чем это будет замечено как ошибка: разрастание хуков не выдаёт сообщения, просто медленно снижает продуктивность (несколько независимых практических измерений латентности в §3 это подтверждают — от единиц миллисекунд до секунд p95 на плохо спроектированном хуке).
- Правило по сути не механизируемо (суждение, а не синтаксис) — оставлять рекомендательным и проверять человеком/критиком.
- Соло-разработчик с низким радиусом поражения — риск ещё не стал реальным.

**«Здесь не нужно вообще» — новый, уточнённый пункт по итогам находок этого цикла:**

- **Полное текстовое перечисление всех синтаксических форм одной shell-команды не нужно вообще как стратегия — оно структурно недостижимо.** Расширять grep-паттерн на каждый новый найденный обход (`/usr/bin/git`, `env git`, `git -C`, следующий, который найдут завтра) — это инженерная работа с отрицательным ROI: пространство форм одной команды в POSIX-оболочке больше, чем можно перечислить, потому что раскрытие слов и алиасов происходит уже после того, как хук принял решение. Вместо этого: платформенный ruleset как потолок (не зависит от текста локальной команды вообще) плюс узкий `PreToolUse`-хук, ограниченный **перечислимым** списком заведомых попыток отключить защиту (`--no-verify`, манипуляция `core.hooksPath`, переменные окружения хук-менеджеров) — такой список можно довести до полноты, в отличие от синтаксиса git.
- Если единственная причина ставить локальный хук — «прод не должен пострадать» без какого-либо технического разделения окружений, хук не решает эту задачу вообще: он защищает ветку `main` в git, а не производственную систему; нужен отдельный барьер уровня доступа/окружения (это уже отдельная тема курса, не эта ступень).

# 8. Честные пробелы — что НЕ измерено и НЕ подтверждено

- **Численная доля нарушений конкретного, однозначного правила файла инструкций** (например, «не коммить в `main`») в реальном использовании — не найдена ни в базовом исследовании, ни в этом цикле проверки. Ближайший контролируемый эксперимент (arXiv `2605.10039`) измеряет другое: влияние структуры файла (нулевое) и затухание соблюдения внутри сессии (~5,6% шансов за функцию) — это не то же самое, что «правило нарушается в X% случаев», и не даёт исходной базовой доли для сравнения.
- **Численная доля хуков, которые реально тихо отказывают в реальных проектах (частота по флоту, не единичные подтверждённые баги)** — не найдена. Есть растущий список подтверждённых механизмов отказа (семь на сегодня, §6, Слой 2) и качественные утверждения индустрии, но не частотная оценка «как часто это происходит на практике».
- **64,6% из WIRE-исследования** — сознательно не используется как база для утверждения «правило нарушается в 65% случаев»: это метрика совместного соблюдения **пары конфликтующих** правил в специально сконструированных испытаниях, не оценка естественной частоты и не про одно однозначное правило без конфликта. Использовать эту цифру на слайде без этой оговорки было бы нечестно.
- **Средняя латентность хука** — есть только точечные измерения разных хуков в разных проектах (30 мс / 440 мс / p95 2,5 с), не контролируемый эксперимент с единым хуком на едином наборе вызовов; порядок величины ясен, точная цифра для конкретно нашего хука («сколько добавляет наш хук защиты ветки») не измерена и должна быть измерена перед занятием, если понадобится точная цифра на слайд.
- **CVSS-значения для CVE-2025-59536 (8,7) и CVE-2026-21852 (5,3)** — унаследованный пробел из базового исследования, не закрыт: значения из вторичных источников, не из первичной записи NVD/GHSA. Рекомендация сверить `github.com/anthropics/claude-code/security/advisories` перед показом остаётся в силе.
- **«Function hooks» (TypeScript-формат хука)** — упомянуты одним источником без независимого подтверждения. **[НЕ ПОДТВЕРЖДЕНО]**, не использовать на занятии как текущую механику.
- **Точный текущий статус `#92271` и `#95650`** (действительно ли патч уже выпущен, а не только закрыт как «известно» без фикса) — не проверялось повторно после первого обращения; при подготовке к показу стоит свериться с актуальным changelog Claude Code.
