# Visible content

## Title bar
MCP убирает человека-мост между агентом и системами вне репозитория — и тем же каналом открывает риск

## Body
[В центре — агент, встроенный доступ vs MCP-расширение]

Кодинг-агент по умолчанию видит только **файловую систему рабочей копии и шелл**. Этого хватает для кода, но не для issue-трекера, живого браузера, деплой-таргета — всего, что **вне репозитория**. Без MCP инженер сам копирует контекст туда-обратно.

MCP-сервер публикует список инструментов при подключении — агент видит их как обычные функции, решает, когда вызвать, **тем же циклом**, что и встроенные.

[Три примера — карточки]

**GitHub MCP server**: issues, PR, CI, алерты безопасности — по наборам (toolsets), выборочно. Явный **режим только для чтения**: инструменты на запись пропускаются, даже если запрошены.

**Playwright MCP server**: не скриншот, а **accessibility-дерево** — структурное описание элементов. Кликает, заполняет формы, генерирует тест.

**Filesystem MCP** — не один сервер, а класс: доступ к директориям **вне** рабочей копии (соседний репозиторий, общий диск).

[Мост к безопасности]
Один MCP-сервер часто закрывает **два угла** Lethal Trifecta одним подключением: доступ к данным (issues, приватные репо) **и** канал действия наружу (создать PR). Третий угол — недоверенный контент — прилетает через тот же сервер, когда агент читает чужой issue.

Задокументированный случай: GitHub MCP server — вредоносные инструкции в публичных issues эксфильтровали данные через создаваемые PR.

[Gold callout]
MCP только для чтения по умолчанию там, где запись не нужна; доступ на запись — осознанное решение о безопасности, а не настройка, которую никто не пересматривал.

## Speaker notes

Без MCP агент видит только файлы рабочей копии и терминал. Этого хватает для кода, но не для того, что лежит вне репозитория: трекер задач, живой браузер, система сборки. Пока моста нет, мостом работает инженер — переносит данные руками. MCP убирает мост: сервер при подключении публикует список своих инструментов, и агент вызывает их тем же циклом, что и встроенные.

У этого есть цена, о которой говорят реже. Сервер публикует не весь интерфейс системы, а отобранный набор инструментов. Чего в наборе нет — агенту недоступно, даже если сама система это умеет: набор инструментов GitHub MCP — подмножество того, что доступно через API GitHub и через команду gh в терминале. Плюс каждая схема инструмента занимает контекст постоянно, с момента подключения, а не по вызову. Поэтому там, где у агента уже есть терминал, узкая команда часто дешевле MCP-вызова, а активный набор серверов стоит держать минимальным.

Отдельно — безопасность, и здесь важно не перепутать знак. Смертельная тройка — доступ к данным, канал наружу и недоверенный контент; опасна именно их комбинация. Один сервер обычно даёт первые две сразу, одним подключением, а третья приходит по тому же каналу, как только агент читает чужую задачу. Это риск, а не удобство: концентрация доступа, а не защита. Задокументированный случай: спрятанные в публичных задачах инструкции заставляли агента выводить данные приватных репозиториев через создаваемые заявки на слияние.

Закрывается это тремя шагами, и порядок в них существенен. По умолчанию — только чтение: инструменты записи пропускаются, даже если агент их запросил. Запись открывают под конкретную задачу отдельным решением, а не настройкой из коробки. И чем меньше серверов подключено, тем меньше и углов тройки, и постоянного контекста.
