# Код или JSON — и что если хук ответил мусором

## Assertion

Хук отвечает двумя независимыми способами — кодом возврата и JSON, и код 2 блокирует безусловно, даже если тот же хук в JSON написал «разрешаю»; а мусорный ответ молчит четырьмя разными способами, а не одним.

## Visual

Код возврата: `0` — успех. `2` — блокирует **безусловно**, даже если JSON сказал `allow`. Другой код (включая `1`) для большинства событий сам по себе **не блокирует**.

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "BLOCKED: direct commit to main/master. Create a feature branch first."
  }
}
```

| `permissionDecision` | Эффект | Уже видели |
|---|---|---|
| `"allow"` | пропускает запрос разрешения | — |
| `"deny"` | предотвращает вызов | ветка `main` |
| `"ask"` | принудительно спрашивает | не git-репозиторий |
| *(поле отсутствует)* | решения нет, обычный флоу | фиче-ветка, пустой вывод |

Четыре формы мусора и тишины:

| Что произошло | Видно ли где-то |
|---|---|
| Валидный JSON, не та схема | неблокирующая ошибка, запись в транскрипте |
| Похоже на JSON, не парсится | та же ошибка, другой текст |
| Пустой вывод, код 0 | не ошибка вообще — штатное «решения нет» |
| Поле не на своём уровне | **молча игнорируется**, ничего нигде, кроме debug-лога |

## Speaker notes

Мы видели три ответа хука — запрет, тишина, вопрос. Вот как именно они устроены механически.

Два способа ответить. Код возврата два блокирует безусловно, даже если тот же хук напечатал в JSON «разрешаю» — блокировка по коду побеждает решение в JSON. А вот любой другой код, включая привычную единицу, для большинства событий сам по себе не блокирует: без валидного JSON на выходе Claude Code считает это некритичной ошибкой и пропускает действие дальше, несмотря на то что единица в Unix традиционно означает провал. Интуиция «скрипт упал — значит заблокировано» здесь просто неверна, буквально по спецификации, не по недосмотру автора хука.

Второй способ — структурный JSON, и это выбор нашего хука. `permissionDecision`: «deny» — видели на ветке `main`, «ask» — вне git-репозитория, поле отсутствует — значит «разрешаю», это пустой вывод на фиче-ветке. Если несколько `PreToolUse`-хуков на одном событии вернули разные решения, приоритет `deny` выше `ask` выше `allow`.

А если хук ответил мусором? Тут не одно состояние, а четыре разных, и разница важна. Валидный JSON, но не той структуры, — некритичная ошибка, в транскрипте появится запись об ошибке хука. Похоже на JSON, но не парсится — та же ошибка, другой текст. Пустой вывод с кодом ноль — это вообще не ошибка, это штатное «решения нет», то же самое состояние, что и пустой вывод на фиче-ветке.

А вот четвёртое — самое коварное: поле стоит не на своём месте, скажем `permissionDecision` не внутри `hookSpecificOutput`, а на верхнем уровне JSON. JSON парсится успешно, но решение молча отбрасывается — без единой записи где бы то ни было, кроме отладочного лога по явному запросу. Без специального усилия штатный интерфейс сессии физически не отличает «сработал и пропустил» от «не сработал вовсе». С этим и разберёмся дальше — сначала на слайде отладки, потом в самих провалах, где это уже не абстрактная возможность, а конкретный зафиксированный режим отказа.
