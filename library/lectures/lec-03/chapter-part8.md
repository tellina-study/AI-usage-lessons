## 2.12. Типовые RAG-задачи (прикладные кейсы)

[for-slide-rag-cases-intro]
До сих пор Раздел 2 разбирал RAG как устройство: принцип (§2.1), когда он уместен (§2.2–§2.3), как ломается (§2.4), из чего собран правильный RAG (§2.6–§2.11). Здесь мы разворачиваем эту теорию на шести **реальных архетипах** задач, потому что «RAG» в вакууме не существует — существует «RAG под поддержку», «RAG под код», «RAG под договоры», и retrieval-дизайн у них разный. Каждый кейс разобран по единому шаблону: **задача → retrieval-дизайн (chunking, индекс, гибрид?, реранк?) → что делает трудным → типовой провал → как чинит хорошая реализация → baseline/counterfactual**. Где деталь взята из источника — стоит ссылка; где деталь придумана для наглядности — помечено «иллюстративный».

### Опорная лесенка улучшений (единый количественный якорь)

[for-slide-rag-cases-anchor]
Прежде чем идти по кейсам, зафиксируем единый количественный якорь, к которому они будут отсылать. Anthropic (инженерный блог «Contextual Retrieval») даёт полную лесенку улучшений на одной задаче ретрива — это удобный общий масштаб для всех кейсов ниже:

| Дизайн retrieval | Доля **проваленных** ретривов (нужного нет в top-20) |
|---|---|
| Базовые эмбеддинги (наивный dense) | **5,7%** |
| + контекстуализация чанков (§2.9, стратегия 7) | 3,7% (−35%) |
| + гибрид с BM25 (§2.6) | 2,9% (−49%) |
| + реранкер (cross-encoder, §2.6) | **1,9% (−67%)** |

Дополнительно из того же источника, полезное как факты для кейсов: оптимально извлекать **top-20** (тестировали 5/10/20); контекст к чанку — 50–100 токенов, стоимость его генерации с prompt caching **$1,02 / 1M токенов документов** (разово); порог «RAG вообще не нужен» — если база **менее ~200k токенов (~500 страниц)**, положите всю базу в промпт (§2.3, §2.11). Преподавательский вывод одной строкой: по данным практиков **наивный dense-RAG проваливает ретрив порядка 40% времени** (kapa.ai, 2026; Towards Data Science, 2026) — три приёма (контекст чанка + гибрид + реранк) закрывают большую часть этого. `[VFY-day-of]` — вендорские числа лесенки.

### Кейс A. Ассистент поддержки / внутренней базы знаний

[for-slide-rag-case-support]
*Задача.* Пользователь (клиент или сотрудник) задаёт вопрос на естественном языке; система находит нужные куски документации и генерирует ответ **со ссылкой на источник**, либо честно отказывается («не нашёл»). *Реальные реализации.* kapa.ai обслуживает документ-ассистентов для Docker, CircleCI, Reddit, Monday.com, OpenAI, Logitech (kapa.ai, 2026); Stripe Dashboard Assistant — RAG поверх документации и статей поддержки (Stripe docs). *Retrieval-дизайн.* Нарезка по смысловым границам (раздел/подраздел), не по фиксированным N символов (§2.9); индекс — **гибрид** плотный + BM25 (§2.6), чтобы ловить точные термины (коды ошибок, имена флагов); реранк cross-encoder поверх объединённых кандидатов; свежесть — **дельта-обновление** (переиндексируется только изменённое; у Stripe — десятки правок в день). *Что трудно.* Технические синонимы и близкие-но-разные термины; частые обновления базы; доступ по ролям (не показать сотруднику чужой раздел). *Типовой провал.* Эмбеддинги решают, что «exponential backoff» (экспоненциальная выдержка перед повтором) и «dead-letter queue threshold» семантически близки, и ассистент уверенно выдаёт **неверную** политику повторов — retrieval подтянул не тот документ, а генератор всё равно ответил уверенно (это ровно §2.4 «вернул что-то ≠ вернул правильное»). *Как чинит.* Гибрид (BM25 ловит точный термин, который плотный поиск «замылил») + реранкер + порог «нет достаточно релевантного → откажись»; плюс кураторство источников (приоритет первичным — документация, справочник API, заметки о релизах; чаты/форумы фильтровать по свежести). *Baseline.* Без гибрида+реранка ~5,7% проваленных ретривов → после 1,9% (в 3 раза меньше, лесенка выше); без RAG вовсе (fine-tune на FAQ) модель не обновляется при десятках правок/день — устаревает мгновенно. Экономика малого документ-бота: ~200 документов → эмбеддинги ~$1–2 и 5 минут; ~300 запросов/мес ≈ $10 API (Intlayer, порядок величины для малого проекта, **иллюстративный**, не enterprise).

### Кейс B. Q&A по документации

[for-slide-rag-case-docs]
*Задача.* «Как сделать X в SDK/продукте?» — ответ строго из актуальной документации, с цитатой и ссылкой; отказ, если в документации этого нет. *Реальные реализации.* Vercel AI SDK docs-copilot (поиск → реранк → ответ с источниками **или отказ**; 25-кейсовый eval-набор в CI — GitHub Alla-N/docs-copilot); Vercel публикует `llms.txt` (тонкий индекс для ассистентов в реальном времени) и `llms-full.txt` (полный экспорт для загрузки в RAG). *Retrieval-дизайн.* Нарезка по секциям документации; плотный индекс; реранк кандидатов; жёсткий контракт «ответ с источниками или отказ»; eval-набор в CI ловит регрессии ретрива при обновлении документации. *Что трудно.* Документация меняется ежедневно (нужен конвейер свежести, §2.11); много версий API (легко подтянуть устаревший синтаксис — провал свежести знания, §2.4); нужна честность отказа вместо выдумки. *Типовой провал.* Ассистент цитирует старую версию API или «додумывает» несуществующий параметр (расхождение ответа с процитированным источником). *Как чинит.* (1) Свежесть — дельта-переиндексация; (2) реранкер + порог отказа; (3) **eval-набор в CI как воротца** — без метрик «на глазок» пропускает регрессии (§2.11). *Baseline.* Без eval-набора регрессия ретрива после обновления документации уходит в прод незамеченной; без контракта отказа система галлюцинирует вместо «не нашёл» — хуже пустого ответа, т.к. подрывает доверие ко **всем** ответам.

### Кейс C. Поиск по кодовой базе

[for-slide-rag-case-code]
*Задача.* «Где реализована аутентификация?», «что сломает изменение этой функции?» — найти релевантный код в большом репозитории и дать контекст ассистенту/агенту. *Реальные реализации.* Cursor индексирует кодбазу эмбеддингами и делает RAG по коду (Towards Data Science, 2026); Sourcegraph Cody исторически строился на эмбеддингах для контекста. *Retrieval-дизайн.* Chunk **по смысловым границам кода** (функция/класс, а не N строк — §2.9); dense-индекс кода; постоянный refresh по мере изменения репо. *Что трудно.* Код — не проза: точные идентификаторы важнее семантической близости; монорепо (>100k репозиториев) взрывают стоимость и поддержку вектор-индекса; отправка кода в сторонний embedding-API — риск безопасности. *Типовой провал.* Dense-эмбеддинги «замыливают» точное имя символа; на масштабе монорепо вектор-поиск дорог и медленен, multi-repo контекст не строится. *Как чинит.* Sourcegraph Cody на Enterprise **отказался от эмбеддингов** и заменил их на Sourcegraph Search (лексический/структурный поиск): безопаснее (код не уходит в чужой API), дешевле в поддержке, масштабируется на 100k+ репо, качество ретрива равное или лучше (Sourcegraph docs). *Baseline / counterfactual.* Против эмбеддингов: приходилось слать весь код в сторонний API, хранить/обновлять векторы, а на >100k репо поиск деградировал — переход на классический поиск снял стоимость, security-риск и потолок масштаба. Это одновременно кейс C **и** живой пример «RAG-как-dense-vectors был не тем инструментом» (см. ниже, «Когда RAG — не тот инструмент»): для кода и точных идентификаторов классический поиск часто бьёт dense-RAG.

### Кейс D. Юридический / договорный поиск

[for-slide-rag-case-legal]
*Задача.* Найти релевантные нормы/пункты договоров/прецеденты и дать ответ с цитатой на конкретный источник права. *Реальные реализации + документированный провал.* Preregistered-исследование Stanford (HAI + RegLab) по коммерческим legal-AI: инструменты LexisNexis (Lexis+ AI) и Thomson Reuters (Westlaw AI-Assisted Research, Ask Practical Law AI) — **все на RAG** — галлюцинируют **17–33% запросов**, несмотря на маркетинг «hallucination-free» (Stanford RegLab; VentureBeat; Legal Dive). *Retrieval-дизайн.* Гибрид (точные цитаты статей/номеров дел критичны → BM25 обязателен, §2.6) + dense + реранк; жёсткая привязка ответа к извлечённому источнику; фильтры по метаданным до векторного поиска (юрисдикция, статус, дата — §2.6, рычаг (b)). *Что трудно.* Цена ошибки высочайшая (юрист несёт ответственность); «правдоподобная» ложь опаснее пустого ответа; точные цитаты (номер дела, статья) должны совпадать буквально. *Типовой провал.* Две формы: **citation hallucination** (сам источник выдуман) и **statement hallucination** (ссылка реальна, но утверждение расходится с её содержанием). RAG **снижает**, но **не устраняет** галлюцинации. *Как чинит.* Верификация цитат постфактум (проверить, что процитированный текст существует и подтверждает утверждение), обязательный человек-в-петле, отказ при низкой уверенности ретрива. *Baseline / counterfactual.* Против чистого LLM без RAG галлюцинации были бы ещё выше; но 17–33% с RAG всё равно означает: маркетинговое «0% галлюцинаций» ложно, и без верификации/человека применять нельзя. Урок, связывающий с §2.5 (Air Canada) и правилом курса: RAG **уменьшает, но не обнуляет** галлюцинации — в high-stakes без верификации выпускать нельзя.

### Кейс E. Deep-research по корпусу (агентный RAG)

[for-slide-rag-case-deepresearch]
*Почему кейс здесь, а не в §1.10.* Deep research часто ошибочно относят к «промпт-задачам» («напиши большой промпт — соберёт отчёт»). Это неверно: определяющий компонент — **retrieval и оркестрация**, а не формулировка промпта, поэтому он разобран как RAG-кейс (§1.10 явно передаёт его сюда). *Задача.* Один сложный вопрос («сравни рынок X по 5 измерениям, со ссылками») → система сама планирует под-вопросы, много раз ищет, читает источники, синтезирует отчёт с цитатами. *Как реально устроены системы (архитектурный паттерн).* **Reasoning-LLM + агентный цикл RAG**: рассуждение направляет поиск, новые находки уточняют рассуждение (закрытая петля) — это *agentic RAG* (§4, Deep-dive box 2), в отличие от статического «retrieve top-k → generate». OpenAI Deep Research: одна мощная reasoning-модель проходит цикл план → поиск → backtrack → синтез. Perplexity: RAG по вебу в реальном времени, ответ аннотирован источниками. Обобщённый паттерн для слайда-схемы: `план под-вопросов → (поиск → чтение → уточнение рассуждения)×N → синтез → верификация цитат`. *Retrieval-дизайн.* Итеративный retrieval (модель решает, что доискать по результатам предыдущего шага) + отдельный **citation-pass** для трассируемости. *Что трудно.* Синтез (не только найти, но и организовать/сопоставить); координация оркестратора; стоимость (много параллельных под-агентов = много токенов). *Типовой провал — фабрикация цитат.* В retrieval-augmented режиме **3–13% URL сфабрикованы** (arXiv:2604.03173, `[VFY-day-of]`); DRBench (100 PhD-задач): точность цитат 78% (OpenAI DR) … 94% (Claude с поиском) — т.е. 6–22% проблемных; DRACO (100 задач из реального использования Perplexity, 2026): лучший результат ~65% citation quality / 68% factual accuracy (arXiv:2602.11685, `[VFY-day-of]`). И контринтуитивно: deep-research-агенты галлюцинируют цитаты **хуже** обычного search-augmented ответа (по одному замеру 10,7% против 4,8% — потому что генерируют кратно больше цитат). *Как чинит.* Отдельный слой **верификации** после синтеза: проверить, что каждый URL резолвится и что процитированный текст реально подтверждает утверждение (как в кейсе D). *Baseline / counterfactual.* Против ручного аналитика — быстрее и дешевле, НО без верификационного слоя 3–13% ссылок ложны → в high-stakes отчёте это дороже медленного человека. Прямая связка с правилом курса (baseline/counterfactual): deep research любит выдавать цифры **без базы** («−50%», «5M acres») и подпирать их правдоподобной, но несуществующей ссылкой — любую метрику из ИИ-ресёрча перепроверяйте по резолвящемуся первоисточнику, число без базы считайте красным флагом.

### Кейс F. Enterprise-поиск по смешанным данным (документы + таблицы)

[for-slide-rag-case-enterprise]
*Задача.* «Сколько мы потратили на облако в Q3 и какая политика это регламентирует?» — ответ требует **и** структурных данных (таблица/БД), **и** текста (policy-документ). *Реальные подходы.* Glean — multi-modal enterprise search (docs, images, code, structured data) через RAG; eSapiens — единый NL-интерфейс: **Text-to-SQL** планировщик для структурного + гибридный RAG для неструктурного (arXiv:2506.16768; паттерн также у LlamaIndex). *Retrieval-дизайн.* Роутер: числовой/агрегирующий вопрос → **Text-to-SQL** к БД; текстовый → dense+BM25+реранк по документам (§2.6); ответ синтезирует оба; плюс авторизация на уровне строк. *Что трудно.* Таблицы нельзя «эмбеддить как прозу» — вопрос «сумма за Q3» требует SQL-агрегации, а не похожих чанков (это ровно тихий провал таблиц из §2.10); нужны другие метрики качества — корректность запроса, соответствие схеме, авторизация, entity resolution. *Типовой провал.* Наивный RAG эмбеддит строки таблицы и «находит похожие», но не может сложить/сгруппировать → неверные числа; Text-to-SQL на сложной схеме выдаёт **невалидный SQL** (синтаксис, не тот столбец, пропущенный фильтр). *Как чинит.* Роутинг «структурный vs текстовый»; валидация/самопроверка SQL + fallback; отдельное измерение query correctness; авторизация на уровне строк. *Baseline / counterfactual.* Против чистого document-RAG по таблицам агрегирующие вопросы просто неотвечаемы (нельзя «найти похожую сумму»); против ручного аналитика с SQL — быстрее, но при кривой схеме без валидации SQL молча даёт неверное число, что хуже «не знаю».

### Когда RAG — не тот инструмент

[for-slide-rag-wrong-tool]
Раздел закрывает failure/judgment-линию главы: RAG — **не «магическая пилюля»**, и половина инженерного суждения — знать, где вместо него правильнее другой инструмент. Четыре документированных случая, каждый с уроком.

- **Dense-RAG → классический поиск (Sourcegraph Cody).** Cody **убрал эмбеддинги** на Enterprise и вернулся к Sourcegraph Search: код уходил в сторонний API (security), векторы надо хранить/обновлять (tech debt), на >100k репо вектор-поиск дорог и не масштабируется, multi-repo контекст не строился; итог — классический поиск дал **равное или лучшее** качество дешевле и безопаснее (Sourcegraph docs). Урок: для кода и точных идентификаторов лексический/структурный поиск часто побеждает dense-RAG.
- **RAG → long-context.** При окне ~1M токенов + prompt caching для **статичного корпуса менее ~200k токенов (~500 страниц)** проще и дешевле положить всю базу в промпт, чем строить RAG (§2.3, §2.11). RAG выигрывает, только когда корпус **больше** окна, **часто меняется**, нужен **per-doc доступ** или **цитаты**. Оговорка: long-context на больших объёмах в проде существенно (по одному источнику — порядка 20–24×, **иллюстративный порядок**) дороже RAG — хорош для прототипа, плох для потока.
- **RAG → fine-tuning.** Для внутреннего code-gen на **проприетарном фреймворке** fine-tuning научил модель фирменному синтаксису/паттернам, которых нет в базовой модели — качество кода заметно выше, чем базовая модель + RAG (порядок «10×» из вторичного источника — **иллюстративный**, не строгий бенчмарк; IBM; Medium). Урок: RAG даёт **что** знать (факты), fine-tuning — **как** рассуждать/в каком стиле; стиль и поведение через RAG не чинятся (подробно — §3, Часть 2).
- **RAG → обычный запрос к БД.** Вопрос «сумма расходов за Q3» — это `SELECT ... GROUP BY`, а не «найди похожие чанки»; эмбеддить таблицу и искать похожее → неверные агрегаты (кейс F). Урок: числовой/агрегирующий вопрос по структурным данным → SQL/BI, а не dense-RAG.

Сквозной урок раздела (это strict-in failure/judgment-контент): RAG **уменьшает, но не обнуляет** галлюцинации (17–33% в legal, 3–13% фабрикованных цитат в deep-research); для кода — классический поиск; для статичного малого корпуса — long-context; для стиля/поведения — fine-tuning; для чисел — просто БД. **Критерий выбора инструмента важнее самого RAG** — это та же ось лестницы (§5), поднятая на уровень «а нужен ли RAG вообще».
