# Семинар 3 — кейсы системного дизайна на трёх механизмах модели

Формат каждого кейса (как в sem-02):
**Кейс** (постановка) → **Что делаем** (решение) → **Уточнение: пивот или нет** (скрытая вводная на отдельном слайде, меняет ли она решение) → **Пример из жизни** (реальный случай).

Три блока = три механизма Лекции 2. В каждом ≥2 кейса.

**Критерий приёмки: в каждом кейсе есть действие над системой** — создание, правка или доработка:
| Кейс | Действие над системой |
|---|---|
| 1.1 Выбор модели эмбеддинга | **Создание** эмбеддинг-поиска (выбор компонента по мини-eval) |
| 1.2 Дедуп тикетов | **Доработка** системы поддержки (модуль дедупликации) |
| 2.1 Извлечение из договоров | **Создание** пайплайна извлечения |
| 2.2 Качество ассистента | **Доработка** существующего чат-ассистента (метрика → grounding) |
| 3.1 Описания товаров | **Создание** генератора карточек (подбор температуры) |
| 3.2 Роутер-классификатор | **Правка** LLM-роутера (greedy для решающей задачи) |

**Кейс «поиск по вики» перенесён в Семинар 4** (Блок 2, устройство retrieval-канала: гибрид + реранкер + полярность) — это классический RAG-retrieval, ближе к архитектурному семинару.

## Блок 1 — Эмбеддинги: поиск и сопоставление по смыслу

### Кейс 1.1 — Выбор модели эмбеддинга под свой корпус
- **Кейс.** Строим семантический поиск/RAG по своим документам (русский + доменные термины). Первое инженерное решение — какая embedding-модель кодирует запросы и документы. По какому критерию выбирать?
- **Что делаем (пошагово, «чем и как»).** (1) Кандидаты: мультиязычная общая (e5, bge-m3) vs доменная/дообученная vs крупная размерность. (2) Собрать мини-eval на СВОИХ данных — 50–100 пар «запрос → релевантный документ». (3) Прогнать кандидатов → recall@k / MRR. (4) Сопоставить качество с размерностью вектора (384 vs 1024 → хранение и латентность поиска). (5) Зафиксировать выбор «качество на моих данных / стоимость». Таблица сравнения через `variants` (3 колонки: мультиязычная / доменная / крупная размерность).
- **Нюансы (после метода).** Лидер бенчмарка MTEB ≠ лучший на твоём домене/языке; больше размерность ≠ всегда лучше; дистанция (cosine/dot) и нормализация должны совпадать с тем, как модель обучалась.
- **Пример из жизни.** Глава Лекции 2 §2.6: финальную проверку кандидатов делай на выборке своих документов и запросов — час работы против недель жизни с неудачным индексом.

### Кейс 1.2 — Дедупликация тикетов поддержки
- **Кейс.** 500 тикетов/день, много дублей, сформулированных по-разному теми же словами. Как автоматически схлопывать похожие?
- **Что делаем.** Эмбеддинги + порог косинусной близости для кластеризации похожих обращений.
- **Уточнение — пивот или нет.** Скрытая вводная: «оплата не проходит картой Visa» и «оплата не проходит картой Mastercard» почти идентичны по вектору, но это **разные** инциденты (разные эквайринги). **Пивот не метода, а признаков:** поверх similarity — жёсткие структурные ключи (тип карты, код ошибки). Вектор ловит тему, теряет различающую деталь.
- **Пример из жизни.** Класс ошибок near-duplicate: тот же механизм, что антонимы в 1.1 — «похоже по смыслу» ≠ «то же самое».

## Блок 2 — Внимание/контекст: что модель реально «понимает» в тексте

### Кейс 2.1 — Извлечение «кто кому платит» из договоров
- **Кейс.** Парсим договоры, извлекаем, какая сторона кому и когда платит. Доверять ли LLM разрешение местоимений/ролей («он», «сторона», «Исполнитель»)?
- **Что делаем.** LLM-извлечение — модель сильна на типовых формулировках; берём как первый проход.
- **Уточнение — пивот или нет.** Скрытая вводная (Winograd-тип): «Заказчик выплачивает Исполнителю аванс, если **он** предоставит гарантию» — кто «он»? Смена одного слова переворачивает референт. **ПИВОТ на критичных полях:** не свободная генерация, а извлечение с человеческой верификацией + структурные правила. Внимание — статистическая корреляция, не понимание причинности.
- **Пример из жизни.** Winograd Schema / WinoBias — академический бенчмарк, где модели систематически ошибаются на кореференции. `[VERIFY-DAY-OF: атрибуция WinoBias — Zhao et al. 2018]`

### Кейс 2.2 — «Ты — опытный юрист»: роль в промпте vs знание
- **Кейс.** Чат-ассистент для юротдела. Хотим поднять качество, добавив в системный промпт «Ты — опытный юрист с 20-летним стажем». Сработает?
- **Что делаем.** Роль задаёт стиль, формат, тон ответа — используем для формы.
- **Уточнение — пивот или нет.** Скрытая вводная: роль **не добавляет** модели знаний, которых нет в весах/контексте. **ПИВОТ ожиданий:** нужна фактическая точность по актуальному праву → не роль, а grounding/RAG на проверяемый источник (мост к Л3).
- **Пример из жизни.** Исследование role-prompt (Zheng et al., 2024, EMNLP): роль улучшает форму, не фактологию.

## Блок 3 — Сэмплинг: температура, варианты, режим под задачу

### Кейс 3.1 — Температура для генератора описаний товаров
- **Кейс.** Маркетплейс автогенерирует описания карточек. Какую температуру ставить и одну ли на все поля?
- **Что делаем (пошагово).** Механика: температура делит логиты перед softmax → меняет ОСТРОТУ распределения следующего токена (не порядок, не «стиль»). Три прогона одного промпта («Столица Франции — одним предложением»): T=0 — три идентичных ответа; T≈0.7 — формулировка гуляет, факт держится; T=1.5 — расползается, теряет связность. Ось = **«предсказуемо/повторяемо ↔ случайно/разнообразно и рискованно»**, НЕ «скучно↔ярко». Иллюстрация распределения (`distribution`): T масштабирует высоты; top-k срезает по счёту; top-p — по накопленной массе.
- **Нюанс (после метода).** Те же карточки наполняют регламентные поля (состав, гарантия) → там нужна не «правильная T», а шаблон/grounding из проверяемого источника. Температура управляет разбросом, а не достоверностью.
- **Пример из жизни.** Таблица сценарных температур (Л2 §4.4); Air Canada как цена свободной генерации факта (форвард к сем-04).

### Кейс 3.2 — Сэмплинг в решающей задаче: роутер/классификатор
- **Кейс.** LLM-роутер (интент → ветка). При T>0 один и тот же вход иногда уходит в РАЗНЫЕ классы. Почему и как сделать выбор стабильным?
- **Что делаем (пошагово).** (1) Для решающих задач сэмплинг = greedy (T=0 / top-k=1), не «творческий» режим: выбор класса становится argmax, повторяемым. (2) Механика top-p (nucleus) и top-k — они ОБРЕЗАЮТ хвост распределения (по массе / по числу), в отличие от температуры, которая МАСШТАБИРУЕТ высоты; как подбирать под задачу.
- **Нюанс (после метода).** Даже greedy не гарантирует калибровку → отдельно порог уверенности (разрыв лог-вероятностей top-1/top-2) и fallback (уточнение / человек). Контраст с 3.1: там разнообразие полезно, тут вредно.
- **Пример из жизни.** Механика температуры/сэмплинга (Л2 §4.1–4.2): распределение вероятностей — «настоящий» выход модели, политика выбора поверх него.

**Перенос из старого расклада.** Старый Кейс 3.2 (T=0 + structured output + аудит) удалён целиком — это про надёжность/аудит, не про механизм сэмплинга; тема воспроизводимости при T=0 живёт в главе Л2 §4.3 и семинаре про надёжность.

## Что унести (по одной строке на блок)
- Эмбеддинги: выбор модели решает мини-eval на своих данных (recall@k/MRR), не место в бенчмарке; «похоже» ≠ «то же» → структурные ключи.
- Внимание: модель коррелирует, не понимает причинность → верификация на критичных полях; качество двигает grounding, не роль.
- Сэмплинг: температура масштабирует распределение (не «стиль», не обрезание хвоста); решающей задаче — greedy; генерации — подобранное T на батче.

## Финал занятия
Доброволец приносит свою задачу (поиск / извлечение / генерация) — разбираем по тому же шаблону: что делаем, где пивот, какой реальный риск.

## Строгая доля failure/judgment (≥30%)
Каждый блок содержит кейс, заканчивающийся границей/свойством механизма: 1.1 — лидер бенчмарка проседает на домене (граница «выбирай по своим данным»); 1.2 — near-duplicate (близость ≠ тождество); 2.1 — кореференция (attention = корреляция, не причинность); 2.2 — роль ≠ знание; 3.1 — регламентные поля (температура ≠ достоверность); 3.2 — greedy не гарантирует калибровку (стабильно ≠ верно). Холистически ≥30%.
