# Раздел 1. Ступень 1: файл инструкций (11 мин)

## A. План раздела

### A.1. Состояние репозитория на входе

Продукт-код есть, конфигурации агента нет ни одной строки. Реальное дерево ступени 1 —
`assets/captures/21-tree-stage1.txt` (показывается в конце раздела, когда файл уже добавлен):

```
index.html
package.json
src/main.js
tests/form.spec.ts
```

`git init` выполняется по ходу этого раздела — это важно для раздела 3: без репозитория хук
защиты ветки честно отвечает «проверить нечего».

### A.2. Проблема — конкретная, на материале `signup-landing`

Не «агент переспрашивает». Первая версия занятия строилась на сценарии «агент во второй сессии
снова спрашивает, какой командой собрать сайт» — **и этот сценарий опровергнут реальными данными**:
на полностью сформулированную задачу агент не задал ни одного уточняющего вопроса и сам прописал в
`package.json` именованные скрипты сборки и теста. В следующей сессии он их оттуда и прочитает.
Записывать команды сборки в файл инструкций — значит дублировать то, что уже лежит в стандартном,
всегда читаемом месте.

Настоящая боль на этом шаге другая, и она следует из требований, которые зал собрал в разделе 0:

> Новая сессия, неделю спустя. Заказчик пишет: «отправил заявку с сайта — она не пришла».
> Разработчик просит агента разобраться. Агент читает код, находит и правит обработчик отправки
> формы в `src/main.js`, запускает тест — тест зелёный — и отчитывается: **«Готово, тест
> проходит»**.
>
> Но тест `tests/form.spec.ts` проверяет ровно одно: что форма **не отправляется** с пустыми
> обязательными полями. Он ничего не знает о том, доходит ли заполненная заявка до внешнего
> сервиса приёма форм. «Готово» для агента — это «сборка собралась и тест зелёный». «Готово» для
> вас — это «заявка реально доставлена, проверено на проде». Эти два определения разошлись, и
> разошлись молча.

Ключевое свойство этой боли: **её источник невозможно вывести из кода**. В репозитории нет ничего,
что связывало бы зелёный тест с критерием приёмки, — эта связь существовала только в разговоре из
раздела 0. И пока она нигде не записана, повторяться будет каждую сессию: у агента нет памяти между
сессиями, он начинает с чистого контекстного окна.

Второе, парное проявление той же дыры: агент не знает, что деплой на прод требует отдельного явного
запроса. В коде это не написано. В требованиях зала — было.

### A.3. Открытый вопрос классу (дословно) + варианты

> «Агент починил форму, прогнал тест, тест зелёный, агент говорит "готово". А заявка на проде
> по-прежнему не доходит — потому что тест проверяет совсем другое. Где должно быть записано, что
> считается "готово" в этом проекте, чтобы агент в следующей сессии не сделал ровно то же самое?»

**Карточки-варианты на слайде (пять):**

`ответить в чате` · `README.md` · `файл инструкций CLAUDE.md` · `комментарий в тесте` ·
`переписать сам тест`

### A.4. Разбор ожидаемых ответов зала

| Вариант | Где это работает | Почему здесь ещё рано — и что вместо |
|---|---|---|
| «Отвечу агенту в чате ещё раз» | Внутри одной сессии — полностью достаточно | Не переживает конец сессии: следующая начинается с пустого контекста, и тот же разбор придётся провести заново. Вместо: записать туда, что читается само, без вашего участия |
| «Напишу в `README.md`» | README нужен людям, впервые открывшим репозиторий, — хорошая практика сама по себе | README не подгружается в начало каждой сессии. Разные адресаты и разный механизм: README читает человек, если захочет; файл инструкций читает агент, хочет он того или нет. Вместо: оставить README людям, а агенту завести его собственный файл |
| «Заведу файл инструкций с полным описанием архитектуры проекта» | Практически нигде: это самый частый способ потратить контекст впустую | Агент выведет структуру кода сам за секунды. Раздел устареет при первом рефакторинге и начнёт врать. Контролируемый эксперимент (§A.8): файлы с содержимым вида «обзор репозитория» не дали измеримого прироста успеха, но подняли стоимость на 20–23%. Вместо: писать только невыводимое |
| «Допишу комментарий в `tests/form.spec.ts`» | Когда правило касается ровно этого файла и агент его точно откроет | Агент откроет тест не в каждой задаче: комментарий в одном файле — надежда, что он туда заглянет. Вместо: правило уровня проекта — в файл уровня проекта |
| «Пусть агент перепишет тест так, чтобы он проверял доставку заявки» | **Правильный инженерный шаг — его стоит сделать** | Но он не закрывает задачу раздела: даже идеальный тест не скажет агенту, **чего делать нельзя** (выкладывать без спроса) и что считать приёмкой там, где теста нет. Вместо — не «вместо», а **вдобавок**: тест почините, и всё равно останется то, что тестом не выражается |
| «Заведу файл инструкций, но только с тем, чего агент не выведет из кода» | На этом шаге — именно то, что нужно | **Не рано: сигнал сработал.** Перестаёт работать, когда файл начинает расти без обрезки — см. §A.8 |

### A.5. Совместное формирование файла (R10): собираем по строке — и одну вычёркиваем

Файл не показывается готовым. Он собирается на глазах зала за три хода, и **второй ход —
вычёркивание**, иначе упражнение остаётся декоративным.

**Ход 1. «Назовите одну строку, которую точно надо записать».**
Зал почти наверняка называет команды: «build — вот эта, test — вот эта». Фасилитатор записывает
их на слайд честно, не подсказывая.

**Ход 2 — вычёркивание. «Проверим эту строку на прочность».**

На слайде рядом с записанной строкой проявляется блок команд **из финального ответа самого агента**
(`assets/captures/36-first-task-dialogue.md`, блок 3):

```
npm install
npm run build          # → dist/
npm run test:e2e       # playwright test
```

> «Смотрите: эти скрипты уже лежат в `package.json` — и имена им придумал сам агент, когда собирал
> проект. В следующей сессии он их оттуда прочитает. Мы это проверили на живом прогоне: на
> полностью сформулированную задачу он не задал ни одного вопроса про команды. Значит наша строка
> почти ничего не добавляет — но платит контекстом в каждом запросе. Вычёркиваем? Оставляем?»

Правильный итог — оставить в сильно урезанном виде (одна строка про то, **как проверить, что
правка реально работает**, а не только компилируется) и вычеркнуть дублирующее. Важно, чтобы зал
увидел: строка в файле инструкций — это не бесплатная заметка, у неё есть цена, и за неё надо
уметь заплатить.

**Ход 3. «Тогда что сюда действительно надо?»**
Возвращаемся к шести требованиям из раздела 0 — и берём ровно ту тройку, которую там отложили в
группу «нигде не будет видно». Это не совпадение и не подгонка: группа и собиралась под этот ход.

- определение «готово» — одна строка;
- граница действий: не выкладывать на прод без явного запроса — одна строка;
- как убедиться руками, что заявка дошла, — одна строка.

Три из шести названных требований, три строки в файле. Фасилитатор проявляет на слайде итоговый
файл — тот, что реально лежит в демо-репозитории (**после обязательной пересъёмки**, см. §A.6).

### A.6. Конкретное решение: что добавляется в репозиторий

`CLAUDE.md` в корне `signup-landing/` — **тринадцать строк**, ровно три содержательных пункта, и
ни одного из тех, что агент выведет сам:

```markdown
# CLAUDE.md

signup-landing: статический лендинг с формой заявки на демо-урок. Готово = `npm run build`
завершается кодом 0, `npx playwright test` зелёный, форма реально отправляет заявку на проде.

## Safety / scope boundaries

- Никогда не запускать деплой на прод без явного запроса.

## Build, test, verify

- To verify a change actually works (not just compiles): открыть `dist/index.html` после сборки,
  вручную отправить форму с заполненными и с пустыми полями.
```

Эти три пункта — ровно те три требования, которые в разделе 0 попали в группу «нигде не будет
видно»: критерий «готово», граница действий, способ ручной проверки. Арифметика 6 → 3 + 3 сходится
здесь буквально.

> **ОБЯЗАТЕЛЬНАЯ ПЕРЕСЪЁМКА (блокирует слайд 1.6).** Захваченный файл
> `assets/captures/28-code-CLAUDE.md.txt` содержит **лишние три строки** — `Build:`, `Test:`,
> `Run locally:`. Показывать его на слайде **нельзя**: полутора минутами раньше, на ходе 2
> совместного формирования, зал своими руками вычеркнул строку про команды как дублирующую
> `package.json`. Если через полторы минуты те же команды проявятся в «итоговом» файле, урок
> разваливается на глазах у зала — и это единственная фактическая нестыковка раздела.
> **Что сделать:** пересобрать `CLAUDE.md` в демо-репозитории без этих трёх строк (останется 13
> строк, как в блоке выше), закоммитить и переснять файл. Дерево ступени 1 при этом не меняется.
>
> Отдельная тонкость, которую стоит проговорить вслух, если кто-то из зала заметит: команды
> `npm run build` и `npx playwright test` **остаются** в первом абзаце — но там они часть
> **критерия приёмки** («готово = собралось кодом 0 и тест зелёный»), а не справочник команд.
> Это разные вещи: справочник дублирует `package.json`, критерий не дублирует ничего.

Плюс `AGENTS.md` как симлинк на тот же файл (`ln -s CLAUDE.md AGENTS.md`) — один источник правды
для разных движков. Дерево после ступени 1 — `assets/captures/21-tree-stage1.txt`.

### A.7. Описание решения: как это работает механически

- Файл-инструкция загружается движком **в начало каждой сессии целиком**, до первого сообщения
  пользователя. Это не документ «на почитать» — это контекст, который тратит токены каждый раз,
  независимо от того, нужен он сегодня или нет.
- Загрузка иерархическая (политика организации → пользовательский → проектный → локальный →
  вложенные), и все найденные файлы **конкатенируются**, а не перекрывают друг друга. Отсюда
  неочевидное следствие: при противоречии между уровнями агент может выбрать любую сторону.
- `@`-импорты организуют файл, но **не экономят контекст**: импортированный файл всё равно
  грузится целиком при старте.
- Официальный ориентир объёма — **до 200 строк на файл**. Наш итоговый файл — тринадцать строк.
  Это не аскеза ради красоты: каждая строка платит контекстом в каждом запросе.
- Симлинк `AGENTS.md → CLAUDE.md` держит один источник правды для разных движков. Острый край,
  который стоит назвать: копирование шаблона обычным `cp -R` без флага `-P` на macOS
  **разыменовывает симлинк** во вторую реальную копию — и проблема дублирования, ради которой
  паттерн и придуман, возвращается молча. Копировать через `cp -a`, `git clone` или `git archive`.

### A.8. Провал / ограничение: файл сам по себе не работает

Это не «страшилка в конце раздела», а прямое продолжение Лекции 3, §4.7 — **presence paradox**.
Формулировка для зала: мы только что добавили файл, и тут же честно признаём его измеренный потолок.

**Слой 1 — контролируемый эксперимент (Gloaguen et al., arXiv:2602.11988).** Три плеча: файла нет
вообще (**это и есть база сравнения**), файл сгенерирован моделью, файл написан разработчиком.
Метрика — реальный успех решения задачи.

| Плечо (против «файла нет») | Эффект на успех | Значимость |
|---|---|---|
| Файл сгенерирован моделью | −0,5% | незначимо (p = 87%) |
| То же, другая связка модель/агент | −2% | незначимо (p = 37%) |
| Файл написан разработчиком | +2,4% | незначимо (p = 21%) |
| **Стоимость и число шагов, любое плечо с файлом** | **+20…23%** | **значимо** |
| Файл от модели, подвыборка: репозитории **без другой документации** | **+2,7%** | подтверждённое исключение |

Читается так: **сам факт наличия файла не покупает успех, но покупается контекстом всегда.**
Единственное подтверждённое исключение — там, где файл реально закрывает информационный пробел, а
не пересказывает то, что уже есть. Ровно поэтому мы вычеркнули строку про команды и оставили три
строки, которых нет нигде.

**Слой 2 — раздутый файл работает против себя.** Официальная позиция разработчика движка
формулируется без смягчений: *«Bloated CLAUDE.md files cause Claude to ignore your actual
instructions!»* — раздутый файл заставляет агента игнорировать ваши настоящие инструкции. Эмпирика
рядом: на бенчмарке следования инструкциям (IFScale, arXiv:2507.11538, 20 моделей семи
провайдеров) при плотности **500 одновременных инструкций** даже лучшие модели держат лишь **68%**
точности, и комплаенс падает почти линейно с ростом числа инструкций — база сравнения — тот же
замер при малом числе инструкций, где точность близка к полной. То есть каждая добавленная строка
не просто стоит контекста: она немного снижает шанс, что сработает соседняя.

**И одна фраза в конце, без развития.** Файл инструкций — это **контекст, а не принудительная
конфигурация**: агент может его учесть, а может не учесть. Здесь фраза и обрывается: ни кейса, ни
формулы, ни анонса следующего раздела. Раздел 1 не должен выдавать ответ на вопрос, который раздел
3 ещё только задаст.

> **Перенесено в раздел 3 (было здесь, убрано как спойлер).** Публичный случай
> `anthropics/claude-code#42863` и формула «правила в промпте — просьбы, правила в коде — законы»
> теперь живут в разделе 3: там они прямое доказательство против конкретного ответа зала
> («перепишу правило капсом»), а не общий тезис за пятнадцать минут до того, как он понадобится.
> При вёрстке слайда 1.7 формулы на нём быть не должно.

### A.9. Критерий «здесь ещё рано»

- **Задача поставлена полно и разово.** Наш собственный живой прогон — прямое доказательство: на
  подробно сформулированную задачу агент не задал ни одного вопроса и справился. Файл инструкций
  не добавил бы ничего, кроме +20…23% стоимости.
- **Крошечный репозиторий или одноразовый скрипт**, где структура помещается в один экран и нет
  нестандартных команд.
- **Всё, что выводимо из кода**, в файл не идёт — ни структура директорий, ни список зависимостей,
  ни обзор архитектуры.
- **Правило, которое недопустимо нарушить ни разу**, в файл идти не должно вообще — но чем его
  тогда закрывать, разберём отдельно, когда до этого дойдёт боль. (Механизм здесь **не называть**:
  это ответ на вопрос раздела 3.)
- **Процедура, нужная не каждой сессии**, в файл не идёт: это скилл. Раздел 4.

### A.10. Место в харнесе (терминология Лекции 3)

Второй слот экипировки — **инструкции-правила, операционный слой** (§4.7). Мы закрыли его самым
тонким возможным способом: один файл, тринадцать строк, только невыводимое. Это и есть
**тонкий агент** из §5.2b — стартовый комплект, который не усложняют, пока не сработал проверяемый
триггер.

## B. Методическая глава

### B.1. Почему прежний сценарий пришлось выбросить — и почему об этом стоит сказать залу

Первая версия этого раздела держалась на сценарии, который выглядит убедительно ровно до тех пор,
пока его не проверяешь: агент во второй сессии снова спрашивает, какой командой собрать сайт, —
вот вам и триггер, заводите файл инструкций. Проверка на живом репозитории этот сценарий не
подтвердила (`assets/captures/36-first-task-dialogue.md`). На подробно сформулированную задачу
агент не задал ни одного уточняющего вопроса — и прямо написал почему: все параметры были
однозначно выводимы из текста задачи. Он сам создал `package.json`, сам прописал туда именованные
скрипты сборки и теста и сам всё запустил. В любой следующей сессии он прочитает эти скрипты из
стандартного места, куда смотрит в первую очередь.

Этот факт стоит произнести вслух перед залом, а не тихо заменить сценарий. Он несёт собственный
урок, ценный сам по себе: **хорошо поставленная задача снимает бóльшую часть потребности в файле
инструкций.** Если вам кажется, что агенту нужен файл, первый вопрос — не «что туда написать», а
«а вы точно сформулировали задачу?». Очень часто файл инструкций пытаются использовать как
компенсацию плохой постановки, и это самый дорогой из возможных способов её компенсировать: плохая
постановка стоит одну сессию, а файл-заплатка — контекст в каждом запросе навсегда.

### B.2. Настоящая боль: не вопрос, а молчаливое решение

Раздел 0 закончился тем, что зал назвал шесть требований и обнаружил: пять из них не видны в коде.
Раздел 1 берёт одно из этих пяти — критерий «готово» — и показывает, что с ним происходит.

Сценарий фасилитатор рассказывает как историю, в настоящем времени:

> «Прошла неделя. Заказчик пишет: отправил заявку с вашего сайта, она не пришла. Вы открываете
> новую сессию, просите агента разобраться. Он читает код, находит проблему в обработчике отправки
> формы, правит `src/main.js`, запускает тест. Тест зелёный. Агент пишет: готово.
>
> А теперь посмотрите, что проверяет наш тест. Ровно одно: что форма **не отправляется**, когда
> обязательные поля пусты. Про то, доходит ли заполненная заявка до внешнего сервиса, он не знает
> ничего — и знать не может, потому что мы его таким написали.
>
> Агент не соврал. Он применил свой критерий готовности: собралось, тест зелёный. Просто это не
> ваш критерий. Ваш критерий прозвучал десять минут назад в этой аудитории — и с тех пор он нигде
> не записан.»

Здесь важна точность обвинения. Агент не нарушил правило — правила не было. Он не поленился
спросить — он не знал, что тут есть о чём спрашивать. Разница между «нарушил» и «не знал»
определяет, каким блоком конфигурации это чинится: «не знал» чинится текстом, «нарушил» — уже не
чинится текстом, и в этом будет содержание раздела 3.

### B.3. Вопрос классу и работа с ответами

Вопрос задаётся дословно (см. §A.3), с пятью карточками-вариантами на экране. Пауза 10–15 секунд,
затем 2–3 голоса. Варианты на экране нужны не для подсказки, а чтобы разговор шёл про **место**
(куда записать), а не про формулировку — иначе зал начнёт сочинять текст правила, а это шаг
совместного формирования, до которого мы ещё не дошли.

Две реакции требуют отдельной подготовки.

**«Пусть агент перепишет тест».** Это лучший из неправильных ответов, и обесценивать его нельзя.
Формула ответа: «Вы правы, и это надо сделать — тест, который не проверяет главного, плохой тест.
Но представьте, что вы это сделали: тест теперь проверяет доставку. Объясните мне теперь этим же
тестом, что деплоить на прод без спроса нельзя. Не получится — это не то, что выражается тестом.
Останется дыра, и она ровно того же происхождения.»

**«Напишу архитектурный обзор проекта в `CLAUDE.md`».** Здесь не надо иронизировать — это самый
частый и самый естественный импульс. Формула: «Разумно, если считать, что агент не понимает
устройство проекта. Но он его понимает: он этот проект и собрал, и структуру прочитает заново за
секунды. А вот что с таким разделом случится через месяц после рефакторинга — он начнёт врать,
причём уверенно. Через пять минут я покажу вам эксперимент, где именно такие файлы дали ноль
прироста успеха и плюс двадцать процентов стоимости.»

### B.4. Совместное формирование: три хода и одно вычёркивание

Это центр раздела по времени (четыре минуты из двенадцати) и главное структурное отличие от первой
версии. Файл не показывается готовым с объяснением постфактум — он собирается вместе с залом.

**Ход 1** занимает меньше минуты. Фасилитатор показывает пустой каркас файла — заголовок и три
пустых раздела — и спрашивает: «Одну строку, которую точно надо записать. Кто?» Зал называет
команды сборки и теста. Фасилитатор пишет их на слайд без комментария — именно так, как назвали.

**Ход 2** — вычёркивание, и это тот момент, ради которого упражнение существует. Рядом с только что
записанной строкой на слайде появляется фрагмент настоящего `package.json` из этого же
репозитория, где те же самые команды уже лежат именованными скриптами.

> «Мы записали в файл инструкций то, что уже лежит в `package.json`. Агент читает `package.json`
> в первую очередь — мы это проверили на живом прогоне, он даже не спросил. Что это значит для
> строки, которую мы только что написали? Она платит контекстом в каждом запросе и почти ничего
> не возвращает.»

Строка вычёркивается на слайде — визуально, перечёркиванием, — и на её месте остаётся сильно более
узкая: «как проверить, что правка реально работает, а не только компилируется». Это уже
невыводимо: последовательность ручной проверки формы на собранной странице из кода не следует.

Если зал возражает («пусть будет, вдруг пригодится») — это отличное возражение, его надо
поблагодарить и ответить числом: файл грузится в каждую сессию целиком, а измеренная надбавка к
стоимости и числу шагов от присутствия файла — двадцать-двадцать три процента относительно работы
вовсе без файла. «Вдруг пригодится» здесь имеет конкретный ценник.

**Ход 3** возвращает зал к требованиям из раздела 0. Вопрос: «Из шести требований — какие три
невозможно восстановить, читая код?» Ответы проявляются на слайде по одному, и складываются ровно
в тот файл, который реально лежит в демо-репозитории: определение «готово», граница про деплой,
способ ручной проверки.

Финальная реплика хода:

> «Тринадцать строк. Не триста. Три содержательных пункта — ровно те три требования, которые
> двадцать минут назад вы сами отложили в группу «нигде не будет видно». И ни одной строки,
> которую агент мог бы узнать сам.»

### B.5. Механика: что именно происходит с этим файлом

После сборки файла — короткий блок про то, как он работает, потому что без этого «файл инструкций»
остаётся магией. Четыре вещи, каждая в одну-две фразы (детали — в §A.7): загружается в начало
каждой сессии целиком; уровни конкатенируются, а не перекрываются, поэтому противоречие между ними
разрешается произвольно; `@`-импорты не экономят контекст; ориентир — до 200 строк, у нас
тринадцать.

И одна строка про `AGENTS.md`: симлинк на тот же файл, чтобы не держать по копии на каждый движок.
С честным острым краем: `cp -R` без `-P` на macOS превращает симлинк в реальную вторую копию —
молча, и дублирование, против которого паттерн придуман, возвращается.

### B.6. Провал и ограничение: сразу после того, как файл появился

Последовательность здесь намеренная. Мы только что потратили четыре минуты на создание файла — и
немедленно показываем его измеренный потолок. Это не подрыв собственного решения, это его точная
калибровка.

Фасилитатор ведёт разбор по двум слоям (§A.8), и первый стоит подать как прямое возвращение к
лекции:

> «На Лекции 3 это называлось presence paradox. Напомню устройство эксперимента, потому что оно
> необычное: обычно сравнивают "наш файл лучше их файла", а здесь было честное третье плечо — файла
> нет вообще. Вот с ним и сравнивали. Результат: файл, сгенерированный моделью, — минус полпроцента,
> незначимо. Файл, написанный разработчиком, — плюс два с половиной, тоже незначимо. А вот
> стоимость и число шагов — плюс двадцать-двадцать три процента, и это значимо во всех плечах.
> Единственное место, где файл реально выиграл, — репозитории, где не было никакой другой
> документации: там плюс два и семь. То есть файл работает ровно тогда, когда закрывает пробел, —
> и не работает, когда пересказывает то, что уже есть. Мы поэтому и вычёркивали строку.»

Второй слой — про раздутие, с официальной цитатой и числом из бенчмарка следования инструкциям.
Здесь полезно связать с личным опытом зала: многие видели файлы инструкций на триста-пятьсот строк
и, вероятно, считали их признаком зрелого проекта. Переформулировать: это признак того, что файл
рос только добавлением. Эмпирическая медиана по тысячам реальных файлов — плюс пятьдесят семь слов
за коммит на добавление против минус пятнадцати на удаление. Файлы растут, если за балансом никто
не следит специально.

И **одна фраза в конце, на которой раздел останавливается**:

> «И последнее, коротко. Файл инструкций — это **контекст, а не конфигурация**. Агент может его
> учесть, а может не учесть, и это официальная позиция, а не жалоба пользователей.»

Дальше — **пауза и переход к разделу 2, а не развитие мысли**. Публичный случай игнорирования
правила и формула «правила в промпте — просьбы, правила в коде — законы» здесь намеренно **не
произносятся**: они прозвучат в разделе 3 как прямой ответ на вопрос, который зал там задаст сам.
Выдать их сейчас — значит превратить третий раздел в подтверждение уже известного вывода вместо
самостоятельного хода.

### B.7. Критерий «ещё рано» и мостик

Критерий проговаривается голосом, нижней плашкой слайда, за полминуты — без отдельного слайда.
Главный пункт в нём — первый, потому что он единственный подкреплён нашим собственным замером:
если задача поставлена полно и она разовая, файл не нужен вообще.

Мостик к разделу 2 строится на разделении авторства, и его нужно сказать точно — иначе разделы 1 и
2 сольются в «два файла с текстом»:

> «Мы записали то, что знали заранее: правила, которые сформулировали сами, до всякой работы. Это
> и есть операционный слой — вы автор, файл стабилен, он в git, его видит вся команда.
>
> Но есть второй класс знания, который заранее записать нельзя, потому что вы его ещё не знаете.
> Оно появляется **по ходу работы**: что вы уже пробовали и отвергли, почему отвергли, какие
> варианты обсуждались и не прошли. Это не правило, которое вы писали, — это вывод из прошлой
> сессии. И записывать его должен не столько вы, сколько сам агент. Раздел второй.»
