## `[плотность]` — почему это шум, а не находка

`deckkit.plotnost` считает слова видимого слоя с порогом, писанным под
канон Лекции 7 (90 слов медианой по `case`, 140 на кадр). Канон ЭТОЙ
лекции (`CLAUDE.md` § «Форма подачи слайда», правка 2026-10-08/10) этот
предел снял явно: **«Жёсткое ограничение «3–5 строк видимого текста»
СНЯТО… Остаётся единственный физический предел: текст не должен
наезжать сам на себя при рендере»**. Задача этого круга — сохранить
самопроверки ядра как есть (включая `plotnost`, он входит в «density
check» из наряда), не редактировать их пороги. Замер входа: медиана
кадров `case` — **136 слов** при старой цели 90; 34 кадра из 76 тяжелее
140. Это ожидаемо, а не сломано — см. визуальную проверку ниже.

Пять параллельных сессий переоткрыли решение по `media` на каждом кадре
(явная инструкция владельца «restore visual richness… much less text») и
положили реальные снимки для 59 из 76 кадров (`rendered/assets/hero/`,

нужно ПОЧИНИТЬ, чтобы этот код впервые заработал на настоящих файлах, а
не про новое содержание (текст/заметки кадров не трогались нигде, кроме
перечисленных ниже структурных полей фронтматтера).

### 1. Путь `media:` — два разных соглашения у пяти сессий

Пять параллельных сессий писали путь в `media:` по двум разным
соглашениям: 31 файл — путём ОТ КОРНЯ РЕПОЗИТОРИЯ
(`library/lectures/lec-08/rendered/assets/hero/…`), остальные — путём ОТ
`LEC_ROOT` (`rendered/assets/hero/…`, тот же способ, что уже использует
Лекция 7). `media.media_path()` разрешает путь ВТОРЫМ способом
(`Path(root) / m`, где `root = library/lectures/lec-08`) — на первом
соглашении получалось удвоение
(`library/lectures/lec-08/library/lectures/lec-08/…`), то есть файл
«не находился» на диске (`[кадр]: файла нет`) молча, про любой из 31
кадра. Исправлено скриптом по всем 76 файлам: префикс
`library/lectures/lec-08/` срезан там, где он был. Проверено: все 59
путей с непустым `media` теперь резолвятся на диск, 0 расхождений.

### 2. Четыре кадра с несколькими логотипами в одном `media:` — непригодный синтаксис

`s43`, `s47`, `s48`, `s49` несли `media:` строкой с несколькими путями
через `; ` (два-три логотипа компаний-сторон разбора). У `media_path()`
нет такого синтаксиса — он читает всю строку как ОДИН путь, который,
разумеется, не существует. `deckkit.media` умеет класть ДВА снимка рядом
(`media_2`/`media_band`, уже используется `build_lec07.py` для типа
`analitika`), но ни один из них не поддерживает ТРИ (ровно столько нужно
`s47`: UMG + Sony + Warner). Вместо того чтобы вводить третий тип кадра
ради одного случая, логотипы каждого кадра сведены в ОДНО
PNG-изображение (`ImageMagick`-подобный композит через `PIL`: контурные
логотипы приведены к общей высоте, положены в ряд с полями, на белом
фоне) — `s43-composite-getty-vs-stability.png`,
`s47-composite-three-labels.png`, `s48-composite-nyt-vs-openai.png`,
`s49-composite-suno-vs-udio.png`. Исходные отдельные логотипы оставлены
в `assets/hero/` (использованы также как источник композита и повторно
на `s57`, который ссылается на уже готовый `s43-getty-images-logo.png`).
Каждый `media:` этих четырёх кадров указывает теперь на свой композит —
один файл, стандартный путь без синтаксиса, которого ядро не знает.

### 3. SVG-логотипы: формат, который `python-pptx` не читает

9 логотипов пришли файлами `.svg` (`s41`, `s42`, `s43`×2, `s47-s49`×3,
`s48`×2, `s49`-риа, неиспользован). `deckkit.media.img_ar`/`norm_image`
открывают картинку через `PIL.Image.open` — PIL не умеет SVG, значит
`img_ar` тихо возвращает `None`, а `draw_media`/`draw_hero` на `None`
просто НЕ РИСУЮТ снимок (ни ошибки, ни предупреждения о пропуске — кадр
молча остаётся без картинки при НЕпустом `media`). Ни ImageMagick, ни
`rsvg-convert`, ни системный `cairo` в этом окружении не установлены и не
ставятся (нет root, `apt-get` недоступен; `pip install cairosvg`
подтягивается, но падает на отсутствии `libcairo.so.2`). Рабочий путь —
портативный LibreOffice этого же пайплайна (`lo-portable-env.sh`) умеет
`--convert-to png:draw_png_Export:{"PixelWidth":…,"PixelHeight":…}`
НАПРЯМУЮ на `.svg`: первая попытка без явного `PixelWidth` отдавала
логотип в его собственном `viewBox` (`s42` — 57×55 px, пикселизация на
полный кадр при развороте), вторая — с `PixelWidth`/`PixelHeight`,
посчитанными от `viewBox` каждого файла под длинную сторону 900 px,
дала чёткие PNG у всех 9. Зафиксировано в `notes/mcp-limitations.md`
([#289-1], ниже) — это НЕ баг этой деки, а общий пробел инструментария
курса (`.svg` логотипы с CDN вроде LobeHub/Wikimedia Commons этот путь
ещё не проходили).

### 4. Keystone `s03` — два ряда вместо одного

### 5. s01/s76 — акты добычи были, флага `media_hero` не было

Обе сессии, отвечавшие за `s01` (обложка) и `s76` (закрытие/Q&A — именно
этот кадр, не `s39`, занимает позицию «последний слайд» ЭТОЙ деки),

БОКОВОЙ колонкой (~13% площади), а не обязательным hero (§5.9,

файла. `s01` сразу прошёл порог (40,5%). `s76` с исходным `HERO_W=7,58`

### 7. `s04`/`s15` — текст наезжал на обводку собственной рамки

После включения реальных `media` (логотип CNET на `s04`, логотип
Midjourney на `s15` — оба в БОКОВОЙ колонке, не hero) сторож `[запас]`
честно предупредил «влезает, но тоньше, чем мера разрешает — строка
занята 99,8–100% рамки ПО ШИРИНЕ». Глазами — не «тесно», а НАЕЗД: нижняя
строка тела ложилась буквально ПОВЕРХ скруглённой обводки своей же
рамки (`ocean_box`), потому что LibreOffice перенёс эту строку на знак
шире, чем насчитал питоновский замер, и получившаяся лишняя строка
вышла за уже нарисованную по более короткой оценке рамку.

Первая попытка фикса — общий довесок К ВЫСОТЕ (`avail - pad`) для ВСЕЙ
ветки одноколоночного тела — ничего не исправила (тот же наезд
пиксель-в-пиксель, потому что `[запас]` мерит риск переноса СТРОКИ ПО
ШИРИНЕ, а довесок сужал только высоту, под которую подбирается кегль) и
вдобавок зацепила ЧЕТЫРЕ чистых кадра (`s01`, `s05`, `s07`, `s30`)
побочным ужатием кегля без какой-либо находки на них — отменена.
Рабочий фикс — довесок К ШИРИНЕ: необязательное поле `body_fit_wpad`
(дюймы), которое `fit_runs` вычитает из ширины ТОЛЬКО при подборе кегля
(рисуется кадр всё равно в полную ширину колонки, поэтому настоящая
строка в LibreOffice гарантированно короче отведённой ей рамки). Поле
по умолчанию `0` — не трогает ни один из остальных 74 кадров; проставлено
`body_fit_wpad: 0.4` на `s04` и `s15`. После фикса — `[запас]` и наезд
исчезли на обоих кадрах, 0 новых предупреждений на остальной деке.
