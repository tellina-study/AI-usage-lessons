# Architecture: the template-step substitutes values

## Assertion

The same path, the same fourth block in the same spot — only now there's no model call inside it.

## Visual

> The same chain: form → field extraction → **substituting values into a fixed form** → Telegram. The decision about the text's form was made once, in advance, not on every run.

## Speaker notes

This is the second architecture diagram, and it's worth looking at not on its own but alongside the previous one — the difference between them is exactly one node, and the rest of the chain is untouched, step for step. Where the first diagram had a node that calls the model on every run, here there's a node that substitutes already-known values into a text form fixed once. No model call happens at this step at all.

The real difference isn't the tool — it's the moment the decision gets made. In the model version, the decision about how the text will sound is made anew on every request. In this version, the decision was made once, in advance, when the text form was designed and fixed, and from then on it's simply reproduced without variation.

That has a direct consequence for reliability: this node has no room to compose anything. It cannot insert a detail into the message that wasn't in the request — because it doesn't compose anything at all, it only copies values into pre-marked places. The placeholder finding we'll break down shortly, on real runs of the model version, is structurally impossible in this architecture — not because this version is "smarter," but because there's simply no step here that could create it.

What this looks like inside the actual tool, with the real parameters of both versions — the next screens.

It's worth addressing one objection that naturally comes up: "what if the template turns out less flexible than the model, and misses something important?" That's a fair question, and the answer isn't "a template is always better" — it's "for this specific need, the template has exactly as much flexibility as it needs": three values, one message form, nothing that would require genuinely different text from request to request. If the need were different — say, the requester's tone had to be accounted for, or the text had to vary with urgency — this same argument would cut the other way, and the model version would be the one to prefer.

The order of events here stays exactly as it really happened: the model version was built first, practice found the placeholder problem, and only after that did the team arrive at the architecture you see on this screen. The two diagrams stand side by side now not because they were equally weighted options from the start, but because side by side makes them easier to compare one to one — what exactly changed, and why that change closes the problem found in practice.
