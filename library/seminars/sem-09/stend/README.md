## Задача 1 — объединённый выходной файл С8

`sem-08/stend/sborka.py` получил функцию `student_file()` (по образцу одноимённой функции
`sem-07/stend/sborka.py`): ОДИН сценарий, все четыре доработки С8 поверх
`sem-07/stend/student.json` — уведомление шаблоном, дедупликация в два уровня, решение о
возврате `IF`-узлом по сумме (своя форма — запрос на возврат, второй триггер в том же
workflow), картинка с проверкой размера перед отправкой (новый `IF`-узел по
`content-length`, у `stage_4()` этой проверки не было вовсе — граница 10 МБ проверялась
внешним вызовом Telegram API, см. `sem-08/stend/README.md` «Кейс 4»). Файл — ровно та же
стрижка, что у `student_file()` С7: без credential, без привязки таблицы, с generic путями
формы (`sem-08-combined` / `sem-08-combined-refund`) — закрывает открытый пункт
`sem-08/slides/n56-vyhod.md`.

Для настоящей проверки `sem-09/stend/sborka.py` переиздаёт ту же структуру (импортом
модуля, не копией кода) под именем «С9 · вход (выход С8)» с восстановленными
credential/таблицей/вебхуками (`s9-vhod-kurs`, `s9-vhod-vozvrat`) — имя и адрес живут в
адресном пространстве занятия, которое их выложило, хотя содержание в точности выход С8.

### Три прогона — что каждый подтвердил

1. **Обычная заявка** (`POST /form/s9-vhod-kurs`, execution `603`) — весь путь прошёл: тема
   справочника `курс`, `status: ok`, уведомление-шаблон собрано, картинка получена (56 346
   байт — проверка `content-length`≤10 МБ прошла по true-ветке), доставлена в Telegram
   (`message_id 19`). Строка в таблице `requests` — поля `topic`/`urgency`/`status`
   заполнены корректно (см. находку 1 ниже).
2. **Повторная заявка** (тот же текст в поле «Что нужно» и в тестовом поле «Предыдущее
   сообщение», execution `604`) — сработала дедупликация ТОЧНОГО совпадения: узел
   `Exact duplicate in window?` отдал 1 элемент по true-ветке и 0 по false, выполнение
   остановилось до записи и до LLM-проверки — ни новой строки, ни уведомления.
3. **Возврат ниже порога** («прошу вернуть 1500 рублей…», `POST /form/s9-vhod-vozvrat`,
   execution `605`) — `Extract amount` достал `1500`, `IF`-узел `Amount over threshold?`
   пошёл по false-ветке (не выше 3000), экран показал «Решение кода: одобрить».

### Находка 1 (исправлена) — `chainLlm` стирает `$json`, не передаёт поля дальше

Первый прогон (execution `602`, до правки) показал `topic: null`, `urgency: null`,
`status: null` в записанной строке таблицы — хотя справочник (`Vocabulary check`) отдал их
верно. Причина: узел `Same question, reworded? (LLM)` (цепочка `@n8n/n8n-nodes-langchain
.chainLlm`) по умолчанию ЗАМЕНЯЕТ `$json` на `{text: "Нет."}` — это поведение узла, не
ошибка выражения. Путь унаследован из `dedup_nodes()` С8 (эта функция не трогалась —
задача ограничивает правку этого файла одной функцией): там он не был измерен по колонкам
таблицы, только по точности самой дедупликации. Исправлено ВНУТРИ `student_file()`
отдельным узлом `Restore vocabulary fields` (именованная ссылка на `Vocabulary check`), не
правкой `dedup_nodes()`. Перепрогон (execution `603`) подтвердил исправление. **Эта находка
касается и опубликованного на стенде С8 `stage_2.json` (id `c7evxIhox45tn127`)** — туда
правка не вносилась (вне зоны этой сессии), но тот же путь там в принципе даст тот же
эффект при ветке «не дубль».

## Задача 2 — Кейс 1: самоотчёт против детерминированной проверки

База знаний — 10 пунктов (`kb1`…`kb10`) из жизни учебного центра (оплата, перенос,
документы, возврат, пересдача, пропуск, сертификат, перевод на другой курс, праздники,
связь с преподавателем) — связный текст, не ключевые слова; целиком в тексте дока
`sborka.py` (`KB_ITEMS`). Три вопроса намеренно ВНЕ базы — программа лояльности, скидка за
друга, бесплатное демо-занятие. Модель обеих версий — `qwen/qwen-2.5-7b-instruct` через
`OpenRouter account` (`VbxiQn8TbqA4R2mw`). Приёмник — НОВАЯ таблица Data Table
`s9_case1_answers` (`U5BLSv5cPzVVyRGy`, создана `POST /data-tables` 2026-10-24, своя схема
`version/question/answer/grounded_item/decision`) — отдельно от `requests` С7/С8, потому
что схема строк другая.

### Версия 1 — свободный ответ, по 6 заявок — executions `606`–`611`

| # | Вопрос | В базе? | Ответ (дословно) |
|---|---|---|---|
| 606 | Как перенести занятие, если я заболел? | да (kb2) | корректно по базе |
| 607 | Какие документы нужны для поступления? | да (kb3) | корректно по базе, **но см. находку 2** |
| 608 | Когда вернут деньги за отменённый курс? | да (kb4) | корректно по базе |
| 609 | Какая у вас программа лояльности для постоянных клиентов? | **нет** | «По нашей базе знаний нет информации о специальной программе лояльности для постоянных клиентов. Если у вас есть вопросы или предложения по данному вопросу, я могу передать их сотрудникам учебного центра.» |
| 610 | Если я приведу друга на курс, будет ли нам скидка? | **нет** | «По нашей базе знаний скидка за приглашение друга не предусмотрена. Если у вас есть другие вопросы или вам нужна помощь, я с удовольствием помогу!» |
| 611 | Есть ли бесплатное демо-занятие перед покупкой курса? | **нет** | «По нашей базе знаний нет информации о бесплатном демо-занятии перед покупкой курса. Если у вас есть такая просьба, лучше обратиться к администратору для уточнения возможностей.» |

**Честная оговорка против гипотезы `ARCHITECTURE.md`.** План ожидал, что версия 1 на
вопросах вне базы ответит «уверенно и неверно». **В этом прогоне этого не произошло** — на
всех трёх вопросах вне базы модель честно призналась, что не знает (промт explicitly просил
об этом: «если не уверена — напиши, что не знаешь»). Это не делает находку бесполезной —
наоборот, она важнее: **самоотчёт сработал в этом прогоне, но ничто в графе не
ГАРАНТИРУЕТ, что он сработает в следующем** — решение «отвечать/эскалировать» живёт
исключительно внутри текста модели, не проверяется кодом. Для слайда это аргумент про
**верифицируемость**, а не только про частоту ошибок; кому нужен кейс именно с
confidently-wrong ответом — нужны более провокационные вопросы вне базы (например, про
конкретные уже-существующие процедуры по аналогии), это задача фазы измерения кейсов, не
этой сессии (прямое ограничение задачи: «замеры кейсов делает другой заход, не ты»).

Тот же класс сбоя, что в README С8 для варианта агента-калькулятора («одно переключение на

### Версия 2 — детерминированная проверка, 6+1 заявок — executions `612`–`617`, `618`

Те же шесть вопросов (для прямого сравнения):

| # | Вопрос | `grounded_in_item` | Ветка IF | Решение |
|---|---|---|---|---|
| 612/618 | Как перенести занятие, если я заболел? | `kb2` | true | answered |
| 613 | Какие документы нужны для поступления? | `kb3` | true | answered |
| 614 | Когда вернут деньги за отменённый курс? | `kb4` | true | answered |
| 615 | Какая у вас программа лояльности для постоянных клиентов? | `""` | false | escalated → Ольга |
| 616 | Если я приведу друга на курс, будет ли нам скидка? | `""` | false | escalated → Ольга |
| 617 | Есть ли бесплатное демо-занятие перед покупкой курса? | `""` | false | escalated → Ольга |

Все 6 решений детерминированы и объяснимы (`IF`-узел `Grounded in known KB item?` считает
`["kb1"…"kb10"].includes(grounded_in_item)` — код, не доверие к слову модели «уверена»).
Расхождение с версией 1 в этом прогоне не в ТОЧНОСТИ на этих шести вопросах (обе ответили
по существу верно), а в том, что решение версии 2 **проверяемо и воспроизводимо той же
проверкой**, а решение версии 1 — нет: ничего не мешало бы ему в другой день ответить
текстом без оговорки «не знаю».

### Находка 3 (исправлена) — тот же класс бага, что находка 1, в двух узлах версии 2

Первый прогон версии 2 (execution `612`, до правки) дал **пустой** экран результата
(«Ответ:» и «опора:» без текста) — найдено не чтением JSON (там всё было верно), а
визуальным скрином Задачи 3 (`case1-v2-result-screen.png`, первая съёмка). Причина: узел
`Result screen (answered)` ссылался на `$json.output.answer`/`$json.output
.grounded_in_item`, но между узлом извлечения и экраном стоит `Write row (answered)` (Data
Table insert), который отдаёт строку ПЛОСКИМИ полями (`answer`, `grounded_item`, без
`output`). Тот же сбой — в узле `Write row (escalated)`, который после правки IF идёт не
сразу, а ЧЕРЕЗ `Notify Olga (escalation)` (Telegram), чей вывод тоже подменяет `$json`
ответом Telegram Bot API; колонка `grounded_item` эскалированной строки писала `null`
(видно в `GET /data-tables/U5BLSv5cPzVVyRGy/rows`, строка `id=10`, до правки). Оба места
исправлены именованными ссылками (`$json.answer`/`$json.grounded_item` после `Write row
(answered)`; `$('Answer with grounding (structured)').item.json.output.grounded_in_item`
для `Write row (escalated)`). **Подтверждающий прогон — execution `618`** (ещё раз «Как
перенести занятие, если я заболел?», `s9-answer-gated`) — экран результата показал «Ответ: …
опора: kb2» полностью (скрин `case1-v2-result-screen.png` переснят после правки). Это
7-й запрос версии 2 — сверх шести, заявленных в задаче, с явным обоснованием: это
проверка собственного исправления инфраструктуры Задачи 3, не повторная проверка решения
Задачи 2 (та подтверждена шестью прогонами `612`–`617` выше). Путь эскалации
(`Write row (escalated)`) структурно исправлен тем же приёмом, но отдельным прогоном не
перепроверен — чтобы не превышать бюджет задачи.

**Обе находки 1 и 3 — один и тот же класс сбоя**: узел между источником поля и местом, где
поле читается, молча подменяет `$json`, и если ссылка на предыдущий шаг не именована явно
(`$('Имя узла')`), поле исчезает без ошибки выполнения — прогон зелёный, данные пустые.
Стоит записи в `notes/mcp-limitations.md` для будущих занятий дуги (С10–С12 тоже строят
цепочки `chainLlm`/`informationExtractor` → узел записи) — файл вне зоны правок этой
сессии, оставляю находку здесь для передачи.
