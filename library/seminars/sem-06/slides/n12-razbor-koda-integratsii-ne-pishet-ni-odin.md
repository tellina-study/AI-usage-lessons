# Кода интеграции не пишет ни один из пяти

## Assertion

Кода интеграции не требует ни один из пяти способов: агент сам шлёт запрос и сам разбирает ответ. Разделяет их то, знает ли агент заранее, что у системы можно спросить. Для регулярного доступа нескольких сессий это оставляет два законных варианта подключения.

## Visual

| Способ | Что делает | Что не делает / ограничение |
|---|---|---|
| вызвать API напрямую | агент сам пишет и шлёт запросы к эндпойнтам, сам разбирает ответ — отдельный код интеграции писать не нужно | заранее не знает спецификацию сервиса: какие есть точки, какие у них параметры и ограничения — без документации или swagger-описания агент их не угадает |
| подключить чужой сервер — удалённо | сервис, который кто-то хостит и обновляет сам; у вас не крутится отдельный процесс | управляете не вы: не видно, что сервис делает внутри и когда в нём что-то меняется; плюс обычные вопросы безопасности удалённого сервиса — кому доверяете ключ, у кого ещё есть доступ |
| подключить чужой сервер — локально | пакет исполняется у вас, конфигурация — строка в репозитории, видна всей команде в ревью; контроля больше, чем у удалённого | это всё равно живой процесс на вашей машине и чужой код — со всеми его зависимостями и правом на обновление |
| написать свой сервер | даёт ровно нужный набор операций и прав, без чужого кода в процессе | написать минимальный сервер сейчас быстро — для этого есть готовый плагин; дорого обходится поддержка: протокол, чужие пользователи, безопасность транспорта — отдельный проект рядом с основным |
| вызывать команду `gh` каждый раз | готовый официальный CLI GitHub — авторизацию и разбор ответа он уже решил за вас, кода писать не нужно | каждый вызов — отдельная команда без общего списка возможностей: агент не видит заранее, что вообще можно сделать, нужный вызов приходится знать заранее |

> **Поворот.** Интеграцию не пишут ни в одном из пяти способов: агент сам шлёт запрос и сам разбирает ответ. Разделяет пятёрку другое — знает ли агент заранее, что у системы можно спросить.
> **Что это оставляет.** Свой сервер избыточен: официальный для трекера уже есть. `gh` и прямой вызов API закрывают вызов, известный заранее; растущий список операций они перекладывают на память разработчика.
> **Два законных варианта.** Между «удалённо» и «локально» готового ответа нет: свежий официальный пример подключается удалённо, решение занятия — локальный процесс, потому что конфигурация становится кодом в репозитории, видимым в ревью.

## Speaker notes

Сначала то, что разбор опровергает. Кода интеграции не придётся писать ни в одном из пяти способов. Агент сам соберёт запрос и сам разберёт ответ — это он умеет, и умеет одинаково во всех пяти случаях. Догадка, с которой заходили в кейс, оказывается ложной, и выбор приходится делать по другому основанию.

Основание такое: знает ли агент заранее, что у системы можно спросить. По нему и разбираются пять способов.

**Прямой вызов API.** Агент сам пишет и шлёт запросы к эндпойнтам, сам разбирает ответ. Предел здесь лежит в другом месте: спецификацию сервиса агент не угадает — какие есть точки, какие у них параметры, какие ограничения. Её нужно дать: документацией, swagger-описанием, примером запроса. Пока описание свежее, способ работает, и работает гибко — доступны любые точки сервиса, включая те, которых нет ни в одном готовом сервере. Устаревает описание молча: сервис поменял версию, описание осталось прежним, агент уверенно шлёт запросы по старым адресам.

**Чужой сервер удалённо.** Сервис, который кто-то хостит и обновляет сам; у вас не крутится отдельный процесс, нечего запускать и нечему падать. Плата за это — управление: не видно, что сервис делает внутри и когда в нём что-то поменялось. Сюда же обычные вопросы безопасности удалённого сервиса: кому вы доверяете ключ и у кого ещё есть к нему доступ. Чем это кончается в худшем случае, видно в провале следующего кейса блока: у одного MCP-сервера для баз данных флаг «только чтение» не делал соединение реально ограниченным.

**Чужой сервер локально.** Пакет исполняется у вас, конфигурация — строка в репозитории, видна всей команде в ревью. Контроля здесь больше, чем у удалённого: версия зафиксирована вами, обновление происходит тогда, когда вы его сделали. Остаётся то, что это живой процесс на вашей машине и чужой код — со всеми его зависимостями и правом на обновление.

**Свой сервер.** Даёт ровно нужный набор операций и прав, без чужого кода в процессе. Написать минимальный сервер сейчас быстро — для этого есть готовый плагин. Дорого обходится поддержка: обновления протокола, чужие пользователи, безопасность транспорта. Это отдельный проект рядом с основным, и заводить его стоит тогда, когда нужного набора операций нет ни у кого из готовых поставщиков.

**Команда `gh` каждый раз.** Готовый официальный CLI GitHub: авторизацию и разбор ответа он уже решил за вас, кода писать не нужно. Каждый вызов при этом — отдельная команда без общего списка возможностей. Агент не видит заранее, что вообще можно сделать; нужный вызов приходится знать заранее — и знает его разработчик.

Вывод складывается из сочетания, в три хода.

Первый: свой сервер избыточен. Официальный сервер для трекера уже существует, и своя реализация повторила бы его работу, добавив к проекту второй проект.

Второй: `gh` и прямой вызов API закрывают вызов, известный заранее. Это их законная область, и она широкая. Растущий список операций они перекладывают на память разработчика — и ровно на этом месте вторник из сцены повторяется, только уже с командами: нужная команда существует, но её никто не вспомнил.

Третий: между «удалённо» и «локально» готового ответа нет, законны оба. Свежий официальный пример подключения к этому же сервису — удалённый http-сервис; решение этого кейса — локальный процесс, потому что тогда конфигурация становится кодом в репозитории, видимым в ревью всей команде. Локальный способ при этом остаётся официально поддерживаемым, так что от существования удалённого примера решение не портится. Знать стоит другое: официальный путь одного и того же поставщика со временем меняется, и ссылку на «официальный способ» в собственной документации приходится перепроверять.

Как приложить этот разбор к своей системе — четыре вопроса по порядку. Есть ли для неё готовый сервер: если есть, свой писать незачем. Сколько операций нужно и растёт ли их число: одна известная операция закрывается командой или прямым вызовом, растущий список требует, чтобы агент видел его сам. Готовы ли вы держать ещё один живой процесс с доступом к секретам: если нет, разовый вызов надёжнее процесса, который никто не обслуживает. И только после этого — где должна лежать конфигурация: в репозитории, если подключение касается всей команды, у себя, если это эксперимент.

Остаётся вопрос, который разбор оставляет открытым: за что тогда вообще платят подключением, если доступ даёт и обычная команда? Платят за список возможностей, который агент читает сам. Сколько это стоит в токенах, считается дальше в кейсе, на экране постоянной платы, и цифра там неожиданная.
