# Решаем: какие операции разрешить, потом — какие права

## Assertion

Первый ход — список операций, которые агент должен уметь. Второй — по каждой строке широкого токена вычёркиваем то, что список не требует.

## Visual

**Ход 1 — что конкретно агент должен делать?**

`читать открытые issue` · `писать комментарий` · `создавать черновик правки`

**Ход 2 — что даёт широкий персональный токен по умолчанию, и что из этого нужно?**

| Право по умолчанию | Нужно для нашего списка операций? |
|---|---|
| все репозитории пользователя, включая приватные | нет — вычеркнуть |
| чтение и запись | частично — чтение нужно, запись (комментарий, черновик) нужна |
| управление настройками | нет — вычеркнуть |
| удаление | нет — вычеркнуть |

> Остаётся: один репозиторий, чтение issue, создание черновика правки.

## Speaker notes

Файл пишется в конце этого разговора. Начать с синтаксиса — значит проскочить два решения, которые весят больше синтаксиса: какие операции агенту разрешить и какие права под них выдать.

Первый ход быстрый: что конкретно агент должен делать? Для нашей задачи список короткий — читать открытые задачи, писать комментарий, готовить черновик правки. Три операции, ничего больше. Список этот составляется под задачу и не берётся у сервера: официальный сервер трекера умеет заметно больше трёх вещей, и из его полного набора нужно знать свои. Операции задают, какие права запрашивать; обратный порядок даёт ключ, заведомо более широкий, чем задача, под которую он выпускался.

Второй ход несёт основной вес. Широкий персональный токен по умолчанию даёт четыре вещи: все репозитории пользователя, включая приватные; чтение и запись; управление настройками; удаление. По каждой строке задаётся один и тот же вопрос — наш список из трёх операций этого требует? Все репозитории, включая приватные: нет, работа идёт в одном. Чтение и запись: чтение нужно для задач, запись нужна для комментария и черновика — строка остаётся. Управление настройками: нет. Удаление: нет. Вычёркивание идёт строка за строкой, и остаётся один репозиторий и две операции.

Порядок важен сам по себе: сначала операции, потом права. Обратный порядок — взять токен, какой есть, и посмотреть, что получится — оставляет в ключе ровно ту строку, которая через несколько экранов окажется решающей.

Соблазн, который стоит разобрать до конца: создать токен с правами по умолчанию и просто не пользоваться лишним. Так нельзя, и причина лежит вне дисциплины. Токеном может воспользоваться тот, кто им завладеет, и тогда решает то, что физически позволяет сделанный ключ, безотносительно вашего намерения. Вопрос «пользуюсь ли я этим правом» к делу не относится вовсе; вопрос ровно один — есть это право в ключе или нет.

Избыточность такого рода — норма, не исключение. Та же системная выборка показывает, что прав выдают больше, чем нужно, и это касается не только отдельных серверов, но и самого транспортного слоя официального SDK протокола.

Сколько времени занимает такая проверка — прямых замеров нет ни в одном источнике, и это честный пробел. Сказать можно другое: разговор, разложенный здесь на ходы, и так происходит в момент создания токена, отдельного времени он не требует.

Этот экран стоит запомнить. Через несколько экранов будет инцидент, который воспроизводится ровно тогда, когда верхняя строка не вычеркнута.

И последнее — что делать, когда операция понадобится четвёртая. Вернуться к этому же разговору и выпустить ключ заново. Дописать право в существующий токен дешевле, и ровно поэтому список прав со временем расползается далеко за пределы задачи, под которую он заводился.
