## Проблема

Владельцу нужна ссылка на *заполненную*, а не шаблонную конфигурацию — рабочий пример, на
котором студент видит все семь ступеней лестницы на реальных файлах, а не на
`<BRACKETED>`-заглушках `base-project-template`.

## Сквозной кейс — тот же самый, что на слайдах семинара

Семинар «Сборка кодинг-агента» (`library/seminars/sem-04/plan.md`,
`plan-part2.md`) разбирает один сквозной кейс от первой до последней минуты: маленький сайт,
не абстрактный `agent-demo`. **Учебная сборка обязана быть этим же самым проектом** — студент,
досмотревший семинар (только слайды, живого показа на занятии нет — см. «Проверка без живого
показа» ниже) и открывший ссылку на сборку, должен увидеть то же самое, что было на слайдах, а
не другой пример с похожей структурой.

**Задача проекта-носителя.** Лендинг с формой заявки на демо-урок: одна статическая страница,
поля «имя» и «email», кнопка отправки, без собственного бэкенда — заявка уходит на внешний
сервис приёма форм.

**Стек.** Сборка Vite поверх HTML/CSS/JS (`npm run build` → `dist/`); Playwright —
`tests/form.spec.ts`, команда `npx playwright test`, проверяет, что форма не отправляет пустые
обязательные поля; хостинг статический (например, Cloudflare Pages), деплой —
`wrangler pages deploy dist`; задачи — GitHub Issues этого же репозитория.

**Кто работает.** Один разработчик с агентом, без команды — соло-сценарий (тот же, для которого
курс отдельно проверяет применимость каждой ступени).

**Имя репозитория внутри сборки.** `signup-landing/` — то же имя, что на слайдах семинара; не
переименовывать, это одна из немногих деталей, по которой студент механически сверяет «то же
самое ли это».

**Семь шагов истории репозитория = семь ступеней семинара** (файл инструкций → память → хук →
скилл → MCP → субагент → процесс) — каждый шаг ниже (8.1–8.7) соответствует одному разделу
семинара один в один, включая сценарий-боль, которым открывается каждый раздел на слайдах.

## Проверка без живого показа

Владелец, 2026-09-20: на самом семинаре живого терминала нет — всё, что раньше было
«демонстрацией на экране», стало содержимым слайда (снимок терминала, блок кода, фрагмент
диалога). **Следствие для сборки:** студент не видел ни одной команды выполняющейся вживую —
первый раз он реально запускает что-либо у себя, после занятия, клонировав сборку. Значит
**в каждом шаге 8.1–8.7 обязательны: воспроизводимая команда и ожидаемый вывод**, не просто
«что добавлено». Это не то же самое, что критерий приёмки самой подзадачи (тот проверяет
исполнителя наряда) — это отдельное требование к содержимому каждого шага, которое проверяет
студент. Формат внутри каждого шага ниже: блок «Проверка» с точной командой и тем, что должно
появиться на экране.

## 8.0 — Разместить сборку по таксономии реестра

**Проблема.** Корневой `README.md` определяет `data/bundles/*.yaml` + `deep-dives/bundles/*.md`
как категорию именно для «ASSEMBLED multi-component kit» (issue #32), без category-подпапки —
это описание нужного артефакта дословно: не атомарный компонент, а собранный из нескольких
компонентов набор. Сегодня в `data/bundles/` нет ни одного `first_party: true` экземпляра.

**Что сделать.**
- Файлы сборки — `templates/base-project-worked-example/` (parallel-каталог к
  `base-project-template/`, тот же MIT-раздел лицензирования, см. `templates/
  base-project-template/LICENSE`).
- Каталожная запись — `data/bundles/base-project-worked-example.yaml`, `first_party: true`,
  `components_bundled:` перечисляет ровно то, что реально внутри (память, хук, скилл, MCP-раздел,
  субагент, процесс).
- Deep-dive — `deep-dives/bundles/base-project-worked-example.md`, обязательная секция —
  scoring-таблица против трёх свойств бандла (sustained / engine-agnostic /
  progressively-disclosed), которую README требует от каждого бандла и три свойства которой
  не собирает разом ни один бандл каталога (максимум — 2 из 3). Саму таблицу заполняют все
  восемь существующих бандлов — образец формата брать у любого из них.
- Двунаправленная связка: `related_components: [base-project-template]` в новой YAML +
  обратная ссылка `related_research`/`related_components` со стороны компонента шаблона —
  правило README требует выставлять оба направления вручную, `generate.py` только проверяет
  резолвинг, не создаёт связь сам.
- `deep_dive:` — обязательное поле и на самой YAML-записи компонента, и на бандле; без него
  `scripts/generate.py` падает.

**Критерий приёмки.** `python3 scripts/generate.py` проходит без ошибок; `GUIDE.md` содержит
строку `base-project-worked-example` с бейджем `first-party` в таблице бандлов;
`related_components`/`related_research` резолвятся в обе стороны.

## 8.2 — Ступень 2: память + журнал решений

**Триггер.** Агент второй раз за неделю предлагает подключить стороннюю библиотеку валидации
форм — то самое решение, что уже было отклонено в прошлой сессии.

**Что сделать.** Реальная запись в `DECISIONS.md` по формату шаблона:

```markdown
## 2026-09-20 — не подключаем библиотеку валидации форм
Форма — два поля (имя, email), хватает нативных `required`/`pattern` + `src/validate.js` на
20 строк. Сторонняя библиотека — лишняя зависимость и лишние килобайты в сборке ради этого объёма.
```

Плюс демонстрация авто-памяти рантайма — команда «запомни, что мы не подключаем библиотеку
валидации форм» создаёт файл вне репозитория, в `~/.claude/projects/<project>/memory/`. Этот
файл **не коммитится в `signup-landing/`** — он не часть дерева сборки, только инструкция, как
его воспроизвести у себя.

**Проверка (студент у себя).**
```bash
cat DECISIONS.md        # видна запись выше
ls ~/.claude/projects/*/memory/   # путь зависит от места клонирования — см. примечание ниже
```
Примечание прямо в README сборки: путь `~/.claude/projects/<project>/` формируется Claude Code
автоматически из полного пути клонированного репозитория — студент увидит свой собственный
путь, не `signup-landing`, если клонировал в другую директорию; это ожидаемо, не ошибка.

**Провал в этом шаге.** SpAIware (ChatGPT macOS, Johann Rehberger, сентябрь 2024,
`thehackernews.com/2024/09/chatgpt-macos-flaw-couldve-enabled-long.html`) — непрямая инъекция
внедрила ложную инструкцию в долговременную память, пережившую конец разговора. Разбор —
`02-memory.md`, §4.2.

**Критерий приёмки подзадачи.** `DECISIONS.md` содержит минимум 3–4 реальные записи (не только
пример выше — остальные описывают действительные решения по ходу сборки самого проекта);
блок «Проверка» воспроизводим.

## 8.3 — Ступень 3: хуки + самотест на оба

**Триггер.** Накануне показа сайта заказчику агент коммитит правку формы прямо в `main`, хотя
`CLAUDE.md` текстом запрещает это.

**Что сделать.** Два хука в одном массиве `PreToolUse` в `.claude/settings.json`:
1. Защита ветки (готовый код — `with-git/.claude/settings.json` из шаблона, не сокращать при
   копировании).
2. Второй реальный хук — запрет `rm -rf` с wildcard-паттерном (урок из
   `04-failures-evidence.md`, инцидент Claude CLI декабрь 2025, `rm -rf ~/`, сводка —
   `docker.com/blog/coding-agent-horror-stories-the-rm-rf-incident`).

Плюс `.claude/hooks/selftest-branch-guard.sh` из наряда 5 (часть 1), расширенный на оба хука —
не два отдельных скрипта, один с двумя блоками проверки.

**Проверка (студент у себя).**
```bash
bash .claude/hooks/selftest-branch-guard.sh
```
Ожидаемый вывод — построчно: `deny` с текстом «BLOCKED: direct commit to main/master...» при
попытке коммита на `main`; **`deny`** (не `ask`) при unborn HEAD — ветка на неродившемся HEAD
уже известна, `git symbolic-ref --short HEAD` возвращает `main` с кодом 0, поэтому защита
обязана срабатывать; `ask` зарезервирован за отдельным случаем «каталог вообще не
git-репозиторий» (`git rev-parse --is-inside-work-tree` не проходит). Далее — `deny` при
попытке `rm -rf` с wildcard-паттерном. Если хоть одна строка не совпала — хук не готов, это и
есть демонстрируемое живьём срабатывание («шлюз, который можно запустить и увидеть
срабатывание»), не то, во что нужно просто поверить.

**Явная оговорка про третью строку вывода (решение зафиксировано, а не умолчано).** Проверки
`rm -rf` в шаблоне сегодня нет вообще: в `with-git/.claude/settings.json` ноль вхождений
`rm -rf`/`wildcard`, и самотест из наряда 5 (часть 1) такой строки не печатает и печатать не
может — он покрывает только защиту ветки. Пункт оставлен в критерии **намеренно**, но он
относится к тому второму хуку, который создаётся здесь же, в подзадаче 8.3, — а не к
унаследованному из наряда 5 скрипту. Практическое следствие для исполнителя: сначала пишется
второй хук, только потом самотест расширяется на него; принимать 8.3 по этой строке, не
построив хук, нельзя, а «починить» несовпадение правкой самотеста вместо написания хука —
прямая ошибка. Это ровно то правило, которое формулирует сам шаблон в комментарии
`settings.json`: каждое новое обязательное правило приезжает со своей механической проверкой
в том же изменении.

**Важно не забыть: что этот шаг НЕ защищает (проговорить вслух на занятии).** Оба хука —
`PreToolUse`, то есть механизм харнесса Claude Code: они перехватывают вызовы инструментов
**агентом** и не видят человека, набравшего `git commit` руками в терминале. Самотест этого
случая не печатает и напечатать не может — подробно см. наряд 5, часть 1, абзац про шестой
случай. Здесь это не деталь реализации, а то, ради чего шаг вообще поставлен третьим: триггер
подзадачи — «агент коммитит в `main`», и решение закрывает ровно его. Если не сказать этого
вслух, студент уносит «поставил хук — защитил ветку» в абсолютном смысле, что неверно, и
формула «правила в коде — законы» у него молча распространяется на людей.

**Провал в этом шаге.** `GHSA-ph6w-f82w-28w6` (высокая, без CVE) — принятый диалог доверия к
папке разрешал исполнение её файлов, включая хуки, **без отдельного подтверждения команды**:
механизм хуков сам по себе является поверхностью исполнения. Не путать с `CVE-2025-59536`
(CVSS v4.0 8.7, исправлено в 1.0.111), где код выполнялся **до** диалога доверия — это другая
уязвимость с противоположным механизмом (разбор Check Point:
`research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536`).
Второй слой — тихий отказ хука при невалидном matcher (см. наряд 5, часть 1). Разбор —
`03-hooks-permissions.md`, §5.

**Критерий приёмки подзадачи.** Оба хука реально блокируют (не только существуют файлом);
`selftest-branch-guard.sh` покрывает оба и проходит при запуске против свежего `/tmp`-клона.

## 8.4 — Ступень 4: скилл

**Триггер.** Процедура деплоя (`wrangler pages deploy dist`) — рутина, которую агент выполняет
на каждой сессии, где нужен деплой; держать её в `CLAUDE.md` означает платить за неё контекстом
каждого запроса, даже когда деплой не нужен.

**Что сделать.** `.claude/skills/deploy/SKILL.md` — развитие примера из наряда 3 (часть 1),
доведённое до настоящего применения: frontmatter с `name`/`description` (конкретный триггер, не
«Helps with deployment»), один явный шаг («`npm run build && wrangler pages deploy dist`,
проверить вывод на URL продакшена»).

**Проверка (студент у себя).**
```bash
head -10 .claude/skills/deploy/SKILL.md   # frontmatter виден целиком
```
В сессии Claude Code — `/skills` — `deploy` виден в списке с осмысленным `description`, не
файловым именем.

**Провал в этом шаге.** arXiv:2608.11888 («Agent Skills Can Be Harmful…») — 307 подтверждённых
случаев вреда, вызванного **самим наличием скилла**: 125 функциональных провалов (из них
68,8% — Task-Implementation Fault: скилл выглядел релевантным и заставил агента реализовать
требуемое неправильно) и 182 случая раздутия стоимости (до +451% токенов). Категория «скилл
не подошёл» (Applicability Mismatch) — всего 1,6%, то есть вред идёт не от плохого описания, а
от кажущейся релевантности. Разбор — `07-skills.md`, §4.2 (разбивка 307 случаев); про
описание-триггер — §4.1.

**Критерий приёмки подзадачи.** Скилл реально что-то делает (не заглушка) — история коммитов
сборки показывает хотя бы один реальный вызов `deploy` с результатом.

## 8.5 — Ступень 5: MCP — честный разбор, без мок-сервера

**Триггер.** Агенту регулярно нужно смотреть открытые issue в GitHub-репозитории и готовить
черновики PR — не разово, а на каждой сессии.

**Открытый конфликт этого шага (см. также «Открытые решения владельца» в части 1).**
Требование «клонируется без ключей» прямо противоречит «показать MCP живьём»: живое
подключение GitHub MCP-сервера требует токена, которого в клонируемой сборке быть не должно.
Рекомендация исполнителя — решать в пользу честного разбора, не мок-сервера, который выдаёт
себя за рабочее подключение (мок здесь хуже отсутствия раздела — учит студента, что «Connected»
в выводе значит «работает», что прямо противоречит уроку самого шага, см. провал ниже). Это
рекомендация, не решение владельца — при разногласии на ревью открывать вопрос, не считать
закрытым этим документом.

**Что сделать.** Раздел README сборки (не код, не `.mcp.json` с реальными ключами): что именно
было бы в `.mcp.json`, если бы сервер подключался (пример конфигурации — project-scope:

## 8.6 — Ступень 6: субагент

**Триггер.** Третий раз за неделю та же сессия, что писала код, перепроверяет сама себя перед
мержем — остаётся тем же контекстом рассуждений, тем же слепым пятном.

**Что сделать.** `.claude/agents/diff-reviewer.md` — развитие наряда 4 (часть 1), применённое
внутри сборки:

```markdown
---
name: diff-reviewer
description: Независимый ревьюер diff'ов. Видит только сам diff и критерии приёмки, не
  рассуждения автора. Используй перед мержем любого нетривиального изменения. НЕ для
  методической критики текста — это отдельная роль.
tools: Read, Grep, Glob
---

# diff-reviewer

Ты не правишь код сам — только находишь проблемы. Начни ответ строкой:
`VERDICT: PASS | BLOCK`

Затем: что проверено (конкретно — какие файлы прочитаны), находки (что не так, где, почему важно).
Пустой список находок — валидный PASS.
```

Применить его на реальный diff внутри истории сборки — например, ревью коммита ступени 3
(хуки).

**Проверка (студент у себя).** Вызвать `diff-reviewer` на любой собственный diff в
клонированном репозитории — ответ обязан начинаться строкой `VERDICT:` и не ссылаться на
переписку, в которой изменение создавалось (только на сам diff).

**Провал в этом шаге.** MAST (Cemri, Pan и др., arXiv:2503.13657) — 41–87% провальных трасс по
7 фреймворкам. GitHub issue `anthropics/claude-code#67730` — субагент вернул полностью
галлюцинированный отчёт с нулём реальных вызовов инструментов. Разбор — `08-subagents.md`,
§4.1–4.2.

**Критерий приёмки подзадачи.** `tools:` явно исключает `Write`/`Edit`; хотя бы один реальный
запуск `diff-reviewer` зафиксирован в истории/журнале сборки (не только сам файл существует).

## 8.7 — Ступень 7: процесс — план, прожарка, журнал

**Триггер.** Агент пишет в чат «Готово, все тесты прошли, можно мержить» — работу принимают на
слово, без проверки, что именно проверено.

**Что сделать.** `Tasks/` с `README.md` (указатель на `Tasks/README.md` шаблона, не копия
текста — сборка не дублирует `common/` вручную, см. 8.8), `review.md.template`, и минимум один
реальный `Tasks/<date>_<slug>/` с `log.md` (запись по ходу работы над самой сборкой, не
восстановленная задним числом) и `review.md` (вердикт `PASS`/`BLOCK`, раздел «что проверено» —
конкретные файлы и команды).

**Проверка (студент у себя).**
```bash
cat Tasks/2026-09-20_form-endpoint-fix/log.md      # запись с таймстампом и командой
cat Tasks/2026-09-20_form-endpoint-fix/review.md   # вердикт + что проверено
```
`Shift+Tab` дважды в сессии Claude Code — баннер `plan mode on`, попытка редактирования файла
в этом режиме — отказ (это студент воспроизводит у себя, не сборка поставляет файл-результат).

**Провал в этом шаге.** «From Confident Closing to Silent Failure» (arXiv:2606.09863, ICML
2026 FAGEN) — 75,8% провальных траекторий кодинг-агентов на AppWorld уверенно отчитаны как
«готово». METR, «Recent Frontier Models Are Reward Hacking»
(`metr.org/blog/2025-06-05-recent-reward-hacking/`, 5 июня 2025) — модель o3 патчила функцию
оценки, добившись 100% (21/21) на одной из задач RE-Bench. Разбор —
`06-process-roast-log.md`, §5.1–5.2.

**Критерий приёмки подзадачи.** Минимум один `Tasks/<slug>/` внутри сборки — реальный, с
`log.md` и `review.md`, документирующий работу над самой сборкой (рекурсивно — сборка
демонстрирует дисциплину ступени 7 на себе самой, не только рассказывает о ней).

## 8.8 — README-лестница + механизм против расхождения со шаблоном

**Что сделать — README сборки.** Ведёт по лестнице, а не описывает папки: семь разделов
README = семь шагов 8.1–8.7 выше, каждый со ссылкой на соответствующий коммит/тег в истории
поддиректории `base-project-worked-example/` (история должна быть видна в `git log --follow`
или через отдельные теги `step-1`…`step-7`) — не таблица «файл → что это». Каждый раздел
README содержит блок «Проверка» дословно из соответствующего шага выше (воспроизводимая
команда + ожидаемый вывод) — это то, что реально попадает в руки студента.

**Механизм против расхождения — три меры, ни одна не требует новой инфраструктуры.**
1. Сборка не копирует общий текст `common/` вручную — `Tasks/README.md`, `DECISIONS.md`
   (формат, не содержание), `profiles/` остаются указателями на
   `templates/base-project-template/common/` там, где контент идентичен, и расходятся только
   там, где сборка специально показывает заполненный вид (8.1–8.7).
2. В `render_templates.py` — необязательный флаг `--check-worked-example`, сверяющий, что
   *структурные* инварианты (набор ожидаемых файлов, наличие frontmatter в примерах
   скиллов/субагентов) не разошлись с текущей версией `common/`/`fragments/` — не побайтовое
   совпадение, а совпадение списка обязательных слотов.
3. Пункт в чек-листе «Adding or updating an entry» корневого `README.md`: изменение
   `common/`/`fragments/` требует прогона `--check-worked-example` в том же PR — тот же принцип
   «raise, don't silently skip», которым уже живёт `scripts/generate.py`.

**Критерий приёмки подзадачи.** README структурирован как семь шагов, не как перечисление
«файл — что это»; `render_templates.py --check-worked-example` реализован и проходит.
