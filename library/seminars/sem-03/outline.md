# Семинар 3 — Три механизма модели в системном дизайне

**Цель:** научить junior-инженера принимать проектные решения, опираясь на механизмы
LLM из Лекции 2 (эмбеддинги, внимание, сэмплинг, токенизация) — и делать это по
структуре «постановка → студенты предполагают → метод → реализация → нюансы».

**Арка:** от «как модель кодирует смысл» (эмбеддинги) → «что она понимает в тексте»
(внимание) → «как она порождает и видит текст» (сэмплинг и токены).

## Блок 1 — Эмбеддинги

- **Кейс 1.1 — Выбор embedding-модели под свой корпус** (создание).
  Постановка (только задача+требования: свой русский корпус с терминами, латентность,
  дорогая смена модели, разметки нет) → студенты сами предполагают критерии → метод
  (мини-eval на своих парах: recall@k/MRR) → варианты по осям (мультиязычная/одноязычная,
  доменная/общая, размерность) → нюанс (лидер MTEB ≠ лучший на домене).
  *Учтено: п.1 (постановка отдельно от критериев/вариантов), п.2 (concept=«как сравнивать»,
  отдельный variants-слайд), п.3 (оси вариантов в заголовках блоков).*
- **Кейс 1.2 — Дедуп тикетов** (доработка).
  Постановка (поток тикетов, надо схлопывать дубли) БЕЗ ловушки → метод (близость по τ +
  структурный гейт; размер eval-набора зависит от задачи, не фикс «200») → ловушка
  Visa/Mastercard показывается в complication, не в постановке.
  *Учтено: п.4 (ловушка убрана из постановки), п.5 (число пар — функция задачи).*

## Блок 2 — Внимание

- **Кейс 2.1 — Извлечение «кто кому платит» из договоров** (создание).
  Постановка (парсим договоры в структуру платежей) БЕЗ упоминания сложности → метод
  (LLM-извлечение + span-обоснование + гейт уверенности + кросс-проверки) → сложность
  (неоднозначная кореференция, Winograd-тип) показывается в complication.
  *Учтено: п.6 (сложность из context → в complication).*
- **Кейс 2.2 — Ассистент юротдела: поднять качество и как измерить** (доработка).
  Постановка (жалобы на точность, метрики нет) → метод (golden set, метрики, замер
  базлайна) → усложнение (роль в промпте не двигает метрику) → разбор (grounding по
  метрике). 4 слайда, без дубля.

## Блок 3 — Сэмплинг и токенизация

- **Кейс 3.1 — Генератор карточек товара: текст описания и структурные параметры**
  (создание). Постановка (генерим и маркетинговое описание, и структурные атрибуты) →
  метод: **два отдельных запуска** — (а) описание: подбор температуры под живость;
  (б) параметры: **structured output** (json_schema, strict) + низкая T → схема решения
  (два режима генерации в одном пайплайне) → нюанс (T управляет разбросом, не
  достоверностью; схема гарантирует форму, не истину значения).
  *Учтено: п.7 (structured output; отдельный запуск для описаний и для параметров;
  слайд distribution убран; схема решения добавлена).*
- **Кейс 3.2 — Токенизация ломает подсчёт/валидацию** (правка). Принято как состав.
  Механизм токенизации из Л2 («модель не считает буквы») не задействован ни в одном
  другом кейсе — это и даёт новизну (п.9). Постановка: фичи считают символы / проверяют
  длину / режут по символам (пароль, маскирование карты, лимит, подсчёт) — на LLM
  ломается. Метод: токен ≠ символ, почему счёт/позиции ненадёжны; решение —
  детерминированный код (len/regex/срезы/count), модель — на смысл, не на подсчёт. Даёт
  сильный контраст с 3.1 (там генерация — ниша модели; тут подсчёт — не её задача).

## Что учтено глобально
- **п.8:** каждый разбор по стандарту схема → логика реализации → ключевые компоненты →
  ключевые комментарии (см. method-doc).
- Постановка каждого кейса — только задача+требования; критерии/варианты студенты
  предполагают сами, разбор идёт после.
