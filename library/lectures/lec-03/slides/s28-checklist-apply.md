# Visible content

## Title bar
«Чек-лист "прежде чем строить"»

## Body
[Слева — нумерованный чек-лист 8 пунктов в Ocean rounded box]

1. Можно ли решить **обычным кодом** (детерминированно, верифицируемо)? → не добавляй ИИ
2. Хватит ли **одного промпта** (+ few-shot / CoT)? → остановись здесь
3. Знание меняется / нужны свежесть, провенанс? → **RAG**, не fine-tuning
4. Нужно стабильное поведение / тон / формат / политика? → **fine-tuning (PEFT)**, не RAG
5. Корпус влезает в окно и стабилен? → **длинный контекст + кэш**, не RAG-инфраструктура
6. Задача предсказуема? → **workflow**. Непредсказуема и ценна? → **агент с budget/loop-лимитами**
7. Подзадачи независимы и широко-параллельны? → **мульти-агент**; иначе — один линейный агент
8. Данные чувствительны? → **карта данных** по фиче + least-privilege + ZDR/BAA + человек-валидатор

[Справа — 2 блока apply]

**Worked example (задача A):** «2000 регламентов, обновляются еженедельно, ответ с ссылкой на пункт» → шаги 3+8 → **RAG со strict grounding**, без агента и FT. Причины: ось «частота изменений» + ось «провенанс»

**Mini-apply (задача B):** «бот техподдержки на ~150 коротких FAQ, меняются раз в квартал, ответы строго из утверждённых формулировок» — пройдите чек-лист **сами** за 2 минуты

[Gold callout, низ]
**Сначала попытка — потом сверка.** Сформулируйте свой ответ (архитектура + ≥2 причины по осям + ≥1 условие смены выбора) **до** разбора. Разбор — позже; иначе Apply вырождается в узнавание.

## Speaker notes

Лестница и матрица сворачиваются в восьмишаговый чек-лист — инструмент, применяемый к задаче за пару минут до написания кода. Каждый шаг — «когда НЕ» из раздела, как вопрос. Можно ли решить обычным кодом? Хватит ли одного промпта? Знание меняется — RAG, не fine-tuning. Стабильное поведение — fine-tuning, не RAG. Корпус влезает в окно — длинный контекст. Задача предсказуема — workflow; непредсказуема и ценна — агент с лимитами. Подзадачи независимы и параллельны — мульти-агент, иначе один линейный. Данные чувствительны — карта данных по фиче, least-privilege, ZDR или BAA, человек-валидатор.

Покажу образец рассуждения на задаче A: сотрудники спрашивают на естественном языке по двум тысячам внутренних регламентов, обновляются еженедельно, с обязательной ссылкой на пункт. Проход: код — нет, нужен естественный язык; один промпт — нет, регламенты не в весах и приватны; знание меняется и нужен провенанс — RAG, не fine-tuning (устареет, forgetting); проблемы поведения нет; корпус большой и меняющийся — длинный контекст не заменяет RAG; задача «вопрос — ответ с цитатой» предсказуема — агент не нужен, это RAG в режиме workflow; данные чувствительны — карта данных, человек-валидатор. Вывод: RAG со строгой опорой и наблюдаемостью; причина по оси «частота изменений» и по оси «провенанс»; условие смены: если бы регламентов было двадцать и менялись раз в год — длинный контекст плюс кэш.

И теперь — ваша очередь, мини-применение. Задача B: бот техподдержки на базе из примерно ста пятидесяти коротких FAQ-статей, меняются раз в квартал; ответы строго из утверждённых формулировок. У вас две минуты. Важно: сначала попытка, потом сверка. Сформулируйте ответ полностью до разбора, по формату: архитектура, не менее двух причин по осям матрицы, не менее одного условия смены выбора, явный критерий «здесь это было бы НЕ так». Ценность упражнения — в самостоятельном переносе рамки на новую задачу; если сначала услышать готовый разбор, оно вырождается в проверку памяти. Полная отработка с тремя кейсами — на Семинаре 3.
