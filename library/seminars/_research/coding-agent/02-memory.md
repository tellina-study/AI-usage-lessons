# Память агента: когда одного файла инструкций перестало хватать

## Резюме (тезисы)

1. У агента «нет памяти» не потому, что это забыли реализовать — LLM в принципе безсостоятелен (stateless): каждый запрос обрабатывается независимо, а «память» сессии — это просто то, что заново подаётся ему на вход текстом при каждом обращении. Контекстное окно — это лимит на этот вход, а не хранилище.
2. Память — не RAG и не файл инструкций. RAG подтягивает внешние документы под конкретный запрос; CLAUDE.md — статичные правила, которые пишете вы; память — это то, что *агент сам* записывает о фактах, предпочтениях и истории работы и перечитывает в следующих сессиях.
3. В Claude Code (версии ≥2.1.59, с февраля 2026) это конкретно устроено так: авто-память включена по умолчанию, живёт в `~/.claude/projects/<project>/memory/`, состоит из индекса `MEMORY.md` (первые 200 строк или 25 КБ грузятся в каждую сессию) и отдельных тематических файлов, читаемых по требованию.
4. Лестница ступеней: маленький разовый скрипт — память не нужна вообще; повторяющиеся сессии в одном репозитории, где вы трижды объясняете одно и то же — самое время для авто-памяти/CLAUDE.md; десятки файлов, противоречия, нужен поиск по смыслу и множественным пользователям — переходите на систему (Mem0, Letta, Zep/Graphiti, Cognee).
5. Память может уверенно врать: устаревшая запись переживает удалённый флаг/файл и агент действует по ней как по факту. Задокументированный механизм атаки — «memory poisoning»: SpAIware (ChatGPT, 2024, Johann Rehberger), MINJA, PoisonedRAG, MemoryGraft — злоумышленник один раз внедряет ложную запись, и она обслуживается как доверенный контекст бессрочно.
6. Независимое живое тестирование (`harness-eval`, 2026) шести систем памяти (Anthropic Memory Tool, Cognee, CrewAI Memory, Graphiti/Zep, LangMem, Letta, LlamaIndex Memory) против простого варианта «просто вставить весь текст сессии в контекст» (file-wiki baseline) показало: **большинство «умных» систем памяти на малых корпусах либо проигрывают простому файлу, либо выигрывают минимально** — Letta и Graphiti/Zep проиграли baseline на 25-67 пунктов на некоторых тестах.
7. Бенчмарки памяти (LoCoMo, MemBench, MemoryAgentBench) сами по себе методологически сырые: у LoCoMo найден баг скоринга, из-за которого ~23% вопросов принципиально нескорируемы, а «шумовой пол» ошибок разметки — около 6.4%. Модели, почти насыщающие LoCoMo, часто плохо работают в MemoryArena — бенчмарке, где память нужно реально *использовать* для последовательных решений, а не просто вспомнить факт.
8. Продвинутая дисциплина: одна запись = один факт, `MEMORY.md` — только индекс, срок годности и ревизия записей, явное разделение «память / DECISIONS.md / knowledge/notes.md» по ролям, и ключевое правило — не писать в память то, что и так выводимо из кода или git.

## 1. Классическая база: почему у агента «нет памяти»

Языковая модель — чистая функция: `текст на входе → текст на выходе`. Между двумя вызовами API она не хранит абсолютно ничего — ни одного бита состояния. То, что выглядит как «диалог», технически — это заново отправленная модели вся история переписки при каждом новом сообщении. «Память» разговора — иллюзия, создаваемая приложением-обёрткой (Claude Code, ChatGPT и т.д.), которое перед каждым запросом склеивает всё, что нужно модели увидеть, в один текстовый блок.

**Контекстное окно** — это ограничение на размер этого блока (у современных флагманских моделей — до 1 млн токенов, Anthropic, 2026). Как только сессия заканчивается (или контекст переполняется и происходит **компактификация** — сжатие истории в резюме), всё, что не было сохранено во внешнее хранилище (файл, базу), исчезает безвозвратно. Новая сессия начинается буквально с нуля: агент не помнит вчерашней работы, если только кто-то — вы или сам агент — не записал нужное на диск.

Отсюда — три принципиально разные вещи, которые часто путают:

- **Файл инструкций** (`CLAUDE.md`) — статичные правила, которые *вы* написали заранее. Они грузятся в каждую сессию целиком, но не меняются автоматически — агент их читает, но не переписывает по итогам работы (разве что по вашей явной просьбе).
- **RAG (retrieval-augmented generation)** — подтягивание внешних документов (базы знаний, документации, кода) по релевантности к текущему запросу. RAG не хранит *историю взаимодействия с агентом* — это внешняя библиотека, а не журнал памяти агента.
- **Память** — то, что агент сам *записывает* о процессе работы (ваши правки, договорённости, контекст, который нельзя вывести из кода) и сам же *перечитывает* в следующий раз. Это единственный из трёх механизмов, где инициатива записи — на стороне модели, а не человека или поисковой системы.

### Типы памяти простыми словами

Классификация из когнитивной науки, которую унаследовали агентные системы (в т.ч. дизайн Stanford Generative Agents, arXiv:2304.03442, 2023 — один из самых цитируемых источников архитектуры памяти агентов):

- **Рабочая (working)** — то, что помещается в текущее контекстное окно прямо сейчас: последние сообщения, только что прочитанные файлы. Исчезает при закрытии сессии или компактификации.
- **Эпизодическая (episodic)** — журнал конкретных событий с временными метками: «19 сентября починили баг X», «пользователь просил не трогать Y». В Karpathy LLM Wiki-паттерне за это отвечает append-only `log.md`.
- **Семантическая (semantic)** — обобщённые факты и знания вне привязки к конкретному эпизоду: «проект использует pnpm, а не npm», «владелец не любит превосходные формы в текстах». Именно это чаще всего хранит `MEMORY.md` в Claude Code.
- **Процедурная (procedural)** — «как делать» вместо «что случилось»: правила, чеклисты, воркфлоу. В агентных системах это роль CLAUDE.md/AGENTS.md и скиллов, а не памяти как таковой.

## 2. Как это устроено в Claude Code конкретно

С версии 2.1.59 (февраль 2026) в Claude Code есть **два взаимодополняющих механизма**, оба грузятся в начале каждой сессии:

| | CLAUDE.md | Авто-память |
|---|---|---|
| Кто пишет | вы | Claude |
| Что содержит | инструкции и правила | выученные факты и паттерны |
| Область | проект / пользователь / организация | один репозиторий, общая для всех worktree |
| Загрузка | каждая сессия, целиком | каждая сессия, только первые 200 строк или 25 КБ `MEMORY.md` |
| Для чего | стандарты кода, воркфлоу, архитектура | ваши предпочтения, правки, контекст вне кода/git |

**Механика авто-памяти (официальная документация Anthropic, code.claude.com/docs/en/memory, сверено 2026-09):**

- Каталог: `~/.claude/projects/<project>/memory/`. `<project>` определяется по git-репозиторию — все worktree и подпапки одного репо делят один каталог памяти. Вне git — по корню проекта.
- Структура: `MEMORY.md` (индекс, по одной строке на запись) + отдельные тематические файлы (`user_role.md`, `feedback_testing.md` и т.п.), которые агент создаёт сам.
- В каждую сессию грузятся только первые **200 строк или 25 КБ** `MEMORY.md` (что наступит раньше) — остальное отбрасывается при старте. Если файл превышает лимит, запись всё равно проходит, но Claude Code возвращает агенту ошибку с требованием переписать индекс компактнее.
- Тематические файлы **не** грузятся автоматически — агент читает их по требованию обычными файловыми инструментами, когда решает, что информация нужна.
- **Frontmatter**: при записи файла с YAML frontmatter Claude Code сам проставляет поле `modified` (ISO 8601 timestamp) — «насколько свежа запись», видно и человеку, и агенту при следующем чтении.
- **Типы записей** (поле `type` в frontmatter, задаётся самим агентом): `user` (роль/экспертиза/предпочтения пользователя), `feedback` (правки и подтверждённые подходы), `project` (текущая работа, дедлайны, решения, не выводимые из кода), `reference` (где искать информацию вне проекта — трекер задач, дашборд).
- Claude **сознательно пропускает** запись того, что и так выводимо из кода (архитектура, пути файлов, найденные баги) и того, что уже написано в CLAUDE.md.
- Команда `/memory` — открыть/просмотреть/удалить файлы памяти, включить/выключить фичу (флаг `autoMemoryEnabled` в `~/.claude/settings.json`). `/context` — проверить, что именно реально загрузилось в текущую сессию.
- **Быстрая запись через `#`**: в начале сообщения набор `#` исторически предлагал сохранить следующую строку прямо в CLAUDE.md («A new feature release for Claude Code... you can now quickly add memories... using the # key», Борис Черни, разработчик Claude Code). По состоянию на сентябрь 2026 в официальной документации `#` как отдельный ввод уже не описан, и есть открытый баг-репорт (`anthropics/claude-code#14868`, декабрь 2025) о том, что для части пользователей шорткат перестал сохранять в CLAUDE.md. Надёжный путь сегодня — явная просьба «запомни это» (уходит в авто-память) или «добавь это в CLAUDE.md» (уходит в файл инструкций), либо ручное редактирование через `/memory`.
- **Компактификация**: корневой CLAUDE.md **переживает** `/compact` — перечитывается с диска и снова вставляется в контекст. Авто-память по устройству та же: и `MEMORY.md`, и его частота вызова — то, что реально «на диске», а не «в переписке», выживает сжатие. Вложенные CLAUDE.md в подпапках и path-scoped правила подгружаются заново только когда агент реально читает файлы этой подпапки — то есть инструкция может «пропасть» после компактификации не потому что стёрлась, а потому что путь ещё не сработал повторно.
- Каталог памяти **исключён** из автоматической чистки старых транскриптов сессий (`cleanupPeriodDays`) — файлы живут, пока их не удалит явно человек или сам агент.

## 3. Ступени: когда память не нужна, когда появляется, когда нужна система

**Ступень 0 — память не нужна.** Разовый скрипт, один прогон, короткая задача без второй сессии. Всё нужное помещается в контекстное окно текущего разговора. Добавление памяти здесь — чистый оверхед: лишний файл, который никто не будет поддерживать.

**Ступень 1 — CLAUDE.md/AGENTS.md достаточно.** Проект живёт дольше одной сессии, но правила стабильны и известны заранее (стек, команды сборки, конвенции). Пишете один раз, редактируете руками по мере необходимости. Авто-память ещё избыточна.

**Ступень 2 — появляется потребность в авто-памяти.** Сигналы (по официальному критерию Anthropic «когда добавлять в CLAUDE.md», применимому и к памяти):
- Claude второй раз наступает на те же грабли;
- вы печатаете в чат одну и ту же правку/уточнение, которое печатали в прошлой сессии;
- решение, которое уже было отменено, снова всплывает как будто впервые (откат к уже отменённым решениям — верный признак, что контекст решения нигде не зафиксирован);
- новый участник команды нуждался бы в том же контексте, чтобы быть продуктивным.

Здесь включаете авто-память (по умолчанию уже включена), либо начинаете вести `LESSONS.md`/`DECISIONS.md` как промотированный, курируемый слой поверх сырой авто-памяти.

**Ступень 3 — файлов уже мало, нужна настоящая система.** Признаки: десятки/сотни разрозненных заметок, которые сам файл-индекс уже не удерживает (>200 строк регулярно превышаются); нужен семантический поиск («что мы знаем про X» — а не «покажи файл X»); несколько пользователей/агентов пишут в общую память одновременно и получаются конфликты; нужны временные метки достоверности факта (что было верно до даты Y, а что — после). Тогда — Mem0 / Letta / Graphiti-Zep / Cognee и подобные, с оговоркой из раздела 5: ни один из них не является «магической таблеткой», и живые тесты 2026 года показывают, что на малых объёмах простой файл часто выигрывает.

## 4. Провалы и ограничения (критично — минимум треть материала)

### 4.1 Устаревшая память, которая уверенно врёт

Память не имеет встроенного механизма протухания. Anthropic Memory Tool, например, не имеет built-in expiry — если не чистить файлы вручную, хранилище растёт бесконечно, и старые записи (в т.ч. про удалённые флаги, отменённые решения, старые пути файлов) продолжают подаваться в контекст как актуальный факт. Исследование стабильности агентных конфигурационных файлов фиксирует «context rot» — устаревшие ссылки на код найдены в 23% выборки из 356 репозиториев (arXiv:2605.08435, 2026). Модель не обязана сомневаться в собственной памяти — по дизайну она доверяет ей как «своей прошлой работе».

### 4.2 Отравление памяти (memory poisoning / injection)

Это не гипотетический риск, а задокументированный класс атак:

- **SpAIware** (ChatGPT, macOS-приложение, Johann Rehberger, сентябрь 2024, thehackernews.com/embracethered.com) — через непрямую инъекцию (вредоносный текст на странице/в документе, который агент прочитал) в долговременную память ChatGPT внедрялась инструкция, которая переживала конец разговора и активировалась в будущих сессиях, включая непрерывную эксфильтрацию переписки на сервер атакующего. OpenAI закрыл вектор эксфильтрации в версии 1.2024.247 (сентябрь 2024), но сам принцип — «однажды попавшее в память обслуживается как доверенный контекст бессрочно» — остаётся структурным свойством любой файловой/векторной памяти без встроенной проверки происхождения записи.
- **MINJA** (2025) — показано, что атакующий без специальных привилегий может внедрить вредоносные записи в память агента просто формулируя определённые запросы (никакого прямого доступа к хранилищу не требуется).
- **PoisonedRAG** (2025) — достаточно вставить всего 5 документов в RAG-хранилище, чтобы управлять выводом системы в >90% случаев.
- **MemoryGraft** (2025) — на MetaGPT DataInterpreter с GPT-4o: 10 отравленных «процедурных» шаблонов (замаскированных под безобидные README/сниппеты кода) захватили ~48% всех последующих обращений к памяти, и отравление держалось до ручной чистки.
- **EchoLeak** (CVE-2025-32711, CVSS 9.3) — фильтр-обходящая инъекция в production-системе Microsoft 365 Copilot в рамках одной сессии; показывает, что аналогичный класс уязвимостей достигает крупных коммерческих продуктов, не только исследовательских прототипов.

Anthropic Memory Tool сам по себе несёт структурный риск того же класса (harness-eval issue #40, pre-screen, 2026-07-05): автоматически инжектируемый в системный промпт «MEMORY PROTOCOL» велит модели доверять содержимому `/memories` как своей прошлой работе и перечитывать/действовать по нему каждую сессию — значит, любая запись, попавшая туда однажды (успешная инъекция, отравленный суммаризированный документ, неверно настроенное общее хранилище), обслуживается как доверенный контекст бессрочно — «структурно аналогично stored XSS». Официальная документация Anthropic не даёт рекомендации «относиться к содержимому памяти как к данным, а не как к инструкциям».

### 4.3 Раздувание: память как второй CLAUDE.md, душащий контекст

Anthropic сама явно предупреждает: файлы CLAUDE.md длиннее ~200 строк потребляют больше контекста и *снижают согласованность* следования инструкциям — этот же лимит зашит в лимит чтения `MEMORY.md` не случайно. Если авто-память превращается в непрерывно растущий лог вместо курируемого индекса, `MEMORY.md` начинает конкурировать с CLAUDE.md за одно и то же контекстное пространство, а Claude Code реагирует принудительно: при превышении лимита запись всё равно проходит, но модель получает системную ошибку с требованием переписать индекс компактнее. Это симптом, а не решение — если требование «сожми» повторяется каждую сессию, значит промотирования в `LESSONS.md`/удаления устаревшего не происходит.

### 4.4 Противоречивые записи

CLAUDE.md-документация прямо признаёт: «если два правила противоречат друг другу, Claude может выбрать любое произвольно». То же относится и к памяти — если один тематический файл говорит «используем npm», а другой (более старый) — «используем pnpm», модель не имеет встроенного механизма разрешения конфликта, кроме собственного правдоподобного, но не гарантированно верного суждения. CrewAI Memory (после переписывания на «Cognitive Memory», ~v1.10, март 2026) — один из немногих продуктов, реализующих автоматическое обнаружение и консолидацию противоречащих записей через LLM-анализ («EncodingFlow»); большинство остальных систем в каталоге (Mem0, LangMem, Letta, Graphiti-Zep) этого не делают вовсе.

### 4.5 Приватность и утечки

- Живой тест LlamaIndex Memory (harness-eval #46, 2026-07-06) обнаружил, что использование `claude -p` (CLI-обёртки, а не «голого» API) в качестве бесплатного LLM-заменителя утекло *собственный email оператора* в извлечённые «факты» — данные, которых не было в обрабатываемом тексте вообще. Это риск методологии «шима», но иллюстрирует общий принцип: LLM, извлекающий факты для памяти, может подмешать посторонний контекст, который потом окажется в постоянном хранилище.
- CrewAI: открытый, неисправленный >4 месяцев (на момент фиксации, июль 2026) баг GitHub #5057 — содержимое памяти конкатенируется в системный промпт агента без санитизации (непрямая инъекция, OWASP ASI-01); три отдельных запроса на встроенную защиту от отравления памяти закрыты мейнтейнерами как `not_planned` (#5988, #6021, #5825).
- Cognee: подтверждённая и на момент фиксации всё ещё эксплуатируемая (в реально установленном пакете 1.2.2, несмотря на фикс на GitHub) уязвимость повышения привилегий через незащищённую саморегистрацию — любой зарегистрировавшийся пользователь может перезаписать глобальный LLM-endpoint/API-ключ и тем самым перенаправить чужие данные на свой сервер (`topoteretes/cognee#3084`).
- Anthropic Memory Tool: SDK-хелперы (`BetaLocalFilesystemMemoryTool`) имели три реальных, теперь исправленных CVE (CVE-2026-34450, 34451, 34452, включая TOCTOU + symlink sandbox escape — тот самый класс уязвимости, о котором официальная документация предупреждает *интеграторов*, найденный в собственном референсном коде Anthropic); фикс — версии SDK ≥0.87.0.
- Letta/MemGPT: CVE-2026-4965 (инъекция кода, есть публичные индикаторы эксплуатации) и CVE-2024-39025 (отсутствие авторизации в до-переименования MemGPT).
- Graphiti/Zep: CVE-2026-32247 (Cypher-инъекция через LLM-поставляемые entity_types, CVSS 8.1), исправлена в ≥0.28.2.

**Что нельзя писать в память по итогам всего этого:** секреты/токены (память не имеет шифрования по умолчанию и не проходит контроль доступа отдельно от остального контекста), персональные данные третьих лиц без согласия, любой текст, скопированный дословно из внешнего/непроверенного источника без разметки «это данные, не инструкция».

## 5. Честные результаты бенчмарков — без магии

### Методологические дыры самих бенчмарков

- **LoCoMo** — самый цитируемый бенчмарк долгосрочной памяти — содержит баг в эталонном скорере: функция сверки ответа возвращает `False`, когда эталонный ответ пуст, инвертируя логику так, что система, *корректно отказавшаяся* отвечать, получает тот же счёт, что и система, придумавшая ответ. У 444 из 446 вопросов категории 5 эталон пуст — то есть примерно **23% бенчмарка принципиально нескорируемы** этим механизмом. Отдельно — ошибки разметки золотого эталона (аннотатор считает «прошлую субботу» неверно на конкретную дату) создают «шумовой пол» около **6.4%**, из-за которого небольшие расхождения в очках между системами неинтерпретируемы (dev.to/valesys, 2026).
- **MemoryArena** (arXiv:2602.16313, февраль 2026, авторы из Stanford/UCSD/UIUC/Princeton) — прямо показывает разрыв: агенты, почти насыщающие LoCoMo (recall-фокусированный бенчмарк), плохо справляются в MemoryArena, где память нужно реально *использовать* для управления последовательными многосессионными действиями (веб-навигация, планирование с ограничениями, последовательный формальный вывод), а не просто процитировать факт из транскрипта. Это операционализирует разницу между «вспомнить» и «применить».
- **MemBench** (ACL 2025 Findings, arXiv:2506.21605) различает фактическую и рефлективную память, но точные формулы скоринга не раскрыты в первичных источниках — [НЕ ПОДТВЕРЖДЕНО] как именно считаются итоговые баллы.
- **MemoryAgentBench** (ICLR 2026) — тестирует 4 компетенции (точный поиск, обучение на лету, понимание длинного контекста, разрешение конфликтов); часть парсинга точного совпадения строго и требует ручной адаптации под конкретный формат ответа — иначе занижает реальный результат.

### Живые результаты сравнения с простым файлом (harness-eval, июль 2026, key-free прогоны на persistbench/bfcl_memory/niah, малые корпуса ~170 символов/задача — весь корпус помещается в контекст модели)

| Система | Против простого файла (file-wiki baseline) | Комментарий |
|---|---|---|
| Cognee | **побеждает** (0.833-1.0 против 0.667) | единственная система в серии, устойчиво обыгравшая baseline на нескольких прогонах; но есть открытая уязвимость повышения привилегий |
| LlamaIndex Memory | **точное совпадение** (task-for-task идентично) | но только после ручного обхода двух реальных багов конфигурации по умолчанию |
| Anthropic Memory Tool | результат смешанный: 0.75 vs 0.583 (обгоняет), niah — идеальный 1.0 | главная находка — модель сама решает, что «стоит» запоминать, и это решение непоследовательно между прогонами |
| CrewAI Memory | **проигрывает** на 2 из 3 бенчей (0.667-0.75 vs 0.75-0.917) | зато единственная с автоматической консолидацией противоречий |
| Graphiti/Zep | **проигрывает** на 25-67 пунктов на каждом тесте | документированная API-ловушка: `search()` возвращает только рёбра графа, упуская большинство однофакторных записей |
| Letta | **проигрывает** и простому файлу, и голой модели без памяти вообще | версия теста устарела (0.6.7, ~18 мес. позади текущего релиза), репозиторий официально объявлен legacy |
| LangMem | 0.0 на multi-turn-тесте | схема консолидации по умолчанию возвращает один широкий блок текста без слоя точности ответа |

**Ключевая оговорка (директива оператора harness-eval, 2026-07-06):** все эти сравнения — на корпусе, целиком помещающемся в контекстное окно модели. Это означает, что весь выигрыш «умной» системы памяти относительно простого файла на этих данных структурно не может проявиться — baseline просто читает всё целиком. Поведение на больших корпусах (тысячи фактов, годы накопления) **не протестировано** ни для одной из систем.

**Вывод для семинара:** ни продавайте, ни покупайте память как магию. На небольших/средних объёмах простой файл с дисциплиной записи регулярно конкурентен с инфраструктурно сложными системами, а иногда их обгоняет — сложность добавляет точки отказа (баги конфигурации по умолчанию, уязвимости, недокументированные API-ловушки), которые надо явно найти и обойти, чтобы получить обещанное преимущество.

## 6. Критерии «здесь память не нужна» — чек-лист

- [ ] Задача одноразовая — вторая сессия по этому же контексту не планируется.
- [ ] Весь нужный контекст помещается в одно контекстное окно без потерь.
- [ ] Правила проекта стабильны и укладываются в один CLAUDE.md < 200 строк — CLAUDE.md один справляется.
- [ ] Никто не повторяет вручную одну и ту же правку/уточнение из сессии в сессию.
- [ ] Нет нескольких участников/агентов, которым нужно делиться контекстом асинхронно.
- [ ] Факты, которые могло бы хранить хранилище, и так выводимы из кода, git-истории или существующей документации.
- [ ] Проект короткоживущий (спринт, эксперимент, одноразовый скрипт) — заводить инфраструктуру памяти дороже, чем просто ещё раз объяснить контекст.

Если хотя бы 2-3 пункта не выполняются — переходите на Ступень 2 (авто-память/CLAUDE.md); если систематически не выполняются почти все и файлов уже десятки — Ступень 3 (настоящая система).

## 7. Фишки для продвинутых

- **Одна запись = один факт.** Не смешивайте в одном файле памяти «предпочтение пользователя» и «статус текущей задачи» — тематические файлы Claude Code (`user_role.md`, `feedback_testing.md`) именно поэтому разделены по типу (`user`/`feedback`/`project`/`reference`), а не по хронологии.
- **`MEMORY.md` — только индекс.** Одна строка на запись со ссылкой на тематический файл, не полный текст. Это не стилистическое предпочтение — это жёсткий лимит (200 строк/25 КБ), за которым контент физически не загружается в сессию.
- **Связи через `[[wiki-ссылки]]`.** Karpathy LLM Wiki-паттерн и практика этого проекта (см. `MEMORY.md` в собственном `.claude/`) используют `[[имя-темы]]` для перекрёстных ссылок между записями — это даёт графовую навигацию поверх плоских markdown-файлов без отдельной базы данных.
- **Срок годности и ревизия.** У каждой записи должна быть дата последней проверки (frontmatter `modified` в Claude Code выставляется автоматически) и периодическая ревизия — «lint-проход», ищущий противоречия, пробелы и устаревшие утверждения (тот же принцип, что в Karpathy-паттерне: «ingest → query → периодический lint»).
- **Не пишите в память то, что уже есть в коде/git.** Официальная документация Anthropic формулирует это явно: Claude «пропускает всё, что можно вывести из кодовой базы — архитектуру, пути файлов, найденные при отладке фиксы» — если агент всё же это записывает, это сигнал раздувания, а не полезности.
- **Разделение ролей: память vs DECISIONS.md vs knowledge/notes.md.**
  - **Авто-память** — быстрый, непрерывный, машинно-локальный слой: то, что агент подметил в процессе, не синхронизируется между машинами, не проходит код-ревью.
  - **`DECISIONS.md`** — append-only журнал **почему**, не что (это уже есть в git-логе), одна запись на решение, которое иначе жило бы только в чьей-то голове или закрытом разговоре. Командный, версионируемый.
  - **`knowledge/notes.md`** (или `LESSONS.md`) — намеренно **промотированный** подмножество памяти: не всё, что агент когда-либо заметил, а то, что подтвердилось дважды или предотвратило бы реальный инцидент. Без регулярного цикла промоции («review auto-memory during each retro; promote anything confirmed twice») этот файл рискует либо замереть после старта, либо превратиться во второй CLAUDE.md, который на самом деле подменяет собой работу авто-памяти.
- **Каждое бинарное правило нуждается в механической проверке.** Правило «не хранить секреты в памяти» без грепа по коммитам/файлам памяти на паттерны токенов — это пожелание, а не гарантия.
