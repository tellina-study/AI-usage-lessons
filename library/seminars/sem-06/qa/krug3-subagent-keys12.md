# Круг 3: новые кейсы 1 и 2 блока субагента — отчёт

## Что построено

Блок субагента состоял из трёх кейсов: специализация (n35–n46, не моя зона), «роль вернула итог,
действий родитель не видел» (n47–n56) и «вторая роль добавляется, границы начинают путаться»
(n57–n64). Второй и третий кейсы перестроены в два новых: **«чтобы ответить на один вопрос, надо
прочитать сорок файлов»** (n47–n54, 8 слайдов) — польза: фокус на нужной части контекста и
незамусоривание контекста родителя — и **«задач несколько, и они независимы»** (n55–n64, 10
слайдов) — польза: параллелизм как причина, с ценой координации как встроенной границей, а не
отдельным кейсом.

## Кейс 1 — фокус и незамусоривание контекста

**Сцена.** Технический директор спрашивает в чате да/нет-вопрос про лимит участников на бесплатном
тарифе. Ответ разбросан по четырём точкам (middleware, конфиг тарифов, миграция для старых
аккаунтов, клиентский дубль проверки) и пятнадцати миграциям, из которых лимит менялся в трёх —
честный ответ требует открыть больше сорока файлов. Правка, ради которой открыли сессию, делит
контекст с этим чтением.

**Почему узнаваемая.** Класс сцены — дословно тот, что назвал владелец: «понять, где в проекте
живёт некоторое поведение, и для этого прочитать десятки файлов». Деталь (тарифный лимит,
разбросанный годами накопленных правок) — не придумана под мораль: это обычная форма технического
долга в любом продукте с тарифными планами, и выбрана отдельно от демо-репозитория занятия
(`signup-landing-demo` слишком мал для честной сцены на сорок файлов — решение владельца
«репу забей» из `SPLIT-PLAN-6-7.md` сохраняется, сцена не требует коммита в демо-репозиторий).

**Разбор (форма А5).** Пять вариантов: прочитать самому / позвать коллегу / субагент в своём окне
/ сохранить как скилл / ответить по памяти. Целевая карточка (субагент) явно НЕ подаётся как «он
читает быстрее» — наоборот, разбор прямо говорит: время чтения то же самое, субагент открывает те
же сорок файлов. Экономится не время, а место в контексте: окно роли с их содержимым закрывается
вместе с ней.

**Опора по механике.** Контрактный факт прежнего кейса («роль возвращает родителю только итог,
промежуточных действий не видно») не исчез — он переехал сюда (`n51`) как объяснение ПОЧЕМУ фокус
работает: что входит в окно роли на старте (системный промпт роли, задача, иерархия инструкций,
снимок репозитория) и чего физически нет (история переписки, уже прочитанные файлы, автопамять).
Источник — `research/mechanics-6-subagent.md` §2.1–2.2, дословные цитаты.

**Граница — новый материал, не использовался раньше.** Окно роли не чистое от всего: по умолчанию
роль наследует описания ВСЕХ MCP-серверов родительской сессии, даже ненужных её задаче. Дословная
цитата из документации харнесса (§2.5 того же файла): «Subagents inherit every MCP tool definition
from the parent session, which can fill their context window before the first turn.» Это связывает
блок MCP и блок субагента этого же занятия — честная оговорка, не décor.

## Кейс 2 — параллелизм и цена координации

**Что переехало.** Прежний кейс 3 («вторая роль добавляется, границы начинают путаться» —
диф-ревьюер + тестировщик, промежуток между их зонами, email с пробелом перед доменом) переехал
ЦЕЛИКОМ: сцена, разбор пяти вариантов, свидетельства MAST + Google Research, механика единственного
рабочего приёма (явная граница в обе стороны), отраслевой разворот Cognition, критерий — те же
формулировки, те же числа, тот же источник, другое место в раскадровке (граница нового кейса, не
отдельный кейс).

**Что перевёрнуто.** Сцена с тремя параллельными запусками одной роли на три независимые правки
(которая раньше была ТОЛЬКО обстоятельством провального кейса — «три параллельных запуска вернули
одинаково надёжные PASS») теперь открывает кейс как причина выгоды: было — три проверки по очереди
(запуск, ждать, запуск, ждать, запуск); стало — одним действием, три отдельных вызова, свой
контекст у каждой, итоги приходят примерно тогда же, когда пришёл бы один.

**Разбор (форма А5).** Главная находка: карточка «проверить зависимость» — не альтернатива карточке
«параллельный вызов на каждую независимую задачу», а обязательный шаг перед ней. Без проверки
условия независимости параллелизм с равной вероятностью либо экономит время, либо создаёт
рассогласование — это прямой мост к границе кейса.

**Механика — новый материал, не использовался раньше.** Параллельный запуск — честная механика
харнесса (fork mode по умолчанию с версии 2.1.232, роль уходит в фон), не просто удобство. Предел —
на одновременность (двадцать ролей разом по умолчанию), не на общее число за сессию. Источник —
`research/mechanics-6-subagent.md` §1.5.

## Числа и источники

Ничего не менялось по содержанию, только по месту: issue `#67730`/`#76726` (связанные с аркой
достоверности) **сняты вместе с аркой** — это решение, не недосмотр, см. ниже. MAST
(Cemri и др., arXiv:2503.13657), Google Research (Kim, Gu, Park и др., arXiv:2512.08296),
Cognition (12.06.2025 → 22.04.2026) перенесены дословно. Дидактический пример «6100→420 токенов»
(`context-window.md`) — новый для деки, взят из `research/mechanics-6-subagent.md` §2.2, честно
подан как иллюстрация документации, не измерение. Механика параллельного исполнения (fork mode,
предел 20) — новый для деки материал из §1.5 того же файла.

## Что снято и почему — арка достоверности, не только тег

Прежний кейс «роль вернула итог» пережил круг 2 (переписан под «что пересекает границу
делегирования», слова «обманул»/«солгал» сняты), но по существу остался кейсом о том, можно ли
доверять отчёту роли: журнал вызовов как способ проверить, не соврал ли вердикт `PASS`, модельный
разбор вердикта, провал про хук `deny`, который не долетел до родителя, критерий «когда формата
достаточно, когда нужен человек». Это **та же арка**, которую владелец запретил по всему занятию
(«агенты к достоверности никакого отношения не имеют вообще»), просто под новой рамкой. Круг 3
снимает её целиком, а не редактирует. Контрактный факт («только итог, без действий») — единственное,
что из неё уцелело, как опора нового кейса 1.

## Структурная находка — вопрос владельцу

Доля strict-in (провалы/границы/альтернативы) для нового материала (`n47`–`n64`) — **5,5 минуты
из 20,75**, для блока целиком (вместе со специализацией, не моей зоной) — **8,75 из 35,0 ≈ 25%**.
Это ниже порога ≥30%, который держался на всех прошлых кругах (было 35,5%). Причина прямая и
честная: прежняя арка достоверности несла почти всю strict-in-массу кейсов 2 и 3 (журнал вызовов,
провал про хук `deny`, два документированных инцидента `#67730`/`#76726`, граница «чего не
закрывают ни формат, ни журнал» — пять слайдов из десяти бывшего кейса 2). Её снятие по прямому
требованию владельца убирает эту массу; новая грамматика («покажи пользу, не только границы»)
структурно несёт меньше провалов на кейс — по одной границе и одному критерию, не каталог
инцидентов. Расчёт — `rework/section-2-subagent-part1d.md` §A.5.

**Вопрос:** это приемлемый компромисс ради главного требования круга 3, или в один из двух кейсов
нужно вернуть третий провал/границу специально ради доли — зная, что добавление границы без
содержательного повода противоречило бы тому же кругу («без выдуманных абстракций», «инженерно и
конкретно»)? Я не стал добавлять границу искусственно и выношу это решение наверх.

**Второй вопрос:** сквозная нумерация и порядок трёх кейсов (специализация / фокус / параллелизм)
в финальной деке — за сведением. Сейчас файлы этой зоны (`n47`–`n64`) рассчитаны как «кейс фокуса
идёт вторым, кейс параллелизма — третьим» (после специализации), но явного решения владельца о
порядке трёх кейсов в этом круге не было — стоит подтвердить при сшивке.
