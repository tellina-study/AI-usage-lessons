# Task class

## Assertion

Response format and reading correctness are different properties. Format is checked cheaply; correctness is only checked by a second, independent source of the same number.

## Visual

> **A formally correct answer says nothing about whether a number was read correctly off a photo.** A syntactically correct date, a number of the right shape, JSON with not a single structural error — all of this is checked with one quick glance at the shape and says nothing about the content. A document can be read entirely wrong while staying flawlessly well-formed.

> **It isn't the image in general that breaks — what breaks is whatever is set smaller on it.** The expectation "compression ruins the picture" is too blunt: the same file, the same compression gives different outcomes for different fields, because the fields have a different character height at the start. And the only counterweight proven in practice is cross-checking what's read against an independent second value of the same fact. A bigger file doesn't help here, and neither does reading the same photo again.

> **Task class.** Wherever a decision made from a photo moves forward with no second reading by a human, a second, independent source of the same number is needed, with an explicit comparison against it. Trusting a single reading isn't enough for that, and checking its formal neatness doesn't close that gap.

> **What follows for assembling a process.** Reading a document isn't a one-time act you can check off as "read." It's one of two values that still have to be compared against each other before anything gets decided on their basis.

## Speaker notes

Let's gather the case into wordings that can be carried over and applied to your own process — without mentioning a single node's name.

First. A formally correct answer says nothing about whether a number was read correctly off a photo. A syntactically correct date, a number of the right shape, a flawless response structure — all of this is checked instantly and says nothing about the document's content. A document can be read entirely wrong and still produce an answer that's perfectly correct in form.

Second, and it needs careful wording, because the first natural assumption here is wrong. It isn't the image "in general, if you compress it too much" that breaks — a specific field breaks, the one set smaller than the rest on the same frame. The same file, under the same compression, gives different outcomes for different fields precisely because they have a different character height from the very start. And the only method that actually caught the error in practice is cross-checking the read value against an independent second source of the same fact. Neither a bigger file nor a more careful model fixes this on its own.

From here follows the whole task class. Wherever a decision made from reading a photo moves forward with no second reading by a human, an independent second source of the same number is needed — and an explicit comparison against it. Not trust in a single reading. Not a check of its formal neatness, which, as we've seen, catches nothing where it's needed.

And the practical conclusion for assembling any similar process. A model reading a document isn't a one-time act after which you can check off "done, read." It's one of two values of the same fact that still have to be set against each other before making a decision on their basis that moves forward with no second check.
