# Phase B — Критический разбор внешних рекомендаций

**Issue:** #52
**Дата:** 2026-05-12
**Источник:** рекомендация про PPTX-native + Figma kit + Slidev twin pipeline.

---

## 1. Что в рекомендации сильно (берём)

### 1.1. Assertion–Evidence как методическая основа
**Сильно.** Подкреплено эмпирически (Garner/Alley на 110 инженерных студентах: лучше понимание, ниже когнитивная нагрузка, лучше отложенное воспоминание). Это **не «дизайн», а педагогика**. Соответствует McGill/UCSD рекомендациям (одна идея на слайд, не больше 4 буллетов, визуал не декоративный).

→ **Берём как обязательный паттерн** для содержательных слайдов.

### 1.2. Структурированная учебная модель слайда вместо markdown
**Сильно.** Поля `assertion`, `learning_goal`, `visual.pattern`, `notes`, `student_action` — это правильный уровень абстракции. Subagent тогда видит «зачем этот слайд», а не просто «вот тебе текст».

→ **Берём.** Это и есть наш `deck.yaml` schema.

### 1.3. Библиотека типов слайдов (slide-types library)
**Сильно.** `cover / section_divider / assertion_visual / process_N / hierarchy / dependency / comparison / case_study / example_bad_good / exercise / reflection / summary / sources` — практичный набор, покрывает 90% учебных слайдов. Чек именно набор типов снимает «всё всегда Title+Body» проблему.

→ **Берём, но в адаптированном минимальном виде** (см. Phase C).

### 1.4. QA-слой как отдельная фаза
**Сильно.** instructional QA / visual QA / accessibility QA. Без QA любой генератор скатывается в «формально работает, по сути плохо».

→ **Берём в виде агентов critic / student / reader** (явно требуемых пользователем) + автоматических чеков.

### 1.5. Visual regression export через PNG
**Полезно.** Экспорт каждого слайда как PNG и проверка переполнений/мелкого текста. С Google Slides это делается через `export` API.

→ **Берём как опцию**, не блокирующую.

### 1.6. «Сначала один эталонный deck вручную, потом автоматизация»
**Сильно.** Это и есть наш сценарий: первые 5 слайдов Л1 — отладочный полигон.

→ **Точно берём**, это методический принцип.

### 1.7. Progressive disclosure через серию почти одинаковых слайдов
**Сильно и переносимо.** Даже если позже хотим анимации — серия слайдов работает в любой среде (Google Slides, PPTX, PDF, Slidev).

→ **Берём.** В нашем плане Л1 v4 уже есть слайды 3+4 как 2-шаговый reveal — это и есть progressive disclosure.

## 2. Что в рекомендации слабо для нас (НЕ берём или берём частично)

### 2.1. Полный PPTX-native пайплайн (PptxGenJS + pptx-automizer)
**Overkill для соло-мейнтейнера.**

| Аргумент рекомендации | Реальность нашего проекта |
|---|---|
| «PPTX — стандарт для офлайн-правки» | Мы используем Google Slides как primary delivery (CLAUDE.md: workspace-mcp — единственный Google integration). |
| «Преподавателю удобнее редактировать PPTX» | Преподаватель — это сам пользователь. Он работает в Claude Code + Google. |
| «PptxGenJS + pptx-automizer = красиво и редактируемо» | Даёт +TS-toolchain (Node.js), +поддержка XML-шаблонов, +новый CI. Для одного курса 17 лекций — не окупается. |

→ **НЕ берём.** Render-таргет остаётся **Google Slides** через `workspace-mcp`. PPTX-export — только если когда-то понадобится для офлайна (через `mcp__workspace-mcp__export_doc_to_pdf` или аналог; либо `download` из Google).

### 2.2. Figma как design lab
**Слишком тяжело и не нужно.**

- Требует Figma-подписку, постоянный design effort, отдельную дизайн-систему.
- Figma MCP сам по словам рекомендации beta: 20 KB write limit, нет assets, нет custom fonts.
- Для наших целей (структурные учебные слайды) достаточно **готового master template в Google Slides** с 8–10 layout'ами.

→ **НЕ берём Figma как обязательный слой.** Заменяем на **один master Google Slides template** с layout'ами под наши slide-types.

### 2.3. Slidev как «web twin»
**Удваивает поверхность сопровождения.**

- Каждый слайд должен работать в двух средах с разной семантикой.
- Slidev PPTX-export кладёт слайды как картинки → нет редактируемого текста → не помощник.
- Web-публикация курса у нас уже есть (wiki + GitHub Pages потенциально). Слайды на сайте — отдельная история, не блокер.

→ **НЕ берём сейчас.** Опционально — позже, если появится запрос на интерактивные онлайн-материалы.

### 2.4. Mermaid как основной генератор схем
**Согласен с критикой.** Mermaid хорош для черновиков, плох как финальный учебный визуал. У нас есть `drawio` MCP — он лучше для постоянных схем.

→ Уже **не основной**. Используем `drawio` для постоянных схем (как сейчас).

### 2.5. Codex / OpenAI MCP
**Не релевантно.** Мы Claude Code only.

→ Игнорируем.

### 2.6. Полный набор `.skills/` (instructional-designer / visual-director / pptx-builder / web-publisher / qa-reviewer)
**Слишком большой набор сразу.** 5 новых skills + переменная инфраструктура — это новая система, а не итерация существующей.

→ **Берём принцип «несколько фаз, каждая со своим агентом», но реализуем постепенно** (см. Phase C: 2 новых skill'а, 3 новых агента, остальное — позже по реальной необходимости).

## 3. Чего в рекомендации нет, а нам критически нужно

### 3.1. Repo-first как архитектурный принцип
**Пользователь явно потребовал** (5/12 уточнение):
> Полный текст презентации и рабочие материалы должны жить в репе, а в Drive — только публикация для передачи или сбора обратной связи.

Это **более жёсткое** требование, чем в рекомендации (там Google Drive вообще не упоминается). Делает архитектуру чище:

- **Source of truth** = `library/lectures/lec-NN/`
  - `deck.yaml` (структура, типы, assertions, learning goals)
  - `slides/` (содержание слайдов в md, по одному файлу на слайд для diff'абельности)
  - `notes/` (speaker notes)
  - `assets/` (картинки, диаграммы, ссылки)
- **Google Drive** = render + publish target (read-only с точки зрения repo'a)
  - Сгенерирован из `deck.yaml`
  - Используется для живой презентации и сбора комментариев
- **Comments → Issues** — отдельный поток: feedback из Google Slides пуллится назад в репо как GitHub-issues или markdown-файлы (не как edits в Drive).

Это снимает три проблемы разом:
1. Diff'абельность правок (git track всё, Drive — нет).
2. Воспроизводимость (любой re-render даёт идентичный результат).
3. Не нужно бояться повредить Google Slides — её можно пересобрать.

### 3.2. Critic / Student / Reader агенты как обязательные чек-пункты
**Пользователь явно потребовал.** Рекомендация говорит про QA-reviewer, но смешивает в нём всё (instructional + visual + accessibility). Лучше разделить по перспективам:

- **`presentation-critic`** — **что не так с дизайном/педагогикой?** Проверяет assertion-evidence, одну мысль на слайд, баланс визуал/текст, нет ли декоративного, проверка времени, переполнения.
- **`student-simulator`** — **студент ИУ6, прошёл ML, ежедневно использует AI**. Что я понял? Что меня сбило с толку? Какой вопрос остался? Скучно ли? Какой жаргон не пояснён?
- **`reader-simulator`** — **слайд без preпreподавателя**. Через 2 недели открываю слайды на повторение. Понимаю ли я слайд из самого слайда + speaker notes, без воспоминаний о лекции?

Это **три разных персонажа с разными чек-листами**. Нельзя слить в одного.

### 3.3. Два-шаговая методика контента: «контент → структура»
В рекомендации этого нет, но без этого получается «генерация сразу в финальный вид». А нам надо:

1. **Контент-проходка** (subagent с экспертной ролью) — берёт narrative-план (v4) и для каждого слайда формулирует assertion + наполнение.
2. **Структурная проходка** — выбирает slide_type, проверяет ритм, баланс, время.

→ Это будет два subagent-вызова в pipeline, не один.

### 3.4. Обработка фидбэка обратной петлёй
В рекомендации фидбэк не упомянут. В нашем repo-first сценарии это **отдельный skill**: «прочитать комментарии в Google Slides → создать GitHub issues с привязкой к slide_id». Иначе фидбэк теряется при пересборке.

### 3.5. Anti-patterns каталог для русскоязычных учебных слайдов
Рекомендация западоориентирована. Нам нужно зафиксировать локальные anti-patterns:
- «Список из 12 буллетов мелким шрифтом» — РФ-академический норматив.
- «Заголовок = тема» вместо тезиса.
- «Картинка-стоковое-фото для красоты».
- Слайд с одной таблицей на 8 колонок.

→ Включить в `notes/decisions.md` после Phase F.
