# Visible content

## Title bar
«Провалы агентов»

## Body
[3 карточки-провала в Ocean rounded box]

**1. Петля без лимитов**
Агент на «синхронизируй заказы» получил HTTP 429 → план→вызов→429→перепланирую→… → **$4,200 за 63 часа**  *(gold-акцент)*
*Почему:* агент не «видит» ни накопленной стоимости, ни времени, ни повторяемости
*Правильно:* задача предсказуема → retry-with-backoff скрипт, не агент; budget/loop-лимиты ВНЕ агента

**2. Reliability compounding**
5 шагов по 99% → 0.99⁵ ≈ **95%**; 10 → ≈ **90%**; 20 → ≈ **82%** — надёжности перемножаются
*Вывод:* «улучшить шаг» — слабый рычаг; «меньше хопов + валидация между шагами» — сильный

**3. Мульти-агентная хрупкость**
зависимые подзадачи → параллельные субагенты принимают конфликтующие неявные решения
*Правильно:* single-threaded линейный агент; мульти-агент — только широко-параллельное независимое

## Speaker notes

Цикл агента имеет четыре места отказа; три класса провалов ниже — эти режимы в датированных кейсах, каждый с уроком и альтернативой. Первый. Команда поставила автономного агента на «синхронизировать заказы в CRM» — задача предсказуемая. Внешний API упёрся в ограничение частоты и стал возвращать ошибку 429[1]. Агент, не имея в плане ветки на 429, действовал по своей природе: планирую, вызываю, 429, перепланирую, снова — тысячи раз в час; итог около $4,200 за шестьдесят три часа (постмортем Sattyam Jain, 2026-04; single-author, числа округлены, иллюстративный). Агент конструктивно не понимает ни накопленной стоимости, ни времени, ни того, что действия идентичны. Урок: без жёстких внешних лимитов «пробуй, пока не получится» исполняется буквально и до разорения.

Важно назвать базу сравнения. Обычный детерминированный скрипт повтора с нарастающей задержкой решает ту же задачу кратно дешевле: получил 429, подождал секунду, две, четыре, восемь, повторил ограниченное число раз — и либо готово, либо быстро сообщил «не смог, нужно вмешательство». Несколько строк кода, секунды-минуты, стоит почти ничего. То есть $4,200 — не цена автоматизации синхронизации вообще, а цена неправильного выбора архитектуры под предсказуемую задачу. Альтернатива двойная: budget gates вне агента и, на уровне архитектуры, скрипт повтора, а не агент.

Второй. В цепочке, где сбой любого компонента портит результат, надёжности перемножа[2]ются: пять шагов по 99% дают примерно 95%, десять — около 90%, двадцать — около 82%. Рассуждение «каждый шаг почти всегда работает, значит и цепочка» математически ложно. Следствие: доработка отдельного агента почти не двигает системную надёжность, а сокращение числа шагов вдвое даёт сопоставимый эффект дешевле. Урок: «докрутить модель» — слабый рычаг, «меньше хопов плюс валидация между шагами» — сильный. Третий. Когда подзадачи зависимы, параллельные субагенты принимают конфликтующие неявные решения и дают несовместимый результат. Урок: мульти-агент[3] по умолчанию — не выигрыш; для задач с зависимостями он хуже одного линейного агента. Во всех трёх «более сложная архитектура» означала «менее надёжная», а не «более продвинутая».
