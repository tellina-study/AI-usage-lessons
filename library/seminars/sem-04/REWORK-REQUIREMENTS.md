## R3 — Сквозность примера и заземление решений (ГЛАВНОЕ требование к структуре)

**Было:** ступени лестницы ощущаются как отдельные разрозненные задачи, много теории про системный дизайн вообще, решения не привязаны к конкретному коду в `signup-landing`.

**Требование — обязательная форма для КАЖДОЙ ступени (1–7), без исключений:**
1. **Проблема** — конкретная, воспроизводимая на `signup-landing` (не абстрактная).
2. **Конкретное решение** — что именно добавляется (файл, блок конфигурации).
3. **Описание решения** — как оно работает механически.
4. **Место в харнесе** — куда именно в структуре агента это встаёт (см. R4 — терминология лекции 3).

Формулировка должна быть понятна **разработчику-новичку**: не «архитектурная теория», а «вот боль → вот файл → вот что в нём → вот почему агент теперь её не повторяет». Меньше абстрактных врезок про «design» вообще, больше — что реально лежит в репозитории `signup-landing` после каждой ступени (дерево файлов уже используется на s01/s08/s54/s56 старой версии — сохранить эту идею, но усилить конкретику внутри каждой ступени, не только на итоговых слайдах).

## R4 — Сверка с методологией лекций, привязка терминологии к Лекции 3

### R4a. Начало занятия: сбор требований и архитектуры — интерактивно

**Было:** сайт `signup-landing` просто появляется готовым тезисом («вот кейс») — занятие сразу входит в «агент собрал лендинг» без обсуждения, какие вообще требования и архитектура у этой задачи.

**Требование:** добавить в открытие занятия (Раздел 0, до первой задачи агенту) короткий **интерактивный слайд сбора требований** — фасилитатор спрашивает у аудитории вслух (открытый вопрос, устно, без письменной работы — по правилу курса «без письменных работ», см. `feedback_no_written_work_in_seminars`): что должно быть у лендинга с формой заявки (поля формы, сборка, тест, деплой) и почему структура репозитория именно такая. Это готовит почву для тезиса «мы не начинаем с конфигурации агента — начинаем с требований задачи», прежде чем показывать пустой репозиторий.

### R4b. Терминология — использовать словарь Лекции 3, не изобретать заново

Я прочитал `library/lectures/lec-03/chapter-part3.md` §4.4 и `chapter-part5.md` §5.2b. Лекция 3 уже вводит **ровно ту же идею**, что несёт весь семинар 4, под собственными терминами:

- **«Harness» / «экипировка агента»** (§4.4) — зонтичный термин: совокупность памяти, инструкций-правил, skills, subagents и MCP-доступа поверх базового цикла plan→act→check.
- **Пять «слотов экипировки»**, в порядке §4.4–4.8: 1) **Память** (§4.5), 2) **Инструкции-правила / операционный слой** (§4.7 — CLAUDE.md/AGENTS.md + журнал задач), 3) **Skills** (§4.8), 4) **Subagents** (§4.8), 5) **Access/MCP** (§4.8).
- **«Тонкий агент» / стартовый комплект** (§5.2b) — дефолт: один файл-инструкция + плоская память, без subagents/skills/MCP, **пока нет конкретного проверяемого триггера**. Это ДОСЛОВНО правило лестницы семинара 4 («не добавляй раньше триггера»), уже сформулированное в лекции.
- **«Бремя доказательства»** (несущая фраза лекции 3, §1.1/§5.1/§4.4) — используй эту формулировку наравне с (или вместо) «триггера» там, где это усиливает связь с лекцией.
- **Presence-paradox исследование** (§4.7, Gloaguen et al.) уже разобрано в лекции: файл-инструкция сам по себе не даёт статистически значимого прироста, кроме случая, когда заполняет реальный информационный пробел. Семинар 4 должен явно ссылаться на этот результат лекции при разборе ступени 1 (файл инструкций), а не пересказывать своими словами.

**Требование:** переработанный план должен явно(!) на первом же keystone-слайде (или в открытии раздела 0) сказать: «сегодня мы берём пять слотов экипировки агента из Лекции 3 (§4.4) и добавляем два практических слоя поверх них — хук и процесс — по тому же правилу лестницы (бремя доказательства)». Не переизобретать терминологию заново под семинар — использовать слова «Harness/экипировка», «слот», «тонкий агент», «бремя доказательства» напрямую.

**Порядок ступеней семинара vs порядок лекции — явное расхождение, зафиксировать сознательно:** лекция даёт порядок Память → Инструкции-правила → Skills → Subagents → MCP; семинар 4 использует Инструкции → Память → Хук → Скилл → MCP → Субагент → Процесс. Расхождение оправдано нарративной логикой сквозного кейса (порядок триггеров на реальном проекте), но план должен **явно проговорить**, что порядок семинара — не противоречие лекции, а другая последовательность применения тех же пяти слотов плюс два новых.

**Хук и процесс — не слоты лекции, объясни почему они добавлены:** у лекции 3 нет отдельного слота «хук» — упомянут вскользь только в связке Claude Agent SDK. План должен явно связать хук с presence-paradox (§4.7): раз инструкция-файл сама по себе не работает надёжно (лекция это уже показала числами), хук — это МЕХАНИЧЕСКОЕ, а не текстовое усиление ровно той же операционной прослойки. А «процесс» (план-режим, независимая прожарка, журнал) — операционализация роли «человек-валидатор» и шага `check` из цикла plan→act→check→iterate (§4.2, §5.2b), тоже уже введённых лекцией. Это делает семинар **прямым продолжением** лекции, а не параллельным курсом понятий.

## R10 (детализация R10 см. выше) / R11 — Реализм сценария на s11 (повторный вопрос агента)

Я прочитал `slides/s11-pain-and-question.md` и `assets/captures/TODO-capture.md` целиком.

**Проблема, которую нашёл владелец, реальна:** сценарий утверждает, что агент во второй сессии переспрашивает **«какой командой собрать сайт»** — но для типового Vite-проекта команда сборки (`npm run build`) обычно и так читается агентом из `package.json` → `scripts`, без необходимости спрашивать. Это слабое, неубедительное место — заявленный триггер недостаточно обоснован.

**Что в сценарии РЕАЛЬНО не выводится из кода** (и на это стоит сузить формулировку): команда **прогона Playwright-теста** — если в `package.json` нет отдельного npm-скрипта под тест (обычный Vite-скаффолд его не создаёт по умолчанию), агенту действительно неоткуда взять эту команду однозначно (`npx playwright test` — не единственный вариант: есть режимы headed/headless, конкретный конфиг, CI-флаги). Также кандидаты на «не выводится из кода»: куда деплоить, какой хостинг, какой критерий «форма прошла тест» на проде.

**Требование:** переформулировать сценарий так, чтобы триггер был про то, что **действительно** не выводится из кода — не «как собрать» (это инфраструктурно тривиально для Vite и должно быть обосновано явно, если всё-таки используется — например «мы не создавали никаких вспомогательных скриптов/тулов сверх стандартного Vite-скаффолда»), а про верификацию/деплой/конкретную команду теста без явного npm-скрипта. Если решаете оставить «команда сборки» как часть примера — добавить явное обоснование в спикерских заметках, почему именно в этом конкретном репозитории это не тривиально (например, кастомный build-скрипт, не просто `vite build`).

**Про плейсхолдер «ждёт реальной сессии Claude Code»:** его цель была неясна на самом слайде (посадка в контекст видимого тела слайда) — см. также §«Замечание сессии-оркестратора» ниже про то, что оркестратор теперь МОЖЕТ реально захватить часть этого материала через `spawn_child_session`, а не оставлять как честную заглушку. См. отдельный раздел ниже.

## R11 — Claude Code уже поддерживает встроенное делегирование субагентам

Я проверил это на собственном опыте текущей сессии (список доступных типов агентов, видимый в системном контексте этой самой сессии): **в актуальном Claude Code уже есть встроенное, готовое из коробки делегирование субагенту (через `Agent`/`Task`-инструмент) — БЕЗ необходимости писать свой `.claude/agents/*.md` файл.** Есть дефолтный `general-purpose` субагент и ряд встроенных типов (`Explore`, `Plan` и т.п.), доступных сразу, без всякой настройки.

**Что это меняет в разделе про субагенты (ступень 6):** нынешняя формулировка неявно подразумевает, что «субагент» — это то, что нужно завести/настроить с нуля (через `.claude/agents/*.md`). Это устарело как формулировка триггера. **Реальный триггер ступени 6** — не «первый раз нужно делегировать подзадачу» (это уже бесплатно доступно из коробки), а **первый раз, когда нужен КАСТОМНЫЙ, ограниченный по правам и переиспользуемый по имени субагент** — то есть конкретно: (а) сужение набора инструментов (например, `tools: Read, Grep, Glob` без `Write`/`Edit`, как в `diff-reviewer.md`), и/или (б) фиксированное, находимое по `description` имя, чтобы Claude мог автоматически маршрутизировать задачу на него между сессиями, а не разово в моменте.

**Требование:** переформулировать assertion и speaker notes раздела про субагенты — явно провести эту границу («делегировать вообще — уже бесплатно; кастомный ограниченный ревьюер по имени — вот что стоит заводить и вот когда»). Материал про `diff-reviewer.md` (`tools:`-ограничение, `description`-маршрутизация) остаётся полностью актуальным как ИЛЛЮСТРАЦИЯ именно кастомного случая — просто assertion слайда-дивайдера и критерия «ещё рано» должны отражать эту более точную границу, а не общее «раньше не было субагентов, теперь завели».

## Замечание сессии-оркестратора — коррекция моей собственной прошлой ошибки

Прошлая сессия (и я, до того как владелец поправил) считала, что позиции TODO-capture.md, требующие «живой интерактивной сессии Claude Code», недостижимы для оркестратора. Это было неверно: у оркестратора есть `spawn_child_session` — реальный инструмент создания настоящих Claude Code сессий. Часть материалов из `TODO-capture.md` (диалог первой задачи, повторный вопрос, `/memory`, вердикт `diff-reviewer`) уже начала захватываться реальными спаунутыми сессиями параллельно с этой перепиской (см. отдельные фоновые задачи оркестратора). Рабочая сессия по переделке (ниже) должна **использовать уже захваченные реальные материалы**, когда они будут готовы, вместо плейсхолдеров «ждёт реальной сессии» — но не блокироваться на этом: если материал ещё не захвачен к моменту написания главы раздела, оставлять честную пометку в тексте главы (не на итоговом слайде) с точным указанием, что именно нужно подставить.

## Итоговый процесс переделки (по указанию владельца)

1. Оркестратор (я) обобщил замечания в это требование.
2. Запускается ОТДЕЛЬНАЯ сессия переделки — по каждому из 8 разделов занятия (Раздел 0 «сбор требований и открытие» + 7 ступеней лестницы) делает: (а) детальный план раздела с учётом всех требований R1–R11 выше, (б) детальную «главу» — полный методический и фактурный текст раздела (сценарий-боль на `signup-landing`, дословный открытый вопрос с вариантами, разбор ответов, конкретное решение с местом в харнесе, критерий «ещё рано», провал/ограничение с реальным источником), включая явную сверку терминологии с Лекцией 3 (R4b).
3. Оркестратор получает 8 разделов-глав, сводит их в единый план (проверяет сквозность кейса, тайминг — 90 минут по-прежнему, бюджет провалов ≥30% холистично), **прожаривает** результат на предмет идеальной арки общения на семинаре (открытие → нарастание → кульминация → закрытие, единый голос, нет швов между разделами).
4. После прожарки и правок — сборка слайдов (новый деск.yaml + slides/*.md с нуля, рендер по обычному пайплайну presentation-designer + 3 QA-агента).
