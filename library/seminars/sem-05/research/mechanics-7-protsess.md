# Механика процесса Claude Code — вход для автора раздела

Этот документ — рабочий справочник для четырёх блоков задания, не готовый слайд.
`stage-7-protsess.md` уже разобрал провалы (самоотчёт vs факт, обход проверки, фабрикация) —
здесь эти темы не повторяются, кроме одной точки пересечения, отмеченной явно (§2.6). Ступень
процесса действительно наименее исследована механически из всей лестницы курса: в отличие от
хуков (ступень 3, где механика документирована исчерпывающе — события, поля, decision control),
о режиме планирования и задачной памяти официальная документация даёт факты, но разбросанные по
пяти разным страницам, и их приходится собирать вручную.

**Методология проверки.** Каждое утверждение о поведении продукта получено одним из трёх
способов: (1) прямой `curl` официальной markdown-версии страницы документации
(`https://code.claude.com/docs/en/<page>.md` — реальный, работающий URL), обращение
**2026-09-27**, тем же днём, когда собирается этот документ; (2) `gh api
repos/tellina-study/signup-landing-demo/...` — реальное содержимое публичного демо-репозитория
курса на ветке `main`, тем же днём; (3) чтение уже собранных материалов этого же семинара
(`section-5-protsess.md`, `WORK-ORDER-demo-repo.md`, захваты `assets/captures/17-*` и `34-*`).
Страницы документации ссылаются на конкретные версии продукта до `v2.1.283` включительно —
содержание актуально по крайней мере для этой линии; ни одна страница не даёт единого номера
версии или даты «обновлено», поэтому перед показом стоит свериться с `claude --version` на
машине для демонстрации (тот же честный пробел, что уже отмечен в `mechanics-3-khuk.md` и
`mechanics-6-subagent.md`).

## 1. Режим планирования — когда и как

### 1.1. Как включается — четыре пути, два разных субъекта включения

Дословно из `permission-modes.md` (раздел «Analyze before you edit with plan mode»): **"Plan mode
tells Claude to research and propose changes without making them. Claude reads files, runs shell
commands to explore, and writes a plan, but does not edit your source."**

Включить режим может **человек**, четырьмя равноценными способами:

1. **`Shift+Tab`** — цикл режимов. Дословно: **"press `Shift+Tab` to cycle permission modes. From
   `auto`, the first press switches to `default`, and the cycle then runs `default` →
   `acceptEdits` → `plan` → back to `default`."** То есть `plan` не первый в цикле — сначала идёт
   `acceptEdits` (автоодобрение правок файлов), только третьим нажатием — план.
2. **`/plan`** как префикс одной реплики — включает режим только на эту реплику.
3. **Флаг запуска**: `claude --permission-mode plan`.
4. **Настройка по умолчанию**: `defaultMode: "plan"` в `.claude/settings.json` проекта —
   «To make plan mode the default for a project's terminal sessions, set `defaultMode` to `plan`».
   В VS Code это делается отдельной настройкой (`claudeCode.initialPermissionMode`), не файлом
   проекта — расширение никогда не читает `.claude/settings.json` для стартового режима.

Включить режим может и **сама модель**, отдельным механизмом — инструментом `EnterPlanMode`.
Официальное описание инструмента (SDK-справочник): **"Enters plan mode, where Claude researches
and presents a plan before making changes."** Это не то же самое, что `Shift+Tab`: человек
переключает режим сессии снаружи, модель может войти в план **сама**, посреди работы, если
решает, что задача требует исследования перед правкой. Прямого официального подтверждения
формулировки «автоматически включается на сложных задачах» (как отдельной настройки-порога) не
найдено — это решение модели по своему усмотрению через доступный ей инструмент, а не
задокументированный триггер по сложности; выносить на слайд как настройку не стоит
**[не подтверждено официально — нет отдельной страницы про автотриггер по сложности]**.

Статус-бар показывает активный режим одной строкой: **`⏸ plan mode on`** — серым, в отличие от
зелёного `⏵⏵` у режимов, которые действуют без вопросов (`accept edits`, `auto`, `bypass
permissions`). Это символьное различие само по себе несёт механический смысл: пауза vs
двойная стрелка «вперёд».

### 1.2. Что физически разрешено, что запрещено — точная граница, не лозунг

Это ключевая деталь, без которой тезис «агент планирует, но не правит» остаётся лозунгом.
Документация делит поведение на три отдельных канала, и они регулируются **разными**
механизмами:

**Чтение и поиск — разрешены безусловно, без исключений.** `Read`/`Grep`/`Glob` работают в plan
mode так же, как в любом другом режиме.

**Bash-команды — разрешены избирательно, и зависят от конфигурации сессии, а не от plan mode как
такового.** Дословно, три случая, применяются по порядку, первый совпавший действует:

- **Интерактивная терминальная сессия с доступным bypass permissions**: ни классификатор, ни
  запрос не применяются к командам планирования вовсе — команда просто выполняется.
- **Auto mode доступен и настройка `useAutoModeDuringPlan` включена** (включена по умолчанию):
  классификатор (отдельная модель) проверяет bash-команды, кроме удалений критических путей, и
  сам решает, пропустить или заблокировать — без вопроса пользователю.
- **Auto mode недоступен или настройка выключена**: команды вне встроенного read-only-набора
  запрашивают подтверждение у человека, включая случай, когда auto-allow сэндбокса включён.

То есть bash в plan mode **не заблокирован категорически** — read-only набор выполняется всегда
свободно, остальное либо решает классификатор молча, либо спрашивает человека; жёсткого барьера
здесь нет ни в одном из трёх случаев.

**Правка файлов — единственный канал, где барьер действительно жёсткий, но и он не абсолютен.**
Дословно: **"edits stay blocked until you approve the plan"** — но с явной оговоркой: **"Except in
interactive terminal sessions with bypass permissions available"**. Дальше в том же документе,
в разделе про `bypassPermissions`, это раскрывается прямо: **"Claude Code also doesn't enforce
plan mode's blocks. Claude is still instructed to plan without editing, but a file edit or shell
command it attempts during planning runs without prompting."** Это критично для раздела курса,
который уже различает «правило в промпте» и «правило в коде» (`CLAUDE.md`, раздел «Хук защиты
ветки» демо-репозитория, процитирован в `section-5-protsess.md` §A.1): **сам барьер plan mode в
обычной терминальной сессии — механический**, инструменты `Edit`/`Write`/`NotebookEdit`
физически отказывают до одобрения плана; но в сессии с доступным bypass permissions этот же
барьер вырождается в **тот же текстовый запрос**, что и правило в `CLAUDE.md` — «Claude is still
instructed», не «is blocked». Один и тот же продуктовый механизм оказывается то хуком, то
просьбой, в зависимости от конфигурации окружения, в котором сессия запущена — это не отдельная
уступка, а прямая иллюстрация всего тезиса ступени.

Инструменты `EnterPlanMode`/`ExitPlanMode` сами по себе обычными правками не считаются:
`EnterPlanMode` не требует подтверждения («Permission required: No»), `ExitPlanMode` требует
(«Yes») — именно на нём висит запрос одобрения плана, разобранный ниже.

### 1.3. Выход из режима — с одобрением плана и без

**Без одобрения:** повторное `Shift+Tab` — «Press `Shift+Tab` again to leave plan mode without
approving a plan.» План при этом никуда специально не сохраняется — остаётся обычным текстом в
переписке, как любая другая реплика модели, без превращения во что-то структурное.

**С одобрением:** инструмент `ExitPlanMode` представляет план и предлагает три варианта, дословно:

- **«Yes, and use auto mode»** — одобрить и перейти в auto mode (если auto mode недоступен
  сессии, формулировка меняется на «Yes, auto-accept edits»; если сессия запущена с
  bypass permissions, — на явную формулировку перехода в BYPASS PERMISSIONS);
- **«Yes, manually approve edits»** — одобрить и разбирать каждую правку по отдельности;
- **«No, keep planning»** — остаться в режиме и уточнить, что переделать.

Одобрение плана **переключает режим сессии** на тот, что описывает выбранный вариант — это не
разовое разрешение на одну правку, а смена режима до следующего переключения.

**`Ctrl+G`** открывает предложенный план в текстовом редакторе по умолчанию для прямого
редактирования **до** того, как модель начнёт действовать — то есть план можно поправить руками,
не переписывая его текстом в чат.

Одобрение плана даёт сессии **сгенерированное имя на основе плана**, если сессию ещё не назвали
явно — механический побочный эффект, полезный для слайда: план не только текст, он оставляет след
даже в имени сессии.

### 1.4. Что происходит с планом при выходе — и честная граница, где документация не договаривает

По таблице «What survives compaction» (`context-window.md`): **план, который Claude написал в
plan mode, при сжатии контекста (`/compact`) «Re-injected from disk»** — то есть план не теряется
при автоматической компакции длинной сессии, он читается заново с диска. Это факт, подтверждённый
дословной строкой таблицы официальной документации.

**Честная граница.** Документация не называет конкретный путь файла, куда план записан отдельно
от остальной истории — «с диска» здесь может означать как отдельный артефакт состояния сессии,
так и просто повторное чтение того же файла транскрипта, где план уже есть как обычное сообщение
(транскрипты в любом случае хранятся на диске, §2.2). Ни одна страница не даёт студенту команду
«открой файл плана» так же прямо, как для `.tasks/README.md` в демо-репозитории — **это и есть
принципиальное отличие**, которое стоит вынести на слайд явно, а не смягчать: план восстанавливается
внутри той же сессии тем же механизмом, что и всё остальное состояние, но не становится отдельным,
именованным, самостоятельно открываемым файлом, который можно показать соседу по столу или закоммитить
в репозиторий, — а `.tasks/active/*.md` именно такой файл, специально для этого заведённый
(разбор — §3). **[выводится из документированного поведения компакции, не процитировано напрямую как
«путь к файлу плана» — не выдавать за подтверждённый путь на диске]**

## 2. Чем продукт помнит ход работы — и чем не помнит

### 2.1. Задачный список сессии (`TodoWrite`/`TaskCreate`/`TaskUpdate`/`TaskList`/`TaskGet`) — что это механически

Начиная с v2.1.268 продукт предоставляет по умолчанию **на ограниченном наборе моделей**
(«Claude 3.x, Opus 4–4.7, Sonnet 4–4.6, Haiku 4.5», дословно) либо старый инструмент `TodoWrite`,
либо новый набор из четырёх Task-инструментов — не оба сразу; переключение — переменной
`CLAUDE_CODE_ENABLE_TASKS=0` (даёт `TodoWrite` вместо Task-набора). На моделях вне этого списка
инструментов нет вовсе, если не включить явно (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1` или явный
allowlist инструментов).

**Жизненный цикл задачи**, дословно, четыре шага: `pending` при создании → `in_progress` при
начале работы → `completed` при успешном завершении → удаление через `TaskUpdate` со
`status: "deleted"`, если задача больше не нужна. Каждое изменение статуса — отдельный,
структурированный вызов инструмента в потоке сообщений, а не свободный текст.

Это список **исключительно текущей сессии**. Он не файл на диске, который можно открыть отдельно
от переписки, — это набор вызовов инструментов внутри одной и той же истории сообщений сессии.

### 2.2. Транскрипт сессии — самый полный журнал продукта, и одновременно самый недолговечный

Дословно из `sessions.md`: **"By default, Claude Code stores transcripts as JSONL at
`~/.claude/projects/<project>/<session-id>.jsonl`... Each line is a JSON object for a message,
tool use, or metadata entry."** Это значит: транскрипт содержит **каждый** вызов инструмента и
его результат — не отчёт модели о себе, а фактический журнал действий, построчно.

Но тут же — два ограничения, важные для тезиса раздела:

- **Формат внутренний и нестабильный**: **"The entry format is internal to Claude Code and
  changes between versions, so scripts that parse these files directly can break on any release.
  To build on session data, use `/export` or the script interfaces instead."** То есть продукт
  сам не считает этот файл публичным контрактом — сознательно не документирует его схему и прямо
  отговаривает от прямого парсинга.
- **Срок жизни ограничен**: транскрипты удаляются в «retention sweep» по истечении
  `cleanupPeriodDays` — **по умолчанию 30 дней** (подтверждено, `settings-reference.md`,
  «Default: `30`»). После этого срока журнал, даже самый полный, какой ведёт продукт, физически
  не существует, если не изменить настройку заранее.

**Это меняет то, как стоит подавать статистику «≈1 действие из 11» на слайде (§2.6 ниже).**

### 2.3. Чекпоинты — снимки файлов, а не журнал действий, и тоже недолговечны

Checkpointing автоматически снимает состояние файлов **перед каждой репликой, начинающей новый
такт**: «Claude Code keeps file snapshots for the 100 most recent checkpoints in a session.» Это
даёт `/rewind` — восстановить код, переписку, или обе части, к любой из этих точек, — но с четырьмя
документированными ограничениями:

- **не отслеживает правки через Bash** («`rm file.txt`, `mv old.txt new.txt`, `cp source.txt
  dest.txt`» — «These file modifications cannot be undone through rewind»);
- **не отслеживает правки субагента**, кроме одного узкого случая (форкнутый скилл на переднем
  плане) — «rewinding doesn't restore the edits» для любого другого субагента;
- **не отслеживает внешние правки** — сделанные не этой сессией;
- **не заменяет систему контроля версий** — дословный, отдельный подзаголовок документации:
  «Not a replacement for version control».

Снимки чекпоинтов удаляются в том же retention sweep, что и транскрипты (~30 дней по умолчанию).

### 2.4. Автопамять — единственный механизм, персистентный между сессиями, и одновременно самокураторский

Auto memory — единственная часть штатной памяти продукта, которая **переживает конец сессии** и
**не подпадает под retention sweep**: «Claude Code deletes old session transcripts after the
`cleanupPeriodDays` retention period, but excludes the memory files in the memory directory from
that retention sweep.» Хранится в `~/.claude/projects/<project>/memory/` — один индекс
(`MEMORY.md`, первые 200 строк или 25 КБ, что раньше, — то, что загружается автоматически в
начале каждой сессии) плюс отдельные тематические файлы, читаемые по требованию.

Но: **что туда попадает — решает сама модель**, дословно: «Claude doesn't save something every
session. It decides what's worth remembering based on whether the information would be useful in
a future conversation» и «Claude skips anything it can derive from the codebase... It also skips
anything your CLAUDE.md files already say.» Это тот же структурный вопрос, что и у самоотчёта
(стадия провалов), только на уровень выше: не «что модель рассказала о сессии», а «что модель
сама решила, что стоит запомнить о сессии» — тоже отбор, тоже без внешней проверки полноты.

### 2.5. Что переживает `/compact` внутри одной сессии — и заметное отсутствие задачного списка в этом списке

Таблица «What survives compaction» (`context-window.md`) перечисляет по каждому механизму, что с
ним происходит при сжатии истории:

| Механизм | После `/compact` |
|---|---|
| Системный промпт и output style | Действуют без изменений |
| `CLAUDE.md` корня проекта и правила без `paths:` | Перечитываются с диска |
| Автопамять | Перечитывается с диска |
| Снимок `git status` | Читается заново из репозитория |
| План из plan mode | «Re-injected from disk» |
| Правила с `paths:` | Подгружаются повторно по факту чтения файла |
| Файлы, которые читались/правились | До пяти, начиная с последних изменённых |
| Содержимое вызванных скиллов | Переинжектируется, с обрезкой по токен-бюджету |
| Фоновые команды/субагенты | Продолжают работать |
| Контекст, добавленный хуками | **Сжимается в общий пересказ, как всё остальное** |

**Задачный список (`TodoWrite`/`Task*`) в этой таблице не назван вовсе** — ни в колонке
«переживает», ни в колонке «сжимается». Единственный логичный вывод из структуры документа:
поскольку список — это обычные вызовы инструментов внутри истории сообщений, а не отдельно
загружаемый механизм (как `CLAUDE.md`, автопамять или план), он подчиняется тому же правилу, что
и «контекст, добавленный хуками», — попадает в общий пересказ компакции как текст, теряя
структуру (`pending`/`in_progress`/`completed` как отдельные структурированные записи). Это
**вывод по структуре документации, не прямая цитата**, — стоит подавать на слайде с этой пометкой,
а не как утверждение документации напрямую. **[выводится из отсутствия строки в таблице, не
процитировано как явное правило]**

### 2.6. Уточнение к цифре «≈1 действие из 11» — другая сторона того же вопроса, а не то же измерение

`stage-7-protsess.md` (§4a, со ссылкой на arXiv:2609.12205) цитирует измерение: самоотчёт агента
упоминает **~1 действие из 11** реально выполненных. Задание этой ступени просит проверить,
**что именно продукт сохраняет сам** — и здесь важно не смешать два разных объекта:

- **Финальное сообщение агента** («готово, тесты прошли») — это узкий, свободно написанный
  пересказ, тот самый объект, который измеряет arXiv:2609.12205.
- **Транскрипт сессии** (§2.2) — механически, построчно, фиксирует **каждый** вызов инструмента,
  без всякого отбора моделью. По структуре документации это гораздо более полный журнал, чем
  финальное сообщение, — просто он: (а) не в человекочитаемом виде без `/export`, (б) внутренний,
  нестабильный формат, (в) исчезает через 30 дней по умолчанию.

**Механический вывод для слайда, отличный от того, что говорит ступень провалов:** дело не в том,
что продукт «забывает» большинство действий — построчный журнал у него есть и он почти полный.
Дело в том, что этот журнал (i) не то, что читает человек по умолчанию (человек читает финальное
сообщение — узкий пересказ), и (ii) не то, что переживает 30 дней и смену машины. Разрыв «отчёт
vs факт» из ступени провалов — это разрыв между тем, **что модель решила сказать**, и тем, **что
происходило**; механика продукта показывает, что полный журнал происходившего физически
существует рядом, просто в форме, которую никто не обязан открывать и которая не предназначена
жить дольше месяца. `.tasks/` (§3) — это осознанная компенсация именно этого зазора: не «более
полный журнал, чем у продукта», а «тот же по сути журнал, вручную вынесенный в форму, которая
переживает 30-дневный сброс, читается человеком без `/export`, и коммитится в тот же репозиторий,
что и код».

### 2.7. Штатные средства «подытожить» сессию — все внутренние, ни один не аудит

- **`/compact [instructions]`** — заменяет историю пересказом, тем же самым процессом, который
  писал историю (не независимая проверка).
- **`/rewind` → «Summarize from here» / «Summarize up to here»** — то же самое, но с точки в
  середине сессии, с возможностью направить пересказ инструкцией.
- **Диалог «Resume from summary» при возвращении** к неактивной >~1 часа сессии старше 100 000
  токенов (Pro/Max) — три варианта: пересобрать по сводке, продолжить как есть, не спрашивать
  больше. Тоже сводка, сгенерированная тем же механизмом.
- **`/export`** — рендерит переписку в читаемый текст **по запросу человека**, не автоматически;
  предназначен для передачи человеку, не для машинной сверки.

Ни один из этих механизмов не проверяет факт — все они пересказывают то, что уже сказано в той же
истории, тем же процессом. Это прямая параллель тезису провалов: даже штатное «подведение итога»
продукта устроено как ещё один слой самоотчёта, не как независимая проверка состояния.

### 2.8. Итог блока — чем `.tasks/` принципиально отличается от всего перечисленного

Ни один из механизмов §2.1–2.7 не даёт одновременно: (а) файл, который можно открыть без
`/export` и без запущенной сессии; (б) стабильный, задокументированный формат, не меняющийся между
версиями продукта; (в) отсутствие автоматического удаления через 30 дней; (г) переносимость между
машинами через обычный `git clone`; (д) видимость для человека и для **любого** будущего агента,
а не только для той сессии, что это писала. `.tasks/active/*.md` в демо-репозитории курса —
обычный markdown-файл в git — даёт все пять свойств сразу, потому что заведён вручную, специально
ради них, а не является побочным продуктом механики харнесса.

## 3. Как пишется правило процесса — на примере `.tasks/README.md` + `CLAUDE.md`, по шагам

Дословно, оба файла существуют на `main` демо-репозитория `tellina-study/signup-landing-demo`
(сверено `gh api` 2026-09-27):

```markdown
# .tasks — один файл на задачу

Пока задача идёт, её файл лежит в `active/`. Закончилась — переезжает в `done/`.
Имя: `YYYY-MM-DD-краткое-описание.md`.

Зачем: у сессии кодинг-агента нет памяти между запусками, а у человека — между днями.
Файл задачи — единственное место, где написано, что уже проверено и что осталось,
в момент, когда это ещё известно.

**Строка «Сверено».** Ставится в начале и в конце сессии — датой, которую печатает
`date -u +%Y-%m-%dT%H:%M:%SZ`, а не по памяти. Запись без неё неотличима от записи,
которую забыли обновить: файл задачи, который никто не сверял, уверенно врёт о
состоянии работы.

**«Что уже проверено» — дословный вывод команд, а не пересказ.** «Тесты зелёные» —
утверждение; `7 passed (3.1s)` — факт.
```

и в `CLAUDE.md`:

```markdown
## Задачная память
- На многошаговую задачу — файл в `.tasks/active/`, до первой правки.
- Договорённость или решение по ходу — в этот файл сразу, а не в конце сессии.
- План сверять в начале и в конце сессии, дату ставить `date -u +%Y-%m-%dT%H:%M:%SZ`.
```

Это — **конвенция курса**, установленная на предыдущем занятии (кейс 2.3 Семинара 4), не
встроенная функция продукта. Продукт не знает о существовании `.tasks/`; ничего в харнессе не
требует такого файла и не проверяет его наличие само по себе. Разбор ниже — почему каждая
формулировка написана именно так, а не проще.

### 3.1. «До первой правки» — что ломается при «напишу в конце сессии»

Наивный вариант: завести файл задачи постфактум, как отчёт о сделанном. Ломается ровно то, ради
чего файл существует: цель правила — зафиксировать, **что было известно в момент, когда это было
ещё известно** («Файл задачи — единственное место, где написано... в момент, когда это ещё
известно»). Запись, сделанная в конце, — это уже пересказ по памяти, тот же жанр, что финальное
сообщение агента из §2.6 и §4a стадии провалов: скудный, отобранный, написанный тем же процессом,
который хочет выглядеть завершённым. Файл «до первой правки» физически не может стать таким
пересказом, потому что в момент его создания результата ещё нет, что писать — не выбор из готового
финала.

### 3.2. «Сверено» с датой из `date -u`, а не по памяти — что ломается при «поставлю дату руками»

Наивный вариант: написать дату так, как модель или человек её помнит («2026-09-27» напечатано
текстом). Ломается работа именно этой строки как факта, а не утверждения: дата, напечатанная по
памяти, не отличима глазом от честной и от ошибочной — ни один читатель файла не может проверить,
действительно ли она соответствует моменту записи, потому что источник даты — та же голова
(человеческая или модельная), что пишет остальной текст. Дата, выведенная командой `date -u
+%Y-%m-%dT%H:%M:%SZ`, — независимый факт: её можно перепроверить, сравнив со временем модификации
файла (`git log --format=%aI` на коммите, добавившем строку) или с текущим `date -u` в момент
проверки. Наивный вариант не даёт такой точки опоры вообще.

### 3.3. «Дословный вывод команд, а не пересказ» — что ломается при «напишу тесты зелёные»

Пример из самого правила: «"Тесты зелёные" — утверждение; `7 passed (3.1s)` — факт.» Наивный
вариант ломается ровно тем механизмом, который описывает практик-лог сентября 2026, процитированный
в `stage-7-protsess.md`: 35 из 101 заявления «тесты прошли» оказались неверны на момент заявления,
и почти все — не ложь, а **устаревшее** утверждение (тест правда проходил, просто раньше). Фраза
«тесты зелёные» без даты и без дословного вывода неотличима на бумаге в двух разных случаях:
тест прошёл только что, и тест прошёл когда-то раньше, а код с тех пор поменяли. Строка
`7 passed (3.1s)`, вставленная дословно рядом со строкой «Сверено» с датой прогона, снимает эту
неотличимость: у читателя есть и результат, и момент, к которому он привязан, — то есть
утверждение становится проверяемым, а не просто убедительно звучащим.

### 3.4. Живой пример этого же правила под давлением реального ROAST — активный файл задачи демо-репозитория

Реальный файл `.tasks/active/2026-09-24-dostroit-dugu-seminara-4.md` (сверено `gh api` 2026-09-27)
показывает, как правило разрастается, когда его действительно проверяют. В разделе «Открытые
вопросы» этот же файл честно фиксирует: **независимый ROAST нашёл в предыдущей версии файла три
SHA, которых для читателя не существует** — они остались от более ранней версии дуги коммитов,
переписанной `rebase`. Ответ на находку — не «поверить на слово, что теперь всё так», а
**добавленная в файл проверочная команда**, дословно:

```bash
grep -oE '`[0-9a-f]{7}`' .tasks/active/*.md | tr -d '`' | sort -u | while read s; do
  git merge-base --is-ancestor "$s" origin/seminar-4-arc 2>/dev/null \
    && echo "$s достижим" || echo "$s НЕ ДОСТИЖИМ"
done
```

Это ровно та же логика, что у строки «Сверено»: утверждение «эти коммиты существуют» заменено
командой, которую можно перезапустить и получить тот же ответ независимо от того, кто пишет файл.
Раздел «Что уже проверено» этого файла подтверждает: все 11 названных SHA достижимы с
`origin/seminar-4-arc` — это не декларация, а результат реального прогона именно этой команды.

### 3.5. Чем это правило принципиально отличается от хука — механически, не морально

`CLAUDE.md` этого же демо-репозитория, раздел «Хук защиты ветки» (ступень 3 занятия), формулирует
разницу прямой цитатой, уже собранной в `section-5-protsess.md` §A.1: **«Это не гейт, а хук: гейт —
строка текста, которую агент читает и может учесть; хук выполняется и отказывает. Правила в
промпте — просьбы, правила в коде — законы.»**

Механически эта разница выглядит так. Хук — это код, который харнесс **сам вызывает** на
конкретном событии (`PreToolUse` до вызова инструмента, `Stop` при попытке завершить такт) и чей
`exit code`/JSON-ответ **встроен в управляющий поток** продукта: `"decision": "block"` буквально
не даёт такту завершиться, независимо от того, «хочет» ли модель остановиться. Правило `.tasks/`
— это текст, который харнесс **загружает в контекст** модели (как часть `CLAUDE.md`) вместе со
всем остальным и **читает модель**, а не харнесс: решение соблюсти его или пропустить принимает
тот же процесс, который вообще пишет финальный ответ. У продукта нет точки в управляющем потоке,
которая проверяла бы наличие файла задачи, строки «Сверено» или дословности вывода **сама**, если
это не реализовано отдельным хуком (§4.3 — что из этого технически можно перенести туда). Разница
не в строгости формулировки правила, а в том, **кто исполняет решение**: в случае хука — харнесс,
детерминированно; в случае `.tasks/` — модель, по своему усмотрению, при том что харнесс не
проверяет результат этого усмотрения ни на одном шаге.

## 4. Как проверяется и отлаживается, что процесс соблюдён

### 4.1. За минуту — по каким артефактам и в каком порядке

1. Есть ли файл задачи вообще — в `.tasks/active/` (задача идёт) или в `.tasks/done/` (закрыта).
2. Есть ли в нём **две** строки «Сверено» — в начале и в конце — и насколько дата второй близка к
   моменту, когда сессия реально закончилась (а не совпадает с датой первой строки, что означало
   бы «сверил один раз и не вернулся»).
3. Существуют ли все названные в файле коммиты и достижимы ли они с той ветки, на которую
   ссылается файл (а не просто существуют как объекты — этого не хватает после `rebase`, §3.4).
4. Совпадает ли вердикт в артефакте ревью (если он есть) с тем, что реально выдал ревьюер, а не
   с тем, что автору правки было бы удобно увидеть.

### 4.2. Что механически проверяется, а что — только глазами

| Что проверяем | Механически? | Как именно |
|---|---|---|
| Файл задачи существует в `active/` или `done/` | Да | `test -f .tasks/active/*.md` |
| Есть строка `**Сверено:**` | Да | `grep -c 'Сверено' <файл>` |
| Дата в строке «Сверено» — валидный ISO-8601, а не текст «сегодня» | Да | regex на формат `date -u` |
| Дата второй «Сверено»-строки близка к текущему `date -u` в момент проверки | Да | разница `date -d` в секундах против порога |
| SHA, названные в файле, — реальные объекты репозитория | Да | `git cat-file -t <sha>` — но **недостаточно**: проходит и на осиротевших после `rebase` объектах (см. §3.4) |
| SHA достижимы с указанной ветки | Да | `git merge-base --is-ancestor <sha> <ref>` — именно эта команда закрыла находку ROAST |
| «Что уже проверено» — дословный вывод команды, а не пересказ | **Частично** | эвристика (наличие числовых паттернов вида `N passed`, кода возврата) отличает «похоже на вывод» от явной прозы, но не доказывает, что вывод не подделан вручную |
| Вердикт ревью отражает реальное, независимое суждение проверяющего | **Нет** | можно механически сверить, что текст вердикта существует и что он датирован не раньше правки, но не то, было ли суждение действительно независимым и верным |

Три нижние строки — граница, о которую разбивается любая попытка сделать процесс полностью
«само-проверяемым» текстом. Существование факта, его дата и ссылочная целостность (SHA) —
проверяемы программой. Правдивость содержания и подлинность суждения — нет: программа может
проверить, что **форма** соблюдена (строка есть, дата свежая, SHA существует), но не то, что за
этой формой стоит реальная, а не сфабрикованная работа. Это ровно тот же разрыв «форма vs факт»,
который стадия провалов документирует на уровне финального отчёта модели — здесь он воспроизводится
на уровне артефакта, который призван этот отчёт заменить.

### 4.3. Что из этого можно заставить исполняться, а не заполняться — мостик к хуку ступени 3

Механически заставить исполняться можно только то, что попадает в **точку управляющего потока**,
которую харнесс сам вызывает. Для процесса такая точка — хук `Stop` (не `SessionEnd`).

Документация проводит эту границу явно. **`SessionEnd`** хуки — «no decision control. They can't
block session termination but can perform cleanup tasks» — этой точкой процесс подпереть нельзя,
она может только убрать за собой, когда сессия уже закончилась.

**`Stop`**, наоборот, — именно та точка, где решение можно заблокировать: дословно, скрипт хука
может вернуть `{"decision": "block", "reason": "..."}`, и это **буквально не даёт такту
закончиться** — с защитой от бесконечного цикла («8-consecutive-continuation cap»). Это значит:
правило «задача не переезжает в `.tasks/done/` без заполненного вердикта» (наряд 4 демо-репозитория,
`WORK-ORDER-demo-repo.md`, п. 3) технически **можно** реализовать не только как строку в
`CLAUDE.md`, а как `Stop`-хук, который перед тем, как разрешить агенту завершить такт, грепает файл
задачи на: наличие второй строки «Сверено» с датой не старше N минут от реального `date -u` в
момент срабатывания хука, наличие строки вердикта, и достижимость названных в ней SHA (та же
команда, что уже реально используется в файле демо-репозитория, §3.4, — только запускаемая
харнессом, а не автором файла). Это ровно тот класс проверки, что §4.2 относит к «механически
проверяется»: существование, формат, ссылочная целостность.

**Что этим же путём заставить исполняться нельзя в принципе** — семантическая правдивость
содержимого. `Stop`-хук может отказать такту, если строки нет или дата протухла; он не может
отличить дословный вывод реальной команды от правдоподобно сочинённого текста той же формы,
и не может отличить вердикт, вынесенный после настоящего независимого прогона ревьюера, от
вердикта, скопированного из того, что автор правки хотел увидеть. Показательно, что этот же
структурный предел есть и у **встроенного** механизма продукта с максимально похожей задачей —
командой `/goal`, чей эвалюатор проверяет условие завершения после каждого такта. Документация
называет это ограничение прямо: **«The evaluator judges your condition against what Claude has
surfaced in the conversation. It doesn't run commands or read files independently»**. То есть
даже штатный, специально спроектированный продуктом «независимый» проверяющий слой читает не
состояние системы, а то, что модель **сама показала** в переписке о своей работе, — тот же
самоотчёт на другом уровне, если условие не сформулировано так, что подтверждающая команда реально
исполняется и её вывод реально попадает в транскрипт. Границу «что можно исполнить принудительно»
двигает не сам факт наличия хука/эвалюатора, а то, читает ли он **реальное состояние** (файл,
git, вывод команды) или **пересказ** этого состояния той же моделью.

### 4.4. Типовые способы, которыми процесс обходят не злонамеренно

- **Файл задачи заведён и не обновлён.** Первая строка «Сверено» стоит на старте, вторая — либо
  отсутствует, либо равна первой (сессия закрыта, но файл никто не открывал перед закрытием).
  Ловится механически: сравнить дату второй строки с реальным временем последнего коммита в этой
  же задаче.
- **Запись сделана после, а не по ходу.** Обе строки «Сверено» и весь раздел «что проверено»
  написаны в одну сессию редактирования файла задачи, задним числом. Частично ловится: если файл
  создан в git одним коммитом, а не двумя (создание в начале, дополнение в конце), — это видно по
  `git log --follow`, хотя сам факт «одного коммита» не доказывает фабрикацию однозначно (можно
  честно вести заметки локально и закоммитить один раз).
- **Ссылка на коммит, которого нет.** Ровно инцидент §3.4: SHA существует как git-объект (проходит
  наивную `git cat-file -t`), но не достижим ни с одной именованной ветки после `rebase` —
  находка, которую в реальности поймал **независимый ROAST**, не автоматическая проверка (проверка
  появилась только **после** находки, как реакция на неё). Это честный пример того, что даже
  механически проверяемые вещи (§4.2, верхние строки таблицы) не проверяются автоматически, если
  никто не написал соответствующую команду заранее, — механическая проверяемость и факт того, что
  проверка действительно выполнена, разные утверждения.

### 4.5. Пример проверочной последовательности — 3–4 шага

1. **Файл существует и на правильном этапе.** `.tasks/active/<...>.md` — задача открыта;
   `.tasks/done/<...>.md` — закрыта. Если ни там, ни там — процесс не начат вообще, дальше
   проверять нечего.
2. **Обе строки «Сверено» на месте, и вторая не устарела.** `grep 'Сверено' <файл>` — должно быть
   две даты, не одна; вторая — не более чем на разумный интервал старше `date -u` в момент, когда
   задача помечена закрытой (для закрытой задачи — старше момента переезда в `done/`, а не
   текущего момента проверки).
3. **Каждый названный SHA — реальный и достижимый.** Ровно команда из §3.4:
   `git merge-base --is-ancestor <sha> <ref>` для каждого SHA, найденного в файле — не
   `git cat-file -t`, этого недостаточно.
4. **Вердикт (если задача прошла через ревью) соответствует тому, что реально вынес проверяющий.**
   Открыть исходный ответ субагента/ревьюера (если он сохранён отдельно, как в наряде 3–4
   демо-репозитория) и построчно сравнить со строкой вердикта в файле задачи — не «похоже на
   BLOCK», а тот же самый текст.

## 6. Чего я не смог подтвердить

- **Автотриггер plan mode «на сложных задачах» как отдельная настройка.** Подтверждён только
  механизм — инструмент `EnterPlanMode`, который модель может вызвать сама, по собственному
  решению; отдельного документированного порога сложности, который включал бы режим
  автоматически, не найдено. **[не подтверждено официально]**
- **Точный путь файла, где хранится план отдельно от общего транскрипта сессии.** Документация
  утверждает, что план «re-injected from disk» после компакции, но не называет дискретный путь,
  который можно открыть независимо от `/export` или запущенной сессии — в отличие от
  `~/.claude/projects/<project>/memory/MEMORY.md` для автопамяти, где путь назван прямо.
- **Теряет ли задачный список (`TodoWrite`/`Task*`) структуру при `/compact` буквально, а не по
  выводу из отсутствия строки в таблице.** Таблица «What survives compaction» не называет этот
  механизм явно ни в «переживает», ни в «сжимается» — вывод о том, что он попадает в общий
  пересказ, логичен по структуре документа (это обычные вызовы инструментов в истории сообщений,
  а не отдельно загружаемый механизм), но не процитирован как прямое правило.
- **Мера, насколько эвристика «дословный вывод vs пересказ» (§4.2) реально ловит подделку на
  практике.** Ни разработчик правила `.tasks/`, ни документация продукта не дают эталонного
  детектора для этого различения — только контрастный пример («"тесты зелёные" — утверждение;
  `7 passed (3.1s)` — факт»), не общий тест.
- **Действует ли на демо-репозиторий `.tasks/` какая-либо механическая проверка сейчас (сентябрь
  2026), кроме той, что вручную вписана в сам файл задачи.** Наряд 4 `WORK-ORDER-demo-repo.md`
  описывает, что должно быть построено (шаблон ревью, правило переезда в `done/`), но, по
  собственному признанию наряда, на 2026-09-27 не выполнен — то есть на сегодня в репозитории
  реально есть только две трети правила (план + запись по ходу), третья (вердикт как условие
  переезда) существует лишь как совместно собранная на занятии формулировка, не как файл.
