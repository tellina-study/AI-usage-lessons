# Механика скилла Claude Code — вход для автора раздела

Этот документ — не конспект лекции и не готовый слайд, а рабочий справочник по **механике**:
когда принимается решение о загрузке скилла, что именно должно быть в файле, как скилл пишется по
шагам и как отлаживается вопрос «почему он не сработал». `stage-4-skill.md` уже разобрал экономику
(с базой сравнения из SkillsBench и Skill Shadowing) и провалы/безопасность (вред от сработавшего
скилла, скилл как чужой код с постоянными правами) — здесь это **не повторяется**, кроме случаев,
когда механика и провал делят один факт (например, «описание — единственный канал выбора» — это и
механика, и причина shadowing; здесь разбирается только механика).

**Методология проверки.** Каждое утверждение получено прямым `curl` официальной markdown-версии
страницы документации, без прослойки суммаризирующей модели. Два разных, но связанных документа:
(1) `code.claude.com/docs/en/skills.md` и `code.claude.com/docs/en/debug-your-config.md` —
Claude Code-специфичная документация; (2) `docs.claude.com/en/docs/agents-and-tools/agent-skills/
overview.md` и `.../best-practices.md` — редиректят на `platform.claude.com` и описывают **общий**
стандарт Agent Skills (тот же формат `SKILL.md`, но с описанием API/VM-окружения, а не терминала).
Оба документа цитируются по отдельности и **сверяются друг с другом** там, где они, на первый
взгляд, говорят разное про одни и те же числа — это оказалось важнее, чем ожидалось (см. §1.1 и
§2.1). Обращение к документации — **2026-09-27**. Версия продукта не указана явно ни на одной
странице, но текст ссылается на конкретные версии до `v2.1.281` включительно (Claude Code) —
значит, содержание актуально по крайней мере для этой линии версий.

## 1. Когда принимается решение о загрузке

### 1.1. Три уровня, дословно — и два разных документа про один и тот же факт

Общая страница Agent Skills (`platform.claude.com/docs/en/agents-and-tools/agent-skills/
overview`) формулирует механизм как архитектурное свойство самой файловой системы: **"This
filesystem-based architecture enables progressive disclosure: Claude loads information in stages
as needed, rather than consuming context upfront."** Три уровня, дословная таблица оттуда:

| Level | When loaded | Token cost | Content |
|---|---|---|---|
| **Level 1: Metadata** | Always (at startup) | ~100 tokens per Skill | `name` and `description` from YAML frontmatter |
| **Level 2: Instructions** | When Skill is triggered | Under 5k tokens | SKILL.md body with instructions and guidance |
| **Level 3+: Resources** | As needed | None until accessed | Bundled files. Reference files load into context when read. Scripts run through bash, and only their output enters context |

Про уровень 1 — дословно и без сокращений, потому что это ключевая фраза для всего раздела:
**"Claude loads this metadata at startup and includes it in the system prompt. The description is
what Claude matches your request against when determining whether to trigger the Skill, so it must
say both what the Skill does and when to use it. This lightweight approach means you can install
many Skills without context penalty: until a Skill is triggered, only its name and description
occupy context."** Это прямой ответ на вопрос «что именно видит модель до решения о загрузке»:
**имя и описание — и больше ничего**. Не первая строка тела, не список файлов внутри, не то, что
скилл умеет делать «на самом деле» — только то, что написано в двух конкретных полях фронтматтера.

**Что расходится между двумя документами.** Claude Code-специфичная страница
(`code.claude.com/docs/en/skills.md`) не повторяет число «~100 токенов на скилл» — вместо этого
она описывает другой, более точный механизм: единый **«листинг» скиллов**, чей размер считается не
построчно на каждый скилл, а как **процент от контекстного окна модели целиком**. Дословно (раздел
«Skill descriptions are cut short», обращение 2026-09-27): **"Claude Code loads a listing of skill
names and descriptions into context so Claude knows what's available. The listing always contains
every skill name, but if you have many skills, Claude Code drops some descriptions to fit the
listing's character budget, which removes the keywords Claude needs to match your request. The
budget scales at 1% of the model's context window. When the listing overflows, Claude Code drops
descriptions starting with the skills you invoke least, so the skills you use most keep their full
text."** Это не противоречие, а **разная степень детализации одного и того же факта**: общий
стандарт даёт круглую оценку «по ~100 токенов на скилл» как порядок величины; продуктовая
документация Claude Code описывает, как это реализовано на практике — динамический общий бюджет,
который **режет по одному скиллу за раз**, начиная с наименее используемых, а не одинаково режет
всех. Я не нашёл в документации явного признания, что это буквально один и тот же механизм,
описанный на двух уровнях абстракции, или два независимо реализованных приближения — это стоит
пометить как несведённый пробел (см. §6), но для занятия разница не критична: оба говорят «дёшево
пока не выбран», просто у второго есть более точный механизм отказа при перегрузке.

Отдельно — **жёсткий потолок на одну запись**, не зависящий от общего бюджета: **"each entry's
combined text is capped at 1,536 characters regardless of budget"** (описание + `when_to_use`
вместе). Это Claude Code-специфичный предел листинга — не путать с лимитом самого поля `description`
как такового (см. §2.1, там другое число и другой источник).

**Численный пример для курса (иллюстрация, не измерение).** У курса 13 скиллов. По грубой оценке
«~100 токенов на скилл» это ≈1300 токенов на весь листинг при старте любой сессии — независимо от
того, какой из 13 реально понадобится. Это меньше 1% окна большинства моделей (для окна в 200k
токенов бюджет Claude Code — ≈2000 токенов), то есть переполнение и урезание при таком масштабе не
наступает. Порог урезания зависит от **суммарной** длины описаний, не от числа скиллов — и первыми
теряют текст именно те, что ещё никогда не срабатывали, то есть скиллы, которым урезание вредит
больше всего: они и так не доказали, что вызываются по смыслу, а теперь и описание неполное.

### 1.2. Тело — что именно происходит в момент срабатывания

Общий стандарт про тело: **"When you request something that matches a Skill's description, Claude
reads SKILL.md from the filesystem using bash. Only then does this content enter the context
window."** Это описание относится к API/VM-окружению, где Claude в буквальном смысле работает
через bash-команды в контейнере. Claude Code-специфичная документация **не** повторяет формулировку
«Claude выполняет `cat SKILL.md`» — вместо этого она описывает результат на уровне продукта:
**"When you or Claude invoke a skill, the rendered `SKILL.md` content enters the conversation as a
single message and stays there across later turns... Claude Code does not re-read the skill file on
later turns."** Это тот же уровень раскрытия («тело — только по срабатыванию»), но я не нашёл в
документации Claude Code прямого подтверждения, что механически это тот же приём «прочитать файл
через bash» — вывод по аналогии, не цитата (см. §6).

Важное практическое следствие именно из формулировки Claude Code, не общего стандарта:

- **Повторный вызов того же скилла без изменений** не добавляет вторую копию — Claude Code
  **"adds a short note that the skill is already loaded rather than a second copy of the
  content."**
- **Повторный вызов с другими аргументами или новым результатом динамической команды** —
  добавляет содержимое **заново, целиком**, а не диффом.
- **После автокомпакции** — Claude Code переприкрепляет **последний** вызов каждого скилла,
  сохраняя первые 5000 токенов каждого, с общим бюджетом на все переприкреплённые скиллы в 25 000
  токенов; при превышении бюджета более старые скиллы **выбрасываются целиком**, не частично.
  Дословно: **"Re-attached skills share a combined budget of 25,000 tokens. Claude Code fills this
  budget starting from the most recently invoked skill, so older skills can be dropped entirely
  after compaction if you have invoked many in one session."**

Практический вывод для занятия: тело скилла — это не «файл, который читается один раз при
триггере», а **сообщение, которое живёт в истории диалога** до конца сессии или до компакции —
инструкции внутри должны формулироваться как постоянно действующее правило («всегда делай X»), а не
как одноразовый шаг («сделай сейчас X»), потому что модель их физически не перечитывает.

### 1.3. Вложения — обещанный ноль, и что мешает ему быть настоящим нулём

Уровень 3 общего стандарта — файлы и скрипты внутри директории скилла, читаются только по ссылке из
`SKILL.md`. Дословно про масштаб: **"No practical limit on bundled content: Files don't consume
context until accessed, so Skills can include comprehensive API documentation, large datasets, or
extensive examples. There's no context penalty for bundled content that isn't used."** Единственное
техническое ограничение — не на размер, а на **глубину ссылок**: рекомендация Best Practices
(`platform.claude.com/.../best-practices`) — **"Keep references one level deep from SKILL.md"**,
потому что при вложенной ссылке (файл A ссылается на файл B, тот — на файл C) модель имеет тенденцию
читать не файл целиком, а превью через `head -100`, и теряет часть содержимого: **"Claude may
partially read files when they're referenced from other referenced files... resulting in
incomplete information."** Это не жёсткий лимит (система не запретит вложенность в три уровня), а
эмпирическая рекомендация — «ноль токенов, пока не открыто» остаётся верным даже при глубокой
вложенности, просто «открыто» на практике не значит «открыто целиком».

### 1.4. Где могут лежать скиллы, и что при совпадении имён

Официальная таблица уровней (`code.claude.com/docs/en/skills.md`, раздел «Where skills live»):

| Уровень | Путь | Загружается в |
|---|---|---|
| Enterprise | `.claude/skills/<name>/SKILL.md` в managed settings | у всех, кому организация раздала |
| Personal | `~/.claude/skills/<name>/SKILL.md` | во всех проектах на этой машине (не Cowork/cloud) |
| Project | `.claude/skills/<name>/SKILL.md` | в сессиях этого репозитория, если закоммичен — у всей команды |
| Nested | `<subdir>/.claude/skills/<name>/SKILL.md` | в сессиях, стартовавших в `<subdir>` или ниже |
| Additional dir | `.claude/skills/<name>/` в `--add-dir` | только в этой сессии |
| Plugin | `<plugin>/skills/<name>/SKILL.md` | где включён плагин, как `/plugin-name:skill-name` |
| claude.ai (synced) | скиллы, включённые в аккаунте | Cowork/cloud/терминал при входе тем же аккаунтом |

**Приоритет при совпадении имени** (та же страница, раздел «Resolve skills that share a name»):
enterprise > personal > project; любой локальный скилл побеждает **встроенный** (bundled) скилл, но
не его алиас (**"Your skill replaces the bundled command, but not its aliases. A project
code-review skill replaces /code-review, and the bundled alias /review never runs your skill"**);
скилл побеждает файл в `.claude/commands/`; скилл из корня репозитория и скилл из вложенной
директории **оба** загружаются — оба остаются доступны, просто вложенный получает уточнённое имя
(`/apps/web:deploy`); плагинный скилл всегда живёт под своим неймспейсом (`/plugin-name:skill`), поэтому
не конфликтует вообще; **скилл, синхронизированный из аккаунта claude.ai, при совпадении короткого
имени с чем угодно локальным — теряет короткое имя** и остаётся доступен только по полному
(`/anthropic-skills:<name>`).

Два имени зарезервированы жёстко и не грузятся вовсе при совпадении: `synced` (каталог для
синхронизации из аккаунта) и `anthropic-skills` (неймспейс синхронизированных скиллов) — скилл или
папка команд с таким именем **не загружается**, о чём при старте выводится уведомление.

**Изменения посреди сессии.** Claude Code следит за директориями скиллов и подхватывает правку
`SKILL.md` без перезапуска (кроме bare mode). Но если верхнеуровневая директория `.claude/skills/`
не существовала на момент старта сессии — за ней никто не следит, пока не выполнена команда
`/reload-skills`, и её нужно повторять после каждого следующего изменения там же. Для вложенной
поддиректории отдельная тонкость: скиллы в `<subdir>/.claude/skills/` **не** грузятся при старте
сессии, если сессия стартовала выше — они появляются **только после того**, как Claude впервые
читает или редактирует файл в этой поддиректории; чтобы получить их раньше, нужен явный `/add-dir
<subdir>` (с версии `v2.1.257`).

## 2. Контракт — что должно быть в файле

### 2.1. Обязательные поля — два документа расходятся буквально

Здесь два первоисточника **не согласуются на уровне формулировки**, и это стоит показать явно, а не
сгладить. Общий стандарт Agent Skills (`platform.claude.com/.../overview#skill-structure`)
формулирует это как требование: **"Required fields: name and description"**, с конкретными
правилами валидации:

- `name`: максимум 64 символа; только строчные буквы, цифры, дефисы; без XML-тегов; без
  зарезервированных слов «anthropic», «claude».
- `description`: непустое, максимум **1024** символа, без XML-тегов, должно описывать что делает и
  когда использовать.

А вот собственная страница Claude Code (`code.claude.com/docs/en/skills.md`, раздел «Frontmatter
reference») формулирует ровно противоположное по модальности: **"All fields are optional. Only
description is recommended so Claude knows when to use the skill."** Разница не косметическая: по
общему стандарту (тому, что валидируется при загрузке в claude.ai/API через `package_skill.py`)
отсутствие `name`/`description` — ошибка. В Claude Code — это допустимое, хотя и деградирующее,
состояние: оба поля **имеют дефолты** (`name` → имя директории, `description` → первая непустая
строка markdown-содержимого) и файл продолжает работать. Практический вывод: **два разных
контракта для двух разных путей распространения одного и того же файла** — то, что сойдёт с рук
локально в `.claude/skills/`, не пройдёт валидацию при выгрузке через Skills API/claude.ai
(см. §2.4 про совместимость наружу).

Полная таблица дополнительных полей Claude Code (все — необязательные, дословно из таблицы
фронтматтера, сверено по `code.claude.com/docs/en/skills.md`):

| Поле | Что делает |
|---|---|
| `when_to_use` | Дополнительный текст-триггер, добавляется к `description` в листинге, считается в тот же лимит 1536 символов |
| `argument-hint` | Подсказка в автокомплите, например `[issue-number]` |
| `arguments` | Именованные позиционные аргументы для подстановки `$name` |
| `disable-model-invocation` | `true` — только явный вызов `/name`; модель не увидит описание вовсе (см. §4.2) |
| `user-invocable` | `false` — только модель может вызвать; скрыт из `/`-меню |
| `allowed-tools` / `disallowed-tools` | Разрешить/убрать инструменты без запроса — **на один ход**, снимается при следующем сообщении |
| `model` / `effort` | Переопределение модели/уровня усилия на время действия скилла |
| `context: fork` + `agent` + `background` | Запуск в изолированном субагенте |
| `hooks` | Хуки, регистрируемые при вызове скилла, живут до конца сессии |
| `paths` | Glob-паттерны — скилл триггерится автоматически только при работе с подходящими файлами |
| `shell` | `bash` (по умолчанию) или `powershell` для инъекции команд |
| `metadata` | Свободный YAML для собственной тулинги; Claude Code не читает содержимое |
| `license` / `compatibility` | Поля стандарта Agent Skills для внешнего распространения; Claude Code принимает, но не действует по ним |

Булевы поля принимают `yes`/`no`/`on`/`off`/`1`/`0` в любом регистре в дополнение к `true`/`false`
— но **только с версии `v2.1.218`**, до неё распознавались лишь `true`/`false`.

Отдельно — то, что часто упускают: **неопознанное поле не вызывает ошибку**, оно просто
игнорируется: **"A field name must match the table exactly, hyphens included: Claude Code ignores
a field it doesn't recognize without reporting an error."** Опечатка в имени поля (`descripton`
вместо `description`) — это тихий отказ на уровне одного поля, а не всего файла: YAML распарсится
успешно, просто нужное поле не сработает.

### 2.2. Что будет, если фронтматтера нет вовсе — ровно случай 12 из 13 в этом проекте

Точная формулировка условия, при котором фронтматтер читается вообще: **"Claude Code reads the
frontmatter only when the opening --- is the file's first line. Otherwise it treats the whole
file, --- markers included, as skill content."** У 12 из 13 скиллов этого проекта файл начинается
сразу с `# заголовок` (проверено `head -5 .claude/skills/*/SKILL.md`, см.
`assets/captures/10-skills-frontmatter-head5.txt` / `11-skills-frontmatter-table.md`) — то есть у
них **нет фронтматтера физически**, не «фронтматтер есть, но без `description`».

В этом состоянии срабатывают дефолты, а не пустота: `name` → имя директории (`build-deck`,
`sync-library` и так далее); `description`, если не задан, — **"uses the first non-empty line of
the markdown content"** (`code.claude.com/docs/en/skills.md`, таблица полей, строка `description`).

Здесь стоит зафиксировать точный механизм, потому что он тоньше, чем «система подставляет имя файла
вместо описания» (расхожая, педагогически удобная формулировка): подставляется не имя, а **первая
непустая строка**. Для 12 скиллов курса это markdown-заголовок `# <имя скилла>` (у `build-deck` —
буквально `# build-deck`), потому что все 12 файлов по конвенции проекта начинаются с такого
заголовка. Прямо под ним, второй content-строкой, уже лежит нормальное человеческое предложение
(у `build-deck`: «Build/rebuild a PowerPoint (PPTX) presentation for a lecture using the
repo-first pipeline + visual loop + 3 QA agents.») — оно было бы неплохим триггером, если бы дефолт
смотрел на «первое предложение», а не буквально на «первую непустую строку». Итог совпадает с
интуитивным «описание = имя», но причина другая: не подстановка имени, а неверная строка —
совпадает с именем только из-за конвенции файла. Начни автор файл прямо с предложения, без
заголовка, — дефолт сработал бы содержательно; это стоит проверить как разбор кейса на занятии, а
не утверждать заголовочный вариант как единственно возможный.

Три следствия, которые стоит различать явно:

- **Скилл без фронтматтера не невидим.** Он загружается, попадает в листинг Уровня 1, доступен по
  явному имени команды (`/build-deck` сработает). Не сломан — недоступен для **автоматической**
  маршрутизации по смыслу, потому что нет содержательного текста для сопоставления.
- **Это не то же самое, что сломанный (невалидный) YAML.** Если `---` стоит первой строкой, но
  содержимое между `---` не парсится как YAML — это другой случай: **"If the YAML between the
  markers doesn't parse, the skill still loads with no fields set"** — конечный результат тот же
  (поля не заданы, дефолты в силе), но путь другой, и в этом случае `claude --debug` покажет
  конкретную ошибку разбора (см. §4.4); при полном отсутствии `---` на первой строке ошибки разбора
  не будет вообще, потому что парсер фронтматтера даже не запускается.
- **Единственный скилл курса с реальным фронтматтером — `pre-user-gate`** (`name: pre-user-gate`,
  `description: Pre-USER-GATE walkthrough — orchestrator self-review before presenting GATE to user.
  Reduces user feedback rounds.`) — рабочий положительный контрольный пример рядом с 12
  отрицательными, и оба типа реальны в одном и том же, уже существующем проекте.

### 2.3. Требования к `description` как к триггеру

Что делает описание рабочим — сходится в обоих документах. Общий стандарт формулирует состав так же,
как уже собрано в `section-2-skill.md`: должно содержать и что делает, и когда использовать. Best
Practices (`platform.claude.com/.../best-practices`) добавляет требование, которого не было явно
зафиксировано в предыдущей проверке — **грамматическое лицо**: **"Always write in third person. The
description is injected into the system prompt, and inconsistent point-of-view can cause discovery
problems. Good: 'Processes Excel files and generates reports.' Avoid: 'I can help you process Excel
files.' Avoid: 'You can use this to process Excel files.'"**

Три официально запрещённых формулировки, дословно, той же страницы — те самые, что уже используются
в совместном формировании раздела занятия (`section-2-skill.md` §A.6):

```yaml
description: Helps with documents
```
```yaml
description: Processes data
```
```yaml
description: Does stuff with files
```

Три официально одобренных примера рядом, для контраста (та же страница):

```yaml
description: Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction.
```
```yaml
description: Analyze Excel spreadsheets, create pivot tables, generate charts. Use when analyzing Excel files, spreadsheets, tabular data, or .xlsx files.
```
```yaml
description: Generate descriptive commit messages by analyzing git diffs. Use when the user asks for help writing commit messages or reviewing staged changes.
```

**Длина — два разных числа для двух разных целей, не путать.** Поле `description` само по себе, по
общему стандарту Agent Skills, — максимум **1024 символа** (§2.1). Отдельно от этого, в **листинге**
Claude Code, комбинация `description` + `when_to_use` **отображается** до **1536 символов**, после
чего обрезается независимо от общего бюджета листинга (§1.1). Первое — валидационный лимит самого
поля; второе — лимит того, что реально попадёт в контекст модели при показе списка. Официальный
совет учитывает именно второе число: **"Put the key use case first"** — потому что при превышении
1536 символов урезается **конец** текста, а не начало.

**Почему это решает выбор между двумя похожими скиллами.** Дословно, зачем вообще нужна точность
описания при масштабе: **"The description is critical for skill selection: Claude uses it to
choose the right Skill from potentially 100+ available Skills."** Это прямая мостовая связка к
находке Skill Shadowing из `stage-4-skill.md` §4в — механика та же самая: единственный сигнал для
выбора между похожими кандидатами — текст `description`, и чем он расплывчатее или чем сильнее
пересекается с описанием соседнего скилла, тем выше шанс, что модель выберет **не тот**, не
получив никакой ошибки. Живой пример дисциплины на масштабе, уже найденный в `stage-4-skill.md`
§4а, — проект `headcount` (172 скилла, имена вида `департамент:скилл`) — именно про то же самое:
не содержание тела, а пространство имён/описаний.

**`paths` — отдельный, не текстовый триггер (расширение только Claude Code, не часть общего
стандарта).** Поле `paths` ограничивает автоматическую активацию по glob-паттерну файлов, с которыми
работает Claude — например, скилл сработает только тогда, когда Claude уже читает или редактирует
`*.tsx`. Это не альтернатива `description`, а дополнительный фильтр: описание всё равно должно
существовать и быть точным, `paths` просто добавляет второе условие «и это ещё должно быть про эти
файлы».

### 2.4. Что ещё может лежать рядом с `SKILL.md`, и как на это ссылаться

Официальный пример структуры (`code.claude.com/docs/en/skills.md`, раздел «Add supporting files»):

```
my-skill/
├── SKILL.md (required - overview and navigation)
├── reference.md (detailed API docs - loaded when needed)
├── examples.md (usage examples - loaded when needed)
└── scripts/
    └── helper.py (utility script - executed, not loaded)
```

Ссылка — обычная markdown-ссылка из тела `SKILL.md`: `[reference.md](reference.md)`. Официальный
совет — **"Keep SKILL.md under 500 lines. Move detailed reference material to separate files."**
Это рекомендация, не техническое ограничение — жёсткого потолка на размер файла в найденной
документации нет.

**Совместимость наружу — какие поля переживают выгрузку из Claude Code.** Если скилл предстоит
загрузить в claude.ai/Skills API (а не только использовать локально), допустимы **только шесть**
полей из общего стандарта: **"Unexpected key(s) in SKILL.md frontmatter: argument-hint. Allowed
properties are: allowed-tools, compatibility, description, license, metadata, name."** Любое
Claude Code-специфичное поле (`paths`, `context`, `when_to_use`, `argument-hint` и другие) даёт
**жёсткую ошибку** при попытке выгрузки, а не тихо отбрасывается — обратная логика по сравнению с
тем, как сам Claude Code обходится с незнакомым полем внутри себя (§2.1).

### 2.5. Ограничения — размер, вложенность, исполнение кода

- **Размер файла** — нет документированного жёсткого потолка; только рекомендация «до 500 строк
  тела», с явной оговоркой, что вложенные файлы можно наращивать «без практического предела», пока
  они не читаются: **"There's no context penalty for bundled content that isn't used."**
- **Вложенность директорий скиллов** (не файлов ссылок внутри одного скилла, а самих `.claude/
  skills/` на разных уровнях каталогов) — поддерживается механически и осмысленно: монорепозиторий с
  `.claude/skills/deploy` в корне и `apps/web/.claude/skills/deploy` во вложенной директории даёт
  **оба** скилла одновременно, различаемых по уточнённому имени (§1.4). Это другое ограничение,
  чем «вложенность **ссылок** внутри одного скилла» (§1.3), где рекомендация — не глубже одного
  уровня.
- **Исполнение кода — разрешено, и это ключевое отличие Claude Code от остальных поверхностей.**
  Официальное сравнение сред выполнения (`platform.claude.com/.../overview#runtime-environment-
  constraints`), дословно по Claude API: **"No network access: Skills cannot make external API
  calls or access the internet. No runtime package installation."** И дословно по Claude Code,
  прямо в контрасте: **"Full network access: Skills have the same network access as any other
  program on the user's computer."** Это не сторонний вывод из исследований безопасности (тот
  разбор уже есть в `stage-4-skill.md`) — это прямое официальное продуктовое описание среды
  исполнения: скрипт, вызванный из скилла в Claude Code, работает с теми же правами, что и любая
  bash-команда в этой же сессии, без отдельной песочницы конкретно для скиллов.
- **Инъекция динамического контекста** (`` !`команда` `` в теле скилла) — отдельный, более узкий
  канал исполнения: команда проверяется против правил `permissions` **до** рендера («Injected
  commands never prompt for permission while the skill renders. Claude Code checks each one against
  your permission rules first»), выполняется с тем же 2-минутным таймаутом, что и обычный вызов
  Bash-инструмента, и ненулевой код возврата **прерывает весь вызов скилла** — с исключением для
  `grep`/`find`/`diff`, у которых код `1` не считается ошибкой (только `2+`).

## 3. Как пишется — на примере `deploy/SKILL.md`, наивно против рабочего

Разбирается тот же реальный файл, что уже используется в разделе занятия
(`assets/captures/30-code-deploy-SKILL.md.txt`, `section-2-skill.md` §A.7):

```markdown
---
name: deploy
description: Деплоит лендинг signup-landing на прод — сборка, smoke-тест формы, публикация,
  проверка прод-URL. Используй, когда пользователь просит задеплоить, выкатить или опубликовать
  сайт — не для обычных правок кода без деплоя.
---

# deploy

1. Собрать: `npm run build` (код выхода должен быть 0).
2. Прогнать smoke-тест формы: `npx playwright test` (должен быть зелёным).
3. Опубликовать: `wrangler pages deploy dist --project-name signup-landing`.
4. Открыть прод-URL, вручную отправить форму с валидными данными — заявка должна дойти.
5. Записать в `.tasks/active/YYYY-MM-DD-описание.md`, что задеплоено, когда и какой командой.
```

### 3.1. Фронтматтер — три наивных варианта и что каждый ломает

**Наивный вариант 1 — фронтматтера нет вовсе.** Файл начинается прямо с `# deploy`. По правилу §2.2
это не ошибка, а тихая деградация: `description` становится строкой `# deploy` — то есть буквально
дублирует имя, никакой информации о том, когда скилл нужен, не попадает в листинг. Ломается ровно
то, ради чего скилл заводился: автоматическое срабатывание по смыслу запроса «задеплой сайт»
становится невозможным, при этом явный `/deploy` продолжает работать.

**Наивный вариант 2 — описание есть, но по официальному списку антипаттернов.** `description:
Помогает с деплоем` — практически буквальный перевод запрещённого **"Helps with documents"** из
§2.3. Формально поле не пустое, фронтматтер валиден, скилл виден в листинге с содержательным на
первый взгляд текстом — но триггер не сообщает **когда** использовать (что отличает «правку вёрстки»
от «выкатки сайта») и не called out явно случаи, когда скилл **не** нужен. Результат — тот самый
класс проблемы, который `stage-4-skill.md` §6 (слой 1) документирует цифрами: скилл, который
выглядит релевантным чаще, чем нужно, срабатывает там, где не должен.

**Рабочий вариант — три части, third person, порядок «что → когда → когда не».** Реальное описание
курса: «Деплоит лендинг signup-landing на прод — сборка, smoke-тест формы, публикация, проверка
прод-URL. Используй, когда пользователь просит задеплоить, выкатить или опубликовать сайт — не для
обычных правок кода без деплоя.» Первое предложение — что делает (третье лицо, без «я»/«вы»,
соответствует официальному правилу из §2.3); второе — явный триггер плюс явное «не для…», третья
часть из § A.6 раздела занятия, которую зал почти никогда не называет сам.

### 3.2. Тело — что сломается при рецепте без конкретики

**Наивный вариант — общая инструкция без команд проекта.** «Собрать проект, прогнать тесты,
опубликовать, проверить, что всё работает» — синтаксически валидный markdown, скилл сработает
(описание триггернёт его), но тело не сообщает **какой именно** командой собирать (`npm run build`?
`vite build`? `make`?), какой именно smoke-тест запускать, на какой именно хостинг публиковать.
Модель либо угадывает по контексту проекта каждый раз заново (то есть скилл не экономит ничего —
задача угадывания команд просто переехала из файла инструкций в тело скилла), либо использует
устаревшую команду, если проект успел смениться. Официальный принцип, который это объясняет прямо
(`code.claude.com/docs/en/skills.md`, раздел «Types of skill content»): **"Keep the body itself
concise... State what to do rather than narrating how or why."** — а «что делать» здесь означает
конкретную команду, не общее описание намерения.

**Рабочий вариант — пять шагов, каждый с литеральной командой этого конкретного проекта.**
`npm run build`, `npx playwright test`, `wrangler pages deploy dist --project-name signup-landing` —
не абстракции «собрать»/«протестировать»/«опубликовать», а команды, которые реально работают в этом
репозитории и больше нигде. Официальное правило про избыточные альтернативы (`best-practices`,
раздел «Avoid offering too many options») подтверждает тот же принцип с другой стороны: **"Don't
present multiple approaches unless necessary"** — вместо «можно опубликовать через wrangler, или
через netlify cli, или руками» скилл называет ровно один способ, тот, что реально используется в
проекте.

### 3.3. Процедура, которая нужна каждую сессию, — механически не выигрывает от превращения в скилл

Это не повторение вывода `section-2-skill.md` §A.5/A.9 («не скилл, а строка в файле инструкций»), а
его механическое обоснование через факты этого документа. Уровень 1 (§1.1) платится **на каждом
ходу, независимо от того, вызывается ли скилл** — дословно из раздела «Find unused skills»:
**"Every skill in the skill listing adds to your context on every turn, whether or not Claude ever
uses it."** Если процедура нужна в каждой сессии — её тело (Уровень 2) в любом случае будет
загружаться почти всегда, то есть скилл не даёт выигрыша ровно там, где выигрыш обещан (тело — не
каждую сессию), а добавляет ровно то, чего не даёт файл инструкций: **шаг угадывания**, сработает
описание или нет. Файл инструкций для действительно всегда нужной процедуры платит тот же налог
на тело, но без риска, что описание не совпадёт с запросом.

## 4. Как отлаживается — «почему скилл не сработал»

### 4.1. Виден ли скилл вообще — `/skills`

Официальный первый шаг диагностики (`debug-your-config.md`, таблица команд): **"`/skills`: Available
skills from project, user, and plugin sources."** Панель показывает project/personal/plugin
скиллы; синхронизированные из claude.ai группируются отдельно, под подписью `claude.ai sync`; для
скиллов, у которых через `skillOverrides` изменена видимость, панель показывает состояние
(`on`/`name-only`/`user-only` — Claude Code называет это `user-only` в интерфейсе — /`off`; `off`
скрывает скилл из панели вовсе). Панель — **не** то же самое, что `/context` (§4.3): `/context`
показывает то, что реально попало в контекст этой сессии, `/skills` — список того, что вообще
доступно, независимо от того, был ли хоть один скилл вызван.

Первая строка из таблицы «Check common causes» (`debug-your-config.md`), дословно: **"Skill
doesn't appear in `/skills`" → "Skill file is at `.claude/skills/name.md` instead of in a
folder" → "Use a folder with SKILL.md inside: `.claude/skills/name/SKILL.md`."** Это не про
содержимое файла — это про то, что модель попыталась исполнить контракт «одна папка — один
`SKILL.md`» и не нашла его в файле, лежащем прямо в `.claude/skills/`.

### 4.2. Виден, но не срабатывает автоматически

Дословный официальный порядок диагностики (`code.claude.com/docs/en/skills.md`, раздел «Skill not
triggering»):

1. **Check the description includes keywords users would naturally say**
2. **Verify the skill appears in `What skills are available?`** — то есть задать Claude сам этот
   вопрос текстом и посмотреть, что он ответит про доступные скиллы
3. **Try rephrasing your request to match the description more closely**
4. **Invoke it directly with `/skill-name` if the skill is user-invocable**

Четвёртый пункт — диагностически самый ценный: если явный вызов `/deploy` работает, а «задеплой
сайт» текстом — не срабатывает, проблема **точно** в `description`, не в теле файла, не в его
расположении, не в правах. Отдельно — из той же таблицы «Check common causes»: **"Skill appears in
`/skills` but Claude never invokes it" → "Skill has `disable-model-invocation: true` in its
frontmatter, or its description doesn't match how you phrase the request" → "Check the badge in
`/skills`: a 'user-only' label means Claude won't trigger it on its own."** Бейдж `user-only` в
панели — прямой, видимый признак первой из двух причин, не требующий чтения самого файла.

**Обратная проблема — срабатывает слишком часто.** Официальный совет короче, но зафиксирован
отдельно: сузить описание, либо явно поставить `disable-model-invocation: true`, если автоматический
запуск вообще не нужен. Это ровно та вторая, «негативная» проверка, которая уже есть в разделе
занятия (`section-2-skill.md` §A.7/B.6 — «попросить починить мелкий баг в вёрстке, скилл открываться
не должен»).

### 4.3. Загрузился ли он в **этой конкретной** сессии — `/context`, `/doctor`, `/skill-doctor`

`/context` показывает раздел Skills — размер листинга **после** применения бюджета урезания (§1.1),
то есть то число, которое реально видит модель, а не сумму полных описаний: **"The Skills row in
`/context` reports the size of the listing after the budget is applied, so it matches what the
model receives. Before v2.1.196, the row counted the full text of every description and could show
a value several times larger than the configured budget."**

`/doctor` даёт оценку контекстной стоимости листинга и называет крупнейших «вкладчиков» — подходит,
когда вопрос не «сработал ли конкретный скилл», а «сколько контекста вообще уходит на листинг».

`/skill-doctor` (`v2.1.252`+) — отдельный отчёт про использование: **"see what each of your skills
costs and how often it gets used, so you can decide which ones to turn off... flags skills in the
listing that have never been invoked and says where to turn them off."** Прямой инструмент против
shadowing из `stage-4-skill.md` §4в — не абстрактный совет «не ставьте скиллы про запас», а
конкретная команда, показывающая, что не вызывалось никогда и сколько это стоит. Не работает через
Remote Control — только в терминале той машины, где идёт сессия.

### 4.4. Пять типовых причин — с явной пометкой «тихо» или «не тихо»

| Причина | Что происходит | Тихо? |
|---|---|---|
| Нет фронтматтера | Дефолты (§2.2): `description` = первая непустая строка тела, обычно заголовок-дубликат имени | Да — ни ошибки, ни лога; скилл просто не матчится по смыслу |
| Описание не описывает условие | Главная официальная причина несрабатывания (§4.2, п.1) | Да — модель не выбирает скилл, сигнала об этом нигде нет |
| Конфликт имён — **точное** совпадение | Разрешается детерминированно по приоритету (§1.4); при вложенности оба доступны под уточнённым именем | Нет — правило задокументировано и предсказуемо |
| Конфликт — **похожее** описание у соседа (shadowing) | Модель молча выбирает не тот из похожих; лога нет, только `/skill-doctor` покажет частоту вызова | Да, тише всех строк — здесь даже не «не сработал», сработал другой |
| Не то место в файловой системе | `.claude/skills/name.md` вместо папки — не появляется в `/skills`; вложенный скилл ждёт первого касания файла в поддиректории | Отчасти — проверяется прямо в `/skills` |
| Опечатка в имени каталога | Влияет только на ручной `/имя` (имя = имя каталога); не блокирует авто-срабатывание — кроме совпадения с `synced`/`anthropic-skills` | Второй случай — да, полностью тихо |

Последняя строка стоит отдельного комментария: интуиция «опечатался в имени папки — скилл не будет
виден» справедлива только в редком случае совпадения с зарезервированным именем; в общем случае
опечатка портит лишь ручной вызов, не автосрабатывание — за него отвечает `description`, не имя.

**Шестая причина, не входившая в исходный список задания, но зафиксированная официально** —
малформированный YAML при `---` на первой строке (§2.2): скилл загружается с пустыми полями молча,
`claude --debug` покажет ошибку разбора.

### 4.5. Штатные средства — что реально есть, а что нет

| Средство | Что показывает | Версия |
|---|---|---|
| `/skills` | Список доступных скиллов, источник, состояние видимости | — |
| `/context` | Размер раздела Skills **после** урезания листинга | точное число — с `v2.1.196` |
| `/doctor` | Оценка контекстной стоимости листинга + крупнейшие вкладчики | — |
| `/skill-doctor` | Использование и стоимость по каждому скиллу, флаг «никогда не вызывался» | `v2.1.252`+ |
| `claude --debug` | Ошибка разбора YAML во фронтматтере, попадает в лог | — |
| `claude plugin validate <dir>` | Находит `SKILL.md`, у которых фронтматтер не парсится, без живой сессии | `v2.1.233`+ |
| `claude --safe-mode` | Сессия без всех кастомизаций, включая скиллы, — если проблема исчезает, причина в одном из отключённых слоёв | — |
| Прямой вопрос «What skills are available?» | Позволяет увидеть, что Claude сам знает о доступных скиллах, без чтения панели | — |
| `claude plugin eval` с грейдером `tool_used: Skill` | Измерить частоту срабатывания скилла на наборе реалистичных запросов, не по одному вручную | — |

Отдельно стоит официальный совет из общей документации Best Practices, применимый до того, как
скилл вообще написан: **«создавайте оценки (evaluations) до объёмной документации»** — сначала
прогнать задачу без скилла и зафиксировать, что конкретно не получается, затем написать минимум
инструкций, закрывающий именно эти провалы, и только потом проверять на трёх и более сценариях. Это
формализованная версия «двух проверок» из `section-2-skill.md` §A.7 (позитивная — срабатывает,
негативная — не срабатывает там, где не должен), просто заранее, а не постфактум.

### 4.6. Пример отладочной последовательности — 4 шага

1. **`/skills`** — скилл вообще в списке? Если нет — причина на уровне файловой системы (файл
   вместо папки, зарезервированное имя, скилл лежит не там, где сессия его ищет) — не читаем тело
   файла вообще, сразу проверяем путь.
2. **Скилл в списке, но не срабатывает на естественный запрос** — попробовать явный `/deploy`.
   Сработал явный вызов, но не сработал текстовый запрос — проблема **точно** в `description`, не в
   остальном файле. Сузить или расширить формулировку по официальному чек-листу (§4.2).
3. **Не сработал даже явный вызов** — подозревать фронтматтер целиком: `claude --debug` и искать
   строку об ошибке разбора YAML, либо, без живой сессии, `claude plugin validate .claude/skills`
   на весь каталог сразу.
4. **Сработал не тот скилл из нескольких похожих** — не хук в описании конкретного скилла, а вопрос
   на уровне всей библиотеки: `/skill-doctor`, посмотреть частоту вызова каждого кандидата,
   при подозрении на shadowing — временно поставить конкурента в `skillOverrides: "off"` и повторить
   тот же запрос, чтобы увидеть, действительно ли скилл, который «должен был сработать», рабочий
   сам по себе.

## 6. Чего я не смог подтвердить

- **Буквальный механизм получения тела скилла в Claude Code.** Общий стандарт Agent Skills описывает
  это как «Claude выполняет `cat SKILL.md` через bash» — для API/VM-окружения. Собственная
  документация Claude Code говорит только о результате («rendered content enters the conversation
  as a single message»), не называя механизм явно. Совпадение уровней раскрытия подтверждено,
  совпадение реализации — нет; это вывод по аналогии, не цитата (см. §1.2).
- **Соотношение двух чисел про Уровень 1.** «~100 токенов на скилл» (общий стандарт) и «бюджет
  листинга = 1% контекстного окна модели целиком, с приоритетным урезанием» (Claude Code) — не
  нашёл прямого официального признания, что это одно и то же правило на разных уровнях детализации,
  а не два похожих, но не идентичных механизма (§1.1).
- **Буквальная обработка первой непустой строки как дефолтного описания при отсутствии
  фронтматтера.** Не нашёл явного указания, обрезается ли ведущий `#`/markdown-разметка заголовка
  при подстановке в качестве `description`, или строка попадает в листинг буквально вместе с
  синтаксисом (§2.2). Не проверено живым запуском — тот же класс ограничения, что и во всех
  позициях общего `TODO-capture.md`: для точного ответа нужна реальная интерактивная сессия с
  файлом без фронтматтера и последующий `/skills`.
- **Живой вид панели `/skills`, `/skill-doctor`, строки `--debug` про парсинг YAML.** Три позиции
  из §5 (6, 7, 8) требуют досъёмки на реальной машине с установленным `claude` — этот ран, как и все
  предыдущие для данного семинара, ограничен `Bash`-инструментом без интерактивного REPL.
- **Версия продукта, для которой актуальны все цитаты.** Как и в `mechanics-3-khuk.md`, ни одна
  страница не показывает номер версии или дату «обновлено» напрямую; внутренние ссылки на конкретные
  версии (`≥v2.1.191` … `≥v2.1.281`) дают только нижнюю границу актуальности каждого отдельного
  факта, не единую версию продукта на день занятия — перед показом стоит свериться с `claude
  --version` на машине, где пойдёт демонстрация.
- **Правило «одна ссылка вглубь» (§1.3) как жёсткий лимит.** Подтверждена только как рекомендация
  Best Practices с объяснением механизма деградации (`head -100` при глубокой вложенности) — не
  нашёл, существует ли техническое ограничение количества уровней вложенности ссылок как таковое,
  или деградация чисто эмпирическая и потенциально зависит от модели/версии.
