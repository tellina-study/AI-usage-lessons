# The cost of structure — on our own doc/adr/

## Assertion

Four costs of structure — not general categories but concrete files in our own `doc/adr/`: a generated table of contents, a redundant record, an orphaned rationale and a manual cross-check.

## Visual

- **Staleness.** `README.md` was assembled by the `adr generate toc` command in October. Records 0188 through 0200 never made it in, yet it looks complete. An agent handed that table of contents will not see the November decision. In one flat file there was nothing to diverge — there is a single source of truth there.
- **Duplication.** Someone did not find 0187 and set up 0193, "Anti-spam thresholds", about the same honeypot. Both records are `Accepted`, and there is no link between them: the format does not forbid two decisions about the same thing, and the tool does not look for similar ones.
- **No cascading delete.** The September decision 0031 was superseded: `adr new -s 31 …` changed its status and placed the links. But record 0187 is justified by the phrase "a captcha is banned by decision 31" — and it stayed `Accepted`, even though its rationale no longer holds. The tool fixes links, but not the meaning of a derived record.
- **Maintenance burden.** Two hundred decisions — two hundred files: a number, a date, a status, links in both directions, a regenerated table of contents. Part of that is done by `adr new` and `adr link`. Noticing that a new record is about the same thing as 0187 is done by nobody.

**The honest bottom line.** For a human it is exactly this burden that usually kills a wiki — an observation, not a measurement. For an agent, editing a dozen and a half files in a single pass costs almost nothing, and the same scheme may pay off where it does not pay off for a human — but that is an argument from mechanism, not verified experimentally. At the scale and connectedness of our example there is a win, but it is neither automatic nor free: a trade-off, not an upgrade by default.
