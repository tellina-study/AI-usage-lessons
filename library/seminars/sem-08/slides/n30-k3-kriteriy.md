# Когда решение обязано быть кодом

## Assertion

Критерий решения можно выразить условием над структурированным значением — решение обязано быть кодом. Критерий принципиально не формализуется как условие — здесь модель в точке решения допустима.

## Visual

| Код в точке решения **обязателен** | Модель в точке решения **допустима** |
|---|---|
| критерий выражается как условие над уже структурированным значением — сумма, дата, принадлежность готовому списку | критерий принципиально не формализуется как условие — оценка тона, намерения, нестандартной формулировки без явного числового порога |
| граница условия (равно порогу, точно на дате, точно в списке) — то, что обязаны проверить прогоном до публикации | граница здесь не существует в том же смысле: нет единственного числа, которое решение либо пересекает, либо нет |
| модель перед этим шагом законна — но только в роли извлечения значения, не в роли сравнения его с порогом | модель и есть сам шаг понимания — переносить его в код было бы равносильно изобретением второй модели внутри оркестратора |

> **Третья строка оси закрыта.** «В промте написано «не возвращай больше суммы X»» — выглядело рабочим решением месяц. Чем оказалось: решение вероятностное — модель обходит правило в измеренной доле прогонов, 3 из 51, все три на границе условия. Алгоритмический гейт — никогда: 0 из 51, включая ту же границу.

## Speaker notes

Критерий третьего кейса, прямой формой, без эссе: когда решение обязано быть кодом, а когда модель в самой точке решения допустима.

Обязано быть кодом, когда критерий решения можно выразить как условие над уже структурированным значением — суммой, датой, принадлежностью готовому списку. Это ровно наш случай: сумма возврата уже извлечена в число, и сравнить число с порогом — задача условия, не задача понимания текста. И отдельно стоит запомнить практическое следствие: граница этого условия — ровно на пороге, ровно на дате, ровно в списке — то, что обязаны проверить прогоном до публикации процесса, не предположить по тексту правила. Именно так нашлась наша ошибка: не в середине диапазона — на границе.

Модель в самой точке решения допустима только там, где критерий принципиально не формализуется как условие: оценка тона письма, намерения человека, нестандартной формулировки без явного числового порога. Там нет единственного числа, которое решение либо пересекает, либо нет, — и переносить такую оценку в код означало бы изобретать внутри оркестратора вторую модель, только хуже обученную.

И важная оговорка, которая закрывает нюансы предыдущего экрана: модель перед этим шагом вполне законна — но только в роли извлечения значения из текста, не в роли сравнения этого значения с порогом. Понять заявку и достать из неё сумму — задача понимания. Сравнить сумму с порогом — задача условия. Это две разные задачи, и ошибка эксперимента началась ровно там, где их перепутали.

Третья строка нашей оси, с которой открывалось занятие: «в промте написано «не возвращай больше суммы X»» — месяц это выглядело рабочим решением. Чем оказалось: решением вероятностным — модель обходит правило в измеренной доле прогонов, 3 ошибки из 51, и все три ровно на границе условия. Алгоритмический гейт на той же границе — ни разу, 0 из 51. Разница между «написано в промте» и «гейт — архитектура, не текст» — это и есть разница, которую сегодня измерили, не предположили.
