# diff-reviewer: файл и вызов

## Assertion

Ревьюер видит только diff и критерии приёмки — не рассуждения, которые привели к изменению.

## Visual

Левая колонка — блок кода `.claude/agents/diff-reviewer.md` целиком:

```markdown
---
name: diff-reviewer
description: Независимый ревьюер diff'ов. Видит только сам diff и критерии приёмки, не рассуждения
  автора. Используй перед мержем любого нетривиального изменения. НЕ для методической критики
  текста — это отдельная роль.
tools: Read, Grep, Glob
---

# diff-reviewer

Ты не правишь код сам — только находишь проблемы. Начни ответ строкой:
`VERDICT: PASS | BLOCK`

Затем: что проверено (конкретно — какие файлы прочитаны), находки (что не так, где, почему важно).
Пустой список находок — валидный PASS.
```

Правая колонка — фрагмент реального diff, на который вызывается ревьюер:

```diff
diff --git a/src/validate.js b/src/validate.js
index b2a06f5..4fbfb4b 100644
--- a/src/validate.js
+++ b/src/validate.js
@@ -6,3 +6,9 @@ export function isFormValid(form) {
 export function showValidationErrors(form) {
   form.reportValidity();
 }
+
+// email regex дополнен: раньше пропускал "a@b" без точки в домене (issue: заказчик
+// прислал тестовую заявку с опечаткой в домене, форма её приняла).
+export function isValidEmail(value) {
+  return /^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(value);
+}
```

Нижняя панель (плейсхолдер, ждёт досъёмки) — ответ `diff-reviewer` на этот diff, начинается строкой `VERDICT: PASS` или `VERDICT: BLOCK`, ссылается только на сам diff, не на историю чата, в которой изменение создавалось.

## Speaker notes

Файл `.claude/agents/diff-reviewer.md` — обычный markdown с YAML-frontmatter, источник — та же документация Claude Code про субагентов. Поле `name` — идентификатор. Поле `description` — это логика маршрутизации, а не документация для человека: по этому полю Claude решает, делегировать ли задачу автоматически, поэтому формулировка там должна явно называть, для чего субагент нужен и для чего не нужен — здесь прямо написано «не для методической критики текста, это отдельная роль». Опционально указываются `tools` и `model`.

Обратите внимание на строку `tools: Read, Grep, Glob` — явное ограничение без `Write` и `Edit`. Это механическая, а не словесная защита от ситуации «критик случайно всё исправил сам вместо того, чтобы найти проблему и остановиться». Из тринадцати живых субагентов этого же курса этим полем почти никто не пользуется — редкая деталь, но именно поэтому наглядная: там, где роль по своей природе обязана только находить, а не чинить, поле `tools` можно и нужно сузить руками.

Сам субагент начинает ответ строго со строки `VERDICT: PASS` или `VERDICT: BLOCK`, дальше — раздел «что проверено» с конкретными файлами, которые реально прочитаны, и раздел «находки». Пустой список находок — валидный `PASS`, это не провал проверки, а нормальный результат.

Справа — реальный фрагмент diff по нашему сайту: ужесточение регулярного выражения для email в `src/validate.js`, после того как заказчик прислал тестовую заявку с опечаткой в домене, а форма её приняла. Именно этот diff и вызывается ревьюером отдельным запросом — не в том диалоге, где правка создавалась.

Нижняя панель — уже сам ответ `diff-reviewer` на этот diff. Мы вернёмся к ней, как только запись реальной сессии будет готова: содержимое ответа принципиально не сочиняется заранее, потому что весь смысл проверки в том, что вердикт формулирует изолированный контекст, а не мы сами по памяти о том, что он мог бы ответить. Пока панель остаётся честным плейсхолдером, а не подставным текстом.
