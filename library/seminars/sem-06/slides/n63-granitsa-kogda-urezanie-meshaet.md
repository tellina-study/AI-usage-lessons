# Где урезание начинает мешать работе роли

## Assertion

Урезание прав начинает мешать работе, когда роли по её же работе нужен инструмент, который у неё отняли по шаблону «урезать всегда». Граница урезания идёт от задачи роли, не от того, что сработало у соседней.

## Visual

| Роль | Нужно по работе → права | Результат |
|---|---|---|
| `code-reviewer` (официальный пример документации) | читать и искать, не менять → `Read, Grep, Glob, Bash`, без `Edit`/`Write` | верно — ревью не чинит код само |
| `debugger` (официальный пример документации) | чинить баг, то есть менять код → тот же набор плюс `Edit` возвращён обратно | без `Edit` не может сделать то, ради чего её завели |

> **Узкий список инструментов диф-ревьюера из этого кейса был верным выбором для роли, которая только находит проблему. Тем же списком — без `Edit` — не хватит роли, чья работа эту проблему чинить.**

## Speaker notes

Третья граница, и она о другом: роль нужна, права у неё урезаны правильным по форме способом, и урезаны не на то.

Документация харнесса показывает это двумя примерами. `code-reviewer` читает и ищет, набор без `Edit` и `Write` — верно, ревью не чинит код за автора. `debugger` — та же база плюс `Edit`, возвращённый обратно, дословно «потому что починка бага требует правки кода». Одна логика урезания, две работы, два разных правильных ответа.

Мост к кейсу. Список `Read, Grep, Glob`, который мы собрали для диф-ревьюера, был верным ровно потому, что его работа — находить проблему. Скопируйте тот же список роли, чья работа эту проблему чинить, и получите `debugger` без `Edit`: она физически не сделает того, ради чего её завели.

Этим ступень закрывается. Весь путь работы целиком — от задачи до показа заказчику — остаётся на отдельный разговор.

Если спросят, как узнать заранее, в какую границу попадает новая роль: спросите так — «что этой роли физически придётся сделать, чтобы выполнить свою работу»; если ответ требует инструмента, которого нет в списке, граница урезания проведена не там.

Если спросят, не противоречит ли это тому, что мы собрали в этом же кейсе: нет — там урезание было верным, роль именно находит проблему. Здесь показан случай, где тот же приём, скопированный без проверки задачи, ломает другую роль.

Если спросят, как это сочетается со счётом «ноль из четырнадцати»: счёт говорит, что урезание почти никто не делает; эта граница говорит, что сделанное не глядя тоже ломается. Обе половины указывают в одно место — права урезают от задачи роли, по одной штуке, с проверкой запуском.

Если спросят про `Bash` у `code-reviewer`: он там есть и в примере документации, и это не противоречие — запустить тест и прочитать вывод ревьюер может, переписать файл чужими руками `Bash` ему не даёт по той же логике списка.
