## Кейс 1 — Трансформация и размножение запроса

| Элемент | Содержание |
|---|---|
| Дивайдер-проблема | Запрос пользователя и формулировка в базе расходятся словами — неясно, какой из способов «поправить вопрос перед поиском» не сделает хуже случай, который уже работал (не называет решение). |
| Сцена-человек-цена | Инженер поддержки включает multi-query + RRF-фьюжн на внутренней базе знаний, чтобы «поднять recall»; метрика на тесте растёт, рекомендация подписана на прод — через неделю тикеты показывают, что нужный документ чаще не попадает в финальную тройку: реранкер и обрезка выдачи съели выигрыш, видимый только на промежуточном recall. Цена — время на диагностику регресса, который «не должен был случиться» по отчёту. |
| Ось сравнения | Одиночный гибридный запрос без трансформации (baseline С10) vs одна из техник трансформации (rewriting/multi-query/HyDE/RAG-Fusion/step-back/decomposition), с явной привязкой к типу запроса (расплывчатый/точный, одношаговый/составной). |
| Разворот П1 | «Добавить ИИ-обработку вопроса перед поиском» выглядит как действие, которое может только помочь. Документированный случай показывает обратное: на хорошо сформулированном, предметно-специфичном запросе та же техника снижает итоговое качество, а промежуточный рост recall маскирует это на этапе тестирования. |
| Граница А7 | Нужно — вопрос расплывчатый/концептуальный, домен с разговорной лексикой (TREC-COVID-тип). Не нужно — вопрос уже написан языком предметной области, с точными сущностями/числами (FiQA-тип, HyDE на персональных данных) — только проверка, что индекс (не запрос) говорит на том же языке, мост к Anthropic Contextual Retrieval. |
| Источник реального случая | arXiv:2603.02153, «Scaling Retrieval Augmented Generation with RAG Fusion: Lessons from an Industry Deployment» — https://arxiv.org/abs/2603.02153 (промышленное развёртывание, анонимизированная enterprise-база знаний). |
| [ЗАМЕР НЕ ГОТОВ] | Собственный прогон трансформации запроса на текстовом стенде С10 (SberQuAD) — не поставлен. Числа Hit@10 0,51→0,48, nDCG FiQA −9,0%/TREC-COVID +5,1% — сторонние измерения, не этого стенда. |

## Кейс 2 — Продвинутый чанкинг

| Элемент | Содержание |
|---|---|
| Дивайдер-проблема | База выросла, резка по предложениям (приём С10) больше не рвёт ответы — но ответы стали расплывчатыми, модель путает соседние разделы регламента: устранили один дефект, получили другой. |
| Сцена-человек-цена | Команда ИИ-ассистента «Марк» по охране труда: на MVP (десятки документов) наивная резка по символам компенсировалась небольшим размером базы; на масштабе в тысячи документов эксперты по охране труда начали «хвататься за голову» от ответов бота — похожие по смыслу, но разные по юридической сути инструкции перекрывали друг друга. Переход к иерархическим чанкам (чанк «знает» заголовок раздела) дал первый качественный скачок. |
| Ось сравнения | Плоская резка по предложениям (baseline С10, один уровень, без контекста куска) vs приём, закрывающий именно потерю контекста — иерархический/parent-document retrieval или Anthropic contextual retrieval; семантический чанкинг — отдельный такт на оси «умнее — не значит лучше». |
| Разворот П1 | Интуиция «чем умнее алгоритм режет текст, тем лучше результат» — семантический чанкинг звучит умнее фиксированной нарезки. Опровержение измеренное: самый «умный» на бумаге метод (семантический чанкинг) в независимых замерах проигрывает самому простому (Vectara/arXiv 2410.13070); у реального случая «Марк» качественный скачок дал не самый умный метод, а иерархия, и лишь на финальном этапе семантическое окно обогнало её — ценой просевшего Precision. |
| Граница А7 | Нужно — длинные структурированные документы с осмысленной иерархией разделов (регламенты, контракты), где есть бюджет на два синхронных индекса (дети+родители). Не нужно — маленькая база, плоские FAQ без вложенной структуры: второй индекс не окупается; семантический чанкинг не брать по умолчанию «потому что умнее» — нужна дорогая настройка порога под свой корпус. |
| Источник реального случая | Habr, `asuleykin`, «Из «песочницы» в Production: как мы масштабировали RAG-систему для эксперта по охране труда», 2026-02-17, https://habr.com/ru/articles/1000424/ — LLM-Score 0,72→0,92 по этапам (фиксы промптов → исправление нарезки → иерархия → тюнинг → семантическое окно). |
| [ЗАМЕР НЕ ГОТОВ] | Собственный прогон parent-document/contextual retrieval на SberQuAD/русском корпусе — не поставлен (С10 измерил только v1 vs v2 по предложениям, без иерархии). LLM-Score 0,72→0,92 — self-reported командой «Марк», не независимый аудит. |

## Кейс 3 — Классификация вопроса → динамические веса RRF-гибрида

| Элемент | Содержание |
|---|---|
| Дивайдер-проблема | Семинар 10 дал один рецепт на все вопросы — гибрид с равными весами + реранкер. Кто (или что) должен решать, что точный вопрос и смысловой вопрос заслуживают разного веса смешивания? |
| Сцена-человек-цена | Инженер поддержки (аналог Ольги) подаёт в тот же стенд два вопроса подряд — «какой код ошибки у отказа клапана 14С-09» (точный ID) и «почему клапан иногда отказывает после недели простоя» (смысловой). Фиксированный гибрид с равным весом обслуживает оба одной формулой: по логам предыдущего занятия видно, что keyword уже дал верный топ-1 на первом вопросе, а vector его «размыл», и наоборот на втором. |
| Ось сравнения | Фиксированные равные веса RRF (baseline С10) vs динамические веса от классификации вопроса слабой decision-моделью (`typesafe/jev-1.13`) или признаками запроса без модели вовсе. |
| Разворот П1 | Интуиция «умный роутер почти бесплатен и только помогает» опровергается цифрой: на части типов запросов (которые не видны заранее) классификатор систематически слабее среднего — разброс по классам Banking77 до 27,5 п.п. — и именно там он выставит неверный вес. Динамические веса не доминируют фиксированные по всем запросам, они меняют профиль ошибок, а не убирают его. |
| Граница А7 | Нужно — трафик большой и однородный по типам вопросов, граница «точный факт / смысловой вопрос» чёткая. Не нужно — вопросы разнообразны и формулировки ad hoc (случай курса: инженерные вопросы без предсказуемого шаблона) — классификатор ошибается ровно на пограничных случаях; отдельно — если dense явно сильнее sparse на корпусе, сам фьюжен может быть вреден (Fusion Tax), и это не лечится подбором веса. |
| Источник реального случая | **Не найден на уровне кейсов 1/2/4/5 — открытый методический вопрос (см. `ARCHITECTURE.md` status, пункт 2).** Сырьё — измеренные бенчмарки: openrouter.ai (jev vs Claude Opus 5, Banking77); arXiv:2610.30612 «The Fusion Tax»; arXiv:2605.27220 «Coverage Illusion». |
| [ЗАМЕР НЕ ГОТОВ] | Собственный прогон динамических весов на текстовом стенде С10 — не поставлен (С10 измерил только фиксированный RRF + реранкер, Кейс 3 того занятия). Числа Jev vs Opus, Fusion Tax, Coverage Illusion — сторонние измерения. |

## Кейс 4 — Семантическое размытие поиска на масштабе

| Элемент | Содержание |
|---|---|
| Дивайдер-проблема | База выросла. Добавили новые разделы. И правильный ответ стал реже первым — хотя индекс тот же. |
| Сцена-человек-цена | Ольга сводит в одну базу поиска материалы нескольких курсов учебного центра — раньше у каждого курса была своя небольшая база, теперь один общий поиск по всем программам. Студент курса «Python для анализа данных» спрашивает про «порядок пересдачи практической работы» — поиск уверенно возвращает правило пересдачи совсем другого курса, потому что формулировка почти идентичная, а верный документ оттеснили более многочисленные похожие по лексике материалы других курсов. |
| Ось сравнения | Маленькая однородная база (один курс, уровень С10) vs большая разнородная база (несколько курсов/отделов) — тот же алгоритм точного/эмбеддинг-поиска, тот же top-k, те же настройки. |
| Разворот П1 | Интуиция «добавить ещё материалов в базу — чисто аддитивное, безопасное действие» ломается: добавление новой, но похожей по лексике темы ухудшает ответы по уже существующим темам, хотя там ничего не менялось. Это не инфраструктурный компромисс (не ANN/квантизация) — содержательный эффект геометрии эмбеддингов, воспроизводимый даже на точном переборе. |
| Граница А7 | Эффект заметен, когда база растёт в тематическом разнообразии (не только в объёме однотипного контента) и термины между темами объективно пересекаются. Лечится не «более умным ретривером» (это усугубляет — сильный эмбеддинг даёт более «убедительные» ложные соседи), а скоупингом по домену/тенанту (metadata-фильтры, domain-scoped retrieval) — смена состава кандидатов, не апгрейд алгоритма. |
| Источник реального случая | arXiv:2606.11350, «When More Documents Hurt RAG: Measuring and Reducing Vector Search Dilution with Domain-Scoped Retrieval» — WYDOT (дорожное ведомство Вайоминга), рост базы ×21 (54→1128 документов), precision@10 0,759→0,281 (−63% отн.) на точном поиске. |
| [ЗАМЕР НЕ ГОТОВ] | Собственный прогон роста разнородности базы на SberQuAD-подвыборке этого стенда — не поставлен (Кейс 1 С10 измерил рост размера однородной базы, не разнородности). Числа WYDOT — измерение реальной системы третьей стороны. |

## Кейс 5 — Самокоррекция поиска (CRAG-форма)

| Элемент | Содержание |
|---|---|
| Дивайдер-проблема | Кто решает, что источника достаточно? |
| Сцена-человек-цена | Ольга внедряет чат-бота по внутренним регламентам центра (учебный план + правила безопасности — двухисточниковый паттерн). На первом прогоне бот уверенно отвечает на вопрос, которого в регламентах вообще нет — грейдер релевантности, настроенный мягко, пропустил общий тематически близкий, но не отвечающий по сути кусок. После ужесточения проверки бот на реальный, покрытый регламентом вопрос (сформулированный другими словами) крутится, переформулирует запрос, ищет снова — и молча останавливается без ответа. |
| Ось сравнения | Обычный RAG без самокоррекции (один поиск, ответ по тому, что нашлось — рецепт С10) vs CRAG-форма (LLM-грейдер релевантности + условный fallback/переформулировка), с явной привязкой к тому, есть ли у fallback безопасный второй источник или только открытый веб. |
| Разворот П1 | «Добавить ИИ, который сам проверяет своё извлечение» выглядит как чистое улучшение. Документированный случай показывает обратное: грейдер — один рубильник между двумя противоположными отказами (слишком строгий → зависание и тишина; слишком мягкий → уверенная ложь), и настройка, убирающая один отказ, систематически создаёт условия для другого. Самокоррекция не убирает ошибку — она выбирает, какую из двух противоположных ошибок получит пользователь. |
| Граница А7 | Нужно — у fallback есть безопасный второй источник (не открытый веб) и выделен бюджет на построение и тестирование счётчика итераций с явным решением «что отдаём, когда бюджет исчерпан». Не нужно/опаснее простого RAG — fallback может пойти только в открытый веб, или нет ресурса на итеративную балансировку «строже → проверить обе стороны регрессии → мягче → проверить снова» (реальный случай прошёл этот цикл четырежды). |
| Источник реального случая | github.com/Dharshiny5/n8n-agentic-rag-conc-compliance — n8n-проект FCA-комплаенс-бота (CONC/SYSC), раздел «A real debugging story», четыре эпизода: переохлаждение грейдера → ложноположительная галлюцинация → бесконечный цикл → почти-ошибочный диагноз. Корроборация — community.n8n.io тред «Agentic RAG Agent Stuck on Iterations» и langchain-ai/langgraph PR #5954/issue #4154 (тот же класс отказа, другая обвязка). |
| [ЗАМЕР НЕ ГОТОВ] | Собственный прогон CRAG-цикла (грейдер + Switch + fallback) на n8n-стенде курса — не поставлен. Числа PopQA/ARC-Challenge CRAG vs vanilla (arXiv:2603.16169) и четыре эпизода Dharshiny5 — сторонние измерения/реальный проект, не этот стенд. |

## Сводный список — что закрыто сырьём брифов, что ждёт собственного замера

1. **Кейс 1** — закрыто сырьём: домен решает эффект трансформации сильнее, чем сама техника
   (FiQA −9% / TREC-COVID +5,1% на одном и том же приёме); промежуточный recall ≠ итоговое
   качество (enterprise-регресс 0,51→0,48). Не закрыто: собственный прогон на русском корпусе.
2. **Кейс 2** — закрыто сырьём: иерархия/контекст куска чинит потерю контекста (0,72→0,86 на
   реальном случае до перехода на семантику); семантический чанкинг — документированный
   контринтуитивный провал по стоимости/выигрышу. Не закрыто: собственный прогон parent-document
   на стенде С10.
3. **Кейс 3** — закрыто сырьём: классификатор систематически слаб на непредсказуемых классах
   (разброс 27,5 п.п.); сам фьюжен может быть вреден независимо от веса (Fusion Tax). Не
   закрыто: реальный найденный инцидент (открытый вопрос владельцу) и собственный прогон.
4. **Кейс 4** — закрыто сырьём: содержательная деградация воспроизводится на точном поиске без
   единой ошибки алгоритма (WYDOT, −63% отн. на precision@10). Не закрыто: собственный прогон
   роста разнородности на SberQuAD-подвыборке.
5. **Кейс 5** — закрыто сырьём: обе стороны цены ошибки документированы на одном и том же
   реальном проекте (не на двух разных анекдотах) — зависание и тишина vs уверенная выдумка. Не
   закрыто: собственный прогон CRAG-цикла на n8n-стенде курса.
