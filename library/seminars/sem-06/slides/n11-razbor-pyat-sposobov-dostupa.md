# Пять способов, у каждого своя цена

## Assertion

У каждого из пяти способов — то, что он делает, и то, чего он не делает. Для регулярного доступа нескольких сессий к общему трекеру два способа отпадают сразу, а между оставшимися двумя законными вариантами подключения — осознанный выбор, не формальность.

## Visual

| Способ | Что делает | Что не делает / ограничение |
|---|---|---|
| вызвать API напрямую | агент сам пишет и шлёт запросы к эндпойнтам, сам разбирает ответ — отдельный код интеграции писать не нужно | заранее не знает спецификацию сервиса: какие есть точки, какие у них параметры и ограничения — без документации или swagger-описания агент их не угадает |
| подключить чужой сервер — удалённо | сервис, который кто-то хостит и обновляет сам; у вас не крутится отдельный процесс | управляете не вы: не видно, что сервис делает внутри и когда в нём что-то меняется; плюс обычные вопросы безопасности удалённого сервиса — кому доверяете ключ, у кого ещё есть доступ |
| подключить чужой сервер — локально | пакет исполняется у вас, конфигурация — строка в репозитории, видна всей команде в ревью; контроля больше, чем у удалённого | это всё равно живой процесс на вашей машине и чужой код — со всеми его зависимостями и правом на обновление |
| написать свой сервер | даёт ровно нужный набор операций и прав, без чужого кода в процессе | написать минимальный сервер сейчас быстро — для этого есть готовый плагин; дорого обходится поддержка: протокол, чужие пользователи, безопасность транспорта — отдельный проект рядом с основным |
| вызывать команду `gh` каждый раз | готовый официальный CLI GitHub — авторизацию и разбор ответа он уже решил за вас, кода писать не нужно | каждый вызов — отдельная команда без общего списка возможностей: агент не видит заранее, что вообще можно сделать, нужный вызов приходится знать заранее |

> **Из сочетания колонок:** для нашего случая — регулярный доступ нескольких сессий к общему трекеру, растущий список операций — `gh` и прямой API остаются рабочими, но оба требуют заранее знать точный вызов на каждое действие: ни один не даёт агенту готового списка возможностей. Свой сервер избыточен, раз официальный для трекера уже есть. Между «удалённо» и «локально» выбора без ответа нет — оба законны: свежий официальный пример для этого же сервиса подключается удалённо, а решение этого занятия — локальный процесс, потому что тогда конфигурация становится кодом в репозитории, видимым в ревью всей команде.

## Speaker notes

Разбираю все пять. У каждого — что он делает и чего не делает, вывод складывается из сочетания.

Прямой вызов API — агент прекрасно справляется сам: шлёт запрос, разбирает ответ, писать отдельный код интеграции не нужно. Но заранее он не знает спецификацию сервиса — какие у него есть точки и какие у них ограничения. Без документации или swagger-описания агент эти детали не угадает, их нужно откуда-то дать.

Чужой сервер удалённо — сервис, который кто-то хостит и обновляет сам, у вас не крутится отдельный процесс. Но управляете не вы: не видно, что внутри, и когда там что-то меняется, — плюс обычные вопросы безопасности такого сервиса.

Чужой сервер локально — контроля больше: пакет исполняется у вас, конфигурация — строка в репозитории, видимая в ревью. Но это всё равно живой процесс на вашей машине и чужой код.

Свой сервер — даёт ровно нужные операции и права. Писать минимальный сервер сегодня не долгая работа, для этого даже есть готовый плагин. Дорого обходится поддержка: обновления протокола, чужие пользователи, безопасность транспорта. Это отдельный проект рядом с основным, не разовая настройка.

И `gh` — официальный CLI GitHub, он уже решил авторизацию и разбор ответа за вас. Но каждый вызов — отдельная команда без общего списка возможностей: агент не видит заранее, что вообще можно сделать, нужный вызов приходится знать заранее.

Вывод: для нашего случая — регулярного доступа нескольких сессий к растущему списку операций — `gh` и прямой API остаются рабочими, но оба требуют заранее знать точный вызов на каждое действие. Свой сервер избыточен, раз официальный уже есть. Между «удалённо» и «локально» — оба законны, выбор этого занятия — локальный, и дальше мы его собираем.

Если спросят про «удалённо» подробнее: свежий официальный пример подключения именно к этому сервису — удалённый http-сервис, не локальный процесс, как в примере, на который опирается этот кейс. Это не делает решение занятия неверным — локальный способ остаётся официально поддерживаемым, — но стоит знать: официальный путь для одного и того же поставщика может со временем смениться с одного способа на другой.

Если спросят про безопасность удалённого сервиса подробнее: у одного MCP-сервера для баз данных флаг «только чтение» не делал соединение реально ограниченным — разберём это в провале этого кейса.

Если спросят, почему `gh` не выигрывает у MCP для этого кейса: он отлично закрывает единичный, заранее известный вызов, но не даёт агенту обнаружить список возможностей самому — с ростом числа операций это ложится на разработчика, который должен помнить и называть каждую команду точно.
