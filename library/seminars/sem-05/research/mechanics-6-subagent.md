# Механика субагента Claude Code — вход для автора раздела

Этот документ — рабочий справочник для §1–4 задания, не готовый слайд. `stage-6-subagent.md`

**Методология проверки.** Каждое утверждение о поведении продукта получено одним из трёх
способов: (1) прямой `curl` официальной markdown-версии страницы документации
(`https://code.claude.com/docs/en/<page>.md` — реальный, работающий URL), обращение
**2026-09-27**, тем же днём, когда собирается этот документ; (2) `gh issue view <N> --repo

содержание актуально по крайней мере для этой линии.

## 1. Как происходит делегирование

### 1.1. Встроенное, без единой строки настройки

Дословно из `sub-agents.md` (раздел «Built-in subagents», обращение 2026-09-27): у Claude Code
уже есть три рабочих встроенных субагента, доступных без единого файла конфигурации —

| Встроенный | Модель | Инструменты | Когда вызывается |
|---|---|---|---|
| `Explore` | наследует модель сессии (на Claude API — не выше Opus) | read-only, `Write`/`Edit` запрещены | поиск/анализ кода без изменений |
| `Plan` | наследует модель сессии | read-only | сбор контекста в plan mode |
| `general-purpose` | `CLAUDE_CODE_SUBAGENT_MODEL`, если задан, иначе модель сессии | «every tool available to subagents» | сложная многошаговая задача с исследованием и правкой |

Плюс служебные `claude` (catch-all без своей модели), `statusline-setup` (Sonnet),
`claude-code-guide` (Haiku). Это и есть несущий тезис раздела в механике: делегирование не
требует ни файла, ни строки настройки — оно уже есть в харнессе. Вызов без `subagent_type`
падает только в узком случае: **"`subagent_type is required: the general-purpose agent is not
available in this session`"** — то есть когда `general-purpose` явно выключен (например,
`CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` или allowlist `tools: Agent(...)`, не включающий
`general-purpose`), а не в обычном случае.

### 1.2. Кто решает — модель сама или пользователь явно

Три паттерна, по нарастающей жёсткости, дословно из раздела «Invoke subagents explicitly»:
**natural language** (назвать роль в тексте — «Claude decides whether to delegate»),
**@-mention** (`@"code-reviewer (agent)"` — «guarantees the subagent runs for one task»),
**session-wide** (`--agent <name>` или `agent` в `settings.json` — вся сессия целиком берёт
системный промпт, права и модель этой роли). Автоматическое делегирование без явного упоминания
работает так: **"Claude automatically delegates tasks based on the task description in your
request, the `description` field in subagent configurations, and current context."** Фраза
«use proactively» в `description` — официально задокументированный приём, чтобы модель звала
роль сама, не дожидаясь явной просьбы (пример — `code-reviewer` в разделе «Example subagents»:
«Use immediately after writing or modifying code»).

### 1.3. Как выбирается роль — `description` как маршрутизация, тот же механизм, что у скиллов

Дословно: **"Claude uses each subagent's description to decide when to delegate tasks. When you
create a subagent, write a clear description so Claude knows when to use it."** Официальная
best-practice-заметка формулирует это ещё точнее: **"Write descriptions that single out one
subagent: Claude uses the description to decide when to delegate. Make each description specific
enough to route to the right subagent."** Это буквально та же механика, что у скиллов (курс уже
знает её из раздела 2): там `description` тоже единственный сигнал для авто-вызова, а
`disable-model-invocation: true` — единственный способ снять модель с этого решения полностью.
У субагентов прямого аналога `disable-model-invocation` нет — вместо этого либо `Agent(deny)` в
`permissions.deny` (см. §1.4), либо явный allowlist `tools: Agent(worker, researcher)` на самом
вызывающем агенте.

Описания стоят контекста: **"When the combined descriptions of your subagents, except the
built-in ones, exceed 15,000 tokens, Claude Code shows a warning at startup with the total token
count."** Предупреждение не блокирует загрузку — каждая роль всё равно загружается; это
исключительно сигнал «сократи описания, перенеси детали в тело роли, которое подгружается только
при реальном запуске».

### 1.4. Где лежат описания — пять уровней, коллизия имён

| Место | Область | Приоритет | Как завести |
|---|---|---|---|
| Managed settings | вся организация | 1 (высший) | админ, через managed settings |
| `--agents` (CLI-флаг) | одна сессия | 2 | JSON при запуске, не сохраняется на диск |
| `.claude/agents/` | проект | 3 | попросить Claude или написать файл |
| `~/.claude/agents/` | все проекты пользователя | 4 | то же |
| `agents/` плагина | где плагин включён | 5 (низший) | установка плагина |

Проектные роли ищутся, поднимаясь по дереву от рабочей директории — **"every `.claude/agents/`
between there and the repository root is scanned."** При совпадении имени между уровнями —
**"the definition closest to the working directory wins."** Внутри **одного** уровня (два файла
в одном `.claude/agents/` с одинаковым `name`) правило другое и слабее: **"Claude Code loads
only one of them, chosen by filesystem read order rather than a documented precedence"** —
`/doctor` находит такие дубли и предлагает переименовать или удалить лишний. Имя не может
начинаться с `-` или содержать `:` (зарезервировано под plugin-scoped id вроде
`my-plugin:reviewer`) — файл с таким именем харнесс просто не загружает, с записью в
debug-лог. Изменение файла на диске подхватывается за несколько секунд без перезапуска, но есть
три документированных исключения, где перезапуск нужен: первый файл в **новой** директории
`agents/` (вотчер следит только за директориями, существовавшими на старте сессии);
`.claude/agents/` внутри каталога, добавленного `--add-dir`/`/add-dir` (не отслеживается вовсе);
сессия, запущенная с `--disable-slash-commands` (не отслеживает вообще ничего из этого).

### 1.5. Параллельно или последовательно, сколько разом

С v2.1.232 fork mode включён по умолчанию в интерактивной сессии — из этого следует поведение по
умолчанию: **"Claude Code runs the subagent in the background... and Claude can't ask for the
foreground"** в этом режиме. Без fork mode (headless `-p`, Agent SDK без явного включения)
субагент по умолчанию тоже фоновый, но может перейти на передний план, когда результат нужен
немедленно. Фоновые субагенты работают **параллельно** друг другу и с основной сессией;
разрешения на permission-запросы всплывают в основной сессии с указанием, какой именно субагент
спрашивает. Два отдельных предела, не один: **concurrent limit** — по умолчанию `20`
одновременно работающих субагентов (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, ошибка
`Concurrent subagent limit reached` при попытке завести 21-й, без ретрая); **depth limit** —
по умолчанию `3` уровня вложенности (`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`), на пределе глубины
инструмент `Agent` у субагента отбирается физически. Общего лимита на число субагентов **за всю
сессию** нет — только на число одновременно работающих.

## 2. Контракт: что субагент получает и что возвращает

### 2.1. Что видит субагент на старте — точный список, не пересказ

Раздел «What loads at startup» даёт исчерпывающий список для **не-форк** субагента:

- **системный промпт** — только собственный промпт роли (или тело markdown-файла) плюс
  служебные детали окружения, добавленные харнессом; **не** системный промпт Claude Code:
  **"Subagents receive only this system prompt plus basic environment details like the working
  directory, not the Claude Code system prompt."**
- **task-сообщение** — сформулированная Claude задача делегирования, не исходный запрос
  пользователя буквально.
- **иерархия `CLAUDE.md`** — все уровни, что видит основная сессия, включая
  `~/.claude/CLAUDE.md`, проектные правила, `CLAUDE.local.md`, managed policy, `AGENTS.md`. Явное
  исключение: `Explore`/`Plan` пропускают её всегда; роль с `omitClaudeMd: true` — тоже (кроме
  managed policy файлов, если это не managed-роль).
- **снимок `git status`** — фиксируется в момент старта субагента; `Explore`/`Plan` его не
  получают в любом случае.
- **предзагруженные скиллы** — только те, что явно перечислены в поле `skills`, полным
  содержимым, не только описанием.
- **список «соседей»** — system reminder с именами `main` и других именованных агентов сессии
  (валидные адресаты `SendMessage`), только если у роли есть инструмент `SendMessage` и хотя бы
  один сосед уже назван.

**Что физически не доходит** до не-форк субагента: история основной беседы, `output style`
основной сессии, авто-память основной сессии, файлы, которые уже прочитал родитель. Дословно:
**"Each subagent starts with a fresh, isolated context window. It doesn't see your conversation
history, the skills you've already invoked, or the files Claude has already read."**

**Единственное исключение — форк** (`isolation`/тип `fork`, `/subtask`): он **наследует всё**
целиком — тот же системный промпт, тот же набор инструментов, ту же модель, всю историю
сообщений, включая незакрытый прогрев prompt-кэша родителя. Это прямо противоположная механика:
изоляция контекста для форка **не работает вовсе**, работает только изоляция результата (его
собственные вызовы инструментов не попадают в основной контекст, возвращается только итог).

### 2.2. Что возвращается родителю

Дословно из «Agent tool behavior»: **"The subagent works through its task autonomously, then
returns its result to the parent conversation. The parent doesn't see the subagent's
intermediate tool calls or outputs, only that final result."** Это механически, а не по
договорённости: `PostToolUse` для завершившегося `Agent`-вызова получает в `tool_response`
только: `status` (`completed`/`async_launched`), `agentId`, `content` (финальные текстовые блоки
ответа), `resolvedModel`, `totalTokens` (только финального запроса, не всего прогона),
`totalDurationMs`, `totalToolUseCount` — счётчик, а не сами вызовы. Каждый отчёт субагента
проходит через сканирование перед тем, как Claude его прочитает (**Subagent output scanning**,
требует `v2.1.210+`): вставка backslash в текст, имитирующий служебные теги харнесса
(`<system-reminder>`, `Human:`/`Assistant:`), и строка-маркер
`[harness: subagent output matched instruction-shaped pattern(s):` при упоминании обхода
разрешений. Сам отчёт приходит родителю под заголовком, явно помечающим его как вывод субагента
без полномочий на инструкции. Иллюстративный числовой пример из документации (не измеренная
статистика, а собственный обучающий пример Anthropic, `context-window.md`): «The subagent read
6,100 tokens of files. You got a 420-token result. That's the context savings.» — это именно
то, чего честный пробел курса просит числом, но это дидактический пример одного вымышленного
сценария, не эмпирика по многим сессиям — так и нужно подавать на слайде, не как измерение.

### 2.3. Поля описания роли — обязательные и необязательные

Обязательны только `name` и `description`. Всё остальное — опционально, со своей семантикой:
`tools`, `disallowedTools`, `model`, `permissionMode`, `maxTurns`, `skills`, `mcpServers`,
`hooks`, `memory`, `background`, `omitClaudeMd`, `effort`, `isolation`, `color`,
`initialPrompt`, `experimental`. Файл, у которого фронтматтер не проходит минимальный контракт,
харнесс **пропускает бесшумно для пользователя, но с записью в debug-лог** — это отдельная,
самостоятельная причина «роль не подхватилась» (см. §4.4): нет `name` → файл читается как
документация; открывающий `---` не на первой строке файла → тоже документация; `name` начинается
с `-` или содержит `:` → пропуск + запись в debug-лог; есть `name`, но нет `description` →
пропуск + запись в debug-лог; YAML не парсится → пропуск + запись в debug-лог.

### 2.4. Семантика `tools:` — что значит явно, что значит «не указано вовсе»

Дословно, ключевая строка для co-building раздела: **"Inherits every tool available to
subagents if omitted."** — не «без инструментов», а «со всеми». Полная матрица:

| `tools` | `disallowedTools` | Результат |
|---|---|---|
| не задано | не задано | наследует **весь** пул, доступный субагентам |
| задано | не задано | только перечисленные |
| не задано | задано | весь пул минус перечисленные |
| задано | задано | `disallowedTools` применяется первым, затем `tools` — резолвится против остатка; инструмент в обоих списках снимается |

Отнять доступ **полностью** можно двумя способами: `disallowedTools`, перечисляющий всё, или
буквально пустой список `tools: []` — оба не вызывают ошибку и роль запускается без единого
инструмента (до `v2.1.208` это давало путающий пустой результат; сейчас — так и остаётся, это
осознанное поведение, не баг). Другое дело — когда **ни одна** строка в непустом `tools` не
резолвится: **"`Agent 'code-reviewer' would be spawned with zero tools — refusing. Its tools
list resolved to nothing: unrecognized [Grpe].`"** — харнесс называет конкретно нераспознанные
записи и не запускает роль вовсе. Оба поля принимают MCP-паттерны уровня сервера:
`mcp__<server>` или `mcp__<server>__*` дают/снимают весь сервер целиком; `mcp__*` в
`disallowedTools` снимает вообще все MCP-инструменты. Запись со спецификатором вроде
`Bash(git push *)` в `disallowedTools` всё равно снимает **весь** инструмент `Bash`, не только
совпавшую команду — для точечного запрета конкретных команд нужен `Bash`-deny-rule в
`permissions.deny` (это применяется и к основной сессии, и к субагентам).

**Живой пример этого же проекта.** Ни один из 12 файлов в `.claude/agents/` этого репозитория
(`book-editor.md`, `consistency-checker.md`, `course-curator.md`, `doc-editor.md`,
`fact-checker.md`, `issue-manager.md`, `librarian.md`, `methodology-critic.md`,
`presentation-critic.md`, `presentation-designer.md`, `reader-simulator.md`, `speech-writer.md`,
`student-simulator.md`) не задаёт поле `tools:` вовсе — то есть все они по определению из этого
пункта наследуют **весь** пул инструментов, доступный субагентам, включая `Write`/`Edit`/`Bash`
и все подключённые MCP-серверы. Это осмысленно для ролей, чья работа — производить или менять
контент (`book-editor` пишет `chapter.md`, `doc-editor` правит Google Docs), но означает, что
критик-роли (`methodology-critic`, `presentation-critic`, `fact-checker`,
`consistency-checker`) технически тоже могут писать и редактировать файлы — их «только критикуй»
держится исключительно на тексте инструкции в теле файла, той же силы просьбы, что и в §3.2.
Официальные примеры («Example subagents») проводят ровно эту границу явно: `code-reviewer`
(`Read, Grep, Glob, Bash`, без `Edit`/`Write`) против `debugger` (`Read, Edit, Bash, Grep, Glob`
— «Unlike the code reviewer, this one includes Edit because fixing bugs requires modifying
code»). Захваченный `diff-reviewer.md` (`assets/captures/31-code-diff-reviewer.md.txt`) — третий,
самый узкий случай (`Read, Grep, Glob`, без `Bash`) — то есть в этом проекте нет ни одного
реального файла, демонстрирующего **явное** урезание `tools:`; на слайде стоит явно сказать, что
живой пример урезания в этом репозитории — не заведён, только смоделирован в захвате.

### 2.5. Наследуются ли хуки, скиллы, MCP-серверы — и прямая проверка тезиса курса про хуки

**Скиллы.** Поле `skills` управляет только **предзагрузкой** полного содержимого в старте —
без него роль всё равно может вызвать любой непреzагруженный проектный/пользовательский/
плагинный скилл через инструмент `Skill` во время работы; чтобы запретить это полностью, `Skill`
нужно снять из `tools`/добавить в `disallowedTools`. Тот же принцип описания-как-маршрутизации
из §1.3 работает и здесь на уровне «скилл внутри субагента».

**MCP.** По умолчанию субагент наследует **все** MCP-инструменты основной сессии — дословно из
`errors.md`: **"Subagents inherit every MCP tool definition from the parent session, which can
fill their context window before the first turn. Disable MCP servers you are not using before
spawning subagents."** Поле `mcpServers` работает в обратную сторону — не ограничивает
наследование, а **добавляет** серверы, которых у родителя вообще нет (inline-определение,
подключается на старте роли и отключается на её завершении) или переиспользует уже настроенный
по имени. Обратный приём — держать MCP-сервер вне основной сессии вовсе, объявив его только в
`mcpServers` конкретной роли, чтобы описания его инструментов не ели контекст родителя.

**Хуки — здесь стоит прямая проверка тезиса, вынесенного в задание.** Курсовые материалы
(`stage-6-subagent.md` §6, слой 1; `section-4-subagent.md` §A.8) утверждают: «вызовы субагента,
по сообщённому поведению харнесса, не запускают хуки родительской сессии» — со ссылкой на issue
`#34692`. **Актуальная официальная документация прямо утверждает противоположное.** Дословно,
`sub-agents.md`, раздел «Define hooks for subagents»: **"In `settings.json`: define session-wide
hooks that also fire inside subagents. Tool events such as `PreToolUse` and `PostToolUse` fire
for the subagent's tool calls the same way they do in the main conversation, and `SubagentStart`
and `SubagentStop` fire when a subagent starts or finishes."** И повторно, `hooks.md`: **"Hooks
from settings files, managed policy settings, and plugins also run inside subagents. When a
subagent calls a tool, tool events such as `PreToolUse` and `PostToolUse` fire the same
configured hooks as in the main conversation, and the input carries the `agent_id` and
`agent_type` common input fields that identify the subagent."** То есть хук из `settings.json`
(в отличие от хука во фронтматтере самой роли, который живёт только пока эта роль работает) —
общесессионный и срабатывает на каждый вызов инструмента **любого** субагента; отличить вызов
субагента от вызова основной сессии позволяют именно поля `agent_id`/`agent_type` в payload —
они появляются именно потому, что `session_id` этого не делает (см. ниже).

**Проверка первоисточника тезиса `#34692` (`gh issue view 34692`, обращение 2026-09-27).** Issue
подан 2026-03-15 на `v2.1.76` с точным репро («PostToolUse-хук не увеличивает счётчик коммитов,
сделанных субагентом»); несколько комментариев 2026-03–2026-07 подтверждают симптом. Затем — тот
же самый комментатор (`yurukusa`), который первым написал «can confirm», **сам отзывает свои
слова 2026-08-26**, дословно: «I finally measured it, and my comment was wrong… The hook fired in
the subagent, and `deny` held there — same as top level» — с воспроизводимым скриптом на
`v2.1.246`, где payload субагента содержит `agent_id`/`agent_type`, а payload верхнего уровня —
нет, ровно как сейчас в документации. Issue автоматически закрыт как stale 2026-05-30 (до
retraction), после чего несколько человек написали «баг всё ещё живой», не проверив
самостоятельно — ровно тот паттерн, который курс уже разбирает как «отчёт — не факт» в другом
контексте. **Вывод для раздела: тезис «субагент не триггерит хуки родителя» — не подтверждён, а
прямо опровергнут** и текущей документацией, и повторной эмпирической проверкой первого
подтверждавшего его комментатора. `section-4-subagent.md` §A.8 нуждается в правке в этой части.

**Но «срабатывает» и «гарантированно блокирует» — разные утверждения**, и здесь остаётся
реальный, отдельно задокументированный разрыв. Два **открытых на 2026-09-27** отдельных
инцидента: `#84701` (2026-08-07, открыт) — хук с `deny` корректно **решил** блокировать `rm -rf`/
`chmod -R 777`, вызванные субагентом, но команды **реально выполнились**; автор нашёл это после
настоящего инцидента (неконтролируемый субагент удалил домашнюю директорию пользователя за
~5.5 минуты). `#73380` (2026-07-02, закрыт 2026-08-31) — `permissions.deny` + `PreToolUse`-хук
корректно блокировали основную сессию и **второй** тестовый субагент, но **первый** субагент в
той же сессии с тем же файлом настроек один раз прочитал запрещённый файл с реальными секретами;
воспроизвести детерминированно автор не смог. Итог для раздела: «хук вызывается для субагента» —
подтверждено официально и опровержением первоисточника противоположного тезиса; «хук
гарантированно исполняет решение `deny` для субагента при любых обстоятельствах» — остаётся
открытым вопросом с минимум двумя независимыми, не до конца объяснёнными репортами о разрыве
именно в enforcement, не в срабатывании.

**Остаток `#76726` (открыт, последний комментарий 2026-09-24) — что подтверждается, что нет.**
Issue заявляет два бага: (1) `session_id` в payload хука для вызова субагента равен `session_id`
родителя; (2) `permission_denials` в результате родителя может быть пустым, хотя внутри
субагента запись была заблокирована. Официальная документация **не утверждает прямо**, что
`session_id` для субагента отличается от родительского — она вводит именно `agent_id`/
`agent_type` как отдельные поля для атрибуции, что косвенно **соответствует** жалобе (если
`session_id` уже различал бы вызовы, эти два новых поля были бы не нужны). Про `permission_denials`
документация Agent SDK (`agent-sdk/typescript.md`, тип `SDKResultMessage`) даёт важное уточнение,
которого нет в самом issue: это **два разных сигнала**. Потоковое событие `SDKPermissionDeniedMessage`
дословно **исключает** любые решения по пути `PreToolUse`-хука: **"In every configuration, this
event skips any denial decided on the `PreToolUse` hook path… so `permission_denials` on the
result message is the authoritative record."** Иначе говоря: если автор `#76726` читал именно
потоковое событие денайлов (а не финальное поле `permission_denials` результата), пустой список —
ожидаемое, документированное поведение, не баг; если он действительно читал `permission_denials`
на итоговом результате и оно было пустым при сработавшем хуке внутри субагента — это отдельный,
не закрытый документацией разрыв. Тип `SDKPermissionDenial` при этом сам по себе не содержит
`agent_id` — то есть даже «авторитетная запись» не всегда позволяет атрибутировать денайл к
конкретному субагенту. **Статус для раздела: частично объяснено, не полностью подтверждено** —
см. §7.

### 2.6. Своя модель у роли — что это меняет

Поле `model` принимает алиас (`sonnet`/`opus`/`haiku`/`fable`), полный ID модели или `inherit`
(модель основной сессии). Порядок разрешения, дословно: (1) параметр `model` конкретного вызова
Agent-инструмента, (2) поле `model` во фронтматтере роли, (3) переменная
`CLAUDE_CODE_SUBAGENT_MODEL`, (4) модель основной сессии. Форс единой модели на все субагенты —
`CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` вместе с `CLAUDE_CODE_SUBAGENT_MODEL`; в этом режиме
собственное поле `model` каждой роли игнорируется. Проверить, на какой модели реально работает
конкретный запущенный субагент — команда `/tasks`, которая показывает модель в строке субагента
(с `v2.1.242` — и уровень `effort`, если он задан). Практическое следствие для «когда заводить
роль»: `model` — единственное штатное место, где экономия по деньгам/скорости получает
механическое подтверждение (роутинг на Haiku для дешёвых механических подзадач — паттерн, уже
зафиксированный в памяти курса `subagent-model-tiering`), а не просто пожелание в тексте
инструкции.

## 3. Как пишется роль — на примере `diff-reviewer.md`, по шагам

Разбирается файл из `assets/captures/31-code-diff-reviewer.md.txt` (уже показан целиком в
`section-4-subagent.md` §A.7) — здесь фокус на том, что именно ломается на каждом шаге при
наивном варианте, с опорой на официальные примеры, а не на пересказ уже собранного co-building.

### 3.1. `name` + `description` — без границы «когда НЕ» роль неотличима для маршрутизации

Наивный вариант: `description: Ревьюер diff'ов` — без явного отрицательного случая. При таком
описании модель не может «single out one subagent», как того требует официальная best-practice
(§1.3), и на смежную задачу (например, ревью архитектурного решения) маршрутизация с равной
вероятностью зовёт эту же роль или вообще не зовёт никого. Реальный файл `diff-reviewer.md`
границу проводит («НЕ для методической критики текста — это отдельная роль», в версии раздела
занятия переформулировано под предметную область проекта). **Живой пример той же техники в этом
самом репозитории** — `methodology-critic.md`: «Глубже чем `presentation-critic` (который про
визуал)» — то же противопоставление соседней роли прямо в `description`, работает без всякого
захвата, можно показывать как второй, независимый пример того же приёма.

### 3.2. `tools: Read, Grep, Glob` — без ограничения роль физически может то, что просили не делать

Наивный вариант — вообще не писать `tools:`. По §2.4 это означает наследование **всего** пула,
включая `Write`/`Edit`/`Bash`. Именно это и произошло в захваченном инциденте раздела: ревьюер
не нашёл проблему в выражении, а сам её исправил — потому что физически мог. Официальный пример
`db-reader` (раздел «Example subagents») формулирует ту же логику явно, причём даже с текстовым
запретом в теле роли: **"The system prompt tells the subagent to refuse write requests, so the
hook is a backstop: if the subagent attempts a write anyway, Claude Code blocks the command."**
То есть даже сама документация не считает словесный запрет достаточным сам по себе для
инструмента, который формально доступен, — и подкрепляет его либо урезанием `tools:`, либо, для
более тонкой логики (не весь `Bash`, а конкретные SQL-команды), — `PreToolUse`-хуком в
фронтматтере самой роли (§2.5 показывает механику этого хука отдельно).

### 3.3. Тело роли — единственный источник поведения, кроме окружения

Тело markdown-файла становится системным промптом роли **целиком**, без системного промпта
Claude Code (§2.1). Наивный вариант — писать инструкцию так, будто роль «помнит» контекст
разговора, из которого её вызвали («проверь как договорились» без указания, что именно) — роль
получит только task-сообщение, которое Claude сформулировал при делегировании, не исходную фразу
пользователя буквально и не историю обсуждения.

### 3.4. Формат ответа — без структуры вердикты трёх прогонов несравнимы

Официального встроенного контракта на формат текстового ответа субагента нет — единственный
рычаг автора роли — явно прописать структуру в теле файла, как это делает `diff-reviewer.md`
(`VERDICT: PASS | BLOCK` первой строкой, дальше «что проверено», дальше находки). Наивный
вариант — просто попросить «внимательно проверь и напиши, что нашёл» — соответствует уже
разобранному в `section-4-subagent-part1b.md` §B.5 сценарию: три прогона дают три структурно
разных ответа, сравнивать их можно только вручную и на глаз.

## 4. Как отлаживается

### 4.1. Убедиться, что позвали именно нужную роль, а не общего субагента

В транскрипте вызов делегирования показывается строкой вида `<имя-роли>(<короткая задача>)` —
дословно из quickstart: **"the delegation appears as a tool call row showing the subagent's name
followed by a short task description, such as `code-reviewer(Suggest code improvements)`."**
Если в этой строке видно `general-purpose` там, где ожидалась кастомная роль — маршрутизация не
сработала (см. причины в §4.4), а не сама роль «поработала как надо, но не так». Чтобы не
зависеть от решения модели вовсе — `@`-упоминание (`@"code-reviewer (agent)"` через тайпахед,
или вручную `@agent-<name>`) гарантирует именно эту роль. `/context` показывает секцию custom
subagents с источником загрузки каждой (project/user/plugin) — быстрый способ убедиться, что
файл вообще увиден харнессом, до того как пробовать её вызывать.

### 4.2. Какие инструменты у роли реально оказались

Самый прямой сигнал — падение при старте: **"Its tools list resolved to nothing: unrecognized
[Grpe]"** называет конкретно опечатавшуюся запись. Но даже без ошибки набор может отличаться от
того, что написано в файле: субагенты в фоновом режиме (по умолчанию!) получают **суженный**
встроенный набор инструментов независимо от `tools:` в файле — `Agent`/`AskUserQuestion`/
`EnterPlanMode`/`ExitPlanMode` (кроме `permissionMode: plan`)/`EndConversation`/
`ScheduleWakeup`/`WaitForMcpServers`/`Workflow` снимаются всегда, а фон дополнительно оставляет
только: `Read, Grep, Glob, LSP, Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch,
TodoWrite, Skill, ToolSearch, EnterWorktree, ExitWorktree, Monitor, TaskStop, SendMessage,
Artifact` плюс все MCP-инструменты. Роль, протестированная автором на переднем плане (где фильтр
слабее), может незаметно потерять инструмент именно в штатном фоновом режиме — проверять нужно
именно то поведение, в котором роль реально будет работать. `/doctor` дополнительно находит
дубли имён в одной директории; `claude plugin validate <dir>` (с `v2.1.233`) проверяет
`.claude/agents/`/`~/.claude/agents/` на нечитаемый фронтматтер до старта сессии.

### 4.3. Что видно в интерфейсе во время работы, что остаётся в переписке

Работающие субагенты показаны панелью строк под полем ввода, вложенные — с меткой `(+N)`;
`Enter` открывает транскрипт конкретного субагента и позволяет отправить ему сообщение, `x`
останавливает или снимает строку, `Ctrl+B` уводит текущую задачу в фон. Завершившаяся успешно
строка исчезает немедленно (с подсказкой в футере «`/tasks` to see subagents» на 30 секунд);
упавшая или остановленная вручную — держится видимой те же 30 секунд. Сам транскрипт субагента
хранится отдельно от основной сессии — `~/.claude/projects/{project}/{sessionId}/subagents/
agent-{agentId}.jsonl`, не затрагивается компакцией основной беседы, живёт `cleanupPeriodDays`
(по умолчанию 30 дней). В самой переписке с родителем остаётся **только** финальный текст ответа
(плюс возможные строки-маркеры сканирования вывода, §2.2) — ни одного промежуточного вызова
инструмента не видно, если не открыть строку в 30-секундном окне или не знать `agentId`/имя,
чтобы явно продолжить (`resume`) эту роль сообщением.

### 4.4. Типовые причины

- **Роль не подхватилась.** Файл в директории, созданной уже после старта сессии (нужен
  перезапуск, §1.4); файл не проходит минимальный контракт фронтматтера (§2.3) — без `name`, с
  `name`, но без `description`, с невалидным YAML — харнесс пропускает его тихо для интерфейса,
  запись остаётся только в debug-логе (`claude --debug`).
- **Роль позвана, но ведёт себя как общая.** В транскрипте строка показывает `general-purpose`
  вместо ожидаемого имени — значит, маршрутизация не связала описание задачи с `description`
  роли (см. §1.3: описание слишком общее или не «single out»), либо роль того же имени на более
  высоком по приоритету уровне (§1.4) перекрыла нужный файл проекта незаметно для автора, либо
  проектные хуки/MCP-серверы этой роли пропущены, потому что папка ещё не прошла workspace-trust
  (частный случай для хуков во фронтматтере — правило строже, чем для хуков `settings.json`,
  §2.5).
- **Субагент «не видит» того, что видит родитель, и переспросить не может.** Это не сбой, а
  прямое следствие §2.1: канал делегирования односторонний, роль стартует с чистым контекстом
  (кроме форка) и получает только задачу; продолжить диалог с уже стартовавшей ролью можно
  только явным `SendMessage` на её `agentId`/имя, и даже тогда сообщение от **любого** другого
  агента не может подтвердить зависший permission-запрос и не может изменить права/`CLAUDE.md`/
  конфигурацию самой роли — это может только сама система разрешений или сообщение от вас лично.

### 4.5. Пример отладочной последовательности — 3–4 шага

1. **Проверить, что роль вообще увидена.** `/context` → секция custom subagents → есть ли имя
   роли и с какого уровня она загрузилась. Если её нет — искать причину в правилах пропуска
   файла (§2.3), не в логике самого файла.
2. **Проверить, что зовут именно её.** Дать задачу естественным языком, посмотреть строку
   транскрипта (`<имя>(<задача>)`, §4.1). Если строка показывает не то имя — принудительно
   вызвать `@agent-<name>`, чтобы отделить «маршрутизация не сработала» от «роль сама ведёт себя
   не так».
3. **Проверить, какие инструменты у неё реально есть.** Попросить роль сделать что-то, что по
   `tools:` в файле делать не должна (например, попросить `diff-reviewer` исправить найденную
   проблему самостоятельно). Если правка проходит — либо `tools:` в файле не тот, что думаете
   (правка не подхватилась, или выше по приоритету лежит другой файл с тем же именем), либо роль
   работала в режиме, где фильтр другой (передний план вместо фонового, §4.2).
4. **Проверить, что отчёт подтверждается, а не декларируется.** Открыть `agent-{agentId}.jsonl`
   (через `Enter` в панели в 30-секундном окне после завершения, или по пути из §4.3) и
   убедиться, что реальные `tool_use`-записи присутствуют и соответствуют разделу «что проверено»
   в текстовом ответе — это тот же принцип, что уже в `stage-6-subagent.md` о содержательной
   галлюцинации без единого вызова инструмента, применённый как рутинная проверка, а не только
   как разбор провала.

## 6. Чего я не смог подтвердить

- **`session_id` для вызова субагента — равен ли он `session_id` родителя буквально.**
  Документация не утверждает это прямо ни в одну сторону; она вводит `agent_id`/`agent_type`
  как отдельные поля атрибуции, что косвенно согласуется с жалобой `#76726`, но это вывод по
  умолчанию поля, а не цитата, прямо отвечающая на вопрос. Не выносить на слайд как
  подтверждённый факт без пометки «выводится, не процитирован».
- **`permission_denials` на итоговом результате пуст ли конкретно для денайла, случившегося
  внутри субагента.** Документация Agent SDK объясняет, почему пуст **отдельный поток**
  (`SDKPermissionDeniedMessage` по определению исключает `PreToolUse`-денайлы), и называет
  `permission_denials` «авторитетной записью» — но не подтверждает и не опровергает напрямую,
  что именно это поле корректно населяется для денайла, случившегося внутри субагента, а не
  только на верхнем уровне; сам тип `SDKPermissionDenial` не несёт `agent_id`. Открытый вопрос,
  не закрытый ни документацией, ни issue `#76726` на момент последнего комментария (2026-09-24).
- **Надёжность enforcement `deny`-хука конкретно для вызовов субагента при любых обстоятельствах.**
  Официальная документация утверждает, что решение хука для субагента равносильно решению для
  основной сессии, и это подтверждено воспроизводимым тестом на `v2.1.246` (retraction в
  `#34692`). Но два отдельных, независимо задокументированных отчёта (`#84701`, открыт;
  `#73380`, закрыт как непроверенный до конца, не как исправленный) описывают случаи, где
  корректно принятое решение `deny` не помешало команде реально выполниться внутри субагента —
  оба недетерминированные, оба не сведены к общей причине их авторами. Это остаётся честным
  разрывом между «хук вызывается и решает правильно» (подтверждено) и «решение хука гарантированно
  применяется к субагенту всегда» (не подтверждено, живые контрпримеры есть).
- **Живой пример явного урезания `tools:` в этом же репозитории.** Ни один реальный файл
  `.claude/agents/*.md` в этом проекте не задаёт `tools:` — единственный пример урезания,
  доступный курсу, остаётся захватом `diff-reviewer.md` из репозитория, который больше не
  существует за пределами `/tmp` (см. `section-4-subagent.md` §A.1, §A.7). Это не противоречит
  ничему выше, но означает: «живой пример урезания прав» на слайде 4.8/4.9 раздела занятия
  по-прежнему держится на захвате, не на файле этого проекта.
- **Версия продукта, для которой актуальны все цитаты этого документа.** Как и в
  `mechanics-3-khuk.md`, ни одна страница не даёт явного номера версии или даты «обновлено»;
  внутритекстовые версии (до `v2.1.281`) дают только нижнюю границу актуальности — перед показом
  стоит свериться с `claude --version` на машине для демонстрации.
