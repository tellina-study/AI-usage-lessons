# Провал: утечка приватных данных через один MCP-сервер

## Assertion

Одновременный доступ к публичному и приватным репозиториям через один и тот же MCP-сервер позволил агенту опубликовать чужие приватные данные в открытом PR — без единой строчки эксплойт-кода.

## Visual

Верхняя широкая карточка с иконкой предупреждения: «26 мая 2025, Invariant Labs. Агент с одновременным доступом к чтению публичного репозитория и к приватным репозиториям пользователя через один и тот же GitHub MCP-сервер прочитал скрытую инструкцию prompt injection в открытом issue, собрал данные из приватных репозиториев — включая физический адрес и зарплату — и опубликовал их в автоматически созданном публичном pull request». Подпись: «CVE не присвоен — архитектурный риск, не баг кода». Нижняя карточка — объясняющая рамка gold-обводкой: «смертельное трио» (Simon Willison, 16 июня 2025) — три условия одновременно делают утечку возможной: доступ к приватным данным, обработка недоверенного внешнего контента, канал отправки наружу.

## Speaker notes

Это реальный, задокументированный инцидент, не гипотетическая угроза. 26 мая 2025 года исследователи Invariant Labs показали цепочку: агент был подключён к GitHub MCP-серверу с одновременным доступом и к публичному репозиторию, и к приватным репозиториям того же пользователя. В одном из открытых issue публичного репозитория лежала скрытая инструкция — классический prompt injection, текст, замаскированный под обычный тикет, но на деле адресованный не человеку, а агенту. Агент прочитал этот issue как часть обычной работы, выполнил спрятанную инструкцию, собрал данные из приватных репозиториев пользователя — включая физический адрес и информацию о зарплате — и сам, автоматически, опубликовал собранное в новом публичном pull request. CVE этому инциденту не присвоили: это не баг в коде сервера, а архитектурный риск самой конфигурации доступа — «toxic agent flow».

Через три недели, 16 июня 2025 года, Саймон Уиллисон дал этому явлению имя и объясняющую рамку — «смертельное трио»: комбинация трёх условий одновременно — доступ к приватным данным, обработка недоверенного внешнего контента и наличие канала отправки наружу — делает утечку возможной без единой строчки эксплойт-кода. Ни одно условие само по себе не опасно: доступ к приватным данным без внешнего контента безопасен, обработка недоверенного контента без канала наружу безопасна. Опасна именно комбинация всех трёх сразу.

Ровно та же схема воспроизвелась независимо в июле 2025 года на Supabase MCP: агент с сервисной ролью к базе данных прочитал вредоносный текст, вложенный в тикет поддержки, и скопировал внутренние данные прямо в ответ клиенту — другая система, тот же механизм.

Перенесите это на наш сценарий с GitHub-сервером в signup-landing: если тот же сервер, что читает публичные issue заказчика, одновременно имеет доступ и к другим приватным репозиториям того же разработчика — например, личным проектам, — комбинация «смертельного трио» собирается сама, без злого умысла с чьей-либо стороны. Отсюда прямое практическое правило: область доступа сервера должна быть ограничена ровно тем репозиторием, где реально нужна, а не расширена «про запас», как и было сказано в блоке кода `.mcp.json` двумя слайдами раньше.
