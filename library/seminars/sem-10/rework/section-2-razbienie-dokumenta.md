# Раздел 2. Кейс 2 — разбиение документа на части

## Постановка

Кейс 1 решил, где база знаний будет жить, когда она вырастет: в отдельном хранилище, не в
промте. Но хранилище не глотает документ целиком: регламент на три страницы или
многостраничная инструкция не укладываются в один кусок хранилища так, чтобы поиск потом мог
точно указать на нужное место. Документ нужно сначала разрезать на части — и от того, где
пройдёт разрез, зависит, останется ли ответ на конкретный вопрос целым внутри одного кусочка
или окажется разорван между двумя соседними.

Версия 1 — естественная первая попытка, та, которую выбирают, если про это не думать отдельно:
резать документ на части фиксированного размера — по счёту символов или токенов, — не
оглядываясь на то, где в тексте проходят границы предложений или абзацев.

## Последовательная итерация

Это ровно тот случай, для которого правило «сначала версия 1, затем проблема, затем версия 2»
писалось буквально: резка по фиксированному размеру была опробована первой, потому что она
проще всего реализуется, и только после того, как замер показал её слабость, появилась
альтернатива — резать по границам предложений, не по счёту символов.

Замер прошёл на 60 документах SberQuAD (длина не короче 500 символов — иначе резать на части
просто нечего) и 72 вопросах с проверенной разметкой ответа. По пути нашлась отдельная находка
о качестве исходных данных: у 22,0% строк исходного датасета поле с позицией ответа не
совпадало с реальным положением текста в документе — такие строки исключены из замера, не
подогнаны под удобный результат.

| Размер куска, символов | Версия 1 (фикс. размер) | Версия 2 (по предложениям) | Версия 3 (по словам) | Версия 4 (фикс. размер + перекрытие) |
|---|---|---|---|---|
| 120 | 9,7% (7 из 72) | 1,4% (1 из 72) | 9,7% (7 из 72) | 5,6% (4 из 72) |
| 180 (заголовочное значение) | 12,5% (9 из 72) | 1,4% (1 из 72) | 8,3% (6 из 72) | 5,6% (4 из 72) |
| 220 | 4,2% (3 из 72) | 1,4% (1 из 72) | 1,4% (1 из 72) | 1,4% (1 из 72) |
| 300 | 6,9% (5 из 72) | 0,0% (0 из 72) | 5,6% (4 из 72) | 1,4% (1 из 72) |
| 450 | 2,8% (2 из 72) | 1,4% (1 из 72) | 0,0% (0 из 72) | 0,0% (0 из 72) |

Таблица выше — четыре колонки результата, доля разорванных ответов для каждой из четырёх
версий. Версия 2 — резать по границам предложений, не по счёту символов — снижает долю
разорванных ответов в разы на каждом из пяти проверенных размеров куска. Версия 1 никогда не
опускается до нуля; версия 2 почти всегда держится в границах 0–1,4%.

Версии 3 и 4 добавлены доп. прогоном: прямым код-портом того же класса инструмента, без новых
технологий и без новой модели. Версия 3 (резать по границам слов) снижает долю разорванных
ответов до 0–9,7% — дешевле в реализации, чем разбор предложений, и держит границу слова, но про
границу фразы ничего не знает. Версия 4 (резать по счёту символов с перекрытием 15% от размера куска)
снижает долю до 0–5,6% — почти вдвое ниже версии 1 на заголовочном размере, но разрыв до уровня
версии 2 всё равно не закрывает.

## Вопрос залу

- Резать строго по счёту символов.
- Резать по границам предложений.
- Резать по границам слов.
- Резать по счёту символов с перекрытием.

Все четыре карточки опираются на измеренный результат — тот же прогон проверил их одним и тем
же способом, на одном и том же наборе из 72 вопросов.

## Разбор вариантов

| Действие | Как делает | Преимущество | Недостатки |
|---|---|---|---|
| Резать по счёту символов | Документ рубится на части заданной длины без оглядки на текст внутри | Проще всего реализовать; один параметр, один проход | Разрывает ответ на вопрос между двумя кусками в 2,8–12,5% случаев, в зависимости от выбранного размера; неочевидно, какой размер «удобнее» без проверки |
| Резать по границам предложений | Разрез проходит только там, где заканчивается предложение | Доля разорванных ответов падает в разы — почти всегда 0–1,4% на всех проверенных размерах | Чуть сложнее в реализации (нужен разбор текста на предложения, не просто счёт символов); зависит от качества разбивки на предложения в конкретном языке и тексте |
| Резать по границам слов | Документ делится на слова; кусок копится, пока не превысит целевой размер, разрез проходит только на границе между словами | Дешёвая альтернатива версии 1 — не рвёт слово; реализуется проще разбора предложений | Разрывает ответ в 0–9,7% случаев: держит границу слова, но ничего не знает о границе предложения |
| Резать по счёту символов с перекрытием | Та же логика, что версия 1, но соседние куски перекрываются на часть длины куска (15% на заголовочном размере — 27 символов) | Разрывает ответ реже версии 1 — 0–5,6% против 2,8–12,5% | Хранилище растёт от дублирования символов; перекрытие не закрывает разрыв до уровня версии 2 и не гарантирует результат для ответа любой длины |

## Решение

### Слой 1 — архитектура

Граница куска должна совпадать с границей смысла внутри документа, не с произвольным счётом
символов. Резка, которая режет документ «как придётся», экономит один шаг подготовки и платит
за это тем, что часть ответов на будущие вопросы окажется разорвана между двумя кусками —
и поиск впоследствии найдёт половину ответа там, где нужен был целый.

### Слой 2 — экран в n8n

На настоящем холсте стенда (не программная схема) — семь узлов подряд: форма «Документ
целиком» → Code-узел «Нарезка фиксированным размером» → Code-узел «Нарезка по границам
предложений» → Code-узел «Нарезка по границам слов» → Code-узел «Нарезка фиксированным размером
с перекрытием» → узел сравнения («попал ли ответ целиком в один кусок») → экран результата. Ни
один из семи узлов не вызывает модель — ни LLM, ни эмбеддинг: это отдельный демо-сценарий,
который прогоняет все четыре версии резки на одном документе и сравнивает их прямо на экране —
не продолжение цепочки хранения из Кейса 1 (там шаг резки встал бы один раз, перед шагом
эмбеддинга, в одной цепочке). Разница между версиями — четыре разные функции в четырёх разных
Code-узлах, не один параметр одного узла: `chunkFixed` режет строку циклом по числу символов, не
глядя на содержимое; `chunkStructural` делит текст на предложения регулярным выражением и
накапливает их в кусок, пока суммарная длина не превысит целевой размер, закрывая кусок строго
на границе предложения; `chunkWordBoundary` делит текст на слова и копит их в кусок тем же
способом, что `chunkStructural`, только границей здесь служит слово. Четвёртая
функция повторяет логику `chunkFixed`, добавляя к ней перекрытие — после отсечения очередного
куска следующий начинается на 15% его длины раньше обычной точки старта. Параметр `chunk_size`
(по умолчанию 180) читает каждый из четырёх узлов резки; различие между ними сидит в самом
алгоритме разреза внутри узла.

## Результат и обобщение

Обратившемуся результат виден напрямую: если ответ на его вопрос разорван между двумя кусками,
модель может получить только половину нужного факта и ответить неполно или неверно: не потому,
что плохо искала, — то, что она нашла, само по себе было неполным. Ольге видно
число — какая доля вопросов рискует получить разорванный ответ при текущей настройке резки.

Принцип переносится на любой инструмент, не только на четыре Code-узла резки в n8n: кусок хранилища —
это единица, внутри которой должен сохраняться смысл; выбор границы разреза — решение, которое
прямо определяет, сколько ответов придёт целыми, не техническая деталь конфигурации.

## Нюансы

**Размер куска не ведёт себя монотонно сам по себе.** У версии 1 доля разорванных ответов не
снижается плавно с ростом размера куска: 9,7% → 12,5% → 4,2% → 6,9% → 2,8% на пяти размерах по
возрастанию. Выбор «удобного» на вид размера (например, 180 символов, заголовочное значение
этого замера) не гарантирует качества сам по себе — требуется проверка на своих данных.
Единое эмпирическое правило из чужого проекта такую проверку не заменяет.

**Перекрытие и резка по словам закрывают разрыв частично.** Доп. прогон 2026-11-02 закрыл то,
что прежняя версия этого раздела держала открытым пунктом: перекрытие между соседними кусками
измерено, и на заголовочном размере оно снижает долю разорванных ответов версии 1 почти вдвое —
с 12,5% до 5,6%. Резка по границам слов ведёт себя похоже — снижает ту же долю до 8,3%. Оба
результата настоящие и измеренные, и оба останавливаются раньше уровня версии 2 (1,4%): слово —
не та единица, которая обязана защищать смысл, эту работу делает предложение. Перекрытие и
резка по словам лечат симптом — долю ответов, не попавших целиком в один кусок. Причина
симптома остаётся прежней: граница куска ставится без оглядки на смысловую границу текста.
