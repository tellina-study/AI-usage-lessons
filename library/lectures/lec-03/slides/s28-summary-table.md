# Visible content

## Title bar
«Итоги: механизм → граница → что делать»

## Body
[Таблица, компактно]

| Механизм | Где ломается | Что делать |
|---|---|---|
| Промпт / роль | не повышает точность, только тон | контекст + RAG для точности |
| Chain-of-thought | faithfulness низкая (25-39%) | проверять результат, не рассуждение |
| RAG | «вернул что-то» ≠ «вернул правильное» | strict grounding + observability |
| Fine-tune / PEFT | не место для фактов, forgetting | eval-петля + версионирование |
| Agent loop | план/действие/проверка/цикл без границ | budget/loop-лимиты вне агента |
| Экипировка / память | каждый слот — компромисс | добавлять только под требование |
| Мульти-агент | p^n, координация хрупкая | координатор > рой; только широко-параллельное |
| Безопасность | injection, ZDR не покрывает всё | least-privilege + карта данных |
| **Не ИИ вовсе** | детерминировано и верифицируемо | **обычный код** |

[Gold callout, низ]
**Знать инструмент — значит знать его границу.** Архитектурный выбор — это поиск САМОЙ НИЖНЕЙ ступени, которая закрывает требование задачи.

## Speaker notes

Соберём весь материал лекции в одну справочную таблицу — не для запоминания наизусть, а как инструмент, к которому можно возвращаться при проектировании реальной системы. У каждого механизма есть своя граница применимости и своя мера противодействия. Промпт и роль в нём не повышают фактическую точность, только тон и глубину изложения — для точности нужны грамотный контекст и RAG. Chain-of-thought даёт прирост на многошаговых задачах, но его словесное рассуждение нельзя аудировать: верность объяснения составляет менее половины случаев даже у сильных моделей — значит, проверять нужно результат, а не проговорённую цепочку. RAG решает проблему устаревшего знания, но сам факт, что система что-то вернула, не означает, что она вернула правильное, — нужны строгая опора на источник и постоянный мониторинг.

Дообучение и его параметр-эффективные варианты — плохое место для фактов и несут риск катастрофического забывания, поэтому обязательны петля оценки и версионирование весов и датасета. Цикл агента — это четыре шага, каждый со своим режимом отказа, и без внешних лимитов по бюджету и числу итераций он способен буквально довести задачу до разорения. Экипировка агента — память, инструкции, навыки, субагенты, доступ к инструментам — это не бесплатный апгрейд, а компромисс, который стоит добавлять только под конкретное требование задачи. Мульти-агентные системы страдают от математического перемножения вероятностей отказа по цепочке шагов, и один координатор надёжнее равноправного «роя»; строить их стоит только под широко параллельные независимые подзадачи. Безопасность агентной системы держится на принципе наименьших привилегий и карте данных по каждой фиче, потому что инъекция через недоверенный контент не решена как проблема, а режим нулевого удержания данных не покрывает всю цепочку сторонних инструментов.

И последняя строка таблицы — самая важная во всей лекции: если задача детерминирована и верифицируема, правильный ответ — обычный код без всякого ИИ. Знать инструмент — значит знать его границу; хороший архитектор ищет не самую мощную из доступных архитектур, а самую нижнюю ступень, которая реально закрывает требование задачи.
