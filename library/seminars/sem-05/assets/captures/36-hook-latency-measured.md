# Латентность хука защиты ветки — измерено локально

Закрывает честный пробел, названный в `research/stage-3-khuk.md` §8: «точная цифра для конкретно
нашего хука ("сколько добавляет наш хук защиты ветки") не измерена и должна быть измерена перед
занятием». Материал под кейс К3 предложения `STRUCTURE-PROPOSAL.md`.

## Что измерялось

Команда хука взята **дословно** из `29-code-settings.json.txt` (`.claude/settings.json` ветки
`seminar-5-hook`, коммит `9803643`): `jq -r '.tool_input.command' | { read -r cmd; grep -qE ...;
git rev-parse --is-inside-work-tree; git symbolic-ref --short HEAD; ... }`. На вход подаётся та же
нагрузка, что приходит хуку в реальности: `{"tool_input":{"command":"git commit -m \"fix\""}}`.

Репозиторий — свежий `git init` с одним пустым коммитом, текущая ветка `feature-x` (то есть хук
проходит весь путь: разбор JSON → совпадение регулярного выражения → проверка репозитория →
чтение ветки → молчание, потому что ветка не защищённая). Это самый длинный путь исполнения.

Метод: 10 прогонов на прогрев, затем 100 прогонов подряд, суммарное время делится на 100.
Повторено трижды.

## Результат

| Что | Средняя латентность на вызов |
|---|---|
| **Наш хук защиты ветки, полный путь** | **19–21 мс** (три прогона: 21 · 19 · 19 · 18) |
| Тот же хук + `ps aux` (опрос процессов) | **51 мс** |

Разброс между прогонами — единицы миллисекунд, то есть цифра устойчива.

### Из чего складываются эти 20 мс

| Составляющая, замерена отдельно | Мс |
|---|---|
| пустой `bash -c true` (сама оболочка) | 3 |
| `jq -r` на той же нагрузке | 7 |
| `git symbolic-ref --short HEAD` | 3 |
| `grep -qE` на строке команды | 15 |

Сумма частей (28 мс) больше целого (20 мс), потому что каждая строка таблицы включает свой
собственный запуск процесса, а внутри хука они делят одну оболочку. **Вывод, который из этого
следует: латентность хука определяется числом порождённых процессов, а не «тяжестью» какой-то
одной операции** — самая дорогая строка здесь не обращение к git, а запуск `grep`.

Это же объясняет, почему добавление `ps aux` даёт скачок: не потому, что опрос процессов «сложный»,
а потому что это ещё один процесс, и на машине с длинным списком процессов он дорожает.

## Как соотносится с внешними источниками

| Источник | Цифра | Наше измерение |
|---|---|---|
| `carlrannaberg/claudekit`, `docs/guides/hook-profiling.md` | простой bash-хук ~30 мс; он же с `ps` ~440 мс | 20 мс и 51 мс — тот же порядок для простого хука; множитель от `ps` у нас 2,4× против их ~15× |
| dev.to (bokuwalily) | p95 2,5 с на хук → ~20 с ожидания за 10 вызовов | не воспроизводили: это плохо спроектированный хук в чужом проекте, не наш |

**Расхождение по множителю `ps` названо честно и не сглажено:** оно зависит от числа процессов на
машине, а не от устройства хука. На слайде корректно говорить «опрос процессов удорожает хук в
разы, у нас в 2,4 раза, у автора профилирования — примерно в 15», а не приводить один множитель
как универсальный.

## Ограничения этого измерения

- Это латентность **самой команды хука**, а не полного цикла «агент вызвал инструмент → хук
  ответил → агент продолжил»: накладные расходы самого Claude Code на запуск хука сюда не входят.
  Измерить их без живой сессии нельзя.
- Одна машина, одна версия окружения. Не выборка.
- Хук проходит по молчаливому пути (ветка не защищённая). Путь с `deny` короче на одно обращение
  к git и заметно быстрее не будет — разница внутри разброса.

## Воспроизведение

```
git init -q /tmp/hookbench && cd /tmp/hookbench
git -c user.email=a@b -c user.name=a commit -q --allow-empty -m init
git checkout -q -b feature-x
P='{"tool_input":{"command":"git commit -m \"fix\""}}'
S=$(date +%s%N); for i in $(seq 1 100); do echo "$P" | bash -c '<команда хука дословно>' >/dev/null; done
E=$(date +%s%N); echo $(( (E-S)/100/1000000 )) мс
```


# Часть 2 — цена ШИРОКОГО матчера: измерено на реальном демо-репозитории

Добавлено 2026-09-30 по указанию владельца курса: его собственный случай — «задача затягивается на
десятки минут или час из-за лишних зажатых хуков, которые гоняли циклы проверок на любое
изменение». Часть 1 выше мерила цену **одного** срабатывания узкого хука; здесь измеряется то, что
эту цену умножает.

## Что измерялось

Репозиторий — настоящий `tellina-study/signup-landing-demo`, ветка `seminar-5-hook`, коммит
`9803643`, склонирован и собран (`npm install` → 17 пакетов). Проверки — те, что реально лежат в
`package.json` этого проекта, а не выдуманные.

Хук с **широким матчером** (`Edit|Write` — то есть на любую правку файла) выполняет полный цикл:
синтаксическая проверка всех файлов `src/*.js`, затем `npm run build`.

## Цена одного срабатывания

| Что | Время | Примечание |
|---|---|---|
| наш **узкий** хук защиты ветки (`Bash` + `git commit`) | **27 мс** | тот же хук, что в части 1, на этом репозитории |
| синтаксическая проверка `src/*.js` | **124 мс** | три файла |
| `npm run build` (vite) | **1 137 мс** | реальная сборка, проходит |
| попытка полного прогона `npx playwright test` | **11 942 мс** | **браузер в этой песочнице не стартует, тесты падают** — это не «тесты прошли», а сколько занимает попытка. Как оценка времени рабочего прогона не годится, приведено только как порядок накладных расходов |

## Умножение — вот откуда берётся час

Задача из N правок, широкий матчер, цикл «синтаксис + сборка». Измерено end-to-end, не
экстраполировано:

| Правок за задачу | Суммарное ожидание | На правку |
|---|---|---|
| 10 | **12 с** | 1 209 мс |
| 20 | **26 с** | 1 330 мс |
| 40 | **51 с** | 1 275 мс |

**И это самый дешёвый возможный случай:** проект на три файла, сборка чуть больше секунды. Дальше
умножение идёт по двум осям сразу:

| Цикл проверок | 20 правок | 40 правок |
|---|---|---|
| синтаксис + сборка (**измерено здесь**) | 26 с | 51 с |
| + полный прогон тестов, 12 с/прогон | ≈ 4 мин | ≈ 8,5 мин |
| то же на проекте с прогоном тестов 60 с | ≈ 20 мин | ≈ 40 мин |
| то же, и хуков **два** (личный + проектный складываются) | ≈ 40 мин | ≈ **80 мин** |

Первая строка измерена. Остальные три — арифметика от измеренной строки, и на слайде они должны
быть помечены как арифметика, а не как замер.

## Что из этого следует

**Беда не в медленном хуке, а в широком матчере.** Наш узкий хук стоит 27 мс и срабатывает один
раз за задачу — 27 миллисекунд за всю задачу. Тот же проект, тот же компьютер, но матчер
`Edit|Write` и цикл проверок внутри — и та же задача платит десятки секунд, а на реальном проекте
с настоящим прогоном тестов — десятки минут.

Множитель — **число правок за задачу**, а не стоимость одного прогона. Оптимизировать надо его.

## Ограничения

- Прогон тестов в этой песочнице не работает (браузер не запускается), поэтому строки с тестами —
  арифметика от измеренного времени попытки, а не замер рабочего прогона.
- Одна машина, один проект, три файла в `src/`. Числа «на правку» на большом проекте будут больше,
  не меньше.
- Накладные расходы самого Claude Code на вызов хука сюда по-прежнему не входят (см. часть 1).

## Воспроизведение

```
git clone --branch seminar-5-hook https://github.com/tellina-study/signup-landing-demo /tmp/sld
cd /tmp/sld && npm install
cat > /tmp/wide-hook.sh <<'SH'
#!/bin/bash
cd /tmp/sld
for f in src/*.js; do node --check "$f" || exit 2; done
npm run build >/dev/null 2>&1 || exit 2
SH
chmod +x /tmp/wide-hook.sh
S=$(date +%s%N); for i in $(seq 1 20); do /tmp/wide-hook.sh; done; E=$(date +%s%N)
echo $(( (E-S)/1000000000 )) с
```

Дата снятия: 2026-09-30. Версии: node/npm из окружения, vite 7.1.14, playwright 1.63.0.
