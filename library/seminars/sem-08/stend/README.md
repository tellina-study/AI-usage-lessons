## Находка процесса: `waiting` ≠ обрыв

Статус `waiting` у execution многошаговой `Form` (узел `n8n-nodes-base.form`, `operation:
completion`) — это НЕ признак того, что данные не дошли. Вторая страница формы ждёт визита в
браузере; весь путь ДО неё (включая решение модели или `IF`-узла) выполняется полностью и
виден в `runData`. Прямое воспроизведение: `POST` на `formWaitingUrl` (адрес с подписью из
ответа на исходную отправку формы) переводит execution из `waiting` в `success` немедленно, без
повторного прогона (проверено на execution `41`). Полный разбор — `notes/mcp-limitations.md`
[#233-5].

## Кейс 4 — картинка в Telegram

- Execution `52`: картинка получена узлом `HTTP Request` (Picsum, 800×450), доставлена как
  фото в Telegram, `message_id 6` — реальный прогон через весь n8n-пайплайн.
- Граница `sendPhoto` (10 МБ) проверена ПРЯМЫМ вызовом Telegram Bot API, не через workflow:
  ephemeral-хостинги (0x0.st, transfer.sh, catbox.moe) для подачи большого файла в
  `HTTP Request`-узел были недоступны в момент проверки (503/412/timeout). Несжатый JPEG
  12 812 355 байт (12,8 МБ — между лимитом n8n 16 МБ и лимитом Telegram 10 МБ) дал настоящую
  явную ошибку: `"Bad Request: file of size 12812355 bytes is too big for a photo; the maximum
  size is 10485760 bytes"`. Уточнение формулировки «тихой порчи» из разбора кейса: Telegram
  отвечает явной ошибкой на превышение своего лимита, не тишиной.
