# Architecture: the model-step composes the text

## Assertion

One extra node between recording the request and sending it — a node that calls the model.

## Visual

> Four blocks: form → field extraction → **a step that calls the model on every run** → Telegram. The decision about the text's form is made anew on every request.

## Speaker notes

This diagram is Version 1's architecture in pure form, with not a single specific tool named. If tomorrow someone builds this same chain in a different orchestrator than the one we use, the wording doesn't change by a word: once the request's fields are extracted, a separate step is added that calls the model on every run and gets back finished, freely composed text.

The important property of this architecture isn't that it calls the model — it's when it does so: the decision about the text's form is made anew on every run, not once in advance. That's where the risk grows that we'll break down shortly on real runs: since the text is reassembled on every call, it sounds a little different each time, and sometimes that "different" carries a detail that wasn't in the request at all.

Next comes the second architecture diagram, with not a single change anywhere else in the chain, but a different answer to this exact one node. That's what we'll compare — these two screens, one against the other, not paragraph against paragraph.

Why even bother drawing such a de-personalized diagram first, instead of going straight to the real interface with real field names? Because whether this is the right node for the task doesn't depend on which tool it's built in. If you build a similar chain on a different engine, directly in code, or through any other orchestrator, the question "does this step call the model on every run, or was the decision made in advance" sounds exactly the same, and the answer doesn't change. The specific names of nodes and parameters are a layer below — they come next, on the following screens, and there they're already tied to a real tool, with its real fields and its real prompt text.

What's worth watching here is where the block sits relative to the rest of the chain you already know: it doesn't replace some old node, it sits alongside, as a new branch, after the request has already been written to the table. The other five nodes from last session are untouched by this architecture.
