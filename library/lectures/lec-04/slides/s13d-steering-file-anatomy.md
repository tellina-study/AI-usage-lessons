# Visible content

## Title bar
Steering-файл: что агент должен знать ПЕРЕД запуском в этом репозитории

## Body
[Слева — 4 компонента, Ocean rounded box]

**Команды сборки/теста/линта** — не «как обычно», а точная команда ЭТОГО проекта: `make test-integration DB=local`, не универсальный `npm test`.

**Конвенции кода** — стиль именования, предпочитаемые паттерны («здесь без классов, только функции»), структура директорий.

**Архитектурные ограничения** — инварианты: «этот модуль без сетевого доступа», «эта таблица read-only для сервиса X», «не менять публичный API без запроса».

**Явное «что НЕ делать»** — отдельно от позитивных инструкций: «не коммитить в main», «не запускать миграции без подтверждения», «не добавлять зависимости без согласования».

[Справа — steering-файл vs README/CONTRIBUTING]

| | README / CONTRIBUTING | Steering-файл |
|---|---|---|
| Аудитория | человек | операционный контекст агента |
| Назначение | объяснить проект, онбординг | что нужно ПРЯМО СЕЙЧАС, чтобы не наделать типовых ошибок |
| Частота чтения | один раз, при онбординге | на каждый запуск агента |

Не дублирование — разное назначение при частичном пересечении содержания (команда сборки нужна обоим).

[Teal callout]
**Версионирование как код.** Коммитится в git, ревьюится в PR наравне с кодом (изменилась конвенция — это часть того же PR, что и код, который её демонстрирует). Файл, который никто не обновлял год, — не нейтральный ноль, а источник **устаревшей** инструкции: агент последует написанному, даже если оно больше не соответствует реальности.

## Speaker notes

Сам факт наличия файла-инструкции класса AGENTS.md или CLAUDE.md не гарантирует пользы — это presence paradox, к которому вернёмся на следующем слайде отдельно. Здесь мы предполагаем, что файл пишется осмысленно, закрывает реальный информационный пробел, и разбираем, как он организован как инженерный артефакт.

Мы называем этот класс файлов steering-файл — файл, который агент читает как проектный контекст перед началом работы. Термин не изобретён для курса: часть агентных сред разработки использует его в собственной документации — например, Kiro от AWS называет свой каталог steering и описывает его ровно как версионируемый проектный контекст для агента.

Что реально идёт в такой файл. Команды сборки, теста, линта — не «как обычно», а точная команда этого проекта: конкретный флаг, пакетный менеджер, порядок шагов. Это ровно тот реальный информационный пробел, который называет исследование presence paradox: модель не может вывести из кода нестандартную команду тестов. Конвенции кода проекта — стиль именования, предпочитаемые паттерны, структура директорий. Архитектурные ограничения — инварианты, которые агент не должен нарушать: «этот модуль без сетевого доступа», «не менять публичный API без запроса». Явные секции «что не делать» — отдельно от позитивных инструкций, конкретный список запрещённого для этого проекта.

Чем steering-файл отличается от README и CONTRIBUTING? Не дублирование — разная аудитория. README адресован человеку: объясняет проект, помогает онбордингу. Steering-файл адресован операционному контексту агента перед запуском: даёт то, что нужно прямо сейчас, чтобы не наделать типовых ошибок. Команда сборки нужна обоим, но README читает человек один раз, steering-файл агент читает на каждый запуск.

Версионирование как код: файл должен жить в репозитории на равных с кодом — коммититься, ревьюиться в PR, эволюционировать вместе с базой. Файл, который никто не обновлял год, — не нейтральный ноль, а источник устаревшей инструкции: агент последует написанному, даже если оно больше не соответствует реальности.
