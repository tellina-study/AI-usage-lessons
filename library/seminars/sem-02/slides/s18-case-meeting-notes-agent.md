# Поручения — сами в таск-трекер

## Assertion

Архитектурный выбор двигают конкретные новые требования — не мода на технологию.

## Visual

Иллюстрация: карточка «протокол встречи» со стрелкой к иконке таск-трекера, подпись «создать задачу → назначить исполнителя → проверить срок». Вверху вводная в кавычках: «И пусть поручения из протокола сами автоматически раскладываются по задачам в таск-трекере». Внизу итог-строка крупным шрифтом: «Архитектурный выбор двигают конкретные новые требования. Начинайте с простейшего варианта и усложняйте только тогда, когда появляется требование, которое простой вариант закрыть физически не может. Не наоборот».

## Speaker notes

Ещё одна дополнительная вводная: и пусть поручения из протокола сами автоматически раскладываются по задачам в таск-трекере. Появилось действие во внешней системе — нужно вызвать API таск-трекера, создать задачи, возможно проверить, что они создались корректно.

Кто передумал ещё раз? Почему?

Ожидаемый ответ: теперь нужен workflow или полноценный агент — вызов внешнего инструмента, проверка результата вызова, возможно несколько шагов: создать задачу, назначить исполнителя, проверить, что поле срока заполнено.

Проговорите официальный разбор явно: архитектурный выбор двигают конкретные новые требования — рост базы данных потребовал RAG, необходимость действия во внешней системе потребовала агента. Начинайте с простейшего варианта, который решает текущую задачу, и усложняйте только тогда, когда появляется требование, которое простой вариант закрыть физически не может. Не наоборот.

### Self-check
1. Проследите всю лестницу кейса «Протоколы встреч» — какое именно требование на каждом шаге стало причиной перехода к следующей архитектуре?
2. Почему правило «начинай с простейшего» защищает от типичной инженерной ошибки — усложнения архитектуры заранее, «на будущее»?
