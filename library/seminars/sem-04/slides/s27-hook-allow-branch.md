# Тот же коммит на рабочей ветке проходит

## Assertion

Тот же коммит, после git switch -c отдельной командой, проходит без единого изменения кода — правило зависит от ветки, не от намерения агента.

## Visual

Снимок терминала, моноширинный шрифт, дословно из капчура:

```
=== git switch -c fix-form-field ===
=== INPUT ===
{"tool_input":{"command":"git commit -m \"fix: second form field\""}}
=== current branch ===
fix-form-field
=== HOOK OUTPUT (stdout) ===
=== hook exit code: 0 (empty stdout above = hook did not block; commit is allowed to proceed) ===
```

## Speaker notes

`git switch -c fix-form-field` — отдельной командой, до попытки коммита. Ветка сменилась, что видно в блоке `current branch: fix-form-field`. Тот же самый текст коммита, `git commit -m "fix: second form field"`, без единого изменения содержимого, подаётся хуку снова. На этот раз stdout хука пуст — хук не вернул `deny`, проверка ветки внутри условия просто не сработала, потому что текущая ветка не `main` и не `master`. Пустой вывод при коде выхода `0` означает: хук отработал, но не заблокировал, и коммит проходит по обычному пути разрешений дальше.

Здесь стоит явно проговорить нюанс, который легко упустить и который зафиксирован в собственном дневнике шаблона курса. Хук читает текущую ветку до выполнения всей Bash-команды целиком, а не после каждого отдельного шага внутри неё. Из этого следует практическое правило: `git switch fix-form-field && git commit -m "..."` одной строкой всё равно получит `deny`, потому что в момент проверки хук видит ветку, с которой всё началось, — `main`, — а не ту, на которую команда переключится через несколько секунд после запуска. Именно поэтому в рецепте `git switch -c` выполняется отдельным вызовом, а не в одной строке с коммитом через `&&`.

Хук не читает намерение всего плана, он читает синтаксис одной конкретной команды в один конкретный момент. Механизм узкий и предсказуемый — что одновременно и его сила, и его ограничение, к которому мы вернёмся в провале раздела.

Стоит явно проговорить, почему это не «баг» хука, а прямое следствие его устройства. Хук получает на вход ровно тот JSON, который Claude Code формирует непосредственно перед вызовом инструмента `Bash`, — снимок состояния на этот момент, не поток событий изнутри самой команды. Требовать от него отслеживать состояние репозитория в реальном времени внутри одной composite-команды означало бы полностью менять модель работы хука, а не чинить частную деталь. Разработчику, который держит это ограничение в голове, достаточно одной привычки: команды, меняющие ветку, и команды, коммитящие изменения, — это два отдельных вызова, а не один составной.
