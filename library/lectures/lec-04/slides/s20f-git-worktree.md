# Visible content

## Title bar
Git worktree: как курс сам потерял 2 часа на общей рабочей копии — и закрыл проблему

## Body
[Слева — проблема, Ocean rounded box]

**Общая рабочая директория = общий риск.** Несколько параллельных агентных сессий (или несколько задач одного разработчика) над одним репозиторием означают: незакоммиченные правки одной сессии видит — и может испортить — другая.

[Справа — решение, Ocean rounded box]

**Git worktree** — механизм самого git: отдельная рабочая директория со своей веткой, но с **общей** историей репозитория и общим `.git`-хранилищем объектов.

`git worktree add --detach /tmp/lec-NN-wt <commit>`
`cd /tmp/lec-NN-wt && git checkout -b phase-X-Y`

[Teal strip — документированный инцидент курса]
Не гипотетическая практика: работа над Лекцией 2 потеряла **~2 часа** на восстановление после конфликта параллельных сессий с общим `.git`. После этого курс ввёл обязательную изоляцию через worktree — и проблема больше не повторялась.

**Изоляция Claude Code — принудительная, не соглашение.** Инструмент блокирует правки и команды с рабочей директорией вне назначенного worktree: параллельные сессии физически не могут задеть чужие незакоммиченные файлы.

[Честная оговорка]
Worktree дешевле отдельного `clone` — делит объектный граф, не дублирует историю. Но конкретное **число** рекомендуемых параллельных worktree (3–5 vs 4–8) — блог-консенсус, не вендорская норма.

[Gold callout]
Механика worktree устойчива вне зависимости от AI-агента; специфика агентного контекста — не изобретение worktree для AI, а то, что несколько параллельных агентных сессий делают проблему общей копии особенно частой и дорогой.

## Speaker notes

Организация среды и харнес-инжиниринг выше разбирали, как оснастить одну рабочую копию для одного агента. Отдельный практический вопрос — что происходит, когда параллельно работают несколько агентных сессий или несколько задач одного разработчика над одним репозиторием: общая рабочая директория означает, что незакоммиченные правки одной сессии видит — и может испортить — другая.

Git worktree — механизм самого git: отдельная рабочая директория со своими файлами и своей веткой, но с общей историей репозитория и общим хранилищем объектов с основной копией. Это не гипотетическая практика для этой главы — курс формализовал её для собственного производства и реально ею пользуется, что делает пример проверяемым, а не абстрактным. Причина, по которой правило вообще появилось, задокументирована честно: работа над Лекцией 2 потеряла около двух часов на восстановление после конфликта веток при параллельной сессии с общим хранилищем; изоляция через worktree закрыла именно этот класс инцидента, не гипотетический.

Зачем worktree лучше отдельного клонирования репозитория: worktree и основная рабочая копия делят общий объектный граф git — история и объекты не дублируются, в отличие от клонирования, которое копирует весь граф заново; создание worktree — операция поверх уже существующей истории, тогда как отдельный клон плюс повторная установка зависимостей заметно дороже по времени и месту на диске. У самого инструмента разработки изоляция принудительная, а не просто соглашение: он блокирует правки и команды с рабочей директорией вне назначенного worktree, то есть параллельные сессии физически не могут задеть чужие незакоммиченные файлы.

Честно про то, что дальше уже не вендорский канон, а практика сообщества: конкретное число рекомендуемых параллельных worktree расходится между источниками — ни одна цифра не взята из официальной документации напрямую. Практический вывод: сама механика worktree — устойчивый паттерн, применимый вне зависимости от того, участвует ли в сессии AI-агент; специфика агентного контекста в том, что несколько параллельных сессий делают проблему общей копии особенно частой и дорогой, если её не решить заранее.
