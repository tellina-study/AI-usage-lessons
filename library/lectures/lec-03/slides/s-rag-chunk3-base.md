# Visible content

## Title bar
«Тихий провал чанкирования: голый ряд цифр»

## Body
[Worked example — до]
300 PDF-руководств с таблицами спецификаций. Наивный RecursiveCharacter, 512 токенов, расплющил таблицу и режет по байту → чанк «12 / 480 / 8.5 / 34» без заголовков «Модель / Напряжение / Ток / Момент». Система не падает — ответ просто неверный.

[Worked example — после]
Table-aware: таблицу отдельным чанком; больше лимита → по строкам с повтором заголовков → «Модель X-500 | Напряжение 480 | Ток 8.5 | Момент 34». Каждая строка самодостаточна. Выигрыш дала не «умная» нарезка, а уважение структуры.

[Ещё два провала + пайплайн]
Анафора («оно», «данная политика») теряет антецедент; смена эмбеддера = пере-нарезка всего корпуса; оценка chunking чувствительна к k.

## Speaker notes

Предыдущий слайд сказал: не карго-культите чужой рецепт, мерьте на своих данных. Этот слайд показывает, как именно чанкирование ломается — и почему это самый коварный вид отказа RAG: он тихий. Возьмём конкретный корпус: триста PDF-руководств по промышленному оборудованию — пояснительный текст плюс таблицы спецификаций «Модель / Напряжение / Ток / Момент затяжки» плюс предупреждения по безопасности. Типичный вопрос: «какой момент затяжки для модели X-500?» — и ответ живёт в ячейке таблицы.

Что выбрал бы наивный инженер: RecursiveCharacterTextSplitter, пятьсот двенадцать токенов, перекрытие пятьдесят — это работает для прозы. Но парсер детектит таблицу и расплющивает её в поток, а символьный сплиттер режет её по произвольному байту на границе пятьсот двенадцать токенов. Результат: первый кусок содержит заголовки колонок и первые строки, а все последующие — ряды цифр без заголовков: «двенадцать, четыреста восемьдесят, восемь и пять, тридцать четыре» без подписей. Почему это тихий провал: система не падает — эмбеддинг считается, ретрив находит чанк с числом тридцать четыре, ответ генерируется. Он просто неправильный: модель не знает, что тридцать четыре — это момент затяжки для X-500, а не ток для X-700. На дашборде «retrieval работает», в проде — травма на производстве.

Правильное решение — не «умная» semantic-нарезка, а банальное уважение структуры[1]: table-aware нарезка, где таблица идёт отдельным чанком, а если больше лимита — по строкам, повторяя заголовки в каждом куске, чтобы каждая строка стала самодостаточной. Плюс parent-document для текста, чтобы предупреждения не отрывались от процедуры, и метаданные для фильтра по модели и версии.

И три вещи, которые нельзя забыть. Анафора: «оно», «этот город», «данная политика» теряют антецедент при разрезе — лечится parent-document или контекстным дописыванием. Смена эмбеддинг-модели — это пере-нарезка всего корпуса[2], а не строчка в конфиге. И оценка самого chunking чувствительна к k: recall@k может врать (девяносто два процента recall при пятидесяти четырёх процентах ответов), поэтому меряют и end-to-end. Проверка на тихий провал простая: сгенерировать двадцать-тридцать вопросов с ответами в таблицах и руками убедиться, что в top-k приходит чанк с заголовками, а не голый ряд цифр.
