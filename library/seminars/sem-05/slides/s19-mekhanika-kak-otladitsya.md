# Как поверить барьеру не на слово

## Assertion

Есть только два принципиально разных тихих отказа, не десяток: сломанный целиком файл настроек виден сразу в интерактивной сессии, а опечатка в одной записи не видна нигде, кроме отладочного лога; три шага проверяют барьер целиком, не только половину.

## Visual

| Средство | Что показывает |
|---|---|
| `/hooks` | Список сконфигурированных хуков: событие, matcher, команда |
| `claude --debug-file <путь>` | Подробный лог выполнения хуков |
| `claude doctor` | Невалидные файлы настроек, отклонённые записи |
| `/status` | Какие файлы настроек реально загрузились |
| Ручная подача JSON на вход скрипту | Код возврата и вывод в обход Claude Code |

| Что сломано | В интерактивной сессии | В headless-прогоне |
|---|---|---|
| Весь файл настроек целиком | **Не тихо** — диалог ошибки сразу | Тихо — узнать только через `doctor` |
| Одна запись (опечатка, регистр, незаякоренный matcher) | **Тихо по-настоящему** — только `doctor`/debug-лог | То же |

Три шага проверки барьера:
1. Хук вообще виден в `/hooks`?
2. Заведомо блокируемый кейс даёт реакцию, а не веру.
3. Негативный контроль — хук пропускает то, что должен.

## Speaker notes

Пять инструментов, все — по нашему хуку. `/hooks` показывает список сконфигурированных хуков с полной командой. `claude --debug-file` пишет подробный лог в файл, который можно смотреть вторым терминалом. `claude doctor` находит невалидные настройки. `/status` показывает, какие файлы реально загрузились в эту сессию. И просто ручная подача: подать JSON на вход скрипту и посмотреть код возврата, в обход Claude Code вообще.

Теперь — два разных тихих отказа, не один, и разница важна именно потому, что зал работает интерактивно. Если сломан весь файл настроек целиком — невалидный JSON, `matcher` записан массивом вместо строки, — это тихо только в headless-прогоне. У вас, в интерактивной сессии, это не тихо: диалог ошибки настроек показывается сразу при старте. По-настоящему тихо — когда ошибка меньше: опечатка в имени события, неверный регистр в `matcher`, незаякоренный шаблон. Тогда падает одна запись, остальной файл работает как ни в чём не бывало, и никакого сигнала нет нигде, кроме `claude doctor`. То, что выглядит страшнее всего — сломанный файл целиком, — зал бы увидел сразу. По-настоящему тихое — опечатка внутри в остальном рабочего файла, которая ничем себя не выдаёт.

И три шага, чтобы поверить не на слово, что барьер живой. Первый — хук вообще виден в `/hooks`? Второй — заведомо блокируемый кейс даёт реакцию, а не веру: попробовали закоммитить на `main`, реакция должна быть видна сразу; нет реакции — включайте debug-лог и смотрите, какие matcher-ы проверялись, совпал ли `Bash`, какой код возврата и вывод дал сам скрипт. Третий — негативный контроль: хук пропускает то, что должен пропускать, коммит на фиче-ветке реально лёг. Без третьего шага проверена только половина барьера — то же самое, что уже говорилось про третий кадр собранного хука.

Эта проверка — не гипотетическая процедура на будущее. Она ровно то, чем построен самотест, который сейчас разберём: три шага, формализованные в скрипт и повторяемые одной командой вместо ручной проверки каждый раз. Разница только в масштабе — самотест прогоняет не один заведомо блокируемый случай, а целый набор форм одной и той же команды, и часть из них барьер пропускает.
