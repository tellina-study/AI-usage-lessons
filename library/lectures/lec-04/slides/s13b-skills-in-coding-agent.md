# Visible content

## Title bar
Skill = директория с коротким SKILL.md, который агент быстро сканирует

## Body
[Слева — анатомия skill, Ocean rounded box]

**Формат**
- `SKILL.md` — YAML frontmatter (название, описание, когда применять) + тело-инструкция
- `scripts/` *(опционально)* — готовые скрипты, которые навык вызывает напрямую
- `references/` *(опционально)* — длинные справочные материалы, не раздувающие основной файл

Ключевая идея: SKILL.md короткий и быстро читается моделью при определении применимости; тяжёлые детали лежат отдельно и подгружаются, только когда навык реально используется.

[Справа — область видимости, 2 колонки]

**Project-level (уровень проекта)** — в репозитории, коммитится в git, команда получает автоматически. Подчиняется дисциплине steering-файла: версионируется, ревьюится в PR.

**Personal (личный)** — в конфигурации разработчика, применяется во всех его проектах (например, личный стиль commit-сообщений). Личная продуктивность, не часть контракта команды.

**3 конкретных SWE-примера:**
- «Оформить PR по конвенциям проекта» — точный формат (Summary / Test plan / Related issues, стиль заголовка)
- «Прогнать тесты и интерпретировать результат» — точная команда ЭТОГО проекта, отличить реальный провал от известного flaky-теста
- «Сгенерировать changelog» — формат проекта (например, Keep a Changelog) + классификация изменений по истории коммитов

[Teal callout]
Общая логика всех трёх: skill не учит модель тому, чего она не умеет в принципе, — он фиксирует **конкретный, проектный вариант** общей процедуры, чтобы агент не изобретал его заново и не дрейфовал от раза к разу. Прямая параллель паттерну structure + constraints + tests.

## Speaker notes

Мы уже вводили skill в общем виде: переиспользуемая процедура под повторяющийся класс задач, которая освобождает агента от необходимости каждый раз заново формулировать её в промпте. Здесь — как это выглядит конкретно в кодинг-агенте.

Формат: навык — это директория, минимально содержащая файл SKILL.md — markdown с YAML frontmatter (название, описание, когда применять) и телом-инструкцией. Опционально рядом лежат scripts — готовые скрипты, которые навык вызывает напрямую, вместо того чтобы модель заново писала код для типовой операции, — и references — длинные справочные материалы, на которые основной файл ссылается, не раздувая себя. Ключевая идея: SKILL.md короткий и быстро читается моделью при определении применимости, а тяжёлые детали подгружаются только тогда, когда навык действительно используется.

Область видимости бывает двух видов. Project-level skill лежит в репозитории и коммитится в git вместе с кодом — команда получает его автоматически. Personal skill хранится в конфигурации разработчика и применяется во всех его проектах — например, личный стиль commit-сообщений. Project-level skills подчиняются тем же принципам, что и steering-файл, который разберём дальше, — версионируются, ревьюются в PR; personal skills — личная продуктивность, не часть контракта команды.

Три типовых навыка. «Оформить PR по конвенциям проекта» — точный формат: секции Summary, Test plan, Related issues, стиль заголовка. «Прогнать тесты и интерпретировать результат» — точная команда этого проекта, не общее «npm test», умение отличить реальный провал от известного флакового теста. «Сгенерировать changelog» — формат проекта, например Keep a Changelog, и классификация изменений по истории коммитов.

Общая логика: skill не учит агента тому, чего модель не умеет в принципе, — он фиксирует конкретный, проектный вариант общей процедуры, чтобы агент не изобретал его заново и не дрейфовал от раза к разу. Прямая параллель паттерну structure plus constraints plus tests.
