# Visible content

## Title bar
«Шесть типовых агентных задач по одной схеме»

## Body
[Таблица: задача · форма петли · где ломается (число/кейс) · лучше workflow?]
1. Coding-агент (Claude Code / Cursor) — читать репо → план → правки → тесты → PR; ломается на больших рефакторингах; НЕТ workflow — открытый поиск по коду требует агентности.
2. Клиентская поддержка (Air Canada · Klarna) — классифицировать → достать политику → решить/эскалировать; Air Canada: бот выдумал политику → трибунал взыскал; Klarna «−700 агентов» → вернули людей; часто ДА для риск-части.
3. ETL / pipeline — заметить дрейф → пропатчить → провалидировать; тихие плохие преобразования; в основном ДА, агент только на край починки.
4. Research-агент — план под-вопросов → искать → синтез → цитаты; ~15× токенов, галлюцинированные цитаты; НЕТ для открытого, ДА если фиксированный lookup.
5. Браузер / Operator — скриншот → план UI → клик; OSWorld ~38%, Operator закрыт; для значимых действий ДА — реальный API.
6. SRE / ops (ITBench) — телеметрия → гипотеза → фикс; ITBench ~14%; для исправления ДА — workflow + подтверждение.

[Gold] Агент — на адаптивный край, workflow-с-воротами — на ствол и значимое действие.

## Speaker notes

Разберём шесть типовых агентных задач по одной схеме: задача, форма петли, где ломается, был бы лучше workflow. Это перевод общего принципа лестницы в конкретные рабочие сценарии, с реальными привязками. Отдельные суммы иллюстративны, но классы и привязки реальны.

Первый — coding-агент, Claude Code или Cursor. Задача — реализовать или починить код по всему репозиторию из формулировки на естественном языке. Петля: прочитать репо, спланировать, отредактировать файлы, прогнать тесты, увидеть ошибки, итерировать, открыть PR. Ломается на больших неоднозначных рефакторингах и уходе в петлю на мигающих тестах. Был бы лучше workflow? Нет — открытый поиск по коду действительно требует агентности, это канонический случай, где агент оправдан.

Второй — клиентская поддержка, и тут два поучительных кейса. Air Canada[1]: бот-поддержка выдумал 90-дневное окно возврата, и трибунал признал авиакомпанию обязанной выплатить — галлюцинация политики стала юридически обязывающей. Klarna публично отпраздновала ИИ, заменивший 700 агентов, а затем восстанавливала человеческие мощности, потому что краевые случаи и суждение об эскалации вернули людей в петлю. Был бы лучше workflow? Часто да для рискованной части: возвраты и ответы по политике хотят детерминированной маршрутизации с guardrails, а не свободной генерации.

Третий — ETL-агент, самозаживающий пайплайн. Петля: заметить дрейф схемы, проанализировать влияние, сгенерировать преобразование, провалидировать, под guardrail применить. Ломается тем, что тихие плохие преобразования портят данные на масштабе, а недетерминизм опасен в пайплайне, который надо аудировать. В основном да — ствол детерминирован, агент уместен только на узком шаге починки дрейфа. Четвёртый — research-агент, Deep Research. Ломается взрывом стоимости примерно в пятнадцать раз по токенам и галлюцинированными цитатами. Нет для действительно открытого исследования вширь, да — если это на деле фиксированный lookup.

Пятый — браузерный агент, Operator. Петля: скриншот и DOM, спланировать UI-действие, клик, наблюдать. На бенчмарке OSWorld первое поколение давало около тридцать восемь процентов[2] успешных задач, и сам продукт Operator был закрыт — живой урок «хайп — уход с рынка». Для любого значимого действия, платежей и форм — да, используйте реальный API, если он есть. Шестой — SRE-агент. На бенчмарке ITBench передовые модели автономно решают лишь около 14% сценариев, поэтому реальная ценность — сузить пространство поиска и оставить суждение людям. Сквозной принцип: агент — на адаптивный край, workflow с воротами — на ствол и на значимое действие; числа Operator и ITBench означают «сузить поиск», а не «заменить человека».
