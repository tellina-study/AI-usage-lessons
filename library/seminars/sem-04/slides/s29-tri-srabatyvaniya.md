# Три срабатывания подряд

## Assertion

Полная проверка барьера — он запрещает то, что должно, и пропускает то, что должно; иначе вы поставили не барьер, а стену.

## Visual

Три кадра в ряд.

**1. Ветка `main`, попытка коммита** — дословный текст отказа крупно:

> `"permissionDecision":"deny"` — **«BLOCKED: direct commit to main/master. Create a feature branch first.»**

**2. После `git switch -c fix-form-field`, тот же коммит:**

```
=== HOOK OUTPUT (stdout) ===
=== hook exit code: 0 (empty stdout = hook did not block) ===
```

**3. Тот же коммит реально выполнен** (подсвечен gold, подпись «и это важнее первых двух»):

```
[fix-form-field a666b27] fix: second form field
 1 file changed, 8 insertions(+)
 create mode 100644 src/validate.js
```

## Speaker notes

Три кадра, и все три настоящие. Это стоит сказать прямо, потому что дальше они работают как доказательство, а не как иллюстрация.

«Первый: отказ, дословный текст — "BLOCKED: direct commit to main/master. Create a feature branch first." Второй: после создания ветки тот же коммит хук пропускает — вывод пустой. Третий, и он важнее первых двух: коммит действительно лёг, вот его хеш, вот изменённый файл.

Третий кадр здесь не для полноты. Барьер, который вы видели только запрещающим, вы не проверили — вы проверили половину. Полная проверка: запрещает то, что должно, и пропускает то, что должно. Иначе вы поставили не барьер, а стену.»

Обратить внимание на вторую картинку отдельно: успешное прохождение выглядит как пустой вывод. Ровно так же, как выглядит хук, который вообще не запустился. Это тот же принцип, что прозвучал на разборе падающей команды — и через минуту он вернётся третий раз, уже как перечень причин молчаливого отказа. Три повтора здесь не избыточность: именно это свойство делает хуки опасными в эксплуатации.
