# Setting up a coding agent

## Assertion

An agent's configuration is a set of decisions taken over the course of working on a project: some of them pay off from day one, some cannot be taken in advance.

## Visual

Full-bleed Ocean rounded gradient (`#21295C` → `#065A82` → `#1C7293`), a decorative "04" in the top-right corner (200pt+ outline, low opacity). Centered — the title "Setting up a coding agent" in 44pt white.

Below the title, in a gold-outlined block — the central question of the session, word for word:

> "What in an agent's configuration is worth putting in place right away, on day 0, as a baseline practice — and what cannot be known in advance, because it is specific to your project?"

Hero illustration across the bottom third: on the left an empty `signup-landing/` directory, on the right the same tree, overgrown with blocks of configuration; between them the seven rungs of a ladder, **unlabeled**.

## Speaker notes

"The standard way to set an agent up on a new project is to open a repository that looks mature and copy its configuration across: a three-hundred-line instruction file, a dozen skills, a few connected servers. Part of that is universal engineering hygiene that pays off on any project. Part of it is decisions made for somebody else's repository, taken on signals that were never present in yours.

Today we work through this not in the abstract but on a single project from the beginning: we take a request from a client, pin down the requirements, stand up a repository, get a working prototype — and then, in the course of ordinary work, we run into the decision point 'do we write this into the agent's configuration or not' six times.

The question for the session: what is worth putting in place right away, on day 0, and what cannot be known in advance, because it is specific to your project?"

Straight on to the request from here, no pause.
