# Visible content

## Title bar
Где хранить состояние задачи между сессиями агента — три паттерна

## Body
[Teal callout, верх]
Не то же самое, что steering-файл (описывает проект целиком, живёт долго) и не написанные самим агентом (self-authored) заметки внутри одной сессии — это дисциплина организации **межзадачного и межсессионного** состояния на диске: что сделано, что осталось, какие тупики пройдены.

[3 карточки-паттерна в Ocean rounded box]

**Паттерн 1 — nested per-task folder (вложенная директория на задачу)**
`tasks/TASK-123/` с `notes.md`, `log.md`, черновиками; план отдельно от лога выполнения.
Сильная сторона: богатая структура на одну задачу — можно разделить типы информации по файлам.
Что ломается на масштабе: количество директорий растёт линейно, без архивации — захламление; удаление ощущается как потеря истории.

**Паттерн 2 — single unified log (единый растущий файл)**
Один файл (`PROGRESS.md`), каждая сессия дописывает запись в конец.
Сильная сторона: одна точка входа, вся хронология без знания номера задачи заранее.
Что ломается на масштабе: файл не помещается в контекст агента целиком (**context rot** — деградация точности модели при разрастании контекста); параллельные сессии, дописывающие в один хвост, — магнит merge-конфликтов.

**Паттерн 3 — flat shared folder (один файл на задачу без вложенности)**
`tasks/TASK-123.md` напрямую, без вложенности.
Сильная сторона: баланс — единая точка входа (`tasks/`), но состояние задачи изолировано в своём файле.
Что ломается на масштабе: список файлов растёт без внутренней структуры; несколько артефактов на задачу требуют условности именования.

## Speaker notes

Отдельный практический вопрос для разработчика, ведущего несколько задач с кодинг-агентом: где и как хранить состояние задачи на диске — что сделано, что осталось, какие тупики пройдены. Это не steering-файл, который описывает проект целиком и живёт долго, и не написанные самим агентом (self-authored) заметки внутри одной сессии — это дисциплина организации межзадачного и межсессионного состояния на файловой системе. Сложились три паттерна, и ни один не общепринятый стандарт — это называемый выбор, который команда делает осознанно.

Паттерн первый — nested per-task folder, вложенная директория на задачу. Внутри могут лежать рабочие заметки, хронология действий, черновики, план отдельно от лога выполнения. Сильная сторона — богатая структура на одну задачу: можно разделить типы информации по файлам. Что ломается при масштабе: директорий растёт линейно, без дисциплины архивации — захламление; удаление ощущается как потеря истории.

Паттерн второй — single unified log, единый растущий файл, куда каждая сессия дописывает запись в конец. Сильная сторона — одна точка входа: вся хронология без знания номера задачи заранее. Что ломается: файл перестаёт помещаться в контекст агента целиком — тот же класс проблемы, что деградация точности при росте контекста. И здесь паттерн проигрывает жёстче всего в git: несколько параллельных сессий, дописывающих в один хвост файла, — магнит merge-конфликтов, причём порядок записей содержательно важен, а git не знает правильного порядка.

Паттерн третий — flat shared folder, один файл на задачу без вложенности. Сильная сторона — баланс: единая точка входа, но состояние каждой задачи изолировано в своём файле. Что ломается: список файлов накапливается без внутренней структуры — нужна дисциплина именования либо внешний индекс.
