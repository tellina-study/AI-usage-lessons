# Звонки продаж

## Assertion

«Карточка звонка: потребность, возражения, договорённости — как это построить?»

## Visual

Карточка: значок аудиозаписи звонка → стрелка → макет карточки-выжимки
(потребность / возражения / договорённости). Справа — вопрос: «Как это
построить?»

## Visual — цитата

«Хочу по каждому звонку менеджера получать карточку: потребность,
возражения, договорённости. Менеджеры перематывают запись, ищут, на чём
остановились в прошлый раз. В отделе 8 менеджеров, по 15-20 звонков в
день, телефония пишет разговор в mp3 и сама кладёт файл в облако —
выгружать вручную не нужно. CRM у нас Битрикс24, открытый REST API.
Аналитики отдела уже используют облачный ИИ по API для черновиков
квартальных отчётов. CRM, кстати, тоже пора почистить от дублей
контактов, но это отдельная головная боль».

## Speaker notes

Зачитайте реплику руководителя отдела продаж целиком. Прямой сигнал, не
выделен особо: нужна карточка-выжимка по звонку (потребность / возражения
/ договорённости), 8 менеджеров, по 15-20 звонков в день. Косвенные
сигналы стоит явно вытащить: телефония уже сама кладёт записи в облако —
не нужно решать проблему выгрузки данных отдельно; CRM Битрикс24 с
открытым REST API — карточку можно писать сразу в CRM без кастомной
интеграции; а привычка аналитиков уже пользоваться облачным ИИ по API —
косвенный сигнал, что организация психологически готова к внешнему API
и это не будет для неё новым классом риска как такового (хотя данные
звонков — не то же самое, что черновики отчётов, к этому вопрос вернётся
позже). Дубли контактов в CRM — шум-двойник: тоже про CRM, но чисто
про качество данных, не про архитектуру извлечения. На входе — запись
разговора, обычный свободный диалог между менеджером и клиентом, без
всякой структуры, с перебиваниями, паузами, отступлениями от темы, иногда
с посторонними звуками на фоне. Вопрос в зал: как это построить? Что
предложите, и почему именно так? Кто начнёт? При разборе спросите: какие
факты из реплики повлияли на ваш выбор, а какие нет?
