# Статус, два тайм-аута, и два реальных отказа

## Assertion

Зелёный статус подключения различает ровно один факт — поднялся ли процесс; для остального нужен отдельный статус, два разных тайм-аута и явное упоминание сервера в запросе, а два реальных отказа проекта показывают, как это выглядит на практике.

## Visual

`claude mcp list` (терминал) и `/mcp` (сессия) показывают один и тот же набор статусов:

| Статус | Значение |
|---|---|
| `✔ Connected` | Готов к использованию |
| `! Connected · tools fetch failed` | Процесс поднялся, список инструментов получить не удалось |
| `! Needs authentication` | Доступен, но требует входа |
| `✘ Failed to connect` | Не ответил |
| `⏸ Pending approval` | Проектный сервер, ещё не одобрен |

Минимальное доказательство работы — явное упоминание сервера в запросе; в выводе вызов инструмента подписан именем сервера.

Два тайм-аута: старт сервера (`MCP_TIMEOUT`, 30 с) и исполнение уже вызванного инструмента (`MCP_TOOL_TIMEOUT`, ≈28 ч) — два независимых таймера.

Два реальных отказа этого проекта:

- Сервер тихо потерял доступ: тестовый статус OAuth-приложения отозвал токен обновления через 7 дней без активности — статус подключения продолжал показывать «подключено».
- Сервер не стартовал вовсе: причина — незакреплённая транзитивная зависимость, ломающая импорт при старте; найдено прямым запуском команды из конфигурации в терминале.

## Speaker notes

Команда статуса показывает не один статус «подключено», а несколько разных. «Connected» — готов к использованию. Но есть отдельная строка: «Connected, но список инструментов получить не удалось» — не гипотетический случай, а встроенный в саму команду статус: продукт различает «поднялся процесс» и «обнаружены инструменты» как два разных факта.

Минимальное доказательство, что сервер реально работает, — не абстрактная проверка, а явное упоминание сервера в запросе: «используя сервер такой-то, узнай...». Признак, что ответ пришёл именно оттуда, — вызов инструмента в выводе подписан именем сервера.

Держите в голове два разных тайм-аута. Один — на старт самого сервера, тридцать секунд по умолчанию; типичная ложная тревога — пакет ещё качается, и первая проверка честно покажет отказ. Второй — на выполнение уже вызванного инструмента, и это существенно больше — около суток. Переподключение тоже устроено по-разному: удалённый сервер, оборвавшийся посреди сессии, переподключается сам; локальный процесс — нет, для него нужна новая сессия или явный запрос на переподключение.

Два реальных случая именно этого проекта. Первый: сервер тихо потерял доступ — приложение авторизации стояло в тестовом статусе, а тестовый статус автоматически отзывает токен через семь дней без активности; статус подключения при этом продолжал показывать «подключено». Второй: тот же класс сервера однажды вовсе не стартовал — причина не в логике сервера, а в незакреплённой транзитивной зависимости, ломавшей импорт при старте; нашли это прямым запуском команды из конфигурации в терминале.
