# Критерий: здесь MCP ещё не нужен

## Assertion

Если задачу решает известный CLI-вызов, разовое действие или снимок данных на момент запуска, подключать MCP-сервер рано — сложность протокола не окупается.

## Visual

Четыре компактные карточки сеткой 2×2, каждая — условие сверху, вывод снизу. Карточка 1: «Хватает gh / psql / aws через Bash» → «Задача сводится к известному CLI-вызову». Карточка 2: «Разовое или редкое действие» → «Не повторяющийся доступ, не стоит постоянного подключения». Карточка 3: «Снимок данных на момент запуска скрипта достаточен» → «Актуальность в реальном времени не критична». Карточка 4: «Нет потребности из нескольких клиентов одновременно» → «Один клиент, одна сессия — MCP не нужен, чтобы сохранять состояние между ними». Под карточками — отдельная строка-метафора в TEAL курсиве: «MCP — общий переходник к внешней системе, чтобы не писать отдельную интеграцию под каждого клиента».

## Speaker notes

MCP решает конкретную проблему — регулярный, структурированный доступ из нескольких клиентов к внешней системе, с сохранением состояния между вызовами. Если этой проблемы на самом деле нет, протокол — лишняя сложность и лишняя поверхность риска, а не польза.

Первый случай: если задача сводится к известному вызову командной строки — `gh issue list`, `psql`, `aws s3 ls` — то обычная команда через Bash решает её так же надёжно, но без токенов на описания инструментов и без дополнительной поверхности для атаки через недоверенный контент. Второй случай: действие разовое или очень редкое — тратить время на настройку постоянного подключения ради одного использования не окупается, дешевле вызвать команду напрямую. Третий случай: достаточно снимка данных на момент запуска скрипта, реальное время не критично для задачи — постоянное живое подключение не даёт здесь преимущества перед разовым запросом. Четвёртый случай: доступ нужен из одного клиента, в рамках одной сессии, без необходимости делиться состоянием между несколькими одновременными подключениями.

Вернёмся к нашему сценарию: доступ к GitHub Issues в signup-landing нужен регулярно, на каждой сессии, — это ровно тот случай, где перечисленные критерии не выполняются, и MCP-сервер оправдан. Но если бы issue заводились раз в месяц, разовый вызов `gh issue list` справился бы без всей этой конфигурации.

База, которую стоит унести с этого раздела: MCP — общий переходник к внешней системе, чтобы не писать отдельную интеграцию под каждого клиента заново, но, как и у любого переходника, у него есть цена подключения и есть более простой путь, когда вилка и розетка и так совпадают без всякого переходника.

Нюанс, который стоит проговорить отдельно: технически разные транспорты MCP несут разные гарантии личности вызывающего. Серверы с транспортом stdio берут личность из окружения самого процесса, а не из аргумента, который модель теоретически могла бы подделать. Серверы с HTTP-транспортом обязаны проходить полноценный OAuth-поток без сквозного проброса чужого токена — нарушение этого правила называется «запутанный заместитель» и уже получило собственные CVE у Atlassian. Это ещё одна причина, почему область доступа стоит проверять предметно, а не полагаться на общее впечатление о надёжности вендора.
