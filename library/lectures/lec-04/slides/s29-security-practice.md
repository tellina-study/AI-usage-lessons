# Visible content

## Title bar
Безопасность — архитектурно разорвать смертельную триаду

## Body
[Слева — Lethal Trifecta: три условия, опасно только пересечение]

**Lethal Trifecta** (смертельная триада, Willison, июнь 2025; Fowler) — опасно не каждое свойство по отдельности, а пересечение всех трёх:
1. **недоверенное содержимое** — issue, письма, веб-страницы: писали их не вы
2. **секреты и приватные данные** — ключи, токены, доступ к базе
3. **исходящая передача** (egress — канал наружу) — агент может отправить данные за пределы контура

*Сошлись все три — получился готовый канал утечки: подмена инструкции агента через прочитанный им текст (prompt injection) → взять секрет → отправить наружу.*

[Справа — четыре контроля, разрывающих триаду; каждый расшифрован на месте]

1. **least-privilege (наименьшие привилегии)** — агенту выдаём только те доступы, без которых задачу не решить. Нет ключа — нечему утекать.
2. **sandbox (изолированное окружение)** — агент работает в песочнице: его ошибка физически не достаёт до прода.
3. **egress-allowlist (белый список получателей)** — заранее перечислено, куда вообще разрешено отправлять данные; всё остальное закрыто.
4. **SAST-гейт (обязательный автоматический скан)** — SAST (static application security testing) — статический анализ кода на уязвимости до запуска; secret-scanning — поиск утёкших ключей и токенов; SCA (software composition analysis) — проверка сторонних библиотек (цепочка поставок) на известные уязвимости.

[Оговорка]
«Первый AI, остановивший атаку нулевого дня» — один отобранный случай; «AI находит 50% уязвимостей» — измерения вендора на своём же коде.

[Gold callout]
Устойчивый паттерн: обязательный автоматический скан как гейт + архитектурный разрыв триады. **Скан необходим, но НЕ достаточен**: продумать, что вообще может пойти не так, — работа человека.

## Speaker notes

Ведущее в фазе безопасности — не «какой сканер лучше», а архитектурная дисциплина, и лучший компас здесь — смертельная триада, Lethal Trifecta. Термин ввёл Саймон Уиллисон в июне две тысячи двадцать пятого, разобрав этот класс на реальных агентных инцидентах [1]; Мартин Фаулер затем закрепил рамку [2]. Идея: опасно не любое свойство агента по отдельности, а их пересечение. Первое — доступ к недоверенному содержимому: агент читает issue, письма, веб-страницы, то есть текст, который писали не вы. Второе — доступ к секретам и приватным данным: ключам, токенам, базе. Третье — способность к исходящей передаче, egress: он может отправить данные за пределы контура. Сошлись все три — подмена инструкции через прочитанный текст, prompt injection, заставляет агента взять секрет и отправить наружу [1].

Практика разрывает триаду четырьмя контролями, и каждый назовём полностью [2]. Наименьшие привилегии, least-privilege: агент получает только те доступы, без которых задачу не решить, — нет ключа, нечему утекать. Изоляция, sandbox: агент работает в песочнице, где его ошибка физически не достаёт до прода. Белый список получателей, egress-allowlist: заранее перечислено, куда вообще разрешено отправлять данные. И обязательный автоматический скан как гейт: SAST, static application security testing, — статический анализ кода на уязвимости до запуска; secret-scanning — поиск утёкших ключей и токенов; SCA, software composition analysis, — проверка сторонних библиотек, из которых собран продукт, то есть цепочки поставок.

Конкретные продукты вторичны: CodeQL и Dependabot у GitHub, Big Sleep и OSS-Fuzz у Google, скан безопасности в AWS Q — это реализации принципа, а не сам принцип [3]. И честная оговорка про громкие цифры: «первый AI, остановивший атаку нулевого дня» — один отобранный случай, а «AI находит пятьдесят процентов уязвимостей» — измерения вендора на собственном коде [3]. Скан необходим, но не достаточен: продумать, что вообще может пойти не так именно в этой системе, остаётся работой человека.
