# MCP and the server, in one screen

## Assertion

MCP is built out of six parts: what a server is and where it runs, where the connection is declared, what happens on connection and on a call, what the context and the cost are made of, and what the server answers with.

## Visual

## Speaker notes

The whole construction at once, six parts. This is the section's anchor screen: every breakdown that follows comes back to it, and it is worth coming back to yourself when something further on turns out to be unclear.

**What a server is.** A separate program living outside Claude Code. The two places where it runs are already familiar from the previous screen: a local process that Claude Code starts at your place, or a remote service that somebody else keeps. One thing is worth adding to the placement: the command written in the configuration is executed literally at the start of a session. Whatever is written there is what will start. This is an executable record, not a declaration, and the decision about the key will grow out of that fact later on.

**Where it is declared.** In a configuration file. `.mcp.json` in the root of the repository is the `project` scope: everyone who clones the project sees it. `~/.claude.json` holds the two other scopes, `local` and `user`. Which of the three is for what is broken down when the connection is assembled; what matters here is the place on the map: a connection lives in a file, the file lies in one of three places, and who will see that connection depends on the choice of place.

**What happens on connection.** Once the transport has come up, Claude Code asks the server for the list of its capabilities itself. The model takes no part in that conversation at all: it is a conversation between client and server at the level of the protocol, before the model has even seen the list — the same mechanics as the transport handshake. By default, what lands in the context out of that answer is only the tool names and the server's instructions about itself; there are no full schemas at start-up — the model pulls a particular tool's schema in later, once it has decided it will be needed. Two things cancel the deferral: the `alwaysLoad` field on an individual server loads all of its schemas at start-up regardless of the general mode, and `ENABLE_TOOL_SEARCH=false` removes the deferral across the whole environment. It is in precisely that mode that the worst-case figure the section will name further on adds up.

**The call.** When the model decides a tool is needed, the agent calls it the same way it would call a function: the full name with the server's prefix, and the arguments the model assembled itself. The format of the full name is `mcp__<server>__<tool>`, where any character outside letters, digits, the underscore and the hyphen is replaced by an underscore. This is not cosmetic: it is precisely the full name that gets written in permission rules, in a subagent's tool list or in a hook's matcher — a short one will not work there, and a mistake in it looks from the outside like "the rule is somehow not being applied".

**Context and cost — three separate line items.** The first: the names of all of the server's tools and its short instructions about itself hang in the context always, from the first second of the session, regardless of whether the agent ever uses it. The second: the full schema of a particular tool is pulled in by the model itself, once it decides it may be needed — that is deferred loading, the default behavior, and it is governed by the `ENABLE_TOOL_SEARCH` variable. The third, separate from the first two: the result of the call itself, which has a budget of its own — a warning when it goes past ten thousand tokens, truncation at twenty-five thousand by default (`MAX_MCP_OUTPUT_TOKENS`). Those three items are worth keeping apart from the very start: the standing cost is paid for the server being connected at all, the cost of a call is paid for each answer, and mixing them up produces strange numbers in both directions. The comparison across ways of getting access comes at the end of the case.

**What the server answers with.** The result arrives over a separate channel, not the one the connection went over. In the output the call is signed with the server's name — it is visible that the answer came from there and not out of the model's general knowledge. For checking the work that is the one handle available: by the text of the answer you cannot tell "the server went and fetched it" from "the model wrote something that looks like it".

Two small things people trip over more often than anything else. `local` and `user` are shown on the map with one and the same file `~/.claude.json` — that is not an error on the screen: one physical file, two different records inside it, `local` under the record for a specific project, `user` under the general `mcpServers` key. And the question "why have a protocol at all when there is an ordinary network call": because all servers describe their capabilities the same way, and the agent reads their description by one method. That is what you buy with a connection — and further on in the case it will be visible how much it costs.

On the governance of the protocol: since the ninth of December 2025 MCP has been developed by a separate directed fund under the Linux Foundation, with the same type of governance as Kubernetes. The openness of a protocol and the honesty of a particular server inside it are different things, and this section's failures will be about the second.

If something on this screen has remained unclear, it will not become clearer further on: the whole case refers back here.
