## Speaker notes

The fifth phase is code review and security, and we combine them for a reason: both are about the same second, critical look at AI's output, and both run into one mechanism — automation bias, which we introduced at the start. This is the densest section of the lecture in failures, four cases, but it is not a horror story — it is a "risk — control" frame.

The load-bearing, counterintuitive thesis of the phase: AI code must be reviewed more, not less. The reason is that the source of its defects is different. AI reproduces the frequent, including vulnerable patterns; it produces the "almost right"; it does not signal its own uncertainty; and its code lacks the familiar human "smells" of unreliability that put an experienced reviewer on guard. The other side: in capability both phases are strong — AI tools really do find bugs and vulnerabilities — but capability does not equal safety, and that is exactly why the temptation to make AI an autonomous gate is dangerous. This section: the review practice, the security practice, and four failures leading to the culmination — the Replit incident.
