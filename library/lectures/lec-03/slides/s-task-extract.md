# Visible content

## Title bar
«Как правильно задать JSON-спеку в промпте»

## Body
[Два уровня контроля]
Промпт-уровень («верни JSON по схеме») — ≈80% валидности, ничего не гарантирует жёстко. Декодер (structured outputs / constrained decoding) — схема → грамматика, недопустимые токены маскируются → ~100% соответствия схеме.

[Три способа описать форму]
Пример-объект (понятен, не выражает типы/enum); JSON Schema (типы/enum/required, но многословна и деградирует на сложной); тип в коде (TS/Pydantic — компактно, нужен конвертер).

[GOOD vs BAD]
BAD — «извлеки данные и верни JSON» без схемы. GOOD — явная схема с типами и комментариями + enum + правило для отсутствующих (null/[]) + few-shot «вход → JSON» + схема в конце + «верни ТОЛЬКО JSON».

[Нюансы]
Reasoning tax (не рассуждать в JSON: «think free → reformat»); сложная схема роняет точность (~87%→70%→56% — дробить, вложенность мелкой).

[Gold callout — инвариант]
Валидный JSON ≠ правильные данные: грамматика гарантирует форму, не истинность значений — каждый JSON проверяется в коде.

## Speaker notes

Четвёртый класс — структурированное извлечение, самый частый интеграционный стык модели с кодом. Owner-правка здесь прямая: показать не мем, а технику — как правильно давать JSON-спеку в промпте. Начинаем с рамки, которую путают чаще всего: есть два разных уровня контроля с разными гарантиями. На уровне промпта вы просто текстом просите «верни JSON по схеме» — это даёт около восьмидесяти процентов валидности и жёстко не гарантирует ничего: ни синтаксис, ни набор полей, ни типы. На уровне декодера (structured outputs, или constrained decoding) схема компилируется в грамматику, и на каждом шаге генерации токены, нарушающие грамматику, физически не могут быть выбраны — отсюда близкое к стопроцентному соответствие схеме. Поддержка на 2026-й движется, поэтому сверяйте в день лекции: OpenAI Structured Outputs со strict-режимом, Anthropic вывел structured outputs в общую доступность на Claude 4.5, Google Gemini responseSchema, из open-source — Outlines, XGrammar, GBNF-грамматики.

Дальше — как описать саму форму, три способа с компромиссами. Пример-объект понятен модели, но не выражает типы и enum. JSON Schema — машинно-проверяемый контракт, но многословна и деградирует на сложных схемах. Тип на языке кода (TypeScript, Pydantic, Zod) компактен и даёт типобезопасность, но требует конвертера. В описания полей кладут микро-инструкции: для перечислимых значений выписывают каждый вариант enum'ом, явно указывают required, держат вложенность мелкой. Сверху — few-shot из двух-трёх пар «вход → ожидаемый JSON», которые фиксируют форму лучше любого текста, и две мелочи с непропорциональным эффектом: схему в конце промпта и «верни ТОЛЬКО JSON, без markdown».

Два нюанса, которые и есть настоящая техника. Reasoning tax: строгий JSON на рассуждающей задаче роняет качество (полный разбор с числами GSM8K — на слайде форматов), лечится двухходовкой «think free → reformat». И сложная схема: точность извлечения падает даже при валидном JSON — важно направление, не точная величина. Инвариант, замыкающий класс: валидный JSON ≠ правильные данные — грамматика гарантирует форму, но не истинность значений, поэтому каждый JSON всё равно проверяется в коде. Строгая схема надёжно помогает на извлечении, классификации и function calling — и только там.
