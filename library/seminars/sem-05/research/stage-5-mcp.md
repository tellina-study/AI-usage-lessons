# Резюме (8 тезисов)

1. **Свежесть подтверждена, а не выдумана.** За неделю 20–25.09.2026 нашлось минимум одно прямое попадание в тему: 24.09.2026 раскрыты две CVE в `DBHub` (Bytebase) — MCP-сервере доступа к базам данных. Одна из них (CVE-2026-61788) показывает ровно тот класс провала, о котором курс уже предупреждает («сервер заявляет успех, но не делает того, что заявил») — только теперь это не косметический баг рендера, а флаг `readonly`, который не блокирует запись.
2. **Вторая свежая CVE (CVE-2026-61742, CVSS 9.3) — новый механизм, которого не было в базовом исследовании: DNS rebinding.** Атака вообще не требует ни prompt injection, ни участия модели — вредоносный сайт в браузере жертвы напрямую дёргает локальный MCP HTTP-эндпойнт. Это расширяет карту провалов третьим измерением: не только «агент прочитал плохой текст», но и «сервер сам — незащищённый сетевой сервис».
3. **Более старая (апрель 2026), но не попавшая в базовое исследование находка достаточно важна, чтобы включить с честной пометкой даты:** OX Security описала архитектурную (не багованную) уязвимость STDIO-транспорта в самом официальном MCP SDK Anthropic — команда процесса исполняется независимо от того, поднялся ли валидный MCP-сервер. Anthropic подтвердила: поведение спроектировано так намеренно, менять протокол отказались.
4. **Контринтуитивный поворот «одобрение не окончательно» теперь подкреплён не анекдотом, а контролируемым экспериментом.** Академическая работа (Rashidi, arXiv:2607.05744, июль 2026) показала на 3 независимых серверных библиотеках: 8 из 8 техник сокрытия доставили полезную нагрузку модели, 0 из 8 вызвали повторное одобрение, при этом человек-рецензент ничего не видит — текст спрятан в невидимом юникод-блоке.
5. **Каждая цифра в этом документе — с явной базой сравнения**, включая ранее «голые» утверждения: доля серверов без аутентификации теперь опирается на новую системную выборку (7973 живых удалённых сервера, 40,55% отдают инструменты вовсе без проверки личности — Zhou et al., arXiv:2605.22333, май 2026), а сравнение CLI/MCP по стоимости подтверждено вторым независимым бенчмарком (Scalekit, 75 прогонов, одна и та же модель и промпты — 3,20 $ против 55,20 $ на 10 000 операций).
6. **Своя дисциплина курса тоже получила проверку боем.** Раздел уже советует «ключ — в переменную окружения, не в файл». Оказалось, что даже эта практика имела дыру: Claude Code до версии 2.1.268 (~10.09.2026) печатал секрет, подставленный из `${VAR}`, открытым текстом в выводе `/mcp` и `claude mcp list` — то есть «безопасная» практика утекала через диагностическую команду, а не через файл.
7. **Классификация «предотвращаем vs решаем» подтверждается, но требует уточнения.** Само подключение MCP-сервера — специфично для проекта, ждёт сигнала (эта часть уже верно спланирована в `section-3-mcp.md`). А вот дисциплина «сначала список операций, потом вычёркивание прав» — универсальная гигиена дня 0: она не стоит дополнительного времени сверх разговора, который и так происходит при подключении, а цена её отсутствия — непредсказуема и потенциально необратима (см. инцидент 26.05.2025).
8. **Честный пробел остаётся честным пробелом.** Прямых измерений «сколько времени команда тратит на security-ревью MCP-сервера перед принятием» не найдено нигде — ни в базовом исследовании, ни в свежем поиске. Формулировка критерия «здесь ещё рано» в этом документе опирается на структурные признаки (триггер + смертельное трио), а не на измеренную стоимость самой проверки.

## 1. Что изменилось с 20.09.2026 (freshness check)

Поиск вёлся по четырём направлениям, которые запросило занятие: новые CVE/инциденты, изменения модели прав/одобрения, новые измерения стоимости определений инструментов в контексте, и общие новости governance MCP. Результат — не «пусто», но и не однородный: часть находок действительно новая (после 20.09.2026), часть — важные пробелы базового исследования с более ранними датами. Ниже они разделены явно, чтобы не выдавать старое за свежее.

### 1.1. Подтверждённо новое (после 2026-09-20)

**CVE-2026-61788 и CVE-2026-61742 (DBHub, Bytebase MCP-сервер к БД) — раскрыты 24.09.2026.**

DBHub — MCP-сервер для Postgres/MySQL/SQL Server/Oracle/MariaDB/SQLite (до версии 0.22.6/0.22.5 соответственно). Два разных механизма:

- **CVE-2026-61788 (CVSS 7.4).** Флаг `readonly = true` у инструмента `execute_sql` не делает соединение реально доступным только для чтения: код, который должен был выставить `default_transaction_read_only = on` в Postgres (или открыть SQLite в read-only режиме), заблокирован на значении конфигурации, которое никогда не заполняется — то есть просто не выполняется. Единственная реальная защита — классификатор, разбирающий первое ключевое слово запроса; любой `SELECT`, вызывающий побочный эффект через функцию, проходит мимо него. С обычной ролью это даёт манипуляцию последовательностями (sequences), с привилегированной — запись произвольных файлов (`lo_export`), чтение файлов хоста (`pg_read_file`) и выполнение кода (`dblink` + `COPY ... TO PROGRAM`).
- **CVE-2026-61742 (CVSS 9.3).** HTTP-транспорт DBHub по умолчанию слушает `0.0.0.0` без аутентификации; проверка `Origin == Host` для защиты от межсайтовых запросов из браузера обходится DNS rebinding — атакующий домен ресолвится сначала в свой IP (для прохождения проверки), затем в адрес жертвы. В результате произвольный сайт может дёргать инструменты DBHub из браузера жертвы **без единой строчки prompt injection и без участия модели вообще**.

Для занятия это две разные и важные вещи: первая — усиленная версия уже запланированного тезиса «подключён ≠ работает», но на уровень выше по ставкам (не фон слайда, а заявленная гарантия безопасности). Вторая — новый класс провала, не описанный в §A.8 плана раздела: провал совсем без ИИ в цепочке, чисто веб-уязвимость в самом MCP-сервере как сетевом сервисе.

**Claude Code, неделя 20–25.09.2026 — версии 2.1.271/2.1.273/2.1.274.** По независимому еженедельному обзору (dev.to, «This week in Claude Code…», неделя от 20.09.2026): добавлен `per-command allowed_domains` для песочницы в auto-режиме (можно разрешить конкретному вызову доступ ровно к тем хостам, которые ему нужны, и ни к каким другим); починен счётчик контекстного окна, который считал ходы «инструментов-советников» примерно вдвое дороже реальной стоимости; починен таймаут вызовов через Streamable HTTP MCP (падал примерно после 5 минут) и добавлена переменная окружения `CLAUDE_CODE_MCP_STARTUP_WAIT_MS`. Параллельно у Gemini CLI 0.60.0 — принудительная проверка идентификатора издателя токена по RFC 9207 в MCP OAuth-потоке. Это не единичный факт, а сигнал: авторизационная часть протокола продолжает уточняться у нескольких вендоров одновременно, не только у Anthropic.

**Governance:** 14.09.2026 Agentic AI Foundation запустила первую сертификацию по MCP (MCPA — Model Context Protocol Associate, пять доменов, включая отдельный домен Security & Governance). Факт нейтральный, для занятия не несёт содержательной нагрузки — упоминается только чтобы явно закрыть вопрос «не изменилось ли устройство governance» (не изменилось, это надстройка над уже описанной в базовом исследовании передачей в AAIF).

### 1.2. Важные пробелы базового исследования (даты раньше 20.09.2026, но не отражены в `05-mcp.md`)

Формально это не «свежесть» в узком смысле задания, но раз занятие спрашивает именно про изменения в модели рисков и прав — не включить их было бы нечестно перед залом. Даты указаны точно, чтобы не путать со свежими находками.

- **OX Security, «The Mother of All AI Supply Chains» (публикация 15–20.04.2026).** Архитектурная (по утверждению вендора — намеренная, не багованная) уязвимость STDIO-транспорта в официальных MCP SDK Anthropic (Python, TypeScript, Java, Rust): команда, переданная в конфигурацию STDIO-подключения, исполняется в системе независимо от того, поднимается ли по итогу валидный MCP-сервер. Anthropic, по данным статьи, подтвердила: поведение — «by design», ответственность за санитизацию перенесена на разработчиков нижестоящих проектов; протокол не изменён. Из этого единственного корня выведено 11 CVE в разных проектах (LiteLLM — CVE-2026-30623, Agent Zero, Windsurf, Flowise, DocsGPT и другие). Цифры масштаба (200 000 уязвимых инсталляций, 150+ млн загрузок, 7000+ публично доступных серверов) — из блога вендора-исследователя OX Security, методология расчёта в открытом доступе не раскрыта прозрачно, поэтому эти три числа помечены как оценка поставщика, не как независимо проверенный факт. Отдельно подтверждено: 6 живых продакшен-платформ скомпрометированы в ходе responsible disclosure — это уже не лабораторная демонстрация.
  - **Почему это важно для занятия:** уже запланированный тезис «официальность — не иммунитет» (§A.4, пример с CVE-2025-53109/53110 у эталонного Filesystem-сервера) можно и нужно усилить: там был баг в одной интеграции, здесь — намеренное архитектурное решение в самом ядре SDK, от которого зависят все сервера на этом транспорте, и вендор отказался его менять.
- **Deadbugz — активная supply-chain кампания (наблюдалась 10.08.2026, разбор Pillar Security опубликован 12.08.2026).** Через GitHub PR (23 pull request с одного аккаунта за 74 минуты 10.08.2026, часть — с готовым эндпойнтом) распространялся MCP-сервер `productivity-suite` с двумя безобидными инструментами. Первые три вызова инструментов — честно то, что заявлено. **После третьего вызова** сервер незаметно переписывает свои `tools/list`/`prompts/get`-ответы, инструктируя агента искать SSH-ключи, AWS-креды, историю шелла и Kubernetes-конфиги — и скрывать это от оператора. Порог в три вызова специально рассчитан на то, чтобы пройти ручную проверку/тест-прогон, который делает разработчик перед тем, как довериться серверу.
  - **Почему это важно:** это прямое, свежее и предметное усиление контринтуитивного поворота «одобрение не окончательно» — гораздо более коварная версия, чем `postmark-mcp` (там подмена произошла через обновление npm-пакета неделями позже; здесь подмена встроена в саму логику сервера с первого дня и рассчитана именно на обход проверки «попробовал — вроде нормально»).
- **Zhou et al., «A First Measurement Study on Authentication Security in Real-World Remote MCP Servers», arXiv:2605.22333 (22.05.2026).** Систематический скан 7973 живых удалённых MCP-серверов: **40,55% отдают инструменты вообще без какой-либо аутентификации** (база — все 7973, не подвыборка). Из 119 серверов с OAuth отдельно протестированы флаги динамической регистрации клиента — 96,6% из этих 119 имеют такой изъян. Итого 325 находок, 9 CVE получены через ответственное раскрытие.
  - **Почему это важно:** обновляет и уточняет уже присутствующую в базовом исследовании статистику Astrix (88% требуют каких-либо учётных данных из 5200+ серверов) — свежая работа даёт более чистый знаменатель именно для «удалённых» серверов и явную долю совсем без аутентификации, а не только «без OAuth».
- **Rashidi, «Unicode TAG-Block Concealment…», arXiv:2607.05744 (08.07.2026).** Контролируемый эксперимент на 3 независимых Python MCP-серверных библиотеках, 8 техник сокрытия payload в описаниях инструментов. Юникод-блок TAG (U+E0000–U+E007F) рендерится как пустота в терминале и IDE, но целиком доходит до токенизатора модели. Результат: **8 из 8** техник доставили нагрузку модели; **4 из 8** обошли санитайзер по строковому совпадению; **0 из 8** вызвали какой-либо механизм повторного одобрения; **32 из 32** «клеток» результата совпали между тремя разными библиотеками (то есть это не баг одной реализации, а системное свойство протокола); санитайзер дал **0 ложных срабатываний** на контрольном корпусе из 25 безобидных описаний — то есть проблему нельзя списать на «просто ещё не откалибровали фильтр».
  - **Почему это важно:** ранее «подмена после одобрения» держалась на одном реальном, но точечном случае (`postmark-mcp`). Теперь это подтверждено воспроизводимым экспериментом сразу на трёх реализациях — статус доказательства повышается с «единичный инцидент» до «системное свойство, продемонстрированное контролируемо».
- **CVE-2026-33032 «MCPwn», nginx-ui (исправлено 15.03.2026, раскрыто/растиражировано в апреле 2026, CVSS 9.8, активно эксплуатируется).** Панель администрирования nginx сама предоставляет MCP-эндпойнт; `/mcp` проверяет авторизацию, а соседний `/mcp_message` — нет, при этом IP-белый список по умолчанию открыт всем. Два HTTP-запроса без единого учётного данного — и захват всего управляемого nginx.
  - **Почему это важно:** отдельный практический пример третьего слоя провалов (см. §6 ниже) — классическая веб-уязвимость (CWE-306, отсутствие аутентификации), не имеющая отношения ни к модели, ни к prompt injection, но встроенная в MCP-эндпойнт. Дополняет вывод базового исследования («30+ CVE за 60 дней, ноль из них с участием модели») конкретным высокобалльным примером.
- **Claude Code 2.1.268 (~10.09.2026) — секреты из `${VAR}` печатались открытым текстом.** `/mcp`, `claude mcp list`/`get` и текст ошибок MCP login показывали значение секрета, подставленное из переменной окружения через `${VAR}`-плейсхолдер в конфиге, вместо того чтобы его маскировать (как уже маскировался буквальный заголовок). Исправлено в 2.1.268.
  - **Почему это важно:** раздел уже учит зал «ключ — в переменную окружения, а не в файл» (Ход 3, §A.5) именно потому, что тогда секрет не виден в диффе конфигурации. Этот баг показывает: сам факт вынесения секрета в окружение не гарантирует, что он нигде не всплывёт текстом — инструмент диагностики (тот самый `claude mcp list`, которым в этом же разделе предлагается проверять статус подключения) оказался ещё одним каналом утечки того же секрета. Это не отменяет практику «ключ в окружении», но снимает с неё ложное ощущение полной герметичности.
- **NSA/AISC, «Model Context Protocol (MCP): Security Design Considerations» (Cybersecurity Information Sheet, опубликовано 20.05.2026).** Первый известный государственный (не вендорский) документ по безопасности MCP. Содержательно совпадает с уже собранной картиной (границы доверия, риски сериализации, злоупотребление через агента), не добавляет новых числовых замеров, но добавляет вес источнику как независимому подтверждению серьёзности проблемы на уровне национального регулятора, а не только исследовательских блогов.

### 1.3. Обновлённые/подтверждённые измерения стоимости в токенах

Свежий поиск не опроверг ни одной цифры базового исследования — только добавил независимые подтверждения того же порядка величины:

- Независимый бенчмарк Scalekit (2026, GitHub-задачи, модель и промпты идентичны в обоих плечах, 75 прогонов, репозиторий `scalekit-inc/mcp-vs-cli-benchmark` в открытом доступе): CLI — **3,20 $**, MCP — **55,20 $** на 10 000 операций в месяц — **17×** разница по деньгам, при разбросе по токенам **4–32×** в зависимости от задачи. Это методологически более сильный источник, чем блог-пост с цифрой «1365 против 44026», на который опирается базовое исследование (тот источник там явно помечен как непроверенный) — теперь та же величина эффекта (порядок в десятки раз) подтверждена вторым, отдельным и воспроизводимым замером.
- «Line-item autopsy» (getunblocked.com, 2026): 42 000–55 000 токенов на 93 определения инструментов, ≈21% от окна в 200К — тот же порядок, что и «типичная связка из 5 серверов — 55 000 токенов» из базового исследования; расхождение в проценте окна (21% против 13,1% у `zhang-liz`) объясняется разным числом и составом серверов в выборке, обе цифры совместимы по порядку величины.

**Вывод по разделу 1:** ничего не переворачивает уже спланированную структуру занятия, но три вещи стоит добавить в материал: (а) DBHub-CVE как более острый пример «заявил — не сделал» и как первый пример провала совсем без агента (DNS rebinding); (б) Deadbugz + Unicode TAG-block работу — усилить блок «подмена после одобрения» подтверждённым, а не единичным фактом; (в) баг с утечкой секрета через `claude mcp list` — честная оговорка к собственному совету «храните ключ в окружении».

## 4. Контринтуитивные повороты (3, каждый развёрнут)

### 4.1. «Подключён» не значит «работает» — и «read-only» не значит «действительно только для чтения»

**Интуитивный ответ зала:** индикатор в `claude mcp list` зелёный, значит сервер на месте и делает то, что должен; отдельная настройка «только чтение» — это явный, декларативный флаг, ему можно доверять буквально.

**Почему это неверно:** статус подключения проверяет ровно один факт — поднялся ли процесс и отвечает ли он на рукопожатие протокола. Он ничего не говорит о том, отдаёт ли сервер инструменты модели, делает ли вызов то, что заявляет в ответе `success`, и — что оказалось самым дорогим случаем — действительно ли включена та настройка безопасности, которую вы явно указали. CVE-2026-61788 в DBHub — учебный пример именно этого: разработчики сервера **сами написали** код, ограничивающий транзакцию только чтением, но условие, при котором этот код исполняется, ссылалось на поле конфигурации, которое никогда не заполнялось. Разработчики сервера тоже думали, что read-only работает — до тех пор, пока кто-то не проверил фактическим запросом с побочным эффектом.

**Чем доказывается:** механически — официальный технический разбор GitLab Advisory Database и независимое подтверждение через GitHub Security Advisory (GHSA-mwwr-p57h-56pf), CVSS 7.4, дата раскрытия 24.09.2026, версия-фикс 0.22.6. В связке с уже запланированным в разделе примером (PowerPoint MCP: параметр фона возвращал `success`, но фон не применялся) — это тот же класс отказа, но на уровень выше по ставкам: там ломался слайд, здесь — заявленная граница безопасности.

### 4.2. Права вычёркиваются, а не выдаются — и это работает, даже когда сама инфраструктура протокола сговорчивее, чем кажется

**Интуитивный ответ зала:** «выдам агенту доступ к репозиторию» звучит как одно решение с одним уровнем детализации — либо даёшь, либо нет.

**Почему это неверно:** у широкого персонального токена по умолчанию — не «доступ к репозиторию», а доступ ко всем репозиториям пользователя (публичным и приватным), чтению и записи, настройкам, удалению — то есть единственное решение «дать доступ» молча тянет за собой десяток решений, которые никто явно не принимал. И это не гипотетическая небрежность: свежая системная выборка показывает, что подобная избыточность — норма, а не исключение. 40,55% из 7973 живых удалённых MCP-серверов вообще не проверяют, кто к ним обращается (Zhou et al.); из тех серверов, что используют OAuth, у 96,6% протестированных есть изъян в самой процедуре регистрации клиента. А на уровне не сервера, а транспорта — официальный SDK самого протокола, по данным OX Security, по умолчанию позволяет STDIO-подключению исполнить произвольную команду процесса вне зависимости от того, состоялось ли валидное MCP-рукопожатие, и Anthropic назвала это намеренным архитектурным решением, а не багом, который будет исправлен. Другими словами: даже уровень «под капотом протокола» устроен так, что «более открыто, чем нужно» — это дефолт, а не отклонение.

**Чем доказывается:** сочетание системного скана (Zhou et al., 40,55%/7973), архитектурного разбора (OX Security + независимое подтверждение TheHackerNews, апрель 2026) и уже присутствующей в базовом исследовании статистики Astrix (79% передают секреты через переменные окружения, 53% — статичные API-ключи, лишь 8,5% — OAuth). Практический вывод для раздела не меняется, только усиливается: дисциплина «сначала список операций, потом вычёркивание всего остального» — единственный способ не унаследовать избыточность по умолчанию, потому что по умолчанию избыточна не только конкретная кнопка «создать токен», а вся экосистема вокруг неё.

### 4.3. Одобрение не окончательно — и теперь это не анекдот, а воспроизведённый эксперимент

**Интуитивный ответ зала:** «я посмотрел, что делает инструмент, одобрил его один раз — дальше это решённый вопрос».

**Почему это неверно:** большинство MCP-клиентов не перепроверяют содержимое описания инструмента при каждом вызове — доверие привязано к имени инструмента, а не к текущему тексту его описания. Раньше в базовом исследовании это подтверждалось одним реальным, но точечным случаем (`postmark-mcp`, сентябрь 2025: несколько недель незаметного BCC-копирования писем после подмены уже одобренного пакета). Теперь у этого тезиса два независимых и более острых подтверждения. Первое — Deadbugz (август 2026): сервер спроектирован так, чтобы вести себя безобидно ровно столько вызовов, сколько нужно, чтобы пройти обычную ручную проверку «попробовал — вроде работает», и лишь затем переключиться на поиск SSH-ключей и облачных credentials. Второе, более фундаментальное — контролируемый эксперимент Rashidi (июль 2026): скрытие инструкции в невидимом юникод-блоке сработало в 8 из 8 попыток на трёх разных серверных библиотеках, ни разу не вызвав механизм повторного одобрения, при том что фильтр по строковому совпадению для контроля не давал ложных срабатываний — то есть проблему нельзя списать на «недостаточно осторожный» san­итайзер, она в самой архитектуре доверия по имени.

**Чем доказывается:** `postmark-mcp` (сентябрь 2025, npm-пакет) + Deadbugz (наблюдение 10.08.2026, разбор Pillar Security 12.08.2026, 23 PR с одного GitHub-аккаунта за 74 минуты) + Rashidi (arXiv:2607.05744, 08.07.2026, 8/8 успешных доставок, 0/8 повторных одобрений, 32/32 согласованных результата между тремя реализациями). Статус доказательства для этого поворота повышается с «единичный реальный инцидент» до «системное, воспроизводимо демонстрируемое свойство протокола» — и именно поэтому его стоит подать в разделе как рабочее правило («фиксируйте версию сервера, перечитывайте изменения при обновлении»), а не как страшилку про один неудачливый npm-пакет.

## 5. Предотвращаем vs решаем: куда попадает эта ступень

Ось Семинара 4 (`REWORK-REQUIREMENTS-v5.md`, §1): «универсальная гигиена — дёшево завести сразу, цена отсутствия непредсказуема, заводить проактивно на день 0» против «специфичное для проекта — ждёт сигнала».

**Само подключение MCP-сервера — специфично для проекта, ждёт сигнала.** Это уже верно закреплено в плане раздела (`section-3-mcp.md`, §A.2): триггер — «агенту нужен живой, повторяющийся доступ к внешней системе», и до этого триггера подключать нечего и незачем — цена подключения (контекст, поверхность атаки, ещё один держатель секретов) реальна и постоянна, а не разовая, так что заводить «на всякий случай» на день 0 — прямое нарушение же собственного бюджета контекста и площади атаки, которые раздел разбирает в §A.7.

**А вот дисциплина «сначала список операций → потом вычёркивание лишних прав» — универсальная гигиена дня 0, а не отдельное решение, которое можно отложить.** Обоснование по тому же критерию, что и в Семинаре 4 («дёшево — цена отсутствия непредсказуема»):

- **Дёшево завести.** Разговор «что агенту конкретно нужно уметь» и вычёркивание лишнего происходит в тот же момент, когда вы и так открываете страницу создания токена/конфигурации — это не отдельная задача, требующая отдельного времени, а способ провести уже необходимый разговор. Сравните с самим подключением: там решение «нужен ли сервер вообще» требует отдельного сигнала (issue от заказчика, повторяющаяся боль), а вычёркивание прав не требует никакого дополнительного сигнала сверх факта, что вы уже создаёте токен.
- **Цена отсутствия непредсказуема.** Разница между «токен с правами на один репозиторий» и «токен с правами на все репозитории, включая приватные» ничего не стоит в момент создания — оба варианта создаются одним и тем же кликом. Но цена отсутствия дисциплины — эксфильтрация приватных данных через публичный issue (инцидент 26.05.2025, §6 ниже), которую нельзя было предсказать заранее и от которой нельзя откатиться постфактум (данные уже опубликованы).

Отсюда практический вывод для раздела: co-building (§A.5, Ход 2) не должен подаваться как «одна из вещей, которые мы сегодня решаем» — он должен подаваться как процедура, которую нужно повторять **при каждом** подключении, вне зависимости от того, насколько сервер выглядит проверенным или официальным (см. §4.2 выше — официальность и SDK-уровень тоже не гарантируют разумный дефолт).

## 6. Провалы и ограничения (3 слоя)

### Слой 1 — безопасность: недоверенный контент как канал исполнения команд

**Механика.** Агент с широким токеном читает недоверенный внешний текст (issue, тикет поддержки, PR) в рамках обычной работы; вложенная в текст инструкция неотличима от легитимной задачи для модели.

**Примеры, дата, источник:**
- GitHub MCP — эксфильтрация приватных репозиториев через публичный issue, 26.05.2025, разбор Invariant Labs (первичный) + независимое подтверждение Simon Willison. CVE не присвоен — архитектурный класс, а не баг кода.
- Supabase MCP — утечка через тикет поддержки, июль 2025, демонстрация Simon Willison / General Analysis.
- **Новое: DBHub, CVE-2026-61742, 24.09.2026** — вариант того же слоя, но без модели вообще: DNS rebinding напрямую вызывает инструменты MCP из браузера жертвы. Показывает, что «недоверенный канал» — это не только текст, который прочитает модель, но и сама сетевая поверхность сервера.

**Масштаб с базой:** «смертельное трио» (Simon Willison, 16.06.2025) — при одновременном наличии доступа к приватным данным, обработки недоверенного контента и канала наружу атака не требует эксплойт-кода вовсе; отсутствие любого из трёх элементов делает такую атаку невозможной в принципе (не «маловероятной»).

### Слой 2 — эффективность: цена контекста и цена одного и того же действия

**Механика.** Определения инструментов занимают контекст в каждом запросе, а не один раз при подключении; для многих задач то же самое действие через CLI дешевле на порядок.

**Цифры с базой:** 55 000 токенов на связку из 5 серверов (против 0 без подключения); 26 224 токена = 13,1% окна 200К (против полного окна); CLI 1365 против MCP 44 026 токенов на одном и том же результате (32×); **новое, независимо подтверждённое:** CLI 3,20 $ против MCP 55,20 $ на 10 000 операций/мес (17×, Scalekit, 75 прогонов).

**Источник:** `05-mcp.md` §3 (zhang-liz/mcp-token-benchmark, июль 2026; независимый аудит 11 серверов, март 2026) + Scalekit mcp-vs-cli-benchmark (2026, см. §1.3 выше).

### Слой 3 — эксплуатация: провал, не имеющий отношения к модели вообще

**Механика.** Классические веб-уязвимости (отсутствие аутентификации, SSRF, path traversal) встроены в сам MCP-эндпойнт как сетевой сервис — модель, галлюцинация или prompt injection здесь ни при чём.

**Примеры, дата, источник:**
- `mcp-atlassian` — CVE-2026-27826 (SSRF), CVE-2026-27825 (произвольная запись файла) — класс «запутанного заместителя» (confused deputy).
- **Новое: nginx-ui, CVE-2026-33032 «MCPwn»** — исправлено 15.03.2026, растиражировано в апреле 2026, CVSS 9.8, активно эксплуатируется: эндпойнт `/mcp_message` не наследует проверку авторизации от соседнего `/mcp`, IP-белый список по умолчанию открыт всем — два HTTP-запроса без единого учётного данного до полного захвата управляемого nginx.
- Более старая сводка масштаба (уже в `05-mcp.md`): «30+ CVE за 60 дней» января–февраля 2026, из которых ни одна не задействует модель напрямую — три классических веб-класса уязвимостей, только предмет — MCP-эндпойнт.

**Урок для раздела:** третий слой стоит явно проговорить как отдельную категорию, не сводя всё к prompt injection — иначе у зала сложится ложное впечатление, что единственная защита от MCP-рисков — фильтровать входящий текст. Часть рисков не имеет отношения к тексту вообще, это обычная гигиена веб-безопасности сервиса, который вы запускаете локально или в сети.

## 7. Критерии «ещё рано» и «не нужно вообще»

**«Ещё рано» (критерии уже согласованы с планом раздела, §A.9 — подтверждены свежим поиском, ничего не опровергнуто):**

- Задача сводится к известному CLI-вызову — разница подтверждена дважды независимо (32× по токенам, 17× по деньгам).
- Разовое или редкое действие, а не повторяющийся доступ.
- Снимка данных достаточно, актуальность в реальном времени не критична.
- Доступ нужен только из текущей сессии, а не из нескольких клиентов с сохранением состояния.
- Нет готовности поддерживать ещё один постоянно работающий процесс с доступом к секретам.
- Отдельный стоп-критерий: подключение достраивает третий элемент «смертельного трио».

**«Не нужно вообще» — уточнение по итогам этого исследования:** даже когда все критерии выше пройдены и подключение оправдано, само по себе прохождение триггера не отменяет обязательности вычёркивания прав (§5) — это не альтернативные, а последовательные проверки. Отдельно, по итогам свежих находок, стоит явно добавить: **«не нужно вообще» — если для той же задачи достаточно read-only-режима, но сервер не даёт независимого способа убедиться, что read-only реально включён** (CVE-2026-61788 — прямой пример, когда декларативный флаг не гарантирует поведение); в этом случае разумнее либо использовать отдельную учётную запись/роль базы данных с урезанными правами на уровне СУБД (а не полагаться на флаг сервера), либо не подключать сервис в режиме записи вовсе.

## 8. Честные пробелы — что НЕ измерено и НЕ подтверждено

- **Стоимость самой проверки перед подключением** (сколько времени в среднем занимает вычёркивание прав / чтение конфигурации нового сервера) — прямых измерений не найдено ни в базовом исследовании, ни в свежем поиске. Курс формулирует критерий «здесь ещё рано» через структурные признаки (триггер, смертельное трио), а не через измеренную стоимость самой процедуры проверки — это осознанный выбор, не пробел в формулировке, но сам временной бюджет процедуры не измерен.
- **Масштаб STDIO SDK-флaw (200 000 инсталляций / 150 млн загрузок)** — цифры от вендора-исследователя (OX Security), методология расчёта публично не раскрыта прозрачно; помечено `[НЕ ПОДТВЕРЖДЕНО]` в §3. Подтверждён только факт существования флaw, номера производных CVE и 6 живых скомпрометированных систем.
- **Реальная эксплуатация Deadbugz «в дикой природе»** — задокументирована живая, работающая кампания с реальным эндпойнтом и реальными PR, но подтверждённых случаев, когда конечный разработчик действительно подключил заражённый сервер и у него украли секреты, в открытых источниках на момент сборки документа не найдено. Кампания активна и проверена исследователями на собственных тестовых вызовах, не на задокументированной жертве.
- **Точная дата фикса Claude Code 2.1.268 и полный список секрет-утечек, которые он закрыл** — источник вторичный (агрегатор еженедельных обзоров), первичный changelog Anthropic напрямую не сверен в рамках этого исследования; номер версии и формулировка фикса совпадают в нескольких независимых пересказах, но дословный официальный текст release notes не процитирован.
- **Сколько именно организаций реально используют DBHub/Bytebase в проде** — не найдено; в отличие от Asana (1000+ клиентов, официально подтверждено вендором), для DBHub нет публичной оценки распространённости, поэтому масштаб последствий CVE-2026-61788/61742 в этом документе оценивается только по механике, не по числу потенциально затронутых установок.
- **Прямое сравнение «до» и «после» появления флага `allowed_domains` в Claude Code** (сколько инцидентов оно предотвратило бы задним числом) — функция слишком новая (неделя 20–25.09.2026), эмпирических данных по эффекту еще нет и не может быть на момент сборки документа.
