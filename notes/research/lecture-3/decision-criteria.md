# Lecture 3 — Decision Criteria — Choosing an AI Architecture

**Date:** 2026-05-16 · **Researcher:** fact-checker subagent (issue #87)
Опорные источники: Anthropic "Building Effective Agents" (A1), "Context Engineering" (A2), "Multi-Agent" (A3); Cognition (A4); BigData Boutique 2026 (D8); IBM/Red Hat explainers (D9/D10). Refs → `sources.md`.

> Центральный тезис лекции: **выбор архитектуры — это инженерное решение под задачу, а не мода. Часто правильный ответ — самый простой, иногда — вообще без ИИ.**

---

## 1. Лестница сложности (правило по умолчанию, Anthropic A1)

```
обычный код (без ИИ)
   └─ если нужен NL/неструктурир. ввод →
один LLM-вызов (промпт)
   └─ если нужны свежие/приватные знания →
LLM + RAG / few-shot / context engineering
   └─ если задача — фиксированная многошаговая →
WORKFLOW (предопределённые пути кода: chaining/routing/parallel/orchestrator/eval-opt)
   └─ только если задача исследовательская/непредсказуемая И ценность оправдывает 4–15× токенов →
АГЕНТ (динамический ReAct-цикл)
   └─ только если задача широко-параллельна И независима →
MULTI-AGENT
```
**Правило:** подниматься на ступень *только* при необходимости. "Optimizing single LLM calls with retrieval and in-context examples is usually enough" (A1).

## 2. Матрица выбора архитектуры

Оси: объём знаний · частота изменений знаний · нужна свежесть · стоимость · латентность · аудит/провенанс · недетерминизм-риск.

| Критерий ↓ / Архитектура → | Обычный код (без ИИ) | Промпт (zero/few-shot) | RAG | Fine-tune (PEFT) | Long context | Агент (ReAct) | Multi-agent |
|---|---|---|---|---|---|---|---|
| **Объём внешнего знания** | н/п | мало (в промпте) | большой/растущий | поведение, не факты | средний (< ~200k ток.) | большой через инструменты | очень большой/параллельный |
| **Частота изменения знаний** | н/п | редко | **часто** ✔ | **редко** (иначе forgetting) | средне | часто | часто |
| **Нужна свежесть/провенанс/цитаты** | детерм. | нет | **да** ✔ (citations) | нет | частично | да | да |
| **Стоимость (отн.)** | мин | низкая | средняя | разовая высокая + инференс дешевле | средняя (caching ↓) | **4× чата** | **~15× чата** |
| **Латентность** | мин | низкая | + retrieval | низкая | выше (длинный ввод) | высокая (циклы) | очень высокая |
| **Аудируемость/детерминизм** | **высокая** ✔ | средняя | средняя-выс. (источник виден) | низкая (в весах) | средняя (context rot) | **низкая** | **очень низкая** |
| **Риск недетерминизма/петель** | нет | низкий | низкий | низкий | низкий | **высокий** | **очень высокий** |
| **Когда это лучший выбор** | спецификация чёткая, верифицируемо, повторяемо | общая задача, знание в модели/промпте | меняющееся знание, нужна свежесть+цитаты | стабильный тон/формат/политика/refusal; дистилляция под латентность | корпус влезает в окно, нет retrieval-инфры | непредсказуемая многошаговая, высокая ценность | широко-параллельные независимые подзадачи |

### Гибрид (норма 2026, D8/D9/D10)
RAG для **знаний, которые меняются** + fine-tune (PEFT) для **стабильного поведения/схемы/тона** + prompt/context engineering поверх. Чистый выбор "одно из" — редкость; вопрос не "RAG или FT", а "где знание, где поведение, как непрерывно оценивать".

## 3. Сформулированные критерии «КОГДА НЕ ПРИМЕНЯТЬ»

### Не применять ИИ вовсе (обычный код лучше)
- Задача детерминированная, верифицируемая, с чёткой спецификацией (парсинг, валидация схемы, арифметика, rule-based маршрутизация, фиксированная цена/политика).
- Цена ошибки юридическая/финансовая, а ответ должен быть точно корректным и одинаковым каждый раз → Air Canada/Chevrolet/MyCity (failures #4,#14): чат-бот добавил риск без выигрыша.
- ИИ добавил бы только: недетерминизм + стоимость + латентность + поверхность prompt-injection.

### Не применять RAG
- Корпус помещается в окно модели (< ~200k токенов у Anthropic) → full-context + prompt caching проще/дешевле, нет retrieval-инфры (A2).
- Нет процесса мониторинга качества retrieval/обновления индекса → молчаливая деградация на масштабе (failure #5). RAG без observability — скрытая бомба.
- Задача = отдать фиксированную политику/значение → детерминированный lookup надёжнее генерации поверх retrieval.

### Не применять fine-tuning
- Знание меняется/нужна свежесть → устаревает, дорого переобучать, catastrophic forgetting (failure #2). Используй RAG.
- Цель — добавить *факты* (а не поведение/стиль/формат) → почти всегда анти-паттерн в 2026.
- Задача неоднозначна для RFT (эксперты независимо не сходятся в ответах) → RFT навредит (A12).
- Нет eval-петли и версионирования датасета → откат невозможен.

### Не применять агента
- Задача предсказуемая/детерминированная → workflow с предопределёнными путями надёжнее и дешевле (A1, Cognition A4).
- Нет жёстких budget/loop/recursion-лимитов → риск catastrophic loop (failure #1).
- Ценность задачи не оправдывает 4–15× токенов и латентность (A3).
- Нужна аудируемость/воспроизводимость результата → недетерминизм агента противопоказан.

### Не применять multi-agent
- Подзадачи зависимы / нужен общий контекст → конфликтующие неявные решения, хрупкость (Cognition A4, failure #15).
- Большинство coding-задач (мало истинно параллельного) (A3).
- Reliability compounding не смягчён checkpoints/валидацией (failure #3).

### Не отправлять данные в провайдерский API
- Высокочувствительные/регулируемые данные без ZDR/BAA/контракта → retention может пережить вашу политику из-за судебного приказа (failure #11); third-party/MCP/Files вне ZDR (failure #12). Альтернатива: on-prem/локальная модель, минимизация PII на входе.
- Цепочка агент→инструмент→внешний API без least-privilege и изоляции недоверенного контента → утечка ключей/данных (failures #6–#10).

## 4. Чек-лист «прежде чем строить» (для слайда-резюме)

1. Можно ли решить **обычным кодом**? Если да — не добавляй ИИ.
2. Хватит ли **одного промпта** (+ few-shot)? Если да — стой здесь.
3. Знание **меняется**? → RAG (не fine-tune). Нужна **свежесть/цитаты**? → RAG.
4. Нужно стабильное **поведение/тон/формат**? → fine-tune (PEFT), не RAG.
5. Корпус **влезает в окно**? → long context + prompt caching, не RAG-инфра.
6. Задача **предсказуема**? → workflow, не агент. **Непредсказуема и ценна**? → агент **с budget/loop-лимитами**.
7. Подзадачи **независимы и параллельны**? → multi-agent (иначе single-threaded).
8. Данные **чувствительны**? → проверь ZDR/BAA/retention каждой фичи и каждого third-party инструмента; least-privilege ключи; человек-валидатор на значимых решениях.

**Человек vs ИИ (LO):** во всех ветках с генерацией — человек-валидатор проверяет *результат и факты*, а не self-rationale модели (CoT может быть unfaithful — Anthropic A5/A6). Агент делает; человек проверяет и направляет.
