# Рендерер деки Семинара 6 — как этим пользоваться

## Решение по киту: КОПИЯ, не вынос в общее место — и почему

Задание прямо предлагало выбор: вынести стабильные модули в `tools/seminar-build/`
(с правкой импортов в Семинаре 5) либо скопировать их в `sem-06/rendered/`. Выбрана
**копия**, и вот почему именно так.

Мандат этой сессии содержит жёсткий запрет: **«Не трогай `library/seminars/sem-05/**`
на запись»**. Вариант «вынос в общее место» требует правки `sem-05/rendered/build_sem05.py`
(минимум — строку `import deck_kit as K` на `sys.path`-переход в новое место) и, скорее
всего, `sem-05/rendered/make_deck_yaml.py`/`audit_grammar.py` (они тоже импортируют
`build_sem05`/`deck_kit` напрямую). Это запись в `sem-05/**` — ровно то, что запрещено
отдельной строкой, независимо от того, ломает она сборку Семинара 5 или нет. Раз вынос
без такой правки не работает, а правка запрещена, вариант «импорт из общего места»
недоступен **этой сессии** технически, а не по вкусу.

Третий форк одного и того же кода — известная болезнь репозитория (копии `build_lecNN.py`,
`notes/decisions.md` за 2026-08-11), и это осознанный компромисс, а не то, что выбрано
по умолчанию: **скопированы без единой правки** (byte-for-byte, кроме docstring-примечаний
по умолчательному имени файла) модули, у которых логика **не зависит от содержания**:

| Файл | Правка |
|---|---|
| `deck_kit.py` | НЕТ — копия без изменений |
| `slide_parts.py` | НЕТ — копия без изменений |
| `metrics.py` | НЕТ — копия без изменений |
| `check_tracks_pdf.py` | НЕТ — копия без изменений (берёт путь к `.pptx`/`.pdf` аргументом, дефолта нет) |
| `check_text_overlap_pdf.py` | НЕТ — копия без изменений (аргумент, дефолта нет) |
| `notes_budget.py` | НЕТ — копия без изменений (аргумент, дефолта нет) |
| `audit_sopostavleniya.py` | дефолтное имя файла `sem-05.pptx` → `sem-06.pptx` |
| `audit_sluzhebnoe.py` | дефолтное имя файла; `RAZDELY` (имена разделов); `TIMING_PATTERNS` (приёмы Семинара 6) |
| `qa_preview.py` | префикс `sem-05-` → `sem-06-`; дефолтные id для предпросмотра |
| `audit_grammar.py` | `import build_sem05` → `import build_sem06` |

| `build_sem06.py` | НОВЫЙ файл — по образцу `build_sem05.py`, не копия (см. ниже) |

**Рекомендация на будущее**, записанная здесь, а не исполненная: когда Семинар 5
перестанет быть «принят и не трогать» (например, откроется его собственный rework-круг)
ИЛИ когда появится третья однотипная дека — самое время сделать настоящий вынос в
`tools/seminar-build/` одной отдельной сессией с мандатом трогать оба семинара. До тех
пор два экземпляра одного и того же кода придётся синхронизировать руками при починке
общих багов (пример такой починки — ниже, в разделе «Что починено»).

## `build_sem06.py` — не копия, адаптация по образцу

В отличие от кита, `build_sem06.py` **переписан**, а не скопирован: жанровые функции
(`g_divider`, `g_cover`, `g_question`, …) и аудиты (`audit_numbering`, `audit_figs`, …)
перенесены почти буквально (их логика не завязана на содержание Семинара 5), а
регистры — `SECTIONS_BY_PREFIX`, `TAGS`, `FIGS`, `BADGE_OVERRIDE`, `PATTERN_ROLE`,
`GENRE_FN` — переписаны под Семинар 6: легаси-дека `sNN`/`deck-s50.yaml` выброшена
целиком (её в Семинаре 6 никогда не было), словарь приёмов сверен с РЕАЛЬНЫМИ слайдами
(см. ниже), а не только с планом.

### Границы разделов

```
n01–n05   Мостик     (без ступени дорожной карты)
n06–n32   MCP        (ступень 0, кейсы 1–3)
n33–n59   Субагент   (ступень 1, кейсы 4–6)
n60–n63   Сборка     (без ступени)
```

Выводятся из САМОЙ ДЕКИ по опорным приёмам (как в Семинаре 5), не только из статической
таблицы: 1-й `section_divider_macro` → начало MCP, 4-й → начало Субагента (состав 3+3),
**ПОСЛЕДНИЙ** `recap_table` → начало Сборки. Отличие от Семинара 5 в одном: там
`recap_table` встречается ровно один раз, и «первый» = «последний». В Семинаре 6 приём
`recap_table` открывает ось ДВАЖДЫ — пустой на n03 (Мостик) и заполненной на n60
(Сборка), — и если взять первый, граница Сборки съела бы всю остальную деку от n03.

### ВАЖНО: `type` ≠ `visual.pattern` — словарь приёмов сверен с написанными слайдами

`SVODKA-SLAIDOV.md` называет 14 **типов** (`type` во фронтматтере, графа «Тип» в
сводной таблице). Это НЕ то же самое, что `visual.pattern`, который реально читает
сборщик для выбора раскладки. Разница обнаружена не по плану, а по факту: на момент
сборки этого кита в `slides/` уже лежало 28 (затем все 63) настоящих файлов, и их
`visual.pattern` оказался **почти буквально словарём Семинара 5**, а не упрощённым
списком из 14 имён:

| `type` (SVODKA) | фактический `visual.pattern` |
|---|---|
| `hero_cover` | `hero_cover` |
| `section_divider` | `section_divider_macro` |
| `reflection_question` (с карточками) | `question_with_option_cards` |
| `reflection_question` (без карточек, n04/n62) | `reflection_question` |
| `recap_table` | `recap_table` |
| `criteria_boundary` | `criteria_checklist_and_boundary` |
| `research_evidence` | `evidence_table_with_gap` |
| `answer_breakdown` | `answer_breakdown_table` |
| `cobuilding` | `cobuilding_config_reveal` |
| `code_artifact` | `code_artifact` ИЛИ `file_tree_snapshot` (дерево репозитория) |
| `mechanics_map` | `mechanics_table` ИЛИ `mechanics_with_figure` ИЛИ `mechanics_debug_toolkit` |
| `failure_vignette` | `failure_vignette` ИЛИ `failure_vignette_table` ИЛИ `failure_vignette_with_figure` |
| `problem_scenario` | `problem_scenario` |
| `lecture_map` | `lecture_map` |
| `base_and_edge` | `base_and_edge` |

Первая версия этого файла держала словарь по графе SVODKA (упрощённый, 14 имён) —
починено ДО первого реального прогона, проверкой по `slides/n*.md`, а не по плану.
Урок записан отдельно: **план — не источник правды о `visual.pattern`, источник —
сами слайды.** `GENRE_FN`/`PATTERN_ROLE` в `build_sem06.py` держат развёрнутый
комментарий с этой же таблицей и датой сверки.

Семь приёмов получили СВОЮ раскладку (`GENRE_FN`); всё остальное — включая три новых
варианта, которых не было в Семинаре 5 (`failure_vignette_table`, `mechanics_table`, и
уже известные `mechanics_debug_toolkit`/`failure_vignette_with_figure`/`file_tree_snapshot`/
`cobuilding_config_reveal` — эти четыре были и в Семинаре 5) — падает в `g_content`
по умолчанию. Новый `visual.pattern`, которого нет ни в одной таблице, **не ломает
сборку**: получает `g_content`, рисуется как обычный содержательный слайд. Это тот же
принцип резинового словаря, что в Семинаре 5 («новое значение `pattern` без записи в
`GENRE_FN` получит раскладку по умолчанию — рабочую»).

## Обязательные поля фронтматтера слайда

```yaml
---
id: n06                    # ровно префикс имени файла (n06-foo.md → id: n06)
type: section_divider      # семантический жанр — словарь SVODKA-SLAIDOV.md, не влияет на вёрстку
duration_min: 0.5          # минуты, дробные (0.5, 1.25, …) — бюджет заметки и сводка по блокам
assertion: "..."           # тезис-предложение — запасной текст дивайдера + источник deck.yaml:axis
learning_goal: "..."       # методическое обоснование — НЕ печатается на слайде, для критиков/людей
visual:
  pattern: section_divider_macro   # ОБЯЗАТЕЛЬНО — выбирает раскладку; см. таблицу выше
  tag: "..."                       # ОБЯЗАТЕЛЬНО для section_divider_macro (иначе НЕТ ЯРЛЫКА)
  figure: имя-файла.png            # опционально — PNG в rendered/figures/; фаза схем ещё не начата
  primary: "..."                   # опционально — заметка для дизайнера, не на слайде
  backup: "..."                    # опционально — протокол решений, не на слайде
---

# Заголовок слайда (ровно одна строка H1)

## Assertion

Тезис-предложение (может дословно совпадать с frontmatter.assertion).

## Visual

Содержимое слайда: таблица `| … | … |`, цитата `> …`, код ```` ``` ````,
список `- …`, термины `` `a` · `b` · `c` `` (≥3), голый абзац.

## Speaker notes

Текст заметки докладчика (контракт — notes_budget.py: речь 120–180 слов
обычно / 60–100 на вопросе; справка 180–270 за швом `---`/`**Справка.**`
или оборотом «Если спросят»).
```

Поле `id`, не совпадающее с префиксом имени файла, не валит сборку — только печатает
`⚠` в `make_deck_yaml.py`. Поле `visual.pattern`, отсутствующее вовсе, тоже не валит
сборку — слайд получает приём по умолчанию (`g_content`) с пустой строкой вместо имени
приёма в отчётах.

## Как собирать Семинар 6

```bash
cd library/seminars/sem-06/rendered

# 1. Полная сборка — пересобирает deck.yaml из слайдов САМА (см. ниже), потом .pptx
python3 build_sem06.py                      # → sem-06.pptx

# 2. Сборка одного блока, пока в deck.yaml войдёт не всё (режим предпросмотра)
python3 build_sem06.py --block n            # → sem-06-n.pptx, список по slides/n*.md

# 3. Конвертация в PDF/PNG — через общую среду без root
cd /path/to/repo
source tools/presentation-build/render-env.sh
cd library/seminars/sem-06/rendered
PROFILE=$(mktemp -d)
soffice --headless "-env:UserInstallation=file://$PROFILE" --convert-to pdf sem-06.pptx
pdftoppm -r 110 -png sem-06.pdf snapshots/iter

# 4. Сторожа — СНАЧАЛА self-test, потом по деке (см. sem-05/RENDERER-NOTES.md
#    «инструмент, через который смотрят, обязан быть тем же, который собирает продукт»)
python3 check_tracks_pdf.py --self-test        && python3 check_tracks_pdf.py sem-06.pptx sem-06.pdf
python3 check_text_overlap_pdf.py --self-test  && python3 check_text_overlap_pdf.py sem-06.pdf
python3 notes_budget.py --self-test            && python3 notes_budget.py ../slides/n*.md
python3 audit_sopostavleniya.py --self-test    && python3 audit_sopostavleniya.py sem-06.pptx
python3 audit_sluzhebnoe.py sem-06.pptx        # требует актуальный deck.yaml рядом
python3 audit_grammar.py                        # сверка форм/приёмов
```

**`deck.yaml` пересобирается САМ перед каждой сборкой** (`build_sem06.main()` зовёт
`refresh_manifest()`) — тот же контракт, что в Семинаре 5: правят слайд, а не
`deck.yaml`; расхождение печатается отдельной строкой `МАНИФЕСТ ПЕРЕСОБРАН`, не тихое.
`make_deck_yaml.py` можно звать и напрямую (`python3 make_deck_yaml.py --check` —
только сверить, ничего не писать).

## Что починено при первом реальном прогоне (не унаследовано из Семинара 5)

Три находки, все — на этапе проверки собственного инструмента, не в написанных
слайдах. Коротко (без описания механизма — он в комментариях `build_sem06.py` на
местах находок):

1. **`measure()` был пересказан по памяти неверно.** Первая версия дописывала
   `xml.getparent().remove(xml)` — строку, которой в `build_sem05.py` НЕТ: там черновой
   слайд остаётся в `_scratch` и никогда не сохраняется, а не удаляется. У слайда
   python-pptx `._element` — корень ОТДЕЛЬНОЙ part-XML (не узел общего дерева
   presentation.xml), и `.getparent()` для него `None` всегда — попытка `.remove()`
   обязана падать при первом же вызове. Поймано первым прогоном `smoke_build.py`.
2. **Бутстрап с нуля падал.** `main()` читает `deck.yaml` ДО вызова `refresh_manifest()`
   — в Семинаре 5 это никогда не проявлялось (там `deck.yaml` существовал с первого
   дня), в Семинаре 6 первая в истории сборка стартует с нуля. Починено: первое чтение
   терпит отсутствие файла, если это `deck.yaml` (манифест ещё не создан) — пустой
   список, который тут же заменит `refresh_manifest()`.
3. **`deck["slides"]` не обновлялся после пересборки манифеста.** Строкой ниже
   `refresh_manifest()` код перечитывает `slides`, но цикл сборки шёл по СТАРОМУ
   `deck["slides"]`, снятому до пересборки. На бутстрапе старое чтение — пустой список,
   и цикл честно собирал 0 слайдов, в то время как аудиты (которые читают `slides`
   напрямую) отчитывались по полному манифесту — рассинхрон был бы незаметен, если
   не считать слайды в выводе. В Семинаре 5 тот же код несёт тот же дефект ЛАТЕНТНО
   (там оба чтения всегда совпадают, потому что `deck.yaml` никогда не пуст
   изначально) — записано как находка для Семинара 5, не как его дефект на практике.

Все три находки — именно то, для чего заведён смоук-тест и обязательный прогон на
собственном материале: они не всплыли бы на статическом чтении кода.

**63 слайда, 8 предупреждений, ни одного падения**:

НЕТ ГЛИФА [n21 таблица строка 4 колонка 0]     — символ ⏸ отсутствует в моноширинном начертании

НЕТ СХЕМЫ [n01 / n41 / n51 / n58]               — 4 схемы объявлены, файлов нет (фаза схем не начата)

Плюс по настоящему PDF (`check_tracks_pdf.py`) — **2 находки**, которых статическая

**Это находки для содержательных сессий, не для этого кита** — переданы в

только три собственных заглушки — `.gitignore` исключает регенерируемые `snapshots/`

## Известные ограничения (на момент сдачи)

- **Фаза схем не начата.** `FIGS = {}`, `rendered/figures/` пуст. Четыре слайда уже
  объявили `visual.figure` (n01 — hero, n41/n51/n58 — субагентские схемы) — как
  только файлы появятся в `rendered/figures/`, они подхватятся без единой правки кода
  (`figure_for()` уже их ищет).
- **`audit_sluzhebnoe.py` требует существующий `deck.yaml`** рядом с проверяемым
  `.pptx` — он читает его напрямую, а не принимает список приёмов аргументом. Если
  нужно прогнать проверку на деке, собранной БЕЗ записи `deck.yaml` (например, на
  смоук-тесте), придётся вызвать её функции (`visible_text`, `PRAVILA`, …) напрямую из
  Python, минуя `main()` — так и сделано при проверке смоук-деки в рамках этой сессии.
- **`criteria_checklist_and_boundary` пока подтверждён только по сверке словаря**, не
  по собственному наблюдению на живом слайде этого типа в момент первого прогона кита
  (сверено позже, при полной сборке — 6 слайдов, работает).
