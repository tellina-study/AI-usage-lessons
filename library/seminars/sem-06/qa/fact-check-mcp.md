### P1 — длительность инцидента `postmark-mcp` преувеличена

**Цитата:** «`postmark-mcp` (сентябрь 2025): **несколько недель** незаметно ставил скрытую
BCC-копию каждого отправляемого письма после подмены уже одобренного пакета» (§A.3.7, Слой 3);
дословно повторено в речи (§B.26): «вредоносный пакет **несколько недель** незаметно ставил
скрытую копию…».

**Что говорит первоисточник:** версия `1.0.16` с backdoor'ом опубликована **17.09.2025**
(Snyk, Qualys); пакет снят с npm по обнаружению **25–29.09.2025** (The Register, дата публикации
разбора — 29.09.2025; Qualys — 30.09.2025). Активный период скрытого BCC-копирования —
**8–12 дней**, то есть чуть больше недели, не «несколько недель».

**Откуда взялась формулировка:** в `research/stage-5-mcp.md` (строка 123) есть фраза «подмена
произошла через обновление npm-пакета **неделями позже первоначального одобрения**» — это про
**другой** промежуток (сколько прошло между первым одобрением пакета командой и моментом, когда
в версии 1.0.16 появился backdoor, за 15 версий), не про то, сколько времени backdoor работал
незамеченным. В видимой части материала (§A.3.7, §B.26) эти два разных промежутка слиты в один:
«несколько недель» подано как длительность **активной, незамеченной** подмены, а это не то, что
подтверждают первичные источники.

**Важно:** в самой речи кейса (§B.26, «Справка») формулировка **верна** — «подмена произошла
через обновление самого пакета неделями позже первоначального одобрения» — то есть справочная
часть точна, а видимый тезис в теле слайда и в произносимой части речи — нет. Это внутреннее
расхождение в пределах одного кейса, не только расхождение с источником.

**Предлагаемая формулировка:** «`postmark-mcp` (сентябрь 2025): backdoor появился в обновлении
пакета недели спустя после первого одобрения — и около полутора недель (17–29.09.2025) скрытая
BCC-копия уходила незамеченной, пока рассылку не заметили и пакет не сняли с npm».

**Источники (дата чтения 2026-10-03):**
[Postmark: Security Alert](https://postmarkapp.com/blog/information-regarding-malicious-postmark-mcp-package) ·
[Snyk blog](https://snyk.io/blog/malicious-mcp-server-on-npm-postmark-mcp-harvests-emails/) ·
[Qualys ThreatPROTECT](https://threatprotect.qualys.com/2025/09/30/malicious-mcp-server-on-npm-postmark-mcp-exploited-in-attack/)

**Уровень: P1** (искажённая величина без корректной базы — курс требует «цена в токенах… подана
как факт или названа границей»; здесь аналогичная проблема с временным промежутком).

### P2 — `requiresUserInteraction` подан без оговорки «честно только для Claude Code»

Текст (§B.24) формулирует аннотацию как встроенное исключение в «архитектуру доверия по имени у
протокола **в целом**». Сама идея доверия по имени — действительно свойство протокола в целом
(верно). Но конкретная аннотация `anthropic/requiresUserInteraction` — это **вендорское
расширение через namespaced `_meta`**, которое гарантированно соблюдает именно Claude Code;
официальная спецификация MCP не включает её в список стандартных аннотаций инструмента
(`readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`), и как минимум один источник
(`littlebearapps/outlook-assistant#271`) прямо отмечает: «other clients ignore it». Для курса,
который целиком про Claude Code, это не меняет практический вывод кейса, но стоит одна
короткая оговорка («соблюдает Claude Code; другой клиент может её игнорировать»), иначе студент
может перенести это как гарантию протокола на любой MCP-клиент.

**Уровень: P2** (отсутствует методологическая оговорка, не искажает факт для целевой аудитории
курса).
