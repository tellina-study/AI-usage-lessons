# Замер «смесь экспертов» — 4-й вариант Кейса 3, Семинара 9 (issue #299, задание З4)

Протокол прогона на живом `https://n8n.lessons.tellian.io`. Все числа ниже — результат
настоящих HTTP-отправок на опубликованные вебхуки и прямого чтения
`GET /executions/<id>?includeData=true` — то же требование, что в `../zamery-k1-k3/README.md`
и `../zamery-k4-novyy/README.md`. Самоотчёт «воркфлоу принял JSON» нигде не используется как
доказательство числа.

## Откуда задание

Владелец курса, разбирая деку Семинара 9 (расшифровка
`../../qa/kommentarii/kommentarii-2026-10-29.md`, минуты 27:20 и 27:50), дословно:

> «Давай 4-й вариант немножко поправим, потому что это похоже на миксче оф экспертс. Русские
> не знаю переводятся, когда у нас одновременно из маленьких моделей решают задачку, и потом
> модель-решатель выбирает лучше. И сделать здесь 4-й вариант, только возможно, под него надо
> будет перепрогнать исследование или тестирование.»
> «Ну, тут опять-таки не хватает отдельного столбца на 4-м слайде с числами, плюс там вместо
> прогонов давай переделаем на смесь экспертов.»

Нынешний 4-й вариант («несколько прогонов, берём самый частый ответ», `slides/n32-k3-razbor.md`
строка 60) заменяется на **смесь экспертов**: несколько маленьких моделей решают задачу
одновременно, модель-решатель выбирает лучший ответ. Задача и корпус — **те же**, что уже
измерены в `../zamery-k1-k3/` (Замер 2/4 этого же кейса), иначе сравнение четырёх вариантов
было бы нечестным — это и есть смысл «перепрогнать исследование под него».

## Постановка — унаследована без изменений

Задача, корпус из 20 вопросов (2 на каждый из 10 пунктов базы `kb1…kb10`) и 5 формальных
правил ответа взяты **импортом модуля**, не копией, из
`../zamery-k1-k3/sborka_zamer3.py` (`TEST_QUESTIONS`, `QMAP_JS`, `CONTACT_PHRASES`,
`judge_criteria_text`) — расхождение корпуса между «смесью» и «кодом»/«судьёй»/«комбинацией»
физически невозможно, потому что это один и тот же объект Python, не переписанный вручную.

Правила ответа (без изменений): не длиннее 280 символов; явно называет ключевую деталь
пункта базы; указывает, куда обращаться дальше; не содержит чисел вне пункта базы; целиком на
русском (без латиницы и иероглифов).

## Эксперты и решатель

**Доступность моделей проверена ДО кодирования id** — прямым `GET
https://openrouter.ai/api/v1/models` без авторизации, 2026-10-29 (457 моделей в каталоге на
момент проверки). Первоначальный план (`mistralai/mistral-7b-instruct`) **снят из каталога
провайдера** — именно тот класс ошибки, от которого предупреждало задание («этот проект уже
один раз споткнулся на несуществующем id», issue #303/K6). Взамен — `mistralai/ministral-8b-2512`,
тот же класс размера (7-8B), другое семейство, в каталоге присутствует.

| Роль | Модель | Семейство | Цена за токен (вход/выход), $ | Настройки |
|---|---|---|---|---|

моделей, а не разницей методик. Это прямое следование подсказке задания.

## Устройство стенда — два сценария

### `s9-m3-mix` (id `BmejEcHtrsfkpHgy`) — основной замер

`Pick KB item` (та же логика сопоставления вопроса с пунктом базы, без счётчика попыток —
смесь не переделывает) → три эксперта генерируют ответ **независимо и параллельно по
смыслу** (каждый читает только вопрос и пункт базы, не видит ответов других двух) →
решатель (`informationExtractor`, схема `{choice: "A"|"B"|"C", reasoning: string}`) получает
все три текста и выбирает лучший по тем же 5 правилам → экран результата.

Канонический порядок букв в основном замере **фиксирован на весь прогон**: A=qwen, B=llama,
C=ministral. Это сделано для простоты одного сценария на все 20 вопросов — и это честно
оговорённая цена замера, см. «Что это не измеряет» ниже.

Узлы выполняются **последовательно** (`Generate (qwen)` → `Generate (llama)` →
`Generate (ministral)` → `Resolver verdict`), не веером с merge-узлом — каждый генератор
читает `Pick KB item` напрямую по имени узла (`$('Pick KB item')`), не выход предыдущего
генератора, так что порядок выполнения не влияет на то, что каждый эксперт видит. Это проще
и надёжнее, чем параллельный merge, и не меняет изоляцию экспертов друг от друга.

### `s9-m3-mix-resolver` (id `uvksJJBFpjxeWIcD`) — решатель отдельно

Принимает вопрос и три **уже готовых** текста ответа через поля формы (`Вопрос`, `ОтветA`,
`ОтветB`, `ОтветC`) и вызывает решателя один раз — без повторной генерации. Нужен ровно для
одной вещи: подать те же три текста, что уже сгенерированы основным замером, но в другом
порядке букв, и посмотреть, изменится ли выбор. Это и есть проверка на устойчивость к
порядку (Часть Б.5 задания) — она ничего не генерирует заново, поэтому стоит всего 1 вызов
модели на вопрос, не 4.

Код сборки обоих сценариев — `sborka.py`.

## Проверка на протечку

`proverka_protechki.py` — механическая проверка собранных промтов (`n4mix-mix.json`,
`n4mix-resolver.json`) **и** выложенных на стенд сценариев (`--stend`, читает
`GET /workflows/<id>` напрямую, не локальные файлы — выложить можно не то, что собрано).

Проверено: (1) промт решателя не содержит кодового вердикта ни по одному из трёх
вариантов — решатель не может скопировать готовый ярлык; (2) промт решателя не называет,
какая модель стоит за какой буквой; (3) ни в одном промте нет образца заполненного
решения; (4) промт решателя не содержит ярлыков «правильный ответ»/«эталон»; (5) поля
формы — ровно те, что уходят в промт.

**Находка самой проверки, первый прогон.** Первая версия скрипта проверяла **шаблон** промта
до вычисления n8n-выражений и дала 3 ложные тревоги: `{{ $('Generate (qwen)').item.json.text
}}` содержит строку «qwen» как ИМЯ УЗЛА СБОРКИ (служебная адресация), а не как текст, который
увидит модель — к моменту отправки это выражение заменяется реальным ответом эксперта. Это
тот же класс ложного срабатывания, что уже назван в `CLAUDE.md` для `grep -P` по кириллице
(совпадение есть в непроверенном представлении, а не в том, что реально доходит до адресата).
Починено — проверка снимает `{{ ... }}` **до** поиска маркеров (`strip_expressions()`), и
прогнана повторно. После починки:

```
Протечки не найдено (проверено по ВЫЛОЖЕННЫМ на стенд сценариям).
```

Других кандидатов на протечку в этой задаче структурно нет: в отличие от K6 (секретная сумма
квитанции) или Кейса 1 (секретный пункт базы, который нужно угадать), здесь у модели нет
скрытого правильного ответа отдельно от самих правил — правило 2 промта («явно включи деталь
X») это и есть требование к форме ответа, та же конструкция уже стоит в промте генератора
`zamery-k1-k3` и уже была измерена там; это не новый риск этого замера.

Посчитаны `analyze.py` — грейдинг прочитанных текстов (не самоотчёт) той же логикой, что

**2. Верный ответ был среди трёх экспертов (потолок приёма): 20 / 20 (100%).** На каждом из
20 вопросов хотя бы один из трёх экспертов дал ответ, формально проходящий все 5 правил —

виновато — верный вариант физически лежал перед решателем).

**4. Цена.** 80 вызовов модели на 20 вопросов — **4,0 вызова на вопрос**, фиксировано (нет

в `zamery-k1-k3` и на n40: `GET https://openrouter.ai/api/v1/models` без авторизации,
прочитан 2026-10-29, не выписка по счёту.

**5. Держится ли выбор за порядок: удержался в 6 из 12 (50%).** На подвыборке из 12 вопросов

## Сводная таблица — смесь экспертов против трёх остальных способов

Код/судья/комбинация — числа `../zamery-k1-k3/README.md`, § «Замер 4», execution 969–1031,
тот же корпус из 20 вопросов.

| Сборка | Сошлось / 20 | Вызовов на вопрос | Вызовов всего (20 вопросов) | Цена (20 вопросов) |
|---|---|---|---|---|
| проверка кодом | 20/20 (100%) | 1,0 | 20 | $0,0007 |
| судья-модель (цикл, до 3 попыток) | 18/20 (90%) | 2,8 | 56 | $0,0031 |
| комбинация код+судья (строгая, до 6 попыток) | 17/20 (85%) | 4,0 | 80 | $0,0047 |
| **смесь экспертов (новый вариант)** | **14/20 (70%)** | **4,0** | **80** | **$0,0042** |

**На чём смесь экспертов лучше.** Единственное её структурное преимущество — число вызовов
НИКОГДА не растёт сверх фиксированных 4: ни код, ни судья, ни комбинация не умеют предсказать
цену заранее (цикл может сойтись за 1 попытку или упереться в потолок), а смесь экспертов
стоит РОВНО 4 вызова всегда, независимо от того, насколько трудный вопрос. Предсказуемость
цены — это весь выигрыш.

**На чём она хуже — и это главное.** По доле сошедшихся (70%) смесь экспертов — **худший из
четырёх вариантов**, хуже даже строгой комбинации код+судья (85%), которая сама уже была
признана наименее надёжной из первых трёх. При этом верный ответ был доступен решателю в 100%
случаев (число 2 выше) — отставание не в том, что эксперты плохи, а в том, что САМ ВЫБОР
плохой: решатель отбрасывает верный вариант в 30% случаев, когда он лежит перед ним. Цена
близка к комбинации ($0,0042 против $0,0047), то есть смесь экспертов — почти такая же
дорогая, как самый дорогой из уже измеренных вариантов, и при этом даёт худшее качество.

**Во что обходится.** Главная находка — не цена, а находка №5: выбор решателя наполовину
держится за порядок, в котором лежат варианты, а не за их содержание. Это прямая параллель
уже измеренному на судье (n40, Zheng и соавторы, arXiv:2306.05685: сильная модель держит
решение в 65,0% случаев при перестановке, слабая — в 23,8%). Решатель этого замера — ТА ЖЕ
модель, что судья в деке (`qwen/qwen-2.5-7b-instruct`) — держит решение в 50% случаев на
нашей подвыборке: число лежит МЕЖДУ измеренными внешними точками 65,0% и 23,8%, ближе к
слабой стороне, чем к сильной. Содержательно это означает: «решатель выбирает лучший ответ»
неточно описывает происходящее — половину времени он выбирает ответ, который оказался на
определённой позиции, а не тот, что лучше по содержанию.

**Отдельная, более резкая находка — доминирование одной позиции независимо от качества.**
В основном замере (фиксированный порядок A=qwen, B=llama, C=ministral на всех 20 вопросах)
решатель выбрал вариант C (ministral) **17 раз из 20 (85%)** — при этом ministral
**индивидуально худший** из трёх экспертов по доле формально верных ответов (65%, против
90% у qwen и 85% у llama, см. ниже). Если бы решатель действительно судил по качеству, он
должен был бы выбирать qwen или llama чаще, чем ministral — вместо этого он выбирает
ministral почти всегда. Это сильнее, чем просто «порядок играет роль» — это говорит, что
решатель на этом стенде систематически предпочитал последний по порядку вариант (или его
содержание) независимо от того, хуже он или лучше двух предыдущих.

| Эксперт | Модель | Доля формально верных (независимо, 20 вопросов) | Как часто выбран решателем (основной замер, фикс. порядок) |
|---|---|---|---|
| qwen (A) | qwen/qwen-2.5-7b-instruct | 18/20 (90%) | 1/20 (5%) |
| llama (B) | meta-llama/llama-3.1-8b-instruct | 17/20 (85%) | 2/20 (10%) |
| ministral (C) | mistralai/ministral-8b-2512 | 13/20 (65%) | 17/20 (85%)|

**Честная оговорка про возможную причину.** Промт решателя перечисляет варианты в порядке
A→B→C и СРАЗУ после варианта C идёт текст правил («Правила, которым должен
соответствовать...») — это может быть не только позиционное предпочтение «последнего в
списке» вообще, а эффект близости к инструкции (recency), специфичный для КОНКРЕТНОЙ формы
этого промта, не доказанное универсальное свойство резолверов. Эта оговорка не отменяет
находку (решатель объективно выбирал C 85% времени при фиксированном порядке, а в
переставленном порядке выбор держался только в половине случаев) — она ограничивает вывод:
измерено поведение ЭТОГО промта на ЭТОЙ модели, не доказана природа эффекта (чистая позиция
vs близость к инструкции vs что-то ещё).

## Что это НЕ измеряет — честные оговорки

1. **Основной замер (20 вопросов) использует ОДИН фиксированный порядок букв на всех
   вопросах** — качество отдельных экспертов (90%/85%/65%) и частота их выбора (5%/10%/85%)
   в основном прогоне СЛИТЫ с позицией: qwen всегда A, ministral всегда C. Перестановочная
   проверка (число 5) частично разводит эти два эффекта, но только на подвыборке из 12
   вопросов из 20, не на всех — разброс (50% held) мог бы быть другим на полном корпусе.
2. **Перестановочная проверка меняет местами только A и C**, не прогоняет все 6
   перестановок трёх элементов (не входило в бюджет: полный факториальный прогон на весь

## Терпимая проверка — перемер той же проверки, терпимой к русской морфологии

**Откуда взялось.** Ручная построчная сверка «решатель выбрал неверный ответ при наличии
верного» (6 строк из построчного разбора `analyze.py`) показала, что все шесть — не ошибки
модели, а артефакт двух хрупких к русской морфологии правил нашей собственной проверки:

1. **деталь** (`kb_keyword`) сверяется точной подстрокой в цифровой записи («24 час»,
   «10 рабочих дней», «5 рабочих дней») — модель, написавшая число **словами** («двадцать
   четыре часа», «десяти рабочих дней»), отвергается, хотя смысл верен;
2. **контакт** сверяется точными подстроками `['администратор', 'личный кабинет',
   'преподавател', 'сотрудник', 'руководител']` — «администрацию» не содержит «администратор»
   (другое слово того же корня, не падеж), «личного кабинета» не содержит «личный кабинет»
   (другой падеж первого слова словосочетания) — склонение роняет правило оба раза.

Три оставшихся правила (длина 280, числа вне базы, латиница/иероглифы) не хрупки к
морфологии и НЕ менялись.

**Новая проверка — не правка существующей.** `analyze.py`, `code_check_node()` в
`zamery-k1-k3/sborka_zamer3.py` и `judge_criteria_text()` не трогаются — они уже измерены и
опубликованы как «буквальная проверка». Терпимая проверка — отдельный файл
`peregreyd_terpimyy.py`, вторая, параллельная проверка тех же уже сохранённых текстов. Ни
одного нового вызова модели не сделано — весь перегрейд читает `raw/mix-20.json` и
`../zamery-k1-k3/raw/zamer3-judgecheck-20.json`.

### Как устроена терпимая проверка

**Деталь.** Для трёх вопросов корпуса, где деталь — число с остатком («24 час», «10 рабочих
дней», «5 рабочих дней»), деталь считается найденной, если видна **либо** цифровая запись,
**либо** словесная запись числа (регулярка на каждый падёж, встречающийся в естественном
ответе — именительный/винительный, родительный/дательный/предложный, инструментальный — для
ВСЕХ чисел корпуса: 5, 10, 18, 24, 3000, не только для попавшихся в этом замере), **и**
остаток («час», «рабочих дней») присутствует как и раньше. Остаток не менялся осознанно:
числительные 5/10/24 управляют тем же падежом существительного что цифрой, что словом («10
рабочих дней» и «десять рабочих дней» — оба родительный падеж множественного числа), хрупким
было только само число. Для деталей без числа (`kb5` — уже regex с Починки 2026-10-26; все
остальные — стем без окончания) логика не менялась, они уже были терпимы к падежу.

**Контакт.** Пять точных фраз заменены на пять стемов: `администра` (ловит и «администратор»,
и «администрацию»/«администрация» — РЕШЕНИЕ, заложенное явно: это другое слово того же
смысла, не падеж, владелец прочитал «обратитесь в администрацию центра» как верный ответ),
`кабинет` (второе слово словосочетания «личный кабинет» — первое склоняется, второе в этом
контексте не меняет корень), `преподавател`/`сотрудник`/`руководител` — без изменений, уже
были стемами.

**Честная оговорка про правило «числа не из базы» (задание требует разобрать явно, не
промолчать).** Если деталь написана словами, в тексте может не быть ни одной цифры вовсе —
тогда `re.findall(r"\d+", answer)` возвращает пустой список, и правило проходит **впустую**
(нет цифр — нет нарушения), не потому что что-то подтверждено. Это не новая дырка: правило
всегда искало цифры, не числительные, и случай «чужое число словами» им не поймать ни
буквальной, ни терпимой версией — граница была и раньше, терпимая проверка её не расширяет и
не сужает.

### Перегрейд — что честно, что нет

**Смесь экспертов** (`raw/mix-20.json`, 20 записей: тексты трёх экспертов + выбор решателя) и
**судья-check** (`../zamery-k1-k3/raw/zamer3-judgecheck-20.json`, 20 записей: `answer`,
`code_ok`, `code_reason`, `judge_ok`) — оба перегрейжены, оба сохранили исходные тексты, оба
не участвовали в цикле «переделай пока не сойдётся».

**Код (`s9-m3-code`) и строгая комбинация код+судья перегрейдить НЕЛЬЗЯ честно — и не надо.**
Обе сборки переделывают ответ до тех пор, пока он не пройдёт ИМЕННО эту проверку (комбинация —
код как одно из двух условий остановки), а эта же проверка потом служит и оценкой качества.
Повторная проверка их финального сошедшегося ответа терпимой версией той же проверки даст
100% тавтологически (терпимая — надмножество буквальной: то, что уже прошло буквальную,
проходит и терпимую) — это НЕ измерение, это свойство устройства цикла. Их опубликованные
числа (100% / 85%) остаются мерой буквальной проверки и ничем больше; это важная оговорка к
уже стоящему на деке числу, не придирка.

**Бонус — вариант «судья-цикл» (`s9-m3-judge`, `zamery-k1-k3/raw/zamer3-full-20.json`,
переменная `variants.judge`).** Приёмный критерий здесь — мнение модели-судьи, не наш код,
поэтому его попытки честно перегрейдить нашей проверкой — это НЕ тавтология (наш код не был
его собственным критерием остановки). Результат: из 28 попыток судейского цикла по всем 20

Ни один из этих трёх не был выбран решателем ни в одном случае — отсюда число 1 (резолвер
верен 20/20): терпимая проверка не «пропускает всё», она ловит настоящие промахи и отвергает
настоящие, не ловит мнимые.

### Вариант «судья-check» (`zamer3-judgecheck-20.json`) — терпимая проверка здесь ничего не меняет

| | Исходный `code_ok` (JS, буквальный) | Терпимая (Python, этот файл) |
|---|---|---|
| Сошлось | 20/20 | 20/20 |

Переходов и регрессий — ноль. Это ожидаемо, не «не нашли»: эти 20 текстов — попытки-1
кодового варианта Замера 4, которые по устройству замера УЖЕ были буквально верны (код там
сходится в 1,00 попытки в среднем на всех 20 вопросах — см. раздел «Замер 4» в
`../zamery-k1-k3/README.md`). Расхождение `code_ok` (20/20) против `judge_ok` (1/20) на этом
наборе — самопротиворечие модели-судьи (ложные «длина >280», номер правила вместо причины
отказа, забракованное легитимное число 18), не морфологическая хрупкость нашей проверки; эта
находка уже задокументирована в `../zamery-k1-k3/README.md` и не переоткрывается здесь.

### Вердикт по спорному выводу

**Вывод «решатель в 85% выбирает слабейшего эксперта» и «качество смеси ниже остальных
вариантов на 30% из-за плохого выбора» — СНИМАЮТСЯ, не держатся терпимой проверкой.**

- Решатель выбирает ответ, формально верный **в 20 из 20 случаев** (число 1 и число 3 = 0%),
  не в 70% с 30%-ным провалом выбора.
- «Слабейший» эксперт (ministral, 65%) оказался единственным 100%-верным формально — выбор
  решателя в его сторону (85% времени, позиция C) при терпимой проверке больше не выглядит
  предпочтением худшего: по форме ответа ministral — лучший из трёх.
- Держится то, что измерено НЕЗАВИСИМО от формальной верности — устойчивость к порядку
  (находка №5, 50%, грейдинг на неё не влияет по конструкции замера). Это остаётся
  действующей находкой: при перестановке букв решатель меняет выбор идентичности в половине
  случаев, значит порядок варианта всё ещё частично определяет выбор отдельно от содержания.

**Чем теперь держится остаточная находка.** Решатель не «выбирает по смыслу хуже остальных» —
он выбирает по позиции (C, 85% времени при фиксированном порядке) и это коррелирует (но не
доказано как причина) с тем, что ответы на позиции C/ministral в среднем самые длинные и
развёрнутые:

| Эксперт | Средняя длина ответа (20 вопросов) |
|---|---|
| qwen (A) | 149,6 знаков |
| llama (B) | 154,8 знаков |
| ministral (C) | **182,5 знаков** |

Выбранный решателем ответ — самый длинный из трёх экспертов в **13 из 20 (65%)** случаев;
средняя длина выбранного ответа (181,2 знака) почти совпадает со средней длиной ministral
(182,5). Когда решатель выбирал C, ministral был самым длинным из трёх в 12 из 17 таких
случаев (71%).

**Честная оговорка — это корреляция, не доказанная причина.** Позиция (C всегда = ministral)
и длина (ministral в среднем длиннее) слиты в этом замере так же, как позиция и идентичность
были слиты в основном замере до перестановочной проверки (см. «Что это НЕ измеряет»,
пункт 1) — нельзя разделить «решатель предпочитает длинные/полные ответы» от «решатель
предпочитает позицию C» на этих данных. Кандидат на замену снятого вывода: **решатель
склонен выбирать самый полный ответ, а не хуже остальных по содержанию** — это согласуется и
с тем, что 100%-верный (терпимо) ministral выбирается чаще других, и с тем, что перестановка
букв меняет выбор в половине случаев (длина и позиция у трёх текстов при перестановке не
меняются, но ПОЗИЦИЯ меняется — если бы решатель судил чисто по длине/полноте текста, выбор
держался бы жёстче, чем измеренные 50%). Разделить эти два фактора — предмет отдельного
замера (полная факториальная перестановка не входила в бюджет этого, см. оговорка №2 раздела
«Что это НЕ измеряет»), не предъявляется здесь как доказанное.

### Это находка, не чинка измерения

Случившееся — живая иллюстрация утверждения, которое сам Кейс 3 разбирает про вариант
«проверка кодом»: формальная проверка **надёжна ровно настолько, насколько надёжен сам
критерий**, и ловит она форму, а до смысла добирается только через форму. Написанный
небрежно критерий забракует верный ответ. Наша собственная проверка это и сделала — шесть раз
из двадцати, причём систематически против одного эксперта (ministral), который чаще других
писал полно и естественно. Материал для занятия: не «модель А хуже модели Б», а «проверяющий
код такой же участник эксперимента, как и модель, и его ошибки так же стоят разбора».

**Это третий раз подряд в этом производстве**, когда собственный автоматический грейдер
расходится с чтением глазами (первые два — `../zamery-k5-povtorno/README-fewshot-desc.md`,
разделы «Автоматический грейдер и ручная проверка разошлись» / «...снова разошлись»). Правило
закреплено в каноне: `tools/seminar-production/README.md` §8.12 «Собственный грейдер —
третий раз расходится с чтением глазами», с адресами всех трёх случаев. `§8.6` того же файла
— про отдельный, не пересекающийся класс отказа (границы слов `grep -P` на кириллице), не
дублирует.

## Данные

- `sborka.py` — сборка и публикация `s9-m3-mix` + `s9-m3-mix-resolver`, импортирует корпус
  `TEST_QUESTIONS`/`QMAP_JS` из `../zamery-k1-k3/sborka_zamer3.py` (не копия).
- `n4mix-mix.json`, `n4mix-resolver.json` — собранные сценарии (выход `sborka.py` без
  `--push`), использованы для локальной проверки на протечку до публикации.
- `stend-ids.json` — id опубликованных сценариев на стенде.
- `proverka_protechki.py` — проверка на протечку (по файлам и по стенду, `--stend`).
- `run_zamer.py` — основной прогон 20 вопросов через `s9-m3-mix`, возобновляемый (пропускает
  уже посчитанные вопросы при повторном запуске). Флаг `--only N` — ограничить калибровкой
  первых N вопросов.
- `run_permutatsiya.py` — перестановочная проверка (12 вопросов) через `s9-m3-mix-resolver`,
  переиспользует уже сгенерированные тексты из `raw/mix-20.json`, новой генерации не делает.
- `analyze.py` — сводка: пять чисел Части Б, доли верных по эксперту, построчный разбор.
  Грейдинг — Python-копия `code_check_node()` из `zamery-k1-k3/sborka_zamer3.py`.
- `raw/mix-calib.json` — исходный калибровочный прогон (вопрос 1 один), сохранён как есть;
  его единственная запись — та же, что первая запись `raw/mix-20.json` (скопирована туда
  перед продолжением на вопросы 2-20, не пересчитана заново).
- `raw/mix-20.json` — полный результат основного замера: по каждому из 20 вопросов — тексты
  всех трёх экспертов, их токены и цена, выбор решателя и его объяснение, execution id.
- `raw/permutatsiya-8.json` — результат перестановочной проверки (имя файла — исторический
  артефакт первого прогона на 8 вопросах; содержимое расширено до 12, см. `subset_indexes`
  внутри файла).
- `peregreyd_terpimyy.py` — терпимая к русской морфологии проверка (см. раздел «Терпимая
  проверка» выше): самопроверка на испорченном входе + перегрейд `raw/mix-20.json` и
  `../zamery-k1-k3/raw/zamer3-judgecheck-20.json` без единого нового вызова модели.
- `raw/peregreyd.json` — выход `peregreyd_terpimyy.py`: обе колонки (буквальная/терпимая) по
  каждому эксперту на каждом вопросе, построчные переходы, результат перегрейда судьи-check.

## Как пересобрать

```bash
cd library/seminars/sem-09/stend/zamery-k3-smes
set -a && source /home/harness/.n8n-lab-credentials && set +a

# Собрать локально и проверить на протечку ДО публикации
python3 sborka.py
python3 proverka_protechki.py

# Опубликовать на стенд (идемпотентно — обновляет по имени, если уже есть)
python3 sborka.py --push
python3 proverka_protechki.py --stend   # повторная проверка того, что реально выложено

# Основной замер (20 вопросов × 4 вызова = 80)
python3 run_zamer.py --output raw/mix-20.json

# Перестановочная проверка (12 вопросов × 1 вызов решателя = 12)
python3 run_permutatsiya.py --source raw/mix-20.json --output raw/permutatsiya-8.json

# Сводка (буквальная проверка)
python3 analyze.py raw/mix-20.json raw/permutatsiya-8.json

# Терпимая проверка — перегрейд уже сохранённых текстов, без новых вызовов модели
python3 peregreyd_terpimyy.py
```
