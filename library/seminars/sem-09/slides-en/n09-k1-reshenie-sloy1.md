# Where the "answer or hand off" decision lives

## Assertion

The step is the same either way. The difference is whether its decision leaves a trace that can be read apart from the answer.

## Visual

> The same request, the same knowledge base. The difference is where the "answer myself or hand off to a human" decision lives: on the left, inside the answer text; on the right, in a separate field that code checks.

> **Next, we see what actually happens in practice.** We build the left version, run it on real questions, and look at the result. Then we build the right version and run it on the same questions.

## Speaker notes

We're deliberately looking at both forms with no single node name and no tool name: if this chain is built tomorrow in a different orchestrator than the one we use, not one line here would change.

Read the diagram by its three rows on the left. What the model does — the same in both panels: it reads the knowledge base, writes an answer. Where the decision is recorded — here the panels diverge: on the left, the decision is recorded nowhere separately, it's dissolved into the text the model composed; if it declines, the text will be a decline, if it answers, an answer, and the process reads and checks none of that difference. On the right, the model is additionally required to name the knowledge-base item it's grounded in, as a separate value, and the decision is now made by a condition in code that checks that value.

The third row — who can check it. On the left, the decision can only be read inside the answer, after the fact, by eye. On the right, it can be checked separately from the answer, by the same code, on any next question.

What doesn't change between the panels is worth saying separately, because it's easy to lose: the model is the same, the knowledge base is the same, and it can make mistakes exactly the same way. Only the place where the decision lives changes.

Notice one more thing deliberately left undrawn here. Both panels are equally honest about what the model does and where the decision is recorded, but neither says which of the two versions answers better. That's not an omission — it's exactly what we're about to check in practice, not in words. The left version is easier to build and easier to explain to a client at first glance: one call, one piece of text, no extra logic around it. The right one looks excessive right up until someone asks why a specific request was answered on its own without calling in a human — and it turns out only this version can answer that question.

Next, we check this in practice. We build the left version, I'll show the real rig, we run it on real questions. Then we build the right version and run it on the same ones.
