# Семинар 7 — сетка кейсов

**Тема занятия:** первый работающий процесс, за который можно отвечать. Автоматизация
процессов как дисциплина и что в ней изменили языковые модели; девять классических типов
блоков и их имена в n8n; полный классификатор со справочником; что справочник не гарантирует;
поведение при отказе; черновик против опубликованного.

**Состояние сквозного процесса:** на входе пусто, на выходе — работающий сценарий из
шести узлов с экраном результата, выгруженный в файл `stend/student.json`.

**Состав:** введение (2 экрана) + теория (4 экрана) + 4 технических кейса + 1 концептуальный.
**Шесть тактов на кейс:** дивайдер → постановка и вопрос залу → разбор вариантов → наше
решение вживую → **обобщение** (принцип для любого инструмента) → **нюансы** (три класса
проблем). Пятый и шестой такты добавлены/переписаны 2026-10-12 по правке владельца: «теперь
это стало просто методичкой по n8n».

**Формат ведения — живое демо с ноутбука, снимки как страховка** (решение владельца
2026-10-12). Такт «наше решение» в каждом кейсе ведущий собирает вживую на своём стенде.
Слайд при этом самодостаточен: на нём принципиальная схема и снимок холста, так что при
отказе техники занятие идёт без потерь и без переключения режимов.

## Введение и теория до первого кейса

Переписаны 2026-10-12 по правке владельца: «введение непонятное, о чём» и «схему можно
переиначить на типы классических блоков и их отображение на n8n явно».

### Введение: автоматизация процессов (два экрана)

**Экран 1 — дисциплина старая.** Процесс — описанная последовательность шагов с условиями и
обработкой сбоев; автоматизация — когда шаги выполняет механизм. Четыре примера, которые
аудитория видела на работе: сборка и доставка кода, перенос данных между системами, заявки и
согласования, интеграции между сервисами. У всех четырёх одно устройство: что-то запускает
процесс, дальше шаги, между ними условия, на сбое — заранее описанное поведение.

**Экран 2 — что изменили языковые модели.** Один новый тип блока: шаг, принимающий решение
на неструктурированном входе. Четыре строки про то, кто делал эту работу раньше: человек ·
набор правил по ключевым словам · отдельная обученная модель под одну задачу · **никто —
работу не делали, дорого**. Последняя строка и объясняет, почему тема возникла: порог
стоимости упал на порядки.

Отсюда рамка дуги: триггеры, условия, циклы, обработка ошибок — старые, и правила для них
выработаны десятилетиями. Нов только шаг модели, и нов он тем, что **может ошибиться
незаметно**. Шов с С4–С6 встроен сюда же.

### Теория: девять типов блоков и их имена в n8n

Несущий экран всех шести занятий — таблица в три колонки: тип блока, что делает, чем
является в n8n.

| Тип блока | В n8n это |
|---|---|
| триггер | Form Trigger · Webhook · Schedule Trigger · Manual |
| действие | HTTP Request · Data Table · отправка письма |
| преобразование | Edit Fields (Set) · Code |
| условие | If · Switch · Filter |
| цикл | Loop Over Items |
| слияние | Merge |
| подпроцесс | Execute Sub-workflow |
| обработчик сбоя | настройки узла · Error Trigger · Stop and Error |
| **шаг модели** | Basic LLM Chain · Information Extractor · Text Classifier · AI Agent |

Девять строк соответствуют девяти ступеням лестницы дуги (`KONTSEPTSIYA-7-12.md` §6): на
каждом занятии закрывается своя строка этой же таблицы. С7 закрывает четыре — триггер,
действие, преобразование, шаг модели — и захватывает обработчик сбоя.

### Теория: как данные ходят в n8n (два экрана)

Подаётся **как особенность конкретного инструмента**, а не как свойство процессов вообще —
по правке владельца и по сути: в Activepieces шаг получает один объект, а перебор задают явно.

**Экран 1 — правило.** Между узлами всегда идёт список элементов, даже когда элемент один;
каждый элемент — объект с обёрткой `json` (и `binary` для файлов), отсюда `$json.поле` в
выражениях. Правило: **узел выполняется по разу на каждый элемент списка**.

**Экран 2 — четыре следствия.** «Узел отработал 5 раз» в журнале · пять писем вместо одного ·
отдельный блок цикла нужен реже, чем кажется · настройка **Execute Once** для «один раз на
весь список».

Разделено на два экрана не ради красоты: на одном таблица следствий уходила на 9 пунктов и
вылезала за рабочее поле — ровно та нечитаемость, на которую указал владелец.

### Теория: выражения в n8n

Переключатель «фиксированное значение / выражение» у каждого поля. Четыре формы: `$json.поле`
(текущий элемент) · `$('Имя узла').item.json['Поле']` (любой предыдущий, по имени на холсте) ·
встроенные величины вроде `$now` · `||` как запас на пустоту. Предупреждение: переименование
узла ломает все выражения, которые на него ссылались, и инструмент об этом не предупреждает.

## Кейс 1 — Полный классификатор (шесть тактов)

**Постановка.** В учебный центр приходят заявки через форму: имя, контакт, свободный текст.
Нужно, чтобы заявка попадала в таблицу сама, а **тема и срочность были заполнены всегда и
значениями из справочника** — иначе по этим столбцам не отсортировать и не посчитать.

**Вопрос залу:** из скольких узлов соберётся процесс, который решает задачу **полностью**?
Карточки: два · три · пять · «зависит от того, что считать решением».

**Разбор.** Три узла дают запись, но не решение: тема будет какой угодно, срочности не будет
вовсе, а проверить результат можно только походом в таблицу. Разница между «заработало» и
«можно поручиться» — два узла: **справочник** и **экран результата**.

**Наше решение — пять узлов.** Форма → извлечение полей со схемой-перечислением → справочник
(не из списка или пусто → «другое» / «не указано») → строка в таблице → экран результата,
печатающий вход, что предложила модель, что оставил справочник и номер строки.

**Обобщение** (такт 5): машинный выход — в закрытый список; гарантия двухуровневая (схема
просит, проверка гарантирует); наблюдаемость с первого прохода. Класс задачи назван явно —
классификация входящего потока в закрытый справочник.

**Нюансы** (такт 6), три класса: гарантия уже́ обещания (формат, не смысл; только в строгом
режиме; отказ по безопасности; обрыв по лимиту) · поведение меняется само (версия модели,
поток) · правило живёт в двух местах (справочник в схеме и в проверке).

## Кейс 2 — Справочник встречается с жизнью (шесть тактов)

**Постановка.** Процесс работает честно: пустых клеток нет, значения из справочника. Заявка
«можно перенести занятие со вторника? И подскажите, как оплатить» возвращает **одну** тему —
про оплату нигде ничего. Клетка заполнена, значение законное, заявка обслужена наполовину.

**Вопрос залу:** что должно попасть в тему, если их две? Карточки: первую из найденных ·
«другое», пусть разбирает человек · две строки вместо одной · главную плюс пометку.

**Разбор.** Четыре ответа различают одно — на кого ложится недоделанное: никто · человек,
и он об этом знает · следующий шаг · тот, кто читает пометку.

**Наше решение — главная тема плюс пометка.** Меняется **один узел из пяти**: в схеме
появляется поле «ещё в заявке», справочник сверяет его тем же списком. Прогоняем пять
трудных заявок: две темы · три темы, одна не наша · про юрлица · про курс без срочности ·
заявка из одного слова «ок».

**Обобщение:** «не знаю» — такое же значение, как остальные; многозначность входа — проектное
решение; у очереди на разбор есть владелец и метрика.

**Нюансы**, три класса: показатель читают в одну сторону (падение доли «другого» празднуют,
а оно двусмысленно) · границы списка устанавливаете вы, и без версии сравнения врут · вход
шире, чем вы думали (языки, форматы, многотемье).

## Кейс 3 — Внешний сервис не ответил (шесть тактов)

**Постановка.** Утро понедельника: в таблице пятница и понедельник, выходных нет вовсе.
Процесс не падал и ни на что не жаловался.

**Вопрос залу:** что должен делать узел, когда вызов не удался? Карточки: остановить весь
процесс · пропустить и идти дальше · повторить · отправить в отдельную ветку.

**Разбор — поворот кейса.** Все четыре карточки это **значения одной настройки** в карточке
любого узла, и одна из них стоит по умолчанию (остановить всё) — именно поэтому таблица пуста.

**Наше решение.** Повтор (3 попытки, пауза 2 с) плюс `Continue (using error output)`; из
выхода `error` заявка пишется в ту же таблицу со `status = not_parsed` и уходит на свой экран.
Отказ показывается настоящим отказом — порчей ключа провайдера на глазах у зала.

**Обобщение:** повтор лечит временный отказ и только его; у отказа должен быть адресат
(очередь неразобранного) ; технический успех и деловой — независимые утверждения.

**Нюансы**, три класса: повтор небезопасен по умолчанию (идемпотентность; таймаут не говорит,
произошло ли действие) · повтор добавляет не только задержку, но и нагрузку (три попытки на
пяти слоях = 243-кратная; нужен разброс задержек) · отказ без адресата — это тишина.

## Кейс 4 — Работает не то, что на экране (пять тактов, без демо)

**Постановка.** Поправили промпт, проверили ручным запуском — хорошо. Через сутки заявки
разобраны по-старому, а на холсте правка на месте. Оба утверждения верны одновременно.

**Вопрос залу:** почему боевые прогоны идут по старому варианту? Карточки: правку не
сохранили · сохранили, но не опубликовали · кэш · ручной и боевой — разные пути.
**Правильных две**, и они описывают одно явление с двух сторон.

**Вводная идёт ЗДЕСЬ, после вопроса.** Сценарий автосохраняется в черновик постоянно, кнопки
«Сохранить» нет вовсе; в бой правка уходит отдельным действием **Publish**; боевые прогоны
исполняют опубликованную версию. Слова «активировать» в n8n 2.x больше нет.

**Обобщение:** среда редактирования и среда исполнения — разные всегда; проверка руками не
покрывает путей, которые есть только в бою; работающая версия обязана быть опознаваемой и
откатываемой.

**Нюансы**, три класса: среды ведут себя по-разному (ручной прогон тяжелее по памяти) ·
часть путей существует только в бою (обработчик ошибок не проверить руками) · вместе с файлом
уезжает больше, чем кажется — **единственный пункт занятия про безопасность**.

## Концептуальный разбавитель — когда строить нечего (5–7 минут)

**Утверждение:** нижняя ступень лестницы — «одного вызова достаточно», и на ней
заканчивается значительная часть реальных задач.

Короткий разбор: что считается признаком, по которому процесс строить **не надо** —
один тип входа, один шаг, результат читает человек, объём такой, что ручная обработка
занимает минуты в день. Против: поток растёт, типов входа становится больше, результат
уходит дальше без человека.

Переход к следующему занятию: в нашем процессе шагов уже два, и между ними ничего не
стоит. Что происходит, когда первый шаг ошибся, — тема Семинара 8.

## Состояние стенда и что из него проверено

**Стенд живой** (владелец поднял его 2026-10-12): n8n 2.42.7, доступ по управляющему API.
Четыре стадии процесса собраны генератором `stend/sborka.py`, выложены на стенд,
опубликованы и прогнаны **настоящими отправками формы** — не проверкой того, что API принял
JSON.

### Задача решается полностью: проверено, а не обещано

В таблице `requests` 10 строк, и в них **ни одной пустой темы и ни одной темы вне
справочника** — включая заявку из одного слова «ок» и бессмысленный ввод.

| Заявка | Тема | Ещё в заявке |
|---|---|---|
| перенести занятие **и** как оплатить | перенос занятия | оплата |
| оплатить, перенести **и** про скидки | оплата | перенос занятия · другое |
| сотрудничаете с юрлицами? | другое | — |
| расскажите про курс | курс | — |
| «ок» | другое | — |

### Ветка отказа

Проверена подменой имени модели (тот же класс отказа, что порча ключа на занятии): три
попытки показаны **на узле модели**, а не на узле, где стоит настройка; элемент ушёл в
выход `error` с исходными данными формы и полем ошибки; строка записана со
`status = not_parsed`; **статус прогона — `success`**.

### Три находки прогонов, внесённые в деку

- повтор на узле извлечения платит вызовами модели (n23/n24);
- зелёный прогон при трёх отказах подряд (n16/n22 прошлого круга, n23 этого);
- заявка с тремя темами: главная плюс пометка, и третья тема честно становится «другим» (n17).

Отдельно стенд поймал ошибку материала: в таблицу ложился контакт из формы, хотя слайд
обещает телефон из текста. Теперь это два разных столбца, и на демо видно, что они разные.

## Чего здесь всё ещё нет

**Снимков холста нет.** Съёмка интерфейса требует входа в UI; у производства есть ключ
управляющего API, но не логин. Это единственное, что осталось от второго слоя подачи: во
фронтматтере трёх слайдов решения стоят `SCREENSHOT-TODO-*`. Рисовать «похожее на n8n»
запрещено правилом курса, и запрет остаётся в силе.

**Файл для студента собран, но не импортирован вручную.** Он выложен на стенд через API и
прогнан, то есть n8n его принял и исполнил; чего не проверено — путь «Import from File» в
интерфейсе. Перед раздачей ведущему стоит пройти им один раз.
