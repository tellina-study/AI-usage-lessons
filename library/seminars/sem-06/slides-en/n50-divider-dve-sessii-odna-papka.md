# Two sessions in one folder. Both reported success

## Assertion

You already have several sessions, and there is almost always more than one worker in one folder — and that is normal. You will give a session a separate copy of the repository straight away, and you will want to give one to a subagent. The isolation field exists for a subagent, it is switched on rarely, and that is a decision. We settle where to divide things with copies and where only with zones.

## Speaker notes

The seminar has already examined two reasons to set up a subagent: reading that does not fit into the context, and tasks standing in a queue for nothing. The third case is about what happens when there comes to be more than one worker and their file directory is shared.

The previous two cases settled questions about the work: where to hand it, and how many such handings to run at once. Here what gets settled is the place. One directory for several workers — and the question of what exactly breaks in it.

Anyone who works with an agent every day usually has more than one session: the first is busy, a second task arrives, a second session is opened. There is almost always more than one subagent in one folder, and that is the normal state of affairs. Subagents end up in the same folder by design: a subagent works where the calling session stands. The difference between a session and a subagent here is a single one, and the whole case rests on it: sessions are almost always given a separate copy of the repository, subagents almost never, and there is a named reason for that. That is where we are heading next.

The mechanism that breaks is older than agents. A working copy of a repository stands on one branch for everyone working in it, and that was the case long before the first agent appeared in the directory. What changed is the frequency. Before, one person worked in the directory with their own hands and knew for themselves what was in the files. Now there are two sessions and a dozen subagents standing in it, and each has its own idea of the state of the files.

You can check this for yourself from memory, without opening anything: how many sessions do you keep open on one repository, and how many times in the past month did you switch branches while somebody else's work was going on alongside? If the answer is "that never happened", then by the end of the case the sign by which a collision is recognized will be visible, and it is not that the work broke noticeably.

The collision figures below are taken from this course's own log. The course is built the very way we are talking about — several sessions in one working copy — and it has caught exactly what is examined next three times.

By the end of the case one thing gets settled: where to divide things with copies and where only with zones. The answer for a session and for a subagent will turn out to be different.
