## A.3. Кейс 3 — «одобрение, выданное один раз, перестаёт быть окончательным»

**Статус: написан заново.** Сырьё — `research/stage-5-mcp.md` §4.3 и §6 (Rashidi
arXiv:2607.05744, Deadbugz, `postmark-mcp`), `research/mechanics-5-mcp.md` §2.4
(`_meta["anthropic/requiresUserInteraction"]`), §1.6 (смена транспорта официального примера как
живой иллюстрация того, что «официальный путь» со временем меняется). В прежнем разделе это была
вторая половина одного слайда провала (3.14) — сам раздел называл её кандидатом на урезание при
нехватке времени. Здесь — полноценный кейс на собственной доказательной базе, не достройка того
же слайда.

### A.3.1. Заголовок дивайдера

> **Решаем, что делать, когда одобрение, выданное один раз, перестаёт быть окончательным**

### A.3.2. Сцена

Три недели назад команда подключила сервер уведомлений: он отправляет сообщение в рабочий канал
при каждом успешном прогоне тестов перед показом. Инструмент одобрили один раз, при первом
вызове. С тех пор сервер обновился сам — пакет подключён через `npx -y`, без зафиксированной
версии, — и никто этого не заметил, потому что всё продолжало работать: уведомления приходили,
как и раньше.

### A.3.3. Вопрос классу

> «Сервер одобрили один раз, три недели назад, и с тех пор ни разу не трогали его конфигурацию.
> Что из перечисленного вы бы изменили в том, как команда работает с уже одобренными серверами, —
> из карточек ниже?»

Карточки: `ничего — одобрили один раз, вопрос решён` · `перечитывать описание инструмента при
каждом обновлении` · `зафиксировать версию сервера` · `запретить автообновление пакета` ·
`сервер официальный — значит не обновляется тайно`

### A.3.4. Разбор (форма А5 — две колонки, круг 2)

| Вариант | Где работает — конкретные случаи | Ограничения |
|---|---|---|
| ничего — одобрили один раз | сервер никогда не обновляется, описание не меняется | доверие — по имени сервера, не по тексту описания: изменение проходит незамеченным |
| сервер официальный — не обновляется тайно | снижает вероятность злого умысла издателя | не отменяет механики: легитимное обновление меняет текст тем же путём |
| запретить автообновление пакета | закрывает канал целиком, если источник зафиксирован | не задаёт версию — это следующий шаг, не альтернатива ему |
| зафиксировать версию сервера | даёт контролируемую точку: обновление — по вашему решению | не читает содержимое обновления — нужен отдельный шаг проверки |
| перечитывать описание при каждом обновлении | закрывает канал смены доверенного поведения | требует, чтобы обновление было замечено — без фиксации версии узнать нечем |

> **Из сочетания колонок:** зафиксировать версию и перечитывать её при сознательном обновлении —
> последовательность, не альтернатива. «Ничего» и «официальность — гарантия» оба не держат
> проверку: держит дисциплина, применённая к уже одобренному, не только к новому.

*Круг 2 (issue 225, А5).* Ячейки сжаты до коротких проверяемых фраз (6–10 слов) — тот же текст,
что теперь на слайде n30; служебные связки, снятые при сжатии, перенесены в заметки докладчика.
Форма таблицы (вариант · где работает · ограничения) — это и есть «два столбца плюс название
варианта» из А5: третий содержательный столбец не заведён.

### A.3.5. Со-сборка / механика доверия

Строится причина, почему большинство клиентов не перепроверяют описание инструмента при каждом
вызове: доверие привязано к **имени** инструмента, не к текущему тексту его описания. Это не
недосмотр одного продукта — так устроена архитектура доверия по имени у протокола в целом.

Отдельно — что делает одобрение по-настоящему неотменяемым, если оно должно быть таким:
аннотация `_meta["anthropic/requiresUserInteraction"]: true` у автора сервера делает
подтверждение обязательным **на каждом вызове**, без опции «больше не спрашивать» — даже в
режимах, где обычно подтверждения пропускаются. Назначение аннотации прямое: для действий, где
сам факт запроса подтверждения — и есть смысл шага. **Оговорка по области действия:** это
расширение конкретного клиента через пространство имён `_meta`, не пункт официальной спецификации
протокола — соблюдает её сегодня Claude Code; клиент, который её не читает, может пропустить
действие без повторного подтверждения.

### A.3.6. Артефакт

Команда в `.mcp.json` фиксирует версию пакета прямо в команде запуска: `npx` больше не
подтягивает последнюю версию при каждом старте.

```json
{
  "mcpServers": {
    "notify": {
      "command": "npx",
      "args": ["-y", "@team/notify-mcp@2.3.1"]
    }
  }
}
```

Запись о проверенной версии уходит туда же, куда в этом проекте уже уходят архитектурные
решения — `DECISIONS.md`: дата, версия, кто проверил описание инструментов перед обновлением.
Это то же самое, что проект уже делает для других решений — не новый формат файла.

*Круг 2 (issue 225, А4).* На слайде (n32) этот же артефакт — два пункта с инлайн-кодом на
светлом фоне, не развёрнутый JSON в тёмной карточке: рендерер рисует любой блок в тройных
кавычках тёмной моноширинной карточкой независимо от содержимого. Факты те же — файл выше
остаётся точным описанием артефакта для текста главы.

### A.3.7. Провал — слоями, с базой

**Слой 1 — контролируемый эксперимент, не анекдот.** Rashidi, arXiv:2607.05744 (08.07.2026):
юникод-сокрытие инструкции в описании инструмента доставило её модели в **8 из 8** попыток на
трёх независимых серверных библиотеках; **0 из 8** вызвали какой-либо механизм повторного
одобрения; санитайзер по строковому совпадению дал **0 ложных срабатываний** на контрольном
корпусе из 25 безобидных описаний. **База сравнения:** 0 ложных срабатываний означает, что
проблему нельзя списать на недокалиброванный фильтр — она в самой архитектуре доверия по имени,
не в качестве проверки.

**Слой 2 — кампания, спроектированная на обход ручной проверки.** Deadbugz (наблюдение
10.08.2026): сервер, распространённый через 23 GitHub PR за 74 минуты, ведёт себя безобидно
ровно 3 вызова инструментов — после чего переключается на поиск SSH-ключей и облачных
credentials. **База сравнения:** порог в три вызова специально выше, чем глубина обычной ручной
проверки перед доверием «попробовал — вроде работает».

**Слой 3 — реальный, но тихий инцидент.** `postmark-mcp` (сентябрь 2025): backdoor появился в
обновлении пакета недели спустя после первого одобрения — и около полутора недель (17–29.09.2025)
скрытая BCC-копия каждого отправляемого письма уходила незамеченной, пока рассылку не заметили и
пакет не сняли с npm. **База сравнения:** обновление пакета — обычное, ожидаемое действие; подмена
вошла в его состав, отдельным заметным шагом она не стала.

*Круг 2 (issue 225, А8 — владелец: «интереснее рассказать не столько техническую начинку,
сколько к чему привело и как это заметили, уровнем выше, пользовательским»).* На слайде (n33)
три слоя сведены к двум вопросам на каждую строку — что случилось и как об этом узнали, — вместо
технической классификации «слой · канал подмены · цифра». Внутренняя механика (диапазон
юникод-символов, который прячет текст от человека, но не от токенизатора модели) остаётся в
заметках докладчика как ответ на вопрос из зала, не на видимом слое. Факты и числа этого
параграфа не менялись.

### A.3.8. Критерий

**Заголовок слайда:** «До каких пор действует старое одобрение»

**Достаточно периодического внимания:** сервер не обновляется автоматически, версия
зафиксирована, обновление — ваше явное решение.

**Не нужно никогда:**

- полагаться на «одобрили один раз» как на постоянную гарантию;
- держать дисциплиной действие, которое требует подтверждения на каждом вызове — для этого нужна
  аннотация `requiresUserInteraction` у автора сервера;
- считать себя защищённым, если автор сервера аннотацию не поставил: технического принуждения к
  повторному одобрению тогда не существует вовсе — только дисциплина версии и перечитывания;
- оставлять шаг в автоматизации, если и дисциплины, и аннотации всё равно недостаточно для его
  чувствительности — такое действие выполняет человек.

*Круг 2 (issue 225, А7 — владелец: «напиши: когда MCP нужен, когда не нужен, прямо чётко, не
надо чтобы люди догадывались»).* Рамка «ещё рано / не нужно вообще» снята — заголовки прямые
(«достаточно периодического внимания» / «не нужно никогда»), правая колонка развёрнута с одного
пункта до четырёх (три новых — прямой ответ на «когда дисциплины мало», «что делать, если
аннотации нет», «где черта автоматизации совсем» — продолжают круг после прожарок, п.6
владельца, новых фактов не вводят).
