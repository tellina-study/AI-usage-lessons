# Настройка узла: выражение версии с шаблоном

## Assertion

Вот сама панель настройки — одно выражение, написанное один раз руками, подставляет готовые значения в заранее заданную форму. Ни одного обращения к модели.

## Visual

> **Узел «Compose notification (template)» (`Set` / `Edit Fields`), Mode — Manual Mapping.** Поле `notification_text` (String): «Новая заявка от `{{ $('Request form').item.json['Имя'] }}`: тема «`{{ $('Vocabulary check').item.json.topic }}`»`{{ $('Vocabulary check').item.json.extra_topics ? ', также: ' + $('Vocabulary check').item.json.extra_topics : '' }}`.»

> «Include Other Input Fields» — включено, «Input Fields to Include» — All: остальные поля заявки проходят дальше по цепочке без изменений.

## Speaker notes

Вот настоящая панель настройки узла «Compose notification (template)» — и сравнивать её стоит прямо с панелью версии с моделью, которую мы видели два экрана назад, потому что узел один и тот же по назначению, а устроен принципиально иначе.

Mode здесь — «Manual Mapping»: одно поле, `notification_text`, типа String, и в нём — выражение, написанное один раз руками. Оно подставляет в заранее заданные места уже известные значения: имя заявителя, основную тему и, если есть, дополнительные темы — с условием внутри самого выражения, которое добавляет фразу «также: …» только тогда, когда дополнительные темы вообще есть, и ничего не добавляет, если их нет. Никакого отдельного узла модели рядом с этим узлом нет — в этой версии цепочки такого узла не существует вовсе, что мы уже видели на прошлом, общем кадре по отсутствию пометки «Model*».

В отличие от панели версии с моделью, это выражение видно на экране целиком, без прокрутки — оно короче и умещается в поле без обрыва. Сравните это с промптом версии 1: там текст заявления длиннее и часть его уходит за край видимой области поля.

Отдельно стоит заметить переключатель «Include Other Input Fields»: он включён, и «Input Fields to Include» стоит на «All». Это значит, что узел не просто собирает текст уведомления в одно новое поле — он заодно пропускает дальше по цепочке все остальные поля заявки без изменений, чтобы следующие узлы не потеряли то, что им может понадобиться.

Результат этого выражения детерминированный: при одних и тех же входных значениях текст всегда получается одним и тем же, без вариаций — и, как следствие, без риска вставить в сообщение что-то, чего в заявке не было. Цена этой надёжности — обратная сторона: если форма сообщения когда-нибудь должна будет меняться по смыслу, а не просто по значениям, это выражение придётся переписывать руками на каждый такой случай. Обе версии мы прогнали через одни и те же заявки — что из этого следует, дальше.
