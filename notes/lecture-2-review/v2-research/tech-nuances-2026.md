# Технические нюансы работы LLM — фактура для "глубоких" слайдов (2026)

## 1. KV-cache и prompt caching

**Механизм:** На каждом шаге self-attention модель кеширует K (key) и V (value) векторы уже обработанных токенов, чтобы не пересчитывать их заново на каждом новом шаге декодирования — пересчитывается только Q (query) для нового токена и его взаимодействие с сохранённым K/V. Prefill (обработка входного промпта) — параллельная операция по всем токенам сразу, поэтому compute-bound (упирается в FLOPs GPU). Decode (генерация по одному токену) — строго последовательная операция, на каждом шаге нужно прочитать весь KV-cache из памяти, поэтому она memory-bandwidth-bound, а не compute-bound. Prompt caching в API — это применение того же принципа на уровне провайдера: если два запроса имеют идентичный префикс, K/V для этого префикса переиспользуются между запросами, а не только внутри одной генерации.

**Цифры/примеры:**
- Claude: cache write 5-min TTL = 1.25× base input price; cache write 1-hour TTL = 2.0× base price; cache read = 0.1× base price (для новых моделей Claude Fable 5.1/Mythos 5.1 — 0.025×, то есть 97.5% экономии). Минимальная длина префикса для кеша: 1024–4096 токенов в зависимости от модели (напр. Sonnet 4.6 — 1024, Haiku 4.5 — 4096). [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- OpenAI: для GPT-5.5 и более старых — cache read = 0.1× base rate (90% экономии), без write fee. Для GPT-5.6+ появилась write fee (1.25× base rate), но cache read даёт уже ~90% скидку с более низкой базовой ценой (пример: $4.00 → $0.40/M). Минимальная длина префикса — 1024 (GPT-5.6+) или 2048 (старые модели) видимых входных токенов, округление до кратного 128. TTL по умолчанию с 29 мая 2026 — 24 часа (раньше — несколько минут); для GPT-5.5+ 24ч — единственный вариант. [OpenAI docs](https://developers.openai.com/api/docs/guides/prompt-caching)
- Google Gemini: implicit caching включено по умолчанию для Gemini 2.5+; cache read по разным источникам ≈10% от базовой цены input (economия до 90%); для Gemini 3.1 Pro cache read $0.20/1M токенов (<200K), storage $4.50/1M токенов в час. [Gemini caching docs](https://ai.google.dev/gemini-api/docs/caching) — точные цены storage/read из основной документации извлечь не удалось напрямую, цифры — из вторичных источников [Tech Jacks Solutions](https://techjacksolutions.com/ai-tools/google-gemini/gemini-context-caching-cost-optimization/) [НЕ ПОДТВЕРЖДЕНО через первичный источник].
- DeepSeek: автоматическое дисковое кеширование; по вторичным источникам cache-hit rate для V4-Flash — $0.0028/M, что «~1785× дешевле» base input Opus 5. [Spheron Blog](https://www.spheron.network/blog/llm-api-pricing-comparison-gpt-claude-gemini-deepseek-2026/) [частично НЕ ПОДТВЕРЖДЕНО первичным источником DeepSeek].
- Требование точного совпадения префикса: кеш срабатывает только если ВСЁ содержимое до breakpoint совпадает байт-в-байт (system prompt, tools, thinking config, images — любое изменение до этой точки инвалидирует кеш). [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- Практическое правило: стабильный контент (system prompt, few-shot примеры, документы) — в начало промпта; переменный (текущий вопрос пользователя) — в конец, иначе каждое изменение в начале ломает кеш для всего, что после него.

**Для слайда:**
- Cache read у Claude/OpenAI/Gemini даёт скидку 90%+ на повторяющийся контекст — но при этом Claude 1-hour cache write стоит **вдвое дороже** обычного input, то есть кеш не бесплатен, а является ставкой на повторное использование.
- Изменение ОДНОГО токена в начале промпта (например, timestamp в system prompt) инвалидирует кеш для абсолютно всего, что идёт после него.

## 2. Недетерминизм при temperature=0

**Механизм:** Общепринятая гипотеза («floating-point non-associativity + параллелизм на GPU») — по данным статьи Thinking Machines Lab — не является главной причиной. Настоящая причина: сервер динамически группирует запросы в батчи разного размера в зависимости от текущей нагрузки, а многие CUDA-ядра (matmul, attention, RMSNorm) не являются **batch-invariant** — при разном размере батча меняется алгоритм редукции (порядок суммирования), и это меняет результат на уровне floating-point даже при temperature=0 и одинаковом запросе.

**Цифры/примеры:**
- Статья: **"Defeating Nondeterminism in LLM Inference"**, автор Horace He в сотрудничестве с Thinking Machines Lab, опубликована **10 сентября 2025**. [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- Эксперимент авторов: стандартный vLLM на 1000 одинаковых запросах дал **80 уникальных завершений** из 1000 при temperature=0; с batch-invariant ядрами — **все 1000 завершений идентичны** (bit-identical). [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- Цена детерминизма: batch-invariant kernels в исходной реализации авторов — падение throughput примерно до 61.5% от baseline (пример замера: 26 сек vLLM по умолчанию → 55 сек детерминированный без оптимизаций → 42 сек с улучшенным attention-ядром). [Thinking Machines Lab](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)
- SGLang интегрировал batch-invariant kernels + CUDA graphs + radix cache + chunked prefill, снизив оверхед примерно до 34.35%. [LMSYS blog](https://www.lmsys.org/blog/2025-09-22-sglang-deterministic/)
- MoE routing: в самой статье Thinking Machines Lab MoE routing **не упоминается** как причина; но независимо от неё, MoE-инференс имеет собственный источник нестабильности — token dropping/capacity overflow при превышении ёмкости эксперта, чувствительность роутинга к распределению токенов в батче. [HuggingFace blog on MoE load balancing](https://huggingface.co/blog/NormalUhr/moe-balance)
- OpenAI seed-параметр: существует (`seed` + `system_fingerprint`), но официально даёt только "mostly deterministic" результат — детерминизм НЕ гарантирован даже при совпадении seed и всех параметров. [OpenAI Cookbook](https://cookbook.openai.com/examples/reproducible_outputs_with_the_seed_parameter)
- Production adoption 2026: SGLang стал официальным проектом PyTorch ecosystem, используется xAI (Grok 3) и Microsoft Azure (DeepSeek R1 на AMD GPU). [Yotta Labs](https://www.yottalabs.ai/post/vllm-vs-sglang-which-inference-engine-should-you-use-in-2026)

**Для слайда:**
- «Temperature=0 не значит детерминизм»: то же самое API-сообщение может дать один из 80 разных ответов из 1000 попыток — причина не в математике модели, а в том, что размер батча на сервере меняется от запроса к запросу.
- Полный детерминизм технически достижим (batch-invariant kernels, доказано bit-identical на 1000/1000 запусках), но стоит ~35-40% throughput — поэтому провайдеры по умолчанию его не включают.

## 3. Reasoning/thinking токены

**Механизм:** И у Anthropic (extended/adaptive thinking), и у OpenAI (o-series/GPT-5 reasoning models) токены "размышления" биллятся **как output tokens** — то есть по цене output, не input, и считаются в лимит max_tokens. У Anthropic thinking-блоки в API возвращаются как **summarized thinking** (не raw chain-of-thought) даже во "внутреннем" виде — сырое рассуждение не экспонируется напрямую пользователю через стандартный ответ; у OpenAI reasoning-токены также не показываются raw — только summarized reasoning в некоторых моделях, сами токены рассуждения потребляются, но не возвращаются в текстовом виде.

**Цифры/примеры:**
- Anthropic: `budget_tokens` — минимум 1024 токена (меньше API отклоняет), должен быть меньше `max_tokens`, кроме interleaved thinking, где `budget_tokens` может превышать `max_tokens` (бюджет считается на весь turn). Рекомендация для сложных задач — стартовать от 16000+ токенов. При budget >32k рекомендуется Batch API из-за риска сетевых таймаутов. [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- Anthropic **важное изменение 2026**: extended thinking (`type: "enabled"` + `budget_tokens`) **deprecated** на моделях 4.6-й генерации и **отклоняется с ошибкой 400** на Claude 4.7+ (Opus 4.7/4.8, Opus 5, Sonnet 5, Fable 5/5.1, Mythos 5/5.1) — вместо него используется **adaptive thinking** (`type: "adaptive"`) с параметром `effort` (`low/high` и т.д.) вместо budget_tokens. [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- Interleaved thinking (мышление между tool calls в одном assistant turn): на Opus 4.5/Sonnet 4.5/старых Claude 4 требует beta-заголовок `interleaved-thinking-2025-05-14`; на Sonnet 4.6 — работает через adaptive thinking автоматически без заголовка; на Opus 4.6 manual-режим интерливинга вообще не поддерживается — только adaptive. Haiku 4.5 interleaved thinking не поддерживает вовсе. [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- Смена `budget_tokens` между запросами **инвалидирует prompt cache** (продемонстрировано на примере: смена бюджета с 4000 на 8000 токенов между 2-м и 3-м запросом → `cache_creation_input_tokens` заново пересоздаётся вместо чтения из кеша). [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)
- OpenAI `reasoning_effort`: значения `minimal/low/medium(default)/high` у GPT-5; у более новых моделей (GPT-5.5+, GPT-5.1 Codex Max+) добавлены `none` и `xhigh`. Отдельный параметр `verbosity` (`low/medium/high`) управляет длиной финального ответа независимо от глубины рассуждения. [OpenAI community/docs](https://developers.openai.com/api/docs/guides/reasoning)

**Для слайда:**
- Мышление стоит как output, а не input: 10 000 "невидимых" токенов рассуждения биллятся по более дорогой output-ставке — бюджет thinking для тяжёлых задач стоит закладывать в 2-5× видимого ответа.
- Anthropic за 2026 год полностью сменила модель управления мышлением: с ручного `budget_tokens` (жёсткий лимит) на `adaptive thinking` + `effort` (модель сама решает, думать ли вообще) — старый API на новых моделях (Opus 4.7+) буквально перестал работать (ошибка 400).

## 4. Structured outputs

**Механизм:** Все три провайдера используют constrained decoding — маскирование логитов на каждом шаге генерации так, чтобы модель физически не могла выбрать токен, нарушающий грамматику JSON Schema. Ограничение применяется НЕ на уровне промпта/инструкции, а на уровне decode: система на каждом шаге отслеживает, какие токены оставляют вывод валидным относительно схемы, и обнуляет вероятность всех остальных.

**Цифры/примеры:**
- OpenAI Structured Outputs (strict mode): заявлена гарантия **100% соответствия схеме** против ~80% у обычного "JSON mode" — при strict=true модель не может выбрать невалидный токен в принципе (в отличие от валидации постфактум). [Newtuple](https://www.newtuple.com/post/openai-structured-outputs) / [datastudios.org](https://www.datastudios.org/post/openai-structured-outputs-vs-json-mode-schema-enforcement-reliability-and-failure-modes)
- OpenAI ограничения strict mode: **не поддерживает** `$ref` для настоящих рекурсивных схем; максимальная глубина вложенности — 5 уровней; `minLength`/`maxLength` для строк не поддерживаются (нужно выносить в постобработку); root-объект не может использовать `anyOf`; опциональные поля моделируются через `null`-type, а не через omit. [OpenAI docs via community summary](https://openai.com/index/introducing-structured-outputs-in-the-api/)
- Латентность: первый запрос с новой схемой требует компиляции constrained grammar — обычно <10 сек, для сложных схем до минуты; независимые тесты фиксировали редкие всплески задержки до **20×** при Structured Outputs сверх обычного first-request компиляционного оверхеда. [Vercel AI discussion](https://github.com/vercel/ai/discussions/3656)
- Anthropic: нативные Structured Outputs (GA) появились в 2026 году — параметр `output_format`, работает через constrained sampling с compiled grammar artifacts, поддерживается для Claude Sonnet 4.5 и Opus 4.1+. До этого единственным способом был **tool-use trick**: объявить "инструмент" со схемой и заставить модель её вызвать через `tool_choice`. По состоянию на апрель 2026, prefill (продолжение ответа с заданного префикса) в новейших моделях больше не поддерживается — вместо него используются native JSON outputs или strict tool use. [Towards Data Science](https://towardsdatascience.com/hands-on-with-anthropics-new-structured-output-capabilities/) [Google Cloud docs](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/partner-models/claude/structured-outputs)
- Google Gemini: `response_schema`/`response_format` с `mime_type: application/json`; поддержка JSON Schema расширена, улучшено соблюдение порядка полей (property ordering); Gemini 3 умеет комбинировать Structured Outputs со встроенными инструментами (Google Search grounding, code execution, function calling) одновременно. [Google AI docs](https://ai.google.dev/gemini-api/docs/structured-output) / [Google blog](https://blog.google/innovation-and-ai/technology/developers-tools/gemini-api-structured-outputs/)
- Спор "schema adherence vs quality": сообщество разработчиков фиксирует, что чрезмерно строгая схема иногда снижает качество содержательного ответа (модель тратит "внимание" на форматирование, а не на суть) — это признанный компромисс, а не решённая проблема [оценка качественная, количественных % не найдено — НЕ ПОДТВЕРЖДЕНО].

**Для слайда:**
- Constrained decoding не "просит" модель соблюдать схему — физически обнуляет вероятность невалидных токенов на каждом шаге. Именно поэтому OpenAI strict mode даёт 100%, а не "почти всегда".
- Рекурсивные структуры (дерево комментариев, вложенные категории) — известное слабое место: OpenAI не поддерживает `$ref` для реальной рекурсии вообще, требуя плоской структуры с parent_id вместо вложенности.

## 5. Chat-шаблоны и специальные токены

**Механизм:** Роли system/user/assistant не являются "инструкциями", которые модель волшебно понимает — они реализованы как последовательности специальных токенов (`<|im_start|>system`, `<|im_start|>user`, `<|im_start|>assistant`, `<|im_end|>` в ChatML) или текстовых маркеров (`[INST]...[/INST]` у Llama), вставляемых в единую линейную последовательность токенов перед подачей в модель. Формат преобразования списка сообщений {role, content} в эту последовательность задаётся chat template — обычно Jinja2-шаблоном, хранящимся в поле `chat_template` файла `tokenizer_config.json` (HuggingFace).

**Цифры/примеры:**
- ChatML (`<|im_start|>`/`<|im_end|>`) — фактический "стандарт" формата, изначально предложен OpenAI; роль вставляется как обычная строка после `<|im_start|>`, что позволяет добавлять новые роли без новых спецтокенов. [AI/TLDR](https://ai-tldr.dev/learn/llm-fundamentals/tokens-and-tokenization/chat-templates-special-tokens/)
- Chat template хранится как Jinja-шаблон в `tokenizer_config.json` под ключом `chat_template` (пример: модели семейства Qwen3). [HuggingFace blog](https://huggingface.co/blog/chat-templates)
- Уязвимость "role spoofing" / Special Token Injection (STI): если модель воспринимает весь вход как один плоский поток токенов, а не структурированные метаданные, то атакующий может вставить в user-контент (например, в текст веб-страницы, которую агент читает через tool) буквальные символы, похожие на `<|im_start|>assistant`, и модель может интерпретировать последующий текст как "свой собственный" ответ или системную инструкцию — это описано как класс атак Special Token Injection / "role confusion". [Sentry blog](https://blog.sentry.security/special-token-injection-sti-attack-guide/) / [arXiv 2603.12277 "Prompt Injection as Role Confusion"](https://arxiv.org/pdf/2603.12277)
- Ключевой механизм уязвимости: модель определяет источник текста по тому, "как он звучит" (стилистически), а не по формальной метке роли — то есть роль не является криптографически защищённой границей. [HiddenLayer research](https://www.hiddenlayer.com/research/inside-the-prompt-how-llms-learn-roles-follow-instructions-and-get-exploited)
- Защита в проде обычно строится на экранировании/детекции спецтокенов во входящем внешнем контенте до подачи в модель, а не только на обучении модели устойчивости к этому.

**Для слайда:**
- Роль "system" — это не привилегия, а просто последовательность токенов в общем потоке; если приложение позволяет внешнему контенту (веб-странице, файлу) содержать текст, похожий на `<|im_start|>assistant`, модель в некоторых случаях может "поверить", что дальше идёт её собственная реплика.
- Формат чата — не свойство модели "из коробки", а обучаемый Jinja-шаблон в конфиге токенизатора; один и тот же checkpoint с разным chat_template может вести себя иначе.

## 6. Glitch-токены

**Механизм:** Glitch-токены — это записи в словаре токенизатора, которые почти не встречались (или не встречались вовсе) в датасете, на котором дообучалась модель, хотя присутствовали в корпусе, на котором строился сам токенизатор (например, из-за автоматического скрапинга специфичных строк типа юзернеймов Reddit). В результате эмбеддинг такого токена остаётся "недообученным" — фактически близким к初始ной инициализации, и модель ведёт себя непредсказуемо, когда этот токен появляется на входе или должен быть сгенерирован.

**Цифры/примеры:**
- Обнаружение: январь 2023, исследователи **Jessica Rumbelow и Matthew Watkins** в рамках семинара SERI-MATS, искавшие кластеры в embedding space GPT моделей; наткнулись на кластер строк вроде `SolidGoldMagikarp`, `TheNitromeFan`, `cloneembedreportprint`. Опубликовано на **LessWrong**. [LessWrong: SolidGoldMagikarp](https://www.lesswrong.com/posts/aPeJE8bSo6rAFoLqg/solidgoldmagikarp-plus-prompt-generation)
- Наблюдаемое поведение: модели GPT-2/GPT-3 оказывались "неспособны повторить" эти токены — вместо этого выдавали странные ответы, уход от темы, отказ. [LessWrong / Gizmodo coverage](https://gizmodo.com/the-mysterious-ai-easter-egg-at-the-heart-of-ari-asters-eddington-2000633209)
- Актуальное состояние 2025-2026: систематическое исследование зафиксировало, что примерно **4.3% записей словаря** в протестированных моделях являются glitch-токенами; фреймворк **GlitchMiner** (принят на AAAI 2026) использует градиентную максимизацию энтропии для их поиска в 10 открытых LLM семейств Llama, Qwen, Gemma, Phi-3, Mistral (градиентный метод требует доступа к весам — закрытые модели вроде GPT-4 им не тестировались). [arXiv via search summary]
- Значит, проблема **не решена** современными токенизаторами (o200k_base у OpenAI, токенизаторы Llama 3/4 на tiktoken-style BPE 128 256 токенов) — она системная для любого BPE-токенизатора, обучаемого отдельно от модели: словарь строится на одном корпусе, модель дообучается на другом. [GlitchHunter/GlitchMiner research summary]
- Специфика конкретно для o200k_base/новых токенизаторов Claude/Llama 4 отдельно (в разрезе "исправили ли именно эти токенизаторы проблему") — точных данных не найдено [НЕ ПОДТВЕРЖДЕНО].

**Для слайда:**
- ~4.3% словаря современных LLM — это токены, эмбеддинг которых модель толком никогда не видела во время обучения: словарь токенизатора и обучающий корпус модели — не одно и то же множество данных.
- Glitch-токены — не баг конкретной версии GPT, а структурная особенность конвейера (токенизатор строится отдельно от модели) — актуальные исследования 2026 года (GlitchMiner, AAAI) показывают, что явление воспроизводится в открытых семействах Llama, Qwen, Gemma, Phi-3, Mistral (10 протестированных открытых LLM; закрытые модели градиентным методом не проверяемы).

## 7. Strawberry-тест в 2026

**Механизм:** Классический провал "сколько r в strawberry" — следствие того, что модель "видит" не буквы, а токены (обычно strawberry — один или два токена), и посимвольный подсчёт требует reasoning поверх токенизированного представления, а не прямого доступа к символам. Современные фиксы — это смесь: (a) точечный RL-патч на конкретно этот вопрос (что подтверждается тем, что похожие вопросы на других словах всё ещё ломаются), (b) chain-of-thought/reasoning с явным посимвольным перечислением, (c) в редких случаях — вызов code execution для точного подсчёта.

**Цифры/примеры:**
- GPT-5.2 (декабрь 2025): **всё ещё** отвечал "два r" в strawberry (правильный ответ — три). [Dataconomy](https://dataconomy.com/2025/12/15/gpt-5-2-still-counts-two-rs-in-strawberry/)
- GPT-5.5 (апрель 2026): корректно отвечает "три r" в strawberry, но при этом **неверно** отвечает "два r" в cranberry (правильно тоже три: c-r-a-n-b-e-r-r-y). Это стало основанием для обвинений в точечном хардкоде именно слова strawberry, а не реального улучшения посимвольного счёта. [9to5google](https://9to5google.com/2026/04/28/chatgpt-strawberry-logic-fix-problem/), [TechCityAuthority](https://www.techcityauthority.com/2026/04/chatgpt-finally-gets-strawberry-right.html)
- Вывод из источников: «фикс strawberry не пофиксил cranberry» — прямое доказательство, что решение не является общим улучшением character-level counting. [Yahoo Tech](https://tech.yahoo.com/ai/chatgpt/articles/long-last-chatgpt-claims-fixed-150000052.html)
- Аналогичные character-level задачи, всё ещё ломающие модели в 2025-2026: разработан специализированный бенчмарк **StrawberryBench** — 847 вопросов в 7 tier'ах (easy/medium/hard/sentence/paragraph + отдельные проверки на именах и иностранных словах), тестирующий подсчёт вхождений произвольной буквы в произвольном слове/тексте. [strawberrybench.fyi](https://www.strawberrybench.fyi/)
- Концептуальная рамка 2026 года для описания этого явления — **"jagged intelligence"** (рваный интеллект): модель блестяще решает мат-олимпиадные задачи (много таких примеров в интернете), но проваливается на тривиальном посимвольном счёте (мало таких примеров в обучающих данных). [Medium via search summary](https://medium.com/@hardik.goel214/the-ai-that-aced-the-math-olympiad-cant-count-the-letters-in-strawberry-996043711642)

**Для слайда:**
- GPT-5.5 (апрель 2026) правильно считает "r" в strawberry, но НЕ в cranberry — прямая иллюстрация того, что модели патчатся под конкретные вирусные вопросы, а не обучаются общему навыку.
- "Jagged intelligence" — модель, побеждающая на математической олимпиаде, может одновременно проваливать подсчёт букв в пятибуквенном слове: интернет полон олимпиадных задач и почти не содержит тренировочных примеров на посимвольный счёт.

## 8. Lost-in-the-middle в 2026

**Механизм:** U-образная кривая Liu et al. 2023 (модели лучше используют информацию в начале и конце контекста, хуже — в середине) остаётся воспроизводимой и на моделях 2025-2026 года, включая заявленные 1M-токенные окна. Простой needle-in-a-haystack retrieval (найти буквально вставленную фразу) в значительной мере "решён" топовыми моделями, но это не то же самое, что reasoning/synthesis по длинному контексту — деградация проявляется именно там, где нужно не найти, а связать несколько фактов или сделать вывод без буквального лексического совпадения (запрос ↔ фрагмент).

**Цифры/примеры:**
- U-образный эффект в 2026: точность на "needle" при позиции 30-70% глубины контекста показывает падение на 5-15 процентных пунктов относительно позиций у краёв; общая деградация по кривой "начало/конец vs середина" — до 20-30 пунктов. [DEV Community summary](https://dev.to/gabrielanhaia/lost-in-the-middle-is-still-real-in-2026-even-on-1m-token-models-2ehj)
- Gemini 3 Deep Think: NIAH-2 на 1M контексте — single-needle 99%, multi-needle 89%; RULER на 256K — выше 80%. Отмечается, что Gemini 3 Deep Think **уникально** удерживает почти-идеальный retrieval на всём заявленном окне 1M, тогда как у трёх других сравниваемых моделей эффективный контекст ограничен практическим диапазоном 200-400K, несмотря на заявленные больше. [оценка из вторичного агрегирующего источника — точный источник методологии не идентифицирован, частично НЕ ПОДТВЕРЖДЕНО первичным бенчмарком]
- Большинство моделей 2026 года теряют **15-30% точности** между 4K и 128K контекстом на бенчмарке RULER. [оценка из вторичного источника, НЕ ПОДТВЕРЖДЕНО первичной публикацией RULER]
- NoLiMa (бенчмарк без буквальных лексических совпадений между запросом и needle): при удалении литеральных подсказок производительность резко падает с ростом длины контекста; **11 моделей** опускаются ниже 50% от их же базовой точности на коротком контексте уже при длине **32K токенов**. [источник по поиску NoLiMa/OpenReview]
- LongBench v2: 503 сложных multiple-choice вопроса, длина контекста от 8K до 2M слов, 6 категорий задач (single/multi-doc QA, long in-context learning, long-dialogue understanding, code repo understanding, long structured data). [arXiv 2412.15204](https://arxiv.org/abs/2412.15204)
- Общий вывод по источникам: разрыв между Google (лидер long-context пайплайна) и конкурентами оценивается в ~12 месяцев и, по утверждению источников, не сокращается на существующих бенчмарках [качественная оценка из вторичного источника, НЕ ПОДТВЕРЖДЕНО количественно].

**Для слайда:**
- "1M токенов контекста" в характеристиках модели ≠ "1M токенов, на которых модель одинаково хорошо рассуждает": простой retrieval почти решён, но NoLiMa (без буквальных совпадений) показывает падение точности вдвое уже на 32K у 11 из протестированных моделей.
- Lost-in-the-middle 2023 года (Liu et al.) не исчез в 2026 — он просто "спрятался" за высокими цифрами needle-retrieval бенчмарков, которые тестируют не то, что нужно для реальных задач синтеза по длинному документу.

## 9. Embedding-модели 2026

**Механизм:** В проде используется смесь проприетарных API-моделей (OpenAI text-embedding-3, Voyage AI voyage-3/-3-large, Cohere embed, Google gemini-embedding) и открытых моделей (BGE-M3, GTE, Qwen3-Embedding). Matryoshka Representation Learning (MRL) — техника обучения, при которой эмбеддинг конструируется так, что его можно обрезать до меньшей размерности (например, взять первые 256 из 1536 чисел) с контролируемой, а не катастрофической потерей качества — в отличие от случайного/неструктурированного обрезания.

**Цифры/примеры:**
- MTEB-лидеры 2026: **KaLM-Gemma3-12B** (open-weight) — 72.32 агрегированный MTEB score; **Qwen3-Embedding-8B** — 75.22 на MTEB English (v2), считается лучшим multilingual перформером среди открытых моделей; **Gemini Embedding** (gemini-embedding-001) — 1-е место на MTEB multilingual со средним score 75.5. [premai.io](https://www.premai.io/blog/best-embedding-models-for-rag-2026-ranked-by-mteb-score-cost-and-self-hosting/), [modal.com](https://modal.com/blog/mteb-leaderboard-article)
- Voyage-3 / voyage-3-large: поддерживает документы длиной 8192-32768 токенов, рекомендуется как managed API опция для англоязычных задач. [аналогично источник выше]
- BGE-M3: рекомендуется как self-hosted опция, покрывает 100+ языков.
- MRL-поддержка: **Jina v4** и **Voyage** лидируют по MRL-бенчмаркам, так как обучались специально с MRL-объективом; **OpenAI text-embedding-3-large** поддерживает уменьшение размерности через встроенный `dimensions` параметр (Matryoshka-стиль); **Gemini** при этом, несмотря на лидерство в full-dimension retrieval, показывает слабые результаты именно в MRL/dimension-compression тестах — ранжируется последним по этому конкретному критерию среди сравниваемых. **EmbeddingGemma** (Google DeepMind, 308M параметров, open-weight) — специально обучена с MRL: 768 dims можно обрезать до 512/256/128. [источники сводного обзора embedding-моделей 2026]
- Важный методологический нюанс из свежего arXiv-исследования (2026): текстовые эмбеддинги в целом устойчивы к обрезанию размерности даже **без** MRL-обучения — MRL даёт явное преимущество только при "тяжёлом" усечении (сокращение размерности примерно на 80%+). [arXiv 2605.16608 "To MRL or not to MRL"](https://arxiv.org/abs/2605.16608)

**Для слайда:**
- MRL — не универсальная "магия обрезания": по данным 2026 года, эффект MRL заметен только при очень агрессивном сжатии (>80% сокращения размерности) — на умеренном обрезании обычные эмбеддинги и так достаточно устойчивы.
- Gemini лидирует в multilingual MTEB (75.5), но занимает последнее место по устойчивости к обрезанию размерности среди сравниваемых моделей — "лучший результат" и "лучшая экономичность" — разные оси, которые не всегда совпадают в одной модели.

## 10. Позиционное кодирование: RoPE и YaRN

**Механизм:** RoPE кодирует позицию токена не как отдельное добавляемое число, а как **поворот** вектора запроса/ключа в комплексной плоскости на угол, пропорциональный позиции токена и частоте конкретной пары измерений эмбеддинга. Ключевое свойство: скалярное произведение (attention score) двух повёрнутых векторов зависит **только от разницы позиций** между ними, а не от абсолютных позиций — то есть кодирование получается по сути относительным, хотя реализовано как модификация каждого вектора по отдельности. Проблема экстраполяции: если модель обучена на последовательностях длиной L, а на инференсе подаётся текст 4L — высокочастотные компоненты поворота "проворачиваются" много раз и результат становится некогерентным (attention "размазывается" — attention dilution), а низкочастотные компоненты не дают достаточного разрешения для различения близких позиций на такой большой дистанции.

**Цифры/примеры:**
- Оригинальный RoPE «не очень устойчив к экстраполяции» — сохраняет качество лишь немного за пределами обученной длины контекста. [EleutherAI blog](https://blog.eleuther.ai/yarn/)
- YaRN (Yet Another RoPE extensioN): комбинирует частотно-избирательную интерполяцию углов поворота RoPE + адаптивное масштабирование "температуры" attention; по заявлению авторов достигает SOTA в задачах расширения контекстного окна, дообучаясь менее чем на **~0.1%** объёма исходных претрейн-данных. [arXiv YaRN paper](https://arxiv.org/pdf/2309.00071)
- Альтернативные методы того же класса: Position Interpolation (PI), NTK-aware Interpolation — все они пытаются подогнать статистику attention-паттернов под то, что модель "видела" при исходной длине обучения, вместо простого линейного растяжения. [EmergentMind summary](https://www.emergentmind.com/topics/rotary-positional-embeddings-rope-extension)

**Для слайда:**
- RoPE не хранит позицию как число — он поворачивает вектор на угол, и именно поэтому attention score зависит только от расстояния между токенами, а не от их абсолютных номеров (относительное кодирование "бесплатно" получается из геометрии).
- "Просто увеличить максимальную длину" не работает: обучение на длине L и инференс на 4L ломает высокочастотные компоненты поворота — YaRN нужен именно для контролируемой перенастройки этих частот, а не для "разрешения" читать длиннее.

## 11. Streaming/латентность

**Механизм:** TTFT (time to first token) определяется временем prefill (обработка всего входного промпта) плюс сетевой оверхед — растёт с длиной промпта. Throughput (tokens/sec) в decode-фазе упирается в memory bandwidth, а не compute, поэтому speculative decoding — использование маленькой быстрой "draft"-модели, которая предлагает несколько токенов вперёд, а большая модель проверяет их за один параллельный проход — даёт выигрыш именно потому, что верификация N токенов за один forward pass дешевле, чем N последовательных forward pass.

**Цифры/примеры:**
- По данным агрегаторов на базе artificialanalysis.ai (2026): типичные значения для крупных моделей — Claude Opus 4.7 ≈ 78 TPS / TTFT P50 ≈ 0.85с; GPT-5.5 (standard) ≈ 92 TPS / TTFT ≈ 1.1с; Gemini 2.5 Flash и Claude Haiku 4.5 — TTFT стабильно <600мс на промптах средней длины. Самые быстрые модели по throughput в целом (не топ-intelligence класс) — до 1500+ tokens/sec (напр. Celeris-1). [оценка из вторичных агрегаторов, НЕ ПОДТВЕРЖДЕНО напрямую первичным artificialanalysis.ai лидербордом — цифры взяты из статей, ссылающихся на него] [artificialanalysis.ai](https://artificialanalysis.ai/leaderboards/models)
- Speculative decoding в проде 2026: по вторичным источникам, Anthropic использует Claude Haiku как draft-модель для Sonnet/Opus внутри своей serving-инфраструктуры; Google DeepMind публиковал исследования и интегрирует speculative decoding в serving Gemini. [НЕ ПОДТВЕРЖДЕНО первичным источником Anthropic/Google — это вторичное утверждение из обзорных статей, официального публичного подтверждения именно "Haiku как draft для Sonnet/Opus" от Anthropic не найдено]
- Типичный эффект speculative decoding: 2-3× ускорение tokens/sec при 60-80% принятых токенов от draft-модели (то есть большинство предложенных draft-токенов совпадает с тем, что выбрала бы основная модель). Алгоритм EAGLE-3 (draft на уровне гибридных feature-представлений) — до 4.79× ускорения на LLaMA-3.3-70B без потери качества. [источники по обзору speculative decoding методов, включая EAGLE-3]
- vLLM и SGLang — оба поддерживают speculative decoding на уровне serving-конфигурации, дают дополнительные 2-5× к латентности сверх базового движка. [source aggregation]

**Для слайда:**
- Speculative decoding — не "предсказание будущего", а бухгалтерская хитрость: маленькая модель предлагает несколько токенов, большая проверяет их **за один** параллельный проход вместо нескольких последовательных — экономия идёт от параллелизма verification, а не от точности предсказания.
- Заявленное ускорение EAGLE-3 — почти 5× (4.79×) без потери качества — иллюстрирует, что современный SOTA speculative decoding подошёл вплотную к границе "почти бесплатного" ускорения decode-фазы.

## 12. Токенизация чисел и кода

**Механизм:** cl100k_base (GPT-3.5/GPT-4) — стандартизировал числа в чанки по **3 цифры слева направо** (например, "1000000" → "100"+"000"+"0"), что не совпадает с тем, как человек группирует числа при чтении справа налево (разряды тысяч, миллионов). Это несовпадение — прямая причина части ошибок в арифметике: модель оперирует не "цифрами", а произвольными group-of-3-digits токенами, чьи границы не совпадают с математически значимыми разрядами. Для отступов в коде: токенизатор GPT-2 кодировал каждый пробел отступа как отдельный токен (растрачивая контекстное окно на Python-код с глубокой вложенностью); GPT-4/новые токенизаторы группируют несколько пробелов подряд в один токен, специально оптимизируясь под Python-style indentation.

**Цифры/примеры:**
- cl100k_base: числа разбиваются по 3 цифры слева-направо (left-to-right chunking), а НЕ справа-налево — исследование показывает, что right-to-left tokenization (принудительно, например, через запятые-разделители разрядов) даёт значительно лучшую производительность в задачах численного рассуждения. [research summary via search](https://arxiv.org/pdf/2402.14903) [fast.ai Karpathy tokenizers post](https://www.fast.ai/posts/2025-10-16-karpathy-tokenizers.html)
- Альтернативная тактика — единичная посимвольная (single-digit) токенизация чисел — по некоторым исследованиям даёт **лучшую** арифметику, чем group-based подходы (и left-to-right, и right-to-left варианты укрупнённой токенизации); задача-специфичные альтернативные схемы токенизации давали прирост точности до **+33%** на арифметике с большими числами. [источник исследования по alternative tokenization for arithmetic]
- o200k_base (GPT-4o, o-series, GPT-5-семейство): словарь вырос примерно вдвое (~200K токенов против ~100K у cl100k_base); переход на o200k_base снижает удельную стоимость токенов на нелатинских языках примерно на **35%**. Точных данных о смене конкретно "3-цифрового" правила на другое в o200k_base **не найдено** — [НЕ ПОДТВЕРЖДЕНО].
- Код и отступы: GPT-2 кодировал каждый пробел индентации Python отдельным токеном — "растрата" длины последовательности; GPT-4 группирует пробелы отступа в единые токены, специально оптимизируясь под Python-style код. [fast.ai / Karpathy tokenizer walkthrough](https://www.fast.ai/posts/2025-10-16-karpathy-tokenizers.html)
- Claude использует собственный токенизатор, обученный на своих данных — строки токенизируются иначе, чем у GPT/Gemini; разные вендоры имеют разные merge-таблицы, размеры словаря и разную обработку кода/пробелов/нелатинских скриптов. [dev.to tokenizer quirks summary](https://dev.to/gabrielanhaia/tokenizer-quirks-claude-gpt-and-gemini-dont-count-the-same-text-the-same-way-1522)

**Для слайда:**
- "1000000" в GPT-4/cl100k_base — это не 7 отдельных цифр и не одно число, а три токена "100"+"000"+"0", нарезанные слева направо, что не совпадает с разрядами (тысячи/миллионы читаются справа налево) — отсюда часть ошибок сложения многозначных чисел.
- GPT-2 тратил один токен на КАЖДЫЙ пробел отступа Python-кода — при 4 уровнях вложенности (16 пробелов) это 16 токенов впустую на одну строку; GPT-4 научился схлопывать это в один токен на всю группу пробелов.
