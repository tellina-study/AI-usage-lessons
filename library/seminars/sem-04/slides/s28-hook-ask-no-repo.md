# Вне репозитория: `ask`, не тихое `allow`

## Assertion

Вне git-репозитория хук не пропускает коммит молча — он честно просит подтверждения, потому что защита без репозитория не может ничего проверить.

## Visual

Снимок терминала, моноширинный шрифт, дословно из капчура:

```
=== каталог: /tmp/no-repo-demo (git init НЕ выполнялся) ===
=== git rev-parse --is-inside-work-tree ===
fatal: not a git repository (or any of the parent directories): .git
(exit code: 128)
=== INPUT ===
{"tool_input":{"command":"git commit -m \"initial\""}}
=== HOOK OUTPUT (stdout) ===
{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask","permissionDecisionReason":"WARNING: branch-protection gate inactive — this is not a git repository yet (no .git found), so this hook cannot check anything. Run git init before your first commit if you want main/master protection; proceeding now commits with no branch discipline in effect."}}
=== hook exit code: 0 ===
```

## Speaker notes

Третий случай, который стоит показать отдельно от `deny` и от тихого `allow` на рабочей ветке. Каталог `/tmp/no-repo-demo` — `git init` в нём ни разу не выполнялся. Прямая проверка `git rev-parse --is-inside-work-tree` завершается ошибкой: «fatal: not a git repository», код выхода 128. Это не гипотетическая ситуация — именно так шаблон курса мог оказаться скопированным в обычную папку до инициализации git, и хук должен как-то вести себя именно в этот момент, не только в уже готовом репозитории.

На попытку `git commit -m "initial"` в таком каталоге хук не пытается угадать ветку — угадывать нечего, репозитория нет физически. Вместо `deny` он возвращает `permissionDecision: "ask"` с развёрнутым текстом предупреждения: гейт защиты веток неактивен, потому что git-репозитория ещё нет, и хук в принципе не может ничего проверить; если нужна защита main/master, сначала нужно выполнить `git init`, а прямо сейчас коммит пройдёт без какой-либо дисциплины по веткам.

Это решение сознательное, а не случайное поведение по умолчанию. Альтернатива — молча пропустить коммит, раз проверка невозможна, — выглядела бы как работающая защита, хотя на деле защиты в этот момент нет вообще: никакого сигнала пользователю, никакой записи о том, что гейт не сработал. `ask` вместо тихого `allow` — это прямое применение принципа, который встретится в провале раздела с другой стороны: гейт, который тихо не срабатывает, неотличим на вид от гейта, который прошёл успешно. Здесь эта проблема решена явно: репозитория нет — хук об этом прямо говорит, а не делает вид, что проверил.

Три случая — `deny` на main, тихий `allow` на рабочей ветке и явный `ask` вне репозитория — вместе описывают полное поведение хука на всех состояниях, которые он вообще способен различить. Ни одно из трёх состояний не оставляет пользователя в неведении о том, что произошло: либо коммит заблокирован с названной причиной, либо прошёл штатно, либо прошёл с явным предупреждением о собственной неполноте. Именно такая полнота охвата и отличает проверенный гейт от гейта, который «вроде бы работает», — и именно это стоит проверить в своём собственном хуке, прежде чем на него полагаться.
