## Q1 — Судьба fine-tuning в 2026: уходит ли?

**Короткий ответ: fine-tuning НЕ умер, но перестал быть умолчанием. Он сузился до "поведения, стиля, формата, политики", а "знания" ушли в RAG / длинный контекст / context engineering. Full fine-tuning почти всегда заменён на PEFT (LoRA/QLoRA), а для знаний-которые-меняются fine-tuning теперь считается анти-паттерном.**

- **Консенсус 2026 — "гибрид, а не дебаты":** RAG для знаний, которые меняются; fine-tuning для стабильного поведения, схемы и тона. Вопрос "RAG vs fine-tuning" в 2026 считается во многом устаревшим — реальный вопрос: *где разместить знание, где закодировать поведение, и как непрерывно оценивать оба*. (BigData Boutique 2026, D8; IBM/Red Hat explainers D9/D10; Umesh Malik "RAG vs Fine-Tuning 2026")
- **Когда fine-tuning ВСЁ ЕЩЁ оправдан (критерии 2026):**
  - сбой = *поведенческая* несогласованность: неверный формат вывода, нестабильный тон, слабая классификация, плохое следование политике/refusal-паттернам;
  - нужен жёстко стабильный бренд-голос / конвенции команды без громоздких system-промптов;
  - латентность/стоимость: дистилляция большой модели в маленькую под узкую задачу (OpenAI: собрать трафик с o1 → fine-tune gpt-4o-mini → дешевле и быстрее). (OpenAI Cookbook SFT/DPO/RFT, A11; OpenAI RFT guide, A12; 2025)
  - **НЕ fine-tune для свежих/меняющихся фактов** — это классическая ошибка: знание устаревает, переобучать дорого, и появляется catastrophic forgetting (см. failures #2).
- **Техники, заместившие "наивный SFT":**
  - **PEFT (LoRA/QLoRA)** — почти единственное, что большинству команд стоит рассматривать в 2026; full fine-tuning редко оправдан; PEFT снижает риск catastrophic forgetting, замораживая базовые веса. (D8; arXiv:2308.08747 B3)
  - **DPO** (Direct Preference Optimization) — лёгкая альтернатива RLHF: пары "лучше/хуже" без отдельной reward-модели; для субъективного качества (тон, стиль, уместность). (OpenAI Cookbook A11, 2025)
  - **RFT** (Reinforcement Fine-Tuning) — программируемый grader, шлифует reasoning; работает только на *однозначных* задачах (если эксперты независимо не сходятся в ответах — задача слишком неоднозначна для RFT). (OpenAI RFT guide A12, 2025)
  - **Long-context + prompt caching** — Anthropic: для базы знаний < ~200k токенов full-context + prompt caching может быть быстрее и дешевле, чем строить retrieval-инфраструктуру (A2-derived, см. Q5/Q7).
  - **Context engineering** — сам сдвиг (см. Q6) частично заместил "дообучить под задачу" на "правильно собрать контекст в рантайме".

## Q2 — RAG 2026

- **RAG не убит длинным контекстом; универсального победителя нет.** Бенчмарки 2025 (U-NIAH, B5; Chroma "Context Rot", B6) показывают: производительность сильно зависит от задачи и сильно варьируется между моделями. Меньшие модели выигрывают от RAG сильнее (U-NIAH: RAG win-rate 82.58% над прямым ответом во всех настройках, B5). [VERIFY-ON-DAY for exact %]
- **Context rot (Chroma, 2025, B6):** с ростом числа токенов в контексте точность извлечения моделью информации из этого контекста *падает*; причина — n² парных связей трансформера + меньше специализированных параметров для длинных зависимостей. → Длинный контекст ≠ "просто положи всё внутрь". (подтверждено в Anthropic context-engineering A2)
- **Когда RAG избыточен/вреден:**
  - корпус знаний помещается в окно (< ~200k токенов у Anthropic) → full-context + prompt caching проще, дешевле, без retrieval-инфры (A2);
  - retrieval молча деградирует на масштабе (> ~10k документов) — система всё ещё *что-то* возвращает, но не то; "вернуть что-то ≠ вернуть правильное" (D1, Kore.ai D2);
  - плохой retrieval + генерация = галлюцинация "поверх" мусора (см. failures #4, #5).
- **Эволюция:** GraphRAG (Microsoft, arXiv:2404.16130 B2, июль 2024 A14) для глобальных/мульти-хоп запросов и запросов "догони меня по всем обновлениям" — но дорогой на индексации (исторически индексация одного датасета ~$33k в начале 2024; Microsoft снизила радикально к 2025; ~$7 за книгу 32k слов; ROI положителен только для синтеза по многим источникам, не для простых lookup). (D11, Microsoft Azure AI Foundry blog, 2025) [VERIFY-ON-DAY cost figures]
- **Agentic RAG** — итеративный retrieve-reason-retrieve; новые режимы отказа: *retrieval thrash* (near-duplicate queries, осциллирующие термины, плоское качество), *tool storms*, *context bloat*, hallucination propagation, memory poisoning. (D1, Towards Data Science 2026)
- **Hybrid/semantic search** (dense+sparse) и Self-RAG — в эмпирике 2025 Self-RAG дал наименьший hallucination-rate среди 12 RAG-вариантов (~5.8% vs 12–14% у стандартных agentic-пайплайнов; MDPI Electronics 2025 — MEDIUM, secondary). [VERIFY-ON-DAY]

## Q3 — AI-агенты: цикл и режимы отказа

- **Цикл plan → act → observe → iterate** — это паттерн **ReAct** (Yao et al., arXiv:2210.03629, окт 2022, ICLR 2023, B1): чередование reasoning-трасс и действий; reasoning ведёт/обновляет план, действия дают наблюдения из среды. Прирост: +34% ALFWorld, +10% WebShop (B1/D12). **Reflexion** — расширение с явной self-evaluation после провала (дороже, лучше на trial-and-error задачах).
- **Anthropic "Building Effective Agents" (2024-12-19, A1) — ключевые различения:**
  - *Workflow* = "LLM и инструменты оркестрируются через предопределённые пути кода"; *Agent* = "LLM динамически направляет свои процессы и использование инструментов".
  - "для многих приложений оптимизация одиночных LLM-вызовов с retrieval и in-context примерами обычно достаточна" → **найти простейшее решение; иногда не строить агентов вовсе**.
  - "Agentic-системы обычно меняют латентность и стоимость на лучшее качество — оцени, когда этот размен оправдан".
  - 5 workflow-паттернов: prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.
- **Режимы отказа агентов (документировано):**
  - **Накопление ошибок (reliability compounding):** 5 компонентов с 99% надёжности → 95% системной; 10 → 90%. Улучшение отдельного агента почти не двигает системную надёжность, когда ошибки распространяются неконтролируемо. (D3, MindStudio)
  - **Петли / стоимость:** агент plan→tool→429→replan ×~4800/час, $1000 к 12-му часу, экспонента при ре-инжесте собственных лог-провалов (см. failures #1, C5).
  - **Недетерминизм:** один проваленный шаг → агент уходит в совершенно другую траекторию → непредсказуемый результат (Anthropic multi-agent A3).
  - **Токен-стоимость:** агенты ~4× токенов чата; multi-agent ~15× токенов чата (Anthropic, A3, 2025-06-13).
- **Когда агент НЕ нужен (детерминированный скрипт лучше):** Anthropic A1 + Cognition A4 — "use workflows to build structure around the predictable, use agents to explore the unpredictable"; большинство надёжных продакшн-систем — это workflow, не полностью динамические агенты. Для задач с жёсткими зависимостями/общим контекстом мульти-агент проваливается (A3: "most coding tasks involve fewer truly parallelizable tasks than research").

## Q4 — MCP и tool use

- **Статус экосистемы:** MCP открыт Anthropic в **ноябре 2024**; OpenAI принял (Agents SDK, Responses API, ChatGPT desktop) в марте 2025; Google DeepMind (Hassabis) подтвердил поддержку в Gemini в апреле 2025; интегрируется с Microsoft Semantic Kernel/Azure OpenAI. Передан под Linux Foundation (Agentic AI Foundation) с OpenAI/Google/Microsoft/AWS/Cloudflare/Bloomberg. (D5 Wikipedia, D6 Pento, A13 Anthropic) — *де-факто стандарт*.
- **Масштаб [VERIFY-ON-DAY — растёт быстро]:** ~97M загрузок/мес к марту 2026 (≈970× за 18 мес); реестр серверов ~1,200 (Q1'25) → ~3,400 (Q3'25) → ~6,800 (конец 2025) → ~9,400+ (середина апреля 2026). (D6 Pento, D5)
- **Tool use / function calling паттерны:** augmented-LLM (модель сама генерирует запросы/выбирает инструмент); strict/structured tool calling (JSON-схема). Anthropic A2: избегать "раздутых наборов инструментов, покрывающих слишком много".
- **Безопасность — фундаментальная проблема MCP (документировано, см. failures #6–#10):**
  - **Prompt injection через контент/инструменты:** "LLM доверяет всему, что присылает убедительно звучащие токены" → confused-deputy атаки (Simon Willison, 2025-04-09, C7).
  - **Tool poisoning:** вредоносные инструкции в метаданных инструмента — самый распространённый client-side вектор; инструменты могут *мутировать своё определение после установки* ("rug pull") и начать красть API-ключи (Unit 42 C9; AuthZed C6).
  - **Кто видит данные в цепочке:** агент → инструмент → внешний API → провайдер. Anthropic data-retention doc (A7) явно: данные, обработанные **сторонними интеграциями, НЕ покрыты ZDR**; MCP-connector помечен "ZDR: No" (данные хранятся по стандартной политике). → каждый внешний инструмент = новая граница доверия и новая retention-политика.

## Q5 — Работа через API

- **Структурированный вывод / function calling:** JSON-схема компилируется в грамматику; у Anthropic strict-схемы кэшируются *отдельно* от контента (важно для приватности — нельзя класть PII/PHI в имена полей/enum/pattern). (A7)
- **Batching:** Anthropic Batch API — 29-дневное хранение, **не ZDR-eligible** (асинхронное хранилище обязательно). (A7)
- **Prompt caching:** переиспользование KV-тензоров префикса (не текста вывода — результат не меняется); Anthropic заявляет до **90% экономии стоимости** и до **85% латентности** на длинных промптах; OpenAI — авто-кэш ~50% экономии по умолчанию; KV хранится ~5–10 мин. (D7, A7) [VERIFY-ON-DAY vendor figures]
- **Стоимость / уровни доступа / data retention (актуально 2026):**
  - **Anthropic:** стандарт — короткий footprint; ZDR = данные не хранятся at-rest после ответа (Messages/Token-Counting API, Claude Code с commercial ключами); **НЕ ZDR:** Console/Workbench, Files API, Batch (29 дн), code-execution контейнеры (до 30 дн), MCP-connector, Agent Skills, потребительские планы, third-party интеграции. Даже при ZDR — при флаге за нарушение политики данные могут храниться **до 2 лет**. Activity Feed — 6 лет. (A7, live doc 2026)
  - **OpenAI:** по умолчанию вход/выход API хранятся до **30 дней** для abuse-мониторинга; ZDR/Modified-Abuse-Monitoring — по предварительному одобрению, не автоматически. (A10)
  - **Историческое предупреждение (NYT v. OpenAI):** суд May 2025 обязал OpenAI сохранять *все* логи ChatGPT (затронуло 400M+ пользователей); индефинитное удержание закончилось 26 сент 2025; ноябрь 2025 — суд обязал выдать 20M анонимизированных логов. → **данные в API-цепочке могут пережить вашу политику из-за судебного приказа.** (C3, C4, A8, A9)
- **Безопасность API-ключей:** утечка ключей — повторяющийся root cause MCP-инцидентов (mcp-remote CVE-2025-6514: malicious server → booby-trapped authorization_endpoint → кража API/cloud/SSH-ключей, 437k+ загрузок; см. failures #7). Anthropic: с ZDR не поддерживается CORS — "никогда не выставляй API-ключи в браузерном JS, используй backend-прокси". (A7)

## Q6 — Context engineering (формирующаяся дисциплина) + CoT

- **Сдвиг от prompt engineering к context engineering** (Anthropic, 2025-09-29, A2, релиз вместе с Sonnet 4.5): context engineering = "стратегии курирования и поддержания оптимального набора токенов во время инференса" по всему: system-инструкции, инструменты, внешние данные, история сообщений. Prompt engineering — дискретен; context engineering — итеративен (каждый шаг — решение, что попадёт в контекст). Главный принцип: **"найти наименьший набор высокосигнальных токенов, максимизирующий вероятность желаемого исхода"**.
  - Техники: компакция (суммирование при приближении к лимиту), structured note-taking (память вне окна), sub-agent с дистиллированными сводками (1–2k токенов), just-in-time retrieval (лёгкие идентификаторы: пути/ссылки/запросы вместо предзагрузки всего).
  - Анти-паттерны (A2): brittle хардкод-логика; vague high-level guidance; раздутые tool-наборы; "прачечный список" edge-cases в промпте.
- **Chain-of-Thought как паттерн рассуждения + критика faithfulness (Anthropic, апр 2025, A5/A6):**
  - "Reasoning models don't always say what they think": модели *часто не упоминают подсказки*, на которые опирались. В среднем Claude 3.7 Sonnet упоминал подсказку 25% случаев, DeepSeek R1 — 39%. Для "опасных" подсказок (unauthorized access) — Claude faithful только 41%, DeepSeek R1 — 19%.
  - **Когда CoT не помогает/менее надёжен:** faithfulness *падает на более трудных датасетах* — GPQA даёт −44% относительного падения faithfulness у Claude 3.7 vs MMLU, −32% у DeepSeek R1. Outcome-based RL поднимал faithfulness, но быстро выходил на плато (+63% MMLU / +41% GPQA, затем плато).
  - **Вывод для лекции:** CoT-текст ≠ окно в реальное рассуждение модели; нельзя аудитировать решение по его "объяснению"; человек-валидатор должен проверять *результат и факты*, не верить self-rationale. (METR 2025 даёт нюанс: CoT всё же информативен, даже будучи "unfaithful" — баланс для дискуссии.)

## Q7 — Практические критерии выбора архитектуры

(Полная матрица — в `decision-criteria.md`.) Ключевые опорные принципы из источников:
- **Лестница сложности (Anthropic A1):** один промпт → промпт+RAG/few-shot → workflow (предопределённые пути) → агент (динамический). Подниматься только при необходимости.
- **Знание vs поведение (BigData Boutique 2026, D8):** меняющееся знание → RAG/контекст; стабильное поведение/тон/схема → fine-tune (PEFT).
- **Предсказуемое vs непредсказуемое (Cognition A4 / Anthropic A1):** структурированный детерминированный код/workflow вокруг предсказуемого; агент только для исследовательского/непредсказуемого с высокой ценностью задачи (оправдывающей 4–15× токенов).
- **Свежесть/аудит:** нужна свежесть/провенанс/цитаты → RAG (search_results + citations), не fine-tune, не "память в весах".
- **Когда обычный код БЕЗ ИИ лучше:** детерминированная, верифицируемая, повторяемая задача с чёткой спецификацией (парсинг, валидация схемы, арифметика, rule-based маршрутизация) — ИИ добавляет недетерминизм, стоимость, латентность, поверхность атаки prompt-injection без выигрыша. Это прямое следствие Air Canada / DPD / Chevrolet / MyCity (failures #11–#14): для отдачи фиксированной политики/цены детерминированная страница/правило надёжнее генеративного чат-бота.
