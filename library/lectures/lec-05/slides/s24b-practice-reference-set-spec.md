# Visible content

## Title bar
Набор проверочных примеров — как проверять ответы ИИ так же, как проверяют код

## Body
[schema_matrix — набор случаев + шкала требований по цене ошибки + граница]

**ЧТО ЭТО**
Небольшая коллекция реальных случаев, для каждого из которых заранее записано, какой ответ считается приемлемым. По сути это те же тесты, только проверяется не код, а ответ модели. Набор собирают из настоящих обращений пользователей, а не из придуманных: правдоподобный пример проверяет воображение команды, а реальный — продукт. Начинают обычно с пяти-десяти случаев и растят набор дальше.

**КАК РАБОТАЕТ**
Набор живёт рядом с продуктом и меняется вместе с ним, а не лежит отдельным документом. Требования назначают заранее — по цене ошибки:

| Что проверяется | Что требуют |
|---|---|
| Обычный запрос | права почти всегда |
| Отказ по правилам безопасности | каждый раз, без исключений |
| Ответ с юридическим последствием | не доверяют модели — жёсткое правило поверх |

Проверка запускается сама, вместе с обычными тестами, и так же останавливает выпуск, а не пишет предупреждение в журнал. Каждый случившийся сбой возвращается в набор отдельным случаем — поэтому однажды пойманная ошибка не повторяется молча на следующем выпуске. Готовые инструменты для этого есть; конкретные названия — в материалах лекции.

[Gold callout — ГДЕ НЕ РАБОТАЕТ]
Три способа обмануть себя этим приёмом. Набор, который всегда зелёный, ничего не измеряет — это сломанный измеритель, а не гарантия. Как только прохождение набора становится целью команды, а не средством, он перестаёт быть мерой. И одна удачная попытка доказательством не является: одинаковые прогоны расходятся между собой, поэтому проверку повторяют, а требование ставят с запасом на разброс. Отдельно: требование выше точности самого измерителя измеряет измеритель, а не продукт — если ответы оценивает другая модель, согласная с людьми примерно в 85% случаев, планка в 95% бессмысленна.

## Speaker notes

Это прямой перенос дисциплины прошлой лекции — теста, написанного до кода, — с кода на продукт. Там тест был исполняемой спецификацией: он говорит, что значит «работает», и говорит это раньше результата. Здесь ровно то же, только проверяется ответ модели.

Что стоит проговорить про сбор набора. Источник примера обязателен и обязательно реальный: рекомендация начинать с пяти-десяти настоящих рабочих примеров, а не выдуманных, — то же требование «реальное прошлое, а не правдоподобное», которое мы применяли к интервью. Придуманный пример проверяет воображение команды, а не продукт. Практическое следствие: набор нельзя написать за один присест в начале проекта — он растёт из эксплуатации, и по числу случаев, пришедших из реальных сбоев, видно, живой он или декоративный.

Про шкалу требований. Три строки на слайде выглядят как три порога, но третья строка — не порог. Это отказ от инструмента: ответ с юридическим последствием не отдают модели вообще, поверх неё ставят детерминированное правило. Различать это важно, иначе шкала читается как «просто поставьте планку повыше».

Чем это физически исполняется, если спросят. Есть промышленные инструменты, встраивающиеся в конвейер сборки: promptfoo останавливает сборку кодом возврата при падении балла ниже порога; штатная проверка в Claude Code прогоняет случаи трижды, а не один раз, так что разброс виден сразу; DeepEval запускается обычным прогоном тестов, и отдельный шаг заводить не нужно. Единого термина для одной строки набора нет — в разных инструментах это goldens, examples, test cases, samples, и искать общий стандарт бессмысленно.

И граница, ради которой карточка вообще имеет право стоять рядом с разбором провалов. Зелёный набор — не доказательство. Насыщение: всегда зелёный набор ничего не измеряет. Подгонка под набор: как только прохождение становится целью, мера перестаёт быть мерой. Разброс: инференс модели недетерминирован даже при нулевой температуре, расхождение между одинаковыми прогонами доходит до пятнадцати процентных пунктов. И надёжность измерителя: модель-судья согласуется с людьми примерно на восьмидесяти пяти процентах — на уровне, на котором люди согласуются между собой.
