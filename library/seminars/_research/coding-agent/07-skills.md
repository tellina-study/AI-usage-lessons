# Скиллы (Agent Skills): вынос знаний из постоянного контекста в загрузку по требованию

## Резюме (8 тезисов)

1. Скилл решает ровно ту проблему, на которой стоит эта ступень лестницы: файл инструкций читается **целиком в каждой сессии**, скилл — **только когда релевантен**. Progressive disclosure: при старте в контекст грузится только имя+описание скилла (≈100 токенов), тело `SKILL.md` — только при срабатывании (<5000 токенов), вложенные файлы — только если агент реально в них заглянул.
2. Триггером служит не название, а поле `description` во фронтматтере — единственное, что видит модель при выборе среди потенциально 100+ установленных скиллов. Плохое описание («Helps with documents», «Processes data») — гарантированный провал срабатывания, даже если тело скилла безупречно.
3. **Живая проверка на материале собственного курса:** из 13 скиллов в `.claude/skills/` фронтматтер с `name`/`description` есть только у одного (`pre-user-gate`). Остальные 12 начинаются сразу с `# заголовок` — система подставляет имя файла как фолбэк-описание. Это факт текущего состояния проекта: 12 из 13 наших скиллов физически не могут сработать автоматически по смыслу запроса, только через явный `/slash`-вызов.
4. Скилл ≠ файл инструкций (грузится всегда) ≠ субагент (свой изолированный контекст и своя задача, а не процедура внутри текущей сессии) ≠ MCP-сервер (доступ наружу — к API, файлам за пределами модели, а не знание внутри неё).
5. Документированная цена ошибки — не абстракция. Исследование skill-induced failures (arXiv:2608.11888) нашло 307 подтверждённых случаев вреда от скиллов: 125 функциональных провалов (68,8% — скилл заставил агента сделать часть задачи неправильно) и 182 случая раздутия стоимости (до +451% токенов, SWE-Skills-Bench).
6. Скилл — исполняемый код и данные из чужого источника, а не просто текст. Аудит Snyk «ToxicSkills» (5 февраля 2026, 3984 скилла из ClawHub/skills.sh) нашёл у 13,4% (534) критическую проблему безопасности; 91% подтверждённых вредоносных образцов использовали prompt injection. В феврале 2026 задокументирована первая координированная malware-кампания через ClawHub — 30+ вредоносных скиллов.
7. «Набрал скиллов из чужого awesome-списка» — путь к деградации выбора: в нашем каталоге уже есть прецедент отклонения (`rohitg00-toolkit`) из-за несовпадения самозаявленных цифр с реальным пересчётом в 3–4 раза; академическая работа фиксирует фазовый переход, после которого точность выбора скилла резко падает.
8. Критерий качества скилла — не объём, а конкретность: `description` с ключевыми словами и явным «когда использовать», тело <500 строк, ссылки не глубже одного уровня, готовые скрипты вместо генерации кода на лету. Наши `sync-library` и `build-deck` соответствуют этому по телу, но проваливают триггер-слой из пункта 3.

## 1. Классическая база

**Что такое скилл, если не кодить вообще.** Представьте сотрудника, у которого на столе — толстый регламент компании (это файл инструкций, CLAUDE.md), а в шкафу — папки-методички по конкретным процедурам: «как оформить командировку», «как закрыть квартал». Регламент со стола сотрудник перечитывает каждый день, хочет он того или нет — это стоит времени независимо от того, нужен ли сегодня хоть один его пункт. Методичку из шкафа он снимает с полки только тогда, когда реально оформляет командировку. Скилл — методичка из шкафа: агент «снимает» её с диска и читает целиком только тогда, когда задача совпала с тем, для чего она написана.

**Чем скилл отличается от файла инструкций.** Разница не в содержании, а в режиме загрузки. Файл инструкций движок подгружает в начало **каждой** сессии целиком, до первого сообщения пользователя — фиксированный налог на каждый запрос вне зависимости от того, нужен ли сегодня хоть один его раздел. Скилл участвует в контексте на старте только именем и описанием; полное тело подключается лишь тогда, когда запрос совпал с тем, что скилл обещает делать. Правило «это нужно каждой сессии → файл инструкций; это нужно иногда → скилл» — прямое следствие разницы в загрузке, не вопрос вкуса.

**Чем скилл отличается от субагента.** Субагент — отдельный «сотрудник»: у него своё изолированное контекстное окно, своя делегированная задача и собственный отчёт по завершении. Скилл — не отдельный сотрудник, а методичка, которую читает **тот же** агент, что ведёт текущую сессию, не выходя из неё. Нужна параллельная, независимая работа с отдельным бюджетом контекста (три критика проверяют один деком одновременно) — это субагент. Нужно «вспомнить, как у нас принято делать X» внутри той же беседы — это скилл.

**Чем скилл отличается от MCP-сервера.** MCP-сервер даёт доступ **наружу** — к внешнему API, базе данных, Google Docs, GitHub — через инструменты, которые физически выполняют сетевые запросы за пределами модели. Скилл ничего не подключает сам по себе — это знание **внутри** модели: как пользоваться уже доступными инструментами, в каком порядке, с какими параметрами. Скилл может *инструктировать*, как вызывать MCP-инструмент (наш `sync-library` явно называет `mcp__workspace-mcp__list_drive_items` с конкретным `folder_id`), но сам этим доступом не является.

## 2. Механика

**Структура папки.** Минимальный скилл — это директория с единственным файлом `SKILL.md`:

```
skill-name/
  SKILL.md          # обязателен: фронтматтер + инструкции
  REFERENCE.md       # опционально: подробности, читается по требованию
  scripts/
    validate.py      # опционально: исполняется, код не грузится в контекст
```

**Фронтматтер — обязательные поля и жёсткие правила валидации** (актуально на 2026-09-20, `platform.claude.com/docs/en/agents-and-tools/agent-skills/overview`):

| Поле | Требования |
|---|---|
| `name` | максимум 64 символа; только строчные буквы, цифры, дефисы; без XML-тегов; зарезервированные слова `anthropic`, `claude` запрещены |
| `description` | не может быть пустым; максимум 1024 символа; без XML-тегов; должно содержать и «что делает», и «когда использовать» |

Официальная рекомендация по имени — герундий (`processing-pdfs`, `analyzing-spreadsheets`) или отглагольное существительное; явно запрещены расплывчатые `helper`, `utils`, `tools`, `documents`, `data`.

**Три уровня послойного раскрытия (progressive disclosure) — с точными цифрами из официальной таблицы:**

| Уровень | Когда грузится | Стоимость в токенах | Содержимое |
|---|---|---|---|
| 1. Метаданные | Всегда, при старте сессии | ≈100 токенов на скилл | `name` + `description` из фронтматтера |
| 2. Инструкции | При срабатывании скилла | <5000 токенов | тело `SKILL.md` |
| 3. Ресурсы и код | По требованию, при обращении | 0, пока не открыт | вложенные `.md`-файлы, скрипты (выполняются, их код не грузится — в контекст попадает только вывод) |

Именно уровень 1 делает возможным «установить много скиллов без штрафа по контексту, пока не сработал ни один» — это прямая цитата логики документации, не догадка.

**Область видимости (scope).** Claude Code ищет `SKILL.md` от более общего к более специфичному: managed (`.claude/skills/` в организационных настройках, видят все пользователи), личная (`~/.claude/skills/<name>/SKILL.md`, все проекты одного разработчика), проектная (`.claude/skills/<name>/SKILL.md` в корне репо — наш случай, все 13 скиллов курса лежат здесь), вложенная для монорепо (`<subdir>/.claude/skills/<name>/SKILL.md`) и плагинная (`<plugin>/skills/<name>/SKILL.md`, неймспейс `/plugin-name:skill-name`).

**Как запускается.** Два независимых механизма, каждый со своим флагом фронтматтера: автозагрузка моделью по совпадению `description` с запросом (`disable-model-invocation`, по умолчанию `false` — скилл *может* сработать сам) и явный вызов через `/skill-name` (`user-invocable`, по умолчанию `true`). Можно сделать скилл только-пользовательским (`disable-model-invocation: true` — опасный `/deploy`) или только-модельным (`user-invocable: false` — скрытый контекст, не должен маячить в меню команд). `[НЕ ПОДТВЕРЖДЕНО]`: точные версии Claude Code для конкретных диагностических команд (`/skill-doctor` — заявлено с v2.1.252) взяты из вторично обработанного фетча документации, не перепроверены по первоисточнику отдельно.

**Статус функции.** Автозагрузка скиллов моделью, форк-выполнение в изолированном субагенте, динамическая инъекция контекста и предварительное одобрение прав (`allowed-tools`) помечены в документации Claude Code как Generally Available, не бета. У самого формата `SKILL.md` — параллельная история: наш каталог (`anthropic-skills.yaml`) отмечает заявку о том, что формат стал кросс-вендорным открытым стандартом (agentskills.io, декабрь 2025, ~40 клиентов вне Claude, включая GitHub Copilot, Cursor, OpenAI Codex, Gemini CLI) — заявка явно помечена в каталоге `[unverified]`, взята из вторичной сводки поиска, не с прямого фетча agentskills.io.

**Как понять, сработал ли скилл, не гадая.** `/skills` открывает интерактивное меню всех доступных скиллов с их описаниями и источником; `/context` показывает всё, что реально загружено в текущий контекст, сгруппированное по источнику; `/skill-doctor` (если версия поддерживает) явно показывает контекстную стоимость каждого скилла в сессии и помечает те, что ни разу не вызывались — это прямой ответ на вопрос «я поставил 10 скиллов, работают ли они вообще» без необходимости гадать по поведению агента.

## 3. Триггер «когда скилл становится нужен» и когда не нужен

**Основной критерий — тот же, что и для «вынести из файла инструкций»:** «это нужно каждой сессии?» → нет → кандидат в скилл. Если правило применяется не в каждой сессии, а только для задач определённого типа — держать его в файле инструкций означает платить контекстом за него в 9 из 10 сессий, где оно не нужно. Прямая официальная формулировка: если пункт — это многошаговая процедура или касается только части кодовой базы, он должен уйти в скилл, а не жить в файле, читаемом каждой сессией целиком.

**Когда достаточно просто хорошего запроса.** Если процедура нужна один раз или почти никогда не повторяется в тех же деталях — писать под неё скилл дороже, чем просто подробно попросить агента один раз. Сигнал «мы уже третий раз объясняем агенту одно и то же в разных сессиях» — момент, когда пора оформить скилл, не раньше. Официальная рекомендация прямо советует **сначала** пройти задачу без скилла обычным промптом и только потом решать, какой контекст стоит переиспользовать — не писать скилл заранее «на всякий случай».

**Когда это должен быть хук, а не скилл.** Разница принципиальная: скилл — это **знание**, которое агент может учесть или не учесть; хук — **механика**, которую харнесс исполняет сам, независимо от «согласия» агента. Наш блок про хуки формулирует это так: «правило, записанное словами, агент может проигнорировать — хук не спрашивает согласия». Если утечка правила недопустима вообще (никогда не коммитить в `main`, никогда не выполнять `rm -rf` вне рабочей директории) — это `PreToolUse`-хук в `.claude/settings.json`, а не текст скилла, каким бы подробным он ни был. Скилл, который пытается быть «жёстким ограничением», на деле остаётся просьбой в текстовой форме.

**Когда это должен быть субагент, а не скилл.** Если работа требует отдельного изолированного бюджета контекста — параллельного выполнения, независимой проверки, делегирования подзадачи с собственным результатом — нужен субагент. Скилл делится тем же контекстным окном, что и всё остальное; он решает проблему «не грузить это, пока не нужно», а не «слишком много в одном окне». Наш `build-deck` — пограничный случай: сам скилл — процедура оркестрации внутри сессии, но внутри него оркестратору явно предписано **не рендерить слайды самому**, а спавнить `presentation-designer` и трёх QA-агентов как субагентов. Скилл здесь — знание «как и когда делегировать», субагенты — сама изолированная работа.

## 4. Провалы и ограничения (структурная часть блока — не менее 30%)

### 4.1 Скилл не подхватывается: описание написано для человека, а не как триггер

Официальный чек-лист авторства скиллов прямо перечисляет расплывчатые описания как антипаттерн: `«Helps with documents»`, `«Processes data»`, `«Does stuff with files»` — все три официально названы примерами того, чего делать нельзя, потому что модель выбирает скилл именно по этому полю среди потенциально 100+ установленных одновременно. Требование сформулировано жёстко: описание должно быть написано от третьего лица (не «I can help you…», не «You can use this to…») и содержать конкретные ключевые слова + явный триггер-контекст.

**Живая проверка на материале собственного проекта.** Мы проверили все 13 скиллов курса (`.claude/skills/*/SKILL.md`) на наличие фронтматтера:

```
build-deck:       NO frontmatter (starts with: # build-deck)
catalog-docs:      NO frontmatter (starts with: # catalog-docs)
compile-wiki:      NO frontmatter (starts with: # compile-wiki)
diagram-refresh:   NO frontmatter (starts with: # diagram-refresh)
extract-links:     NO frontmatter (starts with: # extract-links)
impact-check:      NO frontmatter (starts with: # impact-check)
issue-from-change: NO frontmatter (starts with: # issue-from-change)
pre-user-gate:     HAS frontmatter
publish-article:   NO frontmatter (starts with: # publish-article)
query-kb:          NO frontmatter (starts with: # query-kb)
reflect:           NO frontmatter (starts with: # reflect)
sync-library:      NO frontmatter (starts with: # sync-library)
update-lecture:    NO frontmatter (starts with: # update-lecture)
```

Один скилл из тринадцати. У остальных двенадцати первая строка файла — заголовок `# build-deck`, а не блок `---\nname: ...\ndescription: ...\n---`. В списке доступных скиллов это видно напрямую: `pre-user-gate` показан с реальным описанием-триггером, а остальные двенадцать — как `build-deck: build-deck`, `sync-library: sync-library`: система подставляет имя файла вместо отсутствующего описания. Такой скилл физически не может сработать по смыслу запроса — модели не с чем сопоставить намерение пользователя, кроме имени. Это состояние production-репозитория курса на сегодня: все процедуры производства лекций и работы с библиотекой доступны **только** через явный `/slash`-вызов, не через понимание запроса.

### 4.2 Скиллы, которые молча конфликтуют между собой

Эмпирическое исследование skill-induced failures (arXiv:2608.11888, бенчмарки SkillsBench + SWE-Skills-Bench) зафиксировало измеренный, не гипотетический вред: **307 подтверждённых случаев** сбоя, вызванного именно наличием скилла. Разбивка функциональных провалов (n=125): Task-Implementation Fault — **68,8%** (86/125, скилл сбивает агента и заставляет реализовать требуемое поле/расчёт неправильно или пропустить его), Artifact Misplacement — 19,2% (файлы не туда), Environment Mismatch — 10,4%, Applicability Mismatch — 1,6%.

Ключевая находка, прямая цитата: «большинство функциональных провалов вызваны не очевидно нерелевантными скиллами — наоборот, кажущиеся релевантными скиллы заставляют агента реализовать требуемое поле, поведение API, расчёт или формат вывода неправильно или пропустить его вовсе». Конфликт не громкий («скилл явно противоречит задаче»), а тихий. Эффективностные регрессии (n=182): 62,6% — избыточная процедура, 25,3% — раздувание контекста, до **+451%** токенов на задачу (SWE-Skills-Bench), падение pass rate на 16 из 84 задач в SkillsBench именно из-за подключённого скилла.

### 4.3 «Сет из 50 скиллов из чужого списка» — раздувание и деградация выбора

Академические работы фиксируют не просто «много — это неудобно», а измеримый фазовый переход: после определённого размера библиотеки скиллов точность их выбора моделью резко падает — структурный предел, а не вопрос терпения пользователя. Отдельная находка того же направления: два по отдельности полезных скилла (один максимизирует широту поиска, другой — авторитетность источника) могут **снижать** совместную эффективность при одновременной установке — экологические модели фиксируют отрицательное взаимодействие так же, как между видами в биологии.

Это не только теория. В нашем каталоге уже есть прецедент: коллекция `rohitg00/awesome-claude-code-toolkit` (2,3k звёзд, самозаявленные «135 агентов / 35 скиллов / 176+ плагинов») была **отклонена при прежнем ревью `harness-skills`**, а исследование `agent-lab-manager` нашло расхождение самозаявленных чисел с реальным файловым пересчётом в 3–4 раза. Контраст внутри того же каталога: `karanb192/awesome-claude-skills` выбирает «50+ проверенных» вместо гонки за размером, `voltagent/awesome-ai-agent-papers` идёт в противоположную сторону, набирая 1000+ записей широтой, а не проверкой каждой. Вывод: количество установленных скиллов само по себе не сигнал качества, а сигнал будущей проблемы выбора — если каждый не проверен на нужную задачу.

### 4.4 Скилл как вектор атаки

Скилл — не просто текст, это директория, которая может содержать исполняемые скрипты, и агент запускает её содержимое с теми же правами, что и остальную работу в сессии. Официальная документация не смягчает формулировку: «используйте скиллы только из доверенных источников — тех, что создали сами, или получили от Anthropic»; вредоносный скилл может привести к утечке данных, несанкционированному доступу к системе или другим рискам — в зависимости от того, к чему у Claude есть доступ в момент выполнения.

Это подтверждено количественно, не только предупреждением в документации:

- **Snyk «ToxicSkills»**, аудит от 5 февраля 2026, 3984 скилла из ClawHub и skills.sh: 36% содержат хотя бы один изъян безопасности; **13,4% (534)** — критический (распространение вредоносного ПО, prompt injection, утечка секретов). Из образцов, подтверждённых вручную как вредоносные: **76 payload'ов** (8 публично доступны на момент публикации); **91%** одновременно используют prompt injection, **100%** содержат распознаваемый вредоносный код-паттерн.
- В феврале 2026 задокументирована первая координированная malware-кампания через ClawHub — 30+ вредоносных скиллов, нацеленных на пользователей Claude Code, в одной волне.
- Datadog Security Labs подчёркивает отдельный риск: часть скиллов использует «динамическую инъекцию контекста» (команды выполняются, а их вывод подставляется в контекст ещё до того, как модель увидела сам скилл) — модельные защиты от prompt injection **физически не успевают сработать**, потому что вредоносная команда уже выполнилась до момента анализа.

Практический вывод для курса: скилл из чужого репозитория без явного аудита — не «текстовый файл, максимум неправильно посоветует», а установка стороннего ПО с доступом к файловой системе и сети. Официальная рекомендация — относиться к этому именно так («treat like installing software»), для корпоративного масштаба — сканирование скиллов на уровне организации (Claude Enterprise) либо независимые сканеры вроде `snyk/agent-scan`, созданного специально для проверки скиллов, MCP-серверов и других агентных компонентов на prompt injection и вредоносные нагрузки.

### 4.5 Ложное чувство «я поставил скиллы, теперь агент умный»

Это следствие пунктов 4.2–4.3, а не отдельный аргумент, но именно оно чаще всего остаётся неозвученным. Наличие скилла в списке доступных — не гарантия, что он вообще сработает (см. 4.1), что он поможет, а не помешает (68,8% функциональных провалов из 4.2 приходятся именно на «кажущиеся релевантными» скиллы), и что цена срабатывания оправдана результатом (до +451% токенов при эффективностной регрессии). Установка скилла — не покупка компетенции, а установка процедуры, ещё не проверенной на реальной задаче; официальная рекомендация ставит на первое место не написание документации, а построение трёх оценочных сценариев **до** развёрнутого текста скилла — чтобы не документировать воображаемые проблемы вместо реальных.

## 5. Критерии качества скилла

**Исполняемый рецепт, а не описание намерений.** Разница видна по конкретности: «проверь качество данных» — описание намерения; «запусти `python scripts/validate_fields.py fields.json`, при ошибке исправь и повтори» — исполняемый рецепт. Официальный принцип «degrees of freedom» формализует разделение на три уровня:

| Свобода | Когда уместна | Пример |
|---|---|---|
| Низкая (конкретный скрипт, минимум параметров) | Операция хрупкая, ошибка дорога, нужна консистентность | «Запусти именно `python scripts/migrate.py --verify --backup`, не меняй флаги» |
| Средняя (псевдокод/шаблон с параметрами) | Есть предпочтительный паттерн, но допустима вариация | шаблон функции с параметрами формата вывода |
| Высокая (текстовые инструкции, эвристики) | Верных подходов несколько, решение зависит от контекста | «Проанализируй структуру кода, проверь граничные случаи, предложи улучшения» |

**Проверяемый результат.** Хороший скилл включает шаг валидации, а не просто «сделай X»: официальный паттерн «validate → fix → repeat» (скилл `ooxml/scripts/validate.py`, `pre-user-gate` P0/P1-чеклист в нашем каталоге) даёт агенту объективный сигнал «готово» вместо субъективной самооценки.

**Узкая область видимости.** Домен-специфичная организация («когда пользователь спрашивает про sales-метрики, Claude читает только `reference/sales.md`, а не всё содержимое скилла») бережёт контекст даже после срабатывания скилла — узость должна проявляться не только в `description`, но и в структуре вложенных файлов.

**Конкретность против расплывчатости — на нашем собственном материале.** Скилл `sync-library` не говорит «синхронизируй документы с Google Drive» — он называет точный `folder_id` каждой из шести папок, точный путь манифеста (`/home/levko/AI-usage-lessons/catalog/manifests/documents.yaml`), точный MCP-инструмент (`mcp__workspace-mcp__list_drive_items`) и точное правило транслитерации имён файлов. Это и есть разница между «исполняемым рецептом» и «описанием шагов» — рецепт можно выполнить, не додумывая детали; описание требует, чтобы агент сам изобрёл недостающую конкретику на каждом прогоне, а значит — каждый раз немного по-другому.

## 6. Фишки для продвинутых

**Описание как поисковый запрос будущего себя.** Раз `description` — единственное, что видит модель при выборе среди множества скиллов, писать его стоит как то, что вы бы сами вбили в поиск полгода спустя, забыв детали: не «утилита для PDF», а «извлекает текст и таблицы из PDF, заполняет формы, объединяет документы — используй, когда работаешь с PDF-файлами или пользователь упоминает формы/извлечение документов» (пример из официальной документации).

**Вложенные файлы, подгружаемые только при надобности.** Паттерн — «высокоуровневый гид со ссылками»: `SKILL.md` держит быстрый старт и оглавление, `FORMS.md`/`REFERENCE.md` читаются лишь когда задача реально в них упёрлась. Ограничение, которое легко упустить: ссылки **не глубже одного уровня** от `SKILL.md` — иначе агент по дороге может прочитать файл частично (`head -100`) и потерять информацию. Показательно, что ни один из 13 скиллов курса не использует уровень 3 вообще — все плоские, без вложений; неиспользованная возможность там, где `SKILL.md` уже растёт (`compile-wiki` — 344 строки, `update-lecture` — 175).

**Скилл, оборачивающий обычный скрипт, вместо MCP-сервера.** Для детерминированной операции («провалидировать JSON», «сконвертировать формат») разворачивать MCP-сервер избыточно: скилл со скриптом в `scripts/` — минимальная обёртка, где Claude выполняет скрипт через bash и получает в контекст только вывод. Скрипты предпочтительнее генерации эквивалентного кода на лету — надёжнее, дешевле по токенам, консистентнее между вызовами.

**Ревизия набора скиллов.** `/skill-doctor` показывает контекстную стоимость каждого установленного скилла и помечает никогда не вызывавшиеся — инструмент именно для контроля разрастания. `skillOverrides` в `settings.json` выключает скилл для модели без удаления файла (`"off"`) или оставляет видимым только имя без триггера (`"name-only"`); `disableBundledSkills` разом выключает набор по умолчанию.

**Как понять, что скилл реально вызывался.** Три сигнала: (1) `/skill-doctor` — счётчик вызовов; (2) `/context` — что фактически загружено сейчас; (3) прямое наблюдение — Claude ссылается на специфичные для скилла термины и файлы, значит уровень 2 подгрузился. Если поведение пропало после `/compact` — вероятная причина не в поломке скилла, а в том, что его нужно спровоцировать заново: тело скилла не «прилипает» к сжатому контексту так же автоматически, как корневой файл инструкций.

## Разбор живых скиллов курса

### `pre-user-gate` — единственный с настоящим триггером

```yaml
---
name: pre-user-gate
description: Pre-USER-GATE walkthrough — orchestrator self-review before presenting GATE to user. Reduces user feedback rounds.
---
```

Единственный скилл каталога, формально соответствующий спецификации: `name` — короткий kebab-case идентификатор, `description` — третье лицо, конкретное действие и явный триггер-контекст. Тело — 165 строк не голословных шагов, а конкретный протокол: раздел «0. Self-reported metric re-verification» прямо запрещает доверять самоотчёту продюсер-агента о метрике («PROVEN PASS» — не доказательство) и предписывает перепроверку через focused re-spawn профильного критика с той же методикой. Раздел «Designer-extras grep» задаёт не абстрактное «проверь на мусор», а буквальный regex по трём группам паттернов — проверяемый, а не декларативный шаг.

### `build-deck` — исполняемый рецепт без триггера

```markdown
# build-deck

Build/rebuild a PowerPoint (PPTX) presentation for a lecture using the repo-first pipeline + visual loop + 3 QA agents.

## Role

You are an orchestrator. **Do NOT render slides yourself.** Delegate rendering to
`presentation-designer` agent and QA to `presentation-critic` + `student-simulator` +
`reader-simulator` agents.
```

Тело — образцовый «низкая/средняя свобода» рецепт: конкретный pre-flight-чеклист (`mcp__powerpoint__get_server_info` отвечает, пять утилит через `which`, точные пути `library/lectures/lec-NN/deck.yaml`), фазы с точными действиями («Спавнить `reader-simulator` agent в режиме `text-only`»), явные пороги («минимум 3 итерации на слайд, максимум 7»). Агенту не нужно додумывать, какой инструмент вызвать или сколько итераций достаточно. Но фронтматтера нет вообще — первая строка `# build-deck`, не блок `---`. В списке доступных скиллов он виден как `build-deck: build-deck`: качественное тело есть, триггер-слой отсутствует. Скилл работает исключительно через явный `/build-deck N`, никогда — по смыслу запроса вроде «собери презентацию для лекции 5».

### `sync-library` — конкретность вместо абстракции, тот же пробел в триггере

```markdown
## Constants

- Google account: kzlevko@gmail.com
- Root folder ID: `1-f2hpJrlUbfnMcxhR-6vF3xCsXZUI6am`
- Manifest path: `/home/levko/AI-usage-lessons/catalog/manifests/documents.yaml`
- Export directory: `/home/levko/AI-usage-lessons/catalog/exports/docs/`

## Execution

### Step 1: List Drive contents

Call `mcp__workspace-mcp__list_drive_items` for each folder:
```
mcp__workspace-mcp__list_drive_items(folder_id="1-f2hpJrlUbfnMcxhR-6vF3xCsXZUI6am")
```
```

Блок `## Constants` — буквально то, что раздел 5 называет «конкретность против расплывчатости»: не «синхронизируй с Google Drive», а точные ID шести папок, точный путь манифеста, точное имя MCP-инструмента с параметром. Скилл выполним детерминированно на каждом прогоне, без импровизации. И тот же структурный пробел, что у `build-deck`: нет фронтматтера — нет триггера по смыслу, только явный `/sync-library`.

**Общий вывод из трёх примеров.** Качество тела скилла (конкретность инструментов, путей, порогов) и качество триггер-слоя (фронтматтер с description) — два независимых измерения. Курс силён в первом и почти полностью пропустил второе: 12 из 13 скиллов написаны как хорошие рецепты, которые никогда не сработают сами по себе.

|---|---|---|---|---|
| Что это по сути | Знание/процедура, подгружаемая по требованию в ту же сессию | Механически исполняемое ограничение или реакция, харнесс запускает сам | Отдельный агент со своим изолированным контекстным окном и задачей | Доступ наружу — к внешнему API/сервису/данным |
