## Раздел B — P1 issues (обязательны к фиксу в plan-v2 до chapter)

### P1-1 — LO4 «apply» висит на единственном 2-мин слайде без рубрики успеха
**Где:** §3 (LO4 row: «s28 in-lecture apply»), §4 s28, §8 (retrieval table, s28 = 2 мин apply), §10 открытый вопрос #4.
**Issue:** LO4 = «Применить AI-инструменты для решения типовой аналитической задачи» (Bloom: Apply). В плане LO4 целиком держится на 2-минутном фрагменте s28, где класс применяет чек-лист к 2 задачам. Проблемы методические:
1. **Cognitive-load коллизия:** s28 одновременно несёт LO7-payoff (8-вопросный чек-лист — итог всей лекции), LO4-apply (2 задачи), И «человек-валидатор» (сквозная тема). Три разные когнитивные функции на одном слайде за 3 мин (из них 2 мин — сам apply) → ни одна не получит глубины. Это классический overload финального слайда (зеркалит проблему s28 Лекции 1, removed by user).
2. **Нет критерия успеха:** «применить чек-лист к 2 задачам» — но что считается *выполненным* apply? Нет рубрики «правильный выбор = X, типовая ошибка = Y». Без неё это не measurable Apply, а демонстрация (Understand под видом Apply).
3. **Сам план это признаёт** (§10 #4: «достаточно для apply или вынести отдельным слайдом?») — это не закрытый вопрос, а методический риск, который должен быть решён ДО chapter, иначе book-editor не сможет написать LO4-секцию с измеримым исходом.
**Recommendation:** в plan-v2 — закрыть открытый вопрос #4 явно. Минимум: (а) развести LO7-payoff и LO4-apply на 2 слайда-кадра ИЛИ дать s28 отдельный «решённый пример» (worked example: задача → проход по чек-листу → вывод) ПЕРЕД тем как класс применяет ко 2-й задаче (Mayer worked-example principle); (б) добавить explicit success-критерий LO4 в §3 («apply засчитан, если студент назвал архитектуру И ≥2 критерия из матрицы И ≥1 "когда НЕ"»); (в) явно делегировать основную нагрузку LO4 на Семинар 3 (план это упоминает, но не фиксирует как design-decision — а LO4 в canon привязан и к С3). Зафиксировать: «LO4 in-lecture = floor (worked + 1 mini-apply), mastery = Семинар 3».

### P1-3 — Strict-in расчёт §5: 3 из 15 заявленных слайдов — PARTIAL, не strict-in (см. детальный аудит, Раздел D)
**Где:** §5 (claim: s01,s07,s08,s12,s13,s14,s16,s17,s22,s23,s24,s25,s26,s27,s28 = 15/29 ≈ 52%).
**Issue:** По strict-in определению (решение #78: засчитывается только *полностью* in-bucket; partial → как out) три слайда — partial:
- **s01 (Air Canada hook)** — hook-кейс с провалом, но как hook его *функция* — провокация + ЦВ-постановка; «выученный урок + альтернатива» в нём ещё не развёрнуты (они приходят в s13 «Air Canada revisited»). Hook = partial (провал есть, урок/критерий — отложен). Strict-in считает это out.
- **s14 (миф "fine-tuning ушёл")** — это JUDGMENT-калибровка («не ушёл, сузился»), но это *уточнение области применения*, не провал/ограничение/критерий-НЕ/сравнение-с-альтернативой в strict смысле. Partial-upside, при подсчёте % → out.
- **s25 (лестница сложности)** — это framework-payoff (LO7), формулирует «подниматься только при необходимости» — судительный, но сам по себе не «провал+урок» и не «критерий НЕ применять X» в strict-in смысле (критерии «когда НЕ» живут в s27, s12, s17, s24). Partial → out.
**Перерасчёт strict-in:** твёрдо in-bucket = s07, s08, s12, s13, s16, s17, s22, s23, s24, s26, s27, s28 = **12/29 ≈ 41%**. Это **выше 30% порога** — DoD по слайдам проходит даже после строгой переклассификации. НО: план рапортует 52%, фактический strict-in ≈41%. Завышение на ~11 п.п. опасно тем, что при chapter/speech такая же «оптимистичная» классификация может уронить артефакт <30% незаметно.
**Recommendation:** в plan-v2 §5 — переписать расчёт честно: «strict-in slides = 12/29 ≈41% (s01/s14/s25 = partial-upside, НЕ засчитаны в порог per решение #78)». Это не ослабляет план (41% > 30% с запасом), но делает метрику честной для Phase 3/7/10 methodology-critic. Завышенный baseline = риск незамеченного провала DoD на downstream-артефактах.

### P1-4 — Holistic-распределение §5 заявлено, но не проверяемо: speech-доля строится на незабюджеченных кейсах #13/#14
**Где:** §5 («speech — нарратив #4 (hook), #1 ($4,200), #13/#14 (DPD/Chevrolet — speaker-level)»).
**Issue:** Правило (CLAUDE.md, решение #78) требует strict-in ≥30% **в каждом из 3 артефактов отдельно**. План декларирует это «перевыполняется по дизайну», но:
- Speech strict-in держится на #1 ($4,200), #4 (Air Canada), #13/#14 (DPD/Chevrolet). Кейсы **#13/#14 НЕ присутствуют ни на одном слайде и не в slide-list** — они вводятся только в speech как «speaker-level». Это значит speech-bucket частично опирается на контент, которого нет в chapter/slides source-of-truth. При book-first модели (chapter = PRIMARY) контент, живущий только в speech, — методический риск consistency (speech не должен вводить новый core-материал, которого нет в chapter; anti-pattern «Speech читает chapter» обратное тоже плохо — speech *добавляет* несинхронизированный материал).
- Нет per-artifact оценки %: §5 даёт только slide-расчёт (52%) и нарративный список для chapter/speech без долей. Для L3 (НЕТ waiver) это критично — Phase 3/7/10 будут мерить каждый артефакт; план должен дать book-editor/speech-writer явный per-artifact бюджет, иначе они не смогут таргетировать 30%.
**Recommendation:** в plan-v2 §5 — добавить таблицу «артефакт → strict-in блоки → ориентир %»: chapter (детальные кейсы #1/#4/#5/#11 + сводная таблица ограничений + критерии-НЕ → ориентир ≥35% слов), slides (12 strict-in → 41%), speech (нарратив #1/#4 + критерии «когда НЕ» по разделам → ориентир ≥30% минут). **#13/#14 для speech**: либо завести их хотя бы в chapter deep-dive box (тогда speech их легитимно нарративизирует), либо НЕ закладывать speech-bucket на них (заменить на #1/#4 + критерии-НЕ, которых в speech и так достаточно). Зафиксировать, что speech не вводит core-failure-материал, отсутствующий в chapter.
