### A.8. Механика — что субагент получает и что возвращает

Артефакт уже на слайде (§A.7): роль с урезанным списком инструментов. Здесь — не новый пример, а
точный список того, что стоит за словом «изоляция», которое до сих пор звучало обобщённо.

**Что приходит на вход — точно, не приблизительно.** Дословно из документации Claude Code (раздел
«What loads at startup»): роль получает (1) **свой системный промпт** — тело её собственного
файла — плюс служебные детали окружения вроде рабочей директории, но **не** системный промпт
Claude Code целиком: **"Subagents receive only this system prompt plus basic environment details
like the working directory, not the Claude Code system prompt."** (2) **task-сообщение** —
формулировку задачи, которую составил вызывающий агент, а не исходную реплику разработчика
буквально. (3) **иерархию `CLAUDE.md`** целиком, теми же уровнями, что видит основная сессия. (4)
**снимок `git status`**, зафиксированный в момент старта роли. (5) — только если явно перечислено
в поле `skills` файла роли — предзагруженные скиллы полным содержимым; без этого поля роль всё
равно может вызвать любой скилл инструментом `Skill` во время работы, просто не с первой секунды.

**Что физически не доходит.** Дословно: **"Each subagent starts with a fresh, isolated context
window. It doesn't see your conversation history, the skills you've already invoked, or the files
Claude has already read."** Ни переписки родителя, ни его стиля вывода, ни его автопамяти, ни уже
прочитанных им файлов — не потому что харнесс что-то скрывает, а потому что этого канала
физически нет.

**Одно исключение — форк, одной строкой.** Режим `fork` наследует всё целиком: тот же системный
промпт, тот же набор инструментов, всю историю сообщений. Изолируется в нём только результат —
собственные вызовы инструментов форка не попадают в основной контекст, а не то, что приходит на
вход. Наш `diff-reviewer` (§A.7) — не форк, поэтому всё сказанное выше применяется к нему без
исключений.

**Что возвращается обратно — тоже дословно.** **"The subagent works through its task
autonomously, then returns its result to the parent conversation. The parent doesn't see the
subagent's intermediate tool calls or outputs, only that final result."** Механически, не по
договорённости: сам протокол харнесса передаёт родителю статус, идентификатор роли, финальный
текст, модель и счётчики вызовов — но ни одного промежуточного вызова инструмента.

**Отсюда — та же самая механика на две стороны.** Выигрыш уже виден на `diff-reviewer` (§A.7 и
модельный разбор слайда 4.9 в §B основного файла): оценка не заражена рассуждениями автора
правки, потому что роль физически не получает их на вход. Издержка — обратная сторона того же
самого канала: роль не знает того, что знает вызывающая сессия — почему заказчик прислал именно
эту заявку, какие альтернативы уже отклонили, — и переспросить не может. Канал односторонний:
задача передаётся один раз, итог возвращается один раз.

### A.9. Механика — семантика прав, на самоизобличающем примере

Строка `tools: Read, Grep, Glob` в файле роли (§A.7) уже сработала один раз буквально, не
абстрактно: именно её отсутствие в более ранней версии того же файла позволило роли не найти
проблему, а самой её исправить (§A.2). Разберём, что стоит за этой строкой механически.

**Опущено — не значит «без инструментов».** Дословно: **"Inherits every tool available to
subagents if omitted."** Полная матрица:

| `tools` | `disallowedTools` | Результат |
|---|---|---|
| не задано | не задано | роль наследует **весь** пул, доступный субагентам |
| задано | не задано | только перечисленные |
| не задано | задано | весь пул минус перечисленные |
| задано | задано | `disallowedTools` применяется первым, `tools` резолвится против остатка; инструмент в обоих списках снимается |

Отнять доступ полностью можно двумя способами — явным `disallowedTools`, перечисляющим всё, или
буквально пустым списком `tools: []`, — оба не вызывают ошибку, роль просто стартует без единого
инструмента. Другое дело — неразрешимое имя в непустом списке: харнесс не запускает роль вовсе и
называет конкретную опечатку, дословно: **"Agent 'code-reviewer' would be spawned with zero
tools — refusing. Its tools list resolved to nothing: unrecognized [Grpe]."**

**Проверено мной напрямую, на материале самого курса.** В каталоге `.claude/agents/` этого
репозитория — **13 файлов ролей, и ни один не задаёт поле `tools:`**:

```
$ ls .claude/agents/*.md | wc -l
13
$ grep -L "^tools:" .claude/agents/*.md | wc -l
13
```

По только что показанной семантике это означает: все тринадцать ролей курса — включая
`methodology-critic`, `fact-checker`, `presentation-critic`, `consistency-checker`, чья работа
целиком состоит в том, чтобы **оценивать** материал, — технически имеют право писать и править
файлы, которые пришли критиковать. Держится это исключительно на тексте инструкции внутри самого
файла — той же силы просьбы, что уже разбиралась как недостаточная на прошлом занятии (раздел про
хук). Строка `tools: Read, Grep, Glob` у нашего собственного `diff-reviewer` (§A.7) — ровно тот
шаг, которого курс сам себе не сделал ни разу за тринадцать файлов.

**Ещё одна деталь того же механизма — глубина отнятия.** Строка `tools:` работает на уровне
**типа** инструмента целиком: `diff-reviewer` физически не может вызвать `Write`, потому что
этого инструмента у него просто нет. Более тонкая настройка — «читать можно всё, кроме каталога
`secrets/`» — этим механизмом не выражается: она уже не про список инструментов, а про то, что
происходит внутри разрешённого. Задокументированный разрыв (issue `#54898`): система прав в
харнессе работает на уровне сессии, а не на уровне отдельного субагента. Автор issue закрыл его
сам, опубликовав собственный обходной хук, а не дождавшись исправления от мейнтейнеров;
независимые комментарии позже (19.05, 25.06.2026, от других пользователей) подтверждают разрыв
как нерешённый на уровне продукта. Отнятие прав в этом разделе работает ровно на той грубости, на
которой оно измерено — список типов инструментов, не действия внутри разрешённого.

### A.10. Механика — как отлаживается

Четыре сигнала, каждый — ответ на конкретный вопрос инженера, не абстрактная инвентаризация
средств.

**«Позвали вообще ту роль?»** В переписке делегирование показано строкой вида `<имя>(<задача>)` —
дословно из quickstart: **"the delegation appears as a tool call row showing the subagent's name
followed by a short task description, such as `code-reviewer(Suggest code improvements)`."** Если
в этой строке видно `general-purpose` там, где ожидался `diff-reviewer`, — маршрутизация не
связала задачу с `description` роли (тот же принцип, что уже прозвучал в разделе про скилл: узкое
и конкретное описание маршрутизирует, расплывчатое — нет), или роль того же имени на более
приоритетном уровне настроек незаметно перекрыла нужный файл проекта. Явный вызов
`@agent-diff-reviewer` снимает вопрос полностью — роль запускается принудительно, без решения
модели.

**«Роль вообще увидена харнессом?»** `/context` показывает секцию пользовательских субагентов с
указанием, с какого уровня каждая загрузилась (проект, пользователь, плагин) — с этого стоит
начинать, до попытки вызвать роль вслепую.

**«Какие инструменты у неё реально есть?»** Не только текст файла. Субагенты в фоновом режиме (по
умолчанию!) получают суженный встроенный набор инструментов независимо от того, что написано в
`tools:`. Роль, проверенная автором на переднем плане, может незаметно потерять инструмент именно
в штатном фоновом режиме — проверять нужно то поведение, в котором роль реально будет работать, а
не то, в котором её удобно тестировать.

**Поправленный тезис про хуки — тот же вопрос, что уже звучал на прошлом занятии, теперь без
человека вообще, внутри субагента.** Там разбиралось: хук защиты ветки не видит человека,
набравшего команду в отдельном терминале, — потому что `PreToolUse` реагирует на вызов
инструмента **агентом**, а не на действие вообще. Действующая документация утверждает
противоположное тому, что стояло в этом разделе раньше: хуки уровня `settings.json` **срабатывают
и на вызовы инструментов внутри субагента** — дословно, `hooks.md`: **"Hooks from settings files,
managed policy settings, and plugins also run inside subagents. When a subagent calls a tool, tool
events such as `PreToolUse` and `PostToolUse` fire the same configured hooks as in the main
conversation, and the input carries the `agent_id` and `agent_type` common input fields that
identify the subagent."** Именно эти два поля появляются в нагрузке, чтобы отличить вызов
субагента от вызова основной сессии — иначе они были бы не нужны. Автор комментария, на котором
раньше держалось противоположное утверждение (issue `#34692`), сам его отозвал 26.08.2026,
дословно: *«I finally measured it, and my comment was wrong… The hook fired in the subagent, and
`deny` held there — same as top level»* — с воспроизводимым тестом.

Но «срабатывает» здесь не равно «принуждает» — и это тоньше исходного утверждения, а не слабее
его. Два независимых, до сих пор не разрешённых сообщения о том, что хук внутри субагента вынес
корректное решение `deny` — а команда всё равно выполнилась: один случай — блокирующее решение
было принято правильно для опасных команд, вызванных субагентом, но команды реально выполнились
(автор нашёл это уже после настоящего инцидента с потерей данных); второй — блокировка сработала
для основной сессии и для одного тестового субагента в той же сессии, но не сработала для
другого, с тем же файлом настроек, притом воспроизвести это детерминированно не удалось. Тот же
вывод, что уже звучал на прошлом занятии, ещё раз, без единого исключения: **сработавший барьер —
не значит барьер, который устоял.**
