# Разметка кейсов Лекции 13 по трём осям применимости ИИ

Эмпирическая проверка гипотезы трёх осей (`00-rezyume.md`, `01-05`) на реальных,
задокументированных в курсе кейсах. Источник — `library/lectures/lec-13/slides/s01-s41.md`
(первичный, прочитаны все 41 слайд), сверка по `chapter.md` + `chapter-part2.md` +
`chapter-part3.md` (grep по всем именованным компаниям — совпадает со слайдами, новых кейсов с
метриками не найдено; найдены только непроанализированные упоминания в списках — см. раздел
«Трудные случаи»). Кандидаты из `notes/research/lecture-13/02-*` и `03-*` не добавляли новых
именованных кейсов сверх уже отрендеренных в slides.

## Трудные случаи

Отдельно — кейсы, которые **не укладываются чисто** в заданную 3-осевую схему, и почему это
важно для честности разметки (не прятать «неудобные» строки):

- **UPS ORION.** Центральный anti-hype слайд лекции — **намеренно НЕ-ИИ кейс**, используемый,
  чтобы показать, где классика (OR) выигрывает у ML. Формально это не «кейс применимости ИИ» —
  это кейс *не*применимости, причём успешный. Критически важен для проверки confirmation bias:
  если считать только «ИИ-кейсы», этот самый методически богатый и самый измеримо успешный кейс
  всей лекции выпадает из выборки.
- **Suez Ever Given.** Единственный кейс, где сам источник прямо говорит: «AI не имела роли».
  Весь кейс — вне домена трёх осей (не статистическая задача вообще). Самый чистый пример
  «неприменимо», не «провалилось».
- **«AV решит дефицит водителей».** Не техническая задача ИИ вообще — ложный фрейминг
  (category error уровня абстракции). Оси неопределённости/фидбека/сложности модели ничего не
  объясняют в этом провале — это чисто арифметический и экономико-политический разбор.
- **Порт + ILA-страйки.** Провал адопции объясняется **labor policy**, не неопределённостью
  задачи — ни один из U1-U4 механизмов не покрывает «профсоюз заблокировал расширение
  автоматизации».
- **KONUX.** «Pilot purgatory» — ограничивающий фактор бюрократическая инерция госзаказчика, не
  техническая неопределённость. Плюс цифры интервалов обслуживания — заявка вендора, не
  независимо верифицированная.
- **Amazon Sequoia** (упомянута внутри кейса Amazon Robotics, s08) — слайд сам прямо говорит:
  «Sequoia не AI в строгом смысле — mechatronics + WMS-логика». Присутствует в нарративе
  «AI на складе», но формально не AI-кейс вообще — определительная граница, не ошибка курса, но
  повод не засчитывать её отдельной строкой как AI-успех.
- **Zoox / Locomation / Plus.ai.** Слишком тонко задокументированы (одна строка упоминания без
  метрик) для уверенной разметки по любой из трёх осей — включены в таблицу по требованию
  полноты, но помечены low confidence по всем параметрам.
- **WeRide.** Лекция цитирует «+761% YoY» без абсолютной базы сопоставления — именно та
  «missing denominator»-проблема, которую собственное правило курса (Baseline/Counterfactual
  Mandate) требует флагать как P1 у вендоров. Здесь она встроена в материал лекции без оговорки.
- **КамАЗ-54901 / Cognitive Pilot / Cognitive Pilot Agro.** Разительная асимметрия источников:
  для американских/китайских кейсов — NHTSA-уровня детальная статистика инцидентов; для
  российских — только масштаб флота/объёма, без единой цифры по безопасности или disengagement.
  Это может отражать реальные различия в режимах регуляторной прозрачности, а не различия
  в фактическом качестве ИИ — риск систематической ошибки при межкейсовом сравнении.
- **Tesla Autopilot — algorithm over-reliance.** Схема называет **U4 algorithm aversion**
  (недоверие к алгоритму). Здесь задокументирован направленно **обратный** эффект — избыточное
  доверие, спровоцированное самим наименованием продукта («Autopilot»/«Full Self-Driving»). Это
  не опровергает U4, но показывает, что человеческое (не)доверие к алгоритмам — двунаправленный
  механизм, и схема в её текущей формулировке называет только одно направление.
- **Cruise GM exit.** Задержка истинного последствия инцидента была вызвана **намеренным
  сокрытием** от регулятора, а не технической латентностью фидбека — ни F-A, ни F-B, ни F-C не
  описывают «организация намеренно задержала раскрытие последствия», это отдельный,
  неучтённый в схеме механизм (governance/integrity-induced delay).

## Предварительное наблюдение

Гипотеза находит реальную опору в самых чистых кейсах лекции: экстремальная неопределённость с
полным дистрибуционным сдвигом (Хуситы, COVID) совпадает с документированным провалом именно ML
demand forecasting при явно рабочем человеческом+OR фидбек-контуре — и это эмпирически разводит
две оси (быстрый, целый фидбек-контур не спас ML-компонент именно потому, что проблема была в
Оси 1, не в Оси 2, подтверждая предостережение `02-os-fidbeka.md` против их слития). Низкая
неопределённость в контролируемой среде (склад, порт, рельсы, UPS ORION) действительно совпадает
с успехом — но в двух из самых сильных случаев (UPS ORION, порт/рельсы) выигрывающий инструмент —
классическая математика или чистая автоматизация, а не ИИ, что скорее подтверждает нижнюю
половину оси неопределённости в версии «здесь работает классика», а не прямо версию «здесь
работает ИИ». При этом **большая часть самых подробных и дорогостоящих провальных кейсов лекции
(Argo, Embark, Cruise, TuSimple, Starsky, ILA-страйки)** объясняется не столько неопределённостью
задачи как таковой, сколько **капитал-таймингом, трудовой/регуляторной политикой и организационным
доверием** — факторами, которые три заданные оси не покрывают напрямую. Suez Ever Given — чистый
контрпример самому домену рамки (ИИ здесь попросту неприменим, а не «не справился»), а дело
«AV решит дефицит водителей» показывает ложный фрейминг problem-уровня, который тоже лежит вне
трёх осей. Итог: оси хорошо объясняют *техническую* сторону применимости там, где неопределённость
действительно является узким местом (перцептивные edge-cases — Uber Tempe, Tesla Autopilot;
