# Архитектура: бинарные данные как отдельный контракт

## Assertion

У файла есть размер и формат, и оба проверяются перед отправкой явным условием в цепочке — не доверием к тому, что следующий узел справится сам.

## Visual

> **Бинарные данные — отдельная модель данных от текстовых значений.** У файла есть размер и есть формат, и оба должны быть проверены перед отправкой, явным условием в цепочке.

> **Тот же контракт, что рвался на тексте, здесь рвётся на формате и размере.** В кейсе «Уведомления» узел не падал, а результат тихо оказывался не тем. Здесь узел тоже не падает — рвётся соответствие между тем, что отправлено, и тем, что дошло, по той же причине: формально успешный прогон ничего не говорит о том, дошёл ли результат до получателя в ожидаемом виде.

> **Правило.** Прежде чем файл уходит дальше по цепочке, его размер и формат сверяются явным условием — не предполагаются заранее и не проверяются постфактум по ответу API.

## Speaker notes

Первый слой решения — архитектурный, без привязки к n8n или Telegram, и он звучит так же, как решение в «Уведомлениях», только применённое к другому типу данных.

Бинарные данные — это отдельная модель данных, не просто ещё одно значение поля рядом с текстовыми. У обычного текстового поля есть содержимое, и всё. У файла — есть содержимое, есть размер, и есть формат, и оба этих свойства должны быть проверены прежде, чем файл уйдёт дальше по цепочке.

Контракт между шагами, который мы уже видели рвущимся в кейсе «Уведомления» — узел не упал, результат тихо не тот, — здесь рвётся на формате и размере, а не на смысле текста, но по той же самой причине: формально успешный прогон ничего не говорит о том, дошёл ли результат до получателя в ожидаемом виде. Узел отправки получает от API положительный ответ не потому, что получатель увидел результат, а потому, что API принял запрос.

Отсюда правило. Прежде чем файл уходит дальше по цепочке — к следующему узлу или наружу, в Telegram, — его размер и формат сверяются явным условием внутри самой цепочки. Не предполагаются заранее, потому что на тестовых данных всё помещалось. Не проверяются постфактум по ответу API, потому что ответ API говорит про сам вызов, а не про то, что увидел человек на другом конце. Проверяются именно там, где файл ещё внутри цепочки и у нас есть шанс остановить его или обработать иначе, прежде чем отправка состоится.

Это и отличает архитектурное решение от любой из четырёх карточек вопроса. Карточки предлагали переложить ответственность на платформу, на статус прогона или на получателя — то есть куда-то за пределы точки, где мы ещё могли бы что-то изменить. Правильное место для проверки — ровно здесь, внутри нашей собственной цепочки, до того как файл её покинул.
