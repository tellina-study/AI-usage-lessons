# spec.md — требования до первой сессии

## Assertion

Требования раскладываются на функциональные и нефункциональные и ложатся в `spec.md` первым коммитом; README описывает устройство репозитория и заводится тем же коммитом.

## Visual

```markdown
# spec.md — signup-landing

## Функциональные требования
- Статическая страница-лендинг, форма заявки на демо-урок
- Поля: имя (обязательное), email (обязательное)
- Кнопка отправки; без бэкенда — заявка уходит на внешний сервис приёма форм

## Нефункциональные требования
- Критерий приёмки: форма реально доставляет заявку — проверено на проде,
  а не только «тест зелёный»
- Граница действий: не деплоить на прод без явного запроса
- Доступность: форма управляется с клавиатуры, у полей есть подписи
```

Подпись под файлом: «иллюстративный пример, не захваченный артефакт».

Ниже — строка про второй артефакт того же коммита:

> «`README.md` заводится сразу, отдельно от спеки. Спека — требования к продукту. README — устройство репозитория для того, кто в него зайдёт: человек или агент.»

## Speaker notes

«Первые десять минут работы над проектом уходят не на код. Формулировку заказчика раскладываем на функциональные требования — что должно быть, — и нефункциональные — какими свойствами это должно обладать, — и кладём в `spec.md` первым коммитом.

Отдельно стоит посмотреть на строку «критерий приёмки». Заказчик её не произносил, она выведена нами: без неё «готово» ничем не отличается от «тест зелёный», а это разные утверждения о системе.

Тем же коммитом заводится `README.md`. Спека отвечает на вопрос, что должно получиться; README — на вопрос, как устроен репозиторий. Разделение практическое: два разных читателя, два разных срока жизни. Требования меняются по договорённости с заказчиком, устройство репозитория — по мере рефакторингов.

Теперь задача агенту формулируется иначе: не «собери лендинг с формой», а «вот `spec.md`, инициализируй репозиторий и собери проект по нему».»
