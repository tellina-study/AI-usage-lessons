## 1. Механика серверного правила — чем принципиально отличается от локального хука

### 1.1. Кто исполняет и почему клиент не может обойти, даже имея права на запись

Локальный хук — это код, который **харнесс Claude Code сам вызывает** на событии `PreToolUse`,
внутри процесса, которым управляет тот же клиент, что пытается сделать коммит. У любого достаточно
настойчивого клиента есть способ не дать этому коду увидеть команду — самотест демонстрирует четыре
таких способа буквально одной строкой каждый (`-C`, абсолютный путь, префиксная команда, вторая
строка многострочного вызова), и все четыре работают потому, что хук читает **текст команды**,
которую клиент решил напечатать, а не действие, которое команда произвела.

Правило защиты ветки на GitHub исполняется не на машине клиента и не в процессе Claude Code вовсе.
Дословно из официальной документации («About protected branches», обращение 2026-09-28): «you can
enforce certain workflows or requirements before a collaborator can push changes to a branch in
your repository, including merging a pull request into the branch, by creating a branch protection
rule». Решение принимает сервер GitHub в момент, когда изменение реально пытается попасть на
защищённый `ref`, — независимо от того, каким git-клиентом, из какой рабочей директории, с какого
алиаса или в какой позиции многострочного скрипта был сделан локальный коммит. **Сервер видит не
команду, а результат**: попытку обновить конкретный `ref` конкретным набором коммитов. У четырёх из
пяти `LIMIT`-случаев самотеста в принципе нет объекта для срабатывания на этом уровне — не потому,
что правило умнее регулярного выражения хука, а потому, что оно физически не читает то же самое,
что читает хук, и поэтому не может быть обойдено тем же классом трюка.

Это ключевое отличие стоит формулировать студентам не как «сервер надёжнее», а точнее: **хук —
это надзиратель внутри той же комнаты, где работает клиент, а серверное правило — это дверь,
которая физически не открывается, кем бы её ни толкали**. Разница не в силе воли надзирателя, а в
том, что дверь не читает намерение — она проверяет пропуск в момент прохода.

### 1.2. Что реально можно требовать перед слиянием — источник на каждый пункт

GitHub предлагает два механизма с одинаковой сутью и разной гибкостью: классическое branch
protection rule (одно правило на branch-паттерн, дословно: «Only a single branch protection rule
can apply at a time») и **rulesets** — более новый слой, где на одну ветку одновременно
накладываются несколько правил и «if the same rule is defined in different ways across the
aggregated rulesets, the most restrictive version of the rule applies» («About rulesets»,
2026-09-28). На новых репозиториях GitHub рекомендует rulesets; у демо-репозитория курса на
сегодня (проверено `gh api repos/tellina-study/signup-landing-demo/rulesets` — **2026-09-28**,
результат `[]`) ни того, ни другого не настроено — ни на одной из пяти веток, включая `main`
(`gh api .../branches/main/protection` → `"Branch not protected"`). Это важно проговорить в занятии
прямо: раздел разбирает механику продукта, а не факт того, что она уже включена на курсовом
репозитории.

Реально доступный набор требований («Available rules for rulesets» + «About protected branches»,
обращение 2026-09-28), по источнику:

| Требование | Что именно закрывает | Источник |
|---|---|---|
| **Require status checks to pass before merging** | Слияние блокируется, пока не отработают все указанные проверки (или ветка не станет заново «up to date», если включён строгий режим) | GitHub Docs, «About protected branches» §Require status checks |
| **Require a pull request before merging + N approving reviews** | Прямой push в ветку запрещён — изменение обязано пройти через PR; PR обязан получить N одобрений от людей с правом записи (или конкретно от code owner) | GitHub Docs, «Available rules for rulesets» §Require a pull request before merging |
| **Require review from Code Owners** | Любой файл с назначенным владельцем обязан получить его одобрение отдельно от общего счётчика ревью | Там же |
| **Dismiss stale pull request approvals when new commits are pushed** | Одобрение аннулируется, если после него в PR попал новый коммит — по умолчанию **выключено** | Там же (см. §1.4 — почему выключенность по умолчанию важна) |
| **Require approval of the most recent reviewable push** | Требует, чтобы последний реально попавший в PR пуш одобрил кто-то, кроме автора этого пуша — компромисс, не требующий сброса всех прежних ревью | Там же |
| **Require an additional approval for unattributed Copilot PR** | Если PR открыт Copilot от собственного имени (не от имени человека), требуется на одно одобрение больше — включено по умолчанию для новых и существующих rulesets, в публичном превью | Там же — прямая, свежая (2026 год) реакция площадки на PR, авторство которых не привязано к человеку |
| **Require conversation resolution before merging** | Слияние блокируется, пока не закрыт (resolved) каждый открытый комментарий к PR | GitHub Docs, «About protected branches» |
| **Require signed commits** | Непроверенные (неподписанные) коммиты не проходят через тестовый merge-commit, которым GitHub оценивает мержабельность PR | Там же |
| **Require linear history** | Запрещает merge-коммиты — слияние обязано быть squash или rebase | Там же |
| **Require merge queue** | Каждый PR перепроверяется против актуальной головы ветки и очереди перед PR — без ручного «update branch» | Там же |
| **Require deployments to succeed before merging** | Слияние блокируется, если изменение не задеплоилось успешно в указанное окружение (например, staging) | Там же |
| **Block force pushes / Restrict deletions** | Перезапись истории и удаление ветки запрещены по умолчанию | GitHub Docs, «Available rules for rulesets» — «This rule is selected by default» |
| **Require secret scanning alerts are resolved / Require code scanning results** | Слияние блокируется, если найден нерешённый секрет или алерт сканирования кода нужной серьёзности — обе фичи в публичном превью на 2026-09-28 | Там же |

Все строки — из одного источника, обращение датировано; отдельно ни одна не выдумана и не
досочинена по памяти.

### 1.3. Ядро блока — пять случаев самотеста, закрыты по одному

| # | `LIMIT`-случай самотеста (дословно из капчура) | Закрывается серверным правилом? | Почему именно так |
|---|---|---|---|
| 1 | `git -C <path> commit` on main — ALLOWED: regex matches only 'git' and 'commit' as adjacent words | **Полностью** | Сервер видит не текст локальной команды, а итоговую попытку обновить `refs/heads/main`. Флаг `-C` меняет рабочую директорию клиента до вызова `git`; на то, какой `ref` получит push, он не влияет никак — у сервера просто нет входа, который мог бы прочитать этот флаг |
| 2 | `/usr/bin/git commit` on main — ALLOWED: an absolute path is not the literal word 'git' | **Полностью** | Та же причина: сервер получает git-протокол (pack/refs), а не путь к бинарнику на диске клиента. Абсолютный путь физически не долетает до сервера как информация |
| 3 | `env git commit` on main — ALLOWED: any prefix command hides the commit from the regex | **Полностью** | Та же причина: `env` — тоже деталь клиентского вызова, стёртая до того, как что-либо покидает машину клиента |
| 4 | `git commit` on the SECOND line of a multi-line command — ALLOWED: the hook reads only the first line | **Полностью** | Сервер реагирует на финальный push, а не на порядок строк в локальном Bash-вызове; многострочность команды — тоже клиентская деталь, которая не переживает дорогу до сервера |
| 5 | default branch named 'trunk' — ALLOWED, neither denied nor asked («If your project's default branch is not main/master, add its name to the branch comparison … otherwise this gate protects nothing here») | **Частично** | Первые четыре обхода для серверного правила не существуют по конструкции — оно не читает синтаксис команды вообще. Но правило само нужно **нацелить** на реальное имя ветки (`fnmatch`-паттерн в rulesets или конкретное имя в branch protection): если админ повторит ту же ошибку конфигурации на сервере (правило написано на `main`, а default branch на самом деле `trunk`), защиты не будет и там — тот же класс промаха, просто перенесённый выше. Разница не в устойчивости к этой конкретной ошибке, а в том, что конфигурация теперь **одна, в одном месте**, видимая «anyone with read access to a repository» (GitHub Docs, «About rulesets»), а не N локальных хуков в N клонах, каждый из которых можно забыть завести |

Строка 5 — не смягчение тезиса, а честная граница: серверное правило категорически сильнее против
четырёх форм обхода команды (закрывает класс, а не конкретные четыре формы — пятая форма того же
трюка тоже не сработает), но не спасает от единственной оставшейся ошибки — неправильно названной
цели правила, потому что это уже не вопрос обхода, а вопрос конфигурации, и конфигурировать нужно
что-то в любом случае, хук или сервер.

**Два случая из вводной части, не входящие в таблицу самотеста, но той же природы.** Хук не видит
человека, вводящего команды мимо инструментов агента, — потому что `PreToolUse` привязан к вызову
инструмента `Bash` внутри Claude Code, а не к оболочке вообще; человек, открывший терминал рядом и
напечатавший `git commit` руками, для этого хука не существует. Серверное правило закрывает это
**полностью**, потому что оно реагирует на попытку обновить `ref`, а не на то, кто её инициировал —
человек за клавиатурой, агент через Bash-инструмент, другой хост, веб-редактор GitHub. Второй
случай — хук, превысивший тайм-аут (в самотесте — 10 секунд), не блокирует вызов вовсе, «отказывает
открыто» в противоположную сторону: тайм-аут делает хук **прозрачным**, а не строгим. У CI-проверки
на GitHub эквивалент устроен ровно наоборот: у джобы на GitHub-hosted runner лимит выполнения — «6
hours. Each job in a workflow can run for up to 6 hours of execution time. **If a job reaches this
limit, the job is terminated and fails**» (GitHub Docs, «Reference: limits for GitHub Actions»,
2026-09-28). Провал по тайм-ауту — это `failure`, а `failure` не входит в список статусов, которые
разрешают слияние (§2.2); значит зависшая обязательная проверка **держит ветку закрытой дольше**,
а не открывает её по умолчанию. Прямая противоположность локальному хуку — и стоит показать этот
контраст на слайде рядом с таблицей, а не только саму таблицу.

### 1.4. Обход и границы — что действительно не закрывается

Серверное правило устраняет класс обхода «клиент подделал форму команды», но у него свои,
задокументированные дыры, и все они — на стороне **прав**, не синтаксиса.

**Администратор обходит по умолчанию.** Дословно: «By default, the restrictions of a branch
protection rule don't apply to people with admin permissions to the repository or custom roles with
the "bypass branch protections" permission». Это не гипотетика для курса — реальный аккаунт,
которым ведётся демо-репозиторий, имеет `"admin":true` (проверено `gh api
repos/tellina-study/signup-landing-demo --jq '.permissions'`, **2026-09-28**), то есть по умолчанию
именно этот аккаунт мог бы обойти любое правило, которое сам же настроил, если явно не включить
чекбокс «Do not allow bypassing the above settings». Тезис для слайда: правило, которое можно
обойти его же автору без единого клика мимо интерфейса, не «сломано» — оно **сконфигурировано
так по умолчанию**, и включение более строгого режима — отдельное, недокументированное молчаливо
действие.

**Владелец репозитория/организации отключает правило целиком** — ruleset можно поставить в статус
`Disabled` без удаления («Using ruleset enforcement statuses»), и это не требует прав выше, чем
нужны для его создания.

**Требование ревью можно обойти без формального bypass — через таймингу отзыва одобрения.**
Дословно, ключевая деталь: «Optionally, you can choose to dismiss stale pull request approvals when
commits are pushed that affect the diff» — слово «Optionally» означает, что **по умолчанию
одобрение не сбрасывается**, когда после ревью в PR попадает новый коммит. Если этот чекбокс не
включён отдельно, PR, одобренный один раз, может уйти в слияние с содержимым, которое реальный
ревьюер не видел, — формально требование «есть N одобрений» выполнено, содержательно — нет.

**Обязательная проверка тоже не гарантирует, что она реально проверяла.** Забегая на мостик к §2:
дословно, «Required status checks must have a **successful, skipped, or neutral** status before
collaborators can make changes to a protected branch» — `skipped` в этом списке равносилен
`success` (разбор — §2.2). Это не обход, доступный клиенту в духе пяти `LIMIT`-случаев, — это
свойство самого правила, задокументированное открыто, а не найденное как эксплойт.

**Что серверное правило не видит в принципе — граница, а не дыра для латания.** Оно не оценивает
содержательное качество правки: `Require status checks to pass` требует, чтобы проверка вернула
нужный статус, а не то, что проверка была написана правильно; `Require review` требует одобрения от
человека с правом записи, а не то, что этот человек прочитал diff вдумчиво. И граница движется в
обе стороны прямо в 2026 году: с 1 сентября 2026 GitHub позволяет включить, что «Copilot can submit
an approval that counts toward the repository's required-approvals rule» («Copilot code review can
now approve pull requests», GitHub Changelog, **2026-09-01**) — то есть формальное требование
«получено N одобрений от людей с правом записи» может быть закрыто одобрением от **того же класса
агента**, который написал код, если организация явно включит эту настройку (по умолчанию —
выключено, и GitHub сам оговаривает: «An approval assessment alone does not count toward merge
requirements. Copilot's determination is surfaced so you can decide how to act on it»). Механизм
барьера — серверный и неснимаемый клиентом; но то, чьё судебное решение он засчитывает как
«ревью», — вопрос конфигурации, не физики протокола, и его можно настроить так, что барьер снова
проверяет форму, а не содержание.

## 2. Механика проверки в CI — «исполняется, а не заполняется»

### 2.1. Как проверка становится обязательной

Проверка в CI сама по себе — просто внешний процесс, который в конце публикует один из статусов
(«Types of status checks on GitHub»: **checks** — от GitHub Apps, включая GitHub Actions, с
детальным выводом; **commit statuses** — от внешних интеграций, попроще). Ни одна проверка не
обязательна сама по себе — обязательность возникает не из того, что проверка существует, а из того,
что её **имя** внесено в список «Require status checks to pass before merging» того же самого
серверного правила из §1. Именно в этой точке процессная проверка (текст в файле задачи, который
модель может забыть открыть) и CI-проверка (запись в правиле, привязанная к job-имени) расходятся:
без явной привязки к правилу job может падать сколько угодно раз — это никак не помешает слиянию;
как только имя job вписано в правило, тот же самый merge-button структурно не нажимается без
успешного (или, как показано в §2.2, «skipped»/«neutral») статуса именно этого имени. Курсовая
`.tasks/`-конвенция (`mechanics-7-protsess.md` §3) переносит ровно эту же логику в текст, который
харнесс не проверяет вовсе; CI-проверка, вписанная как required, переносит её в точку, которую
харнесс сервера сам вызывает при попытке слияния, — тот же переход «правило в промпте → правило в
коде», но теперь на уровне хостинга, а не продукта.

### 2.2. Что можно проверить механически из того, что раньше держалось на тексте

`mechanics-7-protsess.md` §3.4 уже разбирает живой пример: реальный файл задачи демо-репозитория
после находки независимого ROAST (три SHA, оставшиеся от версии до `rebase` и не существующие для
читателя) получил проверочную команду `git merge-base --is-ancestor <sha> <ref>`, вписанную в файл
вручную, запускаемую человеком или моделью по своей инициативе. Это тот же класс проверки, который
можно поднять на уровень CI буквально: тот же `git merge-base --is-ancestor`, тот же `grep` на
формат даты и наличие строки «Сверено», тот же счётчик `N passed` — всё это уже отмечено в §4.2
той же ступени как «механически проверяется» (существование, формат, ссылочная целостность SHA).
Единственное структурное изменение при переносе в CI — эта команда перестаёт быть чем-то, что
**можно** запустить, и становится тем, что **обязательно** запускается сервером перед каждой
попыткой слияния, вне зависимости от того, вспомнил ли автор правки её запустить локально.

Три конкретных класса утверждений, которые CI умеет закрыть механически из того, что раньше
держалось только на тексте отчёта:

- **Существование артефакта** — `test -f .tasks/done/<файл>.md` как отдельный шаг workflow, а не
  проверка глазами перед слиянием.
- **Свежесть даты** — тот же `date -u` из «Сверено», сверенный с текущим временем прогона джобы,
  а не с памятью автора PR.
- **Достижимость упомянутого SHA** — `git merge-base --is-ancestor $sha $ref` внутри workflow,
  запускаемая на **актуальном чекауте PR-ветки**, а не на локальной копии, которая могла
  устареть или быть переписана `rebase` без уведомления.
- **Формат вердикта** — `grep -qE '^(APPROVE|REVISE|BLOCK)\b' <файл>` как проверка того, что
  вердикт написан в ожидаемой форме, — не то, что вердикт правдив (это не механизируется, §3), но
  то, что он существует в парсимом виде.

Требуемый статус этой проверки — не только `success`. Дословно из «Status checks» (обращение
2026-09-28): «Required status checks must have a successful, skipped, or neutral status before
collaborators can make changes to a protected branch», и отдельно, курсивом-примечанием той же
страницы: «**A job that is skipped will report its status as "Success". It will not prevent a pull
request from merging, even if it is a required check.**» Это ровно тот структурный разрыв, который
раздел обязан показать честно, а не спрятать за общим «CI строже хука»: если workflow-условие
(`if:`, path-фильтр, `needs:` на джобу, которая сама была пропущена) привело к тому, что required
job **не выполнилась вовсе**, сервер трактует это не как отсутствие проверки, а как её успешное
прохождение. Проверка, вписанная как обязательная, перестаёт быть проверкой в момент, когда условие
запуска перестаёт совпадать с тем, что автор правила имел в виду, — и делает это молча, без
единого сигнала в интерфейсе PR, отличного от зелёной галочки любой другой прошедшей проверки. Это
прямой механический аналог провала хука по тайм-ауту (§1.3) — только на CI-уровне и с
противоположным по духу, но тем же по сути эффектом: «форма пройдена, содержания не было».

### 2.3. Цена

**Задержка обратной связи.** Локальный хук из ступени 3 отрабатывает за миллисекунды внутри
`PreToolUse` — до того, как коммит вообще создан. CI-джоба на GitHub-hosted runner тратит минуты:
время очереди раннера плюс время самого прогона (лимит джобы — 6 часов, «Reference: limits for
GitHub Actions», обращение 2026-09-28); типичная лёгкая проверка (лint, юнит-тесты) — от десятков
секунд до нескольких минут, тяжёлая (сборка, e2e) — десятки минут. Разница с хуком — не «немного
медленнее», а на порядки: секунды локально против минут на сервере, и об этом стоит говорить прямо
эту цифрой, а не общей фразой «CI медленнее».

**Чужая инфраструктура.** Решение о том, прошла ли проверка, принимает не машина автора правки и не
процесс Claude Code, а раннер, которым управляет GitHub (или self-hosted раннер, которым управляет
кто-то ещё). Это устраняет класс клиентских обходов (§1.1), но добавляет зависимость: если раннеры
GitHub недоступны или очередь перегружена, слияние блокируется не из-за качества правки, а из-за
чужой инфраструктуры.

**Стоимость прогонов — не абстрактная, а конкретная по тарифу.** «The use of standard GitHub-hosted
runners is free... In public repositories» (GitHub Docs, «GitHub Actions billing», обращение
2026-09-28) — то есть для публичного демо-репозитория курса CI бесплатен полностью. Для собственного
приватного репозитория студента бесплатная квота ограничена: **2 000 минут в месяц на плане GitHub
Free**, а сверх квоты — по тарифу, например **$0.006 за минуту** для стандартного двухъядерного
Linux-раннера (GitHub Docs, «GitHub Actions billing», таблица «Baseline minute costs»,
2026-09-28). Локальный хук — всегда бесплатен, потому что исполняется на уже оплаченной машине
разработчика; required-CI-проверка на приватном репозитории — это отдельная, растущая со временем
статья расхода, которую нужно прямо назвать студентам, у которых учебные и рабочие репозитории по
умолчанию приватные.

**Хрупкость.** Проверка зависит от версий сторонних действий (`uses: some/action@v1`), от кэшей, от
сетевых зависимостей — каждое из этих звеньев само может быть скомпрометировано или отказать не по
вине автора правки (разбор реального инцидента такого рода — §4).

### 2.4. Где CI хуже локального хука и где лучше — обеими сторонами

**Хуже:** задержка (секунды vs минуты), чужая инфраструктура и её доступность, деньги на приватных
репозиториях, дополнительная поверхность атаки — сама цепочка действий и кэшей CI (§4), и разрыв
«skipped = success», которого у простого `exit 2` локального хука нет вовсе (хук либо явно
отказывает, либо явно молчит — промежуточного «пропущен, но засчитан как прошедший» состояния в
модели `PreToolUse` не существует).

**Лучше:** применяется к **любому** пути попадания кода в ветку — не только к тому клиенту, на
котором установлен хук; не зависит от того, скопирован ли `.claude/hooks/*.sh` в конкретный клон;
видна любому с read-доступом как список required checks в настройках репозитория, а не спрятана в
файле, который нужно отдельно найти и прочитать; и, в отличие от хука, который «отказывает открыто»
по тайм-ауту (§1.3), проверка, не успевшая завершиться, `failure`, а не тихий пропуск.

## 3. Критерий: что держать хуком, что — проверкой в CI, а что не механизируется нигде

| Признак | Хук (клиент, `PreToolUse`/`Stop`) | CI-проверка (сервер, required status check) | Не механизируется нигде |
|---|---|---|---|
| Нужен мгновенный отказ **до** того, как действие уже совершено локально | Да — единственная точка, где решение принимается до коммита | Нет — CI видит только то, что уже стало пушем/PR | — |
| Проверка обязана применяться к **любому** пути попадания кода в ветку (человек, агент, другой хост, веб-редактор), а не только к тем клонам, где установлен файл хука | Нет — хук существует только там, где физически скопирован и подключён | Да — единственная точка, независимая от того, кто и с какой машины делал push | — |
| Проверка стоит дороже секунд (сборка, тяжёлые тесты, обращение к сети) и не обязана реагировать мгновенно | Плохо подходит — при таймауте хук пропускает вызов молча (§1.3) | Хорошо подходит — падение по времени блокирует слияние, а не пропускает его | — |
| Утверждение об **существовании / формате / ссылочной целостности** (файл есть, дата валидна ISO-8601, SHA существует и достижим с нужного `ref`, вердикт в парсимом формате) | Можно — если проверка нужна до коммита конкретно в этой сессии | Можно и обычно правильнее — проверка идёт по факту PR, а не по факту локального такта, и не зависит от того, что "забыли" в конкретном клоне | — |
| **Дословность вывода** — что «7 passed (3.1s)» в файле — реальный, а не сочинённый в форме вывод команды | Частично (эвристика по числовым паттернам — уже отмечено как недостаточная в `mechanics-7-protsess.md` §4.2) | Частично — CI может сам сгенерировать этот вывод и вписать его как артефакт джобы (тогда дословность гарантирована самим фактом происхождения), но не может отличить настоящий прогон от подставленного значения, если вывод копируется руками поверх реального шага | Отчасти здесь — граница подвижна в зависимости от того, кто генерирует текст |
| **Подлинность независимого суждения** ревьюера/критика — было ли одобрение результатом реального прочтения, а не автоматическим/скопированным | — | — | **Да, не механизируется**: даже вписанное как «обязательное ревью», одобрение засчитывается по факту нажатой кнопки, а не по факту прочитанного diff — см. §1.4 (одобрение без сброса при новых коммитах) и §1.4 про Copilot-approval, засчитываемый как ревью, если организация это включит |
| **Осмысленность правки** — решает ли изменение реальную проблему, а не просто проходит все формальные проверки | — | — | **Да, не механизируется**, тот же вывод, что `mechanics-7-protsess.md` §4.3 делает про эвалюатор команды `/goal`: «The evaluator judges your condition against what Claude has surfaced in the conversation. It doesn't run commands or read files independently» — механическая проверка «условие сформулировано так, что подтверждающая команда реально исполнилась» существует, проверка «условие было правильным» — нет ни на одном из трёх уровней (хук, CI, встроенный эвалюатор продукта) |

Нижние две строки — прямое продолжение вывода `mechanics-7-protsess.md` §4.2–4.3, не новый вывод, а
подтверждение того же разрыва «форма vs факт» на новом материале: сервер и CI умеют требовать, что
форма соблюдена (галочка есть, проверка позеленела, ревью нажато), но ни один из уровней — ни хук,
ни серверное правило, ни CI, ни встроенный эвалюатор продукта — не умеет требовать, чтобы за формой
стояло реальное, а не сфабрикованное или автоматическое суждение.

## 4. Провал / ограничение с базой сравнения

### 4.1. TanStack, май 2026 — цепочка сборки как вектор атаки в обход именно тех барьеров, что разбирает этот раздел

Источник — официальный постмортем самой команды TanStack, «Postmortem: TanStack npm supply-chain
compromise» (tanstack.com/blog, опубликован **2026-05-11**, обновлён **2026-05-15**), проверен
через `WebFetch` **2026-09-28**, плюс независимый разбор Wiz Security («Mini Shai-Hulud Strikes
Again: TanStack + more npm Packages Compromised», **2026-05-12**).

**Что произошло.** Атакующий создал форк `TanStack/router` под именем `zblgg/configuration`
(**2026-05-10 17:16 UTC**), закоммитил вредоносный `vite_setup.mjs`
(**2026-05-10 23:29 UTC**) и открыл PR #7378 (**2026-05-11 ~10:49 UTC**). Репозиторий **имел
защиту ветки на `main`** — но один из workflow-файлов, `bundle-size.yml`, запускался по событию
`pull_request_target` для PR из форков без требования одобрения первого контрибьютора. Дословно из
постмортема: «bundle-size.yml ran pull_request_target for fork PRs and, inside that trigger context,
checked out the fork's PR-merge ref and ran a build» — а `pull_request_target` выполняется в
контексте базового репозитория, а не форка, то есть с секретами и разрешениями `main`, минуя
привычное требование ревью, которое применяется к обычному триггеру `pull_request` (тот же
репозиторий, workflow `pr.yml` на обычном `pull_request`, в тот же день «was blocked pending
approval that never came» — ровно то поведение, которого ожидает branch protection; но
`bundle-size.yml` и `labeler.yml` этому правилу не подчинялись, потому что триггер другой).

Вредоносный код заполнил кэш GitHub Actions по ключу
`Linux-pnpm-store-${hashFiles('**/pnpm-lock.yaml')}` (**2026-05-11 11:29 UTC**), после чего
атакующий закоммитил обратно безобидный вид PR — сам PR выглядел чистым, отравленный кэш остался.
Когда легитимный релизный workflow позже собирал `main`, он **восстановил этот же кэш** — дословно:
«A PR running in the base repo's cache scope can poison entries that production workflows on main
will later restore». Отдельная, ключевая для этого раздела деталь: «`actions/cache@v5`'s post-job
save uses a runner-internal token, not the workflow's `GITHUB_TOKEN`. Setting `permissions:
contents: read` does not block cache writes» — то есть ограничение прав токена, которое разработчик
явно выставил как защиту, **не покрывало канал, через который реально произошла атака**.

Публикация в npm пошла не через штатный шаг Publish Packages, а напрямую: «It comes from the
malware running during the test/cleanup phase, which mints an OIDC token via the workflow's
`id-token: write` permission and POSTs directly to registry.npmjs.org». Итоговый диагноз
постмортема: «OIDC trusted-publisher binding has no per-publish review. Once configured, any code
path in the workflow can mint a publish-capable token» — доверие было привязано к
репозиторию/workflow целиком, а не к конкретному шагу публикации.

**Числа с базой сравнения:**

**Как это соотносится именно с темой раздела, не с CI/CD вообще.** Branch protection на `main` в
этом инциденте сделала ровно то, что заявлено в §1: не дала push мимо PR-процесса и защитила
основную ветку от прямой перезаписи. Она **не защитила** от происходящего внутри workflow,
запущенного по PR из форка с правами базового репозитория, — потому что branch protection и
пул-реквест как процесс не покрывают то, что делает конкретный workflow-файл **внутри** прогона
CI. Это ровно граница §1.4 и §2.2 на живом материале: барьер, который не даёт закрытому классу
клиентских действий (push, force-push, слияние без ревью), не эквивалентен барьеру, который
проверяет, что происходит **внутри** доверенной автоматизации, если сама эта автоматизация
неверно сконфигурирована по триггеру.

### 4.2. tj-actions/changed-files, март 2025 — тот же класс годом раньше, на другом уровне цепочки

Второй, более ранний (2025) и предельно широко задокументированный случай — компрометация самого
пакета GitHub Action, а не одного репозитория. Источник — предупреждение CISA (US Cybersecurity and
Infrastructure Security Agency), «Supply Chain Compromise of Third-Party tj-actions/changed-files
(CVE-2025-30066)», обращение через `WebSearch` **2026-09-28**, дата исходного инцидента —
**обнаружено 14 марта 2025, ~16:00 UTC**, **локализовано 15 марта 2025, ~10:30 UTC** (окно
реакции — **≈18,5 часов**, ощутимо дольше, чем 26 минут у TanStack, — разница объясняется способом
обнаружения: у tj-actions находку внесло не автоматическое срабатывание проверки, а вручную
замеченная аномалия в логах у одного из пользователей действия, у TanStack — независимый внешний
исследователь, сообщивший в GitHub Issue почти сразу после публикации).

| Утверждение | База / контрфактум | Источник |
|---|---|---|
| **более 23 000 репозиториев использовали это действие** | Затронуты **все** версионные теги действия сразу — атакующий переписал существующие теги на вредоносный код, а не выпустил новую версию, то есть закреплённая на конкретной версии зависимость (`@v45`) не защищала так, как обычно ожидается от пиннинга по номеру версии | CISA alert AA25-... / Wiz Blog, 2025-03 |
| **вредоносный код дампил память CI-раннера в открытый лог** | Секреты, попавшие в лог сборки, доступны любому с доступом на чтение публичного репозитория — то есть база сравнения: обычный уровень доступа к секретам через сам workflow (только у тех, кто может его редактировать) против уровня доступа после утечки (любой читатель публичных логов сборки) | Wiz Blog / Aqua Security, 2025-03 |

Механический вывод для раздела: серверная защита ветки и обязательные проверки закрывают ровно тот
класс, для которого спроектированы — контроль над тем, **что попадает в защищённый `ref`** и
**чьей рукой**. Ни один из двух случаев не является провалом этого правила как такового — оба
являются провалом **соседнего** доверия: доверия к тому, что делает сторонний код внутри уже
разрешённого CI-прогона (`actions/cache`, `tj-actions/changed-files`), которое ни branch protection,
ни required status checks не проверяют и не обязаны проверять по своей конструкции. Это тот же
структурный урок, что даёт таблица §3: механизм закрывает форму допуска в ветку, а не содержание
того, что происходит внутри уже допущенного процесса.

## 6. Чего я не смог подтвердить

- **Типичное («базовое») окно обнаружения подобных атак**, с которым можно было бы сравнить
  26 минут TanStack и ≈18,5 часов tj-actions как «быстро»/«медленно» в общем смысле — оба
  постмортема дают только собственные цифры, без внешнего эталона. **[не подтверждено официально —
  ни один из двух источников не приводит отраслевой базовой линии]**
- **Действует ли на демо-репозиторий курса какая-либо серверная защита сейчас** (2026-09-28), кроме
  описанной здесь механики: проверено `gh api` напрямую — нет, ни branch protection, ни rulesets не
  настроены ни на одной из пяти веток. Материалы §5 (снимки настроенного правила, упавшей проверки)
  сознательно помечены как «требует досъёмки», а не выданы за уже существующие.
  Дозволение GitHub — «Anyone with read access to a repository can view the repository's rulesets»
  относится к rulesets; классическая branch protection доступна для просмотра только тем, у кого
  есть доступ к настройкам репозитория, — эту асимметрию стоит показать студентам отдельно, если
  дойдёт очередь до практики.
- **Сравнение с GitLab/Bitbucket** сознательно не проводилось — задание ограничивает область
  механикой конкретного хостинга, на котором ведётся курсовой демо-репозиторий (GitHub); аналогичные
  механизмы (protected branches, required approvals, push rules) существуют и там, но их точные
  формулировки не проверялись и не должны выдаваться за эквивалентные без отдельной проверки.
- **Действует ли правило «Require an additional approval for unattributed Copilot pull requests» на
  PR, открытые не Copilot, а другим ИИ-агентом** (например, самим Claude Code через `gh pr create`)
  — документация формулирует правило специально про Copilot как объект распознавания; нет
  подтверждения, что механизм распознавания «PR не привязан к человеку» одинаково срабатывает для
  PR, созданных сторонним агентом от имени человеческого GitHub-аккаунта (что, по всей видимости,
  ровно тот случай, которым PR из-под Claude Code и создаются). **[не подтверждено официально —
  документация не раскрывает механизм атрибуции достаточно подробно, чтобы утверждать это на
  слайде]**
- **Точная механика того, как GitHub отличает «джоба не запустилась вовсе» от «джоба запустилась и
  вернула `skipped`»** на уровне required status checks API — задокументировано только итоговое
  правило («A job that is skipped will report its status as "Success"»), но не разобрано, что
  происходит, если required job с данным именем никогда не появлялась в check suite вообще (по
  наблюдениям в открытых обсуждениях GitHub Community это может приводить к тому, что PR остаётся
  в состоянии ожидания бесконечно, а не к автоматическому «success») — этот пограничный случай не
  проверен здесь напрямую через собственный эксперимент на демо-репозитории. **[не подтверждено
  официально — требует отдельной живой проверки на демо-репозитории, не найдено прямой цитаты
  документации]**
