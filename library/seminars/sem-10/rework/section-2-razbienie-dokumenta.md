# Раздел 2. Кейс 2 — разбиение документа на части

## Постановка

Кейс 1 решил, где база знаний будет жить, когда она вырастет: в отдельном хранилище, не в
промте. Но хранилище не глотает документ целиком: регламент на три страницы или
многостраничная инструкция не укладываются в один кусок хранилища так, чтобы поиск потом мог
точно указать на нужное место. Документ нужно сначала разрезать на части — и от того, где
пройдёт разрез, зависит, останется ли ответ на конкретный вопрос целым внутри одного кусочка
или окажется разорван между двумя соседними.

Версия 1 — естественная первая попытка, та, которую выбирают, если про это не думать отдельно:
резать документ на части фиксированного размера — по счёту символов или токенов, — не
оглядываясь на то, где в тексте проходят границы предложений или абзацев.

## Последовательная итерация

Это ровно тот случай, для которого правило «сначала версия 1, затем проблема, затем версия 2»
писалось буквально: резка по фиксированному размеру была опробована первой, потому что она
проще всего реализуется, и только после того, как замер показал её слабость, появилась
альтернатива — резать по границам предложений, а не по счёту символов.

Замер прошёл на 60 документах SberQuAD (длина не короче 500 символов — иначе резать на части
просто нечего) и 72 вопросах с проверенной разметкой ответа. По пути нашлась отдельная находка
о качестве исходных данных: у 22,0% строк исходного датасета поле с позицией ответа не
совпадало с реальным положением текста в документе — такие строки исключены из замера, не
подогнаны под удобный результат.

| Размер куска, символов | Версия 1 (фикс. размер) — доля разорванных ответов | Версия 2 (по предложениям) — доля разорванных ответов |
|---|---|---|
| 120 | 9,7% (7 из 72) | 1,4% (1 из 72) |
| 180 (заголовочное значение) | 12,5% (9 из 72) | 1,4% (1 из 72) |
| 220 | 4,2% (3 из 72) | 1,4% (1 из 72) |
| 300 | 6,9% (5 из 72) | 0,0% (0 из 72) |
| 450 | 2,8% (2 из 72) | 1,4% (1 из 72) |

Версия 2 — резать по границам предложений, не по счёту символов — снижает долю разорванных
ответов в разы на каждом из пяти проверенных размеров куска. Версия 1 никогда не опускается до
нуля; версия 2 почти всегда держится в границах 0–1,4%.

## Вопрос залу

- Резать строго по счёту символов.
- Резать по границам предложений.
- *(если по ходу занятия подтверждается самостоятельным замером — третья карточка: резать с
  перекрытием соседних кусков, семантическое резание.)* Эта третья карточка — открытый пункт
  для Фазы 4: перекрытие (overlap) этим замером не варьировалось вовсе (во всех прогонах
  overlap = 0), отдельный прогон остаётся несделанным.

## Разбор вариантов

| Действие | Как делает | Преимущество | Недостатки |
|---|---|---|---|
| Резать по счёту символов | Документ рубится на части заданной длины без оглядки на текст внутри | Проще всего реализовать; один параметр, один проход | Разрывает ответ на вопрос между двумя кусками в 2,8–12,5% случаев, в зависимости от выбранного размера; неочевидно, какой размер «удобнее» без проверки |
| Резать по границам предложений | Разрез проходит только там, где заканчивается предложение | Доля разорванных ответов падает в разы — почти всегда 0–1,4% на всех проверенных размерах | Чуть сложнее в реализации (нужен разбор текста на предложения, не просто счёт символов); зависит от качества разбивки на предложения в конкретном языке и тексте |

## Решение

### Слой 1 — архитектура

Граница куска должна совпадать с границей смысла внутри документа, а не с произвольным счётом
символов. Резка, которая режет документ «как придётся», экономит один шаг подготовки и платит
за это тем, что часть ответов на будущие вопросы окажется разорвана между двумя кусками —
и поиск впоследствии найдёт половину ответа там, где нужен был целый.

### Слой 2 — экран в n8n

На настоящем холсте стенда (не программная схема) — пять узлов подряд: форма «Документ
целиком» → Code-узел «Нарезка фиксированным размером» → Code-узел «Нарезка по границам
предложений» → узел сравнения («попал ли ответ целиком в один кусок») → экран результата. Ни
один из пяти узлов не вызывает модель — ни LLM, ни эмбеддинг: это отдельный демо-сценарий,
который прогоняет обе версии резки на одном документе и сравнивает их прямо на экране, а не
продолжение цепочки хранения из Кейса 1 (там шаг резки встал бы один раз, перед шагом
эмбеддинга, в одной цепочке). Разница между версией 1 и версией 2 — это не один параметр одного
узла, а две разные функции в двух разных Code-узлах: `chunkFixed` режет строку циклом по числу
символов, не глядя на содержимое; `chunkStructural` делит текст на предложения регулярным
выражением и накапливает их в кусок, пока суммарная длина не превысит целевой размер, закрывая
кусок строго на границе предложения. Параметр `chunk_size` (по умолчанию 180) читает только
первый узел — второй устроен принципиально иначе, а не тем же кодом с другим значением
разделителя.

## Результат и обобщение

Обратившемуся результат виден напрямую: если ответ на его вопрос разорван между двумя кусками,
модель может получить только половину нужного факта и ответить неполно или неверно — не потому
что плохо искала, а потому что то, что она нашла, само по себе было неполным. Ольге видно
число — какая доля вопросов рискует получить разорванный ответ при текущей настройке резки.

Принцип переносится на любой инструмент, не только на Text Splitter в n8n: кусок хранилища —
это единица, внутри которой должен сохраняться смысл; выбор границы разреза — это не
техническая деталь конфигурации, а решение, которое прямо определяет, сколько ответов придёт
целыми.

## Нюансы

**Размер куска не ведёт себя монотонно сам по себе.** У версии 1 доля разорванных ответов не
снижается плавно с ростом размера куска: 9,7% → 12,5% → 4,2% → 6,9% → 2,8% на пяти размерах по
возрастанию. Выбор «удобного» на вид размера (например, 180 символов, заголовочное значение
этого замера) не гарантирует качества сам по себе — требуется проверка на своих данных, а не
перенос единого эмпирического правила из чужого проекта.

**Граница применимости — прямой формой.** Этот замер не варьировал перекрытие между соседними
кусками (во всех прогонах оно было нулевым) — остаётся открытым, снижает ли добавленное
перекрытие долю разорванных ответов версии 1 ещё дальше, или версия 2 (резка по предложениям)
делает его ненужным. До отдельного прогона перекрытие не входит в это занятие как измеренный
факт, а не как рекомендация.
