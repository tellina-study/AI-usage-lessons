# Visible content

## Title bar
5 категорий MCP-серверов разработчика — и что каждая закрывает

## Body
[5 строк в Ocean rounded box, иконка + категория + проблема]

**Репозиторий / issue-трекер** (GitHub / GitLab / Jira) — читать и писать issue, PR, комментарии, статусы напрямую, без ручного copy-paste. Делает возможным уровень D.

**Файловая система** — доступ за пределами текущего проекта (общая документация, другой репозиторий в монорепо, локальные конфиги). Закрывает задачи, где контекст не помещается в один репозиторий.

**CI/CD** — статусы сборки, логи конвейера, история запусков. Агент итерирует по реальному логу ошибки CI, а не по локальному прогону.

**Базы данных** — чтение (реже запись) схемы и данных. Закрывает «миграция, согласованная со схемой» и «почему запрос медленный».

**Документация / поиск** — внутренняя вики, база знаний, поисковый индекс. Закрывает разрыв между тем, что модель знает в общем, и спецификой организации.

[Gold callout]
**Каждое подключение — решение о scope (объёме доступа), не техническая деталь.**

[Teal callout]
Least-privilege конкретно здесь: доступ к issue-трекеру не обязан включать право удалять issue · доступ к БД для аналитических запросов не обязан включать запись в prod-таблицы · доступ к CI не обязан включать право менять секреты конвейера. «Какой сервер подключить» и «с каким scope» — два разных решения; второе не следует автоматически из первого.

## Speaker notes

MCP как протокол и как граница доверия уже разобраны раньше — механика подключения через единый стандарт и правило «каждое MCP-подключение — новая граница доверия». Здесь называем, какие категории MCP-серверов реально использует разработчик и какую конкретную проблему каждая закрывает.

Первая — репозиторий и issue-трекер, класс GitHub, GitLab, Jira. Даёт агенту читать и, при настройке, писать issue, pull request, комментарии, статусы напрямую, без ручного copy-paste. Это ровно то, что делает возможным уровень D — агента, читающего issue-трекер как источник задач.

Вторая — файловая система: доступ к файлам за пределами текущего проекта, например к общей документации или другому репозиторию в монорепо. Закрывает задачи, где контекст не помещается в один репозиторий.

Третья — CI/CD: статусы сборки, логи конвейера, история запусков. Агент итерирует по реальному логу ошибки CI, а не по локальному прогону, который может отличаться от продакшена.

Четвёртая — базы данных: чтение, реже запись, схемы и данных. Закрывает «миграцию, согласованную со схемой» или «почему запрос медленный».

Пятая — документация и поиск: внутренняя вики, база знаний. Закрывает разрыв между тем, что модель знает из общего обучения, и спецификой конкретной организации.

Ключевой закрывающий тезис: каждое подключение — решение о scope, а не техническая деталь. Принцип least-privilege уже разобран раньше — здесь называем, где он всплывает конкретно. Доступ к issue-трекеру не обязан включать право удалять issue. Доступ к БД для аналитических запросов не обязан включать запись в prod-таблицы. Доступ к CI не обязан включать право менять секреты конвейера. «Какой сервер подключить» и «с каким scope» — два разных решения, второе не следует автоматически из первого.
