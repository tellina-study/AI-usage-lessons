# Visible content

## Title bar
Локальный тестовый инструментарий кодинг-агента: БД, сеть, CI-цикл — один принцип

## Body
[Matrix header — 3 колонки]

**(а) БД — Testcontainers** — реальный сервис (Postgres/Kafka/Redis) в Docker на эфемерном порту на машине разработчика/агента.

**(б) Сеть — MSW** — перехват HTTP на уровне процесса (Service Worker API / Node.js interceptor), один handler для unit/e2e.

**(в) CI-цикл — skill-обёртка** — существующий `lint → type-check → test` упакован в переиспользуемый вызов.

[Строки матрицы]

Что делает: (а) реальная, но одноразовая БД — интеграционный тест детерминированно проходит или падает · (б) один handler переиспользуется на всех уровнях тестовой пирамиды, без облака · (в) агент вызывает одной командой вместо угадывания конвенций репозитория заново

Честная оговорка: (а) skill-паттерн даёт процедуру Docker Compose, не «анализ» БД · (б) без реального примера ответа API агент «придумывает» форму — нужен настоящий JSON в промпте · (в) не новый инструмент, а упаковка уже работающей инфраструктуры

Брать готовым / делать самим: (а) **готовым** — зрелая библиотека, AI-слой (skill для конфигов) оправдан · (б) **готовым** — зрелая библиотека, честная оговорка про придуманный ответ · (в) **делать самим** — дешевле и надёжнее, чем искать «AI-native» замену

[Компактная строка примеров + облачный AI-слой]
Пример: `testcontainers-docker` skill · `mswjs.io` handlers · `lint+type-check+test` skill

Облачный AI-слой (приглушённо, не мейнстрим): **WireMock Cloud** — AI Agent Skills/MCP преимущественно здесь, не в локальном OSS-ядре. **pytest-generator** (Distil Labs) — CPU-only, ≈77% self-reported, нишевый.

[Gold callout]
Локальный, детерминированный, уже существующий инструмент — берите и оборачивайте; облачный AI-слой поверх него — используйте с честной оговоркой о конкретном разрыве.

## Speaker notes

Playwright мы уже ввели как e2e-браузерный MCP-инструмент. Здесь — фокус не на обзоре рынка тестовых SaaS-платформ, а на конкретном вопросе: чем агент проверяет БД и сеть локально, на машине разработчика, без выхода во внешний облачный сервис.

Тестирование с базой данных — Testcontainers: поднимает реальный сервис в Docker-контейнере на эфемерном порту прямо на машине и уничтожает его после прогона; единственная внешняя зависимость — локальный Docker daemon, ничего не уходит в облако. Зачем это агенту: та же логика детерминированного харнеса — реальная, но одноразовая БД, на которой тест либо детерминированно проходит, либо падает. AI-специфика скромная: не «умнее анализирует БД», а skill даёт процедурное знание, как написать корректный Docker Compose.

Сетевые моки — MSW для JS/TS: перехватывает HTTP-запросы на уровне сети прямо в процессе, один и тот же handler переиспользуется в unit, integration, e2e и Storybook. Честная оговорка: без реального примера ответа API в контексте агент может «придумать» форму ответа по обучающим данным — подавать настоящий JSON-пример не опция, а обязательная часть промпта.

WireMock здесь нужно честно развести: локальное OSS-ядро зрелое, но AI-фичи вендора размещены преимущественно на платном WireMock Cloud — «WireMock локальный» и «AI-функционал WireMock локальный» — два разных утверждения. И нишевый честный пример — pytest-generator: полностью локальная, CPU-only генерация тестов, точность около семидесяти семи процентов self-reported, низкая adoption, вендор сам предупреждает о необходимости ревью.

Суждение: Testcontainers и MSW — берите готовыми, они зрелые; skill-обёртку вокруг уже работающего CI-цикла — делайте сами, это дешевле, чем искать AI-native замену уже отлаженной инфраструктуре.
