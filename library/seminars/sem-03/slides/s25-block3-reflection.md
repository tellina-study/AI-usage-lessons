# Когда стохастичность — риск

## Assertion

Когда стохастичность ответа — риск, а не удобство?

## Visual

Верхняя широкая Ocean rounded box карточка (иконка `shield-check`, заголовок «Разобранный пример: когда НЕ LLM вообще»): «Банковский чат-бот использует LLM для диалога, но для детекции номеров банковских карт в переписке (чтобы замаскировать их перед логированием) — не полагается на LLM ни при каком значении температуры. Используется regex по формату номера карты + Luhn-алгоритм проверки контрольной суммы. Причина: нужна гарантия срабатывания на 100% известных случаев, а не вероятностное соответствие — даже при T=0 LLM может пропустить нестандартно отформатированный номер или ложно среагировать на похожую последовательность цифр, а regex с фиксированной грамматикой формата — нет.» Под карточкой короткая строка-вывод (курсив, TEAL): «Тот же принцип, что и в Блоке 1 с полнотекстовым поиском: если задаче нужна гарантия, а не вероятностное приближение — классический инструмент с фиксированной грамматикой правильнее LLM при любом параметре сэмплинга».

Ниже gold-обведённый callout с полным текстом вопроса: «В каких сценариях вашей будущей работы стохастичность ответа (T>0) — это риск, а не удобство?» Под вопросом 2 компактные Ocean rounded box карточки: левая «Где нужна воспроизводимость» (иконка `scale`) с пунктами (классификация с необходимостью аудита — регулятор или руководитель спросит, почему в прошлый раз система выдала другую категорию для того же входа / тестирование ПО — нужен детерминированный оракул для сравнения ожидаемого и фактического результата / автоматическая маршрутизация обращений — расхождение результатов ломает логику последующих шагов); правая «Оговорка про T=0» (иконка `alert-triangle`) с текстом: «Даже T=0 не даёт стопроцентной побитовой детерминированности — серверный батчинг и особенности вычислений с плавающей точкой на GPU могут дать микро-вариативность. T=0 — инженерное приближение к воспроизводимости, не абсолютная гарантия».

## Speaker notes

Пример: банковский чат-бот поддержки использует LLM для ведения диалога, но для детекции номеров банковских карт в переписке пользователя (чтобы замаскировать их перед логированием и не хранить в открытом виде) — не полагается на LLM ни при каком значении температуры. Используется regex по формату номера карты плюс Luhn-алгоритм проверки контрольной суммы. Причина: для этой конкретной подзадачи нужна гарантия срабатывания на 100% известных случаев, а не вероятностное соответствие, пусть даже при T=0 — LLM в принципе может пропустить нестандартно отформатированный номер или, наоборот, ложно среагировать на похожую последовательность цифр, а regex с фиксированной грамматикой формата — нет.

Явно связываем с главой Лекции 2 (даже T=0 — не стопроцентная гарантия побитовой детерминированности) и с деревом решений: тот же принцип, что мы уже дважды видели сегодня — в Блоке 1 про полнотекстовый поиск и здесь: если задаче нужна гарантия, а не вероятностное приближение к ней, классический инструмент с фиксированной грамматикой (regex, контрольная сумма) — правильный выбор, а не LLM ни при каком параметре сэмплинга.

Затем задаём всем классом, не риторически, ждём минимум два ответа: в каких сценариях вашей будущей работы стохастичность ответа — это риск, а не удобство?

Ожидаемые направления: классификация с необходимостью воспроизводимости и аудита — регулятор или руководитель спросит, почему в прошлый раз система выдала другую категорию для того же входа; тестирование ПО — нужен детерминированный оракул для сравнения ожидаемого и фактического результата; любой сценарий, где два разных ответа на один и тот же запрос ломают логику последующих шагов, например автоматическая маршрутизация обращений.

Обязательная оговорка, не пропускаем: даже T=0 не даёт стопроцентной побитовой детерминированности — в производственных системах серверный батчинг и особенности вычислений с плавающей точкой на GPU могут дать микро-вариативность между запусками. Для большинства задач она пренебрежимо мала, но T=0 — это не абсолютная гарантия воспроизводимости, а инженерное приближение к ней. Держите это в уме, если ваша задача требует юридически строгой воспроизводимости.
