# Two Answers to the Same Question

## Assertion

Clients get different answers to the same question. The task is to make this stable — explaining the difference after the fact doesn't solve it.

## Visual

> **Classification.** Clients get different answers to one question — this needs to be made stable.

1. Two requests arrive a couple of hours apart, almost verbatim about the same thing: how much will be refunded for classes the client didn't attend. The process names the first client an exact amount; the second, it tells to contact the administrator, with not a single number.
2. The second client writes again, now annoyed: he remembers a different answer to a similar question. Olga draws the conclusion any engineer would: it's the same question, so somewhere in the model node's settings there's a source of the difference.

> **What it costs the training center.** A client holding two different answers to one question stops trusting either and calls to double-check with a human. Olga: "I don't need the process to be smarter. I need it to give the same answer to the same question."

## Speaker notes

At the top of the screen — the same process that's been standing all day today, in solid blocks: the form, the knowledge-base check, the answer going straight to the client. None of that changes today. Separately, in dashed outline — what we're breaking down today: the model node's settings and the prompt text, which decide whether the client gets the same answer to the same question or not.

Let's classify the problem right away, before telling the story: clients get different answers to the same question — that's a concrete thing, and it needs to be made stable.

Now the story itself. Two requests arrive a couple of hours apart, and both are almost verbatim about the same thing: how much will be refunded for classes the client didn't attend. The process names the first client an exact amount. The second, it tells to contact the administrator, giving no number at all. Some time later, the second client writes again, now annoyed: he remembers getting a different answer earlier when he asked something similar, and wants an explanation.

Olga puts both answers side by side and draws the conclusion any engineer in her place would draw. It's the same question — so the answer is supposed to be the same, and since it isn't, somewhere in the model node's settings there's a source of randomness that needs finding and switching off. That's a reasonable first hypothesis, and it's exactly where any sound investigation of instability starts.

The cost is clear without numbers: a client holding two different answers to one question in their chat history stops trusting either and goes to check with a human — exactly the action the process was supposed to take off Olga's hands. And Olga herself frames the request in the most engineering terms possible, with no complaint about the content of the answer: let the process not get any smarter, just let it behave predictably.

Hence the question the breakdown opens with: what to do with the settings so the process answers an identical question identically. There are five options that come to an engineer's mind first — and next we'll go through each one in turn.
