## 2026-08-11 — Лекция 2 polish pass (issue #156) findings

- **`§[0-9]` scaffold-reference cleanup is a deck-wide, not per-slide, defect.** 10 named review comments pointed at specific slides (s03/s24/s26/s27), but a full-deck grep found the same pattern on 8 additional untouched slides (s02, s04, s15, s16, s19, s21, s22, s23) — some already absent from the actual PPTX render (build script had drifted from markdown source without the §-ref), others genuinely leaking into visible body/notes. **Lesson: always run the deck-wide grep even when the brief names specific slides** — targeted fixes alone under-clean by ~2×.
- **Markdown source and build-script visible text can silently diverge.** Several slides (s04, s21, s22, s23, s26) had stale `§X.Y` text in the `.md` source's Body/Speaker-notes sections that was **already absent** from the corresponding `build_sNN()` function — meaning a prior editing pass fixed the render but not the source, or vice-versa. Cross-check both, not just one, when auditing for forbidden patterns; grep against the rendered PPTX text is the ground truth, grep against `.md` catches source-drift that would resurface on next full rebuild-from-source.
- **`deck.yaml` `visual.primary` free-text fields can contain unescaped inner double-quotes that break strict YAML parsing.** Found 2 instances (`«1-е из 3 "почему"...»`, `«3-е из 3 "почему"...»`) where a Russian curly-quote sentence embedded a literal `"почему"` inside an already-double-quoted YAML scalar — `yaml.safe_load()` fails with a parser error at that line. **The file was already broken before this session** (verified via `git show HEAD:...`), so no tooling that actually parses `deck.yaml` as YAML had been run against it recently, or the break would have been caught. Fixed both instances by rewording to avoid nested quotes (same §-cleanup pass already needed there). **Recommend a `python3 -c "import yaml; yaml.safe_load(open('deck.yaml'))"` sanity check added to the pre-render checklist** — cheap, would have caught this immediately.
- **Shared per-lecture `add_image()` helper had a live silent-failure bug** (height-only calls fell through to "native size" branch, ignoring `h`) — found via visual-loop inspection on a *new* illustration (s01), not by testing the helper directly. Audit showed 13/14 other lecture `build_lecNN.py` copies share the same bug (only lec-02 fixed in this session). See `notes/mcp-limitations.md` [#156-1]. **Lesson: per-lecture copy-pasted build-script helpers accumulate divergent bugfixes — a shared module would propagate fixes automatically.**
- **Decision-tree schema slides benefit from explicit arrowhead connectors, not just thin rectangles.** s25's v1.7 tree used plain `filled_rect` lines root→branches with no visual arrowhead — technically a tree, but read ambiguously at a glance. Adding `MSO_SHAPE.ISOSCELES_TRIANGLE` (rotated 180°) arrowheads at the branch end of each connector made the "flow direction" immediately legible — cheap fix, meaningfully improves the 5-second test pass rate for `schema_pipeline`/`schema_cycle`-adjacent tree diagrams not explicitly covered by the existing subtype table.

## 2026-09-30 — Семинар 5: чему научили четыре параллельные сессии над одной декой (issue #211)

Три автора (рамка, хуки, скиллы) плюс сессия рендерера правили один дек в своих worktree. Уроки переносимые, не про Семинар 5.

**1. Проверка, показывающая ноль, — не то же самое, что чистый результат.** За сутки трижды: проверка курсива стояла у одного входа из шести форм; предпросмотр угадывал перенос по шрифту («моноширинный ⇒ вывод команды») и рисовал мнимое наложение; скан текста схем выдирал строковые литералы регуляркой и отчитался «0 попаданий» при двух датах на схеме. Правило: **проверку доказывают сквозным опытом** — сломать нарочно, убедиться, что поймала, вернуть, убедиться, что молчит.

**2. Молчащая проверка молчит в типичном случае, а не на краю.** Уточнение от сессии скиллов, и оно меняет способ отладки: объяснение «проверка работает, просто не поймала редкий случай» почти всегда неверно. Мнимое наложение возникло на *первой же* моноширинной ячейке таблицы; даты не находились в строках, ничем не отличавшихся от найденных. Проверять надо типичный случай, не экзотику.

**3. Диф ветки против головы — не способ забрать чужую работу.** У N веток, отросших в разное время, `git diff HEAD <ветка>` показывает чужие правки как откат. Забирать надо **поимённым списком файлов по владельцу**. Дважды поймано на грани: один диф воскресил бы удалённый слайд, другой — откатил бы круг правок соседнего блока. Отдельно: `git diff --name-status` выдаёт переименования строками `R` с двумя путями — фильтр по `$2` берёт старое имя и молча теряет файл; нужен `--no-renames`.

**4. Разрешение конфликтов — решение по каждому файлу, не оптом.** «Взять свою сторону списком» затянуло откат чужой правки в файле, который автору не принадлежал. Цена: потерянное обобщение, которого требовал владелец.

**5. Забирать каталог целиком (`git checkout <ref> -- dir/`) опаснее, чем кажется:** воскрешает не только удалённые файлы, но и **старые версии живых**. Худший случай прошёл молча — схема собралась правильно, просто уже отведённого места; сказал о ней только класс предупреждения «схема зажата», а не проверки на ошибки.

**6. Записанное намерение против догадки по косвенному признаку.** Оба ложных дефекта предпросмотра родились из разумной догадки о намерении автора. Починка одна: записать свойство в файл (`word_wrap = False` на рамке), а не выводить его из шрифта. Тот же класс — реестр схем: «намерение» в реестре расходится с каталогом в момент правки, когда на слайд никто не смотрит; нужны предупреждения в обе стороны (файла нет / слайда нет).

**7. Границы, заданные числами, ломаются на первой вставке.** Границы разделов деки трижды переписывались вручную, и каждый раз надзаголовок на хвосте врал молча. Выводить их надо из самой деки по опорным приёмам. Но и это держится на допущении о составе — допущение обязано **говорить о себе вслух**, когда перестаёт выполняться.

**8. «Влезло» и «читается» — разные вопросы.** Проверка на переполнение молчит о таблице, которой хватило 9 pt с первого захода. Нужен отдельный класс «на дне кегля» с порогом **по дну лестницы самого приёма**, а не по абсолютному кеглю: первый — факт о вёрстке, второй — мнение о типографике.

**9. Схема платит первой, и это не выглядит дефектом.** Из 12 схем деки 8 были у́же отведённого (61–85%): не «схема обрезана», а «слайд полупустой по бокам». Механика: **укоротить схему на перегруженном слайде не значит дать ей ширину** — освободившаяся высота уходит в бюджет сжатых соседей. Помогает уменьшение содержания или смена раскладки на более широкую.

**10. На плотном слайде схема стоит дороже, чем кажется по списку предупреждений.** Трижды за круг выбор был «иллюстрация или содержание», и все три раза выиграло содержание; в одном случае схема оказалась чистым дублем таблицы под ней, только читалась миниатюрой.

**11. Заметки — половина деки, и ни одна проверка в них не смотрела.** Разметка в заметках не обрабатывалась вовсе, и `*курсив*` доезжал в PowerPoint звёздочками — дефект жил неизвестно сколько, потому что все проверки были про слайд.

**12. Правка ради долей дюйма дважды вернула уже закрытые дефекты.** Закрытый дефект считается закрытым только после повторного замера.

**13. Когда правка затрагивает работу другого автора — спросить дешевле, чем выполнить и откатить**, даже если указание выглядит однозначным: фронт мог сдвинуться, и автор указания об этом не знает. Сессия рендерера так спасла три заголовка, сделанных лучше, чем предписывало моё указание.

## 2026-10-10 — Сборщик деки как третий слой текста: содержание, которое не проходит ни одной сверки (issue #229)

Найдено при инвентаризации майской Лекции 7 перед её переработкой, подтверждено независимо.

**Что обнаружено.** На слайде 29 собранной деки Лекции 7 в подвале стоят «Приказ 203н» и «EU AI Act
Art. 14», а в карточке — «AI = подсказка, не решение». Ни одного из этих номеров нет ни в
`chapter.md`, ни в `speech.md`, ни в `slides/*.md`, ни в `deck.yaml`. Они **вписаны прямо в
`rendered/build_lec07.py`** (строки 1886 и 1935) и попадают на экран только при сборке.

**Почему это класс дефектов, а не одна опечатка.** Весь контроль качества курса смотрит на
источники: фактчекер читает главу и речь, сверка согласованности сравнивает три артефакта,
предгейтовый обход грепает исходники слайдов. **Сборщик не читает никто.** Любая строка,
вписанная в него руками, видна студенту и невидима каждой проверке — и попадает в `.pptx` с тем же
весом, что выверенное утверждение из главы.

**Насколько это неправда — отдельный вопрос, и ответ осторожный.** Оба номера, судя по всему,
существуют и по смыслу подходят. Дефект не в том, что номер выдуман, а в том, что **его
происхождение не прослеживается ни к одному проверенному месту**: никто не сверял ни редакцию
приказа, ни то, что названная статья регламента говорит именно это. Номер норматива на экране —
утверждение о праве, и оно идёт под именем курса.

**Правило.** Видимый слой деки — это объединение исходников слайдов **и сборщика**. Проверки
обязаны читать оба. Конкретно:
- предгейтовый греп прогонять по **собранному `.pptx`** (через `python-pptx`, по видимому тексту и
  заметкам), а не только по `slides/*.md` — сборщик иначе остаётся слепой зоной;
- любой номер норматива, фамилия, год и число в сборщике — либо переносятся в исходник слайда,
  либо сборщик падает. Содержанию в коде сборки места нет;
- сверка «исходник против рендера» в обе стороны: есть на экране, но нет в исходнике — такой же
  дефект, как обратное.

**Где это уже стоило:** Лекция 7 мая 2026 прошла четыре раунда критиков (включая вердикты
APPROVE-CLEAN по согласованности и методике) с этой строкой на экране. Ни один раунд её не увидел,
потому что ни один не смотрел в сборщик.

## 2026-10-10 — Ложное срабатывание проверки стоит дороже, чем кажется: два класса и как их не отбрасывать молча (issue #229)

Скан видимого слоя планов Лекции 7 дал два попадания, и **оба оказались ложными** — но обнаружить это
можно было только глазами, а значит следующий прогон на другой лекции поймал бы их снова.

**Класс 1. Запрещённая фраза внутри запрета.** План писал «на экране: позиции по порядку, **без
подсветки „вы здесь"**» — то есть исполнял правило, прямо называя запрещённое. Проверка, ищущая
запрещённую фразу, видит её исполнение как нарушение. Это неизбежно для любого грепа по запретам:
**текст, запрещающий приём, содержит имя приёма.**

**Класс 2. Идиома, совпавшая с шаблоном.** «Вот **то же самое**, собранное по сотне опытов» попало под
шаблон превосходных форм (`сам(ый|ая|ое|ые)`). «То же самое» — идиома тождества, и она встречается в
каждом разборе, который сравнивает два измерения, то есть в самом частом жанре отраслевой лекции.

**Чего делать нельзя — молча отбросить.** Соблазн очевидный: дописать исключение и получить чистый
ноль. Но тогда проверка начинает тихо пропускать настоящие случаи того же вида — а отличить
«запрещённое внутри запрета» от «запрещённого всерьёз» машина не может.

**Что сделано вместо.** Идиома тождества снимается **до** проверки (она однозначна). А попадание в
контексте отрицания (`без`, `не`, `нет`, `запрещ*`, `сня*`, `убра*`) уходит в **отдельное ведро
«похоже на запрет, глазами»** — его видно в отчёте, оно не в итоговом счёте, и человек решает. Ноль
в итоге означает ноль, а спорное остаётся на виду.

**И починка доказана двумя мутациями, а не прогоном.** Первая: две новые приманки в самотест —
идиома и запрещённая фраза внутри запрета; самотест падает, если любая из них снова станет
нарушением. Вторая, важнее: в **живой** файл плана дописана строка «раздел идёт 7 минут, и это
главный слайд вечера» — проверка поймала оба нарушения. Без второй мутации «чистый ноль» означал бы
только, что проверка ослеплена починкой.

**Правило:** когда чинишь ложное срабатывание, добавь приманку в самотест **и** проверь на живом
файле, что настоящее нарушение всё ещё ловится. Ослепить проверку починкой легче, чем починить.

## 2026-10-12 — Отрицательный ответ одного источника, принятый за факт отсутствия: один класс ошибки, четыре случая за одно производство (issue #229)

Производство Лекции 7 дало четыре независимых случая **одной** ошибки, и каждый раз она
выглядела добросовестным выводом, а не ошибкой. Это самое переносимое наблюдение сессии.

**Случай 1 — `WebFetch` не нашёл цитату, которой на странице действительно не было… и нашёл
цитату, которой не было тоже.** Уже записано как `[#225-1]`: суммаризирующая модель
пересказывает, доделывает арифметику и выдаёт правдоподобное за прочитанное.

**Случай 2 — «браузера в этом окружении нет».** Агент проверил `chromium`,
`chromium-browser`, `google-chrome`, `firefox`, `wkhtmltoimage`, `cutycapt`, `playwright` —
шесть программ, все отсутствуют, вывод «снимать веб-страницы здесь нечем». Вывод неверен:
средство лежало **в этом же репозитории**, добытое прошлой сессией ровно под эту задачу
(`tools/presentation-build/setup_page_shots.sh`). Проверка «что установлено в системе»
отвечает на другой вопрос, чем «чем это делается здесь»; на второй отвечает `notes/`.

**Случай 3 — «первоисточник за подпиской».** Europe PMC `fullTextXML` отдаёт HTTP 500 для
того же PMCID, который NCBI `efetch db=pmc` выдаёт целиком. Промах одного шлюза записали как
закрытость статьи — а за ней лежало то, что разбор утверждал **неверно**: сравнение трёх
режимов существует только на фантоме, у контроля на животных знаменатель 1, и в список
выигрышей входило время, которое приём проиграл (55,41 против 31,96 минуты, p = 0,0009).
Отдельно: ScienceDirect отдаёт 403 на свой же объявленный адрес открытого доступа для гибридной
статьи под CC-BY-NC-ND.

**Случай 4 — мой собственный, и худший из четырёх.** Вызовы оболочки перестали проходить с
сообщением «классификатор разрешений недоступен». Я записала это в чат владельцу **как
причину**. Настоящей причиной был дроссель cgroup по памяти от `git gc --auto`, который душил
весь контейнер целиком, включая тот процесс, что первым перестал отвечать. Симптом был назван
причиной, и назван вслух как факт.

**Общая механика.** Инструмент, не нашедший чего-то, отвечает на вопрос «нашёл ли **я** это
**так**». Ответ «нет» не равен «этого нет». Разница невидима, потому что отрицательный ответ
приходит в той же форме, что положительный, и выглядит завершённым.

**Правило.** Прежде чем записать отсутствие — источника, инструмента, возможности, —
**предъявить второй независимый путь** и назвать оба в отчёте. Для первоисточника это
`curl` по сырому тексту и второй шлюз (NCBI против Europe PMC). Для инструмента — `notes/`
и репозиторий, а не только `which`. Для собственного окружения — замер (`memory.current`,
`pgrep`), а не вывод по симптому. И формулировка: **«я не смог найти X тем-то»**, а не
«X не существует» — вторая фраза утверждает больше, чем проверено.

**Почему это стоит журнала, а не только каталога ограничений.** Четыре случая пришлись на
лекцию, чья собственная красная линия — **счёт по своему плану вместо счёта по тому, что
получилось**. Конвейер воспроизвёл ошибку, которой учит материал, четыре раза за одно
производство, и трижды из четырёх её снял кто-то снаружи.

**Случай 5, через час после того, как записаны первые четыре — и снова мой.** Я проверила
утверждение Лекции 7 о преемственности с Лекцией 6 и объявила: «в 48 файлах Лекции 6 **ноль**
вхождений „сгусток", „тип задачи", „модальность"». Замер был настоящий. Каталог — не тот:
в `library/lectures/lec-06/` на рабочей ветке лежит **отменённая майская редакция**, а
прочитанная лекция живёт на неслитой ветке `issue-223-lec-06-rework`, где «тип задачи» — 25
вхождений, «модальность» — 37, «три сгустка» — 2, и где только и существует
`effects-vocabulary.md`. На этом основании я отправила агента «привести к тому, что есть»
утверждение, **которого не было**: фразу «те же три сгустка, что в инженерном проектировании»
я перенесла из чужого отчёта, не проверив её существование, — `git log -S` показывает, что на
ветке она не появлялась никогда.

Отягчающее: **указание уже было записано** — `plan-brief.md` §1 самой Лекции 7 говорит прямым
текстом «любая сверка Лекции 7 с Лекцией 6 идёт по ветке `issue-223`, не по `main`», и
`research/01-inheritance-lec06.md` §3.4 эту сверку уже проделал правильно. Я не прочла ни то,
ни другое.

**Что это добавляет к правилу.** Мало спросить «нашёл ли я это так» — надо спросить **«туда ли
я смотрел»**. Для репозитория с неслитыми ветками «файла нет в рабочем дереве» не значит
«файла нет»: ветка, тег, история `git log -S`, и — прежде всего — **собственные брифы
проекта, где адрес уже записан**. Отрицательный результат по неверному адресу неотличим от
отрицательного результата по верному.

**И цена не нулевая, хотя обошлось.** Наряд был ошибочен, но агент его не выполнил буквально:
он перепроверил посылку, нашёл её ложной, сказал это первой строкой отчёта — и вместо
несуществующего дефекта починил семь настоящих (заголовок «трёх клеток» над таблицей из
четырёх строк; «восемь форм» после решения владельца о девятой; номер формы `(9)` там, где
файл сам требует `(8)`; «три клетки из тридцати» при сетке 6 × 7 = 42) и уточнил четыре
междулекционные ссылки. **Субагент, выполняющий ошибочный наряд буквально, стоил бы здесь
правки по всей главе.**

**Случай 6 — зеркальный, и снова мой наряд.** Все пять предыдущих — отрицательный ответ,
принятый за отсутствие. Шестой перевернут: **уверенное положительное утверждение о дефекте,
которого нет.** Я записала в наряд, что «0,76–0,83» в §4.5 — склейка: нижняя граница заявки
первой версии с верхней границей заявки второй. Рассуждение было связным и внутренне
непротиворечивым. Оно было неверным: **0,76–0,83 и есть заявленный разработчиком диапазон
первой версии**, подтверждённый двумя независимыми рецензируемыми работами в открытом доступе
(PMC10317482, PMC10111986), а 0,83 оказалось по совпадению ещё и нижней границей второй
заявки — это совпадение и создало видимость склейки. Провенанс был записан **в этом же
производстве**: `roast/02-fakty.md` §P3-3 и `research/_scratch-clinical.md`.

**Выполни агент наряд буквально — он удалил бы проверенное число** и оставил главу слабее, чем
нашёл. Починка пошла в обратную сторону: строка с диапазоном осталась, а к ней подтянули
соседнюю, где то же заявление стояло в неисточниковой форме «не менее 0,76» со ссылкой на
«информационный лист поставщика», которого найти не удалось.

**Что это добавляет.** Правило «отрицательный ответ не равен отсутствию» имеет зеркало:
**положительный вывод о дефекте — тоже гипотеза, а не находка**, и требует той же второй
проверки. Опаснее он тем, что приходит с готовым объяснением: у «здесь склейка» есть механизм,
мотив и выглядящее подтверждение, а у «здесь всё верно» — ничего, кроме совпадения чисел.
Диагноз, который красиво объясняет наблюдение, проверять хочется меньше всего.

**Практическое следствие для нарядов.** Писать гипотезу гипотезой: не «исправь склейку», а
«проверь, склейка ли это, и если да — исправь». Разница в одном придаточном и в том,
удалит ли исполнитель верное число. Оба раза спасло то, что агент перепроверил посылку, — но
это была его инициатива, а не то, чего требовал мой текст.

## 2026-10-12 — Общий сборщик деков: 73 реализации одной задачи, и что показало их сведение (issue #229)

**Повод — вопрос владельца:** «почему у нас нет общего сборщика и каждый раз пишется?»

**Замер.** В `library/` **73 сборщика, около 60 000 строк**. У одной Лекции 3 их пять (v1, v2,
v3, v3_pub, en). Поколений два: девятнадцать хардкодят каждый слайд своей функцией
(`build_s01`, `build_s02`…), остальные читают файлы кадров. Зрелых «читающих» ровно два —
Лекции 6 и Лекции 7.

**Ключевое число: эти два делят 21 имя функции из 86 и 70.** Это не копии с расхождением, а
два независимых решения одной задачи. И у каждого есть то, чего нет у другого: у Лекции 6 —
таблицы и сетки, у Лекции 7 — настоящие метрики шрифта и пятнадцать доказанных проверок.
Поэтому общее ядро — **объединение**, а не выбор.

### Что сведение нашло в первый же день — и чего ни один сборщик не видел про себя

**1. У Лекции 7 снятие тени промахивалось мимо цели.** Код ищет `effectRef` внутри `spPr`, а
она лежит в `<p:style>` — соседнем узле. Поиск не находил ничего и **молчал**. Замерено: 112
автофигур только в первых двадцати кадрах несут тему с тенью; у Лекции 6 — ноль. Хуже всего
то, что дефект **был записан** — `notes/mcp-limitations.md` `[#223-8]`, статус `active`, — но
запись живёт только на неслитой ветке `issue-223-lec-06-rework`, и сессия Лекции 7 её не
видела. Третий за сутки случай, когда знание есть, а до того, кому оно нужно, не доходит
из-за разрезанных веток.

**2. У прочитанной Лекции 6 — видимый дефект на экране.** На `s18` подпись схемы требует
0,43″ в рамке 0,22″ по настоящим метрикам курсива. Прежний замер курсив не считал и молчал.
Лекцию прочитали залу 10 октября в таком виде. Геометрию ядро не меняет, поэтому регрессия
чистая — дефект от этого не исчез.

**3. Таблицы приехали вообще без проверок** — у Лекции 6 самотеста не было. Девять проб
написаны при переносе.

### Переносимое

- **Регрессия по содержанию, а не по байтам.** `[#211-5]` уже замерил: три пересборки
  нетронутой деки дают три разных sha256 (python-pptx пишет свои отметки времени). Поэтому
  сравнивается содержимое: состав и порядок кадров, фигуры с геометрией в EMU, прогоны текста
  со стилями, заметки со ссылками. Проба `[отпечаток]` доказывает, что сравнение не слепое:
  сдвиг в **1 EMU** регистрируется. Это заодно закрывает прямую жалобу `[#211-5]` — «у
  ревьюера нет хеша, которым показать, что русский рендер не тронут».
- **Доказательство подстановкой, когда перевод ещё не сделан.** Деки не конвертировали;
  низкоуровневые имена живого сборщика пересвязали на ядро и пересобрали. Ноль расхождений
  тогда означает «ядро ничего не изменило», а не «тест написан под результат». Сначала
  снимается базовая линия: каждый сборщик своим же кодом воспроизводит свой же файл.
- **Превосходство доказывается не регрессией.** Что измерение Лекции 7 — строгое надмножество
  измерения Лекции 6, доказано пробой против **независимой переделки старого измерения**, а не
  тем, что «регрессия прошла». Регрессия показала бы совпадение и в случае, если бы обе
  реализации были неправы одинаково.
- **Старое поколение не мигрировать.** Девятнадцать сборщиков обслуживают прочитанные лекции:
  выгоды ноль, риск сломать доставленное реален.
- **Список приближений едет вместе с ядром** (13 позиций в `deckkit/README.md`). Пустой список
  — не достижение, а необнаруженный дефект.

### Чего ядро не берёт намеренно

Раскладка кадра (что где стоит), конкретные числа геометрии (разный материал, не дрейф),
смысловые правила отдельной лекции (`is_grid_line` кодирует таксономию Лекции 1 — верно для
одной лекции, ложно в общем месте), рендер в PDF/PNG (остаётся по лекциям и под `timeout`,
`[#223-6]`).

## 2026-10-12 — Маркеров `[for-slide-sNN]` в главе Лекции 7 нет вовсе; привязка деки к главе идёт через `chapter_ref` (issue #229)

Правило `CLAUDE.md` § «Chapter Multi-Part Pattern» требует: «Slide-маркеры `[for-slide-sNN]` —
на каждом ≥150-слов разделе как Phase 5 anchor для speaker notes». В Лекции 7 их **ноль** —
`grep -c for-slide` даёт 0 по всем шестнадцати файлам главы, и `[sNN]`-маркеров тоже нет.

Привязка устроена **наоборот**: поля `chapter_ref` в `deck*.yaml` и во фронтматтере файлов
кадров указывают из деки в главу. Обнаружено при разрезе `chapter-part4.md` — агент искал
маркеры, чтобы их сохранить, и не нашёл ни одного.

**Что это значит практически.** Направление ссылки определяет, кто ломается при правке.
Маркеры в главе ломаются, когда переставляют кадры; `chapter_ref` в деке ломается, когда
переставляют разделы главы. Второе случается реже — и именно поэтому разрез главы на шесть
файлов прошёл без каскада переименований. То есть фактическая схема Лекции 7 здесь **прочнее**
предписанной, а не беднее.

**Решение: правило в `CLAUDE.md` требует уточнения, а не лекция — приведения к правилу.**
Формулировать как «привязка обязана существовать и быть односторонней», с двумя допустимыми
реализациями, и назвать, что `chapter_ref`-направление предпочтительнее при многочастной главе.
Отдельным изменением, не бундлить (`CLAUDE.md` и без того 775 строк при собственном лимите 600).

**Непокрытое декой — отдельный факт, не дефект.** Дека сама записывает (генератором, в
`make_deck_yaml.py`), что ни один кадр не ведёт в пять файлов части 4 — это Разделы 7–8 главы
(назначение и лечение, оперативная помощь), около 18 700 слов. Это **согласуется** с решением
о слоте: оба раздела остаются в главе и со сцены не идут. Важно, что дека говорит это сама и
счёт порождается, а не вписан руками.

содержанием: четыре подписи плашки в четыре строки капителью (`s32`, `s42`, `s48`, `s49`) и
одно значение, в котором лежит фраза, а не число (`s37`). Это работа переделки, не перевода.

«на `s18` подобрано меньше 4,30"». Она доказывала бы состояние деки на сегодня и соврала бы в
обе стороны: и когда подбор сломается, и когда кадр просто перестанет в нём нуждаться. Переписана
так, чтобы начинать поиск с нарочно слишком широкого слота.

## 2026-10-13 — Девять параллельных сессий на одну деку: что это стоило и чему научило

Владелец отклонил деку Лекции 7 третий раз: «форматирование полотно текста; начало главы
по прежнему пример, а не разбор; в конце блока нет матрицы обещаной» — и велел запустить
отдельную сессию на каждый блок, на введение и на заключение. Запущено девять: восемь по
деке, одна по главе. Все девять вернулись.

### Три правила, купленные этим кругом

**1. Общий индекс git сильнее аккуратного `git add`.** Девять сессий работали в одном
воркtree. `git add` своих путей НЕ защищает: `git commit -m "…"` коммитит **весь индекс**,
включая то, что в него положила чужая сессия. Переименование файла из сессии входа уехало в
коммит блока 2; тринадцать файлов блоков 7–8 уехали в коммит входа. Коммитить только
`git commit -m "…" -- <путь> <путь>`. Предупреждение разослано после того, как случилось
дважды, — и после рассылки больше не повторилось ни разу.

**2. Мерить дефект надо той меркой, в которой он живёт.** «Полотно текста» мерилось числом
слов на кадр — и мера показывала, что у нас 91 слово против 120 у принятой Лекции 6, то есть
«претензия не применима». Дефект был в раскладке: те же слова у Лекции 6 разложены в две
колонки, плашки и вокруг фотографии, а у нас шли абзацами в одну рамку. `columns` по всей
деке стояли на **одном кадре из сорока**. Мера была верной и отвечала не на тот вопрос.

**3. Ограничение инструмента, обойдённое трижды, — это дефект инструмента.** Три сессии
независимо уткнулись в то, что ячейка таблицы красится полужирной целиком, и каждая обошла
скобками, переписав легенду карты. Накопительная карта, которую владелец заказывал дословно,
была физически невыполнима, и сборщик об этом **молчал**. Правило: обход, встреченный больше
одного раза, выносится оркестратору как починка ядра, а не как свойство жанра.

### Самотест деки сломался молча в третий раз

переживают один рез и врут после второго** — теперь кадры выводятся долей от числа страниц,
а устаревший выпуск даёт внятный отказ вместо трассировки. Трассировка читается как
«инструмент сломан», отказ — как «мера не проверена»; это разные сообщения.

## 2026-10-14 — Канонические документы по лекциям: что показал аудит (issue #238)

Сессия чинила гайдбуки по лекциям, а не лекцию. Ниже то, что переносится на любой нормативный
документ курса.

- **«Перенесено туда» без прогона по ссылкам — это семь ссылок в пустоту.** `CLAUDE.md` семь раз
  указывала на `trebovaniya-k-soderzhaniyu.md` §5.12–5.17 со словами «перенесено туда 2026-10-10
  из-за лимита 600 строк»; разделов не существовало, файл кончался на §5.11. Среди недостающих —
  §5.13, форма разбора, на которую опирается ENFORCED-правило о строении раздела. **Правило: после
  переноса куска в другой файл — прогон по ссылкам на номера разделов, а не отметка «сделано».**
- **Из расходящихся норм работает самая низкая, и работает потолком.** Норма заметок стояла в трёх
  значениях: 150–300 (`CLAUDE.md`, пайплайн-док, четыре агента, два скилла), 250–450 (требования
  к содержанию) и 500–800 (решение владельца №10). Цена замерена прожаркой Лекции 7: медиана 289
  слов, **ноль кадров из 122** в норме, недостача ≈25 840 слов; дизайнер написал прямо — «это мой
  лимит, я писал „250–300 слов" в каждый наряд и закрепил цифру в README деки». Владелец на гейте
  называл другое число, и это не помогло. **Правило: расхождение норм чинится одним проходом по
  всем местам, и у каждого числа пишется область действия** (здесь: лекции 500–800, семинары
  250–450 — числа соседних жанров иначе съезжают друг в друга).
- **Дубль номера раздела делает ссылку неразрешимой, и это не ловится чтением.** В пайплайн-доке
  было по два §8, §9 и §10 плюс §3.8 перед §3.7a: ссылка «§8» означала либо параллельное
  производство, либо связь со слайдами. Дешёвая проверка — `grep -c '^## N\.'` на уникальность
  номера. При разведении дублей смотреть, **кто ссылается на старые номера**: семь записей в
  `notes/` ссылались на §8 и §9, поэтому эти два номера сохранены, а переномерован хвост.
- **Файл, на который ссылается нормативный документ, может лежать на неслитой ветке.** Греп по
  рабочему дереву показывает «нет файла» и ничего не говорит о причине. Нашлось через
  `git log --all --oneline --diff-filter=A -- '*имя*'`: `lec-06/post-delivery-analysis.md` живёт в
  коммите `a198ac68` на ветке `issue-223-lec-06-rework`, в `main` его нет. **Правило: прежде чем
  объявлять источник потерянным — искать по всем ветками; ссылка на файл вне `main` помечается
  прямо в тексте, с именем ветки.**
- **Ремесло, живущее в папке одного занятия, следующим занятием не наследуется.** Ось, форма
  разбора, правило счёта разборов, швы, минутный счёт лежали в `library/lectures/lec-07/rework/`
  (11 062 строки), и пайплайн-документ не содержал ни одного из этих слов. Семинары вылечили то же
  самое двумя неделями раньше (`tools/seminar-production/README.md`, вступление). Теперь есть
  `tools/lecture-production/stroenie-i-povestvovanie.md`.
- **Проверка ссылок «файл §раздел» окупается одним прогоном.** Инлайновый скрипт (регулярка
  `` `путь.md` §N `` → заголовки целевого файла) прошёл `CLAUDE.md`, `tools/`, `.claude/`,
  `templates/` и дал 22 места за один запуск; после правок осталось 3, все с объяснённой причиной
  (файл на неслитой ветке + соглашение о per-seminar `ARCHITECTURE.md`). Заводить его сторожом —
  отдельная задача, здесь сознательно не делалось.
- **Побочное, не чиненное:** `CLAUDE.md` — 835 строк при лимите 600, `notes/decisions.md` — 671.
  Оба нарушения старше этой сессии; разрезание — отдельная задача (для журнала она названа ещё
  2026-10-01).

## 2026-10-14 — Прожарка Лекции 7 под новым каноном: два правила процесса (issue #229)

Три замера из четырёх дали одиннадцать P0. Два из них — не про содержание, а про то, как
устроена работа, и переносятся на любое производство курса.

- **Рекомендация реза, принятая до смены цели, исполняется и после — потому что цель и рез живут
  в разных файлах, и ничто их не связывает.** Шаг реза А1 (`CUT-ORDER.md`, 11 октября) снял
  разделы главы §7–§8 целиком: 18 кадров, 13,50 минуты, **21 строка реестра разборов из 45**.
  Рез был посчитан честно и под тогдашний слот правилен. 14 октября владелец назначил главной
  целью результат, который лежал ровно в снятом: измеренная пара «человек + модель» ниже обоих в
  отдельности у профессиональных медиков. Дека к этому моменту была собрана по отменённой
  рекомендации, и ни один из девяти агентов сборки не мог этого заметить — каждый читал наряд, а
  не реестр решений. **Правило: решение владельца, меняющее цель, обязано в тот же круг пройти по
  всем назначенным резам и отменить те, что противоречат новой цели — списком, с адресами.**
  Проверка дешёвая: открыть `CUT-ORDER.md` и для каждого шага ответить, не стало ли снятое
  несущим.
- **Агент, которому сказано «ничего не менять», не должен чистить и чужого мусора.** Агент
  фактчека увидел в рабочем дереве изменённый `lec-07-karkas.pptx` и каталог промежуточных
  замеров, принял их за след мёртвой сессии, откатил pptx и удалил каталог — а это была работа
  параллельно идущего агента рендера, которому пересборка была прямо поручена. Потерь содержания
  нет (файлы кадров и глава не тронуты), замер пришлось вести заново. Корень — разводка работ
  оркестратором: двум агентам был разрешён один каталог. **Правило: агент, которому нужна
  пересборка, работает в своём именованном каталоге (`deck/zamer-<роль>-<дата>/`), и в наряде
  каждого критика стоит «посторонние изменения в рабочем дереве не твои — доложи, не откатывай».**
- **Отрицательный ответ веб-поиска снова оказался не доказательством, и цена была P0.** Прошлый
  круг записал первоисточник как недоступный (403 на `ai.nejm.org`) — прямое чтение препринта той
  же работы открылось с первой попытки и дало доверительный интервал «−8,3…−19,7» против стоящего
  в главе «−18,9…−9,1», уже уехавшего на кадр и в два плана. Правило записано в
  `notes/mcp-limitations.md` `[#225-1]` ещё 10 октября; этот случай — его второе подтверждение
  в другом производстве. **Если прошлый отчёт объявил источник недоступным, это повод прочесть
  его самому, а не унаследовать вывод.**
- **Широкий `git add` оркестратора во время работы агента забирает его правки в чужой коммит.**
  Третий случай одного класса за день. Я коммитил разведку путём `library/.../research/` и
  `tools/`, пока в том же рабочем дереве шёл агент переделки деки: два коммита **захватили часть
  его переименований**, и рез оказался в истории вперемешку с разведкой. Содержание не потеряно
  (агент это проверил построчно и доложил), но коммит перестал отвечать на вопрос «что сделал
  этот наряд». **Правило: пока в дереве работает агент, оркестратор коммитит только
  поимённо — файлы своего отчёта и своих правок, никогда каталогом.** То же правило уже записано
  для агентов в `tools/seminar-production/README.md` §8.9 («коммитить по именам, а не папкой») —
  оно относится и к оркестратору.
- **Наряд, составленный по плану, может противоречить сам себе, если план старше материала.**
  Мой наряд на рез велел снять кадр по шагу `А2` из `CUT-ORDER.md` и тем же пунктом — сохранить
  поимённо кадр, которым он сегодня является: за прошлые круги содержание кадра подменилось, и он
  стал единственным в своём разделе, кто несёт шаги ① и ② формы разбора. **Агент не выполнил
  пункт и доложил конфликт с ценой в минутах — это правильное поведение, и его стоит требовать
  прямо в наряде.** Формулировка, которая работает: «если два пункта наряда противоречат друг
  другу — не выбирай молча, останови этот пункт и назови цену обоих исходов числом».
- **«Шесть разошедшихся счётчиков слов» оказались одним устаревшим числом, а не шестью методами.**
  Фронтматтер главы Лекции 7 нёс четыре разных итога, критика дала пятый, наряд шестой — и это
  выглядело как спор методик. Независимый пересчёт двух сессий сошёлся: расходится **одна строка**
  фронтматтера — часть 4, где записано 20 958 против измеренных 21 981–22 564 (второй замер дал
  ровно верхнюю границу коридора первого). Причина простая: строку не пересчитали после того, как
  дописали §§ 7–9 и разрезали файл. **Правило: прежде чем объявлять расхождение счётчиков, сверить
  слагаемые — обычно врёт не метод, а одно не обновлённое число.** И метод счёта записывается
  рядом с итогом: сброс служебных блоков на любом заголовке H1–H3 (сброс только на H2 занижает
  итог на 27% и выглядит здоровым числом).
- **В требовании надо называть ЕДИНИЦУ измерения, а не только сам замер.** Я поставил в очередь
  работ «найти долю **записей**, созданных копированием предыдущей записи» — а литература измеряет
  долю **текста** (слов и знаков). Сессия Раздела 5 Лекции 7 это заметила, внесла прямым чтением
  то, что действительно измерено (50,1% слов дубля на 104 млн заметок; 46% скопированного текста в
  типичной заметке), а метрику по записям оставила помеченной «через обзор, первичная работа не
  открыта». **Агент, который этого не заметил бы, молча ответил бы на другой вопрос — и число
  выглядело бы исполнением требования.** Правило: формулируя требование о замере, писать единицу
  (доля чего именно: записей · текста · времени · случаев) и допускать явный ответ «в этой единице
  не измерено».
- **Полезное наблюдение о замерах оркестратора:** мой собственный греп счётчиков «N из M» по
  видимому слою дал 17 вхождений, из которых **шесть оказались артефактами** — шаблон ловил
  хвост десятичной дроби («84,9 из ста» читалось как «9 из ста»). Семь настоящих сошлись все.
  То же, что записано про `grep -P` по кириллице в `tools/seminar-production/README.md` §8.6:
  смотреть контекст совпадений, а не счёт.
