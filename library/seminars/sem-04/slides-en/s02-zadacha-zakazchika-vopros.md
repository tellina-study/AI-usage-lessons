# The client's request

## Assertion

The task arrives in the client's own wording: what the result should be is there; how the code is put together, what counts as done, and where the boundaries of action lie are not.

## Visual

The client's request quoted verbatim, as one large block:

> "We need a landing page with a sign-up form for a demo lesson: a single static page, the fields 'name' and 'email', a submit button. We have no backend of our own — send the submission to our form-intake service."

Below it — an open question to the class, in large type, with no option cards:

> "Do we hand this wording to the agent as is — or do we pin down the requirements first?"

At the bottom — a note: "open discussion, not a vote".

## Speaker notes

"Here is the task in the form it arrives in: what the result should be is stated; how it is put together inside, what counts as done, and what must not be done are not stated. This text is what you sit down to work with."

The open question: "Do we hand this wording to the agent as is — or do we pin down the requirements first?"

The format is a discussion, 2-3 voices; arguments are collected, not graded. The spread is usually predictable: some hand it over as is and squeeze out the details as they go, others write the wording out first. Both positions work, and the point of the step is to get that said out loud.

If the conversation drifts into architecture ("do we even need a backend here") — log it as a separate question and move on.

Bridge: "You can hand it over — the agent will deal with what is written. The question is what it is left with when little is written. Let's pin down the requirements."
