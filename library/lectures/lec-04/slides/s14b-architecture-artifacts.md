# Visible content

## Title bar
У каждой практики есть файл в репозитории — вот они целиком

Те же четыре практики, что на предыдущем слайде, — но не описанием, а артефактом, который лежит в репозитории и проверяется сборкой.

## Body

[Колонка 1 — ADR] `docs/adr/0007-event-queue.md`

```
# ADR-0007. Очередь вместо
# прямых вызовов склада
Статус: принято · 12.03.2026
Контекст: при отказе склада
  заказы теряются молча
Решение: заказы идут через
  очередь событий
Последствия: + переживаем
  отказ склада;
  − подтверждение до 2 с
```

Развилку выбрал и подписал человек — текст мог написать AI. Запись неизменяема: устаревшую не правят, а заменяют новой.

[Колонка 2 — Fitness-функция] `tests/architecture/test_layers.py`

```
# инвариант 1: границы модулей
def test_payment_not_ui():
    assert not depends_on(
        "payment", "ui")

# инвариант 2: бюджет 200 мс
def test_checkout_p95():
    assert p95("/checkout")
    < 200
```

Какой инвариант критичен — решает человек, это его определение «хорошего». Нарушен на коммите — сборка красная.

[Колонка 3 — C4 / арх-как-код] `docs/architecture/workspace.dsl`

```
workspace {
 model {
  inzh = person "Инженер"
  app = softwareSystem "Бронь" {
    api = container "API"
    db  = container "БД броней"
  }
  inzh -> api "бронирует"
 }
}
```

Текст, а не картинка: диффается и ревьюится в том же запросе на слияние, что и код; сверка модели с кодом ловит расхождение.

[Колонка 4 — Эволюционная арх.] `.github/workflows/architecture.yml`

```
# гейт: три практики вместе
- adr-lint docs/adr/
  # нет развилки без записи
- pytest tests/architecture
  # инварианты держатся
- structurizr-cli drift
  # модель и код совпадают
# красный шаг → слияние
# заблокировано
```

Своего артефакта нет — есть гейт, который держит три предыдущих вместе на каждом изменении. Направление задаёт человек.

[Gold callout]
Практику видно по артефакту: если по ней нельзя показать файл в репозитории и красный шаг сборки при нарушении — это ещё не практика, а намерение.

## Speaker notes

Предыдущий слайд перечислил четыре практики словами; здесь они же — файлами, которые реально лежат в репозитории. Это и есть проверка на прочность: практика, по которой нельзя открыть конкретный файл и показать шаг сборки, краснеющий при её нарушении, остаётся намерением.

ADR — короткая, в полстраницы, запись на одну архитектурную развилку: контекст (какую проблему решаем, какие силы действуют), решение в утвердительной форме, статус и последствия, включая негативные [1]. Найгард настаивал именно на лёгкости формата: большие документы никогда не поддерживаются в актуальном состоянии, у малых модульных есть хотя бы шанс. Запись неизменяема — устаревшее решение не переписывают, а помечают заменённым новой записью. Для агента, у которого нет памяти между запусками, ADR оказывается тем единственным местом, где хранится «почему»: код показывает, что изменилось, история версий — когда и кто, а обоснование не хранит больше ничто.

Fitness-функция переводит это «почему» в машинную проверку на каждом коммите: направление зависимостей между модулями, бюджет задержки критичного пути, покрытие контракта [2]. Её ценность ровно равна ценности инварианта, который в неё вложил человек, — тривиальный всегда-зелёный гейт даёт только видимость надзора.

Архитектура-как-код — та же логика, применённая к самой модели системы: текстовый язык описания, который версионируется и диффается рядом с кодом, поэтому AI одинаково хорошо его и читает, и порождает, а сверка описанной модели с фактическим кодом ловит расхождение до слияния [3].

Четвёртая колонка — не отдельный артефакт, а сборка трёх предыдущих: эволюционная архитектура складывается из инкрементальных изменений, явных fitness-функций и спроектированной способности систему менять [4]. В репозитории это выглядит как один конвейер, прогоняющий три проверки вместе.
