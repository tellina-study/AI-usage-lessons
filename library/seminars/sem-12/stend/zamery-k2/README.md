## §0. Две инфраструктурные находки (читать первыми — они определили финальный план замера №3)

### 0.1. `nvidia/nemotron-3.5-embed-1b:free` — затяжной отказ free-tier, 12/30, дальше не добирали

Эта модель — одна из двух «рабочих» по С10 (margin 0,593, `sem-10/stend/raw/
case4_working_mm_results.json`). При сборе оригинальных эмбеддингов для замеров №3/№4
модель начала стабильно отвечать HTTP 503 «Service is overloaded», затем HTTP 504
«Worker upstream fetch timed out after 60000ms» — **не на отдельных вызовах, а в течение
десятков минут подряд**, независимо от конкурентности (проверено и на 1, и на 2, и на 4
параллельных вызовах) и независимо от ретраев.

**Числа отказа, честно:**
- Итоговый результат: **12 из 30** оригиналов получены, **18 из 30 — нет**.
- Для большинства из 18 недополученных сканов было сделано **два отдельных раунда по
  до 8 попыток** (экспоненциальный backoff до 25с между попытками внутри раунда) —
  до 16 попыток на скан суммарно, см. `raw/originals_nvidia_nemotron-3.5-embed-1b_free.json`
  (28 записей в `fail_log` на 18 уникальных сканов).
- Непосредственно перед остановкой — **3 свежих независимых одиночных вызова** (другие
  сканы, по одной попытке каждый, без ретраев) — **все 3 упали** с HTTP 504 после полных
  60 секунд ожидания. Это и отличило «перегрузку, которая закрывается повтором» от
  «ответа инфраструктуры, не помехи»: если даже разовый свежий вызов не проходит за 60с —
  ретраи той же модели в упор не помогут.
- Время, потраченное на попытки добрать эту модель: **около 60 минут** (с 15:34 по
  16:36 UTC, несколько циклов перезапуска скрипта сбора).

**Инженерная мораль занятия (прямая, не оговорка):** замер, который опирается на чужую
бесплатную вычислительную мощность, невоспроизводим, даже когда код абсолютно верен и
ретраи настроены правильно. 12/30 — **не идут в сравнение моделей** ни в замере №3, ни
в замере №4 — это отдельно названный, честно описанный провал инфраструктуры, а не
число о модели. (Кэш с частичными 12/30 остаётся в `raw/` для прозрачности, но ни один
расчёт в этом README на него не ссылается.)

### 0.2. `nvidia/llama-nemotron-embed-vl-1b-v2:free` — исчезла из каталога за 17 дней

Вторая «рабочая» модель С10 (margin 0,392). На С10 (2026-11-04) она прошла отбор и была

— 3 из 3 попыток, ретраи не помогают (это не перегрузка, это «эндпоинта нет»). Проверено
не только отрицательным ответом самого вызова (канон §8.7 — отрицательный ответ сам по
себе не доказательство): прямой `curl` живого каталога
`https://openrouter.ai/api/v1/embeddings/models` (40 моделей на 2026-11-21) подтверждает —
модели с этим id в каталоге нет вовсе. Похожая по имени модель `nvidia/nemotron-3-embed-1b:free`
в каталоге есть, но это **другая** модель (другая линия имени — `nemotron-3`, не
`llama-nemotron-embed-vl`), непроверенная margin-тестом С10 — **не подставлена** как
замена.

**Мостик к Кейсу 4 (порог похожести) — одной строкой:** число, снятое на модели, может
оказаться непереносимым не из-за смены модели владельцем решения, а потому что сама
модель однажды просто исчезает из каталога поставщика — порог, настроенный на такой
модели, в какой-то момент будет нечем переносить вовсе.

**Решение (оркестратор, 2026-11-21):** не ждать, пока модель «появится снова» — отсутствие

## §1. Замер №3 — дрожание входа

**Вопрос:** для одной и той же картинки, подвергнутой лёгкому и жёсткому файловому
искажению, насколько уезжает вектор (cosine с оригиналом) и меняется ли первый сосед при
поиске среди всех 30 сканов.

**Модели (после решения §0 — НЕ исходные две API-модели С10):**
1. **CLIP ViT-B/32** (`openai/clip-vit-base-patch32`, HF `transformers`, CPU-инференс,
   локально) — тот же рецепт, что ставился на С10
   (`sem-10/stend/measure/case4_local_clip_retrieval_30.py`).
2. **SigLIP** (`google/siglip-base-patch16-224`, HF `transformers`, CPU, локально) — тот
   же рецепт С10 (`case4_local_siglip_retrieval_30.py`).
3. **`mongodb/voyage-multimodal-3.5`** (платно, через API) — одна кросс-проверка, чтобы
   находка не была свойством одной конкретной локальной архитектуры.

**Почему локальные модели — не запасной вариант, а лучший инструмент именно для этой
задачи:** дрожание входа требует множества ДЕТЕРМИНИРОВАННЫХ повторных прогонов одного и
того же изображения; локальная модель даёт бит-в-бит повторяемый результат без сетевой/
очередной нестабильности free-tier (ровно то, что сломало API-вариант, см. §0.1) — замер
измеряет свойство ВХОДА, а не чужой инфраструктуры. Студент может повторить этот замер
без API-ключа и без денег (CLIP+SigLIP), платная модель — опциональная кросс-проверка.

**Настройки вызова (канон §5 — везде, где есть модель):**
- Рабочее разрешение везде **300×450**, JPEG. Оригинал — качество 80.

  оригинала (кроме composite), детерминированные (без `random`): `common_k2.py::VARIANTS`.

### 1.2. Лёгкий и трудный случай — ИСПРАВЛЕНО 2026-11-21: основной трудный случай — деформация силой Кейса 4, не `composite_rotate_crop`

**Правка оркестратора после первой версии этого README.** Ноль переключений у CLIP/SigLIP
на пяти своих вариантах (включая заявленный тогда «трудный случай» `composite_rotate_crop`,
1°+5%) — по канону §8.11 это не результат сам по себе: нужна проверка той же силой, что уже
дала НЕ ноль у соседнего Кейса 4 этого же занятия (ветка `hc/s12-k4-porog-2-bc37ac51`,
`stend/zamery-k4/measure_siglip_local.py`, band-метрика: 45 из 60 пар не разделяются порогом
на `hard_dup`). Проверка добавлена (`measure_jitter_case4_strength.py`, таблица Б выше) —
и результат ИЗМЕНИЛСЯ: при настоящей силе Кейса 4 (12° + 4%, а не 1° + 5%) CLIP и SigLIP
**тоже перестают быть нулём**.

**Лёгкий случай** (поворот на 1° и пересжатие, как два отдельных лёгких воздействия —
формулировка не менялась):
- `rotate_1deg`: CLIP 0/30 переключений, SigLIP 0/30, voyage **21/30 (70%)**.
- `recompress_q30`: CLIP **2/30 (6,7%)**, SigLIP 0/30, voyage **29/30 (96,7%)**.

**Трудный случай (ФИНАЛЬНЫЙ — `case4_hard_dup`, поворот 12° + обрезка 4%, не 1°+5%):**
- CLIP **7/30 (23,3%)**, SigLIP **6/30 (20,0%)**, voyage **29/30 (96,7%)**.

**Промежуточный шаг (`composite_rotate_crop`, 1°+5% — оставлен как шаг между лёгким и
основным трудным случаем, не как итоговый трудный случай):** CLIP 0/30, SigLIP 0/30,
voyage 22/30 (73,3%).

**Находка №1 (сохранена, уточнена) — внутри своих пяти мягких вариантов трудный случай
не обязан быть труднее лёгкого (канон §8.11).** Для CLIP на своих вариантах пересжатие
(лёгкий случай) дало 2 переключения, а `composite_rotate_crop` (тогдашний «трудный
случай») — 0. Это наблюдение остаётся верным ВНУТРИ своих пяти вариантов — но не
отменяет того, что более грубая деформация извне (Кейс 4, находка №2 ниже) всё-таки
бьёт сильнее.

**Находка №2 (ЗАМЕНЯЕТ прежнюю «честный ноль SigLIP») — ноль на своих вариантах был
свойством СЛАБОСТИ искажения, не устойчивости модели (канон §8.11 буквально: «ноль —
не результат, пока не назван трудный случай»).** На пяти своих, более мягких вариантах
(1°, 5%, q30, 60%) ни CLIP, ни SigLIP не дали ни одного переключения — ЭТО выглядело как
честный ноль об устойчивости модели. Проверка той же силой, что использовал Кейс 4 (12°
поворот + 4% обрезка), это опровергла: CLIP даёт 7/30 (23,3%), SigLIP — 6/30 (20,0%).
Прежняя формулировка «SigLIP полностью устойчив» была НЕВЕРНОЙ не потому, что расчёт был
ошибочен, а потому что искажение было подобрано слишком мягким для вывода такой силы —
ровно случай, который канон §8.11 и называет «задачу выбрали слишком лёгкой».

**Находка №3 (новая) — расхождение со band-метрикой Кейса 4 на тех же файлах, названное,
не скрытое.** Кейс 4 на `hard_dup` у SigLIP получил полосу неопределённости на **75%**
выборки (45 из 60 пар same/diff не разделяются одним порогом). Здесь на тех же самых
файлах (`hard_dup`, та же SigLIP) switch_rate — **20,0%** (6 из 30). Числа не противоречат
друг другу — они измеряют РАЗНОЕ: band-метрика Кейса 4 смотрит, разделяются ли
распределения cosine(same) и cosine(diff) одним порогом ПО ВСЕМ парам сразу; switch_rate
здесь смотрит, выигрывает ли top-1 ARGMAX среди 30 кандидатов для каждого конкретного
скана. Полоса неопределённости в 75% не обязана превращаться в 75% смену первого соседа:
даже когда диапазоны same/diff пересекаются на большинстве пар, конкретный «свой»
оригинал на argmax-поиске обычно (в 80% случаев для SigLIP) всё ещё остаётся самым
похожим — ровно потому что сравнение идёт не с ЛЮБЫМ порогом, а с конкретными 29
альтернативами этого корпуса. Мост к Кейсу 4: отсюда разница между «порог не разделяет
выборку» (это про вердикт/порог) и «поиск не находит нужный документ» (это про top-1) —
эти два отказа ненулевые ОБА, но разного размера, и путать их — методическая ошибка,
которую стоит назвать на кадре.

**Находка №4 (сохранена) — платная модель с margin≈0 (С10) ломается почти на ЛЮБОМ
искажении, лёгком и трудном одинаково.** `voyage-multimodal-3.5` держит cosine к своему
же оригиналу почти идеальным (0,97–0,99) на всех семи вариантах — но ПЕРВЫЙ СОСЕД
меняется в 57–97% случаев, включая 90,0% уже на `case4_soft_dup` (мягчайшем из всех
семи). Прямое измеренное подтверждение разворота П1 Кейса 2: у модели с margin≈0 (С10:
margin −0,010) различение было на грани случайного ДО всякого искажения — лёгкое и
трудное искажение почти не различаются по эффекту, потому что сигнала, который можно
было бы сломать сильнее слабого, просто не было.

## §2. Замер №4 — согласие моделей между собой

### 2.3. Разбор — не честный ноль, а находка сильнее заявленной оси (канон §8.11, «трудный
случай обязан перестать быть лёгким», здесь — обратный неожиданный исход у лёгкого)

Исходное предположение оркестратора о возможном исходе было: «если согласие моделей
окажется ВЫСОКИМ (вариативности почти нет) — честный ноль». Измеренное — не это, но и
не плоское «согласия нет вообще» — два случая расходятся арифметически, и разводить их
нужно точно, не одной фразой на оба (поправка оркестратора 2026-11-21, исходная
формулировка здесь путала близость в процентных пунктах с близостью по отношению к
шансу):

- **Лёгкий случай** (`cohere/embed-5-fast` vs `cohere/embed-5-pro`, один поставщик):
  83,3% несовпадений ⇒ согласие **16,7%**. Случайное согласие при 29 кандидатах —
  **3,45%** (1 − 0,9655). 16,7% / 3,45% ≈ **4,8** — **согласие здесь впятеро выше
  случайного**, и всё равно крайне мало в абсолютных числах: пара одной продуктовой
  линии одного поставщика выбирает одного и того же «похожего соседа» меньше чем в
  одном случае из пяти.
- **Трудный случай** (четыре поставщика, 6 пар): несовпадения 90,0–96,7% ⇒ согласие
  3,3–10%. Нижняя граница этого диапазона (3,3%, пара `cohere-fast`×`voyage-multimodal-3.5`
  и `nemotron-8b`×`cohere-fast`) **практически совпадает** со случайным уровнем
  (3,45%) — здесь формулировка «неотличимо от чистой случайности» верна буквально;
  верхняя граница (10%, `nemotron-8b`×`gemini-embedding-2`) — тоже низкая, но заметно
  выше нуля (≈2,9× случайного).

**Это не «измеритель сломался» — это прямое число к развороту П1 Кейса 2.** Похожесть —
не свойство пары картинок, а то, что задано обучающей целью конкретной модели (находка
Г1 исследования `research/02-vektorizatsiya-kartinki.md`). Три из четырёх моделей
трудного случая (gemini/cohere-fast/voyage) имели margin≈0 на С10
(`case4_working_mm_results.json`) — то есть для них «похожесть» и так была слабо связана
с реальным содержанием документа; ожидаемо, что их выбор «ближайшего соседа» почти не
совпадает ни с рабочими моделями, ни друг с другом, и местами неотличим от случайного.
Пара ОДНОГО поставщика (cohere fast/pro, лёгкий случай) — иначе: архитектура/обучающая
цель линии `embed-5` всё же оставляют измеримый, не случайный след согласия (впятеро
выше шанса), просто этот след мал в абсолютных числах — согласия «впятеро больше, чем
ничего» и «достаточно, чтобы доверять чужому выбору модели» — разные утверждения, и
кейс учит не путать их.

**Вывод для кейса, прямой:** «одна хорошая модель эмбеддинга» — миф на уровне самого
выбора «что с чем похоже», не только на уровне порога (Кейс 4). Чужой выбор модели не
просто «может не подойти» — для 29 кандидатов из 30 сканов он в среднем будет называть
ДРУГОГО «похожего соседа», чем выбрала бы соседняя модель того же самого поставщика.

## §5. Статус по оси Кейса 2 — опровергли или подтвердили

**Оба замера ПОДТВЕРДИЛИ ось кейса, причём сильнее заявленного, не слабее:**

- Замер №3 (числа — после правки 2026-11-21, итоговый трудный случай — `case4_hard_dup`,
  12°+4%, не свой 1°+5%): модель с заведомо слабым различением (margin≈0 на С10) ломается
  почти на ЛЮБОМ искажении, от мягчайшего до самого грубого одинаково (57–97% смены
  первого соседа, включая 90% уже на самом мягком `case4_soft_dup`); модели с реальным
  различением (локальный CLIP/SigLIP) — устойчивы к своим пяти мягким вариантам (0–2/30),
  но НЕ абсолютно устойчивы к деформации силой Кейса 4 (CLIP 7/30 = 23,3%, SigLIP
  6/30 = 20,0%) — первая версия этого README ошибочно назвала это «честным нулём»,
  пока не проверила трудный случай настоящей силой (канон §8.11).
- Замер №4: даже у пары одного поставщика одной продуктовой линии согласие (16,7%) хоть
  и впятеро выше случайного (3,45%), остаётся низким в абсолютных числах; у четырёх
  разных поставщиков согласие (3,3–10%) местами неотличимо от чистой случайности — обе
  формулировки верны для своего случая, не взаимозаменяемы (см. §2.3 — точная разводка).
  «Похожесть» действительно задаётся каждой моделью по-своему, не общим свойством пары
  картинок.

**Два отдельных, честно названных пробела инфраструктуры** (не относятся к выводу о
моделях, см. §0): `nemotron-3.5-embed-1b:free` недоступна была для полного прогона
(12/30, затяжной отказ free-tier); `llama-nemotron-embed-vl-1b-v2:free` исчезла из
