# Кода интеграции не пишет ни один из пяти

## Assertion

Кода интеграции не требует ни один из пяти способов: агент сам шлёт запрос и сам разбирает ответ. Разделяет их то, знает ли агент заранее, что у системы можно спросить. Для регулярного доступа нескольких сессий это оставляет два законных варианта подключения.

## Visual

| Способ | Что делает | Что не делает / ограничение |
|---|---|---|
| вызвать API напрямую | агент сам пишет и шлёт запросы к эндпойнтам, сам разбирает ответ — отдельный код интеграции писать не нужно | заранее не знает спецификацию сервиса: какие есть точки, какие у них параметры и ограничения — без документации или swagger-описания агент их не угадает |
| подключить чужой сервер — удалённо | сервис, который кто-то хостит и обновляет сам; у вас не крутится отдельный процесс | управляете не вы: не видно, что сервис делает внутри и когда в нём что-то меняется; плюс обычные вопросы безопасности удалённого сервиса — кому доверяете ключ, у кого ещё есть доступ |
| подключить чужой сервер — локально | пакет исполняется у вас, конфигурация — строка в репозитории, видна всей команде в ревью; контроля больше, чем у удалённого | это всё равно живой процесс на вашей машине и чужой код — со всеми его зависимостями и правом на обновление |
| написать свой сервер | даёт ровно нужный набор операций и прав, без чужого кода в процессе | написать минимальный сервер сейчас быстро — для этого есть готовый плагин; дорого обходится поддержка: протокол, чужие пользователи, безопасность транспорта — отдельный проект рядом с основным |
| вызывать команду `gh` каждый раз | готовый официальный CLI GitHub — авторизацию и разбор ответа он уже решил за вас, кода писать не нужно | каждый вызов — отдельная команда без общего списка возможностей: агент не видит заранее, что вообще можно сделать, нужный вызов приходится знать заранее |

> **Поворот.** Интеграцию не пишут ни в одном из пяти способов: агент сам шлёт запрос и сам разбирает ответ. Разделяет пятёрку другое — знает ли агент заранее, что у системы можно спросить.
> **Что это оставляет.** Свой сервер избыточен: официальный для трекера уже есть. `gh` и прямой вызов API закрывают вызов, известный заранее; растущий список операций они перекладывают на память разработчика.
> **Два законных варианта.** Между «удалённо» и «локально» готового ответа нет: свежий официальный пример подключается удалённо, решение занятия — локальный процесс, потому что конфигурация становится кодом в репозитории, видимым в ревью.

## Speaker notes

Сначала то, что разбор опровергает. Кода интеграции не придётся писать ни в одном из пяти способов: агент сам соберёт запрос и сам разберёт ответ, это он умеет. Значит, выбор идёт по другому основанию.

Разделяет пятёрку одно: знает ли агент заранее, что у системы можно спросить. Прямой вызов API — спецификацию сервиса агент не угадает, её нужно дать документацией или swagger-описанием. `gh` — официальный CLI GitHub, авторизация и разбор ответа уже решены за вас, но общего списка возможностей он не даёт: нужную команду помните вы.

Три средних карточки этот список дают. Чужой сервер удалённо — его держит и обновляет кто-то другой, у вас не крутится процесс; зато не видно, что внутри и когда оно поменялось. Чужой сервер локально — пакет исполняется у вас, конфигурация лежит строкой в репозитории и видна в ревью; это по-прежнему живой чужой код на вашей машине. Свой сервер даёт ровно нужные операции и права; минимальный пишется быстро, для этого есть плагин, дорого обходится поддержка.

Вывод складывается из сочетания. Свой сервер избыточен, раз официальный есть. Между «удалённо» и «локально» законны оба; берём локальный — ради конфигурации, видимой в ревью.

Если спросят, почему тогда вообще платят за сервер, раз доступ даёт и команда: платят за список возможностей, который агент читает сам. Сколько именно это стоит, посчитаем через два экрана — цифра там неожиданная.

Если спросят про «удалённо» подробнее: свежий официальный пример подключения именно к этому сервису — удалённый http-сервис, в отличие от примера, на который опирается кейс. Решение занятия от этого неверным не становится: локальный способ остаётся официально поддерживаемым. Знать стоит другое — официальный путь одного и того же поставщика со временем меняется.

Если спросят про безопасность удалённого сервиса подробнее: у одного MCP-сервера для баз данных флаг «только чтение» не делал соединение реально ограниченным — разберём это в провале кейса.

Если спросят, почему `gh` не выигрывает: он отлично закрывает единичный, заранее известный вызов. С ростом числа операций помнить и называть каждую команду точно приходится разработчику — и ровно на этом месте вторник из сцены повторяется, только уже с командами.

Если спросят про поддержку своего сервера подробнее: обновления протокола, чужие пользователи, безопасность транспорта. Это отдельный проект рядом с основным, и заводить его стоит тогда, когда нужного набора операций нет ни у кого из готовых поставщиков.

Если прозвучит «мы возьмём API, потому что так гибче»: это законный выбор, и он не отменяется этим разбором. Спросите только, где будет жить описание эндпойнтов, которым вы кормите агента, и кто обновит его, когда сервис поменяет версию.
