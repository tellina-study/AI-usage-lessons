# Visible content

## Title bar
Сравнение 3 паттернов по 4 критериям — решающая ось зависит от команды

## Body
[Таблица 4×3 в Ocean rounded box]

| Паттерн | Git-diff-поведение | Устойчивость к параллельным сессиям | Обнаруживаемость человеком | Что ломается на масштабе |
|---|---|---|---|---|
| **1. Вложенная папка на задачу** (nested per-task folder) | конфликтов между задачами нет; артефакты растут вложенно | высокая между разными задачами; директории могут «осиротеть» без явного закрытия | легко по номеру задачи; трудно обзорно без индекса | захламление неархивированными директориями закрытых задач |
| **2. Единый журнал** (single unified log) | append-only, но одна точка записи для всех | низкая — общий хвост файла = магнит конфликтов при параллельной записи | высокая обзорно; низкая точечно (нужен полнотекстовый поиск) | файл не помещается в контекст агента целиком (context rot) |
| **3. Плоская общая папка** (flat shared folder) | конфликт только при работе над одной и той же задачей | высокая между разными задачами (как Паттерн 1, но без директорий) | высокая обзорно (`ls`) и точечно (по имени файла) | список файлов растёт без внутренней структуры; несколько артефактов на задачу требуют условности именования |

[Teal callout]
**Нет единственно верного ответа** — это следствие взвешивания осей под ситуацию команды, а не рекомендация в обход них. Команда, работающая строго последовательно одним агентом за раз, — устойчивость к параллелизму не решающая ось, Паттерн 2 может быть валидным выбором. Команда с малым числом задач и низкой параллельностью может предпочесть Паттерн 1 ради богатой структуры на задачу — и это не будет ошибкой при её реальных условиях. Команда, регулярно запускающая несколько параллельных сессий на разных задачах, — здесь решающая ось именно устойчивость к параллелизму, и Паттерн 2 наиболее уязвим по построению.

## Speaker notes

Три паттерна хранения состояния задачи — это три разных набора компромиссов, и они не складываются в один суммарный балл: у каждого паттерна есть условие, при котором он ломается специфическим для себя образом. У nested per-task folder — это захламление осиротевшими директориями закрытых задач. У single unified log — конфликты параллельной записи и то, что файл перестаёт помещаться в контекст агента целиком. У flat shared folder — плоский список файлов без внутренней структуры на масштабе. Правильный выбор — назвать решающую ось под конкретную ситуацию команды, а не искать «лучший» паттерн вообще.

Для команды, работающей строго последовательно, одним агентом за раз над одной задачей, устойчивость к параллелизму не является решающей осью, и единый растущий журнал — простейший в реализации, с лучшей обзорностью — может быть вполне рабочим выбором. Для команды, регулярно запускающей несколько параллельных сессий агента над разными задачами одновременно — а это всё более типичная ситуация по мере того, как кодинг-агенты становятся частью повседневной практики, — решающей осью становится именно устойчивость к параллелизму, и здесь единый журнал наиболее уязвим по построению: два параллельных сеанса, дописывающие в конец одного и того же файла, почти гарантированно создают конфликт.

Команды, для которых решающей осью оказывается устойчивость к параллелизму при умеренной сложности задачи — а это большинство начинающих команд, — чаще сходятся к плоской общей директории с одним файлом на задачу. Но это следствие взвешивания осей, а не универсальная рекомендация в обход них: команда с малым числом задач и низкой параллельностью вполне может предпочесть вложенную директорию на задачу ради богатой структуры, и это не будет ошибкой при её реальных условиях. Как и с матрицей уровней автономии этой лекции, здесь нет одного правильного ответа вообще — есть правильный ответ для названных условий команды.
