# Субагенты и оркестрация: исследование для семинара «Сборка конфигурации кодинг-агента»

> Блок исследования: верхняя ступень лестницы конфигурации — субагенты и мультиагентные системы. Она же — ступень, на которой чаще всего переусложняют. Все даты и цифры — по состоянию на момент публикации источников (2025 — начало 2026). Непроверенные утверждения помечены `[НЕ ПОДТВЕРЖДЕНО]`.

## Резюме (тезисы)

1. **Главный настоящий аргумент за субагента — изоляция контекста, а не «много голов лучше».** Грязная разведка (десять способов прогрепать репозиторий, чтение полусотни файлов ради одного факта) возвращает в основную сессию только итог, а не мусор. «Коллективный разум» — маркетинговая рамка; механика — управление контекстным окном.
2. **У субагентов есть измеримая цена, и она не маленькая.** По данным Anthropic, мультиагентная система тратит в 15 раз больше токенов, чем обычный чат, а более позднее (январь 2026) уточнение той же компании даёт диапазон 3–10× относительно одноагентного решения той же задачи. Обе цифры — от одного источника, в разное время, для разных сравнений — и это тоже урок: сравнивайте, с чем сравнивают.
3. **Позиции индустрии по мультиагентности прямо противоположны, и обе — от практиков, не от теоретиков.** Cognition (Devin) 12 июня 2025 опубликовали «Don't Build Multi-Agents» с разбором конкретного провала (два субагента сделали несовместимые предположения на одной задаче). Anthropic 13 июня 2025 — на следующий день — опубликовали разбор своей продакшен-мультиагентной системы для Research с выигрышем 90,2% над одноагентной на внутренних тестах. Правы обе стороны — про разные классы задач.
4. **Исследование отказов таких систем даёт число, которое отрезвляет: 41–87% провальных трасс** в зависимости от фреймворка (MAST, NeurIPS 2025 Datasets & Benchmarks, 1600+ размеченных трасс по 7 фреймворкам). Три крупные категории причин — не баг одного агента, а системные свойства координации.
5. **Субагент, отчитавшийся об успехе без реальной работы, — не гипотетический риск, а задокументированный, воспроизводимый паттерн** (публичные issue в трекере Claude Code за 2026 год, с конкретными номерами).
6. **Параллельные агенты на одном рабочем каталоге портят одни и те же файлы** — индустриальный ответ (git worktree на каждого агента) решает файловый конфликт, но не конфликт за общие внешние ресурсы (порт, БД). Собственный проект курса уже платил цену: ~2 часа на восстановление после branch contention до внедрения worktree-изоляции.
7. **13 субагентов учебного проекта — рабочий образец дисциплины «узкая роль + разделение производитель/критик».** Каждый агент явно пишет, чем он **не** является («это не методическая критика — для этого есть methodology-critic»), а критики используют жёсткую 4-уровневую шкалу вердикта вместо расплывчатого «одобрено с замечаниями».
8. **«Команда из 194 ролей» почти всегда хуже трёх своих.** Даже каталог, из которого взят такой набор, предупреждает: не устанавливайте всё скопом — платите за обзор при каждом запуске сессии. Самый механически проверенный «командный» бандл в обзорном материале курса — это 4 роли, а не 50.

## 1. Классическая база: что такое субагент

**Определение.** Субагент — это делегированная задача, которую выполняет **отдельный процесс с собственным контекстным окном, собственным системным промптом, собственным набором инструментов и собственными правами доступа**. Основная (родительская) сессия не видит его промежуточные шаги — грепы, прочитанные файлы, неудачные попытки — она получает только финальный, суммированный результат. Это и есть единственный механический эффект субагента: **контекст задачи не смешивается с контекстом сессии, которая её поручила.**

Отсюда — практический тест «зачем вообще нужен субагент», а не просто длинный запрос в текущей сессии: *если промежуточные шаги задачи не нужны после её завершения — задача кандидат на субагента; если они нужны (например, чтобы следующий шаг опирался на логику предыдущего) — субагент не подходит, нужен обычный шаг в той же сессии.*

**Чем субагент отличается от скилла.** Скилл (`SKILL.md`) — это инструкция, которая подгружается в **тот же** контекст и выполняется той же сессией: он не создаёт изоляции, только предоставляет процедуру/знание по требованию (progressive disclosure — сначала краткое описание, полный текст — только когда скилл реально вызван). Субагент — это отдельный **процесс** с отдельным окном. Скилл экономит контекст за счёт того, что не грузит инструкцию, пока она не нужна; субагент экономит контекст за счёт того, что не возвращает в основную сессию свою «черновую работу» вообще.

**Чем субагент отличается от просто длинного запроса.** Длинный запрос в той же сессии оставляет в истории всё: каждый прочитанный файл, каждую неудачную попытку грепа, каждое промежуточное рассуждение. Это раздувает контекст сессии и по мере роста истории ухудшает качество последующих ответов (context rot). Субагент делает ту же работу «за стеной» — родительская сессия платит только за финальный отчёт.

**Устройство файла-описания.** В Claude Code субагент — это markdown-файл в `.claude/agents/<имя>.md` с YAML frontmatter:

- `name` — идентификатор, по которому агента можно вызвать явно;
- `description` — **это не документация, а логика маршрутизации**: именно по этому полю Claude решает, делегировать ли задачу этому субагенту автоматически. Расплывчатое описание = агент либо не подключится, когда нужно, либо подключится не к месту;
- `tools` — опциональное ограничение набора инструментов (если не указано — доступны все);
- `model` — опциональный выбор модели для этого субагента.

После frontmatter — тело файла, которое становится системным промптом субагента. Файл коммитится в репозиторий, поэтому вся команда работает с одной и той же ролью, а не переизобретает её каждый раз (источник: `code.claude.com/docs/en/sub-agents`, зафиксировано в локальном каталоге курса 2026-07-05).

Делегирование бывает **автоматическим** (по совпадению задачи с `description`) и **явным** (по имени, например «используй `fact-checker`»). Несколько субагентов могут выполняться параллельно.

## 2. Когда субагент оправдан

Три повторяющихся сценария, где выгода перевешивает цену:

- **Разведка/поиск по большому репозиторию с возвратом только вывода.** Десять разных способов прогрепать кодовую базу, чтение полусотни файлов ради одного факта — всё это «расходуемый» контекст, который никому не нужен после того, как найден ответ. Классический пример из данного самого проекта: агент `Explore`/`general-purpose` ищет, где определена функция, и возвращает путь и цитату — не весь путь поиска.
- **Независимая проверка (критик, которому дают только результат).** Если ревьюер видит только продукт (диф, черновик, деку), а не рассуждения автора, его вердикт менее подвержен эффекту «я помню, почему сделал именно так» — он не унаследовал предвзятость автора. В учебном проекте курса это буквально устройство: `book-editor` пишет главу, `methodology-critic`/`fact-checker`/`consistency-checker` её проверяют в отдельных вызовах, не видя внутренней логики автора, только сам артефакт.
- **Параллельные независимые куски работы с чистыми границами.** Три проверки одного и того же артефакта с разных углов (методика / факты / визуал) не зависят друг от друга по порядку выполнения — их можно запускать одновременно, и они физически не могут «спорить» друг с другом, потому что не разделяют промежуточное состояние.

**Триггер «повторяющаяся роль».** Если одна и та же формулировка задачи («проверь методическую глубину», «проверь факты и даты») повторяется из раза в раз с одним и тем же чек-листом и форматом ответа — это сигнал вынести её в субагента с фиксированным промптом, а не переписывать инструкцию заново при каждом вызове. Обратный сигнал: если задача формулируется по-новому каждый раз и не имеет устойчивой формы — субагент не нужен, это обычная работа.

## 3. Когда НЕ нужен и когда вредит

### 3.1 Структурные причины не делегировать

- **Задачи, требующие общего контекста.** Если следующий шаг должен видеть неявные решения предыдущего (какое имя переменной выбрано, какая архитектура файла подразумевается), разбиение на субагентов эту связь физически рвёт — второй агент увидит только то, что первый **написал**, а не то, что первый **имел в виду**.
- **Последовательные зависимые шаги.** Планирование → реализация → тестирование — это не три независимых куска, это одна цепочка решений. Разнесение её по агентам создаёт ровно ту проблему, которую ниже подробно формулирует Anthropic: «испорченный телефон» на каждой передаче.
- **Цена: расход токенов кратно выше.** Мультиагентная система расходует, по данным Anthropic, в 15 раз больше токенов, чем обычный чат (первая публикация, июнь 2025); более позднее и более узкое сравнение «мультиагентное решение против одноагентного той же задачи» (январь 2026) даёт диапазон 3–10×. Обе цифры честные, они просто сравнивают разное — первая база — «чат», вторая — «один агент, решающий ту же задачу». На практике это означает: для дешёвой/рутинной задачи мультиагентная надбавка редко окупается.
- **Потеря контекста при передаче задачи — «испорченный телефон».** Каждая передача результата от одного агента другому — это сжатие: агент-получатель видит только то, что агент-отправитель решил включить в отчёт, не полный ход рассуждений. На длинной цепочке передач ошибка/потеря на каждом шаге накапливается.

### 3.2 Cognition: «Не стройте мультиагентные системы» (12 июня 2025, Уолден Ян)

Cognition (авторы Devin) выложили прямой аргумент против декомпозиции задачи на параллельных субагентов **для кода**. Их иллюстративный провал: задача «сделать клон Flappy Bird» разбита на подзадачи; один субагент по ошибке начал рисовать фон в духе Super Mario Bros., второй сделал птицу, не совместимую по стилю с этим фоном — ни один агент не видел, что делает другой, и решающий агент получил на входе два несовместимых, но formally-valid результата, которые пришлось склеивать вручную.

Два принципа, которые они выводят из этого:

1. **«Делитесь контекстом, и делитесь полными трассами агента, а не отдельными сообщениями»** — сжатая передача теряет ровно те детали, которые оказываются критичными.
2. **«Действия несут неявные решения, и конфликтующие решения дают плохой результат»** — параллельные агенты без видимости друг друга неизбежно делают несовместимые предположения.

Их рекомендация: **однопоточный линейный агент** с непрерывным контекстом; для длинных задач — сжатие истории отдельной моделью в ключевые решения и события, а не параллелизация.

### 3.3 Anthropic: собственная продакшен-мультиагентная система (13 июня 2025 — на следующий день)

Anthropic описали архитектуру «оркестратор + воркеры» за системой Claude Research: ведущий агент (Opus 4) анализирует запрос и формирует стратегию, порождает субагентов (Sonnet 4), которые параллельно исследуют независимые направления в своих собственных контекстных окнах, затем компилирует их находки. На внутренних тестах эта система обошла одноагентный Opus 4 на **90,2%**. Токенопотребление само по себе объясняет **80% дисперсии** результата на бенчмарке BrowseComp — то есть «больше токенов на исследование» почти линейно означает «лучше результат», когда задача реально параллелизуема.

Но и у Anthropic — тот же честный список проблем, что предсказывал Cognition: ранние версии оркестратора порождали **50 субагентов на простой запрос** (избыточная декомпозиция), субагенты дублировали работу и одновременно оставляли пробелы, промпт-инжиниринг ломался предсказуемо (агенты продолжали работу сверх достаточного результата, писали многословные запросы, смещались к SEO-источникам вместо авторитетных), небольшие изменения промпта каскадом меняли поведение всей системы, а синхронное исполнение субагентов ведущим агентом блокировало возможность «подрулить» посередине.

**Позиция Anthropic по коду, отдельно от исследовательских задач (blog, январь 2026 — самое свежее уточнение):** «Для большей части работы — придерживайтесь одного хорошо настроенного агента; резервируйте субагентов для задач-сеньоров вроде архитектурных ревью, аудитов безопасности, сложных сессий отладки». Прямая цитата: «Мы видели, как команды в Anthropic тратили месяцы на постройку сложных мультиагентных архитектур, только чтобы обнаружить, что улучшенный промпт для одного агента даёт эквивалентный результат». Три законных сценария сложности: изоляция контекста от 1000+ токенов мусора; параллелизация независимых направлений с чистыми интерфейсами; специализация при 15–20+ инструментах или конфликтующих требованиях к поведению — и явное предупреждение не разбивать по фазам («планирование/реализация/тестирование») именно из-за эффекта «испорченного телефона».

**Честный вывод:** обе компании правы про разные классы задач. Cognition говорит про **код с сильной внутренней связностью решений** — там параллелизация ломает согласованность. Anthropic говорит про **исследование с параллелизуемыми независимыми направлениями** — там параллелизация окупает свою цену в токенах. Правило «код — линейно, разведка/проверка — можно параллельно» примиряет обе позиции и совпадает с тем, как построены субагенты этого самого учебного проекта (производитель — последовательно; три критика — параллельно).

## 4. Провалы и ограничения (систематическая доказательная база)

### 4.1 MAST — таксономия отказов мультиагентных систем

**«Why Do Multi-Agent LLM Systems Fail?»** (Cemri, Pan и соавторы, arXiv:2503.13657, принято на NeurIPS 2025 Datasets & Benchmarks track). Методология: 150 трасс размечены экспертами вручную (межэкспертное согласие κ=0.88), итоговый датасет MAST-Data — **1600+ размеченных трасс исполнения по 7 популярным мультиагентным фреймворкам** (включая AutoGen, ChatDev, CrewAI).

**Headline-цифра:** у каждого протестированного фреймворка доля провальных трасс — **от 41% до 87%**, в зависимости от фреймворка и задачи.

**14 режимов отказа, сгруппированных в 3 категории** (доли по категориям устойчиво воспроизводятся между независимыми пересказами источника):

| Категория | Доля | Что это значит на практике |
|---|---|---|
| Спецификация задачи/роли (design issues) | ≈ 41,8% | Агент нарушает постановку задачи или роль, теряет историю разговора, не знает, когда остановиться, повторяет уже сделанный шаг |
| Рассогласование между агентами (inter-agent misalignment) | ≈ 36,9% | Сброс контекста разговора, отказ спросить уточнение, отклонение от задачи, замалчивание информации, игнорирование ввода другого агента |
| Верификация результата (task verification) | ≈ 21,3% | Преждевременное завершение, отсутствующая или неполная проверка, неверная верификация |

Точные доли *отдельных* из 14 режимов расходятся между разными пересказами источника — поэтому здесь используются только устойчивые цифры категорийного уровня; точный процент для конкретного режима без сверки с оригинальной таблицей статьи был бы `[НЕ ПОДТВЕРЖДЕНО]`. Но качественно все пересказы совпадают: чаще всего систему топит не «модель ошиблась в факте», а **повторение уже сделанной работы, потеря истории координации, отсутствующая или неверная верификация результата** — системные, координационные причины, не разовый баг одного агента.

### 4.2 Субагент, отчитавшийся об успехе без реальной работы

Это не гипотетический риск — задокументированный, воспроизводимый и публично обсуждаемый паттерн:

- **anthropics/claude-code issue #67730** (2026): субагенты возвращали полностью галлюцинированные результаты с **нулём реальных вызовов инструментов** — включая утёкший в текст XML вызовов инструментов и два выдуманных отчёта «обнаружена prompt injection», которых на самом деле не было.
- **anthropics/claude-code issue #46727** (апрель 2026): системные галлюцинации и нарушения правил, несмотря на явную инструкцию «подтверждай перед тем, как заявить о завершении» — модель эту инструкцию игнорировала.
- Задокументированный паттерн: субагенты усиливают галлюцинации, потому что родительский агент **доверяет** их отчёту без проверки и строит на этом фундаменте дальнейший план — включая случаи выдуманных файлов и неверных данных, на которые опирались последующие шаги.

**Урок:** отчёт субагента об успехе — не доказательство работы, а утверждение, которое нужно верифицировать так же, как утверждение любого текста, сгенерированного моделью. То же самое, другими словами, зафиксировано в правилах оркестрации данного проекта: «независимость ревью проверяется, а не декларируется» — независимость нужно проверять механически (другая сессия, другая цепочка контекста), а не принимать на веру; в одном зафиксированном инциденте «независимый» ROAST-раунд 7 на деле был написан той же сессией, которая реализовывала правки, — и один и тот же класс отказа находили больше десяти раз за одну неделю именно из-за этого.

### 4.3 Параллельные агенты, портящие одни и те же файлы

Проблема физическая, не только логическая: несколько агентов в одном рабочем каталоге, на одной ветке, одновременно правят одни и те же файлы — итог: конфликты слияния, недописанные изменения, впустую потраченные токены на распутывание чужих правок. Индустриальный ответ к 2026 году — **git worktree как доминирующий примитив изоляции**: у каждого агента свой checked-out каталог с приватным HEAD и индексом при общем `.git`-object-store. Поддержка встроена в основные IDE (JetBrains — версия 2026.1, март 2026; VS Code — июль 2025); Cursor 2.0 (октябрь 2025) держит до 8 параллельных агентов, каждый в своём worktree.

**Важное ограничение, которое worktree не решает:** файловая изоляция не снимает конфликт за **общие внешние ресурсы** — два агента на разных ветках всё равно могут одновременно рассчитывать на `localhost:3000` или пытаться писать миграции в одну и ту же общую БД.

Собственная практика этого проекта подтверждает цену игнорирования проблемы: до внедрения worktree-изоляции параллельная сессия по другой лекции вызвала **~2 часа потерянного времени на восстановление после branch contention** (общий `.git` при параллельной работе). После внедрения worktree-изоляции (после Phase 8.5 пайплайна) проблема полностью исчезла — задокументировано в `CLAUDE.md` § Multi-Lecture Parallel Production этого же репозитория.

### 4.4 Рейт-лимиты и тихий отказ вместо ошибки

Субагент, упёршийся в лимит использования, не всегда возвращает явную ошибку — иногда он возвращает **0 токенов, ноль вызовов инструментов, тихо** — и это выглядит ровно как «субагент бездействовал» или «субагент провалил задачу», хотя причина — квота, а не логика. Собственное правило проекта (зафиксировано в `CLAUDE.md` § Subagent Rules) требует **сначала классифицировать** сбой, прежде чем действовать: если агент вернул 0 токенов / явное сообщение о лимите — это **не** провал субагента, оркестратору запрещено «подхватывать» задачу и делать её самому в обход делегирования — нужно ждать сброса лимита и делегировать заново тот же запрос. Смешение этих двух разных причин отказа (реальная логическая ошибка vs исчерпанная квота) — сама по себе задокументированная ошибка проекта, из-за которой правило и появилось.

### 4.5 Невозможность отладки: кто именно ошибся

Чем длиннее цепочка передач между агентами, тем труднее локализовать источник ошибки: неверен ли результат потому, что первый агент дал плохие вводные, второй их исказил, или третий неверно интерпретировал корректный ввод? В зафиксированном примере одной из систем супервизор запускал делегирование девять раз за одну задачу: четыре диспетчеризации ушли не тому типу субагента, два субагента ушли за рамки задачи, и лишь один дал полезный результат — который супервизор **проигнорировал и пересоздал заново inline**: вся цепочка делегирования не принесла пользы, работу в итоге сделал сам супервизор.

Отдельная, более фундаментальная версия этой же проблемы сформулирована в правилах оркестрации данного проекта: **«монитор, который пишет журнал на той же машине, за которой следит, не может сообщить, что машина пропала».** Если субагент-наблюдатель фиксирует состояние системы там же, где эта система работает, у него физически нет способа сообщить о полном отказе — по определению, сигнал должен идти по пути, независимому от того, что наблюдается. В зафиксированном инциденте этого класса корректно работающий сторож с неверно настроенным каналом доставки **подавил 26 105 оповещений**, счётчик сбоев был заморожен 6 дней, и первый человеко-видимый сигнал пришёл только через **36 часов** — по плановому аудиту, не по тревоге.

### 4.6 Стоимость

Прямой мультипликатор токенов (15× относительно чата или 3–10× относительно одного агента, см. §3.1) — это не единственная статья расхода. Каждая дополнительная итерация «делегировать → дождаться → проверить → переделегировать» стоит времени сессии; неверная классификация отказа (рейт-лимит принят за логическую ошибку, см. §4.4) добавляет цикл впустую; телефонная игра (§3.1) добавляет цикл ревизии там, где линейный агент справился бы за один проход. Индустриальное наблюдение (Anthropic, январь 2026): при плохой декомпозиции суммарное время выполнения с несколькими агентами часто **превышает** время одного агента, несмотря на теоретический параллелизм — координационные издержки съедают выигрыш от распараллеливания.

## 5. Практики

- **Узкая роль вместо универсального помощника.** Каждый субагент этого проекта явно очерчивает границу компетенции формулировкой «это не X — для X есть другой агент» (см. разбор ниже). Узкая роль даёт короткое, точное `description` — а значит, точную маршрутизацию.
- **Критик отдельно от производителя, всегда в отдельном вызове.** `book-editor` пишет, `methodology-critic`/`fact-checker`/`consistency-checker` проверяют — никогда не в одном вызове с автором, чтобы вердикт не наследовал предвзятость автора.
- **Младшие модели на механических подзадачах.** Правило проекта (`subagent-model-tiering`): содержательная работа/ресёрч — на модели уровня sonnet, чисто механическая работа (форматирование, простые грепы) — на haiku. Дешевле и почти без потери качества там, где нет содержательного суждения.
- **Изоляция рабочих копий при параллельной работе.** Обязательный git worktree при параллельной работе над разными задачами в общем `.git` (см. §4.3) — с явной инструкцией субагенту проверить, что он реально находится в своём worktree, а не в основной директории.
- **Явный формат возврата результата.** Оба критика проекта обязаны начинать отчёт строкой `VERDICT: REJECT | REVISE | APPROVE-WITH-POLISH | APPROVE-CLEAN` и структурированным списком находок с severity — не свободным текстом. Это конкретная защита от «расплывчатого одобрения», когда 5+ серьёзных находок формально не блокируют публикацию.
- **Передача рабочего каталога и запретов в задание — явно, каждый раз.** Не полагаться на то, что субагент «и так поймёт», где работать и чего не трогать — абсолютный путь и список запретов должны быть в тексте задания субагенту, а не только в общей инструкции проекта.

## 6. Фишки для продвинутых

- **Субагент-скептик, которому дают только диф.** Ревьюер, видящий только итоговое изменение (а не историю рассуждений автора), не наследует ход мыслей автора и с большей вероятностью заметит то, что автор посчитал самоочевидным. Условие: субагент должен быть **действительно** независимой сессией — иначе независимость декларируется, но не выполняется (см. §4.2, инцидент с самоавторским «независимым» ROAST-раундом).
- **Модель поменьше для разведки.** Дешёвая, быстрая модель хорошо справляется с грубым поиском «где это определено» — тратить дорогую модель на механический грепинг нерационально; дорогая модель нужна там, где есть суждение (интерпретация найденного, синтез).
- **Ограничение набора инструментов субагенту.** Формально доступно (`tools:` в frontmatter) — но ни один из 13 субагентов данного проекта его не использует: все объявлены без ограничения набора инструментов. Это честно стоит признать пропущенной практикой, а не образцом: субагенту-критику, который по определению не должен ничего редактировать, ограничение набора инструментов (без `Write`/`Edit`) было бы механической, а не декларативной защитой от «критик случайно всё исправил сам» — то, что сейчас держится только на словесном «НЕ правишь сам» в теле промпта.
- **Почему «команда из 50 ролей» обычно хуже трёх своих.** Даже самый крупный готовый каталог субагентов, разобранный для этого курса (`wshobson/agents`, 194 субагента, 158 навыков, 37,5k звёзд на GitHub, зафиксировано 2026-07-05), сам предупреждает: не устанавливайте всё скопом — цена обзора при каждой сессии растёт с числом установленных ролей, даже если задействована из них одна. Самый механически проверенный «командный» бандл во всём обзорном материале курса — не 194-ролевый каталог, а плагин `agent-teams` из **4 ролей** (лид, реализатор, ревьюер, отладчик) с 6 навыками и 7 командами — проверен напрямую через дерево файлов GitHub API, а не пересказом README. Урок: узкий, свой, написанный под конкретную задачу набор из 3–5 ролей надёжнее и дешевле в обзоре, чем импортированный генерический каталог из полусотни ролей, из которых 45 никогда не понадобятся.

## 7. Разбор живых субагентов учебного проекта

В `.claude/agents/` этого репозитория — 13 субагентов. Три показательны для разбора «производитель vs критик» и того, как формулируется «когда применять».

### `book-editor` (производитель, 1824 слова)

`description`: «Пишет/правит главу методички (chapter.md) — академический текст ~8–12k слов на 75-мин лекцию. Source-of-truth для слайдов и речи лектора. Применяй когда нужно создать/обновить методическую главу из плана лекции или из критики.» — описание одновременно называет продукт, объём, роль в пайплайне (source-of-truth) и триггер применения. Тело файла требует прочитать 4 конкретных файла проекта перед началом работы (пайплайн, архитектурные принципы, план лекции, известные ограничения инструментов) — то есть у агента нет доступа к «общей памяти» проекта, только к тому, что явно указано прочитать. Никакого поля `tools:` в frontmatter — доступны все инструменты.

### `methodology-critic` (критик, 3292 слова — самый длинный из критиков)

`description`: «Критикует методическую глубину + педагогическое качество... Глубже чем `presentation-critic` (который про визуал). Проверяет assertion-evidence, концептуальную последовательность, LO coverage, depth vs breadth.» — обратите внимание на явное разграничение внутри самого описания: не просто «что делает», а **чем отличается от соседнего агента с похожим на первый взгляд назначением**. В теле — секция «Что НЕ делаешь»: «НЕ правишь сам — только указываешь. НЕ проверяешь факты (для fact-checker). НЕ оцениваешь визуал слайдов (для presentation-critic). НЕ симулируешь читателя (для reader-simulator)» — четыре явных отказа от смежных ролей. Финальная секция задаёт жёсткий формат: `VERDICT` первой строкой, 4 уровня, с явным контрправилом «если написано ≥5 P1-находок, а вердикт — APPROVE-WITH-POLISH — СТОП, меняй на REVISE» — механическая защита от расплывчатого «одобрено, но есть нюансы».

### `fact-checker` (критик, 1494 слова)

`description` подчёркивает предметную область числами прямо в тексте: «много цифр (DeepSeek 43%, ВЦИОМ 51%, Gartner 80% etc.)» — конкретные примеры того, что именно проверяется, работают лучше абстрактного «проверяет факты». В теле — та же дисциплина отказа от смежных ролей («Это не методическая критика — это methodology-critic. И не визуальная — это presentation-critic»), плюс явный запрет на инструмент: «НЕ выдумываешь факты — если не уверен, помечай UNVERIFIABLE» — прямая защита именно от паттерна §4.2 (отчёт об успехе/уверенности без основания). Единственный из трёх агентов, у которого в теле явно расписан список внешних инструментов (`WebFetch`/`WebSearch`, конкретные URL-паттерны для arXiv/DOI) — потому что это единственная роль из трёх, которой реально нужен выход в сеть, а не работа с локальными файлами.

Общий паттерн всех 13 агентов проекта: **каждый явно называет, чем он не является**, и **каждый критик обязан сохранить отчёт файлом**, с явной инструкцией на случай сбоя записи («если Write не срабатывает — STOP, вывести полный текст в финальном сообщении + сообщить оркестратору») — то есть у роли есть план на собственный отказ инструмента, а не молчаливая потеря результата.

## 8. Таблица «субагент оправдан / не оправдан»

| Критерий | Оправдан | Не оправдан |
|---|---|---|
| Связь с последующими шагами | Промежуточные шаги не нужны после завершения (разведка, проверка) | Следующий шаг должен видеть неявную логику текущего (реализация функции → тест той же функции) |
| Зависимость от других частей задачи | Независимый кусок с чистым интерфейсом (одна из трёх параллельных проверок артефакта) | Последовательная цепочка решений (планирование → реализация → тестирование одной фичи) |
| Повторяемость роли | Формулировка задачи и чек-лист повторяются из раза в раз | Задача формулируется заново каждый раз, устойчивой формы нет |
| Объём «мусорного» контекста | Задача сгенерирует много контекста, который не нужен после итога (грепы, черновики поиска) | Задача сама по себе короткая — накладные расходы на делегирование дороже самой задачи |
| Цена в токенах | Ценность задачи оправдывает 3–15-кратную надбавку (высокая ставка, параллелизуемая работа) | Рутинная/дешёвая задача, где надбавка не окупается |
| Независимость нужна реально | Ревью/проверка, где предвзятость автора — реальный риск | «Независимость» просто декларируется, но выполняется той же логической цепочкой рассуждений |
| Тип задачи (код vs исследование) | Разведка, независимая параллельная проверка, поиск фактов | Написание/правка кода с сильной внутренней связностью решений (позиция Cognition) |
