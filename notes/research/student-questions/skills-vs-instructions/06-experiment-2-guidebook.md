## 1. Что проверялось

Уточнённый вопрос владельца курса: длинный справочник (дизайн-гайд, не короткая процедура из
первого раунда) можно подключить **как скилл** или **как документ в `docs/` + строка-указатель в
always-on-файле** (`AGENTS.md`). Что надёжнее приводит к тому, что исполнитель реально открывает и
применяет справочник — и не решает ли здесь больше формулировка указателя/описания, чем выбор между
двумя механизмами.

Артефакт раунда — `docs/design-guide.md`, дизайн-гайд вымышленного проекта «Волна», **2216 слов**
(`wc -w`, 28 545 байт). В него вплетены шесть нормативных правил R1–R6 (не чек-листом — живут в
своих разделах: шапка, палитра, состояния, типографика, доступность, конец документа). Задачи —
две: **T1** («Карточка товара», написать документ-спецификацию компонента) и **T2** («Модальное окно
подтверждения удаления», то же для другого компонента). Ни одна задача не упоминает гайдбук, слово
«конвенция» или «правила проекта» — только саму работу.

Семь плеч, 25 прогонов (бюджет распределён неравномерно — больше прогонов там, где решается
различие):

| Плечо | Механизм | Что варьируется | Прогонов (T1/T2) |
|---|---|---|---|
| **S2** | Скилл `skills/design-guide-good` | `description` явно называет триггеры (вёрстка, цвет, типографика, состояния) | 5 (3/2) |
| **S1** | Скилл `skills/design-guide-vague` | `description: "Навык дизайна."` — расплывчатое | 3 (2/1) |
| **P3** | `docs/` + `AGENTS-P3.md` | Указатель с условием срабатывания («если задача касается вёрстки, палитры, типографики или состояний элементов — сначала прочитай...») | 3 (2/1) |
| **P2** | `docs/` + `AGENTS-P2.md` | Указатель-императив, полный путь («перед любой работой над дизайном прочитай `.../design-guide.md`») | 5 (3/2) |
| **P1** | `docs/` + `AGENTS-P1.md` | Расплывчатый указатель, неполный путь — **дословная формулировка владельца**: «Смотри `docs/`, там инструкции по тому, как делать дизайн» | 5 (3/2) |
| **N** | `docs/` есть, указателя нет | Контроль снизу: справочник существует в репозитории, `AGENTS-N.md` о нём не говорит вообще | 2 (1/1) |
| **F** | Весь гайдбук вклеен в always-on | Верхняя граница по цене контекста: `AGENTS-F.md` несёт полный текст гайда внутри себя | 2 (1/1) |

Тела скиллов S1/S2 одинаковы — отличается только `description`. Тела always-on-файлов
P1/P2/P3/N — одинаковые 12–16 строк обычных проектных правил (сборка, lint, ветки, секреты), разница —
одна строка-указатель (в N её нет вовсе, вместо неё — другое правило про ревью PR, то есть файл не
короче, просто без упоминания гайда).

## 2. Почему канарейки, а не число вызовов инструментов

Слабость первого раунда (`04-own-experiment.md`): «открыл документ или нет» выводилось косвенно —
по числу вызовов инструментов харнеса и по отсутствию формальных признаков в тексте. Это работает,
но оставляет зазор: агент мог угадать правдоподобное значение без открытия файла, и отличить
«угадал» от «прочитал» по тексту одного ответа нельзя.

Второй раунд закрывает это: значения R1, R2, R4, R5, R6 в гайдбуке подобраны нарочно нестандартными,
так что их совпадение в выходном файле — прямая улика, а не удачное совпадение с типовой практикой:

- **R1** — ровно `**Design-guide:** DG-v1` второй строкой документа (версия-метка, не общепринятый формат);
- **R2** — цвета только токенами `P-INK`/`P-SEA`/`P-GOLD`, hex запрещён (большинство моделей по
  умолчанию пишут hex-коды, не вымышленные токены);
- **R4** — ровно четыре размера шрифта, в пунктах: 34/26/19/15 (нестандартная шкала; типовая
  вёрстка использует 12/14/16/18/24 или похожие px-значения);
- **R5** — минимальный контраст `4.8:1` (нестандартный — отраслевой ориентир 4.5:1, модель, не
  открывшая документ, напишет именно 4.5:1 или не укажет число вовсе);
- **R6** — маркер конца документа `<!-- DG-v1 -->` (комментарий, который невозможно вывести логически).

Метрика **«открыл»** = сработала хотя бы одна из этих пяти канареек (R1 ∨ R2 ∨ R4 ∨ R5 ∨ R6).
**R3** (порядок состояний: покой → наведение → нажатие → недоступно) из канареек исключён
сознательно — такой порядок частично угадываем по логике UI без чтения документа, значит он не
доказывает факт открытия, даже если совпадает.

## 3. Предрегистрация — правило решения до прогонов

Правило решения (`_exp2/PRE-REGISTRATION.md`) записано и закоммичено **до** запуска прогонов —
коммит `71d5845d` («стенд второго раунда + ПРЕДРЕГИСТРАЦИЯ правила решения до прогонов»); сырые
данные и расчёт появились отдельным коммитом **после** — `1cfa37fb` («25 прогонов отработали, сырые
данные + расчёт по предрегистрации»). Порядок коммитов в `git log` — это и есть гарантия того, что
правило не подгонялось под результат постфактум.

Гипотеза владельца, зафиксированная заранее: разница между хорошей и плохой **формулировкой**
(`description` скилла / текст указателя) больше, чем разница между **механизмами** (скилл против
`docs/` + указатель), потому что оба механизма делают одну и ту же работу — дают модели повод
открыть документ.

Формулы:

- `D_мех = | S2 − среднее(P2, P3) |` — скилл с нормальным описанием против указателей, тоже
  нормально сформулированных.
- `D_форм = (W1 + W2) / 2`, где `W1 = среднее(P2, P3) − P1` (хороший указатель против расплывчатого)
  и `W2 = S2 − S1` (хорошее описание скилла против расплывчатого).
- **Порог различимости — 0,25** доли открытия. Обоснование: при 3–5 прогонах на плечо один
  отдельный прогон меняет долю на 0,20–0,33, значит разница меньше 0,25 неотличима от одного
  случайного исхода.

Пять исходов перечислены заранее в предрегистрации (подтверждена гипотеза / не подтверждена /
неразличимо при этом N / доминирует само наличие указателя / дословная формулировка владельца не
срабатывает) — без права добавить шестой после того, как числа стали известны.

условия) так же, как на T1.

## 5. Расчёт по предрегистрации

Из `_exp2/RAW-decision.txt`:

```
плечо  открыл
S2     5/5 = 1.00
P2     2/5 = 0.40
P3     3/3 = 1.00
S1     0/3 = 0.00
P1     0/5 = 0.00
N      0/2 = 0.00
F      2/2 = 1.00

D_мех  = |S2 − среднее(P2,P3)| = |1.00 − 0.70| = 0.30
W1 (указатель: хороший − расплывчатый) = 0.70 − 0.00 = 0.70
W2 (скилл: хорошее описание − расплывчатое) = 1.00 − 0.00 = 1.00
D_форм = (W1 + W2)/2 = 0.85

D_форм − D_мех = 0.55   (порог 0,25)
```

**Исход 1 — гипотеза владельца подтверждена** (0,55 ≥ 0,25). Разница между хорошей и плохой
формулировкой (0,85) почти втрое больше разницы между механизмами (0,30).

Проверка остальных четырёх заранее перечисленных исходов:
- Исход 2 (механизм решает больше формулировки) — не выполнен, `D_мех < D_форм`.
- Исход 3 (неразличимо при этом N) — не выполнен, разница 0,55 заметно выше порога 0,25.
- Исход 4 (наличие любого указателя доминирует: все из S1/S2/P1/P2/P3 ≥ 0,80, у N = 0) — **не
  выполнен**: S1 = 0,00, P1 = 0,00, P2 = 0,40 — три из пяти плеч с хоть каким-то указателем ниже
  0,80.
- Исход 5 (дословная формулировка владельца не срабатывает) — **подтверждён**: P1 = 0,00 при
  N = 0,00 и P3 = 1,00. Указатель, буквально процитированный владельцем в постановке вопроса,
  неотличим по результату от полного отсутствия указателя.

## 6. Побочный результат: прочитал ≠ соблюдает

Метрика «открыл» и метрика «правил соблюдено» измеряют разные события, и разница между ними —
результат, которого не предполагала гипотеза владельца.

**R3 и R4 не выполнены ни в одном из 25 прогонов, независимо от плеча.** Пройдя построчно по всей
таблице §4: столбец R3 — «нет» у всех 25 файлов; столбец R4 — «нет» у всех 25 файлов. Это включает
**F** — плечо, где весь текст гайдбука присутствует в контексте с первого токена сессии, без
необходимости что-либо открывать. Наличие текста не конвертировалось в соблюдение этих двух правил
ни разу.

Максимум по сумме правил, достигнутый хоть одним прогоном — **4/6** (все 5 прогонов S2). Ни один из
25 прогонов не дал 5/6 или 6/6: правила R3 (порядок состояний ровно словами «покой → наведение →
нажатие → недоступно») и R4 (ровно четыре размера шрифта 34/26/19/15, не три и не пять) требуют не
просто открыть документ, а воспроизвести точную форму — и этого открытие само по себе не дало даже
при полном тексте в контексте (F).

Средние по правилам у трёх «открывающих» плеч различаются и упорядочены так же, как доля открытия,
но не совпадают с ней количественно:

| Плечо | Доля открытия | Правил соблюдено (ср.) |
|---|---|---|
| S2 (скилл, осмысленное описание) | 1,00 | **4,00/6** |
| F (гайдбук целиком в always-on) | 1,00 | **3,00/6** |
| P3 (указатель с условием) | 1,00 | 2,67/6 |

При одинаковой доле открытия (1,00 у всех трёх) скилл с осмысленным описанием даёт на 1 правило из
6 больше, чем весь гайдбук целиком в always-on. Вывод: **открыть документ и выполнить его —
разные события, и второе не следует из первого автоматически** даже при идентичной доле открытия.
Вероятное объяснение по тексту самих файлов (см. образцы в `_exp2/out/S2/`, `_exp2/out/F/`): задача
не требовала размера 34pt (заголовок экрана) внутри спецификации одного компонента — ни карточка
товара, ни модальное окно сами по себе не нуждаются в этом уровне иерархии, поэтому R4 физически не
может быть выполнен без того, чтобы модель добавила неиспользуемый размер искусственно; а R3 падает
на форме — модели пишут состояния списком с жирными подзаголовками («**Покой.** ... **Наведение.**
...»), по смыслу верно и в правильном порядке, но не буквальной строкой `покой → наведение →
нажатие → недоступно`, которую требует правило.

## 7. Цена — по `RAW-tokens.csv`

Средние токены на прогон по плечу (пересчитаны из `_exp2/RAW-tokens.csv`, совпадают с
`RAW-decision.txt`):

| Плечо | Токены (ср.) | n |
|---|---|---|
| S2 | 65 990 | 5 |
| P3 | 65 581 | 3 |
| F | 64 938 | 2 |
| P2 | 60 891 | 5 |
| N | 59 542 | 2 |
| P1 | 58 352 | 5 |
| S1 | 58 076 | 3 |

**С базой — по факту открытия, не по плечу.** Разбивка 25 прогонов не по названию плеча, а по
тому, открыл ли конкретный прогон гайдбук (столбец «Открыл» из §4), даёт более честное сравнение,
потому что P2 внутри себя смешивает оба исхода:

- Прогоны, которые **открыли** гайдбук (12 из 25: все 5 S2, 2 из 5 P2, все 3 P3, все 2 F) —
  средняя стоимость **65 476 токенов**.
- Прогоны, которые **не открыли** (13 из 25: все 3 S1, все 5 P1, 3 из 5 P2, все 2 N) — средняя
  стоимость **58 491 токен**.
- Разница: 65 476 − 58 491 = **6 985 токенов, +11,9% к базе «не открыл»** (58 491).

Это — цена одного дополнительного вызова чтения файла на ~2200 слов внутри одной сессии: порядка
+12% к стоимости сессии, в которой документ не открывался вовсе.

**Честное наблюдение про F.** Сравнивая **F** (весь гайдбук вклеен в always-on, не нужно ничего
открывать) с прогонами, которые читали его **по требованию** (S2 + P3 + два прогона P2, 10 прогонов,
средняя 65 584 токена): F стоит **64 938** — на 1% **дешевле**, не дороже (разница статистически не
значима при n=2 против n=10, но направление однозначное: не дороже). **Для справочника на 2216 слов
«весь текст в always-on» стоит за один прогон примерно столько же, сколько чтение по требованию** —
разница в среднем около одного вызова инструмента (вставить файл в промпт против вызвать инструмент
чтения), не порядок величины.

Разница возникает не в одном прогоне, а **в масштабе**: F платит свои +12% (относительно
«не открыл») **в каждой сессии, на каждом ходу, где дизайн не нужен вовсе** — always-on-файл
грузится целиком при старте независимо от задачи. P1/P2/P3 платят эти же +12% **только в той доле
сессий, где задача реально касается дизайна и формулировка указателя сработала**; сессии с другими
задачами (бэкенд, тесты, инфраструктура) эту цену не платят вообще, потому что указатель — пассивная
строка текста, пока модель не решит её исполнить, а не содержание документа.

**Сопоставление с первым раундом.** В `04-own-experiment.md` §5 раздутый файл на **62 КБ**
(инструкция «прочитай целиком») стоил **+31,8…+35,5%** токенов относительно минимального указателя,
при идентичном результате по форме в условии, где задача называла процедуру явно. В этом раунде F
(весь текст гайда внутри always-on-файла, 29 590 байт / 2216 слов самого гайда) стоит **+11,1%**
относительно базы «не открыл» (58 352 у P1 как ближайший аналог «того же always-on-слоя без текста
гайда внутри» — см. ниже) — разница в разы меньше. Разница объясняется **размером файла, а не
механизмом**: раздутый файл первого раунда (62 КБ) больше гайдбука этого раунда (28,5 КБ, то есть
≈2,2 раза) почти во столько же раз, во сколько различаются ценовые эффекты (33% против 11%, то есть
≈3 раза — направление совпадает, не линейная пропорция при n=2 против n=2…5). Механизм в обоих
случаях один («весь текст — в контексте каждого запроса сессии безусловно»); разный эффект —
следствие разного объёма текста, который этот механизм тащит.

## 8. Ограничения

Жёстко, по аналогии с `04-own-experiment.md` §8 — это не формальность, а условие, без которого
числа выше легко переобобщить:

1. **25 прогонов, одна модель (Haiku), один справочник, короткие однозадачные сессии.** Это
   показывает **направление**, не размер эффекта. Статистический тест (доверительный интервал,
   p-значение) не проводился и при таком N **невозможен**. Любая формулировка вида «плечо X на
   Y% надёжнее» в строгом статистическом смысле была бы псевдоточностью — числа в этом отчёте — это
   доли и средние по малым выборкам (n=2…5 на плечо), а не оценка параметра генеральной совокупности.
2. **Плечи со скиллом — проба механизма активации (метаданные в контексте, тело по требованию), не
   вендорская фича Agent Skills целиком.** Контракт полей, лимиты символов листинга, поведение
   после компакции контекста — не воспроизводились; тестировался принцип progressive disclosure,
   а не конкретная реализация платформы.
3. **Плечо F — «большой файл, прочитанный по велению» (точнее, вклеенный в тело always-on-файла,
   который субагенту явно передаётся целиком), а не автозагрузка харнесом при старте сессии** в
   том смысле, в каком реальный `CLAUDE.md`/`AGENTS.md` грузится кодом оболочки. Перенос выводов
   про F на буквальный always-on-механизм платформы делается с этой оговоркой.
4. **Каждый прогон — свежая сессия со своим контекстным окном.** Остаточного контекста между
   прогонами одного плеча нет; единственный общий канал — файловая система репозитория. Прогоны
   одного плеча не влияют друг на друга и не обучаются на предыдущих.
5. **Плечо N в принципе могло наткнуться на `_exp2/docs/` само**, листая репозиторий в рамках
   задачи — это не изъян измерения, а честная часть условия (так бывает и в реальной работе).
   По данным — **не наткнулось ни разу** (0/2), но при другом N или другой модели эта доля не
   гарантированно останется нулевой.
6. **Канарейки доказывают факт открытия файла, не качество результата.** Прогон может открыть
   гайдбук и всё равно не выполнить конкретное правило (см. §6) — метрика «открыл» и метрика
   «правил соблюдено» измеряют разные, не взаимозаменяемые события.

## 9. Как воспроизвести

Из корня репозитория:

```bash
# Проверка R1-R6 по всем 25 файлам — таблица как в §4
python3 notes/research/student-questions/skills-vs-instructions/_exp2/check2.py

# Сверка сырых чисел и расчёта по предрегистрации
cat notes/research/student-questions/skills-vs-instructions/_exp2/RAW-compliance-full.txt
cat notes/research/student-questions/skills-vs-instructions/_exp2/RAW-decision.txt

# Пересчёт стоимости токенов (как в §7)
column -s, -t notes/research/student-questions/skills-vs-instructions/_exp2/RAW-tokens.csv

# Прямой осмотр артефактов — например, почему F не проходит R3/R4 при полном тексте в контексте
cat notes/research/student-questions/skills-vs-instructions/_exp2/out/F/F-T1-1.md
cat notes/research/student-questions/skills-vs-instructions/_exp2/out/S2/S2-T1-1.md

# Правило решения, записанное до прогонов
cat notes/research/student-questions/skills-vs-instructions/_exp2/PRE-REGISTRATION.md

# Порядок коммитов — предрегистрация раньше данных
git log --oneline -- notes/research/student-questions/skills-vs-instructions/_exp2
```

**Чего в `_exp2/` нет:** точный текст промпта делегирования каждому из 25 субагентов не сохранён
отдельным логом — воспроизведены артефакты-входы (`docs/design-guide.md`, `always-on/AGENTS-*.md`,
`skills/*/SKILL.md`) и артефакты-выходы (`out/*/*.md`). Повторный прогон потребует восстановить
формулировку задачи T1/T2 по структуре выходных файлов, а не копированием несуществующего лога.
