## Главный блокер — отсутствие `N8N_API_KEY`

В этой сессии (изолированный git-worktree, не главная интерактивная сессия, где владелец
поднимал стенд С7 2026-10-12) не нашлось ни переменных окружения, ни файла
`~/.n8n-lab.env`, ни какого-либо другого источника `N8N_API_URL`/`N8N_API_KEY`. Искал:

- `env | grep -i n8n` — пусто.
- `~/.n8n-lab.env` — не существует (проверено по точному пути, на который ссылается
  `sem-07/stend/sborka.py` и `sem-07/stend/README.md`).
- Единственный найденный в репозитории документ по теме —
  `attachments/1791813016-2cd010ed-n8n-lab-agent-handover.md` (и его точная копия с
  суффиксом «(1)») — это **шаблон**, не заполненный секретами: поле `N8N_API_KEY` в нём
  буквально `<PASTE: Settings → n8n API → Create an API key>`, и сам документ говорит
  прямо: «Nothing in `workain/infra` can mint the API key for you... this repo commits
  `terraform.tfstate`, so any key it provisioned would be a key published to git history».
  То есть отсутствие ключа здесь — не недосмотр, а то, как эта инфраструктура устроена
  намеренно.
- Прямая проверка: `curl https://n8n.lessons.tellian.io/api/v1/workflows` без ключа —
  **живой ответ `401`**. Сам стенд работает и отвечает; закрыт именно управляющий API, как
  и должно быть без ключа.

**Следствие.** Все шесть стадий, описанных в `sborka.py`, невозможно ни создать, ни
опубликовать, ни прогнать на этом стенде из этой сессии. Это касается ВСЕХ четырёх кейсов

## Что сделано вместо этого — честно, по каждому пункту задания

### Generated, not deployed: `sborka.py` + шесть `stage-*.json`

`sborka.py` написан по образцу `sem-07/stend/sborka.py` (та же форма `api()`, тот же флаг
`--push`) и **достраивает** `sem-07/stend/student.json` — не переписывает его. Запущен
**без** `--push` (сеть не нужна для этого режима):

```
python3 sborka.py
  stage-1-before.json — 10 узлов (НЕ прогнано)
  stage-1-after.json — 10 узлов (НЕ прогнано)
  stage-2.json — 11 узлов (НЕ прогнано)
  stage-3a-model.json — 6 узлов (НЕ прогнано)
  stage-3b-code.json — 6 узлов (НЕ прогнано)
  stage-4.json — 11 узлов (НЕ прогнано)
```

Все шесть файлов — валидный JSON (проверено `json.load` на каждом), построены по образцу
уже рабочих узлов этого же стенда (`student.json`, `sem-07/stend/sborka.py`), но **ни один
не проверен импортом в настоящий n8n** — это не то же самое, что «настоящий прогон», и не
выдаётся здесь за него. Возможные неточности в точных именах параметров/`typeVersion`
узлов (`Telegram`, `lmChatOllama`, `chainLlm`, `readWriteFile`) — риск, который снимается
только реальным импортом на стенде, не этой сессией.

### `student.json` не тронут

Правило соблюдено буквально: `sborka.py` читает `sem-07/stend/student.json` только на
чтение (`json.loads(... .read_text())`), копирует узлы (`json.loads(json.dumps(...))`,
не ссылку) и ни разу не записывает обратно в файлы С7. `git status` подтверждает: в
`sem-07/stend/` изменений нет.

### Секреты — ни один не попал в файл

Токен Telegram-бота, данный оркестратором в этом цикле, использован **ровно два раза**,
оба раза напрямую через Telegram Bot API, никогда — как параметр узла n8n и никогда — в
записи в файл:

```
curl https://api.telegram.org/bot<TOKEN>/getMe
→ {"ok":true,"result":{"id":8961470896,"is_bot":true,"first_name":"n8n demo",
   "username":"n8ndemo_study_bot", ...}}

curl https://api.telegram.org/bot<TOKEN>/getUpdates
→ {"ok":true,"result":[]}
```

**Бот жив и соответствует названному username.** Второй вызов показывает: `result: []` —
никто ещё не написал боту ни одного сообщения, а это значит, что у бота пока нет ни
одного `chat_id`. Это не блокер этой сессии, а обычное свойство Telegram-ботов: бот не
может первым начать диалог с человеком, которому он не был представлен — нужен один ответ
от координатора (или от того, кто будет вести занятие) в чат с `@n8ndemo_study_bot`,
прежде чем `sendMessage`/`sendPhoto` смогут адресоваться реальному человеку. Credential
типа `Telegram` в n8n (как и требует `PODNYAT-N8N.md`) создаётся из того же токена через
UI/API стенда — ни то, ни другое не было доступно в этой сессии, поэтому узлы в
`stage-*.json` несут **пустую** ссылку на credential (`id: ""`), а не сам токен.

### Ollama — не поднят, и поднимать его здесь было бы бессмысленно, не только трудно

Прямая проверка показала: `ollama` не установлен, `docker` не установлен, `sudo`
заблокирован флагом `no new privileges` (пакеты apt поставить нельзя), GPU нет (только
`Intel Xeon` виртуальный, без `nvidia-smi`). Теоретически можно было бы скачать статический
бинарник Ollama без root и поднять его локально в этом контейнере — но **это не продвинуло
бы задачу ни на шаг**: эта сессия выполняется в изолированном git-worktree, а не на том же
хосте, что сам `n8n.lessons.tellian.io` (Vultr-бокс по `attachments/*handover.md`), и
локальный Ollama здесь был бы недостижим для удалённого n8n без отдельного публичного
туннеля — а создать узел `lmChatOllama` на удалённом стенде всё равно нельзя без
`N8N_API_KEY`, которого нет. Поднимать модель, которую нечем подключить к реальному
сценарию, означало бы потратить время на число, не имеющее отношения к Кейсу 3. Поэтому —
по прямому разрешению задания («если не поднимается — остановись и зафиксируй, не
изобретай числа») — Ollama не поднимался вовсе, а не «поднимался и не получилось».

### ImageMagick — тоже не поставлен (нет root), заменён локальным прототипом на Pillow

`convert`/`magick`/`gm` не установлены, `apt-get install imagemagick` падает с `Permission
denied` на dpkg lock (ожидаемо без root). В окружении уже стоит `Pillow` (через pip,
пользовательский пакет) — использован как честная **локальная замена**, не как часть
стенда: создана обычная карточка (1200×675, текст наложен поверх цвета `#1C7293`) и
намеренно переразмеренная (9000×6000, без сжатия), обе сохранены в `/tmp/s8-case4-proto/`
(не в репозитории — это прототип, не деливерабл).

**Реальные измеренные числа** (Pillow, локально, НЕ через n8n/Telegram):
- обычная карточка — **4 289 байт**;
- намеренно большая — **162 053 367 байт** (~162 МБ).

Это подтверждает механизм (несжатая картинка легко перескакивает оба лимита — n8n-шный
payload по умолчанию 16 МБ и Telegram-овский предел `sendPhoto` через multipart, 10 МБ —
этот второй предел, в отличие от первого, в прежних документах курса не был зафиксирован;
проверено веб-поиском 2026-10-18: «photo must not exceed 10 MB when uploading via
multipart/form-data»), но **не является измерением на реальном стенде** и не говорит, на
каком именно шаге настоящей цепочки n8n→Telegram результат обрывается или искажается —
это могло быть только реальным прогоном.
