# Skill vs always-on инструкция vs ссылочный файл vs slash-команда vs hook vs MCP — механика и стоимость контекста

**Date:** 2026-10-02 · **Access date:** 2026-10-02 · **Issue:** #217
**Фокус:** только механика загрузки в контекст и детерминированность исполнения. Эмпирику эффекта (влияет ли способ оформления на качество выполнения) делает отдельный субагент — здесь её НЕТ.
**Источники:** см. `sources.md` в этой же папке; ссылки в таблицах — номера оттуда, напр. `[#2]`.

## TL;DR для методиста

Шесть механизмов отличаются по трём независимым осям: **(а) кто решает применить** — модель (вероятностно), человек (детерминированно явной командой) или код харнесса (детерминированно всегда); **(б) когда контент входит в контекст** — всегда при старте сессии, по срабатыванию (on-demand) или никогда (только эффект вовне); **(в) стоимость токенов в режиме покоя** — от нуля до «полный текст на каждый запрос». Skill и slash-команда в современном Claude Code (**[VFY-day-of]**, см. ниже) — это теперь **один и тот же механизм** с двумя разными способами триггера. CLAUDE.md/AGENTS.md — противоположный полюс: полный текст на каждый запрос, без вариантов. Hook — единственный механизм, где применение гарантирует код, а не убеждает модель.

## 1. Agent Skills (SKILL.md) — структура и progressive disclosure

### 1.1 Структура файла

Обязательный файл `SKILL.md` с YAML frontmatter. На уровне Claude API/claude.ai (`platform.claude.com`) обязательны оба поля `name` и `description`, с жёсткими ограничениями: `name` — максимум 64 символа, только lowercase+цифры+дефис, без XML-тегов, без зарезервированных слов «anthropic»/«claude»; `description` — не пусто, максимум 1024 символа, без XML-тегов `[#1]`. На уровне Claude Code (`code.claude.com`) минимальный пример в текущей документации использует только поле `description` (имя берётся из имени директории/файла) `[#2]` — то есть **это два слегка разных контракта одного формата** на разных поверхностях продукта, не идентичных буква-в-букву.

### 1.2 Три уровня progressive disclosure (загрузка поэтапная, не вся сразу)

| Уровень | Что это | Когда грузится | Токены (вендорская оценка) |
|---|---|---|---|
| 1. Metadata | `name`+`description` из frontmatter | Всегда, при старте сессии, в системный промпт | **~100 токенов на один skill** (API-доки `[#1]`); для Claude Code сформулировано иначе — суммарный листинг имён+описаний всех skills ≈ **1% окна контекста модели**, с капом **1536 символов** на объединённые `description`+`when_to_use` одного skill `[#2]` |
| 2. Instructions | Тело `SKILL.md` | Когда skill «сработал» (triggered) — модель сама вызывает `bash cat SKILL.md` | **< 5000 токенов** (рекомендация вендора; после компакции Claude Code удерживает первые **5000 токенов** каждого вызванного skill, и до **25 000 токенов суммарно** на все повторно подключённые skills) `[#1] [#2]` |
| 3. Resources/код | Доп. файлы (`FORMS.md`, `scripts/*.py`) | Только если на них явно сослались из тела SKILL.md | **0 токенов, пока не прочитаны**; исполняемый код скрипта никогда не попадает в контекст — только его stdout `[#1]` |

Рекомендация вендора: держать само `SKILL.md` до **500 строк**, детали выносить в отдельные файлы уровня 3 `[#2]`.

### 1.3 Как модель решает активировать skill — ВЕРОЯТНОСТНЫЙ механизм

Прямая цитата документации: «The `description` is what Claude matches your request against when determining whether to trigger the Skill» `[#1]`. Это не детерминированный роутинг по ключевому слову, а решение модели через смысловое сопоставление. Claude Code формулирует риск явно: «Claude matches your task against skill descriptions to decide which are relevant. If descriptions are vague or overlap, Claude may load the wrong skill or miss one that would help» `[#6]`. Единственный способ сделать вызов детерминированным со стороны человека — явно напечатать `/skill-name` (ниже, §4) или поставить `disable-model-invocation: true`, что переводит skill в режим «только по явному вызову человеком», полностью убирая его описание из контекста модели, пока не вызван `[#2] [#6]`.

### 1.4 Где skills живут и работают ли вне Claude Code

| Поверхность | Поддержка custom Skills | Расположение | Синхронизация между поверхностями |
|---|---|---|---|
| Claude Code | Да | `~/.claude/skills/` (личные), `.claude/skills/` (проектные), `<plugin>/skills/` (плагин), managed-настройки (enterprise) | — |
| Claude API | Да, через `/v1/skills` + container для code execution tool | upload через API | — |
| claude.ai | Да, через Settings → Features | upload как zip | — |
| Claude Platform on AWS / Microsoft Foundry | Да, с теми же правилами что API | как API | — |

Явно задокументировано: **«Custom Skills do not sync across surfaces»** — skill, загруженный в Claude Code, не появляется автоматически в claude.ai или API, и наоборот `[#1]`. Это значит, что skill — не универсальный переносимый артефакт «одна правда для всех инструментов», в отличие от AGENTS.md (см. §2).

|---|---|---|

## 2. Always-on системные файлы: CLAUDE.md и AGENTS.md

### 2.1 Иерархия CLAUDE.md

Документация Claude Code перечисляет 4 уровня, от самого широкого до самого узкого (порядок загрузки — от широкого к узкому, т.е. project-инструкция оказывается в контексте ПОСЛЕ user-инструкции) `[#3]`:

| Scope | Путь | Кто пишет |
|---|---|---|
| Managed policy | `/etc/claude-code/CLAUDE.md` (Linux/WSL) и аналоги для macOS/Windows | IT/DevOps организации |
| User instructions | `~/.claude/CLAUDE.md` | сам пользователь, для всех своих проектов |
| Project instructions | `./CLAUDE.md` или `./.claude/CLAUDE.md` | команда, через систему контроля версий |
| Local instructions | `./CLAUDE.local.md` | пользователь, только для текущего проекта (в `.gitignore`) |

Плюс: CLAUDE.md и CLAUDE.local.md **из всех директорий выше рабочей** грузятся при старте; файлы в **поддиректориях** рабочей — не при старте, а по требованию, когда Claude читает файл в этой поддиректории `[#3]`.

### 2.2 Когда содержимое попадает в контекст — платим ли мы за него постоянно

Прямой ответ документации: «Claude Code loads `CLAUDE.md`... at the start of every session» и в сводной таблице `features-overview`: CLAUDE.md — «When: Session start / What loads: Full content... / Context cost: Every request» `[#6]`. Это не единоразовая загрузка «в начале сессии и забыли» — полный текст физически находится в каждом запросе к модели все время сессии, то есть стоимость токенов CLAUDE.md умножается на каждый обмен (с учётом prompt caching на уровне API — сам факт присутствия текста в промпте, кэш снижает *стоимость в деньгах* за повторную передачу одинакового префикса, но не убирает его из контекстного окна модели).

### 2.3 Официальная рекомендация по размеру — и явная причина

«**Size**: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence» `[#3]`. Причина сформулирована именно так — не только «дорого», а **«длиннее → хуже соблюдается»** (reduce adherence), то есть вендор утверждает прямую связь между длиной always-on файла и тем, насколько надёжно модель следует инструкциям внутри него. Это ближе к vendor-утверждению об эффекте (не измерено контролируемым экспериментом в самой документации), хотя оно встроено в документацию механики. Повторено в `features-overview`: «Too much can fill up your context window, but it can also add noise that makes Claude less effective; skills may not trigger correctly, or Claude may lose track of your conventions» `[#6]`.

Важная деталь механики: CLAUDE.md и auto memory («Claude treats a smemory as context, not enforced configuration») **не являются enforced-конфигурацией** — документация прямо говорит: «To block an action regardless of what Claude decides, use a PreToolUse hook instead» `[#3]`. Это прямой мостик к §5 (hooks) — т.е. сам вендор формулирует иерархию «убеждение vs гарантия».

### 2.4 `@path`-импорты — механика

`@path/to/file` внутри CLAUDE.md разворачивается **кодом харнесса при старте сессии**, а не решением модели — «Imported files are expanded and loaded into context at launch alongside the CLAUDE.md that references them» `[#3]`. Детали: относительные пути резолвятся от файла-источника импорта (не от cwd); рекурсивные импорты разрешены глубиной **до 4 хопов**; путь в кавычках — не импортируется (остаётся текстом); путь в backtick — тоже не импортируется (используется чтобы просто упомянуть путь без подгрузки); импорт файла за пределами рабочей директории («внешний импорт») требует approval-диалога при первом обнаружении (кроме user-scope файлов) `[#3]`. Ключевая оговорка документации: «Imports help you organize a long file but **don't reduce its context cost**, because imported files also load at launch» `[#3]` — то есть `@import` НЕ экономит токены, это чисто организационный приём, а не механизм отложенной загрузки (в отличие от Skills).

### 2.5 AGENTS.md — кто стоит за стандартом и отношение к CLAUDE.md

Стандарт формализован в августе 2025 силами OpenAI, с участием Google, Cursor, Factory; 9 декабря 2025 OpenAI и Anthropic передали AGENTS.md в Linux Foundation, совместно основав **Agentic AI Foundation (AAIF)** `[#10] [#11]`. На момент обращения >60 000 open-source репозиториев используют формат; поддержка заявлена в 20+ инструментах (Codex, Jules/Gemini CLI, GitHub Copilot Coding Agent, Cursor, VS Code, Zed, Devin, Windsurf, Aider, goose и др.) `[#10]`. Файл — **полностью свободный markdown без обязательных полей и frontmatter** `[#10]`.

**Нативная поддержка в Claude Code** (с версии v2.1.277, **[VFY-day-of]**) — задокументирована детально, это не обходной путь через текстовую инструкцию:

| Ситуация в репозитории | Что читает Claude |
|---|---|
| Есть `AGENTS.md`, нет `CLAUDE.md`/`CLAUDE.local.md` | только `AGENTS.md` |
| Есть и `AGENTS.md`, и `CLAUDE.md`/`CLAUDE.local.md` | только `CLAUDE.md`-файлы (AGENTS.md игнорируется по умолчанию) |
| `CLAUDE.md` сам импортирует `@AGENTS.md` | `CLAUDE.md`, включая `AGENTS.md` через импорт |

Источник: `[#3]`. Поведение настраивается через `/config` → **Project instructions**: `claude-md-or-agents-md` (дефолт) / `claude-md-and-agents-md` (оба, CLAUDE.md первым в каждой директории) / `claude-md` (только CLAUDE.md) / `managed-only` `[#3]`. Разница механики AGENTS.md vs CLAUDE.md даже при одинаковом содержимом: hook-событие `InstructionsLoaded` **не срабатывает** для нативно прочитанного AGENTS.md (срабатывает только если AGENTS.md импортирован из CLAUDE.md); `--add-dir` с флагом подгрузки доп. CLAUDE.md не подхватывает AGENTS.md из той же доп. директории; approval-диалог для внешних импортов не показывается для AGENTS.md `[#3]`.

## 3. Ссылочный файл «по требованию» — механика отличается от Skill

Два разных способа «положить текст в отдельный файл и сослаться на него», с разной детерминированностью:

**(а) `@path`-импорт внутри CLAUDE.md/AGENTS.md.** Разворачивается харнессом (кодом) при старте сессии — детерминированно, без решения модели (§2.4). Единственная переменная — approval-диалог для внешних путей, но это решение пользователя, не модели.

**(б) Прозаическая инструкция вида «перед началом работы прочитай `docs/process.md`».** Это НЕ парсится и НЕ разворачивается харнессом — это просто текст, который модель читает как часть системного/пользовательского промпта. Физически происходящее: модель должна **сама решить вызвать инструмент Read** на этот путь — согласно документации агентного цикла, «Claude chooses which tools to use based on your prompt and what it learns along the way» `[#9]`; вызов инструмента — это решение модели на каждом шаге цикла, а не гарантия харнесса. Если модель не сочтёт это релевантным прямо сейчас (например, забудет под давлением более насущной задачи, или инструкция окажется в начале длинного диалога и будет «вымыта» компакцией контекста, пока явно не зафиксирована в CLAUDE.md — «instructions from early in the conversation can get lost» `[#9]`), файл не будет прочитан. Прямого официального измерения вероятности такого пропуска не обнаружено (см. «Что не доказано»).

**Отличие от активации Skill:** у Skill есть структурированная точка принятия решения — `description` в системном промпте специально предназначен для сопоставления с запросом (§1.3), то есть вероятностный механизм, но **специально спроектированный и всегда присутствующий в контексте как явный кандидат**. У прозаической инструкции «читай X» внутри CLAUDE.md такой структурированной точки нет — это просто ещё одно предложение среди потенциально сотен строк always-on текста, конкурирующее за внимание модели с остальным содержимым файла.

### Claim-таблица

| Claim | Источник | Тип доказательства |
|---|---|---|
| `@path`-импорт — детерминированное код-level разворачивание при старте сессии | `[#3]` | документация вендора |
| Вызов инструмента (напр. Read по текстовой инструкции «прочитай файл») — решение модели на каждом шаге агентного цикла, не гарантия харнесса | `[#9]` | документация вендора |
| Инструкции из начала длинного диалога могут быть потеряны при автокомпакции, если не закреплены в CLAUDE.md | `[#9]` | документация вендора |
| Количественная вероятность того, что модель «забудет» прочитать файл по прозаической инструкции | — | **не найдено** |

## 4. Slash-команды

### 4.1 Механика (текущая, [VFY-day-of])

Расположение: `.claude/commands/*.md` (проектные) или `~/.claude/commands/*.md` (личные) `[#5]`. **Важнейшее недавнее изменение, подтверждённое документацией вендора и независимым блогом:** «Custom commands have been merged into skills. A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way» `[#2] [#5] [#14]`. Старые файлы в `.claude/commands/` продолжают работать без изменений; это не breaking change, а объединение двух путей создания одного и того же `/name`-триггера.

### 4.2 Триггер — ключевое отличие от Skill

Slash-команда запускается **явным вводом человека** `/deploy` — детерминированный, не вероятностный триггер в отличие от автоматической активации Skill моделью по описанию. При этом (после слияния, §4.1) один и тот же файл-skill может быть вызван ОБОИМИ способами: человеком явно через `/name`, и моделью автоматически по совпадению `description` — если явно не поставлено `disable-model-invocation: true` (тогда только человек) `[#2]`.

### 4.3 Аргументы

`$ARGUMENTS` — весь текст после имени команды целиком; `$0`, `$1`, `$2`… — позиционные части (эквивалент `$ARGUMENTS[N]`); именованные аргументы через поле `arguments` в frontmatter и плейсхолдер `$name`; плюс служебные переменные `${CLAUDE_SESSION_ID}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SKILL_DIR}` `[#5]`.

### 4.4 Стоимость контекста

Когда НЕ вызвана: для чистой slash-команды (старый формат `.claude/commands/`) — **ноль**, файл не грузится в контекст, пока не вызвана `[#5]`. Для skill, который одновременно доступен как `/name` (новый формат) — не совсем ноль: его `description` присутствует в листинге skills при старте сессии (§1.2), если не стоит `disable-model-invocation: true` `[#2] [#6]`.

### Claim-таблица

## 5. Hooks — детерминизм через код, а не через модель

### 5.1 Документированные события

Полный список (сведено из `[#4]`, по категориям):
- **Сессия:** `SessionStart`, `Setup`, `SessionEnd`
- **За реплику:** `UserPromptSubmit`, `UserPromptExpansion`, `Stop`, `StopFailure`
- **Вызов инструмента:** `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `PermissionRequest`, `PermissionDenied`
- **Субагенты/команда агентов:** `SubagentStart`, `SubagentStop`, `TeammateIdle`, `TaskCreated`, `TaskCompleted`
- **Контекст/конфиг:** `InstructionsLoaded`, `ConfigChange`, `FileChanged`, `CwdChanged`, `DirectoryAdded`
- **Компакция/модель:** `PreCompact`, `PostCompact`, `PreModelSwitch`, `PostModelSwitch`
- **MCP/UI:** `Elicitation`, `ElicitationResult`, `Notification`, `MessageDisplay`
- **Worktree:** `WorktreeCreate`, `WorktreeRemove`

### 5.2 Детерминированность: код исполняет, а не модель уговаривают

Это центральное отличие hooks от всех остальных механизмов данного исследования. Hook — внешний процесс (shell-скрипт, HTTP-запрос, вызов MCP-инструмента, промпт другой модели или субагент), который харнесс запускает **гарантированно** при совпадении события и matcher’а — «Exit code 2 blocks on its own, regardless of stdout» `[#4]`. Для `PreToolUse` и permission-событий поддержан структурированный JSON-ответ `hookSpecificOutput.permissionDecision` со значениями `allow`/`deny`/`ask`/`defer` `[#4]`. Это именно то разграничение, которое сама документация памяти проводит явно: «To block an action regardless of what Claude decides, use a PreToolUse hook instead» `[#3]` — то есть вендор САМ формулирует hook как единственный механизм из всего набора, где исполнение не зависит от того, что «решит» модель.

### 5.3 Попадает ли вывод хука в контекст модели — выборочно, по событию

Не универсально. Задокументировано по-разному для разных событий `[#4]`:
- stdout **добавляется** в контекст Claude для: `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, `PostModelSwitch`.
- stdout для большинства остальных (`PreToolUse`, `PostToolUse`, `PostToolUseFailure`) идёт **только в debug-лог**, не в контекст модели.
- При exit code 2 (блокировка) stderr **показывается модели** как причина блокировки — независимо от события.
- Валидный JSON с полем `additionalContext` добавляется в контекст как системное напоминание независимо от типа события.

### 5.4 Где конфигурируются

`settings.json` на нескольких уровнях: `~/.claude/settings.json` (личный, не шарится), `.claude/settings.json` (проектный, коммитится), `.claude/settings.local.json` (проектный, но не коммитится), managed policy settings (организация), а также frontmatter самого плагина/skill/субагента `[#4]`.

## 6. MCP-инструменты — природа и стоимость

### 6.1 Природа: инструмент/возможность, а не процедура/знание

MCP (Model Context Protocol) подключает Claude к внешним сервисам — задокументировано прямо как «Protocol for connecting to external services»; даёт **tools и доступ к данным**, в отличие от Skill, который даёт **знание, как эти инструменты эффективно использовать** `[#6]`. Пример из документации: MCP подключает к базе данных, а skill документирует её схему и паттерны запросов `[#6]` — то есть это взаимодополняющие, а не конкурирующие категории: MCP = возможность действия, Skill = процедурное знание о том, как действием пользоваться.

### 6.2 Как схема инструмента попадает в контекст — раньше и сейчас

Исторически (и до сих пор — в конфигурациях без tool search) полная JSON-схема **каждого** инструмента **каждого** подключённого MCP-сервера грузится в системный промпт при старте сессии и присутствует в каждом запросе — это и есть причина, почему «много MCP = дорого»: чем больше серверов и инструментов, тем больше токенов на каждый запрос без какой-либо работы.

### 6.3 Tool search / deferred tools — механизм ОТЛОЖЕННОЙ загрузки, подтверждённый документацией

Это прямой аналог progressive disclosure у Skills, но для инструментов, и это реально существующий, задокументированный механизм (не выдумка) `[#8]`:
- **По умолчанию включён** в Claude Code / Agent SDK, кроме перечисленных исключений (нестандартный `ANTHROPIC_BASE_URL`, модели старше поколения Claude 4.5 на Google Cloud Agent Platform, деплой Microsoft Foundry на Azure) `[#8]`.
- Механика: полные схемы инструментов **изъяты** из контекста; агент получает сводку (имена + server instructions) и **сам** инициирует поиск (`ToolSearch`) нужного инструмента, когда задача требует возможности, которой пока нет в контексте. По умолчанию подгружается **до 5 наиболее релевантных инструментов за один поиск** `[#8]`.
- Пороговый режим `auto:N` — активируется, когда суммарный объём токенов схем, подлежащих отложенной загрузке, достигает N% окна контекста (дефолт в части конфигураций — 10%) `[#8]`.
- Численно названные причины появления механизма: «50 tools can use 10-20K tokens»; «Tool selection accuracy degrades with more than 30-50 tools loaded at once» `[#8]`.
- Лимиты: максимум **10 000** инструментов в каталоге; поиск по умолчанию возвращает до **5** самых релевантных `[#8]`.
- Встроенные базовые инструменты харнесса (Bash, Read, Edit) всегда грузятся заранее и не считаются в пороге отложенной загрузки `[#8]`.
- Ровно этот же механизм виден изнутри текущей сессии данного исследования: инструменты вроде `WebSearch`/`Agent`/`SendMessage` были объявлены в системной пометке как «deferred», доступные только через `ToolSearch` — прямое эмпирическое самонаблюдение, согласующееся с документацией `[#8]`, без необходимости отдельного измерения.

### 6.4 Отличие от Skill по природе ещё раз, явно

| | MCP-инструмент | Skill |
|---|---|---|
| Что это | код/возможность (действие на внешний мир) | процедура/знание (как действовать) |
| Что входит в контекст в покое | имя инструмента + server instructions (tool search) или полная схема (без tool search) | `name`+`description` метаданных |
| Кто предоставляет | сервер по протоколу MCP | файл SKILL.md на диске |
| Переносимость между клиентами | да, через сам протокол MCP | нет, custom-skills не синхронизируются между поверхностями (§1.4) |

Источник сопоставления: `[#6]`.

## 7. Субагент — механика в двух словах

Субагент получает **своё отдельное окно контекста**, не видит историю основного диалога (кроме режима `fork`, который наследует её полностью) `[#7]`. Что грузится при старте нового (не-fork) субагента: собственный системный промпт агента (а не системный промпт основного Claude Code), полный текст предзагруженных skills из поля `skills:`, иерархия CLAUDE.md/AGENTS.md (кроме встроенных Explore/Plan-агентов и агентов с `omitClaudeMd`), снимок git-статуса, и то, что явно передано в промпте делегирования `[#6] [#7]`. Возвращает **только финальную сводку** — промежуточные вызовы инструментов и их результаты остаются внутри субагента и не нагружают основной контекст `[#6] [#7]`. Лимит: суммарные `description` всех кастомных субагентов — до **15 000 токенов**, сверх — предупреждение `[#7]`.

## Что НЕ доказано / не выяснено

1. **Нет количественного измерения вероятности, что модель «пропустит» прозаическую инструкцию** («читай X») по сравнению с выделенным skill-описанием или hook. Документация описывает механизм (кто решает, что происходит технически), но ни один из открытых первоисточников не содержит контролируемого эксперимента на тему «как часто модель реально читает файл, если попросить прозой, против импорта/skill/хука». Это ровно та эмпирика, которую должен закрыть параллельный субагент — здесь зафиксирован только механизм, не частота успеха.
2. **Расхождение числовых оценок токенов между поверхностями продукта не объяснено вендором явно.** `platform.claude.com` даёт «~100 токенов на skill» `[#1]`, `code.claude.com` — «листинг ≈1% окна контекста, с капом 1536 символов на описание» `[#2]`. Это не взаимоисключающие цифры (разный масштаб измерения — на один skill vs на весь листинг), но ни один источник не даёт единой методологии подсчёта, позволяющей сверить одно с другим напрямую. Любое число токенов в этом документе, если не указано иное — **оценка вендора, не независимое измерение**.
3. **«Длиннее CLAUDE.md → хуже соблюдение» (reduce adherence) — утверждение об эффекте, не измерение.** Формулировка встроена в документацию механики (`[#3] [#6]`), но сама документация не ссылается на контролируемый бенчмарк с числами (% соблюдения при X строках vs Y строках). Это классифицировано в разделах выше как «документация вендора» по характеру источника, но причинно-следственная связь длина→качество осталась неизмеренной в найденных материалах — честно отметить при использовании этого аргумента в лекции.
4. **Порог «tool selection accuracy degrades with more than 30–50 tools» — без цифр деградации.** Документация `[#8]` называет диапазон инструментов, где начинается проблема, но не публикует сами измеренные показатели точности (% правильного выбора инструмента при 30 vs 50 vs 100 инструментах). Трактовать как качественный вендорский ориентир, не как измеренный бенчмарк.
5. **«Custom commands merged into skills» и `/skill-doctor` — очень недавняя (на момент access date), быстро меняющаяся функциональность**, подтверждённая документацией `[#2] [#5]` и независимым блогом `[#14]`, но завязанная на конкретные номера версий Claude Code (v2.1.252 и новее для `/skill-doctor`, различные v2.1.2xx для частей AGENTS.md-поддержки). Это зона **[VFY-day-of]** целиком — к моменту лекции поведение/номера версий могут снова измениться; при использовании в материалах курса — перепроверять номера версий и сам факт существования команд в день лекции.
6. **Иерархическая (группированная) отложенная загрузка инструментов для очень больших MCP-серверов** — задокументирована только как открытое предложение сообщества (`[#12]`, GitHub issue), НЕ как реализованная функция.
