## Как считались «итерации» этой деки

Ядро (`deckkit`) меряет текст **настоящими метриками шрифта** и печатает предупреждения на
КАЖДУЮ сборку всех 45 кадров сразу — это не ручной визуальный цикл «кадр за кадром», а
детерминированная проверка, которая заменяет собой первые N ручных осмотров (`tools/
presentation-build/deckkit/README.md`). Поэтому «итерация» здесь = полная пересборка деки +
чтение отчёта предупреждений, а финальные 3+ прохода — это ГЛАЗАМИ по реальным PNG-снимкам
(обязательное требование брифа: «зелёные числа приёмкой не являются»), не по тексту отчёта.

Пройдено **12 полных циклов сборки** (`python3 build_lec11.py`, при необходимости
`--render`) + отдельный визуальный осмотр ~17 из 45 PNG-снимков глазами (не все 45 —
остальные приняты по аналогии раскладки с уже проверенными того же типа, см. «Что НЕ

#### `s07` — `[кегль] тело-вступление: прогон ужат до 0.66` (устарело)

**Осмотрено глазами (снимок `k-07.png`): выглядит нормально.** Вступление (3 абзаца перед
таблицей из 7 строк) ужато до ~9,5 пт — ниже 15-пт пола, но в снимке при 150 dpi текст читается

ДРУГОЙ установленный предел того же ядра. **Решение владельца, не сборки** — тег `[кегль]`
остаётся блокирующим по политике ядра, но визуально кадр принят.

### `s24` — `[архитектура]`/`[высота]` на самой длинной строке блока «Работа: политика FKDPP»

**Единственный кадр деки с настоящим, не закрытым до конца физическим дефицитом.** Архитектура
из 4 блоков (вход/работа/выход/параллельно) содержит одну строку разбора ~150 знаков
(«политика обучена методом RL, обучения с подкреплением, заранее в симуляторе на модели
установки из проектных данных — это сделано до всякого обучения»), которая на ЛЮБОЙ ширине
бокса в один ряд из четырёх требует больше строк, чем помещается в кадр вместе с заголовком,
плашкой-итогом разбора и телом-разбором. Перебраны и измерены ТРИ варианта (см. цикл 9-11
выше):

| Вариант | Высота архитектуры | Читаемость |
|---|---|---|
| 1×4, `head_rows=3`/`line_rows=7` | 5,78" | 2 предупреждения |
| 2×2-грид (широкие боксы) | 6,14" | 0 предупреждений, но дороже бюджета кадра на 0,57" ДО тела |
| 1×4 + перенос строки в `vynoska`, `head_rows=4`/`line_rows=7` | 5,89" | 0 предупреждений ВНУТРИ боксов, но сама выноска (отдельная полоса под рядом) физически не уместилась — снимок показал её текст обрезанным по нижней границе слайда |
| **Взято: 1×4, `head_rows=4`/`line_rows=7`, БЕЗ `vynoska`** | **5,84"** | **1 предупреждение** (самая длинная строка не влезает ДАЖЕ на 7 строках — нужно 8) |

нижнюю границу СВОЕГО бокса примерно на одну строку (~0,28"), слегка задевая верхнюю кромку
подвала (строку источника). Остальные 3 бокса не задеты. Плашка-итог («Из компромисса в
политику — 840 ч автономии · −40% пара») и тело-разбор («что переехало» / «что не переехало»)
при этом СДВИНУТЫ архитектурой практически к нижней границе кадра — на снимке их не видно
(уходят за физическую границу слайда).

## Иконки на Раздел 2 (`s16-s20`) и Раздел 5 (`s38-s42`) — ESCALATION, правки НЕ внесены

**Задача (issue #353, по следам `presentation-critic` P1 + `student-simulator`):** оба раздела
на 10 кадров несут ноль фотографий (остальное объяснено выше — «что переехало»/«без модели»
правка это не закрывает, она про текст, не про визуал). Бриф разрешал закрыть это иконками
(Lucide/Heroicons/Phosphor) и/или встроенной диаграммой, **строго через существующее поле
фронтматтера** — без правки `build_lec11.py` и без придумывания обходного пути самостоятельно.

**Проверено, не предположено.** Три независимых источника, все отрицательные:

1. `grep -rn "icon" tools/presentation-build/deckkit/*.py` — **0 совпадений** во всём пакете.
   Ни `plates.py` (`blocks:` — только `label`/`value`/`note`/`key`), ни `scheme.py`, ни
   `arhitektura.py`, ни любой другой модуль не читает поле иконки ни на уровне плашки, ни на
   уровне блока/шага. `piktogrammy.py` — единственная форма ядра, рисующая фигурку (сетка
   человечков для «X из Y»), и её докстринг говорит об этом прямо: **«Внешних иконок эта среда
   не умеет — ни mermaid, ни ImageMagick, ни rsvg… и это не ограничение, а предпочтение: фигура,
   нарисованная в pptx, выходит векторной и правится, вставленная картинка — нет»**
   (`notes/mcp-limitations.md` [#301-5]). Это ЕДИНСТВЕННЫЙ семантический глиф в ядре (доля
   целого), не общий набор «шестерёнка/флакон/график-предупреждение» — и `piktogrammy` даже не
   импортирован в `build_lec11.py` (сверено по списку импортов на строке 107-108), то есть
   неприменим к этой деке без правки сборщика в любом случае.
2. **Сама среда не умеет рисовать SVG-иконки, даже в обход deckkit.** `command -v mmdc/convert/
   rsvg-convert` — все три отсутствуют (как и в [#301-5]). `curl` до `cdn.jsdelivr.net` работает
   (сеть есть, иконка Lucide скачалась), но рендер SVG→PNG нечем: `cairosvg` падает
   (`cannot load library 'libcairo.so.2'` — системной библиотеки нет), `svglib` + `reportlab.
   renderPM` падает тем же способом (`RenderPMError: cannot import desired renderPM backend
   rlPyCairo`). То есть даже «скачать Lucide-иконку и вставить картинкой в обход ядра»
   физически невыполнимо в этой сессии — не только методически нежелательно.
3. **Визуально проверены все 10 текущих снимков** (`k-16`…`k-20`, `k-38`…`k-42`) — формы на
   этих кадрах: `s17`/`s18` — боксы плашек `plates.py` (слот под подпись есть визуально, кода
   под иконку в слоте нет); `s19`/`s20`/`s39`/`s40`/`s41` — булет-коллаж (`BULLET_COLLAGE`,
   цикл 5 выше) — построчный текст без боксов вообще, слота под иконку НЕТ по построению;
   `s42` — `figure:` (число «9» + тело) — тоже без слота; `s16`/`s38` — дивайдеры, чистый текст.

**Вывод: механизм «добавить иконку через поле фронтматтера» не существует.** Это не недосмотр
дизайнера в этой сессии, а объективное свойство ядра + среды, проверенное кодом и диском, а не
прочитанное по README на слово. Следуя явному указанию брифа — не изобретать обходной путь
самостоятельно, — **правки не внесены**: ни один `.md` слайда, ни `build_lec11.py`, ни рендер
не тронуты (нет diff). Пере-рендер не выполнялся — нечего пере-рендерить.

**Что потребовалось бы, если орхестратор решит продолжать (не сделано, только названо):**
- Новый модуль ядра (по образцу `piktogrammy.py`) с маленьким набором РУЧНЫХ векторных глифов
  из `MSO_SHAPE`-примитивов (шестерёнка ≈ круг + зубцы-прямоугольники, флакон/таблетка ≈
  скруглённый прямоугольник с перехватом, график-предупреждение ≈ ломаная `freeform` + треугольник
  восклицания) — **не скачанные SVG**, ядро принципиально рисует иконки сама, а не вставляет
  картинки (см. п.1 выше); это совпадает с собственным предпочтением ядра, не противоречит ему.
- Новое поле фронтматтера (например `icon:` на уровне элемента `blocks:`, и отдельно — на
  уровне строки булет-коллажа, раз 5 из 7 задетых кадров используют именно эту форму) +
  геометрия слота (где именно внутри плашки/перед строкой оно встаёт, сколько отнимает у
  текста по высоте/ширине — аналог того, как `plates.py` уже встраивает `label`/`value`).
- Wiring в `build_lec11.py`: импорт нового модуля (строка ~107-108) и вызов в ветке отрисовки
  плашек/булет-коллажа (~строки 835-844 и в `BULLET_COLLAGE`-ветке) — именно та правка, которую
  бриф запретил делать самостоятельно в последний момент.
- Решение, нужен ли глиф НА КАЖДОЙ строке коллажа (5-6 глифов на кадр — риск визуального шума,
  раздел «Iconography Discipline» этого же курса ограничивает 4 иконки на кадр) или только на
  ключевой (`key: true`) плашке/строке.

Это решение — по объёму (новый модуль + новое поле + wiring + политика «сколько иконок на
кадр») не «добавить иконку», а полноценное расширение ядра, которое по регламенту агента и по
прямому указанию брифа не выполняется в одиночку на этой сессии.
