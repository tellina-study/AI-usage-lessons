# Граница размера — проверено настоящим вызовом

## Assertion

Собрали файл ровно между двумя лимитами и отправили его напрямую в Telegram. Ответ — настоящая ошибка, не придуманная для примера.

## Visual

| Что | Байт |
|---|---|
| Проверенный файл (несжатый JPEG) | **12 812 355 байт** (~12,8 МБ) |
| Лимит Telegram на фото (`sendPhoto`) | **10 485 760 байт** (10 МБ) |
| Собственный лимит n8n на бинарные данные (справочно) | **16 МБ** |

> Настоящий ответ Telegram Bot API на этом файле:
> `"Bad Request: file of size 12812355 bytes is too big for a photo; the maximum size is 10485760 bytes"`

## Speaker notes

Проверили границу настоящим вызовом, а не предположением.

Ограничение самого n8n по умолчанию — 16 МБ на сообщение с бинарными данными. Ограничение Telegram на фото, отправленное через узел отправки фото, — отдельное и более узкое: 10 485 760 байт, то есть 10 МБ. Это два разных порога, и файл может пройти мимо первого и не пройти мимо второго.

Собрали намеренно несжатый файл ровно между этими двумя порогами — 12 812 355 байт, около 12,8 МБ: меньше лимита n8n, но больше лимита Telegram на фото. Отправили его напрямую через Telegram Bot API — тем же вызовом, которым пользуется узел отправки внутри цепочки, только без самого n8n между нами и Telegram, потому что промежуточный хостинг для подачи такого файла через узел получения картинки в момент проверки был недоступен.

Ответ пришёл настоящий, не придуманный для примера: файл такого-то размера слишком велик для фото, максимальный размер — столько-то байт. Telegram прямо называет размер файла и прямо называет предел — не тишина, не обрыв соединения, а явная, читаемая ошибка.

И это уточняет то, что мы видели в сцене кейса. Там карточка пропадала тихо, без явной ошибки, — потому что проблема на границе n8n чаще выглядит именно так. Сам Telegram на своей собственной границе отвечает иначе: явным текстом, который можно поймать и показать человеку. Тихая потеря вероятнее на стороне платформы-оркестратора или при сетевом сбое, а не на стороне самого Telegram API, который о своём лимите говорит прямо.

Отсюда практический вывод для архитектурного правила с прошлого экрана. Проверку размера нельзя строить только на том, что API рано или поздно откажет с понятным текстом: часть превышений — на стороне Telegram — действительно откажет явно, а часть — на стороне самого n8n или при сетевой проблеме — откажет тихо. Условие внутри цепочки, которое сверяет размер и формат до отправки, не зависит от того, какая из двух сторон в конкретный момент решит сообщить об ошибке честно, а какая — промолчать.
