# Visible content

## Title bar
«Провалы агентов»

## Body
[3 карточки-провала в Ocean rounded box]

**1. Петля без лимитов**
Агент на «синхронизируй заказы» получил HTTP 429 → план→вызов→429→перепланирую→… → **$4,200 за 63 часа**  *(gold-акцент)*
*Почему:* агент не «видит» ни накопленной стоимости, ни времени, ни повторяемости
*Правильно:* задача предсказуема → retry-with-backoff скрипт, не агент; budget/loop-лимиты ВНЕ агента

**2. Reliability compounding**
5 шагов по 99% → 0.99⁵ ≈ **95%**; 10 → ≈ **90%**; 20 → ≈ **82%** — надёжности перемножаются
*Вывод:* «улучшить шаг» — слабый рычаг; «меньше хопов + валидация между шагами» — сильный

**3. Мульти-агентная хрупкость**
зависимые подзадачи → параллельные субагенты принимают конфликтующие неявные решения
*Правильно:* single-threaded линейный агент; мульти-агент — только широко-параллельное независимое

## Speaker notes

Цикл агента имеет четыре места отказа; три класса провалов ниже — ровно эти режимы в датированных кейсах. Каждый — не «ИИ ошибся», а кейс с уроком и альтернативой.

Первый. Команда поставила автономного агента на «синхронизировать заказы в CRM». Задача предсказуемая: известен источник, приёмник, логика. Внешний API упёрся в ограничение частоты и стал возвращать ошибку 429. Агент, не имея в плане ветки на 429, действовал по своей природе: планирую, вызываю, 429, перепланирую, снова — тысячи раз в час. К двенадцатому часу — порядка тысячи долларов; дальше быстрее, когда агент стал подгружать собственные лог-ошибки как контекст. Итог — около $4,200 за шестьдесят три часа. Агент конструктивно не понимает ни накопленной стоимости, ни времени, ни того, что последние тысячи действий идентичны. Урок: без жёстких внешних лимитов «пробуй, пока не получится» исполняется буквально и до разорения. Альтернатива двойная: budget gates вне агента (потолок по деньгам, токенам, времени, детектор повторов); и на уровне архитектуры — синхронизация предсказуема, её правильная архитектура это детерминированный скрипт с повторами, не агент. Корневая ошибка — «выбрали агента там, где задача из ступени workflow».

Второй. В цепочке компонентов, где сбой любого портит результат, надёжности перемножаются. Пять по 99% дают примерно 95%; десять — около 90%; двадцать — около 82%. Инженер рассуждает «каждый шаг почти всегда работает, значит и цепочка» — математически ложно. Следствие: улучшение отдельного агента почти не двигает системную надёжность, а сокращение числа шагов вдвое даёт сопоставимый эффект дешевле. Урок: «улучшить модель» — слабый рычаг, «уменьшить число хопов плюс валидация между шагами» — сильный.

Третий. Когда подзадачи зависимы или нужен общий контекст, параллельные субагенты принимают конфликтующие неявные решения, давая несовместимый результат. Урок: мульти-агент по умолчанию — не апгрейд; для задач с зависимостями он хуже одного линейного. Альтернатива — single-threaded агент. Во всех трёх «более сложная архитектура» означала «менее надёжная», а не «более продвинутая» — пятая точка возврата центрального вопроса.
