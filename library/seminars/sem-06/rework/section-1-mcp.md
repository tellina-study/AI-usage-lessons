### A.1.3. База — терминологический шлюз (перед первым кейсом, 1,0 мин)

**MCP (Model Context Protocol)** — протокол, по которому агент подключается к внешней системе и
получает от неё три разных вида возможностей, различающихся тем, **кто решает ими
воспользоваться**:

| Примитив | Кто инициирует | Как выглядит на практике |
|---|---|---|
| Инструмент | модель — сама решает вызвать | «прочитать открытые issue», «создать черновик правки» |
| Ресурс | приложение — по явному упоминанию | пользователь вставляет ссылку на конкретный объект |
| Подсказка | человек — явной командой | пользователь выбирает готовый сценарий из меню |

Практический вывод: если нужно, чтобы агент **сам** решал воспользоваться возможностью — это
обязан быть инструмент, не «просто данные», оформленные ресурсом.

Протокол — открытый, с нейтральным владельцем (см. §A.00). Скилл на прошлом занятии — тоже
открытый формат. У MCP это свойство выражено сильнее: у протокола есть собственная спецификация
и фонд, а сходящаяся практика нескольких поставщиков — это уровень скилла, не MCP.

### A.1.4. Вопрос классу (дословно)

> «Агенту теперь регулярно нужно смотреть открытые issue репозитория и готовить черновики правок
> по ним. Вы почти готовы подключить официальный сервер доступа к трекеру. Выберите, что вы
> проверите до того, как это сделать, — из карточек ниже, — и в каком порядке.»

Карточки: `ничего — сервер официальный` · `сколько токенов он добавит` · `какие права даю
токену` · `не хватит ли обычной команды` · `сколько у сервера звёзд`

Ни цифры, ни источника на слайде нет.

### A.1.5. Разбор (сразу за вопросом, форма А7)

| Вариант | Где работает — конкретные случаи | Ограничения |
|---|---|---|
| ничего — сервер официальный | снижает риск как общая эвристика в большинстве областей | официальность не гарантирует, что сервер делает то, что заявляет: автор сервера сам может быть уверен в неверном |
| сколько у сервера звёзд | сигнал, что сервер кто-то использует и успел заметить явные неполадки | не измеряет, проверяет ли сервер, кто к нему обращается — список с проверкой и без неё выглядит одинаково |
| сколько токенов он добавит | всегда стоит знать: величина измеримая и неочевидная | считать её раньше вопроса «нужно ли вообще» — оптимизировать то, что не следовало подключать |
| не хватит ли обычной команды | разовое действие в одной сессии команда закрывает без сервера | перестаёт хватать, когда доступ нужен регулярно, из нескольких сессий, с сохранением состояния |
| какие права даю токену | обязательный шаг для любого сервера, без исключений | не отвечает, нужно ли подключение вообще — это отдельный, более ранний вопрос |

> **Из сочетания колонок:** вычёркивание прав и подсчёт цены — обе законные и обязательные
> проверки, но они отвечают не на первый вопрос. Последовательность: сначала — нужно ли вообще
> (не хватит ли обычной команды), потом — с какими правами, потом — по какой цене. Начинать с
> цены — популярная ошибка: можно отлично оптимизировать то, что вообще не следовало подключать.

### A.1.6. Со-сборка — две части

**Часть 1 (операции → права).**
Ход 1: «Что конкретно агент должен делать?» Зал называет, список фиксируется: читать открытые
issue; писать комментарий; создавать черновик правки. Ничего про удаление, настройки репозитория,
другие репозитории.

Ход 2 — вычёркивание прав. На слайде список того, что даёт широкий персональный токен «по
умолчанию»: все репозитории пользователя, включая приватные · чтение и запись · управление
настройками · удаление. По каждой строке — вопрос «нужно для нашего списка операций?» Лишнее
вычёркивается на слайде. Остаётся: один репозиторий, чтение issue, создание черновика правки.

«Запомните, как выглядит этот экран сейчас. Через несколько минут я покажу вам инцидент, который
воспроизводится ровно тогда, когда верхняя строка не вычеркнута.»

**Часть 2 (ключ → область).**
Ход 3: «Где хранить ключ?» В переменной окружения, не в файле.

Ход 4: «Куда положим сам файл?» Три варианта: только у меня на этой машине (`local`, дефолт) · в
репозиторий, для всех (`project`) · глобально во всех моих проектах (`user`). В репозиторий —
целевое для проверенного сервера. Только у меня — целевое для эксперимента. Дефолт команды
подключения кладёт сервер в `local`, не в `project` — если про это не знать, получится разговор
«я подключил, всё работает» — «а у меня нет», и оба правы.

### A.1.7. Артефакт

`.mcp.json` в корне `signup-landing/`:

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_PAT}"
      }
    }
  }
}
```

Четыре строки существа: чем запускается, что запускается, откуда ключ (подстановка из окружения),
и — вне файла — какие права у этого ключа: один репозиторий, не вся учётная запись.

Механика конфигурации коротко: три области — физически разные файлы (`local`/`user` —
`~/.claude.json`, `project` — `.mcp.json` в корне репозитория). При конфликте имён побеждает вся
запись приоритетной области целиком, поля не смешиваются: `local` → `project` → `user` →
сервер из плагина → коннектор → политика организации.

**Честный пробел, названный здесь один раз (см. §A.00).** Этот файл — целевое решение раздела,
снятое с более раннего захвата демо-репозитория; коммита с ним в текущей ветке `signup-landing`
нет, и в репозитории курса такого файла тоже нет. Слайд показывает разбираемый пример, не
обещает «склонируй и повтори».

### A.1.8. Цена в токенах — верхняя граница с условием (кандидат на компрессию)

«Подключение стоит X токенов» — утверждение о режиме **без отложенной загрузки**. По умолчанию
на актуальных моделях при старте сессии в контекст попадают только имена инструментов и короткая
инструкция сервера; полная схема конкретного инструмента подгружается отдельно, когда модель сама
решает, что он может понадобиться (управляется переменной `ENABLE_TOOL_SEARCH`).

| Значение | База сравнения |
|---|---|
| ≈55 000 токенов ≈ 21% окна 200К — связка из 5 серверов без отложенной загрузки | контекст без подключённых серверов — 0; это худший случай, не дефолт |
| 1 365 против 44 026 токенов — одно и то же действие через CLI и через MCP | 32-кратная разница при одинаковом результате |

Проверить у себя: не выставлен ли `ENABLE_TOOL_SEARCH=false`, и что реально показывает `/mcp` по
конкретному серверу — это не цифра, которая устареет, это команда, которая всегда актуальна.

### A.1.9. Провал — слоями, у каждой цифры база

**Слой 1 — эксфильтрация в связке.** Май 2025 (Invariant Labs). Агент с доступом к трекеру под
персональным токеном с правами на все репозитории пользователя, включая приватные. Атакующий
создаёт в публичном репозитории issue с инструкцией собрать данные о других репозиториях этого
пользователя и опубликовать здесь. Разработчик просит агента разобраться с открытыми issue. Агент
честно читает issue — встроенная инструкция попадает в контекст как задача, неотличимая от
легитимной. Читает приватные репозитории, публикует их содержимое в автоматически созданном
публичном PR. CVE не присвоен — архитектурный класс, не баг кода.

Возврат к ходу 2 со-сборки: строка «все репозитории, включая приватные» — та самая, которую
только что вычеркнули. Убрать её — сценарий не проходит вообще: читать нечего.

**Обобщение** (Simon Willison, 16.06.2025) — «смертельное трио»: доступ к приватным данным +
обработка недоверенного внешнего контента + канал наружу. При всех трёх атакующему достаточно
написать текст, который агент прочитает в рамках обычной работы. Нет хотя бы одного из трёх —
атака этого типа невозможна в принципе, не «маловероятна».

**Слой 2 — без модели вообще.** CVE-2026-61742 (DBHub, 24.09.2026, CVSS 9.3): HTTP-транспорт по
умолчанию слушает без аутентификации, защита от межсайтовых запросов обходится DNS rebinding.
Счёт «два HTTP-запроса и ноль учётных данных до захвата» — деталь вторичного технического
разбора (Strix.ai), не первичной записи NVD/GHSA, и ниже называется с этой оговоркой — против
«обычной» атаки через prompt injection, которая требует хотя бы одного успешного чтения агентом
вредоносного текста. Смертельное трио — не единственный путь к утечке: сервер сам может быть
незащищённым сетевым сервисом.

### A.1.10. Критерий

**Заголовок слайда:** «Когда хватает команды, а когда нужен сервер» (пункты 16/18 сверки —
свой заголовок на каждый предел, не общая рамка «ещё рано / не нужно вообще»)

**Ещё рано** (ждёт сигнала): разовое или редкое действие; снимка данных достаточно; доступ нужен
только из текущей сессии; нет готовности поддерживать ещё один постоянно работающий процесс с
доступом к секретам; отдельный стоп-критерий — подключение достраивает третий элемент
смертельного трио.

**Не нужно вообще** (не вопрос момента): задача сводится к известному вызову CLI — 32-кратная
разница по токенам не исчезнет с ростом доверия к серверу; правильный инструмент здесь — обычный
скрипт, не постоянно подключённый сервер.

прежний разбор («удалить сервер», «написать автору» как первые ходы; таблица из пяти статусов на
видимом экране) избыточно техническим и попросил строить кейс на двух пользовательских вопросах —
как понять, что сервер реально работает, и как правильно задать вопрос агенту. Числа и источники
не менялись, менялась только расстановка: что на экране, что в заметках.

### A.2.1. Заголовок дивайдера

> **Решаем, что делать, когда сервер подключён, а агент через него не ходит**

Слово «сервер» здесь уже можно называть: кейс идёт вторым в блоке про доступ наружу, зал знает
тему. Разрыв назван прямо: не «работы нет» (звучит как жалоба на результат), а «агент через него
не ходит» — ровно то, что разбирает кейс: процесс подключён и отвечает, но ничто не доказывает,
что именно через него агент получил ответ.

### A.2.2. Сцена

Сервер доступа к трекеру — тот самый, что собрали в прошлом кейсе — стоит уже две недели. В
понедельник утром разработчик просит агента посмотреть, что скопилось во входящих issue за
выходные, и подготовить черновики. В ответ — любая из трёх реплик: «всё сделал», «новых задач не
нашёл», «во входящих пусто». В репозитории — ни одного нового черновика, ни одного комментария, ни
в одном из трёх случаев. `claude mcp list` показывает ровно то же, что показывал всю неделю:
`✔ Connected`. Зелёная отметка значит одно — процесс сервера поднят и ответил на рукопожатие; она
ничего не говорит о том, пользовался ли им агент в этой конкретной задаче.

Три реплики, а не одна, — намеренно: снимает ложное чувство, что дело во лжи агента. «Не нашёл» и
«пусто» звучат честно, но ни одна из трёх не наблюдение за сервером — агент мог ни разу к нему не
обратиться и ответить по смыслу задачи.

### A.2.3. Вопрос классу

> «Статус сервера зелёный, а результата — ни одного. Выберите, что вы проверите дальше, — из
> карточек ниже.»

Карточки: `ничего — статус зелёный` · `посмотреть, что именно показывает статус подробнее` ·
`спросить агента, почему он решил, что всё сделал` · `явно попросить агента обратиться к серверу
по имени и показать вызов`

Карточки «удалить сервер и подключить заново» и «написать автору сервера» сняты как первые ходы —
круг 2 назвал их нереалистичными для открытого вопроса. Оба остаются реальными действиями, но не
первыми: в разборе показано, что это дорогие и медленные проверки, а граница кейса (A.2.8)
возвращается к ним отдельно — для случая, когда более дешёвые варианты уже не сработали.

### A.2.4. Разбор (форма А5 — две колонки)

| Вариант | Что делает | Что не делает / ограничение |
|---|---|---|
| ничего — статус зелёный | подтверждает: процесс сервера поднят и ответил на рукопожатие | не проверяет, обращался ли к нему агент в этой задаче — это два разных факта |
| посмотреть, что именно показывает статус подробнее | различает «процесс не поднялся», «список инструментов не получен», «нужна авторизация» — сужает круг причин | не показывает, вызывал ли агент сервер именно сейчас — статус живёт отдельно от конкретной задачи |
| спросить агента, почему он решил, что всё сделал | иногда вскрывает прямо: агент признаётся, что не нашёл способа проверить и ответил по смыслу задачи | агент пересказывает своё понимание, а не наблюдение — это тоже не факт о транспорте |
| явно попросить обратиться к серверу по имени и показать вызов | доказывает: в выводе вызов инструмента подписан именем сервера — факт, не предположение | требует заранее знать имя сервера и чуть более точной формулировки задачи |

> **Из сочетания колонок:** первые три сужают картину, но ни один не факт. Доказывает работу
> только явный именованный вызов — разбираем его дальше.

### A.2.5. Со-сборка / механика — в двух частях

**Часть 1 — как понять, что сервер реально работает.** Статус (`claude mcp list`/`/mcp`)
различает больше, чем одно слово «подключено» — отдельно видно, поднялся ли сам процесс и
получен ли список инструментов. Но даже самый подробный статус — факт про процесс, не про то,
обращался ли к нему именно агент в этой задаче. Минимальное доказательство — явное упоминание
сервера в запросе («используя сервер такой-то, узнай…»); признак, что ответ пришёл именно
оттуда, — вызов инструмента в выводе подписан именем сервера. Отдельно: долгий ответ — не всегда
сбой, запуск сервера и выполнение уже начатого вызова идут по разным часам.

**Часть 2 — как правильно задать вопрос агенту.** Расплывчатая просьба («посмотри, что
скопилось, и подготовь черновики») не даёт доказательного вызова — агент может ответить по смыслу
задачи, вообще не тронув сервер. Явное имя сервера в тексте запроса («используя сервер трекера,
выведи список открытых задач…») и есть доказательный вызов, применённый к формулировке: после
такой просьбы есть что проверить — подписан ли вызов в выводе именем сервера.

Технические детали — коды пяти статусов, точные тайм-ауты (`MCP_TIMEOUT` 30 с, `MCP_TOOL_TIMEOUT`
≈28 ч) и асимметрия переподключения (удалённый — сам, локальный `stdio` — нет) — остаются
подтверждёнными фактами курса, но круг 2 убрал их с видимого экрана по правилу А8: на уроке они
живут в «если спросят» заметок докладчика, не в теле кейса.

### A.2.6. Артефакт — записанная процедура, не новый файл

Этот кейс не меняет конфигурацию — его решение процедурное, и это стоит сказать прямо, не
выдавая его за файл, которого нет. Команда добавляет в `CLAUDE.md` проекта (тот же файл, где уже
живёт раздел про ветки) короткую строку правила: после подключения любого сервера и после любого
подозрения в тишине — явный именованный вызов, прежде чем доверять зелёному статусу. Это строка в
файле, который уже есть, не новый артефакт — и она проверяется так же, как остальные правила
этого проекта: прочитана, не исполняется сама.

**Почему CLAUDE.md, а не хук (добавлено кругом 2 по прямому запросу владельца).** Прошлое занятие
уже показало оба вида правил рядом в одном файле: «Repository etiquette» — записанное словами
правило, которое читает человек или агент и решает, следовать ли ему; «Хук защиты ветки» —
настоящий код, который срабатывает сам на git-команду, без решения в моменте. Хук умеет
реагировать только на чётко описанное событие — команда, имя файла, код выхода. «Подозрение в
тишине» таким событием не является: его нельзя формально описать заранее, оно требует, чтобы
кто-то заметил и решил, что пора проверить. Вот почему это строка в CLAUDE.md, а не механизм —
решение процедурное именно потому, что решает человек, не правило.

### A.2.7. Провал — слоями, по последствиям и по тому, как заметили

**Слой 1 — сервер сам говорит неправду о своём режиме.** Команда работала с MCP-сервером для баз
данных одного известного производителя в режиме, который считали ограниченным только чтением, —
именно для того, чтобы агент не мог ничего испортить в чужой базе. Флаг `readonly = true` у
инструмента `execute_sql` на деле не делал соединение реально ограниченным — код, который должен
был это гарантировать, ссылался на поле конфигурации, которое никогда не заполнялось (CVE-2026-
61788, DBHub, 24.09.2026, CVSS 7,4 из 10). Разработчики сервера сами были уверены, что режим
работает, — узнали только тогда, когда кто-то выполнил запрос с реальным побочным эффектом и
увидел, что он прошёл.

**Слой 2 — доступ пропадает тихо, транспорт жив.** Инцидент `[#49]` этого же проекта
(`notes/mcp-limitations.md`): инструменты, которые ещё вчера работали, однажды перестали — без
предупреждения, без красного статуса; `claude mcp list` продолжал показывать `✔ Connected`.
Заметили не по статусу, а по тому, что обычные вызовы начали требовать повторного входа. Причина —
OAuth-приложение `workspace-mcp` в статусе `Testing` в Google Cloud Console автоматически отзывает
`refresh_token` через 7 дней без активности; то же приложение в статусе `In production` токен не
отзывает вовсе — «долгий» или «короткий» интервал тут ни при чём, это целиком следствие одной
невыбранной настройки публикации.

Оба слоя проверяются одинаково — реальным действием с наблюдаемым результатом, не чтением
настройки сервера.

### A.2.8. Критерий

**Заголовок слайда:** «Когда достаточно посмотреть на статус, а когда нужно вызвать самому»
(переформулировано кругом 2 — владелец просил конкретнее: «читать» против «дёргать самому»)

**Достаточно посмотреть на статус:** сервер используется нерегулярно, под наблюдением человека
при каждом вызове.

**Нужно вызвать самому — доверять флагу, который сервер не может независимо подтвердить, не
нужно никогда** (если для задачи хватило бы read-only режима, но сервер не даёт способа
убедиться, что он реально включён — разумнее завести отдельную роль/учётную запись с урезанными
правами на уровне самой базы данных: флаг сервера такой гарантии не даёт).

**Или решение — не подключать вовсе:** явный вызов систематически не проходит, а автор сервера не
отвечает — вопрос смещается туда же, где решался первый кейс этого блока: подключать ли сервер
вообще.
