# Visible content

## Title bar
«Извлечение в JSON: строгая схема помогает»

## Body
[Постановка]
Из текста нужно достать поля по фиксированной структуре: сущности, атрибуты, класс — вход для кода, не для чтения человеком.

[Архитектура: constrained decoding / JSON mode]
Ограничение сэмплинга только допустимыми по грамматике токенами → близкое к 100% соответствие схеме. JSON — интерфейс между моделью и кодом.

[Gold callout — граница]
Тот же JSON на «подумай и реши» роняет качество (reasoning tax, §1.9). Строгую схему — только на стыке с кодом.

## Speaker notes

Четвёртый класс — структурированное извлечение. Постановка: из текста нужно достать поля по фиксированной структуре — сущности, атрибуты, категорию — и отдать это дальше в код, а не человеку на чтение. Это обратная сторона того, о чём мы говорили в разделе про форматы. Там принуждение JSON на рассуждающих задачах роняло качество, здесь та же строгая схема, наоборот, помогает.

Механизм называется constrained decoding — ограничение сэмплинга на этапе генерации только теми токенами, которые допустимы по грамматике схемы. Результат — близкое к стопроцентному соответствие схеме, а значит, парсинг на стороне кода однозначен и не ломается на неожиданной формулировке. Практический вывод простой: JSON — это интерфейс между моделью и кодом, а не формат для размышления. Применяйте его именно на стыке с кодом — извлечение полей, классификация, function calling, машинный ввод-вывод.

И тут же граница, чтобы не спутать два случая. Тот же строгий JSON, наложенный на задачу «подумай и реши», включает reasoning tax из предыдущего разбора и роняет качество. Разделяйте по оси: где нужен однозначный машинный контракт — строгая схема обязательна и полезна; где нужно рассуждение — не насилуйте его форматом, а если структурированный результат всё же нужен, разбейте на два шага. Извлечение и классификация — это единственный класс, где принуждение формата выхода надёжно работает в плюс.
