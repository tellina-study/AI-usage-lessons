### A.1.2. Источники данных для агента (круг 2, часть Б.1)

Пологий заход вместо прежней абстракции «инструмент · ресурс · подсказка» — владелец отверг её
целиком как терминологию, которую раньше на занятии не вводили.

Агент к этому моменту курса умеет работать с двумя источниками данных. Первый — файлы
репозитория: он читает их напрямую, это материал прошлых занятий. Второй — файлы, которые ему
дали явно: вставили текст в чат, приложили документ. Оба источника — файлы в буквальном смысле,
их можно один раз показать агенту, и этого достаточно.

Список открытых задач в трекере не ложится ни в один из двух источников. Это не файл
репозитория — трекер живёт в отдельной системе, заказчик ведёт его не в проекте. И это не файл,
который можно один раз дать и забыть, — список меняется каждый день без участия разработчика;
снимок, снятый сегодня утром, к обеду уже неточен.

Снимок здесь не выручит: агенту нужен способ самому обратиться к системе в момент работы и получить
свежий ответ. Такое обращение к системе по сети называется **вызовом API**: агент отправляет
запрос и получает ответ сразу, без файла-посредника.

Здесь экран вслух произносит догадку, которую кейс опровергает: **кажется, что за такой вызов
придётся платить написанной интеграцией.** Без произнесённой догадки повороту разбора (§A.1.6)
нечего опровергать. Механика MCP — §A.1.3, прежде чем вернёмся к сцене.

### A.1.3. MCP и сервер, одним экраном (круг 2, часть Б.2)

Одностраничник — опорный экран кейса, к которому разбор возвращается до самого конца. MCP
устроено из шести частей.

1. **Что такое сервер.** Отдельная программа, не часть Claude Code. Она может работать в двух
   местах: локальным процессом, который Claude Code запускает сама на машине пользователя, или
   удалённым сервисом, который хостит и обновляет кто-то другой. Команда в конфигурации
   исполняется буквально при старте сессии — что записано, то и запустится.

2. **Где объявляется.** Файл конфигурации:

   ```json
   {
     "mcpServers": {
       "github": {
         "command": "npx",
         "args": ["-y", "@modelcontextprotocol/server-github"]
       }
     }
   }
   ```

   `.mcp.json` в корне репозитория — область `project`, видят все, кто клонирует. `~/.claude.json`
   — области `local` (дефолт) и `user`. Какая область для чего и почему дефолт не туда, куда
   ожидаешь, — разбирается отдельно при сборке подключения (§A.1.7); здесь — только место на
   карте.

3. **Что происходит при подключении.** После того как транспорт поднялся, Claude Code сама, без
   участия модели, спрашивает у сервера список его возможностей (`tools/list`, `prompts/list`,
   `resources/list`). Сервер отвечает именами инструментов и короткой инструкцией о себе, не
   полными схемами.

4. **Вызов.** Когда модель решает, что инструмент нужен, агент сам поднимает нужный сервер и
   вызывает его точно так же, как вызвал бы функцию: полное имя с префиксом сервера и аргументы,
   которые модель собрала.

5. **Контекст и цена — три отдельные статьи, не одна цифра.** Первая: имя сервера и короткая
   инструкция — в контексте всегда, с первой секунды сессии. Вторая: полную схему конкретного
   инструмента модель подгружает сама, когда решает, что он может понадобиться (отложенная
   загрузка, `ENABLE_TOOL_SEARCH`). Третья, отдельная от первых двух: результат самого вызова — у
   него свой бюджет, предупреждение при выходе за 10 000 токенов, обрезка за 25 000 по умолчанию
   (`MAX_MCP_OUTPUT_TOKENS`). **Постоянная плата идёт за то, что сервер подключён вообще; цена
   вызова — отдельно, за каждый ответ.** Сопоставление по способам доступа, с опорой на
   исследование, — в §A.1.9.

6. **Чем отвечает сервер.** Отдельный канал результата, не тот же самый, что при подключении. В
   выводе вызов подписан именем сервера — так видно, что ответ пришёл именно оттуда, не из общих
   знаний модели.

Формат имени инструмента: `mcp__<сервер>__<инструмент>` — любой символ вне букв, цифр,
подчёркивания и дефиса заменяется на подчёркивание. Это не косметика: именно это полное имя
пишут в правилах разрешений, списке инструментов субагента или матчере хука — короткое имя там
не сработает.

Обнаружение возможностей (шаг 3) не спрашивает модель: это разговор клиента с сервером на уровне
протокола, до того как модель вообще увидела список, — та же механика, что и рукопожатие
транспорта. `local` и `user` в карте выше показаны с одним и тем же файлом `~/.claude.json` — не
ошибка: один физический файл, но две разные записи внутри него, `local` под записью конкретного
проекта, `user` под общим ключом `mcpServers`.

Протокол — открытый, с нейтральным владельцем (см. §A.00). Скилл на прошлом занятии — тоже
открытый формат; у MCP это свойство выражено сильнее — у протокола есть собственная
спецификация и фонд, а сходящаяся практика нескольких поставщиков — это уровень скилла, не MCP.

*Источник фактов — `sem-05/research/mechanics-5-mcp.md` §1.1/§1.4 (транспорты, кто запускает
процесс), §1.2 (области local/user), §2.1–§2.4 (discovery, полное имя, tool search, подпись
вызова).*

### A.1.4. Сцена (пересмотр по сторителлингу, П2 — человек и цена)

Сайт живёт третий месяц; заказчик месяц ведёт задачи в трекере репозитория, перенос между
трекером и чатом агента разработчик делает руками, несколько раз в неделю. **Эпизод:** в среду
утром он копирует в чат задачу «форма не отправляется с телефона»; днём заказчик дописывает в
неё строку «и с планшета тоже»; разработчик её не видит — в чате лежит утренний снимок; вечером
правка уезжает без неё; утром в задаче: «а планшет?».

**Цена, названная в том, что понятно залу:** час на вторую правку, письмо с объяснением — и
заказчик, который теперь перепроверяет, дошло ли написанное им. Ошибся не агент: перенос руками
по устройству отдаёт агенту прошлое состояние задачи. Полный текст сцены — §B.3 (part1c).

Прежняя сцена описывала состояние; факты сохранены все, добавлены промах, цена и человек,
который её предъявляет. На эпизод ссылаются вопрос (§A.1.5) и провал (§A.1.10).

### A.1.5. Вопрос классу (круг 2, часть Б.4 — переписан под «как дать доступ»)

> «Чтобы той среды не повторилось, агент должен сам смотреть открытые задачи трекера в момент
> работы и готовить по ним черновики правок. Выберите способ, которым вы дадите ему доступ
> снаружи, — и объясните, чем остальные четыре подходят хуже именно для регулярного доступа.»

Карточки: `вызвать API напрямую` · `подключить чужой сервер — удалённо` · `подключить чужой
сервер — локально` · `написать свой сервер` · `вызывать готовую команду gh каждый раз`

Три обязательных варианта — из замечания владельца к кругу 1 (issue 225, п.2): API, удалённый
MCP-сервер, свой сервер; локальный MCP-сервер разводит «готовый сервер» на то, где он физически
работает. Пятая карточка (круг 2, построчный разбор n11) заменена на конкретный, названный
инструмент — `gh`, официальный CLI GitHub, вместо прежней неясной «разовой команды», которая не
была про подключение к трекеру. Ни цифры, ни источника на карточках нет — выбор идёт по
рассуждению, не по узнаванию цифры.

### A.1.6. Разбор — поворот кейса (сразу за вопросом, форма А5 — две колонки; круг 2,
построчный разбор n11; пересмотр по сторителлингу, П1)

**Поворот кейса стоит здесь, и он один на весь кейс.** Зал выбирал способ, держа в голове
догадку из §A.1.2: MCP берут затем, чтобы не писать интеграцию. Разбор её опровергает — **кода
интеграции не пишет ни один из пяти способов** — и называет настоящее основание выбора: **знает
ли агент заранее, что у системы можно спросить.** Материал лежал в таблице с начала, первой
строкой второй колонки; пересмотр поднял его в заголовок, в первый блок вывода и в первую фразу
речи. Вторая половина поворота — §A.1.9: подключением покупают список возможностей, за список и
платят; критерий (§A.1.11) этим замыкается.

| Способ | Что делает | Что не делает / ограничение |
|---|---|---|
| вызвать API напрямую | агент сам пишет и шлёт запросы к эндпойнтам, сам разбирает ответ — отдельный код интеграции писать не нужно | заранее не знает спецификацию сервиса: какие есть точки, какие у них параметры и ограничения — без документации или swagger-описания агент их не угадает |
| подключить чужой сервер — удалённо | сервис, который кто-то хостит и обновляет сам; у вас не крутится отдельный процесс | управляете не вы: не видно, что сервис делает внутри и когда в нём что-то меняется; плюс обычные вопросы безопасности удалённого сервиса |
| подключить чужой сервер — локально | пакет исполняется у вас, конфигурация — строка в репозитории, видна всей команде в ревью; контроля больше, чем у удалённого | это всё равно живой процесс на вашей машине и чужой код — со всеми его зависимостями и правом на обновление |
| написать свой сервер | даёт ровно нужный набор операций и прав, без чужого кода в процессе | написать минимальный сервер сейчас быстро — для этого есть готовый плагин; дорого обходится поддержка: протокол, чужие пользователи, безопасность транспорта — отдельный проект рядом с основным |
| вызывать команду `gh` каждый раз | готовый официальный CLI GitHub — авторизацию и разбор ответа он уже решил за вас, кода писать не нужно | каждый вызов — отдельная команда без общего списка возможностей: агент не видит заранее, что вообще можно сделать, нужный вызов приходится знать заранее |

> **Поворот.** Интеграцию не пишут ни в одном из пяти способов: агент сам шлёт запрос и сам
> разбирает ответ. Разделяет пятёрку другое — знает ли агент заранее, что у системы можно
> спросить.
>
> **Что это оставляет.** Свой сервер избыточен: официальный для трекера уже есть. `gh` и прямой
> вызов API закрывают вызов, известный заранее; растущий список операций они перекладывают на
> память разработчика.
>
> **Два законных варианта.** Между «удалённо» и «локально» готового ответа нет: свежий
> официальный пример для этого же сервиса подключается удалённо, а решение этого занятия —
> локальный процесс, потому что тогда конфигурация становится кодом в репозитории, видимым в
> ревью всей команде.

**Правка А3 (круг 2):** старая терминология «барьер» снята из заголовков следующего шага — ниже
просто называется, что решается: какие операции разрешить и какие права под них выдать.

### A.1.7. Со-сборка — две части

**Часть 1 (операции → права).**
Ход 1: «Что конкретно агент должен делать?» Зал называет, список фиксируется: читать открытые
issue; писать комментарий; создавать черновик правки. Ничего про удаление, настройки репозитория,
другие репозитории.

Ход 2 — вычёркивание прав. На слайде список того, что даёт широкий персональный токен «по
умолчанию»: все репозитории пользователя, включая приватные · чтение и запись · управление
настройками · удаление. По каждой строке — вопрос «нужно для нашего списка операций?» Лишнее
вычёркивается на слайде. Остаётся: один репозиторий, чтение issue, создание черновика правки.

«Запомните, как выглядит этот экран сейчас. Через несколько минут я покажу вам инцидент, который
воспроизводится ровно тогда, когда верхняя строка не вычеркнута.»

**Часть 2 (ключ → область).**
Ход 3: «Где хранить ключ?» В переменной окружения, не в файле.

Ход 4: «Куда положим сам файл?» Три варианта: только у меня на этой машине (`local`, дефолт) · в
репозиторий, для всех (`project`) · глобально во всех моих проектах (`user`). В репозиторий —
целевое для проверенного сервера. Только у меня — целевое для эксперимента. Дефолт команды
подключения кладёт сервер в `local`, не в `project` — если про это не знать, получится разговор
«я подключил, всё работает» — «а у меня нет», и оба правы.

### A.1.8. Артефакт

`.mcp.json` в корне `signup-landing/`:

```json
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_PAT}"
      }
    }
  }
}
```

Четыре строки существа: чем запускается, что запускается, откуда ключ (подстановка из окружения),
и — вне файла — какие права у этого ключа: один репозиторий, не вся учётная запись.

Механика конфигурации коротко: три области — физически разные файлы (`local`/`user` —
`~/.claude.json`, `project` — `.mcp.json` в корне репозитория). При конфликте имён побеждает вся
запись приоритетной области целиком, поля не смешиваются: `local` → `project` → `user` →
сервер из плагина → коннектор → политика организации.

**Честный пробел, названный здесь один раз (см. §A.00).** Этот файл — целевое решение раздела,
снятое с более раннего захвата демо-репозитория; коммита с ним в текущей ветке `signup-landing`
нет, и в репозитории курса такого файла тоже нет. Слайд показывает разбираемый пример, не
обещает «склонируй и повтори».

### A.1.9. Постоянная плата одинакова — вторая половина поворота (круг 2, часть А9; пересмотр
по сторителлингу, П1 и П5)

**Заголовок слайда:** «Постоянная плата одинакова: своё, чужое, локально, удалённо»; прежняя
оговорка про худший случай сохранена в утверждении слайда и в речи.


«Подключение стоит X токенов» — утверждение о режиме **без отложенной загрузки**. По умолчанию
на актуальных моделях при старте сессии в контекст попадают только имена инструментов и короткая
инструкция сервера; полная схема конкретного инструмента подгружается отдельно, когда модель сама
решает, что он может понадобиться (управляется переменной `ENABLE_TOOL_SEARCH`).

| Значение | База сравнения |
|---|---|
| ≈55 000 токенов ≈ 21% окна 200К — связка из 5 серверов без отложенной загрузки | контекст без подключённых серверов — 0; это худший случай, не дефолт |
| 1 365 против 44 026 токенов — одно и то же действие через CLI и через MCP | 32-кратная разница при одинаковом результате |

**Сопоставление по способам доступа (круг 2, часть А9).** Постоянная плата — имя и инструкция
каждого подключённого сервера в контексте всегда — одинакова у своего сервера, у чужого локально
и у чужого удалённо: транспорт и то, кто автор, на неё не влияют, влияет только число
подключённых серверов и их инструментов (§A.1.3, пункт 5). Не платит её только то, что вообще не
MCP-сервер — прямой вызов API или команда `gh`: именно это и показывает строка 1 365 против
44 026 выше, тем же приёмом, которым сравнивались варианты доступа в §A.1.6. Эта оценка — не
придуманная: источник тот же, что и у 21%/55 000 (`research/stage-5-mcp.md` §1.3, getunblocked.com,
«line-item autopsy», 2026).

**Вопрос «к себе» — единственный в блоке** (П5): «Сколько серверов подключено у вас прямо
сейчас и сколько инструментов они описывают? Эту плату вы вносите в каждой сессии — даже там,
где агент не сходил ни к одному.» Диагностических команд кейса 2 вопрос не называет.

Проверить у себя: не выставлен ли `ENABLE_TOOL_SEARCH=false`, и что реально показывает карточка
конкретного сервера в сессии — это не цифра, которая устареет, это команда, которая всегда
актуальна.

### A.1.10. Провал — чужая инструкция в issue заставила агента опубликовать приватный код
(круг 2, построчный разбор n16 — заголовок называет риск напрямую, без отсылки к экрану
со-сборки)

Вернёмся к ходу 2 со-сборки (§A.1.7): строка «все репозитории пользователя, включая приватные» —
ровно та, которую только что вычеркнули.

**Смертельное трио** (Simon Willison, 16.06.2025) — название для сочетания трёх возможностей,
которые вместе делают утечку возможной без единой строчки кода эксплойта: доступ к приватным
данным, обработка недоверенного внешнего контента, канал наружу. Не хватает хотя бы одной — атака
этого типа невозможна, не «маловероятна». *(Круг 2: определение дано здесь, до обоих слоёв ниже —
на прежнем слайде термин в слое 2 использовался раньше, чем появлялось его определение; владелец
назвал это «утверждением с выдернутым контекстом».)*

**Слой 1 — эксфильтрация в связке.** Май 2025 (Invariant Labs). Агент с доступом к трекеру под
персональным токеном с правами на все репозитории пользователя, включая приватные. Атакующий
создаёт в публичном репозитории issue с инструкцией собрать данные о других репозиториях этого
пользователя и опубликовать здесь. Разработчик просит агента разобраться с открытыми issue. Агент
честно читает issue — встроенная инструкция попадает в контекст как задача, неотличимая от
легитимной. Читает приватные репозитории, публикует их содержимое в автоматически созданном
публичном PR. CVE не присвоен — архитектурный класс, не баг кода. Убрать строку «все репозитории,
включая приватные» — читать нечего, сценарий не проходит вообще.

**Слой 2 — без модели вообще.** CVE-2026-61742 (DBHub, 24.09.2026, CVSS 9.3): HTTP-транспорт по
умолчанию слушает без аутентификации, защита от межсайтовых запросов обходится DNS rebinding.
Счёт «два HTTP-запроса и ноль учётных данных до захвата» — деталь вторичного технического
разбора (Strix.ai), не первичной записи NVD/GHSA, и называется с этой оговоркой — против
«обычной» атаки через prompt injection, которая требует хотя бы одного успешного чтения агентом
вредоносного текста. Смертельное трио — не единственный путь к утечке: сервер сам может быть
незащищённым сетевым сервисом, и этот случай именно такой.

### A.1.11. Когда MCP нужен, а когда нет (круг 2, часть А7 — рамка «ещё рано / не нужно вообще»
снята целиком)

**Заголовок слайда:** «Когда MCP нужен, а когда не нужен» (владелец дословно: «напиши: когда MCP
нужен, когда не нужен, прямо чётко, не надо чтобы люди догадывались» — прежние заголовки «ещё
рано» и «не нужно вообще» запрещены этим же правилом как рамка).

| MCP нужен, когда | MCP не нужен, когда |
|---|---|
| доступ нужен регулярно, из нескольких сессий — разового снимка данных недостаточно | доступ разовый или редкий, и снимка данных на сегодняшний день достаточно |
| вы готовы поддерживать ещё один постоянно работающий процесс с доступом к секретам | такой готовности нет — тогда разовый вызов надёжнее процесса, который никто не обслуживает |
| операций больше одной, список операций растёт, и агент сам решает, к какой обратиться — за этот список и вносится постоянная плата | задача сводится к одному известному вызову CLI: список возможностей не нужен, а тридцатидвухкратная разница по токенам никуда не денется |
| подключение не достраивает третий элемент смертельного трио | подключение достраивает третий элемент смертельного трио — доступ к приватным данным и обработка чужого текста уже есть, остаётся канал наружу; это стоп-критерий |

Третья строка названа через список операций — то, за что по повороту кейса (§A.1.6, §A.1.9) и
вносится постоянная плата: сервер нужен ровно тогда, когда список стоит своей цены.

Есть доступ наружу. Следующий вопрос — что происходит, когда сервер подключён, а работы от него
нет.

## A.2. Кейс 2 — «подключён, а агент через него не ходит»

**Статус: написан заново, круг 2 правок владельца применён (issue #225); круг сторителлинга
переставил кейс на обратный ход.** Сырьё — `research/mechanics-5-mcp.md` §3 (статусы, два
тайм-аута — теперь только в заметках докладчика) и §4 (отладка, два реальных инцидента этого
проекта), `research/stage-5-mcp.md` §4.1 и §6 (DBHub CVE-2026-61788, инцидент `[#49]`). Круг 2
снял с экрана технику и построил кейс на двух пользовательских вопросах: как понять, что сервер
реально работает, и как правильно задать вопрос агенту. Числа и источники не менялись.

**Круг сторителлинга (`PERESMOTR-STORITELLING.md`, П1/П2/П4/П5/П6).** Этот кейс выбран тем,
который в блоке MCP идёт **иначе**: он рассказывается **с конца**. Кейсы 1 и 3 идут общей схемой
(дивайдер, сцена, вопрос, разбор, механика, провал, граница), и к третьему разу зал предсказывает
следующий экран — замечание студента на прожарке. Здесь развилка открывает кейс его **финалом**,
сцена восстанавливает приведшую к нему неделю, а голосование спрашивает, какой проверки человеку
не хватило.

Четыре сквозные правки. **Поворот вынесен в развилку (П1):** проверка была настоящей и говорила
правду — о том, что процесс поднят; работу агента доказывает вызов, подписанный именем сервера
(прежде эта мысль вскрывалась только на разборе и читалась как техническая оговорка). **Человек
и цена (П2):** статусу поверил тот, кто сам собрал этот сервер в прошлом кейсе, и потратил пять
рабочих дней, прежде чем узнал, что ответы агент строил из общих соображений о том, что обычно
лежит в трекере; цена — неделя отчётов о работе, которой не было, и разговор с заказчиком, в
котором нечего показать. **Вопрос «к себе» (П5)** — один на блок, в конце разбора. **Кейс
сокращён (П6):** слот с 11,0 до 10,0 минуты при тех же девяти слайдах, ничего не снято, минута
уходит в общий резерв занятия; записанная речь тоже короче (1103 слова против 1134), хотя кейс
прибавил человека, цену и вопрос в зал.

### A.2.1. Заголовок дивайдера

> **Пять дней он верил зелёной галочке**

Смысловая строка: «Пять рабочих дней разработчик верил зелёной отметке подключения. Проверка была
настоящей и говорила правду — о том, что процесс поднят. За эти пять дней агент ни разу не
заглянул в трекер.»

Прежний заголовок («Решаем, что делать, когда сервер подключён, а агент через него не ходит») был
шестым подряд в одной грамматике и обещал процедуру. Наблюдаемая проблема правилом А2 по-прежнему
названа — в карте занятия (`n05`, ячейка кейса 2); развилка её разыгрывает, начиная с исхода. Тег
дивайдера снят правилом А6 и не возвращается.

### A.2.2. Сцена — та же неделя изнутри

Заголовок слайда: «Неделя, в которой ничего не сломалось». Сервер доступа к трекеру из прошлого
кейса стоит две недели.

В понедельник разработчик просит агента разобрать входящие задачи за выходные и подготовить
черновики; ответ звучит как итог работы. Вторник, среда, четверг — то же каждое утро: «всё
сделал», «новых задач не нашёл», «во входящих пусто», и он пересылает это заказчику. В среду он
смотрит статус подробнее, в четверг спрашивает агента напрямую, почему тот считает, что задач
нет, — всё сходится. В пятницу заказчик спрашивает про задачу, которую завёл во вторник: в
репозитории за неделю ни черновика, ни комментария.

Всю неделю `claude mcp list` показывал `✔ Connected`: процесс поднят и ответил на рукопожатие.

Две собственные проверки человека (среда, четверг) добавлены этим кругом намеренно: без них он
выглядит невнимательным, и кейс рассыпается — учить нужно тому, что три честные проверки подряд
дают ноль фактов о работе агента. Они же — опора голосования A.2.3. Три реплики агента остаются
по прежней причине: «не нашёл» и «пусто» звучат честно, и ни одна из трёх не наблюдение.

### A.2.3. Вопрос классу

> «За неделю он сделал три из этих четырёх проверок — и остался без ответа. Выберите ту, которой
> ему не хватило, и скажите, чем она отличается от остальных трёх.»

Карточки (состав не менялся): `ничего — статус зелёный` · `посмотреть, что именно показывает
статус подробнее` · `спросить агента, почему он решил, что всё сделал` · `явно попросить агента
обратиться к серверу по имени и показать вызов`

Карточку назовут быстро — работает вторая половина вопроса. Голосование остаётся в прежнем
формате (защищено `CUT-ORDER.md`); меняется то, о чём спрашивают: зал судит уже случившееся.
«Удалить и подключить заново» и «написать автору» сняты как первые ходы — к ним возвращается
граница кейса (A.2.8).

### A.2.4. Разбор (форма А5 — две колонки)

Заголовок слайда: «Три проверки — правда. Правда о другом». Колонки переименованы в прошедшее
время, форма двух колонок сохранена.

| Проверка | Что доказала | Чего не доказала |
|---|---|---|
| ничего — статус зелёный | процесс сервера поднят и ответил на рукопожатие | что агент обращался к нему в этой задаче — это отдельный факт |
| статус подробнее | различает «процесс не поднялся», «список инструментов не получен», «нужна авторизация» — круг причин сужается | вызывал ли агент сервер именно сейчас: статус живёт отдельно от конкретной задачи |
| спросить агента | иногда вскрывает причину сразу: агент признаётся, что не нашёл способа проверить и ответил по смыслу задачи | агент пересказывает своё понимание; наблюдения за транспортом в пересказе нет |
| попросить обратиться к серверу по имени и показать вызов | вызов инструмента в выводе подписан именем сервера — это видимый факт | требует заранее знать имя сервера и чуть более точной формулировки задачи |

> **Статус говорил правду — о том, что процесс поднят.** Работу агента доказывает одно: вызов,
> подписанный именем сервера. Три честные проверки за неделю дали ноль фактов об этом.

> **У кого прямо сейчас подключён хоть один сервер — и когда вы последний раз видели его имя в
> выводе агента?**

Вопрос в зал стоит последним блоком, после ответа, и голосования не открывает: это единственное
место блока MCP, где материал прикладывается к проекту слушателя (П5).

### A.2.5. Со-сборка / механика — в двух частях

**Часть 1 — как понять, что сервер реально работает.** Статус (`claude mcp list`/`/mcp`)
различает больше, чем одно слово «подключено» — отдельно видно, поднялся ли сам процесс и
получен ли список инструментов. Но даже такой подробный статус — факт про процесс, не про то,
обращался ли к нему именно агент в этой задаче. Минимальное доказательство — явное упоминание
сервера в запросе («используя сервер такой-то, узнай…»); признак, что ответ пришёл именно
оттуда, — вызов инструмента в выводе подписан именем сервера. Отдельно: долгий ответ — не всегда
сбой, запуск сервера и выполнение уже начатого вызова идут по разным часам.

**Часть 2 — как правильно задать вопрос агенту.** Расплывчатая просьба («посмотри, что
скопилось, и подготовь черновики») не даёт доказательного вызова — агент может ответить по смыслу
задачи, вообще не тронув сервер. Явное имя сервера в тексте запроса («используя сервер трекера,
выведи список открытых задач…») и есть доказательный вызов, применённый к формулировке: после
такой просьбы есть что проверить — подписан ли вызов в выводе именем сервера.

Технические детали — коды пяти статусов, точные тайм-ауты (`MCP_TIMEOUT` 30 с, `MCP_TOOL_TIMEOUT`
≈28 ч) и асимметрия переподключения (удалённый — сам, локальный `stdio` — нет) — остаются
подтверждёнными фактами курса, но круг 2 убрал их с видимого экрана по правилу А8: на уроке они
живут в «если спросят» заметок докладчика, не в теле кейса.

### A.2.6. Артефакт — записанная процедура, не новый файл

Этот кейс не меняет конфигурацию — его решение процедурное, и это стоит сказать прямо, не
выдавая его за файл, которого нет. Команда добавляет в `CLAUDE.md` проекта (тот же файл, где уже
живёт раздел про ветки) короткую строку правила: после подключения любого сервера и после любого
подозрения в тишине — явный именованный вызов, прежде чем доверять зелёному статусу. Это строка в
файле, который уже есть, не новый артефакт — и она проверяется так же, как остальные правила
этого проекта: прочитана, не исполняется сама.

**Почему именно CLAUDE.md, не хук (добавлено кругом 2 по прямому запросу владельца).** Прошлое занятие
уже показало оба вида правил рядом в одном файле: «Repository etiquette» — записанное словами
правило, которое читает человек или агент и решает, следовать ли ему; «Хук защиты ветки» —
настоящий код, который срабатывает сам на git-команду, без решения в моменте. Хук умеет
реагировать только на чётко описанное событие — команда, имя файла, код выхода. «Подозрение в
тишине» таким событием не является: его нельзя формально описать заранее, оно требует, чтобы
кто-то заметил и решил, что пора проверить. Вот почему это строка в CLAUDE.md, не механизм —
решение процедурное именно потому, что решает человек, не правило.

### A.2.7. Провал — слоями, по последствиям и по тому, как заметили

**Слой 1 — сервер сам говорит неправду о своём режиме.** Команда работала с MCP-сервером для баз
данных одного известного производителя в режиме, который считали ограниченным только чтением, —
именно для того, чтобы агент не мог ничего испортить в чужой базе. Флаг `readonly = true` у
инструмента `execute_sql` на деле не делал соединение реально ограниченным — код, который должен
был это гарантировать, ссылался на поле конфигурации, которое никогда не заполнялось (CVE-2026-
61788, DBHub, 24.09.2026, CVSS 7,4 из 10). Разработчики сервера сами были уверены, что режим
работает, — узнали только тогда, когда кто-то выполнил запрос с реальным побочным эффектом и
увидел, что он прошёл.

**Слой 2 — доступ пропадает тихо, транспорт жив.** Инцидент `[#49]` этого же проекта
(`notes/mcp-limitations.md`): инструменты, которые ещё вчера работали, однажды перестали — без
предупреждения, без красного статуса; `claude mcp list` продолжал показывать `✔ Connected`.
Заметили не по статусу — по тому, что обычные вызовы начали требовать повторного входа. Причина —
OAuth-приложение `workspace-mcp` в статусе `Testing` в Google Cloud Console автоматически отзывает
`refresh_token` через 7 дней без активности; то же приложение в статусе `In production` токен не
отзывает вовсе — «долгий» или «короткий» интервал тут ни при чём, это целиком следствие одной
невыбранной настройки публикации.

Оба слоя проверяются одинаково — реальным действием с наблюдаемым результатом, не чтением
настройки сервера.

### A.2.8. Критерий

**Заголовок слайда:** «Когда достаточно посмотреть на статус, а когда нужно вызвать самому»
(переформулировано кругом 2 — владелец просил конкретнее: «читать» против «дёргать самому»)

**Достаточно посмотреть на статус:** сервер используется нерегулярно, под наблюдением человека
при каждом вызове.

**Нужно вызвать самому — доверять флагу, который сервер не может независимо подтвердить, не
нужно никогда** (если для задачи хватило бы режима только чтения, но сервер не даёт способа
убедиться, что он реально включён — разумнее завести отдельную роль/учётную запись с урезанными
правами на уровне самой базы данных: флаг сервера такой гарантии не даёт).

**Или решение — не подключать вовсе:** явный вызов систематически не проходит и автор сервера не
отвечает — вопрос смещается туда же, где решался первый кейс этого блока: подключать ли сервер
вообще.
