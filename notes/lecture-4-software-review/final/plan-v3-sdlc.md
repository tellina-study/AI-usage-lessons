# План v3 — Лекция 4 «AI в жизненном цикле разработки ПО (SDLC)»

## 0. Что меняется относительно v2

**Было (v2):** несущая ось — лестница автономности A→B→C→D. Разделы = уровни автономности.

**Стало (v3):** несущая ось — **фазы SDLC**; AI показан как обзор подходов ведущих вендоров и методологов, обобщённых по фазам. Лестница A→D **демотирована** до 2 обзорных слайдов в Разделе 0 (остаётся ментальной линзой «режим ≠ бренд», не каркасом).

**Ключевая педагогическая находка ресёрча:** фазы SDLC **неравномерны** по зрелости AI — сильные (реализация, ревью, безопасность, требования) и тонкие (архитектура, CI/CD, эксплуатация, где ни один вендор не делает продукт). Эта неравномерность — сама по себе учебный материал и естественный источник «когда AI не нужен/не применим» (≥30%).

**Несущая ценность (P1 #4, ENFORCED в плане):** лекция отвечает не на «какие есть тулы», а на **«в какой фазе какой режим AI оправдан, а где — нет»**. Вендоры — иллюстрация, не предмет. Каждый вендор-слайд заканчивается микро-суждением «устойчивый паттерн X (остаётся) / вендор-хайп Y ([VFY])».

**Источники (готовы):** `notes/research/lecture-4/{anthropic-sdlc-kit,other-vendors-sdlc,methodologists-and-failures}.md`.

## 1. Центральный вопрос (переформулирован)

> AI-инструменты покрывают весь жизненный цикл разработки — **но по-разному в каждой фазе**. Где AI реально усиливает фазу, где создаёт ложную уверенность, где не достаёт вовсе — и что в работе инженера НЕ делегируется ни в одной фазе?

## 2. Учебные цели (mapping)

- **LO1** — распознавать, в каких фазах SDLC AI помогает, в каких вредит/создаёт ложную уверенность, в каких не применим.
- **LO4** — применять чек-лист «когда AI да / когда нет» по фазам к своей задаче.
- **LO7** — соотносить подходы вендоров/методологов с фазами и отличать устойчивый паттерн от вендор-хайпа.

## 3. Несущая ось, keystone и фундаментальные концепты (P1 #3)

**Keystone-слайд (s05):** несёт (а) **определение** «фаза SDLC = стадия жизненного цикла со своими входами/выходами/артефактом»; (б) сам **цикл** intent → spec → design → code → test → review → ship → operate → docs; (в) **находку-неравномерность** — AI касается каждой фазы по-разному (сильные vs тонкие). Предъявляется в Разделе 0 **ДО** первого погружения; заголовок и 1-я строка — про саму ось, НЕ про устройство курса и НЕ защитный recap. (Pre-USER-GATE §6; цена пропуска в Лекции 4 = ~5 циклов deck.)

**Ввод фундаментальных концептов до первого употребления (chapter §0, P1 #3):**
- **SDLC-фаза** — определяется на s05 / chapter §0.
- **automation bias / ложная уверенность** — центральный механизм «когда AI вредит»; вводится в chapter §0, до первого употребления на s27 (Stanford).
- **Brooks essential vs accidental complexity** — вводится в chapter §0 (или §2-intro), до употребления на s12 (архитектура). Устраняет term-сироту (в v2 Brooks появлялся только в синтезе).

### Раздел 1 — Требования и планирование (s08–s10) — 3 слайда
- **s08** Divider «Требования · spec-driven».
- **s09** Вендоры: AWS **Kiro** (EARS: requirements→design→tasks), GitHub **Spec Kit** (`/specify→/plan→/tasks→/implement`), Anthropic **plan mode** (нельзя редактировать до accept), Atlassian **Rovo/Jira** (декомпозиция задач). *Суждение:* устойчивый паттерн = spec-first как контроль дрейфа; хайп = «spec = единственная истина»[VFY].
- **s10** **[SI]** Провал/лимит: prompt-and-pray → невысказанные допущения; узкое место = **human intent, не модель**; «spec = истина» — вендор-overclaim (docs = контекст, код = истина).

### Раздел 2 — Архитектура и дизайн (s11–s13) — 3 слайда, целиком «когда не AI»
- **s11** Divider «Архитектура · где AI не достаёт».
- **s12** **[SI]** Честный разрыв: ни один вендор не делает продукт для архитектуры; всплывает лишь как side-step (Kiro design.md, Spec Kit `/plan`). **Brooks essential complexity** не делегируется.
- **s13** **[SI]** **Poisoned context** (AI копирует плохие примеры кодбазы) → почему дизайн остаётся человеческим. Альтернатива: ADR + человеческое проектирование.

### Раздел 3 — Реализация / кодирование (s14–s19) — 6 слайдов, главное поле
- **s14** Divider «Реализация · главное поле».
- **s15** Две философии (диаграмма): **in-editor human-in-loop** vs **async delegation**; здесь же A→D как «режимы реализации» (единственная точка, где демотированная лестница работает на контент).
- **s16** In-editor: Cursor (Agent/Composer), JetBrains **Junie** (реальный дебаггер), Windsurf. *Суждение:* режим = синхронный контроль, IDE-нативность — moat; бренды меняются[VFY].
- **s17** Async — **сгруппировано по РЕЖИМУ, не 6 логотипов**: «клонировать репо в облаке → открыть PR» (Codex Cloud / Jules / GitHub coding agent / Devin как примеры); Anthropic explore→plan→implement→commit + `/batch`. *Суждение:* async = режим C→D, бренды взаимозаменяемы[VFY]; отличается зрелостью гейтов.
- **s18** **[SI]** Провал: **70%-проблема** (Osmani) + «почти правильно» (SO 66%) + knowledge paradox (усиливает seniors > juniors). Урок: скорость кода ≠ качество ПО; читать diff до accept.
- **s19** **[SI]** Anti-hype: **Devin** 13.86% SWE-bench (только 25% бенча, контаминация признана); **Cursor** признаёт, что GPT-5/Sonnet сильнее его Composer. Бренд ≠ доказательство автономии.

### Раздел 4 — Тестирование и QA (s20–s22) — 3 слайда
- **s20** Divider «Тестирование».
- **s21** Вендоры: AWS **Q /test**, **Qodo** (test-first), JetBrains; Anthropic **TDD** (failing-test→fix) + Stop-hook гейт + инциденты → регресс-тесты. *Суждение:* устойчивый паттерн = тест-как-исполняемая-спека + детерминированный gate; хайп = «AI сам покрыл»[VFY].
- **s22** **[SI]** Провал: LLM говорит «all green», тесты падают (Fowler); **coverage↑ (32% vs 5.3% классов) но mutation-kill↓ (2.4% vs 15%)** (Meta). Урок: детерминированный test-run **gate**; mutation, не coverage.

### Раздел 5 — Ревью кода + Безопасность (s23–s29) — 7 слайдов, тяжёлый failure-кластер
- **s23** Divider «Ревью + Безопасность» (методически связаны: оба про «поймать то, что AI внёс/пропустил»).
- **s24** Ревью-вендоры: GitHub **Copilot code review**, Cursor **Bugbot**, **Qodo Merge**, Atlassian Rovo (валидация против Jira-критериев); Anthropic adversarial fresh-context / writer-reviewer. *Суждение:* устойчивый паттерн = AI-review как assist; хайп = review как gate[VFY].
- **s25** **[SI]** Провал ревью: Thoughtworks **«Complacency with AI-generated code»** (Radar **Hold**); AI-review ~19.4% F1 / высокий FP (vs human-review baseline); **curl** закрыл bug-bounty (valid-rate <5%). Урок: AI-код ревьюить **больше**, не меньше.
- **s26** Безопасность-сигнатура: GitHub **Autofix+CodeQL+secret+Dependabot**; Google **Big Sleep** (живой SQLite zero-day) + OSS-Fuzz (20-летний OpenSSL баг); Anthropic **`/security-review`** + least-privilege identities. *Суждение:* устойчивый паттерн = обязательный SAST-гейт; хайп = «AI закрыл безопасность»[VFY].
- **s27** **[SI]** Провал безопасности: **Stanford** — код менее безопасен + больше уверенности (**automation bias**); **NYU ~40%** уязвимы (1689 программ / 89 сценариев MITRE Top-25). *(reuse s21-old.)*
- **s28** **[SI]** Провал безопасности: **slopsquatting** (576k сэмплов, supply-chain — отдельный класс); **CamoLeak** CVSS 9.6 + утечка корп-секретов. *(reuse s22-old/s23-old.)*
- **s29** **[SI]** Кульминация: **Replit** стёр prod-БД в code-freeze и солгал о rollback. *(reuse s16-old.)* Урок: автономный агент без hard-gate = катастрофа; accountability не делегируется.

### Раздел 6 — CI/CD + Эксплуатация + Документация (s30–s32) — 3 слайда, тонкий трио + bright spot
- **s30** Divider «Доставка · эксплуатация · доки».
- **s31** **[SI]** CI/CD + Эксплуатация (объединены — обе тонкие): агенты **потребляют** пайплайны, не владеют; Anthropic headless `-p` + `--allowedTools` + **human-only prod gate**; эксплуатация — **слабейшая фаза**, только AWS **Q CloudWatch** (владеет телеметрией). Где AI пока не достаёт.
- **s32** Документация — **bright spot**: DORA 2024 **+7.5% (на +25% adoption; парно со stability −7.2%)**; Atlassian Confluence AI. **[SI]** Провал: **cognitive debt** (генерация обгоняет понимание, Radar Hold); онбординг-доки галлюцинируют setup/deploy.

### Раздел 7 — Обобщение + фреймворк решения (s33–s37) — 5 слайдов

- **s34** **СИНТЕЗ — матрица «фаза SDLC × сила/риск AI × вендор-лидер»** (несущий слайд обобщения). *(переделка decision-matrix s29-old.)*
