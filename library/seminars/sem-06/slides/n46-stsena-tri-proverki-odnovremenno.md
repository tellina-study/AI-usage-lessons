# Три проверки вместо одной по очереди

## Assertion

Три независимых правки обычно проверялись по очереди: запуск, ожидание, следующий запуск. Сегодня все три запускаются одним действием — и итоги приходят примерно тогда же, когда пришёл бы один.

## Visual

**Было.** Диф-ревьюер — роль с одностраничника этой ступени — уже используется каждый день. Три независимых изменения — поправки в трёх разных, не связанных друг с другом формах — проверялись одно за другим: запустить проверку первой правки, подождать итог, запустить вторую, снова подождать, и только потом третью.

**Стало.** Разработчик запускает все три проверки одним действием, без единой строки настройки: три отдельных вызова одной и той же роли, каждый на свою правку. Роли не знают друг о друге и не делят между собой ничего — у каждой свой контекст, свой набор файлов, нужных для её конкретной правки.

> **Итоги приходят примерно тогда же, когда пришёл бы один — не три раза по одному.**

## Speaker notes

Диф-ревьюер — та самая роль, которую мы видели целиком на одностраничнике ступени, — уже используется каждый день, и правки у разработчика теперь идут не по одной: три независимых изменения — поправки в трёх разных, не связанных друг с другом формах — готовы к проверке одновременно. Раньше это означало то же самое, что обычно: запустить проверку первой правки, подождать итог, запустить вторую, снова подождать, и только потом третью.

Сегодня разработчик запускает все три проверки одним действием, без единой строки настройки: три отдельных вызова одной и той же роли, каждый на свою правку. Роли не знают друг о друге и не делят между собой ничего — у каждой свой контекст, свой набор файлов, нужных именно для её правки. Итоги приходят примерно тогда же, когда пришёл бы один — не три раза по одному.

Если спросят, можно ли на той же фактуре показать и предел выгоды: да, и дальше в этом кейсе разберём именно это — на двух разных ролях, проверяющих разные стороны одной и той же правки, вместо трёх копий одной роли на разные правки.
