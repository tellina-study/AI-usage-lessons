# What else is set up right away

## Assertion

The gate is not the only cheap baseline: three more practices are set up on the first day and do not wait for a signal.

## Visual

**1. The create - roast - improve loop.** Not "wrote it and shipped it", but four steps:

- **create** — a draft of the solution or the plan, rough and fast;
- **roast** — go through it with a fixed list of questions: is this the simplest version that works? which assumptions are unverified? is there a premature abstraction? does every new file have an owner? are risky changes bundled into one batch when they should have been separated?
- **improve** — make the edits that came out of the breakdown;
- **show it and get sign-off** — before the work itself begins.

> "We have just read that self-critique with no external signal makes the result worse. The roast is not that. There are two external signals here: the fixed list of questions, which does not depend on what the agent wrote a minute ago, and the human at the "show it" step. And what gets roasted is the plan, not finished code — the place where an edit is cheapest."

A live example: the team making this course works exactly this way — the loop is written into its instruction file as mandatory for any non-trivial task, together with the list of roast questions itself.

**2. A progress log for the task — in any form.** A file per task, a list of steps with marks, a plain text log — the form does not matter, what matters is that it exists. Why on the first day: everything that is held only inside the session is unavailable by the next session — it has to be reconstructed from scratch, and that does not always work.

> "How such a log is kept, what forms it takes and exactly where it breaks — a separate case in the section on memory."

**3. A rule is written down together with its reason.** Next to every rule in the instruction file — a "why" line: which case gave rise to it and how that case ended. Why: a rule with no reason reads like a matter of taste a month later and is the first to be dropped; a rule with a named cost of violation is already a ready-made criterion showing when the text needs to be backed by a mechanism. The same live example — in the course team's instruction file the mandatory rules carry a "why" line with the concrete case that gave rise to them.

**Closing line:**

> "None of the three requires a signal and none of them costs almost anything on the first day. That is why they are set up right away — together with the gate, not instead of it."

## Speaker notes

"It is easy to take the wrong conclusion away from case 1.2: the only thing worth setting up in advance was one line, which we have just been told is unreliable. So there is not much to do in advance. That is not so, and here are three things that get set up on the first day.

The first one is the create, roast, improve loop. A draft of the plan, then a pass over it with a fixed list of questions: is this the simplest version that works; which assumptions are unverified; is there a premature abstraction; does every new file have an owner; are risky changes bundled into one batch. Then the edits — and only then show it and get sign-off. A minute ago we read that self-critique with no external signal makes the result worse — and this is not a contradiction. There are two external signals here: the list of questions, which does not depend on the text just written, and the human at the "show it" step. And what gets roasted is the plan, not finished code — that is where an edit is cheapest. The team making this course works exactly this way: the loop is written into its instruction file as mandatory for any non-trivial task.

The second one is a progress log for the task, in any form. A file per task, a list of steps with marks, just a log. Everything that is held only inside the session is unavailable by the next session. How such a log is kept and where it breaks — a separate case in the section on memory.

The third one is that a rule is written together with its reason. Next to the rule, a line: which case gave rise to it. A rule with no reason reads like a matter of taste a month later and is the first to be dropped. A rule with a named cost of violation is a ready-made criterion showing when the text needs to be backed by a mechanism. That very criterion: name the action, the cost and the frequency."
