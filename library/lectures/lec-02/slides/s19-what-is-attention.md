# Visible content

## Title bar
«Внимание — распределение весов на весь контекст: три проекции Query / Key / Value»

## Body
[Gold callout — сразу под заголовком]
**Q — про текущий шаг. K и V — про уже обработанный контекст.**

[Строка-схема из трёх плашек]
**Query** — «что я сейчас ищу» · **Key** — «что я предлагаю» · **Value** — «что я отдам, если меня выбрали»

[Worked-пример на нашем предложении, Ocean rounded box]

«Кот съел мышь, потому что **он** был голоден»

- **Q(«он»)** = «ищу: кто мог быть голоден»
- **K(«Кот»)** = «я — одушевлённый субъект»
- **V(«Кот»)** = содержимое, которое вольётся в представление «он»

Совпадение Q(«он») и K(«Кот») даёт высокий вес → V(«Кот») определяет обновлённое представление токена «он»

[Справа — bar chart, Ocean rounded box]

**Распределение весов на токенах контекста — сумма = 1**
[Bar chart на 7 токенах — та же нарезка, что в матрице s18; лидер «Кот» — gold, согласуется с s18]

[3 нумерованных факта]
1. На вход — **все токены контекста**.
2. На выходе — **распределение весов, сумма = 1**.
3. **Пересчитывается на каждом шаге** генерации.

[Строка-подпись внизу, курсив]
*Метафора: фонарик в тёмной комнате — луч направлен на релевантные токены, яркость света = вес внимания.*

## Speaker notes

Зафиксируем определение точно. Рабочая метафора — фонарик в тёмной комнате: все токены контекста присутствуют, но луч направлен на те, что релевантны текущему вопросу, и яркость по предметам — это веса. Формально на каждом шаге внимание возвращает распределение весов на все токены контекста, сумма равна единице, и это распределение пересчитывается на каждом шаге генерации заново.

Теперь — один уровень глубже, на нашем же предложении, чтобы не потерять конкретику. Для каждого токена модель вычисляет три проекции его вектора: Query, Key и Value. Возьмём токен «он» из «Кот съел мышь, потому что он был голоден». Его Query можно грубо прочитать как «ищу: кто мог быть голоден» — запрос текущей позиции к остальному контексту. Токен «Кот» предлагает свой Key — нечто вроде «я — одушевлённый субъект», визитную карточку, по которой его находят чужие запросы. Когда Query «он» и Key «Кот» хорошо совпадают, вес между ними получается высоким — именно это мы видели в матрице на предыдущем слайде. А дальше в дело вступает Value «Кот» — содержимое, которое реально вливается в обновлённое представление токена «он». Итог позиции «он» — взвешенная сумма Value всего контекста, где Value «Кот» вносит наибольший вклад.

Простыми словами: Query — это вопрос, который задаёт токен; Key — это то, чем токен отвечает на чужие вопросы; Value — это то, что токен реально передаёт, если его выбрали. Запомнить стоит одно структурное наблюдение: Query — про текущий шаг, а Key и Value — про уже обработанный контекст, который не меняется. Из этой асимметрии вырастает главная оптимизация всей индустрии вывода моделей — увидим её на следующем слайде, когда разберём, почему длинный чат тормозит.
