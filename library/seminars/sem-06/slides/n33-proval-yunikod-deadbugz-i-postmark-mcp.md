# Восемь из восьми, три вызова в запасе, полторы недели тишины

## Assertion

Юникод-сокрытие доставило инструкцию модели в восьми случаях из восьми, без единого механизма повторного одобрения. Кампания ведёт себя безобидно ровно три вызова, прежде чем искать ключи доступа. Подмена уже одобренного пакета оставалась незамеченной около полутора недель.

## Visual

1. **Юникод-сокрытие, 8 из 8.** Невидимые человеку юникод-символы спрятали инструкцию в описании инструмента (Rashidi, arXiv:2607.05744) — модель получала её в 8 из 8 попыток, ни разу не включив повторное одобрение. Узнали по контролируемому эксперименту: фильтр по тексту описания дал 0 ложных срабатываний на 25 безобидных описаниях — фильтр здесь ни при чём, подводит сама архитектура доверия по имени.
2. **Кампания Deadbugz, три вызова в запасе.** Сервер, распространённый через 23 правки на GitHub за 74 минуты, вёл себя безобидно ровно три вызова — и только потом начинал искать SSH-ключи и учётные данные. Нашли исследователи безопасности, разбирая опубликованные серверы, не команда, которая его поставила: порог в три вызова рассчитан именно на то, чтобы пройти обычную проверку «попробовал — работает».
3. **`postmark-mcp`, полторы недели тишины.** Уже одобренный пакет получил вредоносный код при обычном обновлении: каждое отправленное письмо тайно копировалось на адрес атакующего. Около полутора недель (17–29.09.2025) это оставалось незамеченным — заметили саму рассылку, после чего пакет сняли с npm.

> Фиксируйте версию сервера. Перечитывайте изменения при обновлении. Одобрение — не решённый вопрос навсегда.

## Speaker notes

Три факта, каждый острее предыдущего: что случилось и как об этом узнали.

Контролируемый эксперимент, не анекдот: юникод-сокрытие инструкции в описании инструмента доставило её модели в восьми случаях из восьми, на трёх разных независимых серверных библиотеках. Ни разу это не вызвало какого-либо механизма повторного одобрения. При этом тот же фильтр по строковому совпадению не дал ни одного ложного срабатывания на контрольном наборе из двадцати пяти безобидных описаний — значит, причина лежит в самой архитектуре доверия по имени, не в недокалиброванном фильтре.

Кампания, спроектированная на обход ручной проверки: сервер, распространённый через двадцать три запроса на внесение правок за семьдесят четыре минуты с одного аккаунта, ведёт себя безобидно ровно три вызова — порог специально выше, чем глубина обычной ручной проверки, достаточно, чтобы пройти обычное «попробовал, вроде работает», — и лишь затем переключается на поиск ключей доступа.

И реальный, тихий инцидент: вредоносный код попал в обновление уже одобренного пакета. Обновление пакета само по себе обычное, ожидаемое действие — подмена вошла в его состав, отдельным заметным шагом она не стала. Backdoor появился в обновлении пакета недели спустя после первого одобрения, скрытая копия каждого отправляемого письма уходила на адрес атакующего без единого взлома, и около полутора недель это оставалось незамеченным, пока рассылку не заметили и пакет не сняли с npm.

Фиксируйте версию сервера. Перечитывайте изменения при обновлении. Одобрение — не решённый вопрос навсегда.

Если спросят про детали юникод-эксперимента: использован специальный диапазон символов, который терминал и редактор кода отображают как пустоту, но который целиком доходит до токенизатора модели — человек, читающий описание инструмента перед одобрением, физически не видит того, что видит модель.

Если спросят, почему порог именно три вызова у кампании с подменой: это специально выше, чем глубина обычной ручной проверки перед доверием — рассчитано на то, чтобы пройти типичный тест-прогон «попробовал — вроде нормально».

Если спросят про письма подробнее: подмена произошла через обновление самого пакета неделями позже первоначального одобрения, без заметного события — ни новое разрешение не запрашивалось, ни предупреждение не показывалось. Активный период скрытого копирования — около полутора недель, не дольше: пакет сняли с npm, когда рассылку заметили.
