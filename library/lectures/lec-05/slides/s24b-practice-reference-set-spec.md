# Visible content

## Title bar
Эталонный набор — как проверять ответы ИИ так же, как проверяют код

## Body
[что это → механизм → с ИИ и без ИИ → где не работает]

**ЧТО ЭТО**

Небольшая коллекция реальных случаев, для каждого из которых заранее записано, какой ответ считается приемлемым. По сути те же тесты, только проверяется не код, а ответ модели. Собирают его **из настоящих обращений, а не из придуманных**.

**МЕХАНИЗМ**

1. Набор живёт **рядом с продуктом** и меняется вместе с ним, а не лежит отдельным документом.
2. Проверка запускается сама, вместе с обычными тестами, и так же **останавливает выпуск**, а не пишет предупреждение в журнал.
3. Каждый случившийся сбой возвращается в набор отдельным случаем — однажды пойманная ошибка **не повторяется молча**.
4. Начинают с пяти-десяти случаев и растят набор дальше; готовые инструменты для этого есть.

[Подписанная схема справа: «Требование назначают заранее — по цене ошибки» — обычный запрос: права почти всегда · отказ по правилам безопасности: каждый раз, без исключений · ответ с юридическим последствием: не доверяют модели — жёсткое правило поверх. Подпись: «последняя строка — не порог, а отказ от инструмента»]

**С ИИ И БЕЗ ИИ**

| БЕЗ ИИ — обычные тесты кода | С ИИ — ответ каждый раз другой |
|---|---|
| Ответ либо совпал с ожидаемым, либо нет, и повторный прогон даёт тот же результат. Порог один: всё зелёное. | Совпадения по буквам не бывает, поэтому результат — **доля** пройденных случаев, проверку повторяют, а требование ставят с запасом на разброс. |

[Gold callout — ГДЕ НЕ РАБОТАЕТ]
**Набор, который всегда зелёный, ничего не измеряет**, а как только его прохождение становится целью команды, он перестаёт быть мерой. И требование выше точности измерителя измеряет измеритель: если ответы оценивает модель, согласная с людьми в 85% случаев, планка в 95% бессмысленна.

## Speaker notes

Это прямой перенос дисциплины прошлой лекции — теста, написанного до кода. Там тест говорит, что значит «работает», и говорит это раньше результата. Здесь то же, только проверяется ответ модели.

Что стоит проговорить про сбор набора. Источник примера обязателен и обязательно реальный: рекомендация начинать с пяти-десяти настоящих рабочих примеров, а не выдуманных, — то же требование «реальное прошлое, а не правдоподобное», которое мы применяли к интервью. Придуманный пример проверяет воображение команды, а не продукт. Практическое следствие: набор нельзя написать за один присест в начале проекта — он растёт из эксплуатации, и по числу случаев, пришедших из реальных сбоев, видно, живой он или декоративный.

Про шкалу требований. Три строки на слайде выглядят как три порога, но третья строка — не порог. Это отказ от инструмента: ответ с юридическим последствием не отдают модели вообще, поверх неё ставят детерминированное правило. Различать это важно, иначе шкала читается как «просто поставьте планку повыше».

Чем это физически исполняется, если спросят. Есть промышленные инструменты, встраивающиеся в конвейер сборки: promptfoo останавливает сборку кодом возврата при падении балла ниже порога; штатная проверка в Claude Code прогоняет случаи трижды, а не один раз, так что разброс виден сразу; DeepEval запускается обычным прогоном тестов, и отдельный шаг заводить не нужно. Единого термина для одной строки набора нет — в разных инструментах это goldens, examples, test cases, samples, и искать общий стандарт бессмысленно.

Что здесь от обычных тестов, а что новое. В тестах кода ответ либо совпал с ожидаемым, либо нет, и повторный прогон даст то же самое. У модели совпадения по буквам не бывает, поэтому результат — доля пройденных случаев, проверку повторяют, а требование ставят с запасом на разброс.

И граница, ради которой карточка вообще имеет право стоять рядом с разбором провалов. Зелёный набор — не доказательство. Насыщение: всегда зелёный набор ничего не измеряет. Подгонка под набор: как только прохождение становится целью, мера перестаёт быть мерой. Разброс: инференс модели недетерминирован даже при нулевой температуре, расхождение между одинаковыми прогонами доходит до пятнадцати процентных пунктов. И надёжность измерителя: модель-судья согласуется с людьми примерно на восьмидесяти пяти процентах — на уровне, на котором люди согласуются между собой.
