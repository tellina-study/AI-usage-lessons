# Протоколы встреч — разбор 2

## Assertion

Начинайте с простейшего варианта, усложняйте только когда требование не закрыть иначе

## Visual

Схема: «протокол» → «извлечь поручение» → «вызвать API таск-трекера» →
«создать задачу» → «проверить, что создалась корректно». Внизу — строка:
«разовый вызов → RAG → агент — каждый шаг оправдан требованием, не модой».
Под ней — полоса «Разовый вызов → RAG → Агент» с подписью-осью «ступени
архитектуры», активный шаг — Агент.

## Speaker notes

Появилось действие во внешней системе: нужно вызвать API таск-трекера,
создать задачи, возможно проверить, что они создались корректно, с
правильным исполнителем и сроком. Один вызов модели или даже поиск по
базе такое не закрывают — нужен workflow или полноценный агент, который
вызывает внешний инструмент и проверяет результат вызова. Смотрите, что
произошло за три шага: сначала разовый вызов, потому что весь вход
помещался в контекст. Потом RAG, потому что база выросла и понадобился
поиск по произвольному запросу. Потом агент, потому что появилось
действие во внешней системе. Архитектурный выбор двигали конкретные
новые требования, а не мода на технологию. Начинайте с простейшего
варианта, который решает текущую задачу, и усложняйте только тогда,
когда появляется требование, которое простой вариант закрыть физически
не может. Не наоборот.
