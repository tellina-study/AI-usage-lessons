## 3. Порядок фаз (что/как/где/когда)

Правка идёт **поверх готовой лекции**, не с нуля — применяется §11a
`tools/lecture-production/README.md`: правка главы/раздела → регенерация слайдов ТОЛЬКО этого
раздела → согласование → и только в конце полная пересборка деки целиком.

### Фаза 1 — спайк: deckkit на одном разделе (блок T, разведка)

**Что:** перед тем как переписывать весь build-скрипт, проверить на **одном разделе** (например
Раздел 1, s06-s13), можно ли подключить deckkit-примитивы и каталог форм к существующим
`slides/*.md`, не переписывая вручную всю логику `build_lec11.py`/`build_lec11_part2.py` с нуля.
**Как:** `presentation-designer` + `/build-deck`, пробный прогон на 7-8 слайдах.
**Где:** `library/lectures/lec-11/rendered/`.
**Когда:** первым шагом — остальные фазы блока K зависят от результата.
**Выход:** либо «миграция — механическая, переносим остальное», либо «миграция требует
переписать слайды целиком» — оба исхода докладываются до продолжения, не предполагаются заранее.

### Фаза 2 — полная миграция деки на deckkit (блок T)

**Что:** перевести сборку всех 41 слайдов на deckkit по результату спайка.
**Как:** `presentation-designer`.
**Где:** `library/lectures/lec-11/rendered/build_lec11*.py` → новый deckkit-based build.
**Когда:** после Фазы 1, до блока K (без неё 15pt-пол и 33 формы неприменимы).

### Фаза 3 — повествование: построчный аудит §1–§3 + редизайн keystone + реестр (блок N)

- Построчная проверка §1 (уже есть диагноз — не соответствует), §2.1–§2.7, §3 на формат
  «термин → данные → как получают → решение → без AI → примеры» (`stroenie-i-povestvovanie.md`
  §3, шаг 1). Править только там, где реально отсутствует общее описание стадии до примера —
  не переписывать разделы, которые уже соответствуют.
- Редизайн `s05-keystone-two-models.md`: два столбца → два ряда (ряд 1 — измеренная тройка на
  материале отрасли discrete/process, ряд 2 — перенос на одном слайде) + строка вывода. Контент
  (цифры 78%/5,5%/95%, адрес оси) сохраняется, меняется раскладка.

## 5. Roast / открытые риски

1. **Фаза 1 (спайк) может показать, что deckkit-миграция дороже, чем выглядит.** Если
   миграция требует переписывать содержание слайдов (не только обёртку рендера) — это меняет
   оценку всего цикла, и об этом нужно доложить владельцу ДО Фазы 2, не после.
2. **Фазы 3 и 5 правят одни и те же файлы (`slides/*.md`) в разное время** — риск конфликта,
   если параллелить с Фазой 4. Решение: Фаза 4 трогает только видимый текст минут/методологии
   (узкий scope), Фаза 3 — только структуру/контент; оркестратор проверяет diff перед Фазой 5,
   чтобы не потерять ничью правку.
3. **Блок N (повествование) по §2-§3 не аудирован построчно** — диагноз «не соответствует»
   пока доказан только для §1. Фаза 3 начинается с чтения, не с предрешённой правки.
4. **Разбиение на PR.** Рекомендация: минимум 2 PR в рамках этого issue — (а) Фазы 1-2 (тулинг,
   самый тяжёлый diff по риску регрессии рендера) отдельно от (б) Фаз 3-8 (контент+форма+
   редактура+метрики). Если Фаза 1 покажет, что миграция тривиальна — можно объединить в один PR,
   решение принимается по факту результата спайка, не заранее.
