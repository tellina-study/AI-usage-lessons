# Протоколы встреч

## Assertion

«Поручения из протоколов мы всё равно руками переносим в таск-трекер...»

## Visual

Карточка-цитата. Рядом — иконка таск-трекера с ручным вводом задачи.
Справа — вопрос: «Меняет ли это архитектуру ещё раз?»

## Visual — цитата

«Спасибо за поиск по протоколам, реально экономит время перед ретро. Но
вот что заметила: поручения из протоколов мы всё равно руками переносим
в YouTrack — открываем протокол, читаем, что нашла система, заводим
карточки, проставляем исполнителя и срок. У YouTrack, я узнавала, открытый
REST API, задачу можно создать одним вызовом. Прошлась по майским
протоколам вчера вечером — примерно половина поручений так и висит без
исполнителя, руки не дошли перенести. Отдельно хотела спросить про цвет
тегов в трекере, но это, наверное, к админу инструмента».

## Speaker notes

Зачитайте реплику целиком. Прямой сигнал, не выделен особо: поручения из
протоколов система уже находит, но их всё равно вручную переносят в
таск-трекер одно за другим, и половина поручений из майских протоколов
до сих пор без исполнителя. Косвенный сигнал здесь — ключевой для этого
шага разбора, проговорите явно: наличие открытого REST API у YouTrack —
это именно то, что делает следующий архитектурный шаг (агент, вызывающий
API таск-трекера) технически дешёвым, а не гипотетическим. Без открытого
API пришлось бы городить что-то через экспорт-импорт или писать
интеграцию с нуля. Цвет тегов в трекере — шум-двойник: тоже про
таск-трекер, но чисто косметический вопрос, не влияет на архитектуру.
Вопрос в зал: меняет ли это архитектуру ещё раз? Что здесь появилось
нового по сравнению с поиском по базе, о котором мы только что говорили
минуту назад? Кто передумал — и, что важнее самого факта смены мнения,
почему именно эта деталь заставила вас пересмотреть архитектуру, а не
просто добавить ещё один шаг к прежнему решению? При разборе спросите:
какие факты из реплики повлияли на ваш выбор, а какие нет?
