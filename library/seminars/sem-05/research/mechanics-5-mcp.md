# Механика подключения MCP — вход для автора раздела

Этот документ — рабочий справочник, не готовый слайд. `stage-5-mcp.md` уже разобрал провалы,
права и риски подключения MCP (CVE, эксфильтрация, «подключён≠работает» как контринтуитивный
поворот) — здесь эти выводы **не повторяются**, кроме случаев, где механика и отладка делят один
факт (например, статус `✔ Connected` — это одновременно механика вывода команды и материал для
блока отладки; здесь разбирается сам механизм показа статуса, а не то, что из него неверно
заключает пользователь — это уже сделано в `stage-5-mcp.md`).

**Методология проверки.** Каждое утверждение о поведении продукта получено одним из трёх способов:
(1) прямой `curl` markdown-версии страницы официальной документации
(`https://code.claude.com/docs/en/<page>.md` — рабочий URL, отдаёт чистый markdown) и построчное
чтение раздела; (2) собственный `grep`/разбор HTML-версии той же страницы, когда markdown-версия
через какой-то путь (например, инструмент выборки контента) обрезала раздел до summary — тогда
источником берётся именно `curl`, а не пересказ; (3) существующий каталог реальных инцидентов этого
же проекта, `notes/mcp-limitations.md`. Обращение к документации — **2026-09-27**, тем же днём,
когда собирается этот документ. Явного баннера «обновлено: …» ни одна страница не показывает, но
текст ссылается на конкретные версии продукта до **v2.1.283** включительно — значит, содержание
актуально по крайней мере для этой линии версий.

## 1. Как подключается — способы и области видимости

### 1.1. Два способа, один и тот же результат

`claude mcp add` — не отдельный механизм, а команда, которая **пишет** конфигурацию в один из двух
файлов (см. §1.2) и, для проектной области, дополнительно требует подтверждения при следующем
запуске. Второй способ — написать ту же запись руками в `.mcp.json`. Документация прямо называет
этот путь равноправным для проектной области: **"It's the one most worth writing by hand because
it's checked into the repository, where it doubles as configuration-as-code for your team."**
(`mcp-quickstart.md`, раздел «Edit .mcp.json directly», обращение 2026-09-27). Разница не в
результате (файл на диске идентичен), а в том, что команда сразу проверяет синтаксис и печатает
подтверждение, а ручная правка — нет: **"Claude Code reads `.mcp.json` at startup"**, ошибку в
JSON вы узнаете только на следующем запуске.

Третий путь, для JSON-конфигурации целиком — `claude mcp add-json <name> '<json>'`:

```bash
# HTTP-сервер из JSON одной строкой
claude mcp add-json weather-api '{"type":"http","url":"https://api.weather.com/mcp","headers":{"Authorization":"Bearer token"}}'

# stdio-сервер из JSON одной строкой
claude mcp add-json local-weather '{"type":"stdio","command":"/path/to/weather-cli","args":["--api-key","abc123"],"env":{"CACHE_DIR":"/tmp"}}'
```

(`mcp.md`, раздел «Add MCP servers from JSON configuration», обращение 2026-09-27).

### 1.2. Файлы — их ровно два, и один из них не тот, что можно подумать

| Область | Файл | Кто видит |
|---|---|---|
| `local` (по умолчанию) | `~/.claude.json`, под записью конкретного проекта | Только вы, только этот проект |
| `project` | `.mcp.json` **в корне репозитория** | Все, кто клонирует репозиторий |
| `user` | `~/.claude.json`, под верхнеключом `mcpServers` | Только вы, все ваши проекты |

Источник: `mcp-quickstart.md`, таблица «Find your configuration on disk», обращение 2026-09-27.
Дословно про частую ошибку места: **"Claude Code doesn't read paths such as
`~/.claude/.mcp.json`, `~/.claude/config/mcp.json`, `~/.claude/mcp.json`"** — проектный файл лежит
**в корне репозитория**, а не в `.claude/`, и это отдельно подтверждено таблицей типовых причин
отказа: **"MCP servers in `.mcp.json` never load → File is under `.claude/`, or its servers sit
under a top-level `servers` key, as in VS Code's `mcp.json`, instead of `mcpServers`"**
(`debug-your-config.md`, обращение 2026-09-27).

### 1.3. Что коммитится, а что нет — и что произойдёт при конфликте имён

**Коммитится только `.mcp.json`** (область `project`) — дословно: **"Commit `.mcp.json` to
version control. Teammates who clone the repository and start Claude Code see a prompt to approve
the server, then it connects for them too."** `local` и `user` живут в `~/.claude.json` — файле
вне репозитория, секреты туда не попадают вместе с кодом просто потому, что файл физически не в
дереве git.

**Приоритет при конфликте имён** (от высшего к низшему, `mcp.md`, раздел «Scope hierarchy and
precedence»): `local` → `project` → `user` → сервер из плагина → коннектор claude.ai. Отдельно,
начиная с v2.1.259, поверх всех этих пяти уровней стоит `managedMcpServers` — настройка
организации, которая **побеждает** даже локальную область. Механика разрешения конфликта — не
слияние полей, а выбор целой записи целиком: **"When the same server is defined in more than one
place, Claude Code connects to it once, using the definition from the highest-precedence source.
The entire server entry from that source is used; fields are not merged across scopes."** То есть
если в `local` у сервера `github` не указан `env`, а в `project` указан — при конфликте имён
победит **вся** запись `local`, включая отсутствие `env`, а не гибрид «URL из одной, ключ из
другой». Совпадение имени в трёх изменяемых пользователем областях проверяется **по имени**;
совпадение с плагином или коннектором claude.ai — **по эндпойнту** (URL/команда), с точным правилом
эквивалентности: **"Two URL spellings count as the same endpoint when they differ only in the
letter case of the scheme or host, the scheme's default port... or a trailing slash."**

Отдельное предупреждение именно про этот случай — **не про потерю данных, а про повторную
авторизацию**: **"Claude Code stores OAuth sign-ins per endpoint, so when you authenticate the
definition that loads in one project, you still need to sign in separately in a project where a
different definition loads."**

### 1.4. Транспорты — кто и что реально исполняет на вашей машине

Три варианта, и разница именно в том, **что физически происходит на машине**, а не только в
синтаксисе:

- **`stdio`** — Claude Code запускает **локальный процесс**. Поле `command` — не декларация, а
  **исполняемая команда**: `claude mcp add playwright -- npx -y @playwright/mcp@latest` в момент
  подключения не проверяет пакет заранее, оно буквально то, что будет запущено при старте
  сессии. Документация формулирует это отдельно как повод для проверки: **"For stdio servers, run
  the configured command directly in your terminal to see the underlying error"** — если команда,
  которая лежит в конфиге, при прямом запуске в терминале делает что-то не то, то ровно то же самое
  она сделает и запущенная Claude Code, только без видимого вывода.
- **`http`** — рекомендованный способ для удалённых серверов, поддерживает OAuth 2.0.
- **`sse`** — задокументирован явно как устаревший: **"The SSE (Server-Sent Events) transport is
  deprecated. Use HTTP servers instead, where available."**
- **`websocket`** (через `add-json`) — постоянное двустороннее соединение; отдельная деталь для
  блока проверки (§3): такие серверы **не показываются** в `claude mcp list` вовсе, только в
  `claude mcp get <name>` или `/mcp`.

Разделитель `--` в команде `claude mcp add` — не синтаксический украшательство, а граница
парсинга: **"Everything after the `--` separator is the command Claude Code runs to start the
server."** Пропуск `--` — частая, задокументированная причина того, что реально запускается не то,
что вы думаете: **"If the command shown differs from what you typed, you likely omitted the `--`
separator before the server command."**

### 1.5. Секреты — синтаксис подстановки и то, чего он не решает целиком

Подтверждённый синтаксис (`mcp.md`, раздел «Environment variable expansion in `.mcp.json`»):

```
${VAR}            # подстановка значения переменной окружения
${VAR:-default}   # подстановка VAR, если задана, иначе default
```

Подставляется в пяти местах: `command`, `args`, `env`, `url`, `headers`. Если переменная не
задана и нет `:-default` — конфигурация всё равно загрузится, но с предупреждением: **"Claude Code
reports a missing-variable warning for that server in `claude mcp list` output and uses the
unexpanded `${VAR}` text as-is."**

Отдельная, менее очевидная защита — **для удалённых серверов** Claude Code читает часть переменных
окружения как **пустые**, даже если они реально заданы: **"In a remote server's `url` and
`headers`, Claude Code reads credential variables from your environment as empty rather than
expanding them."** Список триггеров — не фиксированный перечень имён, а паттерн: любое имя с
`TOKEN`, `SECRET`, `PASSWORD`, `KEY` или `AUTH` (без учёта регистра), плюс отдельно поимённо
`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `AWS_BEARER_TOKEN_BEDROCK`, `HTTPS_PROXY`,
`NPM_TOKEN` и другие. Смысл — не дать `.mcp.json` из чужого репозитория или плагина утащить
**ваши собственные** учётные данные Claude Code на сторонний сервер. Обходной путь для легитимного
секрета с «плохим» именем — задокументирован явно: **"copy it into a variable with a name of your
own and reference that name instead"**. Отдельная диагностическая строка для этого случая:
**"When a remote server's `url` or `headers` references a covered variable you have set, Claude
Code names it in a debug-log line. To read the line, run `claude --debug-file
/tmp/claude-debug.log` and search that file for `never expanded toward a remote server`."** — эта
конкретная строка идёт в блок отладки (§4).

**Важная оговорка про историческую находку `stage-5-mcp.md` (п.6 резюме).** Официально подтверждён
и сам факт, и версия фикса: **"The `/mcp` detail view shows references this way in Claude Code
v2.1.268 or later"** — то есть с этой версии `/mcp`, `claude mcp list` и `claude mcp get`
показывают **имя** ссылки `${VAR}`, а не резолвленное значение, ни в командной строке, ни в URL. До
этой версии секрет, подставленный из окружения, отображался диагностическими командами буквально —
то есть тот самый баг, о котором уже пишет `stage-5-mcp.md`, на сегодня (2026-09-27) официально
подтверждён и как факт истории, и как факт исправления.

### 1.6. Что реально изменилось к сентябрю 2026 — не выдумано, три конкретных пункта

- **Клиентский runtime.** Claude Code различает два «клиента» MCP-протокола: v1 (MCP TypeScript SDK
  1.x) и v2 (SDK 2.0, добавляет ревизию протокола `2026-07-28`). v2 становится дефолтом «в сессиях,
  где не запрашиваются feature flags, начиная с Claude Code v2.1.274», иначе — с v2.1.232. На
  практике для механики подключения из этого важно одно: **v2 сам спрашивает HTTP-сервер, поддерживает
  ли он новую ревизию**, а для stdio-серверов такой опрос нужно включать явно переменной
  `MCP_PROTOCOL_NEGOTIATION=auto` (`mcp.md`, раздел «MCP client runtimes»).
- **Кеш обнаружения инструментов.** Начиная с v2.1.221, ранее подключавшийся HTTP/SSE-сервер может
  показывать статус `cached 2h ago · connects on first use · 5 tools` — это означает, что список
  инструментов взят из **сохранённого прошлой сессией кеша**, а не из живого соединения; реальное
  подключение произойдёт при первом фактическом вызове инструмента этого сервера, не при старте.
  До v2.1.238 кеш был включён по умолчанию; сейчас — выключен, если не включён постепенным
  роллаутом (`MCP_DISCOVERY_CACHE=1`/`0` — явное переключение).
- **Официальный пример GitHub-сервера сменил транспорт.** Свежий официальный пример подключения
  GitHub теперь — не локальный `npx @modelcontextprotocol/server-github` (как в целевом решении
  этого раздела курса, `.mcp.json` из §A.7 `section-3-mcp.md`), а **удалённый HTTP-сервер** от
  самого GitHub: `claude mcp add --transport http github https://api.githubcopilot.com/mcp/
  --header "Authorization: Bearer YOUR_GITHUB_PAT"`. Это не делает решение раздела курса неверным
  (`stdio`-вариант документирован и поддерживается как один из четырёх официальных способов), но
  стоит явно проговорить на занятии как живой пример того, что «официальный путь» для одного и
  того же провайдера может со временем смениться с одного транспорта на другой.

## 2. Что происходит в момент подключения и что попадает в контекст

### 2.1. Обнаружение инструментов — кто кого спрашивает и когда

После того как транспортное соединение установлено, Claude Code сам, не по запросу модели,
отправляет серверу запросы обнаружения возможностей — `tools/list`, `prompts/list`,
`resources/list` (`mcp.md`, раздел «Failed discovery requests»). Если запрос обнаружения не
удался по временной причине (сетевая ошибка, ошибка сервера) — до трёх повторов с короткой
задержкой; ошибки авторизации, `4xx` и таймауты запроса — **не** повторяются. Если сервер потом
присылает уведомление `list_changed` (сервер сам объявляет об изменении набора инструментов) —
Claude Code обновляет список **без** переподключения; при неудаче обновления — сохраняется
**прежний** список, а не пустой (это изменилось в v2.1.214 — раньше временная ошибка при
обновлении **стирала** список до пустого).

### 2.2. Имена, которые видит модель

Формат: **`mcp__<server-name>__<tool-name>`**, где любой символ вне `A-Z`, `a-z`, `0-9`, `_`, `-`
заменяется на `_`. Для инструмента `query` сервера `database-tools` модель видит
`mcp__database-tools__query`. Для сервера, поставляемого плагином — более длинная форма:
`mcp__plugin_<plugin-name>_<server-name>__<tool-name>`, а сам сервер регистрируется под именем
`plugin:<plugin-name>:<server-name>`. Это не косметика — документация прямо указывает, где
понадобится именно это полное имя, а не человекочитаемое: **"Use this full name when referencing
the tool in permission rules, a skill's `allowed-tools` list, a subagent's `tools` field, or a
hook matcher."** Для семинара это прямое практическое следствие: если в промпте, хук-конфигурации
или списке инструментов субагента написать просто `query` — правило не сработает; нужен полный
префиксированный вид.

### 2.3. Цена в токенах — что попадает всегда, что по требованию, и почему базовая цифра курса требует уточнения

Здесь — самое важное расхождение с базовым исследованием курса, и его стоит подать честно, а не
спрятать. `stage-5-mcp.md` §1.3 приводит цифру **42 000–55 000 токенов на 93 определения
инструментов, ≈21% окна 200К** (getunblocked.com, «line-item autopsy», 2026) как базовую меру
цены подключения. Официальная документация, обращение 2026-09-27, описывает **другой** дефолтный
режим для актуальной версии продукта:

> **"Tool search keeps MCP context usage low by deferring tool definitions until Claude needs
> them. Only tool names and server instructions load at session start, so adding more MCP servers
> has minimal impact on your context window. Claude Code doesn't impose a fixed per-server tool
> cap; the practical limit is your context window budget."** (`mcp.md`, раздел «Scale with MCP
> tool search»)

То есть **сегодня, по умолчанию** (на моделях Sonnet 4.5, Haiku 4.5, Opus 4.5 и новее — именно
они поддерживают нужный для этого протокольный блок `tool_reference`), в контекст при старте
сессии попадают **не** полные схемы всех инструментов, а только их **имена** и **инструкции
сервера** (короткий текст, который сервер присылает о себе целиком, а не по одному на инструмент).
Полное определение конкретного инструмента подгружается моделью **по требованию**, отдельным
вызовом `ToolSearch`, только когда модель решает, что инструмент может понадобиться. Управляется
переменной `ENABLE_TOOL_SEARCH`:

| Значение | Поведение |
|---|---|
| *(не задано)* | Все инструменты откладываются и подгружаются по требованию (дефолт) |
| `true` | То же явно, независимо от отката для нестандартных площадок |
| `auto` | Пороговый режим: то, что откладывалось бы, грузится сразу, пока определения занимают **<10% окна**; при достижении 10% — откладывается всё |
| `auto:N` | Тот же порог, но `N`% вместо 10 |
| `false` | Все определения грузятся сразу, без отложенной загрузки |

Отдельно — обрезка длины: **"Claude Code truncates each tool description and each server's
instructions at 2,048 characters by default"**, изменяется переменной
`CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` (нужна v2.1.280+). И явное исключение для инструментов,
которые нужны буквально на каждом ходу: поле `alwaysLoad: true` в конфигурации конкретного сервера
принудительно грузит **все** его инструменты сразу, вне зависимости от `ENABLE_TOOL_SEARCH` —
документация честно называет цену такого исключения: **"each upfront tool consumes context that
would otherwise be available for your conversation."**

**Как это соотносится с базовой цифрой курса, а не отменяет её.** Цифра 42–55 тыс. токенов на 93
определения — это ровно та величина, которую даёт режим **без** отложенной загрузки (`false`,
либо один из перечисленных выше откатов — нестандартный `ANTHROPIC_BASE_URL`, площадка Microsoft
Foundry на Azure, старые модели на Google Cloud Agent Platform). На дефолтной, актуальной на день
обращения конфигурации именно **это** число при старте сессии не набирается — набираются только
имена и короткие инструкции; полная цена в духе «42–55 тыс.» может быть достигнута лишь если модель
за сессию реально дотянет через `ToolSearch` большинство определений — то есть это уже не
фиксированная цена подключения, а функция от того, сколько инструментов реально понадобилось.
**Практический вывод для слайда:** цифра базового исследования остаётся верной как порядок
величины *максимума*/*худшего случая* (и как факт для площадок, где поиск инструментов недоступен),
но не как гарантированная цена *каждого* подключения по умолчанию — это стоит явно сказать на
занятии, а не тихо заменить одну цифру другой.

Отдельная, не связанная с определениями инструментов ось расходов — **размер результата вызова**,
а не размер описания: предупреждение при выходе за 10 000 токенов, обрезка/вынос в файл по
умолчанию за 25 000 (`MAX_MCP_OUTPUT_TOKENS`), с отдельным путём для инструментов, которые сами
заявляют больший лимит через `_meta["anthropic/maxResultSizeChars"]`. Для слайда это стоит держать
явно отдельно от цены определений: одна ось — «сколько стоит, что сервер подключён», другая —
«сколько стоит один конкретный ответ инструмента».

### 2.4. Поток одобрения — что спрашивается и что запоминается

Два разных момента одобрения, которые легко перепутать:

1. **Одобрение самого сервера** (только для области `project`, один раз на проект). Первое
   появление сервера из `.mcp.json` требует диалога доверия: **"The first time Claude Code sees a
   project-scoped server, it asks you to approve it."** Это диалог **workspace trust**, не
   диалог конкретного инструмента — клонированный репозиторий не может сам себя одобрить: **"A
   cloned repository can't approve its own servers."** Явное отклонение — заносится в
   `disabledMcpjsonServers`; сбросить решение целиком — `claude mcp reset-project-choices`.
2. **Одобрение конкретного вызова инструмента** — стандартный permission-prompt, тот же механизм,
   что у `Bash`/`Edit`. Есть отдельная, специальная аннотация для авторов серверов —
   `_meta["anthropic/requiresUserInteraction"]: true` — которая делает подтверждение **обязательным
   на каждом вызове**, без опции «больше не спрашивать», причём даже в режимах `acceptEdits`,
   `auto` и `bypassPermissions`; в режиме `dontAsk` (никогда не спрашивает) такой вызов просто
   **отклоняется**, а не проходит тихо. Смысл аннотации — задокументирован прямо: **"Use this for
   tools whose permission prompt is itself the point, such as a consent or access-grant step where
   auto-approval would mean no human ever agreed."**

Отдельный, третий канал ввода — **elicitation**: сервер может запросить у пользователя
структурированные данные **посреди** выполнения задачи (форма или ссылка для перехода в браузер),
и диалог появляется автоматически, без предварительной настройки — механизм, полностью отдельный
от permission-prompt на вызов инструмента.

## 3. Как проверяется, что подключение живое

### 3.1. Таблица статусов — и что «✔ Connected» буквально означает

`claude mcp list` (из терминала) и `/mcp` (внутри сессии) показывают один и тот же набор статусов
(`mcp-quickstart.md`, таблица, обращение 2026-09-27):

| Статус | Значение |
|---|---|
| `✔ Connected` | Готов к использованию |
| `! Connected · tools fetch failed` | Соединение установлено, но список инструментов получить не удалось |
| `! Needs authentication` | Сервер доступен, но требует входа |
| `✘ Failed to connect` | Сервер не ответил |
| `✘ Connection error` | Попытка соединения выбросила ошибку |
| `⏸ Pending approval (run claude to approve)` | Проектный сервер, ещё не одобренный |
| `⊘ Disabled for this project (re-enable via /mcp)` | Отключён вручную для этого проекта |

Строка `! Connected · tools fetch failed` — не гипотетический случай, а буквально встроенный в сам
инструмент проверки статус: **транспорт может подняться, а обнаружение инструментов — отдельно
провалиться**, и продукт различает эти два факта в своём собственном выводе, а не только теоретически.
Это прямая механическая опора для тезиса «зелёный статус — утверждение о транспорте, а не о
работе» из `stage-5-mcp.md` — не интерпретация, а то, как устроен сам вывод команды.

Отдельная деталь про сами статусы: часть из них — **не** результат попытки подключения, а
**конфигурационное решение**, которое печатается без обращения к серверу вообще (`⏸ Pending
approval`, `✘ Rejected`, `⊘ Disabled`) — до версии v2.1.238 два последних всё же ходили на сервер
для health-check-а, что означало лишнюю задержку и сетевой запрос к серверу, который вы явно
отключили; сейчас — не ходят.

### 3.2. Минимальный безопасный вызов, который доказывает работу

Официальная рекомендация — не абстрактная проверка, а **явное упоминание сервера** в тексте
запроса: **"You don't normally need to name a server in your prompt, since Claude chooses relevant
tools on its own. Naming it here guarantees the demonstration goes through the new server rather
than another tool, such as web fetch, that could answer the same question."** Пример из
документации: *«Use the claude-code-docs server to look up what MCP\_TIMEOUT does»*. Признак, что
ответ реально пришёл от сервера, а не от общих знаний модели — **вызов инструмента в выводе
подписан именем сервера**: *«the tool call in Claude's output is labeled with the server name».*
Это прямой рецепт для демонстрации на занятии: не просто «спросить что-то», а спросить так, чтобы
без сомнений было видно, что ответ пришёл именно через подключённый инструмент, а не мимо него.

### 3.3. Где смотреть схемы инструментов конкретного сервера

`/mcp` внутри сессии — выбрать сервер из списка, откроется его карточка с числом инструментов и
списком; там же — статус `cached`, если применим (§1.6). Из терминала — `claude mcp get <name>`
показывает конфигурацию и, при ошибке, строку `Issue:` с деталями отказа. Отдельная деталь: **не
все транспорты видны в `claude mcp list`** — WebSocket-серверы туда вообще не попадают, только в
`claude mcp get`/`/mcp`.

## 4. Как отлаживается, когда «подключён, но не работает»

### 4.1. Типовые причины — таблица из документации, не реконструкция

Официальная таблица (`debug-your-config.md`, раздел «Check common causes», обращение 2026-09-27),
отфильтрованная до строк про MCP:

| Симптом | Причина | Что делать |
|---|---|---|
| Серверы из `.mcp.json` вообще не грузятся | Файл лежит в `.claude/` или ключ называется `servers`, а не `mcpServers` | Файл — в корне репозитория, ключ — `mcpServers` |
| Проектный сервер добавлен, но не появляется | Диалог одобрения был пропущен/отклонён | `/mcp` → одобрить |
| Сервер не стартует из части директорий | В `command`/`args` — относительный путь | Абсолютный путь для локальных скриптов; `npx`/`uvx` из `PATH` — можно оставить как есть |
| Сервер стартует без ожидаемых переменных окружения | Переменные не заданы в самой записи сервера и не входят в окружение, которое Claude Code передаёт stdio-серверам | Задавать `env` внутри записи конкретного сервера в `.mcp.json`, не надеяться на окружение запуска |

### 4.2. Штатные средства отладки

| Средство | Что делает |
|---|---|
| `claude --debug='mcp,startup'` | Включает подробный лог именно по категориям (список категорий через запятую); фильтр применяется только в форме через `=` |
| `claude --debug-file <path>` | То же самое, но пишет в конкретный файл — удобно для `tail -f`; неявно включает debug-режим |
| Лог по умолчанию | `~/.claude/debug/<session-id>.txt` — если сервер показывает 0 инструментов при статусе «подключён», официальная рекомендация буквальна: **"Run `claude --debug=mcp` and read the server's stderr in the debug log"** |
| `claude --safe-mode` | Сессия со всеми пользовательскими настройками отключёнными (включая **все** MCP-серверы, хуки, плагины) — если проблема исчезает здесь, причина в одном из этих слоёв, а не в ядре продукта |
| `CLAUDE_CONFIG_DIR=/tmp/clean claude` из директории без `.mcp.json`/`.claude` | Чистая комната — если баг воспроизводится и тут, причина вне вашей конфигурации |
| `claude mcp get <name>` | Точная строка `Issue:` с кодом HTTP-ошибки или текстом, который вернул сам сервер |
| Прямой запуск команды stdio-сервера в терминале | «The command starts and waits for input» → сервер сам исправен, проблема в разделителе `--` или конфиге; «The command errors» → сообщение прямо называет, чего не хватает (например, отсутствующий Node.js) |
| `curl -I <url>` для HTTP-сервера | `404`/`405` → сервер жив, путь неверный/метод не тот; `401`/`403` → нужна авторизация; отсутствие ответа → проблема сети/URL |

### 4.3. Таймауты — что именно зависает и на сколько

Отдельная, редко проговариваемая механика: у **старта** сервера и у **вызова** его инструмента —
два разных таймера. `MCP_TIMEOUT` — таймаут именно **старта** сервера, **30 секунд по умолчанию**;
превышение — типичная причина `✘ Failed to connect` при первой попытке (особенно на stdio, пока
`npx` скачивает пакет: **"The first check can show `✘ Failed to connect` while `npx` downloads the
package"**). Отдельный, гораздо более долгий таймер — на выполнение уже вызванного инструмента:
`MCP_TOOL_TIMEOUT`, по умолчанию **≈28 часов**; и третий, «таймаут простоя» —
`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` (5 минут для сетевых серверов, 30 минут для stdio по
умолчанию) — обрывает вызов, если сервер молчит, **не** дожидаясь общего 28-часового предела.

Переподключение — не одинаковое для всех транспортов. Удалённый сервер, оборвавшийся посреди
сессии, переподключается автоматически: **до пяти попыток с экспоненциальной задержкой**, начиная
с одной секунды. Первое подключение при временной ошибке (5xx, отказ соединения, таймаут) —
**до трёх повторов**. А вот stdio: **"Stdio servers are local processes, and Claude Code doesn't
reconnect them automatically."** — упавший локальный процесс не будет сам перезапущен, нужна новая
сессия или `Reconnect` из `/mcp`.

### 4.4. Наблюдение этого же проекта — зависший `claude mcp list`

`TODO-capture.md` (позиция 11) фиксирует честный отрицательный результат: попытка
`claude mcp list` в demo-окружении **без единого реально сконфигурированного сервера** зависла на
«Checking MCP server health…» и не ответила за 15 секунд. Это стоит показать на занятии именно как
наблюдение, а не как объяснённый механизм: документация описывает retry/backoff **для
сконфигурированных** серверов (§4.3), но не даёт прямого объяснения зависанию при их полном
отсутствии — вывод в §6 держит это честно как неподтверждённое. Практический совет для повторной
попытки на реальной машине: увеличить таймаут через `MCP_TIMEOUT=60000 claude` перед повтором и,
если зависание повторится, сразу включать `claude --debug-file` — так подтверждённая механика
(§4.2–4.3) не оставляет зависание немым.

### 4.5. Два реальных отказа этого проекта, задокументированных до сегодняшнего дня

Из `notes/mcp-limitations.md` — не гипотетические, а прожитые этим же проектом кейсы, ровно того
класса, который стоит показать как «так это выглядит вживую»:

- **[#49] OAuth-токен отзывается через 7 дней неактивности, пока статус показывает
  `✔ Connected`.** `workspace-mcp` — все вызовы Drive/Docs/Sheets/Slides возвращают `ACTION
  REQUIRED: Google Authentication Needed`, при этом `claude mcp list` продолжает показывать
  сервер как подключённый. Причина — OAuth-приложение в **Testing**-статусе Google Cloud Console,
  где `refresh_token` автоматически отзывается через 7 дней без активности. Это прямой живой
  пример разбора §3.1: транспорт (соединение до Google) жив, авторизация — мёртва, и статус
  различает это не идеально сразу же, но задокументированная официально механика (§3.1,
  `! Needs authentication` vs `✔ Connected`) объясняет, почему в принципе возможен разрыв между
  «зелёным» статусом списка и реальной работоспособностью.
- **[#86] `uvx workspace-mcp` вообще не стартует — регрессия непинованной транзитивной
  зависимости.** `claude mcp list` показывает `✗ Failed to connect`; причина видна только через
  Python-traceback при **прямом запуске команды из конфигурации в терминале** (`aiofile==3.10.0`
  собран без поля `Author` в метаданных wheel, транзитивная зависимость ломает импорт на старте) —
  ровно тот диагностический шаг, который официальная документация называет первым при статусе
  «не подключается» (§4.2, строка «прямой запуск stdio-команды»). Workaround — пин рабочей версии
  зависимости прямо в `.mcp.json` через `uvx --with aiofile==3.9.0`.

### 4.6. Пример отладочной последовательности — 5 шагов

1. **Подключить и проверить статус.** `claude mcp add ...` → `claude mcp list`. Если статус не
   `✔ Connected` сразу — не спешить чинить: для stdio первая проверка нормально может показать
   `✘ Failed to connect`, пока `npx`/`uvx` качает пакет (§4.3); повторить через несколько секунд.
2. **Минимальный именованный вызов** (§3.2) — попросить агента явно назвать сервер в задаче.
   Если вызов в выводе подписан именем сервера и вернул ожидаемый результат — сервер работает не
   только по транспорту, но и по факту.
3. **Если вызов не удался — посмотреть `claude mcp get <name>` и `/mcp`-карточку сервера**, строка
   `Issue:`. Код `401`/`403` — авторизация; `404`/`405` — неверный путь при живом сервере; пусто —
   сетевая проблема или неверный URL целиком.
4. **Прямой запуск.** Для stdio — вызвать ровно ту команду, что в `command`/`args`, напрямую в
   терминале (§4.2, §4.5 — оба реальных инцидента проекта нашлись именно так). Для HTTP —
   `curl -I <url>`.
5. **Если всё ещё неясно — включить лог.** `claude --debug-file /tmp/mcp-debug.log`, повторить
   попытку, затем `grep -i mcp /tmp/mcp-debug.log` — искать конкретные строки: `never expanded
   toward a remote server` (секрет заблокирован как учётные данные, §1.5), `Hook output does not
   start with {` (не про MCP, но похожий формат строки — для калибровки, чего ожидать в этом же
   логе), либо явный stderr самого сервера.

## 5. За границей области — на будущее

Явно не входит в это занятие (владелец: «только подключение»), но всплыло в исследовании и стоит
держать в очереди отдельно:

- **Авторство MCP-серверов** — `server instructions`, best practices для полей `_meta`
  (`anthropic/requiresUserInteraction`, `anthropic/maxResultSizeChars`), плагин
  `mcp-server-dev`, `/mcp-server-dev:build-mcp-server` — всё это адресовано автору сервера, не
  подключающему.
- **`claude mcp serve`** — Claude Code сам может выступить MCP-сервером для другого клиента; это
  превращает Claude Code из подключающего в подключаемого — обратная задача, не эта.
- **Протокол в целом** — v1/v2 клиентский runtime, ревизия `2026-07-28`, `list_changed`,
  каналы (`--channels`, push-сообщения от сервера в сессию) — глубокая механика протокола,
  разобранная в документации подробно, но избыточная для занятия про «подключил → работает».
- **Кастомная авторизация не через OAuth** (`headersHelper`, Kerberos/SSO/короткоживущие токены,
  ограничение OAuth-скоупов, CIMD вместо Dynamic Client Registration) — реальная механика, но
  редкий кейс корпоративной интеграции, не первое подключение с нуля.
- **`MAX_MCP_OUTPUT_TOKENS`/`anthropic/maxResultSizeChars`** — цена **результата** вызова, а не
  подключения; упомянуто в §2.3 одной строкой для полноты, разбор — отдельная, не в это занятие,
  тема (ближе к «эффективность работы с уже подключённым сервером»).

## 7. Чего я не смог подтвердить

- **Причина зависания `claude mcp list` при нуле сконфигурированных серверов** (§4.4). Официальная
  документация подробно описывает retry/backoff **для существующих** серверов, но не даёт прямого
  объяснения тому, что должно проверяться, когда серверов нет вовсе. Это честный пробел: наблюдение
  реальное (зафиксировано в `TODO-capture.md` этой же папки), причина — не найдена ни в
  документации, ни в каталоге лимитаций проекта.
- **Точная механика «Yes, и не спрашивать больше» именно для MCP-инструментов.** Официальная
  таблица поведения (`permissions.md`) явно перечисляет `Bash`, `Edit`/`Write`, `WebFetch`,
  `WebSearch`, но не даёт отдельной строки специально для обычного (не отмеченного
  `requiresUserInteraction`) MCP-инструмента — по общей логике префиксных правил (`mcp__server__tool`
  можно сохранить как правило разрешений) это, вероятно, работает аналогично `Bash`/сохранению
  правила на репозиторий, но это **вывод по аналогии, не цитата** — не выносить на слайд как
  факт без пометки.
- **Версия Claude Code, реально установленная в среде демонстрации курса.** Ни одна страница
  документации не показывает единый номер текущей версии; ссылки на версии в тексте (до v2.1.283
  включительно) задают только нижнюю границу актуальности контента на день обращения
  (2026-09-27), не точную версию на машине, где будет вестись занятие — перед показом стоит
  свериться с `claude --version` на реальной машине.
- **Живая досъёмка позиций №11–12 из `TODO-capture.md`** (`claude mcp add`/`list`, `/mcp`) — не
  выполнена в этой сессии по той же причине, что и в предыдущих документах этой папки: доступен
  только `Bash`, не интерактивная сессия Claude Code с реально подключаемым сервером.
- **Актуальность стдио-варианта `.mcp.json` из целевого решения раздела** (`@modelcontextprotocol/
  server-github` через `npx`) относительно нового официального примера через удалённый
  `api.githubcopilot.com/mcp/`. Оба задокументированы как поддерживаемые способы подключения к
  GitHub на день обращения — но не проверялось, устарел ли конкретно пакет
  `@modelcontextprotocol/server-github` или продолжает поддерживаться параллельно; это отдельный
  вопрос сопровождения демо-репозитория, не этого документа.
