## Раздел 4. Скиллы (11 мин) — Ступень 4

**Состояние репозитория.** Добавляется `.claude/skills/deploy/SKILL.md`:

```
signup-landing/
├── CLAUDE.md
├── AGENTS.md -> CLAUDE.md
├── DECISIONS.md
└── .claude/
    ├── settings.json
    └── skills/
        └── deploy/
            └── SKILL.md                # ← новое на этой ступени
```

**Сценарий-боль.** В `CLAUDE.md` за несколько недель накопилась процедура деплоя сайта на прод —
40 строк («собрать, прогнать тест формы, опубликовать на Cloudflare Pages, проверить прод-URL»),
нужных примерно раз в две недели, когда реально пора выкатывать изменения. Она грузится в контекст
**каждой** сессии, даже когда речь идёт про мелкий баг-фикс, никак не связанный с деплоем (прямой
сигнал ступени 4: «файл инструкций облагает налогом каждый запрос процедурой, которая нужна не
всегда»).

**Открытый вопрос классу (дословно).** «В `CLAUDE.md` этого сайта накопилась процедура деплоя на
40 строк, нужна раз в две недели. Она грузится в контекст каждой сессии, даже когда вы просто
чините баг в форме. Куда её вынести — и как сделать так, чтобы агент сам понял, когда её открыть?»

**Ожидаемые ответы зала.**

| Вариант | Разумен? | Где работает | Где ломается |
|---|---|---|---|
| «Оставлю в `CLAUDE.md` — вдруг понадобится» | Нет | Никогда не окупается | Ровно тот антипаттерн, который ступень называет по имени: постоянный налог на контекст независимо от релевантности |
| «Вынесу в отдельный файл, сошлюсь `@deploy-instructions.md`» | Частично | Организационно удобно | `@`-импорты **не экономят контекст** — импортированный файл всё равно грузится целиком при старте сессии (раздел 1); проблема налога не решена |
| «Заведу отдельный файл и буду сам напоминать агенту его прочитать» | Частично | Работает, пока не забыли | Требует, чтобы человек помнил каждый раз — не использует способность модели самой решить, когда это нужно |
| «Заведу скилл `.claude/skills/deploy/SKILL.md` с фронтматтером `description`» | Да (целевой ответ) | Всегда, при корректно написанном description | Ломается, если description расплывчатый — см. провал ниже |

**Что добавляем — предметно.** Минимальный скилл — директория с `SKILL.md`, обязательные поля
фронтматтера (источник: `07-skills.md`, §2): `name` (≤64 символа, kebab-case), `description`
(не пусто, ≤1024 символа, обязано содержать и «что делает», и «когда использовать»). Три уровня
progressive disclosure с точными цифрами:

| Уровень | Когда грузится | Стоимость | Содержимое |
|---|---|---|---|
| 1. Метаданные | Всегда, при старте сессии | ≈100 токенов | `name` + `description` |
| 2. Инструкции | При срабатывании | <5000 токенов | тело `SKILL.md` |
| 3. Ресурсы/код | По требованию | 0, пока не открыт | вложенные файлы, скрипты |

Наш `deploy/SKILL.md` — конкретная процедура деплоя этого сайта, не абстрактный шаблон:

```markdown
---
name: deploy
description: Деплоит лендинг signup-landing на прод — сборка, smoke-тест формы, публикация,
  проверка прод-URL. Используй, когда пользователь просит задеплоить, выкатить или опубликовать
  сайт — не для обычных правок кода без деплоя.
---

# deploy

1. Собрать: `npm run build` (код выхода должен быть 0).
2. Прогнать smoke-тест формы: `npx playwright test` (должен быть зелёным).
3. Опубликовать: `wrangler pages deploy dist --project-name signup-landing`.
4. Открыть прод-URL, вручную отправить форму с валидными данными — заявка должна дойти.
5. Записать в `Tasks/<date>_<slug>/log.md`, что задеплоено, когда и какой командой.
```

Антипаттерн для контраста (официальный чек-лист, прямо запрещён): `«Helps with documents»`,
`«Processes data»` — модель выбирает скилл именно по `description` среди потенциально сотни
установленных, расплывчатая формулировка гарантирует несрабатывание.

**Слайды раздела.**
1. Блок кода: `deploy/SKILL.md` целиком.
2. Реальный вывод `head -5 .claude/skills/*/SKILL.md` по 13 скиллам этого курса — фронтматтер с
   `description` есть только у одного скилла из 13 (`pre-user-gate`), остальные 12 начинаются
   сразу с `# заголовок`.
3. Таблица-контраст `/skills`: `pre-user-gate: Pre-USER-GATE walkthrough — orchestrator
   self-review before presenting GATE to user. Reduces user feedback rounds.` против
   `build-deck: build-deck` (имя вместо описания-триггера).

**Что делать — рецепт.**
1. Создать `.claude/skills/deploy/SKILL.md` с содержимым из блока выше — фронтматтер обязан
   называть и «что делает», и «когда использовать» в одном `description`.
2. Если процедура деплоя раньше была записана текстом в `CLAUDE.md` — вырезать её оттуда, не
   дублировать в двух местах.
3. Проверка положительного срабатывания: в новой сессии попросить «задеплой сайт на прод» — агент
   должен открыть скилл сам, без явного `/deploy`.
4. Проверка отрицательного срабатывания: в новой сессии попросить починить мелкий баг в вёрстке —
   скилл открываться не должен (нерелевантный запрос — иначе description слишком широкий).
5. Живая проверка антипаттерна на своём же курсе: `head -5 .claude/skills/*/SKILL.md` — посчитать,
   у скольких скиллов есть фронтматтер с `description`; ноль или один из многих — типичный
   результат, не редкость.

**Провал.** Живая проверка на материале собственного курса: у 12 из 13 скиллов проекта нет
фронтматтера с `description` — они физически не могут сработать по смыслу запроса, только через
явный `/slash`-вызов. Источник: `07-skills.md`, §4.1. Второй слой (углубление, не просто «нет
триггера», а «даже сработавший скилл может навредить»): исследование skill-induced failures
(`arXiv:2608.11888`) нашло 307 подтверждённых случаев вреда от скиллов — 125 функциональных
провалов, из которых **68,8% (86/125)** — Task-Implementation Fault: «кажущиеся релевантными
скиллы заставляют агента реализовать требуемое поле, расчёт или формат вывода неправильно или
пропустить его вовсе»; 182 случая раздутия стоимости, до **+451%** токенов на задачу
(SWE-Skills-Bench). 3,5 мин.

**Критерий «здесь не нужно».** Нужно каждой сессии → это не скилл, это файл инструкций (ступень 1);
процедура одноразовая или почти никогда не повторяется в тех же деталях → дешевле один раз подробно
попросить, чем писать скилл заранее «на всякий случай» — официальная рекомендация: сначала пройти
задачу без скилла обычным промптом, решить о переиспользовании потом; правило недопустимо нарушить
никогда → это хук (ступень 3), а не скилл — скилл остаётся знанием, которое агент может учесть или
проигнорировать.

**База и нюанс.**
- **База (слайд):** «скилл — методичка в шкафу, которую снимают с полки только когда задача реально
  совпала с темой методички».
- **Нюанс (речь):** `description` как «поисковый запрос будущего себя» — конкретные ключевые слова +
  явный триггер-контекст, не «I can help you…»; скилл — исполняемый код и данные из чужого источника
  (аудит Snyk «ToxicSkills», 5 февраля 2026, 3984 скилла: 13,4% (534) с критической проблемой
  безопасности, 91% подтверждённых вредоносных образцов используют prompt injection).

## Раздел 5. MCP (13 мин) — Ступень 5

**Состояние репозитория.** К концу раздела 4 в `signup-landing/` уже есть `CLAUDE.md`, `AGENTS.md`,
`DECISIONS.md`, `.claude/settings.json`, `.claude/skills/deploy/SKILL.md`. Добавляется `.mcp.json`:

```
signup-landing/
├── CLAUDE.md
├── AGENTS.md -> CLAUDE.md
├── DECISIONS.md
├── .mcp.json                          # ← новое на этой ступени
└── .claude/
    ├── settings.json
    └── skills/
        └── deploy/
            └── SKILL.md
```

**Сценарий-боль.** Заказчик и сам разработчик теперь регулярно заводят задачи и баги как issue в
репозитории `signup-landing` на GitHub — не разово, а на каждой сессии агенту нужно посмотреть
открытые issue и подготовить черновик PR. Сейчас это делается вручную (копипаст ссылок) или
редкими вызовами `gh` через Bash, синтаксис которых агент не всегда помнит стабильно (ладдер-триггер
ступени 5: «нужен доступ к внешней системе»).

**Открытый вопрос классу (дословно).** «Агенту теперь регулярно нужно смотреть открытые issue в
репозитории `signup-landing` и готовить черновики PR. Вы почти готовы подключить официальный GitHub
MCP-сервер. Что вы проверяете до того, как это сделать?»

**Ожидаемые ответы зала.**

| Вариант | Разумен? | Где работает | Где ломается |
|---|---|---|---|
| «Ничего — это официальный сервер от GitHub, ему можно доверять» | Нет | Никогда как единственная проверка | Даже эталонные официальные серверы получают CVE: у собственного Filesystem MCP-сервера Anthropic — CVE-2025-53109/53110 («EscapeRoute», выход из песочницы) |
| «Проверю, сколько токенов это добавит в каждый запрос» | Да, частично | Всегда стоит проверять — измеримая, неочевидная стоимость | Сама по себе не закрывает риск безопасности — нужна вторая проверка (права доступа) |
| «Разрешу его сразу на все репозитории, чтобы не настраивать дважды» | Нет | Никогда | Это буквально повторяет реальную конфигурацию инцидента GitHub MCP heist — см. провал ниже |
| «Спрошу, не хватит ли обычной команды `gh` через Bash + проверю права доступа» | Да (целевой ответ) | Почти всегда как первый шаг | Перестаёт хватать, когда доступ реально нужен из нескольких клиентов/сессий одновременно с сохранением состояния |

**Что добавляем — предметно.** `.mcp.json` в корне репозитория (project-scope — коммитится,
ревьюится как код, источник: `05-mcp.md`, §2). Три примитива протокола и то, кто решает их
использовать (источник: `05-mcp.md`, §1): **инструменты (tools)** — решает модель; **ресурсы
(resources)** — решает хост (`@`-упоминание); **подсказки (prompts)** — решает человек (`/`-команда).
Перед подключением — измеримая стоимость контекста (источник: `05-mcp.md`, §3):

| Замер | Значение |
|---|---|
| Типичная связка из 5 серверов, без Tool Search | ≈55 000 токенов определений до начала работы |
| То же, с Tool Search (по умолчанию) | тот же объём минус более 85% |
| Реалистичная связка 5 серверов (`mcp-token-benchmark`) | 26 224 токена = 13,1% от окна 200К |
| Одно и то же действие («язык репозитория») CLI vs MCP | 1 365 против 44 026 токенов |

**Слайды раздела.**
1. Блок кода: `.mcp.json` — минимальный рабочий пример (`mcpServers` с одним сервером, только
   к репозиторию `signup-landing`, не ко всем приватным разом).
2. Снимок терминала: `claude mcp add` + `claude mcp list` → `✓ Connected`.
3. Снимок панели `/mcp` — число доступных инструментов.
4. Контрпример из этого же курса: `notes/mcp-limitations.md` — `workspace-mcp`, где
   `claude mcp list` продолжал показывать `✓ Connected`, пока сервер был фактически недоступен
   из-за непин-нутой транзитивной зависимости (`aiofile` 3.10.0) — тезис «подключён» ≠ «работает».

**Что делать — рецепт.**
1. Прежде чем подключать сервер — проверить, не хватит ли `gh issue list`/`gh pr create` через
   Bash (критерий «здесь не нужно» ниже); подключать MCP только если доступ нужен регулярно и из
   нескольких сессий.
2. Подключить с минимальными правами, ограничив область конкретным репозиторием, не всей
   организацией/всеми приватными репозиториями сразу: `claude mcp add github --scope project`
   (конкретные флаги — по официальной документации на момент подключения; здесь важен принцип
   «минимум прав», не точный синтаксис версии).
3. Закоммитить `.mcp.json` — проектная конфигурация ревьюится как код, а не живёт только в
   `local`-области одной машины.
4. Проверка: `claude mcp list` → `✓ Connected`; `/mcp` → инструменты реально перечислены, не
   ноль при заявленном подключении (это и есть класс проблемы «Connected, но не то же самое, что
   работает» — см. контрпример на слайде 4).
5. Дисциплина после подключения (не разовая, повторяющаяся): периодически перечитывать
   `.mcp.json` и `claude mcp list`, убирать неиспользуемые серверы — тот же принцип «минимальный
   набор», но как практика, а не решение один раз при подключении.

**Провал.** GitHub MCP — эксфильтрация приватных репозиториев (26.05.2025, Invariant Labs): агент
с одновременным доступом к чтению публичного репозитория и к приватным репозиториям пользователя
через один и тот же MCP-сервер прочитал скрытую инструкцию prompt injection в открытом issue,
собрал данные из приватных репозиториев (включая физический адрес и зарплату) и опубликовал их в
автоматически созданном публичном pull request. CVE не присвоен — это архитектурный риск
(«toxic agent flow»), не баг кода. Второй слой (углубление, объясняющая рамка): «смертельное трио»
(lethal trifecta, Simon Willison, 16.06.2025) — комбинация (1) доступа к приватным данным,
(2) обработки недоверенного внешнего контента и (3) канала отправки наружу делает утечку возможной
**без единой строчки эксплойт-кода**; та же схема — в независимой демонстрации Supabase MCP
(июль 2025, Willison/General Analysis): агент с сервисной ролью к БД прочитал вредоносный текст,
вложенный в тикет поддержки, и скопировал внутренние данные в ответ клиенту. Источник:
`05-mcp.md`, §4 и таблица «инциденты». 4,5 мин.

**Критерий «здесь не нужно».** Хватает обычной команды (`gh`/`psql`/`aws` через Bash) — задача
сводится к известному CLI-вызову; разовое или редкое действие, не повторяющийся доступ; снимок
данных на момент запуска скрипта достаточен, актуальность в реальном времени не критична; нет
потребности из нескольких разных клиентов одновременно (источник: `05-mcp.md`, таблица «MCP
оправдан / хватит скрипта»).

**База и нюанс.**
- **База (слайд):** «MCP — общий переходник к внешней системе (БД, трекер задач), чтобы не писать
  отдельную интеграцию под каждого клиента».
- **Нюанс (речь):** stdio-серверы берут личность вызывающего из окружения процесса, не из
  аргумента (который модель могла бы подделать); HTTP-серверы обязаны проходить полноценный
  OAuth-поток без сквозного проброса токена («запутанный заместитель», Atlassian
  CVE-2026-27826/27825); сканирования публичных реестров систематически находят 33–66%
  серверов с уязвимостями в зависимости от методики скана.

## Раздел 6. Субагенты (10 мин) — Ступень 6

**Состояние репозитория.** Добавляется `.claude/agents/diff-reviewer.md`:

**Сценарий-боль.** Третий раз за неделю фасилитатор просит ту же сессию, что писала правку
`src/validate.js`, честно перепроверить саму себя перед тем, как деплоить изменение на прод
«максимально придирчиво». Сессия старается быть adversarial к себе — но остаётся тем же контекстом
рассуждений, той же цепочкой решений, тем же слепым пятном, которое и породило возможную ошибку
(ладдер-триггер ступени 6: «повторяющаяся роль (ревью, разведка), которой не нужен общий контекст
с основной сессией»).

**Открытый вопрос классу (дословно).** «Вы третий раз за неделю просите ту же сессию, что писала
правку формы, перепроверить саму себя перед тем, как деплоить на прод. Она честно старается быть
придирчивой. Достаточно ли этого — и если нет, что именно нужно заменить?»

**Ожидаемые ответы зала.**

| Вариант | Разумен? | Где работает | Где ломается |
|---|---|---|---|
| «Достаточно, если явно попросить быть adversarial» | Нет | Никогда механически | Документация Claude Code формулирует условие независимости конкретно: ревьюер должен видеть только diff и критерии, **не рассуждения, которые привели к изменению** — тон не создаёт независимости |
| «Позову коллегу» | Да в команде | Хорошо, если коллега реально доступен | Курс явно адресует и соло-случай (наш разработчик работает один) — решение не должно зависеть от наличия второго человека |
| «Открою новую вкладку в том же чате» | Нет | Иллюзия разделения | Обычно та же цепочка контекста (context lineage) — независимость не достигается сменой вкладки |

**Что добавляем — предметно.** `.claude/agents/diff-reviewer.md` — markdown с YAML frontmatter
(источник: `08-subagents.md`, §1): `name`, `description` (это логика маршрутизации, а не
документация — по этому полю Claude решает, делегировать ли автоматически), опционально `tools`
(ограничение набора инструментов) и `model`. Пример, по образцу пары
`methodology-critic`/`fact-checker` этого же курса (§7 того же файла — оба явно называют, чем
**не** являются, и оба обязаны начинать ответ строкой вердикта):

```markdown
---
name: diff-reviewer
description: Независимый ревьюер diff'ов. Видит только сам diff и критерии приёмки, не рассуждения
  автора. Используй перед мержем любого нетривиального изменения. НЕ для методической критики
  текста — это отдельная роль.
tools: Read, Grep, Glob
---

# diff-reviewer

Ты не правишь код сам — только находишь проблемы. Начни ответ строкой:
`VERDICT: PASS | BLOCK`

Затем: что проверено (конкретно — какие файлы прочитаны), находки (что не так, где, почему важно).
Пустой список находок — валидный PASS.
```

Обратить внимание на поле `tools: Read, Grep, Glob` — явное ограничение без `Write`/`Edit`:
механическая, а не словесная защита от «критик случайно всё исправил сам» (курс отдельно фиксирует,
что ни один из 13 живых субагентов проекта `lessons-3bb49d40` этим полем не пользуется — редкая,
но именно поэтому наглядная деталь для демонстрации).

**Слайды раздела.**
1. Блок кода: `diff-reviewer.md` целиком.
2. Фрагмент реального diff по сайту (например, правка `src/validate.js`).
3. Ответ `diff-reviewer` на этот diff — начинается строкой `VERDICT:`, ссылается только на diff,
   не на историю чата, в которой изменение создавалось.

**Что делать — рецепт.**
1. Создать `.claude/agents/diff-reviewer.md` с содержимым из блока выше.
2. Ограничить `tools:` списком без `Write`/`Edit` (`Read, Grep, Glob`) — ревьюер находит проблемы,
   не чинит их сам.
3. Сделать небольшую правку в `signup-landing/` (например, в `src/validate.js`).
4. Явно вызвать `diff-reviewer` на этот diff отдельным запросом, не в том же диалоге, где правка
   создавалась — проверка: ответ начинается с `VERDICT: PASS` или `VERDICT: BLOCK`, раздел «что
   проверено» называет конкретные файлы, а не общую фразу «всё проверено».
5. Если `BLOCK` — исправить названные находки и запросить узкую перепроверку того же ревьюера, не
   полный повторный проход (лимит 2 круга — см. раздел 7).

**Провал.** MAST — таксономия отказов мультиагентных систем (Cemri, Pan и др.,
